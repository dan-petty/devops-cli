# Proposal

## Why

ConfigMap `devops-cli-config-sandbox` is the credential-free copy of the Service config that the planner run Job of #4003 mounts at `/config`, and #4147 records that no command renders it: `src/devops_cli/commands/k8s/stack_lifecycle.py:947:return render_active_devops_configmap(product)` renders only `devops-cli-config`, so a person copies the ConfigMap by hand, strips the credential keys, and the copy drifts from the active config at the next deploy.

## What Changes

- Add `drop_secret_named_keys` beside the masking walk at `src/devops_cli/security/sanitizer.py:502:if is_secret_parameter_name(str(key))`: it drops each dict entry whose key `is_secret_parameter_name` matches, at any depth of dicts and lists, and keeps every other key with its value.
- Add `CONST_K8S_DEVOPS_SANDBOX_CONFIGMAP` beside `src/devops_cli/config/constants.py:1204:CONST_K8S_DEVOPS_CONFIGMAP: Final[str] = "devops-cli-config"`.
- Add a keyword-only `drop_secret_keys` parameter to the two render functions, which drops the credential-named keys after the service block is set and before the refusal at `src/devops_cli/k8s/configmap.py:91:unknown = unknown_setting_keys(written)`, so a credential key of the template leaves the config instead of failing as an unknown setting.
- Add `render_active_devops_sandbox_configmap` beside the active render at `src/devops_cli/k8s/configmap.py:153:active_settings = settings if settings is not None else load_settings()`: it renders from the same template and active config, drops the credential keys, renames the ConfigMap and keeps the one data key at `src/devops_cli/k8s/configmap.py:16:_CONFIG_KEY = "devops-cli.yaml"`.
- Apply the sandbox ConfigMap on both deploy paths right after `src/devops_cli/commands/k8s/stack_lifecycle.py:1295:_apply_rendered(config_map, f"ConfigMap {CONST_K8S_DEVOPS_CONFIGMAP}", kubectl_ctx)`, delete it beside `src/devops_cli/commands/k8s/stack_lifecycle.py:1772:CONST_K8S_DEVOPS_CONFIGMAP,`, and name it in the dry runs at `src/devops_cli/commands/k8s/stack_lifecycle.py:1429:"config_map": (` and `src/devops_cli/commands/k8s/stack_lifecycle.py:1716:"config_map_delete": (`.
- Add the test case that parses the rendered manifest as `tests/k8s/test_k8s_configmap.py:61:inner = yaml.safe_load(doc["data"]["devops-cli.yaml"])` does, walks every key at any depth, names the credential keys of a hand-built config and asserts that the rendered one holds none.
- Update the deploy, Argo CD, teardown and dry-run cases for the second applied ConfigMap, including the payload list at `tests/commands/k8s/test_k8s.py:1610:_APPLY_STDIN = ["kubectl", "apply", "-f", "-", *_CONTEXT]`.
- Add the row of the sandbox ConfigMap to the table under `k8s/README.md:1099:### Homelab Values at Deploy Time`, and say that deploy-stack renders it with every credential-named key removed and that teardown-stack deletes it.
- Change no manifest: the run Job already mounts the name at `k8s/devops/roadmap-service/cronjob-planner-run.yaml:113:name: devops-cli-config-sandbox`, and the admission policy admits it at `k8s/devops/roadmap-service/admissionpolicy.yaml:144:(variables.planner && v.configMap.name == "devops-cli-config-sandbox"))) ||`.
- The change fits one pull request.

## Existing Tool Considered

mikefarah/yq (MIT, maintained, last activity 2026-11-09) partly covers the need: it drops map entries whose key matches a pattern at any depth, but it renders and applies no ConfigMap, holds no copy of the project's name rule `is_secret_parameter_name`, and `kustomize configMapGenerator` removes no key. The change builds its own code instead: about 2k tokens to build, 1k tokens a year to keep, 2k tokens to fix, and about 1 hour. It deletes no internal code.
