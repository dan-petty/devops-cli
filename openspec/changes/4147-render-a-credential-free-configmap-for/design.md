# Design

## Decisions

- **Reuse `is_secret_parameter_name` and remove the matching keys instead of masking them, but keep a key whose value is a number or a boolean.**: It is the one tested record of a secret-suggesting name (SECURITY.md rule 12), it covers nested keys, and a masked value under a credential key still names the setting to the planner. The name rule alone also matches `step_tokens`, `token_budget`, `step_token_budget` and `item_token_budget` of the template, which are counts: dropping them would give the planner the code defaults, 8000000 and 20000000 in place of 32000000 and 80000000. Every credential of the settings is text, so a number or a boolean under a credential-like name is no credential.
- **Drop the credential keys before the config is written and checked, with a keyword-only `drop_secret_keys` parameter on the two render functions.**: The render refuses a key that no setting declares at `src/devops_cli/k8s/configmap.py:91:unknown = unknown_setting_keys(written)`, and it writes the config at `src/devops_cli/k8s/configmap.py:88:data[_CONFIG_KEY] = yaml.dump(config, Dumper=_BlockDumper, sort_keys=False)`, so a template that holds a credential key fails before any drop that runs after the render, and the drop runs on `config` before that write.
- **Render the sandbox ConfigMap in `render_active_devops_sandbox_configmap` beside the active render at `src/devops_cli/k8s/configmap.py:153:active_settings = settings if settings is not None else load_settings()`, and call it from both deploy paths.**: One render path keeps the same template and active config, and it meets the `--stack devops` criterion on a native cluster and on an Argo CD-managed cluster.
- **Put the removal walk beside the masking walk at `src/devops_cli/security/sanitizer.py:502:if is_secret_parameter_name(str(key))`.**: The name rule and its walk stay in one place, and the k8s renderer holds no pattern of its own.
- **Check the rendered ConfigMap by parsing it and walking every key at any depth, in two cases of one test: a hand-built config that holds credential keys, and the rendered ConfigMap.**: A serialized text scan can match a value and miss a nested key, and the hand-built config proves that the walk names a credential key instead of only passing on output that already dropped it, as the parse at `tests/k8s/test_k8s_configmap.py:61:inner = yaml.safe_load(doc["data"]["devops-cli.yaml"])` does.
- **Apply the sandbox ConfigMap right after `devops-cli-config` and before the manifests, on the native path and the Argo CD-managed path.**: The planner run Job mounts it, so the ConfigMap exists before the pod starts, and the first manifest that the command sends on stdin stays `devops-cli-config`, as `src/devops_cli/commands/k8s/stack_lifecycle.py:1295:_apply_rendered(config_map, f"ConfigMap {CONST_K8S_DEVOPS_CONFIGMAP}", kubectl_ctx)` shows.
- **Keep the name and the single data key of the rendered ConfigMap, and change no manifest.**: The run Job mounts the name at `k8s/devops/roadmap-service/cronjob-planner-run.yaml:113:name: devops-cli-config-sandbox` and the admission policy admits it at `k8s/devops/roadmap-service/admissionpolicy.yaml:144:(variables.planner && v.configMap.name == "devops-cli-config-sandbox"))) ||`, so the contract holds with no manifest edit.
- **Do not re-export the new renderer from the `devops_cli.k8s` package.**: The command imports the module directly at `src/devops_cli/commands/k8s/stack_lifecycle.py:55:from devops_cli.k8s.configmap import render_active_devops_configmap`, and the package list holds only the sibling at `src/devops_cli/k8s/__init__.py:37:"render_active_devops_configmap",`, so a package export changes no import site.
- **Leave the existing places that name the sandbox ConfigMap unchanged: the run Job, the admission policy, the cluster document, the run Job test and the living spec.**: They state the mount and the admission rule, such as `docs/CLUSTER.md:96:The template of the planner's sandboxed run Job is the suspended CronJob` and `tests/roadmap/test_roadmap_run_job.py:106:) == (False, None, "devops-cli-config-sandbox", [], [])`, and this change keeps the name and the data key that they record.
- **Reuse the existing YAML parser, renderer and name rule.**: The repository already parses the manifest at `src/devops_cli/k8s/configmap.py:76:manifest = yaml.safe_load(template_content)` and holds the name rule, so the change adds about 25 lines and no dependency.

## Rejected alternatives

- **A new config-only pattern such as token|password|secret|key.**: A second list drifts from CONST_MCP_SECRET_PARAMETER_WORDS, and a bare `key` matches non-credential names such as `keyring` and `keys`.
- **An explicit allow-list of safe keys.**: It needs an update for each safe key and can omit a setting that the Service needs.
- **Copy every key and rely on the admission policy.**: The admission policy judges the shape of a Job; it cannot remove a key from a ConfigMap that already exists.
- **A new deploy-stack flag.**: It adds a second path for the same stack, and a person must remember it.
- **A manifest file under `k8s/devops/`.**: It would put the homelab's settings in git, and `k8s/README.md:1101:This repository is public, so it holds no homelab value.` records that git holds no such value.
- **Leave the copy to a person.**: The issue removes the manual step, and a hand copy drifts from the active config at the next deploy.
- **A private filter inside the k8s renderer.**: It puts a second copy of the name rule beside the k8s rendering, where the next credential rule would not reach it.
- **Drop every key whose name matches, whatever its value.**: It removes the four token budget keys of the template, and the planner then runs with budgets 4 times lower than the Service.
- **A list of exempt key names.**: It needs an entry for each new count and a reason for each, as the list at `src/devops_cli/config/constants.py:629` does for MCP parameters; the type of the value says the same with no list.
- **Mask the values with `mask_secret_named_values` and keep the keys.**: A masked value under a credential key still names the setting to the planner, and the control asks for the key to go.
- **Drop the credential keys after the render, on its output manifest.**: `src/devops_cli/k8s/configmap.py:91:unknown = unknown_setting_keys(written)` refuses the template before it returns, so a credential key would stop the render and never reach a later drop.
- **Scan the serialized ConfigMap text for credential words.**: It can match a value and miss a nested key.
- **Rely on the admission policy for the test.**: It does not run in the offline unit test, which doubles the process edges and reaches no cluster.
- **Export the new renderer from the `devops_cli.k8s` package.**: `src/devops_cli/commands/k8s/stack_lifecycle.py:55:from devops_cli.k8s.configmap import render_active_devops_configmap` shows that the command imports the module directly, so the package export changes no import site.
- **Add yq for the key removal.**: It needs a second render step and a new binary in the image, and it still needs the ConfigMap writer; the alternatives check of 2026-11-10 records it as partly covering the need.
- **Add kustomize.**: configMapGenerator builds a ConfigMap from files and literals and cannot remove a selected key.

## Unchanged references

- `src/devops_cli/k8s/__init__.py` (import): The command imports the renderer from the module at `src/devops_cli/commands/k8s/stack_lifecycle.py:55:from devops_cli.k8s.configmap import render_active_devops_configmap`, so the package export list keeps its current entries.
- `k8s/devops/roadmap-service/cronjob-planner-run.yaml` (quoted target): The volume config mounts the name at `k8s/devops/roadmap-service/cronjob-planner-run.yaml:113:name: devops-cli-config-sandbox`, which the render keeps.
- `k8s/devops/roadmap-service/admissionpolicy.yaml` (quoted target): The rule admits the sandbox name at `k8s/devops/roadmap-service/admissionpolicy.yaml:144:(variables.planner && v.configMap.name == "devops-cli-config-sandbox"))) ||`, and the name does not change.
- `docs/CLUSTER.md` (document): The document names the sandbox ConfigMap as the credential-free config of the planner pod at `docs/CLUSTER.md:96:The template of the planner's sandboxed run Job is the suspended CronJob`, which this change makes true.
- `tests/roadmap/test_roadmap_run_job.py` (quoted target): The case asserts the mounted name at `tests/roadmap/test_roadmap_run_job.py:106:) == (False, None, "devops-cli-config-sandbox", [], [])`, which the render keeps.
- `openspec/specs/k8s-planner-run-job/spec.md` (spec text): The living spec states the mount; the change adds requirements through the delta and the archive, so no group edits the spec.

## Security

The rendered sandbox ConfigMap crosses a trust boundary: it leaves the workstation for the cluster as the config that the sandboxed planner run Job reads, so it must hold no credential. A person must confirm two things before a deploy: that a new key of the template whose name holds no word of CONST_MCP_SECRET_PARAMETER_WORDS still holds no credential, and that the live sandbox ConfigMap holds no credential key after the deploy. The test in tests/k8s/test_k8s_configmap.py fails if a credential key reaches the rendered ConfigMap, and the test in tests/security/test_secret_redaction.py fails if the removal walk keeps one. A credential that a person writes as a number under a credential-like name stays in the ConfigMap, because the walk reads it as a count; the settings declare no such credential, and a person must not add one.
