# Design

## Decisions

- **Detect the rejection in the stage job, before it selects items.**: The job already owns the clone, the heads of `origin` and the rule that deletes the staged branch of a closed item. `plan_stage` reads the heads and the plans on the default branch first, finds the rejected plans, and gives the selection the rejections of this round. So an item whose branch was deleted by hand is also left out in the round that finds the rejection.
- **Read one pull request for each open New or Ready item whose record holds `stage.pr` and whose plan is not on the default branch.**: The read is one conditional `GET` for each staged plan in each round. `--item` limits the read to the named item. A merged plan has its folder on the default branch, so the item is no candidate.
- **Write the reason as a comment of the stage job with a second marker, `CONST_ROADMAP_STAGE_REJECTED_MARKER`.**: Refine already reads the newest comment of the stage job after its own last comment as `stage_return`, keeps it out of `replies`, and gives the item one new look and no second one on the same body. The second marker lets the stage request find the comment, and both markers are removed from the text that a model reads.
- **Take the reason from the last comment of a trusted author that is over `EVIDENCE_MIN_CHARS` characters.**: `trusted_replies` keeps the comments of a person with write access and of the Service bot, and the job drops the comments of the bot. A one-word comment such as `rejected` is no reason, so the job takes the comment before it. A pull request with no such comment gets a comment that says so, and the hold still applies.
- **Return the item to New, clear the stage record and write `stage.rejected` as JSON in one `set_field` write.**: The record holds the pull request, the time of the close, the files that `text_paths` finds in the reason, and a hash of the text outside the refine section (`body_hashes`). Refine looks at New items only, so the return is what lets refine read the reason. Clearing `stage.branch` is what lets `stage_return` see the comment.
- **Take the hash from `stage.text_hash`, which `_stage_one` records.**: The hash of the body at the time of the read would hold an edit that a person made before the first look, so the edit would not end the hold. The hash of the text that the plan came from is the right baseline. A record with no such key takes the hash at the time of the read.
- **Keep the Status of an item that the same run stages.**: A named Ready item would end New with a new draft, and the implement job takes only Ready or Planned items. `apply_stage` knows the changes it stages, so `_reject_plan` writes only the record for those items. The rejection then leaves the Status as it is.
- **Hold the item with a new rule `_rejected` of the selection, before `_held`, and let `--item` overrule it.**: The hold ends when `body_hashes` differs from the recorded hash or when `changed_since` finds a commit on the default branch that changed a named file at or after the close. This is the check of `_cited_code_changed` in refine, so `changed_since` and `text_paths` become public.
- **Delete the staged branch with the rule of a closed item, under a lease.**: When every commit past the default branch is the session identity's or a clean merge, the job runs `git push --force-with-lease=refs/heads/<branch>:<sha> origin :refs/heads/<branch>`. The sha is the commit that the plan judged, so a commit that a person pushes in the time between the plan and the write keeps the branch. A refused lease with a changed branch is a kept branch, and the job still writes the comment and the record. Then `issue_holder` finds no hold, and `add_worktree` finds no pushed branch to refuse. A branch with another commit stays, the plan lists it, and the pushed branch still holds the item with its own reason.
- **Judge a named item without the branch that the run deletes.**: `plan_stage` removes the deleted branches from the heads that the selection reads. So `_held` does not hold the item on a branch that the same run deletes, and a run with `--item` can stage it.
- **Order of the writes: delete the branch, post the comment, then set the Status and the record.**: A failed delete leaves no comment and no record, so the next round tries again. A failed record write after the comment can post a second comment in the next round. That case is rare, and it holds no loss of data. A check for the marker of the pull request in the comments of the issue would stop the second comment, but it adds code for a rare case, so the change does not add it.
- **Add the key `rejected_plan` to the plan request only for an item with a `stage.rejected` record.**: The job reads the comments of that item only. The text comes from the newest comment of a trusted author that holds the rejected-plan marker.
- **Let `--item` overrule the hold and still write the rejection.**: A person who names the item wants a plan now. The run writes the comment and the record, then stages the new plan, which clears `stage.rejected`. The item keeps its Status. The request of that run holds the reason that the run found, so the model still reads it.
- **Keep the code of the new rules in `src/devops_cli/roadmap/stage_rejected.py`.**: `stage.py` has about 2,000 lines. The module holds the record, the choice of the reason, the text of the comment and the hold. `stage.py` holds the plan and the writes, which need its git helpers.
- **Share one list of markers and one reader of a comment of the stage job.**: `CONST_ROADMAP_STAGE_COMMENT_MARKERS` names both markers. `stage_comment_text` in `refine.py` removes them and cuts the text, for refine and for the stage request. The stop errors of the run stay in `stage.py`; the read of the pull requests takes them as an argument.

## Rejected alternatives

- **Do the copy in the row `stage_ready`.**: `_recorded_pull` returns no pull request once `stage.ready` equals `stage.pr`. The record of #3049 holds `stage.pr` and `stage.ready` as `3183`, so the row never reads a plan that was marked ready and then closed. The row has no clone, so it cannot judge the authors of the branch.
- **Only ignore the branch of a closed plan in `issue_holder`.**: `issue_holder` lives in `src/devops_cli/git/worktree_add.py` and reads no pull request. `add_worktree` refuses a pushed branch that holds a commit of another author, and takes over one that only the App wrote to, so a plan that is staged again would reuse the rejected commit. Deleting the branch fixes both.
- **Write the reason into the body of the issue.**: The body hash decides the hold and the approval of an item that a bot filed (`trust.is_approved`). A body edit by the job would reset both. A comment changes neither.
- **Add a new refine key and a new refine wait.**: `stage_return` and the rule "An item the stage job returned gets one new look" of roadmap-refine already do this for a comment of the stage job.
- **Rely on `devops roadmap return --comment`.**: The command works when a person or an agent runs it. The case here is a person who only closes the pull request, and the reasons of #3049, #3076, #2754 and #2740 stayed on the pull request after a `return` with the text `returned per agent request`.
- **Read the closed pull requests with one listing for the round.**: A listing of closed pull requests is a window of recent pull requests, and a round that comes late misses a rejection. One read of the recorded number cannot miss it.
- **Hold the item for ever.**: The issue asks that the stage job takes the item again after a change of the body or of a cited file.
