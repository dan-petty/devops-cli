# Design

## Decisions
1. **A job block marker ends a section.** `_section_tokens` ends the section at the first token after the heading that is a `heading_open` of the same or a higher level, or an `html_block` whose stripped content is in `_JOB_BLOCK_MARKERS`. `_JOB_BLOCK_MARKERS` is a module-level `frozenset` in `refine.py` that holds the four constants `CONST_ROADMAP_REFINE_START_MARKER`, `CONST_ROADMAP_REFINE_END_MARKER`, `CONST_ROADMAP_ALTERNATIVES_START_MARKER` and `CONST_ROADMAP_ALTERNATIVES_END_MARKER`. The module already imports the four constants. The change adds no new literal. Reason: the job blocks are not text of the section, and both markers are a border of a block.
2. **Only an HTML block counts.** A marker in a code span, or inside a paragraph as inline HTML, is part of an `inline` token, so it ends no section. Reason: markdown-it-py 4.3.0 gives each marker line as its own `html_block` token (CommonMark HTML block type 2 ends at the line that holds `-->`), also directly after a paragraph or a list item. A person who quotes a marker in prose does not write a block. The level of the token does not matter, because no job writes its block inside a list item.
3. **A heading inside a job block still starts a section.** The search for the heading does not change. Only the end of the section changes. So when a person writes no Dependencies section, `body_dependencies` finds the `### Dependencies` part that `render_proposal_section` writes in the refine block, and that part ends at the next heading of its level or at the refine end marker. Reason: acceptance criterion 2 of #6613. Today the part runs past the refine end marker when no `Watched files` part follows it.
4. **One rule for each caller.** The rule is in `_section_tokens`, so `body_dependencies`, `body_questions` and `_quoted_titles` (of `title_dependencies`) all get it. Tests prove it for `body_dependencies` and `body_questions`.
5. **A new version of the rules.** `CONST_ROADMAP_REFINE_RULES_SINCE` gets the UTC time of the build commit, and its comment names #6613. Reason: the comment of the constant says that a change to a rule that sets a next step sets a later time in its pull request, and #6451 did that for the same reader. The change removes false dependencies, so a wait on a person that a false dependency set, such as a dependency cycle, gets one new round. A new version ends no blocked wait.
6. **No data migration.** The refine record of an item keeps its old `refine.blocked_by` until the next refine round of the item.
7. **Spec deltas.** One ADDED requirement in `roadmap-refine/waits`, which holds the Dependencies rules. One MODIFIED requirement in `roadmap-refine/proposal`, because the requirement "The body's answered key questions are not asked again" states the old end of the section, and AGENTS.md rule 8 asks to fix a document that a change makes wrong.
8. **Evidence for the pull request.** After the build, the build agent counts again, read-only: for each item of `GitHubRoadmapStore("dan-petty/devops-cli").open_items()`, it compares `body_dependencies(item.body)` on the base and on the branch. The pull request body gives the count of items whose list changes, and the items. The issue gives the count of 2026-11-21: 2 of 812 open items.

## Rejected alternatives
- **Remove the alternatives block before the read** (`without_alternatives(body)` in `body_dependencies`). Rejected: it fixes one block in one caller. `body_questions` and `_quoted_titles` read the same body, and the refine `### Dependencies` part also runs past the refine end marker into the text after it (base output `[4989, 5506]`).
- **Remove every job block before the read** (`text_of_a_person`). Rejected: the refine block holds the `### Dependencies` part that names the blockers of an item when a person wrote none (acceptance criterion 2, and the docstring of `body_dependencies` names `render_proposal_section` as a source).
- **Make the alternatives job write a heading before its block.** Rejected: the bodies of the open items keep their old blocks until the next check, the heading changes the body hash that the job records, and text that a person writes after a block has the same problem.
- **A markdown-it-py plugin that splits the body into sections.** Rejected: no plugin knows the job block markers of this project (the alternatives check of #6613 gives `none`), and the token that the parser gives already shows the marker.
