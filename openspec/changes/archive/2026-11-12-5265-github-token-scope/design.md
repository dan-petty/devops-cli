# Design

## Decisions

- **A gh child reads the token from a file, not from its environment.** gh gives its environment to each `--jq` filter, and gh reads `oauth_token` of `hosts.yml` when the environment holds no token. Each gh child gets a folder of its own, made with `tempfile.mkdtemp` (mode 0700), with `hosts.yml` written with `os.open(..., 0o600)`. A shared folder would hold the token between calls, and two calls at one time would write one file. `config.yml` with `version: "1"` stops the move of the configuration to the format of several accounts, which would ask GitHub for the login. The folder is directly in the runtime folder of the user (`platformdirs.user_runtime_path`, a tmpfs of the user), else directly in the temp folder of the system, else in the data directory when it is absolute: the root file system of a runner Job is read-only. No folder of devops-cli is between the runtime folder and the token folder, so a link below the runtime folder cannot move it. tempfile uses the current folder when it can write no temp folder, so a runtime or temp folder that resolves into the current folder is skipped. A relative data directory resolves under the current folder, which can be the working tree of a project, where a folder that a killed process leaves could be staged. `contextlib` removes the folder when the child ends, and the block holds the timeout and the error paths of `run` and `run_async`.
- **The token goes only where git reaches a remote.** `git_reaches_remote` in `core/process.py` skips the global options of git and reads the first other word. The options that take the next word as their value are `-C`, `-c`, `--git-dir`, `--work-tree`, `--namespace`, `--config-env` and `--attr-source` (git.c `handle_options`). An option that the function does not know makes it read a value as the subcommand. That gives no token to the call, so a failure is a refused network call and never a token in a local call.
- **One new git folder for each network call.** The agent can write the folder of the clone and the home folder, so no folder that lives across a turn holds the configuration of a network call. A folder that lives for the whole run would be writable by the agent between two calls, as the folder belongs to the same user.
- **The sweep comes first and last.** A sweep comes before the check of the settings, so that a refused setting, which stops the call, still ends the processes before the job writes to GitHub. The check runs git in the checkout, which reads the configuration of the agent, so a second sweep follows it. `end_leftover_processes` runs before `mkdtemp`, so that no process of the agent and no program that the check started sees the new folder, and again before the call with the token, so that a program that one of the calls without the token started is gone. The keeper pushes a `wip:` commit from inside a turn, so the first sweep also ends the background processes of that turn.
- **The objects of the clone, linked, not copied.** The `objects` folder of the new git folder is a symbolic link to the object folder of the clone. A push reads the commits from it, and a fetch writes the new objects into it, so no object moves after the call. Objects hold no configuration, and git starts no program from them. `-c gc.auto=0 -c maintenance.auto=false` keep git from packing or pruning the shared objects with the refs of the new folder only. The check refuses `objects/info/alternates`, because git would then start `git for-each-ref` in the repository that the file names (`--alternate-refs` of the connectivity check).
- **The refs are copied, with no token.** `git for-each-ref refs/remotes/origin/` in the clone and `git update-ref --stdin` in the new folder copy the remote-tracking refs, so a fetch tells the remote what the clone has. After the call, `git update-ref` writes the one ref that the call changed into the clone. These calls run with `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1` too.
- **The URL of `origin` is read once.** `apply_implement` reads `remote.origin.url` of the clone before its first item, when no agent ran yet: the pod of a Job starts with a new home volume, and `ensure_checkout` cloned it. Each network call uses that URL, so a later edit of the configuration of the clone does not move the remote. The trusted helper answers only for `https://github.com`.
- **The settings check is a signal and a second guard.** A call with the token reads no setting of the clone, so the check is no condition of the invariant. It shows an attempt at once, with its own class, and it holds when a later change brings a network call back into the clone. It reads only the keys, never the values, and the reason names the key. The allowlist holds the keys that `git clone`, `git init`, `ensure_checkout` and the eval write: `core.repositoryformatversion`, `core.filemode`, `core.bare`, `core.logallrefupdates`, `core.ignorecase`, `core.precomposeunicode`, `remote.origin.url`, `remote.origin.fetch`, `branch.<name>.remote`, `branch.<name>.merge`, `user.name`, `user.email`, `commit.gpgsign` and `extensions.worktreeconfig`.
- **The attributes.** `git check-attr --stdin filter diff merge` reads the attributes of each path that `git ls-files --cached --others --exclude-standard` lists, from every attribute file that git reads (the files of the tree, `info/attributes` and the global file). A `filter` with any value, a `diff` that is not a built-in pattern of git, and a `merge` other than `text`, `binary` and `union` stop the item.
- **The check runs only in a runner.** A person can have a global filter, such as `nbstripout`, so the check of a turn runs where `roadmap.implement.in_runner` is true, as `end_leftover_processes` does. The eval of the implement step runs no network call, and its git calls get no token.
- **The failure class `git_config`, action `wait`.** A new Job starts from a new clone, but the agent would write the setting again. A person reads the stop. The stop pushes nothing.

- **A sweep before each child with the token, in a runner.** After a turn, the job runs code of the checkout: the tests, the hooks of `pre-commit` and the exit checks. A process that such code leaves could read the token of a later gh or git child. So the process runner ends the leftover processes before and after each child that gets the session's token, in a runner only: a workstation runs other children of the person at the same time. The job runs its gh children one at a time, so the sweep ends no child of its own.
- **git in a verification command only as the negative search.** The step runs a verification command of the plan in the checkout. A network git call there would read the configuration that the agent can write, with the token. The stage gate already allows only `uv run devops` and `! git grep`, and no plan of the Service of the last 14 days names another git form, so the narrow rule breaks no plan.
- **The `shallow` file goes with the objects.** A shallow clone, which a run with `--source` can name, lists in `shallow` the commits whose parents it does not hold. Without the file, a fetch in the new git folder walks into those parents and fails. The file holds commit IDs only and names no program. The copy opens it with `O_NOFOLLOW`, and the write-back makes a new file with `tempfile.mkstemp` and puts it in place with `os.replace`, so neither follows a link.
- **The lookup of the token in a thread, the folder in the event loop.** A cancel of an async call stops the await, not the thread. When only the lookup runs in the thread, a cancel leaves a token in memory and no file.

## Rejected alternatives

- **A local fetch of the commits into the new git folder** (the first design): a fetch of `main` of this repository into an empty bare repository took 15 s, 37 MB and 27 s of CPU on a workstation (git 2.55.0), for each network call. A push of a `wip:` commit happens after each ticked task. The linked objects cost nothing, and git reads no configuration from them.
- **Alternates** in place of the link: a fetch would write the new objects into the new folder, and a second fetch, with no token, would have to move them into the clone. The process runner gives a `fetch` the token, so that second fetch would need an exception for a local path.
- **The configuration of the clone, checked just before a network call in the clone**: the call would still read the global file, the hooks of the clone and the attribute files, and the check would have to follow every file that git reads. A new folder removes the files instead of judging them.
- **`GIT_CONFIG_COUNT` with `core.hooksPath`, `core.fsmonitor` and `core.sshCommand`** (an earlier draft): a credential helper, a filter and a proxy of a configuration file still applied.
- **An empty `HOME` only, with no `GIT_CONFIG_GLOBAL` and no `GIT_CONFIG_NOSYSTEM`**: it closes the global file too, but `/etc/gitconfig` of a workstation would still apply. The two keys say what they do, and the guard accepts them only with their fixed value.
- **One item for each Job**: the Service starts each Job with `--item`, but `apply_implement` runs each selected item, and the tests run two. The `origin` of `add_worktree` keeps the second item on the same network calls.
- **A jq filter that devops-cli runs itself**, with a jq library in a child with an empty environment: it replaces an option of gh with our own code, and `--template` would need the same.
- **`GH_TOKEN` for gh and a filter that refuses `env` and `$ENV`**: a text check of a filter language is no boundary.
- **The two-container Job (#3700)**: the structural fix, larger, and it needs a change of the admission policy.
- **The in-process REST client for every gh call of the runner**, so that no child holds the token: about 30 modules call `run_gh`, so it is larger than this fix. The sweep before each child with the token closes the same path.
- **A refusal of a shallow clone** in the check of the settings: the check runs only in a runner, so a workstation would keep the unclear error of git.
