# Proposal

## Why

Issue #2913, part W6 of the tracker #2908. On 2026-10-31 the owner ran `devops roadmap implement --item 2747 --confirm` on a workstation. The command refused: "The implement job runs a step only in a runner pod. Set roadmap.implement.in_runner to true there." The supported path exists, but no help text or document names it: `devops k8s run-job --template runner --repo <owner/name> -- roadmap implement --repo <owner/name> --item <n> --confirm`. The owner left out the second `--repo`, and the command failed with "Cannot resolve the repository; pass --repo owner/name."

The refusal is right about the step: a step runs only in the pod of a runner Job, because the shell of the agent is no security boundary. But the refusal is a dead end. A person who wants to implement one item by hand must know a second command with a long argument list.

## What Changes

- `devops roadmap implement --item <n> --confirm`, run where `roadmap.implement.in_runner` is false, starts the runner Job. It uses the code of `devops k8s run-job --template runner`: the same Job builder, the same token variable, the same follow of the log. The repository is `--repo` or the origin of the checkout. The command puts the repository in the Job args (`roadmap implement --repo <repo> --item <n> --confirm`), so the pod needs no checkout. It follows the log and exits with the exit code of the container. With `--no-wait` it prints the name of the Job. A new option `--context` chooses the cluster context, as in `run-job`.
- The command refuses, before it creates the Job: an Item that an agent or a person claimed (W3), an Item whose Status is neither Ready nor Planned, and a repository that has a runner Job that has not ended.
- `--source`, `--filter` and `--limit` need the runner. With `--confirm` outside the runner, the command refuses them, and refuses a missing `--item`. The refusal names the `run-job` command, where the options go after `--`. The refusal of `--group` with `--confirm` names the path too.
- `--dry-run --item <n>` outside the runner makes no request and prints the Job it would make. It ignores `--source`, `--filter` and `--limit`.
- The code of `run-job` changes in two ways that serve the path. The runner Job and its pod carry the label `implement-repo` that the Service uses as its lock, so a Service round waits while a Job of this path runs. And `run-job` with the runner template refuses to create a Job while a Job with that label has not ended, so there is one runner Job for each repository at a time, whoever starts it. The body of the command moves to a function, `start_job`, that `run-job` and `implement` both call.
- `repository_label` moves from `implement_submit.py` to `k8s/cluster_job.py`, which both the Service and `run-job` import.
- The help text of `implement`, `k8s/README.md` and `docs/ROUTINE_TASKS.md` name the path. `docs/ROADMAP_WORKFLOW.md` (W1, #2909) is a separate change and names it there.
- Observable behavior changes (a command, an option, two refusals, a label on a Job), so the change carries spec deltas.
- The change fits one pull request.

## Capabilities

### Modified Capabilities

- `roadmap-implement-job`: the job outside a runner starts a runner Job for one Item; the refusals.
- `roadmap-implement-runner`: the runner Job carries the repository label, and `run-job` refuses a second runner Job for a repository.

## Feasibility

Checked on 2026-10-31 against the real system:

- The refusal is in `require_runner` of `src/devops_cli/roadmap/implement_run.py`, text `implement_job_runner_refused` in `messages.py`. `_implement_job` in `src/devops_cli/commands/roadmap.py` calls it when `--confirm` is set. `apply_implement` calls it again, so the library keeps the guard. The change leaves both calls as they are. The step still runs only in the pod.
- `run-job` builds the Job in `execute_job` of `src/devops_cli/commands/k8s/cluster_jobs.py`, from `build_job` of `src/devops_cli/k8s/cluster_job.py`. `_runner_env` puts the repository into `DEVOPS_CLI_SERVICE_GITHUB_APP_TOKEN_REPOSITORY`. `execute_job` and `dry_run_job` are plain functions. So the body of the typer command can move to one function that two commands call.
- `build_job` already takes `labels`, and the Service passes `implement-repo=<digest>` through `ClusterJobs.create`. `execute_job` does not pass labels. So today a Job from `run-job` has no `implement-repo` label, and the lock of the Service (`run_implement_round` lists Jobs by that label) cannot see it. A manual Job and a Job of the Service could then run for the same repository together.
- The premise of the second failure is true: `_target` in `commands/roadmap.py` resolves the repository from `--repo` or the `origin` of the working directory, and the command prints "Cannot resolve the repository; pass --repo owner/name." when it finds none. The pod has no checkout, so the Job args must carry `--repo`. They do in the path above.
- A full plan on the workstation does not fit. `plan_implement` needs a model clone and, for a Staged item, the bot login of the GitHub App: `_branch_reason` returns "no App" when `service.github_app.bot_login` is unset, and a workstation does not set it. So the check before the Job reads only the Item (labels and Status) through the roadmap store. The pod runs the full plan and leaves out the Item with a reason in its log.
- The runner image, the CronJob `devops-cli-runner` and the admission policy need no change. The policy applies only to the user of the Service. The label is an extra Job label, and the policy does not pin Job labels.
- A repository that the App is not installed on fails in the pod, not on the workstation. The workstation reads the Item with the token of the person, which does not tell if the App covers the repository. GitHub answers the token request of the pod with HTTP 422, and the error then names the repository (`github_app_repository_not_granted`). The command follows the log by default, so the person sees the cause.
- The lock is best effort. A check and a create are two calls, so a Job that starts between them is not seen. `execute_job` lists the Jobs just before it creates one, and the Service lists them again after its plan and before its create. A hard lock needs an object on the server, such as a Lease, and is a separate item.
- The label is the digest of the lower-case repository, because GitHub names are not case sensitive and `--repo` is typed by a person.
- The premise holds. No part of the item needs code that compensates for a missing tool.

## Existing Tool Considered

`devops k8s run-job` is the tool: it builds the Job from the CronJob template, follows its log and returns its exit code. The change reuses it whole (`execute_job`, `dry_run_job`, `_runner_env`, `build_job`), and reuses `claimed_by` of the claim module, the `RoadmapStore`, `StoreRequests` for the dry run, `render_request_plan`, and `job_state` of `cluster_job_api.py` for the state of a listed Job. `kubectl` lists the Jobs, as `run-job` already runs `kubectl`. The change builds only the check of the Item before the Job (about 60 lines) and the call from the command. It deletes no internal code. It moves `repository_label` and the body of `run_job`.
