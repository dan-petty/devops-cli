# Design

## Decisions

- **One function starts the Job.** The body of the typer command `run_job` moves to `start_job(args, context, template, repo, wait, start_timeout, dry_run, before)`. `run_job` calls it. `devops roadmap implement` calls it with the runner template, so the two commands cannot drift: the same environment value, the same labels, the same dry run, the same follow of the log and the same exit code. `start_job` raises `typer.Exit`, as `run_job` does, so the exit code of the container becomes the exit code of `implement`.
- **The Job carries the label of the Service.** `start_job` gives the runner template `implement-repo=<digest of repo>` through `execute_job(labels=...)`. The Service lists Jobs by that label and creates none while one runs. So a Job of the manual path blocks the Service, and the Service does not pick the same Item. `repository_label` moves to `k8s/cluster_job.py`, a module with no GitHub or roadmap import, so `run-job` does not import the roadmap Service code.
- **The lock is in `start_job`, so both commands have it.** Before it creates the Job, `start_job` lists the Jobs with the label (`kubectl get jobs -l implement-repo=<digest> -o json`) and refuses when one has not ended. The state comes from `job_state` of `cluster_job_api.py`, the function the Service uses. `run-job --template runner` shows the same refusal, because two runner Jobs for one repository can push to the same branch. The dry run lists the lookup as a request.
- **The lock is best effort.** The check and the create are two calls. `execute_job` lists the Jobs just before the create, and the Service lists them again after its plan, which reads git and the network, and before its create. A Job that starts between a list and a create is not seen. The label hashes the lower-case repository, so every spelling of a name has one lock.
- **The check of the Item reads the store only.** `require_startable(item)` in the new module `roadmap/implement_outside.py` refuses an Item that `claimed_by` names (an agent or a person), and an Item whose Status is neither Ready nor Planned. It runs before any cluster request. An Item with `owner/service` passes: the Service's own claim holds nothing against a job, and a running Job is caught by the lock. The check stands in front of the pod's plan, which does the full judgment (branch, pull request, authors, stop and retry) and leaves the Item out with a reason in the log.
- **The refusals for options come from one list.** `--source`, `--filter` and a `--limit` that is not the default are the options that need the runner (they choose a clone and a filter of a job that runs there). `--item` is required, because the check, the lock and the Job args are for one Item. One message names the options and the command, with the repository filled in. The options go after `--` of `run-job`.
- **`--dry-run` follows `--item`.** Outside the runner, `--dry-run` with `--item` prints the Job, and ignores `--source`, `--filter` and `--limit`. Without `--item` it prints the requests of the job as before. `--confirm` and `--dry-run` stay exclusive. A variable `DEVOPS_CLI_DRY_RUN` that wins over `--confirm` gives the same print.
- **The guard stays.** `require_runner` and `apply_implement` are not changed. In the pod, `in_runner` is true and the command takes the old path. The command chooses the new path only when `in_runner` is false.
- **`--context` and `--no-wait`.** `implement` gets `--context` and `--wait/--no-wait` with the text of `run-job`. It gets no `--start-timeout`: the default of `run-job` fits.

## Rejected alternatives

- **Run the full plan on the workstation before the Job.** `plan_implement` needs a model clone, and `_branch_reason` leaves every Staged item out with `implement_left_no_app` when `service.github_app.bot_login` is unset. A workstation does not set it. The plan would refuse items that the pod accepts. The pod runs the plan anyway.
- **Build a second Job in `roadmap/`.** The Service builds its Jobs through the Kubernetes API (`ClusterJobs`), and `run-job` through `kubectl`. A third builder would be new code to keep. `start_job` is the one that a person already uses.
- **Claim the Item for the person at the start.** A claim as `human` would make the pod leave the Item out (the job leaves out an Item that a person claimed). The lock label already stops the Service.
- **Forward `--filter` and `--limit` to the pod.** `--item` takes the one Item and ignores the filter and the limit (`roadmap-implement-job`). Forwarding them would do nothing, and a silent option is worse than a refusal.
- **Keep the old refusal and add a hint.** The owner asked on 2026-10-31 that the command do the work. A hint still makes the person type a second command.
