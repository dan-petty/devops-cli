# Proposal

## Why

Issue #2564: the roadmap Service runs one lane per repository, and each lane sends its model calls on its own thread. With several repositories, several lanes send their model calls at the same time. The `devops-background` tier serves one model call at a time. The gateway kills a call that waits 1100 s. So a round that starts many lanes at once holds its calls at the gateway, and the held calls time out.

## What Changes

- `src/devops_cli/ai/client/network.py` holds one model call slot, a `threading.Semaphore`, with `set_model_call_limit`, `get_model_call_limit`, `reset_model_call_limit` and `model_call_slot`. The slot is None until a process sets it, so a CLI process sends its model calls with no such limit.
- `src/devops_cli/ai/client/unified.py` holds the model call slot around the model call in `_dispatch_messages`, so a lane that cannot take the slot waits in the process, where no stall timer runs, not at the gateway.
- `src/devops_cli/config/defaults.py` and `src/devops_cli/config/settings.py` add `service.model_call_concurrency`, an integer of at least 1, default 1.
- `src/devops_cli/server/service.py` sets the slot from `service.model_call_concurrency` when the Service starts.
- The limit of a Service's model calls is a service's behavior a consumer observes, and the new option is a devops option. The change carries a spec delta.
- The change fits one pull request.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `roadmap-service-limits`: the Service limits its model calls to a configured count in flight, default one.

## Impact

- Code: `src/devops_cli/ai/client/network.py`, `src/devops_cli/ai/client/unified.py`, `src/devops_cli/config/defaults.py`, `src/devops_cli/config/settings.py`, `src/devops_cli/server/service.py`.
- Documents: `docs/CONFIGURATION.md` and `docs/ENV_VARS.md`, regenerated by `devops docs generate`.
- Tests: `tests/test_ai_client_network.py` (that a dispatch call holds the slot and the slot admits only its limit), `tests/test_service_limits.py` (that the Service keeps one model call in flight by default and installs its limit), `tests/conftest.py` (the reset of the slot after each test).

## Feasibility

- On the base commit, `_dispatch_messages` in `src/devops_cli/ai/client/unified.py` sends its model call with no per-Service limit. Each lane of the Service is a `threading.Thread`, and the model call blocks that thread.
- The gateway's stall timer is a timeout on a call that waits at the gateway. A call that waits in the process for a slot does not run it. A `threading.Semaphore` shared by the Service's worker threads keeps the model calls in flight to the count it sets.
- I ran `tests/test_ai_client_network.py::test_dispatch_calls_hold_the_model_call_slot` on the base. It failed: three slow dispatch calls ran with three in flight at once, so their peak was three, not one. After the change the same three calls keep one in flight, and the test passes.

## Existing Tool Considered

The Python standard library covers the need: `threading.Semaphore` limits the threads that run a block at once. The change adds one semaphore and its setter, one `with` line in `_dispatch_messages`, one setting and one default, and deletes no other code. No library is needed.
