# Design

## Decisions

- **Two modules.** `decision_point.py` holds the type of a point (`DecisionPoint`), the modes, the resolvers, the chain (`ResolverChain`, `chain_of`), the records, the join and the class `Registry`. `decision_registry.py` holds the one registry, `REGISTRY`, with an entry for each point. A point is defined beside its workflow (`VERIFY_SCREEN` in `stage_jev_screen.py`), and that module imports `decision_point.py`. So the registry is a module of its own that imports the points, and no import goes in a circle.
- **The settings check imports the registry only when it has a key to check.** `roadmap.decisions` is empty by default, and then the load of the settings imports no decision code. With a key, the check imports `decision_registry.py`, which imports pydantic_ai (about one second). The Service imports pydantic_ai for its jobs anyway.
- **The chain.** `chain_of(point, settings)` gives no chain when the mode is `off`, or when the point has no rule and no model resolver can run (the point asks no model, or `ai.decision_model` is empty). The workflow then does what it did before the point. Else `ResolverChain.decide` builds the evidence and asks the rule. When the rule gives no band, it asks the model of `ai.decision_model` once, with all questions in one request, and `band_of` gives the band from the cuts file. An error of `FAILED` gives the resolver `fallback` and no band, and the log names the cause. The chain writes one decision record and one count for each decision.
- **What acts.** A decision acts only in the mode `on` and with a band. The workflow reads `Decision.acts` and the band. In `shadow` the chain runs and records, and the workflow acts as with `off`.
- **The identifier** is the point, the subject and a time-ordered UUID (version 7) as the sequence. A counter of the process would start again at each restart of the Service, and two runs of one item would then share an identifier and join the wrong outcome.
- **The records** are log lines: `decision {json}` and `decision outcome {json}`. The JSON log formatter of the Service keeps the message, so Loki holds them. `parse_record` reads one line back, and `join` is a pure function of two lists. A digest of text is in the record only as a SHA-256 hash. A point that declares a digest of counts (`counts_only`) puts the digest in the record. The record keeps the answers that the model gave also when the band fails, so a point with no cuts yet still collects the data of its first fit.
- **The confidence floor.** The screen asks only yes/no questions, which have a probability and no confidence. `band_of` refuses a missing answer or a missing cut, and that is the low-confidence case of this point. A floor in the cuts file comes with the first point that asks a choice or a score question (`stage.explore_stop`, #4399).
- **The refusal of `on`** is a general rule of the registry: each entry names the path of its cuts file, and `Registry.check` refuses `on` when that file is not in the repository. The error names the point and the file. #4410 asks for this rule for `stage.explore_stop`. That point registers in #4399, and the rule then applies to it with no new code.
- **The series bound.** `DecisionPoint.series()` lists the label sets that a point can write: 3 bands for each resolver that answers, and `none` for `fallback`, in `shadow` and `on`. `Registry` refuses a catalogue above `CONST_ROADMAP_DECISION_POINT_MAX_SERIES` (60, the bound of ADR 0020). The screen has a model and no rule, so 8 series.
- **The model name.** `decide_all` and `_decide_one` take `model_name`, and `create_jev_model(model_name, settings=...)` builds it. The check of a System One name (`is_decision_model_name`) moves into the settings, and the bridge uses it, so the setting and the bridge accept the same names.
- **The removed setting.** `RoadmapStageConfig` ignores an unknown key, so the image of this change loads a ConfigMap that still holds `roadmap.stage.jev_screen`. One step removes it. The ConfigMap gets `ai.decision_model` only after the image runs, because `AIConfig` refuses an unknown key.
- **The cuts file** keeps its cuts and its report. Its `step` is the name of the point, `stage.verify_screen`, so the file, the setting, the metric and the records use one name.

## Rejected alternatives

- **One module with a function that imports the points.** `decision_point.py` would import `stage_jev_screen.py` inside a function to break the circle. A second module states the dependency, and each later point adds one import line there.
- **A light list of names in `constants.py` for the settings check.** The list and the registry would be two sources of the names, and a test would have to keep them equal.
- **A process counter as the sequence of the identifier.** A restart sets it back to 0, so two decisions can share an identifier, and the join then labels a case with the outcome of another run.
- **Keep the old key `roadmap.stage.jev_screen` for one release.** The live ConfigMap loads without it, because the section ignores an unknown key. A kept key is a shim, and the project keeps none before 1.0.
- **Ask the default Jev model of the constant when `ai.decision_model` is empty.** ADR 0020 says an empty name means no decision model. A constant would send requests that no setting turned on.
- **A separate confidence setting.** A second threshold beside the fitted cuts gives two sources of truth.
- **The false-clear counter of the screen as a live series.** ADR 0020 replaces it with the join of the decision records and the outcome records. A counter has no identifier of one case and cannot give a labelled case.
