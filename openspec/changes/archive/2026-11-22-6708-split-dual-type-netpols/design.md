# Design

## Decisions
1. **Split, with the rules as they are.** Each policy with both types becomes `<name>-ingress` (type `Ingress`, the ingress rules) and `<name>-egress` (type `Egress`, the egress rules), with the pod selector, the labels and the rule comments of the old policy. Reason: kube-router enforces two single-type policies correctly (retest of 2026-11-22), so the split alone makes the ingress rules hold. The names say the direction, and the old name stays the prefix, so a search for the old name finds both.
2. **Narrow an in-namespace egress rule only to exact ingress ports.** An in-namespace egress rule with no ports gets ports only when the in-namespace ingress rules of its destinations give the exact ports. That is true in `gitea` only: the one in-namespace ingress rule admits TCP 3000, so the in-namespace egress rule gets TCP 3000. In `argocd`, `llm`, `logging`, `mattermost`, `monitoring` and `otel`, an ingress rule admits every pod of the namespace on every port, so no port list is exact, and the rule stays. In `object-store`, the rule already has the 9 ports of the ingress rule (#6707).
3. **The row refuses each policy with both types.** `dual_type_problems` refuses each NetworkPolicy whose types hold `Ingress` and `Egress`. Reason: the controller bypass works in both directions. An egress rule of such a policy can let traffic skip its ingress rules, and by the same chain an ingress rule can let the pods that it selects skip their egress rules. A rule for one shape must model the peers, the selectors, the `ipBlock` ranges and the ports, and it can miss a case. Single-type policies are enforced correctly, so a rule on the types is simple and complete.
4. **The types as the API server sets them.** The rule reads `policyTypes` as written. With no `policyTypes`, it reads `Ingress`, and `Egress` when the policy has an egress rule (`SetDefaults_NetworkPolicy` in `pkg/apis/networking/v1/defaults.go` of Kubernetes). Reason: the controller reads the stored types, so a policy with no `policyTypes` and an egress rule has both types.
5. **Split the 4 policies of namespace `devops` too.** `devops-default-perimeter`, `crawl4ai-perimeter`, `renovate-perimeter` and `searxng-perimeter` become `<name>-ingress` and `<name>-egress` as in Decision 1. Their egress rules reach no pod that they select, and each ingress peer is a pod that the same policy does not select, so no path changes. The manifest comments, `docs/CLUSTER.md`, `k8s/README.md` and the specs `crawl4ai-service`, `searxng-service`, `renovate-service`, `roadmap-implement-runner` and `k8s-network-policies` that name them use the new names.
6. **The row reads the whole environment tree.** The rule reads each NetworkPolicy document of each YAML file under `k8s/`, as the deploy path check of the module does. The policies that a Helm chart makes are not in the tree. The live query of the acceptance criteria reads them: on 2026-11-22 each of them has the type `Ingress` only.
7. **Fixture checks first.** Four `check_*` functions: a policy that writes both types and a policy with no types and an egress rule, which the rule refuses; a set of single-type policies, with written and with default types, which the rule accepts; and the scan of the tree.
8. **The checks and tests that name a policy read the new name.** `tests/gate/k8s_checks` (`argo_workflows`, `argocd_apps`, `deploy_stack`, `gateway_database`, `llm_gateway`, `object_store`, `runner`) and the tests `tests/ai/benchmark/test_k8s_llm_gateway.py`, `tests/ai/test_ai_gateway_portkey.py` and `tests/k8s/test_k8s_argo_workflows.py` look up a policy by name. They read the new policy of the same direction. The rules do not change, so the expected values stay. The docstring of the teardown test in `tests/commands/k8s/test_k8s.py` names the two monitoring policies.
9. **Spec deltas.** One ADDED requirement in `k8s-network-policies` for the row. Eighteen MODIFIED requirements that name a split policy now name the new policy.

## Rejected alternatives
- **Refuse only the shape: an egress rule that reaches the own pods on a port that no ingress rule of the policy admits from them.** Rejected: this was the first form of the row. It needs a model of the peers, the selectors, the `ipBlock` ranges and the ports (about 120 lines), it does not cover the other direction, and it can miss a case. It also let the 4 policies of namespace `devops` keep both types.
- **Keep both types and give the egress rules the ports of the ingress rules.** Rejected: the controller still runs the egress rules in the chain of the destination pod, so each later egress rule to the own pods opens the same path again. Two single-type policies remove the cause.
- **Narrow each in-namespace egress rule with no ports.** Rejected: in 6 namespaces an ingress rule admits every pod of the namespace on every port, so no port list is exact, and a list would stop paths that work today. Single-type policies are enforced correctly, so the ingress rules of the destinations hold.
- **A Kyverno or kube-linter custom check.** Rejected: Kyverno adds an admission controller and still needs a custom policy, and kube-linter has no check for this controller behavior, so a custom check is new code too.
- **A change to the controller.** Rejected for this item: the controller is part of k3s and is not in this repository. The private report upstream is a person step of #6708.
