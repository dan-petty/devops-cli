# Proposal

## Why

Issue #2911, part W4 of the tracker #2908. On 2026-10-31 `devops roadmap implement --plan` printed "No item to implement" while #2147 and #2747 were Ready and planned. Both items have the label `effort/medium`, and the default filter of the implement job asks for `effort/low`. The output gave no reason. A person or an agent had to read the code to find it.

The cause is in the plan. `plan_implement` and `select_stageable` list a reason only for an item that the filter names. An item that matches no filter is dropped without a word. And no command tells, for one item, why each job takes it or leaves it.

## What Changes

- New command `devops roadmap explain <issue>`. For the stage job and for the implement job it prints `yes`, or `no` with the reason of the first rule that fails. It uses the filter and the limit that the Service uses, and `--filter` and `--limit` replace them for one run.
- The rules are the rules of the jobs, not a copy of them. A walk over the items by priority (`walk_named`) is the one loop of both jobs: it returns the items taken, the items left out with their reasons, and the items that pass every rule but come after the limit. `explain` reads the result of that walk for its item. The filter has one new function, `StageFilter.mismatch`, that names the family the item misses.
- The reason texts live in `MESSAGES.roadmap` and nowhere else. The texts for "not an item" and "closed" were written twice (stage and implement). They become `item_left_not_item` and `item_left_closed`. Two new texts, `item_left_filter` and `item_left_limit`, serve the new rules. `explain` and the "Left out" lists print the same strings.
- `stage --plan` and `implement --plan` get `--why`. It adds a section "Matched no filter" that lists each open item the filter does not name, with the family it misses. Without `--why` the output is as it was. The new section is not part of "Left out", so the metric of skipped items counts the same items as before.
- `explain` makes no model call and no write. Its dry-run class is `request-plan`: `--dry-run` makes no request and lists the reads of a run.
- The rule "the failures ledger" of the issue is not built (see Feasibility). The group budget is reported from the stop record of an earlier run.
- Observable behavior changes (a command, an option on two commands, an output section, and the wording of two reasons), so the change carries spec deltas.
- The change fits one pull request.

## Capabilities

### New Capabilities

- `roadmap-explain`: the command that names, for one item, the first rule that stops each job.

### Modified Capabilities

- `roadmap-stage`: `--why` lists the items that matched no filter.
- `roadmap-implement-job`: `--why` lists the items that matched no filter.

## Feasibility

Checked on 2026-10-31 against the real system:

- The evidence holds. `devops gh api repos/dan-petty/devops-cli/issues/2147` and `.../2747` show open items with the labels `effort/medium` and `status/planned`. `DEFAULT_IMPLEMENT_FILTERS` in `src/devops_cli/roadmap/implement.py` is `("status=ready", "status=planned", "effort=low")`. `plan_implement` keeps only the items for which `filters.matches(item)` holds, so both items never reach the judge, and no reason is printed. The test `test_an_item_that_the_filter_does_not_name_is_not_in_the_plan` states this behavior.
- The rules already return reasons. `_Judge.reason` of `stage.py` and `_Judge.judge` of `implement.py` return the text of the first rule that fails, from `MESSAGES.roadmap`. So the first-failing-rule order, the texts and the "Left out" lists exist. What is missing is the filter reason, the limit reason, and a way to ask for one item.
- The selection can run for one item without a model. `plan_implement` calls no model. `plan_stage` calls the model only after `select_stageable` returns, so the selection is a function that can be called alone.
- The rule order of the issue is not the order of the code. The code checks the Status first, then the claim, the tracker, the author and so on. `explain` follows the code, so it never names a rule that the job would not name first. The design records this.
- The failures ledger cannot be read for an item. `FailureLedger` in `src/devops_cli/roadmap/run.py` counts failed rounds for each repository and job, not for each item. It keeps them in the memory of the Service and in a state file on the volume of the Service (`service_state_dir`). A workstation or a runner Job cannot read that file, and a read of the Service over the network is a touch of the cluster, which the issue forbids. So `explain` does not report ledger rounds. The record of the item holds the stop of its own: `implement.stopped` and `stage.needs_split`. `explain` reports those, with the text the job prints. The suspension of a whole job is on the Service `/metrics` (`CONST_SERVICE_METRIC_JOB_SUSPENDED`) already.
- A group over the budget is known only after the model plans the item. `explain` makes no model call, so it reports that rule from the record of an earlier run (`stage.needs_split` with the file cap of now), which is the rule `_recorded_split` of the job.
- The dry-run rule. `tests/invariants/test_dry_run_class_ratchet.py` requires a class for every command. `explain` reads GitHub and git, so its class is `request-plan` and it declares `--dry-run`, as `claim` and `return` do.
- The premise holds. No part of the item needs code that compensates for a missing tool.

## Existing Tool Considered

The need is specific to the rules of this roadmap, so no open tool covers it. The change reuses the rules of the jobs (`_Judge` of stage and implement), `StageFilter`, `priority_order`, `plan_implement`, `read_planned_changes`, `StoreRequests` and `render_dry_run`. It builds one function (`walk_named`, about 30 lines), one filter method, and `explain.py` (about 120 lines) that reads the result of the walk. The written cost is about 60 000 tokens to build and review, and the tests keep the rest. It replaces the two copies of the "not an item" and "closed" texts with one, and it deletes the loop that stage and implement each had.
