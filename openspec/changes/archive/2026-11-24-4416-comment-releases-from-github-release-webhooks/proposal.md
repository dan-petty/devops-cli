# Proposal

## Why

The `release_comments` row of the roadmap (#4416) posts `Released in <tag>` on a closed issue only on its 11-minute round, because `CONST_ROADMAP_WEBHOOK_EVENTS` holds no `release` event. A release that release-please just published therefore waits up to 11 minutes on an idle repository, even though the row already keeps an idempotent marker ledger and a `Live since <time>` pass.

## What Changes

- Add `CONST_ROADMAP_RELEASE_WEBHOOK_EVENTS` in `src/devops_cli/config/constants.py` and union it into `CONST_ROADMAP_WEBHOOK_EVENTS`, so the roadmap consumer subscribes to `release` and the onboard row requires that event of each hook.
- Name the `release` event in step 8 of `docs/CLUSTER.md`, extend the sorted event lists of `tests/server/test_server_service.py` and `tests/roadmap/test_roadmap_run_due_table.py`, and drop the `release` case of the no-subscriber table, which the subscription makes false.
- Parse the optional `release` object into the new `WebhookRelease` model of `src/devops_cli/models/webhooks.py`, with the six fields that the code reads.
- Refuse a `release` delivery in the roadmap consumer of `src/devops_cli/server/routes/webhooks.py` when its action is not `published`, when it is a draft, when it is a prerelease or when it holds no publication time, before any GitHub request.
- Add `comment_one_release` to `src/devops_cli/roadmap/release_comments.py`, carry the release of a delivery on `WebhookDelivery`, and register the scoped `("release", "published")` update of `src/devops_cli/roadmap/run.py` on the lane of the `release_comments` row.
- Run the scoped update at once from a published delivery in `src/devops_cli/server/routes/webhooks.py`, so a delivery that names no issue number runs its update, and say in step 20 of `docs/CLUSTER.md` that a published delivery comments at once and that the row keeps its 11-minute round.
- Keep the 11-minute round of the row, which reconciles a missed delivery and posts `Live since <time>` after the images run in the cluster.
- The change fits one pull request.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `roadmap-release-comments`: A published release delivery comments at once
- `roadmap-scoped-updates`: The Service runs a subscribed event's scoped update on the lane of its table row
- `roadmap-service-webhooks`: The payload holds the release fields, The consumer refuses an unwanted release delivery, The consumer takes the pull request, review, check and release events

## Existing Tool Considered

semantic-release/github (MIT, maintained) posts a success comment on each issue that a release resolves, but it belongs to semantic-release, while this repository releases with release-please and keeps its own marker ledger, release payload model and draft and prerelease refusal. The change extends the internal code instead of adopting the tool, at about 80k tokens to build, keep and fix and 1.5 hours of elapsed time, and it deletes no internal code: the comment path reuses `ReleaseLedger`, `marker` and `released_body` of `src/devops_cli/roadmap/release_comments.py`.
