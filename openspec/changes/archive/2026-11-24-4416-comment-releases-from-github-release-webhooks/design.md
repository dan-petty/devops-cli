# Design

## Decisions

- **Subscribe the roadmap consumer to the `release` event and run the update scoped to a published delivery on the lane of the `release_comments` row**: ADR 0017 makes each subscribed event run the update scoped to it at once, and the row's adapter `src/devops_cli/roadmap/run.py:def _run_release_comments_adapter` calls no model, so its update must not wait behind a model round.
- **Refuse a draft, a prerelease, an action other than `published` and a release with no publication time in the roadmap consumer, before any scoped update**: The refusal then costs zero GitHub requests, a refused delivery counts as ignored instead of a failed job, and the scoped update always holds a publication time for the release record it builds.
- **Make the issue number of the delivery optional and carry the release of the delivery on the record `src/devops_cli/roadmap/run.py:class WebhookDelivery`, so the release update reads its tag**: One delivery type keeps one map of scoped updates and one code path, and a release delivery names no issue number.
- **Gate the scoped branch of `deliver` on the release that the delivery carries, and keep the subject of a trigger an issue number**: The subject of a trigger in `src/devops_cli/server/routes/webhooks.py:def roadmap_consumer` is an issue number, so a release tag cannot be one, and `src/devops_cli/server/routes/webhooks.py:349:if scoped is not None and subject is not None:` is the gate that the group widens.
- **Reuse the ledger, the marker and the body of `src/devops_cli/roadmap/release_comments.py:class ReleaseLedger` with `marker`, `released_body` and `_comment_once` for the comment and the ledger**: The marker, the body and the ledger stay in one module, so the webhook path and the 11-minute round cannot drift apart.
- **Keep the release feed of the row as it stands, and build the release of the scoped update from the delivery**: `src/devops_cli/roadmap/release_feed.py:class GitHubReleaseFeed` already reads the closed issues of one release, so the scoped update adds no feed behavior and the feed module with its test stays unchanged.
- **Keep the 11-minute round of the row**: `DEFAULT_ROADMAP_RELEASE_COMMENTS_INTERVAL_MINUTES` is 11, and `Live since <time>` waits for the image builds and the rollout, so the round reconciles a delivery that GitHub lost.
- **Declare only the six fields of the release object that the code reads**: `src/devops_cli/models/webhooks.py:81:model_config = ConfigDict(extra="ignore", frozen=True)` drops the rest, so the model follows no change of the GitHub release object.
- **Add the event through a named constant, `CONST_ROADMAP_RELEASE_WEBHOOK_EVENTS`, and union it into `CONST_ROADMAP_WEBHOOK_EVENTS`**: `src/devops_cli/config/constants.py:4040:CONST_ROADMAP_WEBHOOK_EVENTS: Final[frozenset[str]] = frozenset(` is built from named event sets, and a named set keeps the intake keys free of the event.
- **Modify the base requirement `The Service runs a subscribed event's scoped update on the lane of its table row` of `roadmap-scoped-updates`, and keep its whole-round hint only for a delivery that carries no release**: A published `release` delivery names no issue number and no pull request number, and the unmodified requirement would keep it a whole-round hint, which contradicts the scoped update that this change adds.
- **Drop the `release` case of the no-subscriber table in the group that subscribes the event, and not in a later group**: `tests/server/test_server_service.py:1884:("release", _event_payload("published")),` asserts `tests/server/test_server_service.py:1901:[(200, {"status": "no_subscriber"})] * 2,`, which the subscription makes false, so the group that adds the event is the group that must change the case.
- **Keep step 8 of `docs/CLUSTER.md` in step with the constant, and let the open repository-hook items #6431, #6630 and #6013 land on that line separately**: `find_issues` names them on the same constant and the same hook row, but the onboard row writes the event and the 11-minute round reconciles a delivery that never arrives, so none must be delivered first.

## Rejected alternatives

- **Keep the poll only and subscribe to no event**: `src/devops_cli/config/defaults.py:1239:DEFAULT_ROADMAP_RELEASE_COMMENTS_INTERVAL_MINUTES: int = 11` makes the row due every 11 minutes, so a release then waits up to 11 minutes, which is the latency of #3672.
- **Add the release to `CONST_ROADMAP_INTAKE_BATCH_KEYS`**: `src/devops_cli/config/constants.py:4040:CONST_ROADMAP_WEBHOOK_EVENTS: Final[frozenset[str]] = frozenset(` shows that the event set is built from the intake batch keys, and a release delivery names no issue, so an intake key would run a whole intake round.
- **Refuse the draft, the prerelease and the other actions in the scoped runner**: `src/devops_cli/server/routes/webhooks.py:394:refusal=refuse_comment,` runs the refusal before `deliver` queues anything, so a refusal in the runner would cost the GitHub requests of the update.
- **Run the scoped release update on the model lane**: `src/devops_cli/roadmap/run.py:def _run_release_comments_adapter` calls no model and needs no clone, so a model-lane update would wait behind a model round for no reason.
- **Run the scoped release update on the triage lane**: `src/devops_cli/roadmap/run.py:1389:SCOPED_UPDATES: Mapping[tuple[str, str], ScopedUpdate] = MappingProxyType(` gives the triage lane the `issues` actions alone, and a release delivery names no issue.
- **Write a new module for the webhook path of the comment**: `src/devops_cli/roadmap/release_comments.py:class ReleaseLedger` already holds the ledger, and `marker`, `released_body` and `_comment_once` hold the marker and the body, so a second copy would drift.
- **Call `comment_releases` with no cluster and no registry**: `src/devops_cli/roadmap/run.py:def _run_release_comments_adapter` reads the releases of the window through the feed listing, so the update would not be scoped to its delivery.
- **Add a second delivery type for the release**: `src/devops_cli/roadmap/run.py:class WebhookDelivery` is the one record that `src/devops_cli/roadmap/run.py:def scoped_update_of` reads, so two types give two paths to the same map.
- **Set the subject of the trigger to the release tag**: The subject of `enqueue_trigger` in `src/devops_cli/server/routes/webhooks.py:def roadmap_consumer` is an issue number, so a tag string fails the type check; the plan gates the scoped branch on the release of the delivery instead.
- **Model the whole GitHub release object**: `src/devops_cli/models/webhooks.py:81:model_config = ConfigDict(extra="ignore", frozen=True)` sets `extra="ignore"`, so fields that no code reads would only follow each change of GitHub.
- **Remove the 11-minute round**: `src/devops_cli/config/defaults.py:1239:DEFAULT_ROADMAP_RELEASE_COMMENTS_INTERVAL_MINUTES: int = 11` makes the row due every 11 minutes, and its second pass posts `Live since <time>` after the images run, so a lost delivery would lose that comment.
- **Keep the base requirement of `roadmap-scoped-updates` unmodified and add the release rule as a separate requirement**: `openspec/specs/roadmap-scoped-updates/spec.md` states that the consumer hands a delivery to its scoped update only when it names an issue number or a pull request number, so an unmodified requirement would contradict the scoped update of a release delivery.
