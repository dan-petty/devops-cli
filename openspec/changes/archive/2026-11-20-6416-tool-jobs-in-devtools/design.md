# Design

## Decisions

- **A stage of the pinned Dockerfile for the host jobs.** `.devcontainer/Dockerfile` pins the image already, and its `devcontainers-cli` stage gives the Dev Containers CLI to the devcontainer build action in the same way. The stage `devtools-bin` copies only the nine commands that the host jobs run, so an export writes about 600 MB and not the whole `/usr/local/bin` of the image. The stage names no version.
- **A cache in front of the build.** The build pulls and unpacks the whole image, 1796 MB in 10 layers, to export the commands: 35 s to 61 s for each job in the first runs. `actions/cache`, pinned by SHA as in `.github/actions/setup-toolchain`, restores `$RUNNER_TEMP/devtools-bin`. The key is `devtools-bin-<os>-<arch>-<digest>-<sorted commands>`. The key step reads the digest from the `FROM` line of the stage `devtools`, so a Renovate digest update makes a new key, and another edit of the Dockerfile keeps the key. The build runs only on a miss, and the cache step saves the directory at the end of the job. The log of the cache step names the digest. Measured on the pull request at `adc6cfd75`: a miss took 39 s to 59 s for the step (Static Analysis 39 s, the test shards 42 s to 55 s, the Service Image Tests shards 41 s to 57 s, Image Pins 51 s, Copilot Setup Steps 59 s), and a hit took 1 s to 2 s (a test shard and a Service Image Tests shard 1 s, Copilot Setup Steps 1 s, Image Pins 2 s, with 34 MB for kubectl and helm). The old `install-tools` steps took 6 s to 10 s. A pull request restores an entry that a run on `main` saved: each list of commands has a job that runs on `main` (`Static Analysis` and the shards on each push, `Service Image Tests` on its schedule, `Copilot Setup Steps` and `Image Pins` on a push that changes their paths, `.devcontainer/Dockerfile` among them). So a job pays a miss once on `main` for each digest of the image and list of commands, and again after GitHub evicts the entry.
- **The action copies only the named commands, and the job puts them on PATH.** The action outputs the directory and writes no environment file: zizmor cannot know the trigger of a composite action, so it reports each write of `GITHUB_PATH` there (`github-env`), and it reports none in a workflow whose triggers are safe. The next step of each job that runs the commands puts the directory first on `PATH` from `env:`, before `/usr/local/bin` of the runner. A test shard gets promtool and no other tool of the image, so the tests that skip where a tool is missing run as before. The Service Image Tests copy the two commands to the tools directory that they mount, and the mount holds no other tool.
- **Rule Pack Tests stays a container job.** The Semgrep of the image is a venv whose `python` is `/usr/bin/python3.14` of the image, so the action cannot take it to the host. The job runs only when a rule file or its workflow changes. `Initialize containers` took 52 s and 105 s in two runs, of 110 s and 158 s. The Copilot agent gets no Semgrep for the same reason: no hook of `.pre-commit-config.yaml` and no row of `devops ci` runs Semgrep.
- **Image Pins runs on the host, and on a push to main.** As a container job it spent 40 s in `Initialize containers` on each run. kubectl and helm are single files, so the cached action gives them in 1 s to 2 s on a hit. No other job asks for kubectl and helm, so the workflow also runs on a push to `main` that changes its paths: an entry that a pull request saves is in the scope of that pull request only. The job only reads, and the concurrency group of a push to `main` is its commit, so a merge cancels no run before it saves the entry.
- **The rules lock refuses an old `semgrep_version` field.** The model of an entry already sets `extra="forbid"`. `rules.lock` is a generated file that `--check` holds equal to what `devops review rules test` writes, so a lock with the old field is drift, and the error names the field. One run of `devops review rules test` writes the lock again. To ignore the field would need `extra="ignore"`, which also accepts any other field that no code writes.

## Rejected alternatives

- **Every tool job in a container, as the issue body planned.** The `bwrap` row of `Static Analysis` needs the sandbox of the host (`docs/SDLC.md`, row 15), and the default seccomp profile of Docker refuses its namespaces. The shards write coverage data with `/__w/...` paths that `Tests & Coverage` cannot join on the host. GitHub ignores `container` in `copilot-setup-steps`. The Service Image Tests run `docker load` and `docker run`. A container job also pulls the whole image on each run, with no cache.
- **The stage build with no cache.** The first runs of this change took 35 s to 61 s for the step, and the slowest shard and the join of `Tests & Coverage` took 424 s, over the 360 s of AGENTS.md rule 5.
- **`docker create` and `docker cp` of the full image.** The pull is the same 1796 MB as the stage build, and the workflow must name the image once more.
- **A layer fetch with crane or oras.** It downloads only the layer that holds the commands, but the step must find that layer by its content, which changes with each devtools build, and the two tools are not on the runner.
- **`jdx/mise-action` with the `mise.toml` and `mise.lock` of the devtools repository.** The workflow then reads the lock of another repository at a ref that Renovate must also move, apart from the image digest, and the job downloads each tool from its release again.
- **A separate tools image of the devtools repository.** It holds the same commands in fewer layers, but it is a second image to build, publish and pin, and the devtools repository has no such image.
- **A `docker://` step of the devtools image that copies the commands.** A Docker action writes as root, and it can write only to the workspace and to the runner home that the runner mounts. The workflow names the image once more, and the pull is not cached.
- **Maintained setup actions.** `opentofu/setup-opentofu` and `aquasecurity/setup-trivy` cover two of the nine commands. Each one adds a version input apart from the image, against the owner decision of 2026-11-19.
- **Regenerate `rules.lock` with Semgrep 1.186.0.** The next Semgrep of the image fails the check again, so each image update needs an edit under `src/`.
