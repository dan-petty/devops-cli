# Design

## Decisions

- **Plain issue-branch flow** (owner decision of 2026-11-21, #3702 comment 7065393209). The phases work the branch as a developer does:
  - `prepare` (App token, no code of the pull request) makes a full clone in a folder that is new to the run, switches to the branch, and records the base and the lease.
  - `agent` (no GitHub credential) rebases, does the work and writes the patches.
  - `publish` (App token, no code of the pull request) applies the patches in a new repository, commits as the bot and pushes with `--force-with-lease`.
- **The base and the lease come from `prepare`.** `prepare` fetches nothing after the clone: the full clone holds the default branch and the pushed branch. The lease is the tip of the pushed branch, or empty for a new branch, which must not exist when `publish` pushes. The base of the patches is the lease when the lease is not empty and the run makes no rebase (`--no-rebase`). In every other case, a new branch too, it is the tip of the default branch. The agent rebases onto that commit and makes no remote call. `publish` takes the base only from the state, never from `outcome.json` or the tree of the agent, and fetches it at depth 1 into its new repository. The full clone makes a merge base sure, so no deepen and no merge-base check is necessary.
- **The archive stays its own commit.** The agent writes `work.patch` up to the commit before the archive commit, `archive.patch` with the archive commit alone, and `after.patch` with the commits after it, such as a fix round of a scoped check. `publish` writes one commit of the bot for each patch that changes a file. A later rebase can then skip the archive commit and archive again.
- **The agent settles the stops of the rebase as a developer does.**
  - `git rebase --skip` for the archive commit of the item only (owner decision: "skip the archive commit"): `git show --name-status REBASE_HEAD` shows a removal or a move out of `openspec/changes/<item>-`, and every path is an OpenSpec path or a generated document. The plan commit adds its change folder, so the rule keeps it, and a conflict there stops the item with the class `conflict`. The conflict fixer of #6620 holds the same rule; #6640 makes the two copies one function.
  - For conflicts only in the generated documents and `uv.lock`, the side of the default branch by the stage of the index (`git rm` when the default branch deleted the file, else `git checkout --ours`), and a new generation.
  - Any other conflict, and a git command of the settle that fails, aborts the rebase and stops the item with the class `conflict` and the action `wait`, with nothing to push. The model step that settles such a conflict is #6640.
  - The agent takes the rebase choice of `prepare` from its inputs, so the base and the patches agree.
  - The implement job no longer calls `fix_rebase_conflict`.
- **The patch, the publish and the clone come from #6655.** The agent writes each patch with the fixed format flags of `patch.py`, from commit to commit, so a file that no commit holds is not published, as before. `publish_patch` applies the patches in a new repository and gives its git calls their own home folder. The outputs go into an `out/` that the agent phase makes after the sweep.
- **`publish` reads the new tree from its objects.** The folder of the change, `proposal.md` and `tasks.md` come from `git ls-tree` and `git cat-file` of the new commit. The title and the body are built from them and from the facts of the item. The why of the agent is checked again with `safe_text`, `closing_keyword_in` and `build_body`, and the title of the item replaces a why that fails.
- **The marks come at the end.** `publish` writes the record of the run once, from `outcome.json`. A killed Job loses the groups of its run: a run makes no push before `publish`. `devops roadmap follow` shows only the live log of the Job while it runs, and the trace of the last run that reached `publish`. `roadmap/steps/open.py` reads `implement.checked_sha`, which `publish` writes after the push, as before.
- **A second run pushes nothing.** `publish` pushes no commit when the lease holds the new tree already, and a second `publish` of a run that wrote a result writes nothing. `prepare` clears `implement.published_sha` and `implement.result`, so `publish` takes the sha as the lease only after its own push, also at a stop. A `publish` that runs again takes the draft from `implement.pr`, and deletes a branch only when the run made it, as `prepare` found no branch.
- **The plan title stays.** After the first push the plan is inside a commit of the bot, so `prepare` records the summary of the plan in `implement.plan_summary` once and later Jobs read it. A title with a closing keyword gives way to the title of the issue.
- **The withdraw stays, as small as before.** An earlier Job can push its work at a stop. `prepare` records `implement.base` once: the tip of the branch, or `new`. At a return to New, `publish` pushes the base back with a lease on the tip that `prepare` found, or, for `new`, deletes the branch with that lease and closes the recorded draft. The fetch of the base takes its full history: after a rebase no branch of `origin` holds the base, and `origin` refuses a shallow commit that no branch holds.
- **Until #3700, the `git_call` calls of `prepare` and `publish` read no global or system configuration** (#6655): the clone, the read of the plan title, and every git call of `publish`. `--phase all` runs the phases in one container, and an earlier item of the same Job can have run code of a pull request in the home folder. The read of the plan title in `prepare` gets the state folder of the run as its home. The other git reads of `prepare` (the authors, the profile, the change folders and the comments of the step inputs) use the configuration of the session. This change adds no git hardening before #3700.
- **The symlink stop of the step stays until #3700.** `publish` refuses a new or changed link, gitlink and `.gitmodules`. The stop in the step keeps a link out of the formatters while the agent and the token share a container.
- **No count line and no new token permissions.** One process mints one token for the three phases in `--phase all`, so the token without `workflows: write` and the count line of the agent container wait for #3700. `publish` refuses a workflow file that the merged plan does not name.

## Rejected alternatives

- A push of the rebased branch in `prepare`: the rebase can need the settle of a conflict, which is work of the agent.
- One commit for the whole run: a later rebase would skip the whole item when it skips the archive commit.
- A patch of the working tree with `git add -A` for implement: a file that no commit holds was never published, and the run folder holds no ignore rule of the target.
