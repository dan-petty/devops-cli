# Design

## Decisions

- **A flag, not the name alone.** `--skip-wait` leaves out the wait. The name of an item alone does not: the Jobs that #5412 starts from the Service name `--pull` too, and they keep the wait. The flag needs `--confirm` and one of `--item` or `--pull`, so a person cannot skip the wait of every Staged item.
- **One more attempt for each release.** `fix_plan.version` holds the release of the last counted attempt on the head of `fix_plan.key`. Releases only go forward, so when that release is older than the current one, each counted attempt on the head ran on an older release. A record with no `fix_plan.version` is older, because the key comes with this change. A version that `packaging` cannot read is not older, so the cap holds. The extra attempt runs on the current release and writes it, so the next named run on the same release is refused.
- **The budget decides the class of a SIGTERM.** Kubernetes sends the same SIGTERM for an eviction, a node drain and the deadline of a Job. The pod has no API token to read its own conditions. The setting `roadmap.fix_plan.time_budget_seconds` stays below the deadline of the Job, so a SIGTERM before the budget is spent did not come from the Job controller. A SIGTERM after it is `deadline`, also when a drain comes in that time: that error counts the attempt, which is the safe side. A person who deletes a Job before the budget ends makes an evicted attempt.
- **An evicted attempt does not count in any rule.** It keeps the marks of the attempt before it: the count, the time and the release. So the next due round of the row, or the retry of a Job, takes the plan at once and does not wait 6 hours. `fix_plan.evicted` bounds this at 3 for each head, and a later evicted attempt counts. A free retry that is not bounded can repeat forever.
- **A stop of the Service is evicted.** The row of the Service ends an attempt at its next safe point when the pod drains for a rollout or a node drain (#4485). The class is the same as an eviction of a Job pod.
- **No result line for an evicted attempt.** A stop of the Service writes no line today, because the job did not fail (`docs/roadmap/job-success.md`). An eviction is the same case. A deadline kill spent the tokens of the attempt, so it writes the line with `result=timeout` and the class `timeout`, and the name `kill=deadline` tells it apart from the budget `timeout`.
- **Write in the grace period, then exit.** The handler sets SIGTERM back to the default before it raises, so a second SIGTERM ends the process at once. The step writes one record update and the lines, then raises `AttemptKilled` with the class. The command exits 75 for `evicted` and 143 for `deadline`. The failure classifier already reads 143 as `timeout`.
- **The handler only in the command.** `sigterm_raises` sets a handler only in the main thread. The Service has its own SIGTERM path (`begin_service_stop`) and runs the row in a worker thread, so the row keeps that path.

## Rejected alternatives

- **The name of an item skips the wait.** Rejected: #5412 makes Service Jobs that name `--pull`, and the Service must keep the wait (issue #5413, Proposed Fix 1).
- **Classify the kill in the next run from the Job status.** The reason `DeadlineExceeded` of the Job and the condition `DisruptionTarget` of the pod tell the classes apart. Rejected: the pod of a Job mounts no service account token (`automountServiceAccountToken: false` in `k8s/devops/cronjob-runner.yaml`), the Service does not track the Jobs that a person starts with `devops k8s run-job`, and the record does not name the Job of an attempt.
- **`podFailurePolicy` alone.** Rejected as the only rule: it counts pods of one Job, not attempts on a head over many Jobs and rounds of the Service. It stays the retry owner for #5412.
- **A new failure class `evicted`.** Rejected: an evicted attempt writes no result line, so no class is needed, and the class list of `roadmap/failure.py` is fixed.
- **Raise `ServiceStoppingError` from the handler.** Rejected: it is an `Exception`, and the model client, the retries and the planner catch `Exception` in places, so it could become a `failed` attempt or a retry.
