# Design

## Decisions

- **The Job runs the hook stages as its own child.** `implement_hooks.py` starts `uv run pre-commit run --hook-stage <stage>` through `run_subprocess`. The child is no `git` client, so the process runner gives it no GitHub token, and `build_subprocess_env` drops every variable that matches `*TOKEN*`. The agent can edit `.pre-commit-config.yaml`, and the config can name any `entry`. No hook of the repository ever runs inside a `git commit` or `git push` of the Job.
- **The commit stage is an exit check of the step.** It comes last, after the format, the verification commands and `ruff` and `mypy`, on the staged files (`_stage` has staged all). `pre-commit run` with no file option reads the staged files, as the git hook does. A hook that fixes a file makes pre-commit exit 1. The check then stages the changed files and runs the hooks one more time. This is what a person does after a failed commit, and it makes no repair round for a fixer that converges. A second exit 1 is a failure that goes to the agent.
- **A repository with no hook configuration runs no hook.** The implement job runs for other repositories too, and `pre-commit run` fails when the file is missing. The agent can also edit the file: `repos: []` makes every hook pass. So no run reads the file of the checkout. `trusted_config` writes the file of `origin/<default>` to the cache directory (`git ls-tree` finds it, `git show` reads it), and every run of `pre-commit` gets it with `--config`: the install, the `pre-commit` stage of a step, and the `pre-push` stage of the scoped checks. The step gets the path from the Job (`hooks`), and runs no hook when it gets none. An item that changes the configuration itself is not checked with its own change: the default branch decides.
- **Exit 1 is repairable, other codes are not.** pre-commit exits 1 for a failed hook, and 3 for an unexpected error. A step with exit 3 stops with the output, because the agent cannot fix a broken environment.
- **One budget of repair rounds.** `roadmap.implement.repair_rounds` (default 3, at least 0) bounds the extra turns of a step. A turn for a failed `ruff`, a failed `mypy`, a failed hook or a missing tick takes one round. `_attempt` loops: judge the exit, ask for a repair while a round is left, judge again. A turn that changes a file that it may not change, or a turn that a limit ends, stops the step as before. `StepOutcome.repair_rounds` counts the turns.
- **Environments are installed once, by the Job, before the first step.** `pre-commit install-hooks` clones the two remote repositories and builds their environments in `PRE_COMMIT_HOME`, which is `<data dir>/pre-commit` on the home volume. A failed install (no network, no disk) stops the item at the step `hooks` before the first model request. The step on its own (`devops roadmap implement --group`) installs them at its first `pre-commit run`.
- **Scoped checks run after the final rebase.** `_push` rebases onto the fetched default branch, then runs the scoped checks, then pushes. So the head that passes is the head that goes out. A fix step that a failed check causes adds a commit. The docs are generated again after it, because a fix can change a command or an option. Then the checks run again.
- **The scoped checks are three commands.** (1) The `pre-push` stage over the range `origin/<default>..HEAD`: it holds every hook that the devcontainer runs on a push, and it comes from `.pre-commit-config.yaml`. (2) `devops ci --check --only constructs,docs,openspec`: the ast-grep scan, the docs sync and the OpenSpec gate over the final tree, which the commits of the docs and the archive reach with no hook. The names are rows of `get_check_specs()`, and a test holds that. (3) `devops ci test <modules>` with the test modules that `select_tests_for_sources` (the selector of that command) picks for the changed Python files of `src/` and `tests/` (added, copied, modified or renamed). The Job selects the modules itself and passes them as paths, so the command makes no second selection. The check stays scoped: a change to a shared module (the constants, the settings, the messages) selects hundreds of test modules (333 of 725 for this item), which no Job of 2 CPUs runs in the time limit of a command. Above `CONST_ROADMAP_IMPLEMENT_SCOPED_TEST_MODULES` (30) modules, only the changed test modules run. When no test covers the change, no test command runs: `--no-fallback` would fail the check, and no fix step can repair that. The comment on the pull request says which case held. The required checks of CI run the suite.
- **A failed scoped check is a fix step.** `run_fix_step` already exists: the group "Make check `<name>` pass" with the log, the verification commands of the change, and the exit checks of a step. The Job reuses it, up to `repair_rounds` times for all scoped checks together. When the budget is used, the Job stops the item at the step `scoped checks` and pushes nothing. A stop that a fix step causes there pushes nothing either. So does any error in the phase: `_scoped_checks` turns a `DevOpsCLIError`, an `AIClientError` and a `TimeoutExpired` into a stop that pushes nothing, except the rejected credentials, which end the run as before. A hook run that runs out of time is a `HookRun` with an exit code that no repair round can fix, so the step stops with the reason, as for exit code 3. The stops of earlier steps keep their rule: they push the commits that passed.
- **A failed check after the push gets the same bounded rounds.** `_checks` loops up to `repair_rounds` times: a fix step, `_push` (which runs the scoped checks again), a comment for the round, and a new watch. The comment holds the outcome line and the scoped runs of the round. The comment of #3053 on the other steps of an item stays its work.
- **The comment on the pull request is the trace.** `_outcome_line` shows the repair rounds of each step. A new line for each scoped run shows the check, the result and the seconds. Run time per item is read from these lines.
- **`devops-ci-pre-push` is split.** The runner image holds no `actionlint`, and the `actionlint` row fails when the program is missing. A push that changes no workflow has nothing for `actionlint` or `zizmor` to check. So `devops-ci-pre-push` runs `lint,format`, and `devops-ci-workflows-pre-push` runs `actionlint,zizmor` with `files: ^\.github/(workflows|actions)/`. A pre-commit hook in the `pre-push` stage that has `files` and no `always_run` runs only when the pushed range changes a matching file.
- **The runner holds what the local hooks run.** The local hooks run `uv run ast-grep` and `uv run devops`. `pre-commit` and `ast-grep-cli` are dev dependencies, and the runner stage syncs them. A test reads every local hook of the config and checks that its entry starts with `uv run` and names only a tool that the lock or the Dockerfile provides. A new hook that needs another program fails the test until the image holds the program (#3072).

## Rejected alternatives

- **`pre-commit install` in the clone.** Rejected, with the evidence in the proposal: git runs the hook as its child with `GH_TOKEN`, and the agent writes the hook configuration. A fix would be to run `git commit` and `git push` with no token, but a push needs the token for its credential helper.
- **Install the hook environments in the image.** The runner image would hold a cache of 51 MB, and the Dockerfile would copy the config. The root filesystem is read-only, and `pre-commit` writes `db.db` and a lock file in `PRE_COMMIT_HOME`. The database holds the absolute path of each clone, so a copy of the cache to the home volume would still point into the image. The install costs 9 s in a Job of about an hour, and the perimeter admits the fetch. The image build is the check that a build time over 5 minutes is a P0 for, and `#3072` edits the same Dockerfile. Rejected as more cost than gain.
- **Run `devops ci --only` rows in place of the hooks.** There is no row for the file hygiene hooks or `detect-private-key`. A list of equal checks in the Job would be a second copy of `.pre-commit-config.yaml`.
- **Two budgets, one for the hooks and one for the static checks.** A repair for a hook can break `mypy`, and the reverse. Two budgets need a rule for the crossing. One budget is simple and bounded.
- **Run the scoped checks before the final rebase.** The rebase can change the head, and the push would send a head that no check saw.
- **The full `devops ci` before the push.** It takes 2.5 minutes on a quiet host and more under load (ADR 0014), and the required checks of CI run it. The scoped checks cover the changed paths.
- **Add `actionlint` to the runner image.** That is the work of #3072 and it changes the Dockerfile that another change edits. Path scoping is right on its own: a push without a workflow change has nothing to lint.
- **Push the head that failed, so the draft shows it.** The issue asks that the Job pushes only a head that passed the scoped checks.
