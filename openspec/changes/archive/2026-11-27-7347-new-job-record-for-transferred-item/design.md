# Design

## Decisions

- **One rule for a block, in the store.** `written_elsewhere(held, number)` of `store.py` says whether the block `held` of issue `number` was written for another issue. `own_record` gives the block, or an empty record. Each read and each write of a record takes the block through `own_record` first, so no key of such a block reaches a row or a Job, and no write merges into one.
- **The branch tells.** A block was written for another issue when a branch that it names is the branch of another issue number: `stage.branch`, `implement.branch`, and the `branch` of the JSON of `stage.pending`. A job names each branch `<type>/<issue>-<slug>`, so the branch tells the number that the item had when the job wrote the block. A branch that names no issue number tells nothing, and so does a block that names no branch.
- **The whole block is empty, the item fields too.** A field key of a block (`Status`, `Priority`, `Value`, `Effort`, `Owner`) says that a job of this repository wrote that label. `field_values`, `Item.holds_service_stop`, the claim (`claim.py`) and the Status sync (`status_sync.py`) read it to tell the label of a job from the label of a person (ADR 0016). No job of this repository wrote the labels of an issue that came with them, so each label reads as the value of a person, and no job reverts it. The keys of another version go with the block for the same reason: no release of this repository wrote them.
- **The block of a write.** `record_block(held, changes, number)` is the one function that builds the block of a record write, for the GitHub store (`_edit_issue`) and for the in-memory store of the tests. It takes `own_record` of the block that GitHub holds at the read of the write, not the record of the Item of the caller, and then calls `encode_job_record`. A block of another issue with no change gives no block: the body then ends at its text. `encode_job_record` does not change, so the block of the record of an issue is the block that the base writes for the same record, byte for byte. No item gets a body write only because of this release.
- **Where the reset runs.** Each record write resets: `set_field`, `set_fields`, `set_marks` and `write_issue_body` all go through `_edit_issue`. The stage round also resets with no other write. `read_stage_round` puts the items with `foreign_record` into `StagePlan.resets`, by the item scope of the round (`_items_of`), and `StageWriter.begin` sends `set_marks(item, {})` for each one before the removals. The three callers of `begin` get the reset: `plan_stage` of the command, the stage row of the Service (`stage_submit.py`) and the stage Job (`stage_job_phases.py`). A reset that fails is a failed write of that item, as each write of `write_each`.
- **The flag on the record.** `IssueRecord.foreign_record` and `Item.foreign_record` say that the body holds such a block. The stage round reads the flag from the listing and sends no request to find the items. The field changes the schema of `IssueRecord`, so `LISTING_SCHEMA_KEY` changes and each lane reads its listing in full one time. That read also replaces each record that an older release decoded.
- **The plan pull request of a record.** `recorded_plan(item)` gives `RecordedPlan(pull, branch)` from `stage.pr` and `stage.branch`, or None when the number is no number or the branch does not name the item. `RecordedPlan.is_pull(number, head_ref)` compares a pull request with it. A recorded number alone names no pull request of the item.
- **The watch row.** The GraphQL query reads `headRefName`, and `_find_plan_item` takes the head branch. The candidates of the REST round and of the scoped round carry the item of the record as a hint. `_process_rest_pulls` reads the pull request and drops the hint when the head branch is not the recorded branch. It then looks for the item by number and head branch, as the GraphQL round does. `_check_closed_stage_plans` reads the pull request and writes for the item only when `is_pull` holds. The recorded branch names its item, so at most one item has a pull request as its plan.
- **The cleanup of a closed item.** `_reconcile` judges a recorded branch only when it names the item. `StageWriter._remove` takes the recorded number as the draft only when an open pull request of that number has the branch as its head. It finds that in the one read of the open pull requests that the cleanup of an orphan already makes.
- **A plan that closed with no merge.** `staged_plans` takes an item only when `recorded_plan` gives a plan, so a number with no branch that names the item sends no read. `closed_plans` takes the close as a rejection only when the head branch of the pull request is the recorded branch.
- **The round of `stage_ready.py` and the implement selection.** No row calls `mark_stage_ready` today, and the path holds the rule for the row that calls it again: `_recorded_pull` reads through `recorded_plan`, and `_settle` records no outcome for a pull request whose head branch is not the recorded branch. `_pull_reason` of the implement selection takes the branch of the route. When the head branch of the recorded pull request is another branch, it leaves the item out with `implement_left_pull`, the reason of a pull request that is no open draft.
- **Each writer of `stage.pr` writes the branch.** `_stage_one` writes `stage.branch` and `stage.pr` in one write. `_record_pr_marks` of the open step wrote the number only, so a plan that `devops roadmap step open` opened had no recorded branch. It now writes the head branch as `stage.branch` in the same write, and only when the branch names the item: a branch of another issue number in the block makes the block the record of another issue.
- **The orphan and the open row.** `orphan_mark` gives the mark only when its branch names the item, and `open_candidates` takes `implement.branch` only when it names the item.

## Known limits

- **A record of another issue that names no branch of another number.** A block that names no branch, such as a block that holds only `implement.job`, or the block of an item that keeps its number, reads as the record of the issue. The rows prove each recorded number and branch before a write (the decisions above).
- **A plan pull request that GitHub does not hold.** A block that passes the check can hold `stage.branch` with the number of the item and `stage.pr` with a number that the repository does not hold. The read of that pull request then fails the item of the stage round in each round, as before.
- **A record with `stage.pr` and no `stage.branch`.** The stage job always wrote both keys in one write (`_stage_one`, since #2686). Only `_record_pr_marks` of the open step wrote the number alone, for a plan that `devops roadmap step open` opened with a store. Such a record names no plan: the `watch` row and the stage round do not take its pull request until a run of the open step on that pull request records the branch.
- **The labels of the issue.** GitHub keeps the labels of a transferred issue that the new repository also has. The change removes no label: a label is the value of a person, and the rows read it as one.
- **A branch whose slug starts with a number.** `issue_of_branch` reads the number after the type as the issue, so a branch such as `fix/2026-cleanup` names issue 2026. No job writes such a branch: each branch that a job records starts with the number of its item.
- **The entries of the brain.** An entry that an older release wrote holds the record as that release decoded it. A conditional read that GitHub answers with 304 saves the entry again (`_revalidate_issue`), so the entry lasts until the issue changes. A read of one issue then gives the old decoded record, and each row still proves a recorded number and branch before a write. The write that replaces a record changes the issue, and the store then saves the new record.

## Rejected alternatives

- **A repository stamp by name in the block.** Each record write would put the name of the repository into the block, and a read would give an empty record for a block with another name. That finds a block with no branch key and the block of an item that keeps its number. But a rename of a repository or a move to another owner changes the name (`RepoRef.key` of `src/devops_cli/github/repo_ref.py` is the casefolded `owner/name`), so each record of the repository would read as empty, and the next write would reset it. A stamp by the immutable repository id is possible later and is not part of this change: the REST payload of an issue holds `repository_url` and no id (`_IssuePayload` of `github_store.py`), so each store would need one more read.
- **Keep the item fields of such a block.** `status_sync.py:202` compares `job_record[Status]` with the Status label to see that a job wrote the label, and `claim.py:145` releases a claim by it. With the fields kept, the Service takes a label that came with the issue as its own write.
- **Reset in the read.** A read that writes breaks the rule that a plan and a dry run send no write (`roadmap-stage/round`, "A stage plan makes no GitHub write"), and the listing reads each item in each round of each lane.
- **Close the open pull request that has the branch as its head, whatever its number.** `StageWriter._remove` does that for an orphan, whose record holds no number. For a closed item the record holds a number, and a pull request with another number is one that the job did not record.
