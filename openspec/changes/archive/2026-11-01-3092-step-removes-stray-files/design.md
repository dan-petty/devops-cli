# Design

## Decisions

- **Remove first, then keep `git add -A`.** The stray files are gone before `_stage` runs, so `add -A` stages exactly the tracked changes and the allowed new files. The three calls of `add -A` stay as they are. The other way is to replace `add -A` with an add of an allowed set. That needs a list of changed tracked files (`git diff --name-only`) and a list of allowed new files, and each of the three call sites would build it. One removal at the start of the checks is the smaller correct change.
- **A stray file is untracked, not ignored, and not allowed.** `git ls-files --others --exclude-standard -z` gives the untracked, not ignored files. Git applies `.gitignore`, `.git/info/exclude` and the global excludes, so the step parses no ignore file. An ignored file such as one under `.data/agent/scratch/` is never listed, never deleted and never committed.
- **The group allows a file in three cases.** (a) The file is a code span of the group text: the `Changes:` line and the tasks. Every created path is in `Changes:`, so this covers `creates`. A `Reads:` path is a code span too, and it is tracked already, so it never shows as untracked. (b) The file is under `openspec/changes/<item>-*/`. (c) The file is `test_*.py` under `tests/`, and some test file that the group names sits in the same directory. So an agent may add a second test file next to the one that the plan names, in the mirror directory of the module. A file in the root of the checkout, or in a directory that the group does not name, is a stray file.
- **The paths are compared as normalised POSIX paths.** `posixpath.normpath` turns `./tests/x.py` into `tests/x.py`. A code span that is a command or a word never equals a path of the checkout, so it allows nothing.
- **The step deletes with `Path.unlink`.** The names from git are relative to the checkout and git lists no path outside it. A stray symbolic link is unlinked and its target stays. The step removes no directory: git does not track an empty directory, and a reset runs `git clean -fd`.
- **The removal runs at two places.** It runs at the start of `_exit_failure`, which is after every turn that ends the first run. It runs after the extra turn too, before `_foreign_change` compares the checkout with the tree of the first turn. Without it, a stray file that the extra turn writes would stop the step as "a file the step had not changed".
- **The names go to three places.** `ToolCallLog.removed_stray` writes one line to the Job log and keeps the names, masked and escaped as the other lines of the log are, because the name is text that the model chose. `StepOutcome.removed` carries them in the report. The message of the extra turn names them and says why: the group does not name the file, and a scratch file belongs under `.data/agent/scratch/`. When no extra turn follows, the agent is not running, so the log and the report are the record.
- **A fix step has no stray rule.** The synthetic group of a fix names a check, not a file, so no path can allow a new file. A rule that deleted every new file would delete the work of the fix. The fix step keeps the earlier behavior. A fix step is rare, and the job runs it after the pull request exists.
- **The eval counts the removed files.** The eval reads the diff of the result. A removed file is not in it, so `no_scratch` and `diff_scope` would pass for an agent that wrote scratch files, and the eval would lose the signal that #3030 built it for. `StepOutcome.removed` goes to both properties. The eval measures the agent, and the step is the repair.
- **The prompt keeps its rule.** The prompt adds one sentence: the step deletes a file that the group does not name. The test of #3007 stays and still passes.

## Rejected alternatives

- **Pass `ruff` and `mypy` only the group paths and leave the stray files in the tree.** The stray file would still reach `git add -A` and the commit. The issue asks that the file is gone from the commit and from the tree.
- **Stop the step when a stray file exists.** This is what happens now, through `ruff`. Four of 13 stops of 2026-11-01 show it loses the work for a file that the agent can lose without harm.
- **Parse the `Changes:` line with a regular expression.** The project has the markdown-it parser in `step_files.py`, and a group is code spans already. Fewer rules also mean fewer wrong splits: a span is a span, wherever it sits in the group.
- **Delete every untracked file outside `tests/`.** An agent may create a source file that the plan lists. A plan lists every created file in `Changes:`, so the group allows it. A rule by directory would delete it.
- **A hook on the `write_file` tool that refuses a path.** It would catch the tool only. The shell can write a file too, with `uv run python -c`. The step judges the checkout, which holds both.
