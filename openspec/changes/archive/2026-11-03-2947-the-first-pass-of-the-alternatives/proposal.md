# Proposal

## Why

Issue #2947: the alternatives check takes at most `roadmap.alternatives.limit` items (5 by default) in a round, and the repository has 141 open issues. Almost none has a check: `devops_cli_roadmap_alternatives_total` shows about 34 checks in 14 days. At 5 items in each round, the first pass over the open items takes about a month, and rule 3 of AGENTS.md (use an open tool before you build) is not asked for most items. The issue asks for a second setting, `roadmap.alternatives.first_pass_limit` (20 by default). A round uses it while an item has no check. When every item has a check, a round goes back to `roadmap.alternatives.limit` (5) for the rechecks.

The title of the issue says "a day". The row runs every 719 minutes, about twice a day (`DEFAULT_ROADMAP_ALTERNATIVES_INTERVAL_MINUTES`), and the acceptance criteria say "a round". This change delivers 20 items in a round, about 40 items a day. The first pass over 141 items then takes 8 rounds, about 4 days.

## What Changes

- `AlternativesConfig` gets `first_pass_limit` (integer, at least 1), and `defaults.py` gets `DEFAULT_ROADMAP_ALTERNATIVES_FIRST_PASS_LIMIT = 20`.
- `select_items` takes the keyword `first_pass_limit: int | None = None`. When an eligible item has no check and its last check did not fail inside `roadmap.alternatives.retry_days`, the cap of the round is `first_pass_limit`. In every other round the cap is `limit`. `None` keeps `limit` in every round, which is the case of `--limit`.
- `plan_alternatives` passes `config.first_pass_limit` when it gets no `limit`. The row `_run_alternatives_adapter` in `run.py` stops passing a limit, so the row and `devops roadmap alternatives` share one rule, as the requirement "The limit of a round is a setting" says now.
- `--limit` replaces both limits for one run. The help text of `--limit` and of `devops roadmap run` names both settings.
- The example ConfigMap shows both settings under `roadmap.alternatives`.
- The table of limits in `tests/roadmap/test_roadmap_limit_classes.py` gets an entry for the new default. The documents that name the limit are updated, and the generated documents are regenerated.
- The change carries a spec delta in `roadmap-alternatives`: the limit of a round, a setting and an option of a command, is observable. It MODIFIES two requirements that exist, "The limit of a round is a setting" and "The Service runs the check twice a day", because both say that `roadmap.alternatives.limit` is the one cap and a scenario of each (4 items with no check, limit 2, 2 checks) is no longer true.
- The change fits one pull request.

## Feasibility

Checked on `origin/main` 69234732 in a scratch clone, with a temporary `HOME`. Each premise has its output.

- The limit is 5 and one setting caps the row and the command. `git grep -n "alternatives.limit\|ALTERNATIVES_LIMIT" origin/main` printed `src/devops_cli/config/defaults.py:723:DEFAULT_ROADMAP_ALTERNATIVES_LIMIT: int = 5`, `src/devops_cli/roadmap/run.py:613:    plan = plan_alternatives(store, repo=repo, limit=load_settings().roadmap.alternatives.limit)` and `src/devops_cli/roadmap/alternatives.py:852:        limit=config.limit if limit is None else limit,`. `openspec/specs/roadmap-alternatives/spec.md:161` says the setting caps "the row and `devops roadmap alternatives`". `git grep -n -i "first_pass" origin/main` printed one hit, `tests/commands/test_devcontainer.py:1916` (`first_passwords`), which has nothing to do with the check, so the setting is not set anywhere.
- The probe on the unchanged tree. A script (`python -I`) that seeds 25 New items of a collaborator in `InMemoryRoadmapStore` and calls `select_items` with the setting printed `fields: ['limit', 'recheck_days', 'retry_days']`, `settings: limit=5 recheck_days=30 retry_days=3` and `25 unchecked, limit 5 -> selected 5`.
- The switch needs only `select_items`. It builds the list `unchecked` after the filters `_is_eligible` and `_in_retry_delay` (`alternatives.py:515-524`), and returns `ordered[:limit]` (`:527`). So the list is the exact set of items "with no check" that the issue means, and an item whose check failed lately is in neither list.
- The change works. In the scratch clone I made the edits of What Changes in code (+13 lines, -2 lines in 4 files) and ran a probe with the defaults: `25 unchecked: limit=5 first_pass_limit=20 -> 20`, `0 unchecked, 8 due: ... -> 5`, `3 unchecked, 10 due: ... -> 13`, `2 unchecked in retry delay, 8 due: ... -> 5`. I reverted the edits (`git checkout -- src`).
- Three existing tests break with the change, so the tasks change them. `pytest tests/roadmap/test_roadmap_alternatives.py tests/roadmap/test_roadmap_limit_classes.py tests/docs` printed `3 failed, 187 passed`: `test_the_row_checks_at_most_the_limit_of_the_setting_and_the_command_uses_it_too` (4 unchecked items, limit 2: the row now checks 4), `test_the_commands_limit_option_has_no_default_of_its_own` (3 unchecked items, limit 1: the command now checks 3) and `test_every_numeric_limit_of_the_roadmap_jobs_has_a_class` (the new default has no entry in `LIMITS`, `tests/roadmap/test_roadmap_limit_classes.py`).
- The generated documents change. With the scratch edits, `devops docs check` printed `Out-of-date documentation file: .../docs/CONFIGURATION.md differs from generated content.` The line `docs/CONFIGURATION.md:271` holds `limit=5 recheck_days=30 retry_days=3`. The help text `Maximum number of items to check in this run (default: roadmap.alternatives.limit, 5).` is in `src/devops_cli/lang/en/help.py:1320`, and the same text is in `docs/CLI_REFERENCE.md:6570` and `docs/commands/roadmap.md:84`.
- The Service budget holds. `RequestBudget.admit` (`src/devops_cli/server/service.py:211-235`) gives each GitHub request its place in the window and waits while the window is full, "whatever a round costs" (docstring, `:176-179`). The row sends its requests through that budget, and this change adds no request path. An upper bound for one item is 1 comment read, up to `CONST_ROADMAP_ALTERNATIVES_MAX_FACT_READS` (30, `constants.py:3061`) fact reads, and 3 writes. For 20 items that is at most about 680 requests, over the budget of 500 an hour (`defaults.py:903`). The budget then makes the round wait, never fail, and a skipped class (`test`, `docs`, `refactor`, `chore`, `ci`, `perf`) makes no model call and no search (`k8s/README.md:615`). Not verified: how many Firecrawl credits 20 items use. The caps are 10 searches for an item (`constants.py:3060`), so at most 200 searches in a round. The owner holds the Firecrawl plan.
- The lane order holds. `MODEL_LANE_ROWS` holds `refine`, `stage`, `alternatives` in that order (`run.py:706-731`), and this change edits no row.
- Eligibility. `_is_eligible` takes open items with Status New or Ready from an author with write access (`alternatives.py:483-488`). An item In Progress or Blocked is no "open item" for the switch. The issue says "every open item has a check"; the spec text says "eligible item".

## Existing Tool Considered

No open tool or library covers a cap on the items of one round of an internal row. The cap is one integer setting that the project already declares with pydantic `Field(ge=1)`, as for `limit`. A scheduler such as APScheduler or a queue such as Celery would replace the Service's due table, which is much more than this need. The nearest option with no code is to raise the default of `roadmap.alternatives.limit` to 20. It is rejected in `design.md`. Cost to build and test: about 45,000 tokens and about 1 hour of elapsed time. Cost to keep: one keyword and one setting, about 2,000 tokens at the next change of the selection. Cost to fix: one test of the table of caps in `select_items`, about 5,000 tokens. The change deletes one argument of the row in `run.py` and no module.
