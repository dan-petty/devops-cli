# Proposal

## Why

Issue #2700: the `devops-cli Telemetry` dashboard holds its `command` variable as a hand-kept list of command groups, so a new command group shows only after a person adds it. No panel shows a sub-command: the "Subcommand Latency Breakdown" row reads `devops_cli_command_duration_seconds`, the time of the whole command group. `devops_cli_subcommand_duration_seconds` is sent for each sub-command, but its `command` label holds only the leaf name (`set`, `list`), which repeats across command groups.

## What Changes

- `OTelTyper` sends `devops_cli_subcommand_duration_seconds` with the labels `command` (the command group, such as `pr`), `sub_command` (the command path below `devops`, such as `pr threads reply`) and `status`. Click's `command_path` gives both. A command with no command group above it names itself in both labels.
- `k8s/monitoring/dashboards/devops-cli.json` gets its `command` variable from `label_values(devops_cli_command_total, command)`, and gets the multi-value variable `sub_command`, with All, from `label_values(devops_cli_subcommand_duration_seconds{command=~"$command"}, sub_command)`. Both refresh when the time range changes.
- The row "Sub-commands" holds the panel "Sub-command Calls" (runs and errors by `sub_command`) and the panel "Telemetry: $sub_command" (p50, p95, p99, mean and count), which repeats for each selected sub-command, four to a line. The RAG panels that sat below that row get their own row, "RAG Retrieval".
- The metric labels and the dashboard are observable, so the change carries a spec delta for `command-telemetry`.
- The change fits one pull request.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `command-telemetry`: the sub-command histogram names the command group and the sub-command, and the devops-cli dashboard finds and repeats each sub-command from its series.

## Feasibility

Checked on 2026-10-29:

- `src/devops_cli/core/cli.py` already reads `get_current_context().command_path` for the span attribute `cli.command_path`. `tests/test_otel_command_coverage.py` shows that a delegated `devops dummy set` gives the path `devops dummy set`, so the command group and the path below `devops` come from it with no new state.
- Prometheus `label_values(<series>, <label>)` and panel repeat by a multi-value variable are features of the classic (v1) dashboard schema that the dashboard sidecar provisions today. The Grafana chart runs Grafana 13 (`k8s/monitoring/grafana-values.yaml`).
- The Auto grid layout with a "query has data" show/hide rule needs the v2 dashboard schema. The classic file provider that the sidecar feeds refuses a plain v2 dashboard with "dashboard appears to be in v2 format" (https://community.grafana.com/t/provisioning-in-grafana-13-with-v2-dashboards/163029). One report says that a Kubernetes-style wrapper with `apiVersion: dashboard.grafana.app/v2` loads. That needs a check on the cluster, so this change keeps the v1 schema and #2703 adds the Auto grid.

## Existing Tool Considered

Grafana query variables and panel repeat cover the need. The change builds nothing: it deletes the hand-kept list of 41 command groups and the test that compared it with `_COMMAND_SPECS`.
