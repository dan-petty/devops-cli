# Design

## Decisions

- **Cut the work that every test repeats, not a test.** The step `Tests & Coverage Quality Gate` is 92% of the job (`baseline.md`). Inside it, 13,900 tests each pay a fixed cost that no test asked for. The cut removes that cost. The same tests run, the same lines are covered, the coverage floor (`fail_under = 85`) and the 90% floor of the changed lines are unchanged, and no test is skipped or marked.
- **Five cuts, each measured on its own.**
  1. `tmp_path_retention_policy = "failed"` in `pyproject.toml`, and a runtime directory made without a number. Tool: pytest's own option (`tmp_path_retention_policy`, documented under "Temporary directory location and retention" in the pytest docs; the pinned pytest 9.1.1 has it in `_pytest/tmpdir.py`). `make_numbered_dir` took 88.7 s of CPU in a run (28,028 calls, 3.2 ms each) and 15.4 s after the change. The autouse fixture `isolate_session_bus` made a second numbered directory for each test with `tmp_path_factory.mktemp("run")`. It now makes one directory for each worker and a `tempfile.mkdtemp` inside it, which lists nothing.
  2. `isolate_llm_response_cache` no longer builds the cache. It reset the cache before and after each test, and built it in between, which loaded and validated the settings (a YAML parse and a pydantic model) in each of the 13,900 tests: 53.6 s of CPU. The cache is built on its first use, as the product builds it. A test that uses the cache gets it from `get_llm_response_cache()` as before.
  3. The root conftest raises the young threshold of the garbage collector, `gc.set_threshold(50_000, ...)`, tool: the standard library's `gc` module (`gc.set_threshold`). In a worker, collections fell from 4,000 to 7,000 to 120 to 190, and the time in the collector from 22 to 37 s to 5 to 10 s.
  4. Five test servers (`serve_forever` of `http.server` and `socketserver`) wait for their shutdown with a poll interval of 0.5 s by default. Their fixtures now pass the 0.01 s that `tests/support/waits.py` names. That removes 19 s of idle teardown of the workers (54 fixture finishes that each waited 0.1 to 0.5 s).
  5. `tests/support/typer_commands.py` builds the click command of a Typer app once for each state of its registered commands and groups. `typer.testing.CliRunner.invoke` called `typer.main.get_command(app)` on every call, which reads the signature of 4,800 command functions: 53 ms of CPU for each of 317 calls in a 1,040-test sample (13% of the time of the sample under the profiler). The `cli` fixture and the tests that build a `CliRunner` themselves all go through `typer.testing`, so one session fixture covers them. The key holds the registered commands, groups and callback of the app, and the cache holds them too, because four tests add a hidden command to `devops_cli.main.app` and remove it again (`tests/test_fastmcp_in_process.py`, `tests/invariants/test_hermetic_floor.py`): a cache by the app alone served them the tree without their command.
- **One test helper keys by content.** With the policy `failed`, the directory of a passed test is deleted, and the next test of the same name prefix gets the same path. `tests/support/markdown_examples.py` kept a parse by path, so four tests that write a different README at the same path read the first one. The parse is now kept by the text of the document. A cache by path is wrong in any run that reuses a path, so `docs/TESTING.md` says so.
- **The guard is a command, a unit-tested read, and one job.** `devops ci job-time` reads the job time of the last 10 completed `push` runs of `ci.yml` on `main` through the GitHub session (`GitHubClient.get_job_run_times`: the listing of runs with `status=completed`, then the jobs of each run, stopping at the tenth run where the job ran to an end). The conclusion of the job decides, not the conclusion of the run: a job that ended `success`, `failure` or `timed_out` counts, a skipped or cancelled job does not. A listing of successful runs only would drop the run that the guard itself turned red, so a slow window would clear itself without the tests getting faster, and it would hide the slow runs that failed. It fails when the mean is over 300 s (`CONST_CI_TEST_BUDGET_SECONDS`, the budget the gate already warns on) and when fewer than 10 runs could be read. The tests run the command over the fake of the GitHub API (`github_api`) with the recorded runs and jobs of `main` (`tests/fixtures/github/ci_runs_main.json`), so the guard is tested offline at the HTTP edge.
- **How the guard sees the last ten runs.** It does not run in the pull request that it measures. A pull request has one run, and a guard on it would fail every pull request, the one that fixes the time included, for as long as the history of `main` is slow. The job `Test Job Duration` runs on `push` to `main` and on the daily `schedule`, in `ci.yml`, with no `needs` to or from it. On a push it reads the ten runs before that push, because it starts beside the test job of the same run. Each later push reads one more run of the new code. A slow window turns the run of `main` red, which the release pull request already shows (a red `main` is fixed first), and the daily run catches a runner that slows down while nobody pushes. The red run still gives its test time to the next window, because the guard reads the job's own conclusion.
- **Expected red after the merge.** The guard reads the ten runs before a push, and at the merge these are the slow runs (372 to 387 s on average, `baseline.md`). The job `Test Job Duration` is therefore red on the merge push and on the pushes after it, until the window holds enough runs of the new code. If the new code averages 277 s and the old runs 372 s, the mean falls under 300 s only when at least 8 of the 10 runs are new, so about 8 pushes stay red. This red is not a regression and not a defect of the cut. It is the guard stating that the ten-run mean is not yet shown. The first push whose window holds only new runs reads the true mean.

## Rejected alternatives

- **`gc.freeze()` after collection.** It cut the 23 full collections of `tests/test_memory_profiler.py` from 6.4 s to between 1.3 and 2.7 s. With it, four tests warned `HypothesisWarning: ... register_random was passed an object that could be garbage collected immediately`, which the run without the freeze does not print. A change of what the collector can see is a change of what a test sees. The raised threshold alone gives the gain on the whole run: on four pinned CPUs the same tree took 305 and 311 s with it and 324 and 324 s with the default thresholds.
- **Fewer or more workers.** On four pinned CPUs, 13,918 tests, the options of the gate: `-n 4` took 324 s and 1,095 s of CPU, `-n 6` took 326 s and 12% more CPU, `-n 8` took 303 s and 4% more CPU. Overlapping the idle waits of tests did not pay for the longer start of more workers (every worker collects the whole suite). The host was shared and the spread between runs was 5%, so the one favorable run is not a gain. Left as `-n logical`.
- **A different coverage core.** The default core of coverage 7.16.1 on Python 3.14 is `sysmon` (`coverage/core.py`: `env.SYSMON_DEFAULT`). On 22 test modules, serial, one CPU: no coverage 37 s, `sysmon` 44 s (+19%), `ctrace` 55 s, `pytrace` 136 s. `sysmon` is the cheapest way to measure the same lines. The cost of coverage (269 s without it and 324 s with it on the pinned full run, 55 s) stays. Issue #2373 owns the question of branch measurement, which would raise it.
- **`yaml.CSafeLoader` for the settings file.** The pure-Python YAML parse is 53 s of CPU in a run; libyaml's loader cut it to 27 s with the settings read through it. It was left out: the loader accepts a document nested 10,000 deep that the pure-Python loader refuses with `RecursionError`, and `tests/config/test_config_file_that_is_not_yaml.py` pins that refusal for the settings file. Taking the gain needs a second change to the settings error path, and the gain is 26 s of CPU, 2% of the run. A change of the loader of the settings is a behavior change and is its own item.
- **Probes of the startup-import budget without `-X importtime`.** `tests/test_cli_startup_imports.py` is 99 s of the 1,314 s of test time. Issue #2369 proposes counting `sys.modules` instead. The budget counts every module that `-X importtime` reports, "failed imports included" (the docstring of `_StartupImports`), and `sys.modules` lists fewer, so the same limits would admit more. That is a change of the limits, which the owner sets. Left to #2369.
- **Checks of committed files as rows of `devops ci` (#2164).** It moves tests out of the pytest run into other jobs. That changes the number of tests in the job and is a change of its own with its own acceptance; it is not needed to reach the target. Left to #2164.
- **A larger runner, or two jobs that each run half of the suite.** The runner size is a repository setting, which only a person changes. Two jobs would rename the required check `Tests & Coverage` (the required checks are a repository setting too) and would make the job time a different number from the wall time of the work, which is the figure that this item must not hide.
- **A cache of bytecode across runs.** Collection takes 40 s on the runner, 13 s of it to compile the sources the first time (30 s cold and 17 s warm in a serial collection of the suite on a workstation). pytest checks the time of a source file before it uses its rewritten bytecode, and a checkout gives every file a new time, so a restored cache is never valid unless every time is set to one fixed value, and then a changed file of the same size would run its old bytecode. A wrong test result is worse than 13 s.
- **Fewer autouse fixtures.** About 25 autouse fixtures run for each test, and they make up about 30% of the collection (the fixture closure of each test, 6.9 s of 22 s in a profile of a serial collection) and some of the set-up. Merging them changes the order of their teardown, which the conftest documents (`reset_process_wide_state` must tear down last). A refactor of the fixtures is its own item; the three that cost time are cut here.
- **A separate workflow (`workflow_run`) for the guard, so that its red stays out of the conclusion of `ci.yml`.** It was proposed to stop the guard from hiding its own run. Reading the conclusion of the test job instead removes the cause: the red run still counts. A second workflow adds a trigger, a token and a file for no further gain.
- **A step of the test job as the guard.** The refined proposal of the issue puts the check at the end of the test job. It cannot see its own run as one of the ten, and as a step of the required check it fails every pull request while the history of `main` is slow, including the pull request that cuts the time. A job in `ci.yml` that runs on `main` only gives the same coverage of the history without that deadlock.
- **`timeout-minutes` as the guard.** It stops a job that runs too long; it says nothing of the mean of ten runs.
- **A scheduled workflow that opens an issue through `devops roadmap intake`.** It adds a token with `issues: write` and an issue for each day the mean stays over the limit. The failed run of `main` is the signal the owner already watches, and the check stays a command anyone can run: `devops ci job-time`.

## Consequences

- The job time stays a noisy number: one run in 24 took 279 s and another 425 s on the same tests. The mean of ten runs has a spread of about 12 s. The cut is measured as 0.79 to 0.82 of the time and CPU of the base on four pinned CPUs, which projects the job to 294 to 317 s depending on the base mean (24 runs or the newest 10) and the ratio. The target (under 300 s) is therefore not shown to be met, and the margin, if there is one, is inside the spread of the mean of ten runs (about 12 s). The ten runs on the runner, read by `devops ci job-time`, are the proof. #2699 stays open until they read under 300 s.
- The guard counts a job that failed. A job that stopped early, for example at the checkout, has a short time and lowers the mean a little. A run where the test job failed after the whole suite ran, and a run that hit its time limit, show their true time. This bias is smaller than the bias of listing successful runs only.
- The directory of a passed test is gone when the run ends. A person who debugs a test that fails keeps its directory (policy `failed`).
- A cycle that a test leaves is collected later. No test reads that; the full suite passes with the threshold.
