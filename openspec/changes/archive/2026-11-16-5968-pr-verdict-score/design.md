# Design

## Decisions

- **One label for each verdict and kind.** The verdicts are workflow labels, because the roadmap code reads them (#4652). The owner gave needs fix one label for each kind on 2026-11-16: `verdict/fix-plan` for a plan and `verdict/fix-implementation` for a delivery. Discard plan belongs to a plan and discard implementation to a delivery. Mergeable and issue changed apply to both kinds.
- **`verdict/fix-plan` replaces `plan/needs-fix`.** The stage review, the row `plan_drift`, a vet and the step fix-plan used `plan/needs-fix` for "the plan needs a fix". That is the verdict needs fix of a plan, so each reader and writer now uses `verdict/fix-plan`, and the constant `PLAN_NEEDS_FIX_LABEL` becomes `FIX_PLAN_LABEL`. No code reads both names (owner). At rollout an agent renames the GitHub label with one `PATCH`, so each open pull request keeps its mark.
- **The plan comment section names no label.** The step fix-plan found the open findings of a plan comment by the whole heading, which names the label. The comments on the open plan pull requests name `plan/needs-fix`, so the reader now finds the section by the first sentence of the heading, which names no label. The recorded stage comments keep the old name and still read.
- **A label of the other kind leaves the pull request unscored.** A first verdict label of the other kind, such as `verdict/fix-plan` on a delivery, gives no verdict. The report counts the pull request as unscored, apart from the open ones, and the read logs the pull request and the label (owner).
- **The first verdict comes from the label events.** The step fix-plan removes `verdict/fix-plan` after a repair, and a vet can add `verdict/mergeable` after a fix. The labels of today lose the first verdict, so the read takes the `LABELED_EVENT` items of the timeline, which GitHub keeps after an unlabel. The first event of a verdict label gives the verdict. A later event keeps the history and does not change the score.
- **One GraphQL search, not one search for each kind.** One search `is:pr author:app/<slug> created:>=<window start>` gives both kinds, and the title splits them. The same request gives the label events, so the read sends one request (1 point) for each 100 pull requests. A REST search gives the labels of today only, and the events endpoint costs one request for each pull request (113 on 2026-11-16). A search with more results than GitHub returns (1000) stops the report, so a short read never reads as all.
- **A verdict scores the job that opened the pull request.** A plan pull request scores stage and a delivery pull request scores implement.
- **One shared setting for the partial score.** `roadmap.verdict_partial_score` (0 to 1, default 0.5) gives the score of needs fix for both jobs. The owner gave one value, and a job-level setting can come when the values must differ.
- **The shares count the pull requests with a verdict.** The share of a verdict is its count over the pull requests with a verdict. The open and the unscored pull requests are counts of their own, so the share does not fall while the vets work.
- **No slug, no read.** The bot login comes from `service.github_app.slug`. With no slug there is no bot, so the report reads no verdict and its text names the setting. The Loki part of the report does not change.

## Rejected alternatives

- **`plan/needs-fix` as the needs-fix verdict of a plan, and `verdict/needs-fix` for a delivery.** The first plan of this change. The owner replaced it on 2026-11-16: one family `verdict/*` holds each verdict, and each kind gets its own needs-fix label.
- **An alias that reads both `plan/needs-fix` and `verdict/fix-plan`.** The owner refused it: two names give one meaning. The rename of the GitHub label at rollout keeps the mark of each open pull request.
- **A label of the other kind as a verdict of the pull request.** `verdict/fix-plan` on a delivery would score the implement job with a verdict for a plan. The owner asked for an unscored count with a logged reason.
- **The labels of today, with an order of the verdicts.** On 2026-11-16, 38 of 100 bot pull requests got `plan/needs-fix` at some time, and the step fix-plan removes it after a repair. An order such as "discard before needs fix before mergeable" also gives a wrong first verdict for "mergeable, then issue changed".
- **The issue events endpoint for each pull request.** It gives the same events at one REST request for each pull request: 113 requests for the 7-day window of 2026-11-16, against 2 GraphQL requests.
- **A merge as the success of an attempt.** The first version of #5968 gave a lagging merge credit. The owner replaced it with the verdicts on 2026-11-16, because a merge after a fix is not a success of the attempt.
