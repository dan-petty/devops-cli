# Proposal

## Why

Issue #2654, a part of #2653: no command makes a Ready item Staged. An agent makes the branch, writes the OpenSpec change and opens the draft pull request by hand, with the whole repository in its context. The task groups it writes have the size of habit, not of a budget. A later implementation step can then be too big for the context window of a model.

## What Changes

- `src/devops_cli/roadmap/stage.py` holds the stage job: the selection by label filter, the plan, the writes and the reconcile of staged branches whose items closed. `src/devops_cli/roadmap/stage_change.py` holds the reply of the model, the files of the change, and the measure of each task group.
- `devops roadmap stage [--repo] [--item N] [--filter family=value]... [--limit N] [--step-tokens N] [--dry-run | --plan | --confirm]` in `src/devops_cli/commands/roadmap.py`.
- `src/devops_cli/ai/tasks/roadmap_stage_change.md` and `roadmap_stage_split.md` are the prompts. One `chat_structured` call with `ai.for_task("analysis")` plans the change. A second call runs at most once to split task groups over budget, and a third at most once to correct a failed validation.
- Each task group is measured with tiktoken and `ai/context_packer.py`. The budget is `roadmap.stage.step_tokens` (default 40000), a new setting. `--step-tokens` overrides it for one run.
- `src/devops_cli/github/client.py` gets the calls that open a draft pull request and close a pull request.
- `src/devops_cli/roadmap/store.py` gets `StageRecordKey`: `stage.branch`, `stage.pr`, `stage.sha`, `stage.groups` and `stage.needs_split`.
- `src/devops_cli/git/worktree_add.py` gets three public functions, `read_remote_heads`, `remote_branches` and `issue_holder`, so the stage job applies the held-issue rule of `worktrees add` and does not copy it.
- `CONTEXT.md` gets the terms Staged and Step.
- The command, its options, its messages and its setting are observable, so the change carries a spec delta for the new capability `roadmap-stage`.
- The change fits one pull request. The Service row for the job (#2659) is a separate item.

## Feasibility

Checked on 2026-10-29 against the real system:

- `openspec --version` prints `1.14.3`. In a scratch project, `openspec validate 1-x --strict` exits 0 for a change with one requirement that says SHALL and has one scenario. It exits 1 and prints `ADDED "X" must include at least one scenario` for a requirement with no scenario. So the validation catches the errors that a model makes, and its output can go back to the model.
- `openspec list --specs` prints one line for each capability, such as `roadmap-refine  requirements 20`. The names are the directory names under `openspec/specs/`. The job reads the directory and gives the names to the model, as `openspec/config.yaml` asks, so planning needs no binary. This differs from the text of #2654, which names the command; design.md gives the reason.
- `openspec validate <change> --strict --json` exits 0 and reports an INFO issue `Archive would refuse this delta: ... not found` for a MODIFIED requirement whose name is not in the base spec. Without the base spec in the directory, it reports that only ADDED requirements are allowed. So the job copies the base specs into the scratch directory and treats every issue as a problem. A MODIFIED requirement that drops a scenario of the base spec is reported the same way.
- tiktoken 0.14.0 is a dependency. `devops_cli.ai.context_budget.count_tokens("hello world")` returns 2 offline. `ContextPacker.pack_file` in `src/devops_cli/ai/context_packer.py` returns `packed_tokens` for a file.
- `add_worktree` in `src/devops_cli/git/worktree_add.py` makes `<type>/<issue>-<slug>` at the fetched `origin/main` and refuses a held issue. `branch_form.py` gives the form and `is_valid_slug`.
- ADR 0015 says that the App has Contents and Pull requests write, and that git gets its token through `gh auth git-credential`. So a push and a pull request by the App work.
- `src/devops_cli/commands/pr.py` (`_fallback_create_pr`) already opens a draft with `POST /repos/{owner}/{repo}/pulls` and `draft=true`. The job sends the same request through the GitHub session.
- The `RoadmapStore` reads `labels`, `author_association` and `job_record` of an item. `refine.py` writes the section "Dependencies" of a refined body as `#N` references.
- The premise holds. No part of the item needs code that compensates for a missing tool.

## Existing Tool Considered

OpenSpec covers the change and its validation: the job writes the files its schema names and runs `openspec validate --strict`. `worktree_add.py` and `branch_form.py` cover the branch. The GitHub session covers the pull request. #2654 names `devops pr create` for it, and the job does not use it: that command works on the checked-out branch of the current directory and runs `gh` in a child process (design.md, Decisions, gives the reason). The job adds `GitHubClient.create_draft_pull`, about 15 lines, instead. Tiktoken covers the measure, and `ai/context_packer.py` covers the packing. `refine.py` covers the selection and the structured call, and the job follows its shape.

The job builds the selection by label filter, the plan call, the measure loop and the writes. No open tool covers them: the Copilot coding agent writes no OpenSpec change and cannot use the models of the gateway (#2653). The estimated cost is about 1,400 lines of code and tests, 400k tokens of agent work and two days of elapsed time, plus upkeep when the schema of OpenSpec changes. The change deletes no internal code.
