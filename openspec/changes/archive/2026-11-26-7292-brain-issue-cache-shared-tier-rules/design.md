# Design

## Decisions

- **One visibility check, in its own module.** `src/devops_cli/roadmap/stores/visibility.py` holds `Visibility`, the answers of the process with their lifetimes (30 min for an answer, 60 s for unknown), `SWEEP_USER`, `configured_valkey_user` and `for_user`, which makes a private repository public to `SWEEP_USER`. `visibility_of(repo, is_private)` takes the read of GitHub from its caller, so the module does not import the GitHub store. `listing_shared.repository_visibility` and `TieredSnapshotStore` call it, and so does the issue cache. The import cycle `listing_shared` to `github_store` to `brain_issues` is the cause of the move: `brain_issues.py` cannot import `listing_shared.py`.
- **The store gives its own read.** `GitHubRoadmapStore._cached_issue` and `_remember_issue` pass `self.repository_is_private`, so the visibility read uses the runner and the credentials of the store, and each of the 9 call sites of the store goes through these two methods.
- **The order of the answers.** `private` of the caller, then the answer that the process holds, then the read of the caller. A caller that has none of them gets an unknown answer, which sends no command.
- **The visibility read comes after Valkey answered.** When the process holds no answer, the cache sends one `GET` of the key prefix `valkey:roadmap:v1:issue` before the visibility read. That key holds no value and names no repository. When Valkey gives no reply, the cache sends no visibility read, a read counts `fallback` and a write counts `skipped`. So a process with no Valkey, such as a job pod or a command of a person, sends no added GitHub request, and no command names a repository before its answer.
- **No command for a refused entry.** For a private or an unknown answer, the cache does not call the mapping. A read gives None and counts `private` or `unknown`. A write counts the same result. The process that sends `SWEEP_USER` takes a private answer as public, as the snapshot store does.
- **The key.** The mapping has the prefix `valkey:roadmap:v1:issue:<owner>/<name>` with `RepoRef.key`, as `snapshot_key` builds the key of the snapshot. `TieredMapping` adds `:<number>`, so the `:` after the name ends the repository part, and the keys of `o/n` are no keys of `o/nn`. `issue_key` gives the key of an issue. The mapping itself has no visibility check, so it becomes the private `_issue_cache`, which only `cached_issue` and `remember_issue` use.
- **The webhook route uses the visibility of the delivery.** `_remember_delivery_issue` and `_remember_own_delivery_issue` pass `payload.repository.private`. GitHub sends this field in each delivery and signs the body, and the record that the route writes comes from the same body. The route sends no GitHub request. A delivery with no such field uses the answer that the process holds. With neither, the route writes nothing and counts `unknown`.
- **Lazy imports in `brain_issues.py`.** The GitHub store imports this module, and the help of a command must load no cachetools (`tests/gate/startup_imports.py`). The module imports `visibility`, `valkey.cache` and `valkey.tiered` in the functions that use them.
- **No migration.** The old keys have a TTL of 24 hours and no reader after the release. The first read of each issue after the release is a miss, which reads GitHub one time.

## Rejected alternatives

- **Import the check from `listing_shared.py` inside the functions of `brain_issues.py`.** `listing_shared.py` imports `GitHubRoadmapStore` at `src/devops_cli/roadmap/stores/listing_shared.py:102`, and `github_store.py` imports `brain_issues.py` at `src/devops_cli/roadmap/stores/github_store.py:72`. The issue cache also needs the names `_configured_valkey_user`, `_visibility` and the `SWEEP_USER` rule of `TieredSnapshotStore._checked`, which are private to the snapshot module. A shared module with no import of the store removes the cycle.
- **Read the visibility before each command while the breaker is closed.** In a process with no Valkey, the breaker is closed until the first command fails (`DEFAULT_VALKEY_CACHE_BREAKER_FAILURES` is 1). The probe of 2026-11-26 shows a tier of `valkey://localhost:6379/0` in a test with no fixture, so this order adds one GitHub request to each first read of an issue of each such process, and to each test of the store that records its requests.
- **Read the entry first, then the visibility, as the snapshot store reads `meta` first.** The read sends the name of the repository and returns its record before the answer. The `GET` of the key prefix gives the same proof that Valkey answers, and names no repository.
- **Let the webhook route send the visibility read, kept for 30 minutes.** `_read_and_route` is `async` (`src/devops_cli/server/routes/webhooks.py`) and runs the consumer on the event loop. A `gh` read there holds each other request of the Service, and a failed read comes again after 60 s.
- **Let the webhook route use only the answer that the process holds.** The answer of a process ends after 30 minutes, and a delivery in the time until the next round would write nothing. The entry that the tier holds then stays for a row for up to 1 hour (`DEFAULT_BRAIN_ISSUE_MAX_AGE_SECONDS` is 3600), with the state before the delivery. The field `repository.private` is in each delivery, so the route has an answer with no request.
- **Keep the delivery answer as the answer of the process.** A delivery would then change the answer that the snapshot store uses for 30 minutes. The route uses the field only for the entry of its own delivery.
- **Delete the keys of the old prefix in the release.** A `SCAN` and `UNLINK` of 453 keys (the count of the issue) is a second code path that runs one time. The TTL of 24 hours removes the same keys with no code.
- **Keep an entry of a private repository in the memory of the process.** #7063 reads live issue state because another process changes an issue through a webhook, and `entries=0` of the mapping is the result. A copy in the process would bring that defect back.
