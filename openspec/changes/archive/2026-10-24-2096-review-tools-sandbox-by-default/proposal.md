# Proposal

## Why

Issue #2096, part 4 (Part D) and the last open part of the tracker #772: a review ran its tools with no sandbox. `DirectToolExecutor` started each tool as a child process of devops-cli, with the network, the environment and the files of the user, and it was the executor of the orchestrator when nobody gave it another. `SandboxToolExecutor` existed (bubblewrap through `HostSandbox`, with `prlimit`), but no review selected it.

The issue also takes the scope that #1978 moved here: the sandbox must bind the Python installation that the `python` of a `.venv` outside the tree links to, behind the `_is_python_installation` guard of `HostSandbox`, and mypy and its canary need a writable cache directory (`MYPY_CACHE_DIR`).

A run of each pinned tool through the sandbox executor on this host showed that the sandbox could not run any tool as it was: it did not bind the program of the tool, so `prlimit` failed with "No such file or directory" for each one.

## What Changes

- `devops review path`, `devops review branch` and `devops review pr`, and the MCP tools of these commands, run every analyzer, evidence tool and canary in `SandboxToolExecutor`, and in no other place: no option, config key or MCP parameter turns the sandbox off (decision 1 of #772). An orchestrator, the mypy scan and the canary runner that get no executor make a `SandboxToolExecutor`. The scans of `devops scan`, `devops k8s audit` and the agent tools are not reviews, and a scanner that gets no executor still runs its tool as a child process.
- Before its first run, the sandbox executor checks the host one time: bubblewrap and `prlimit` are installed, and bubblewrap can start `prlimit -- true` in a sandbox. A host that fails the check fails closed. Each run raises the new `SandboxUnavailableError` with the cause, and no tool runs, in the sandbox or outside it. Each scan reports a coverage gap with the cause, a canary that did not run withholds no finding, and the review says the cause, and what a person can change on the host, one time when it ends.
- The sandbox binds what a tool needs to start: the virtualenv that holds the program in its `bin`, else the program file; for a read-only bind that is a virtualenv, the Python installation that its `python` links to, behind the guard of the `.venv` of the tree, also at the path of the minor-version link that uv makes; and the host paths of `CONST_TOOL_HOST_READ_ONLY_PATHS` (the CA certificates that the engine of Semgrep loads when it starts). It refuses a bind that holds the home directory or the tree, or passes through a credential directory. A request names the directories that its tool writes in the new field `writable_dirs`, and the sandbox binds them read-write: the mypy cache, the cache of the mypy canary, which `MYPY_CACHE_DIR` names in place of `--cache-dir`, and the Ruff cache of the tree, which `RUFF_CACHE_DIR` names (#772 Part D).
- Each tool gets the address space that it was measured to need: `ToolLimits.for_tool` gives Gitleaks 8 GiB and Semgrep 16 GiB, and the least, 2 GiB, to every other tool. Every Semgrep scan runs `CONST_SEMGREP_JOBS` (4) jobs, so its need does not grow with the processors of the host.
- A scanner names the data that a fetch step got before through `data_dirs`: the Trivy cache (`TRIVY_CACHE_DIR`) and the `osv-scalibr` database of osv-scanner (`OSV_SCANNER_LOCAL_DB_CACHE_DIRECTORY`). The request names each directory by its variable and binds it read-only.
- The sandbox executor makes its `HostSandbox` at its first use, so a review that starts no tool, such as a dry run, does not load the container engine library that `HostSandbox` reads tmpfs sizes with. The osv-scanner scan gives the dry-run outcome in a dry run, as every other scan does, where it built its tool command before.
- A Ruff scan keeps its cache in a directory of the tree, outside the tree, in the data cache directory (`BaseSecurityScanner.cache_dirs`). The Ruff canary keeps no cache (`--no-cache`), because its file is in a new scratch directory on each run. A mypy run that ends with an exit code other than 0 or 1 fails with the code and its error, where it read as a clean scan before. A Semgrep scan with no cached registry ruleset keeps the reason of its own gap before the fetch command.
- Tests: `scanner_fake` answers `SandboxToolExecutor` as it answers `DirectToolExecutor`, and the floor allows bwrap only in a test with the `bwrap` mark. The recorded Semgrep run of the scanner contract suite is recorded again with `--jobs 4`.
- `SECURITY.md`, `ARCHITECTURE.md`, `docs/TESTING.md` and the module docstring of `tool_executor.py` describe the sandbox default. `devops docs generate --sync-readme` adds `SandboxUnavailableError` to the reference of errors.
- The commands, a message and the record of each run change where a consumer sees them, so the change carries a spec delta. It creates the capability `review-tool-sandbox`.
- The change fits one pull request.

## Capabilities

### New Capabilities

- `review-tool-sandbox`: a review runs its tools in the network-less sandbox and in no other place, a host that cannot start the sandbox runs no tool, and the sandbox gives each tool what it needs.

### Modified Capabilities

None.

## Feasibility

- Command output, devcontainer (rootless Podman on WSL2, kernel 6.18): bubblewrap 0.13.1 and `prlimit` of util-linux 2.42.4 are installed. `bwrap --unshare-all --die-with-parent --ro-bind / / --dev /dev --proc /proc --tmpfs /tmp true` exits 0. The kernel has no `kernel.apparmor_restrict_unprivileged_userns`. A probe that the sandbox executor starts reads `/proc/net/dev` and finds the interface `lo` only.
- Command output, base 11ddf0f0: each pinned tool started through `SandboxToolExecutor` ended with exit code 127, `prlimit: failed to execute <program>: No such file or directory`, because the sandbox shows only `/usr`, the system links and the tree. The mypy scan reported that run as `ran` with no finding.
- Command output, after the binds: Semgrep 1.179.0 stops at start with `ca-certs: no trust anchor file found, looked into /etc/ssl/certs/ca-certificates.crt`, and runs with `/etc/ssl/certs` bound read-only. The `python` of the Semgrep virtualenv links to `cpython-3.14-linux-x86_64-gnu/bin/python3.14`, a link that uv makes to `cpython-3.14.7-linux-x86_64-gnu`, so a bind of the resolved installation alone leaves the link empty in the sandbox.
- Command output, `prlimit --as`: Gitleaks 8.30.1 panics (`allocator_unix: failed to reserve memory`) at 2, 4 and 5 GiB and runs at 6 GiB, on one file and on the source tree of devops-cli; it runs RE2 as WebAssembly in wazero, which reserves 4 GiB. Semgrep with one job needs more than 2 GiB and runs at 4 GiB; with four jobs it stops at 4 GiB and runs at 8 GiB, also on 100 files; with the default job count on 16 processors it stops at 16 GiB on 100 files. Four jobs took 6.4 s on those 100 files, and the default jobs took 6.3 s, with the same 11 results. `prlimit --data` does not let Semgrep run at 2 GiB either. Mypy runs at 2 GiB on two modules of devops-cli and everything that they import, with no cache, in 26 s.
- Command output: Ruff 0.16.8 in the sandbox fails with `Failed to initialize cache at <scratch>/.ruff_cache: Read-only file system`, because a review starts Ruff in a new scratch directory, which the sandbox binds read-only. With `RUFF_CACHE_DIR` set, Ruff writes there and not to a `cache-dir` that the config of the tree names. For a tree with a Ruff config, three sandboxed review scans from three scratch directories read and wrote one cache entry. For a tree with no Ruff config, Ruff roots its default settings at the working directory, so each run wrote a new entry. Three runs of the Ruff canary, each in a new scratch directory, left three entries and read none.
- Command output: Trivy 0.75.0 with `TRIVY_CACHE_DIR` bound read-only logs `Using existing checks from cache`, and with an empty cache in the sandbox it uses the checks that its binary holds. Both config scans found the same four findings. `osv-scanner scan source --offline-vulnerabilities --download-offline-databases`, run outside the sandbox with `OSV_SCANNER_LOCAL_DB_CACHE_DIRECTORY` set, wrote `<directory>/osv-scalibr/PyPI/all.zip`; the strings of the binary name `OSV_SCANNER_LOCAL_DB_CACHE_DIRECTORY` and `osv-scalibr`. In the sandbox, with that database bound read-only, osv-scanner found 48 advisories for `django==1.11.0` with no network.
- Code: `devops review rules test --check`, which `.github/workflows/ci.yml` runs on `ubuntu-24.04`, calls `run_subprocess` in `src/devops_cli/review/rules_pack.py` and no `ToolExecutor`, so the default does not reach it. No CI job runs a review, and the tests fake the sandbox: the only tests that start bubblewrap carry the `bwrap` mark and skip where bubblewrap is not installed. So CI on a GitHub runner needs no package and no host change. Upstream: Ubuntu restricts unprivileged user namespaces through AppArmor since 23.10 and lets an application make them through a profile with the `userns` rule (ubuntu.com, "Restricted unprivileged user namespaces are coming to Ubuntu 23.10"). That profile is a change of the host, which only a person makes, so the change adds no switch that turns the sandbox off in CI.
- Code: popeye reads the cluster API and is no tool of a review (`_STATIC_ANALYZERS` in `src/devops_cli/ai/review/pipeline.py`). `devops k8s audit` calls `run_popeye_scan`, which makes `PopeyeScanner()` with no executor, so popeye still runs as a child process in `DirectToolExecutor`, with the network that it needs. The named network profile of #772 decision 2 is a follow-up.
- golangci-lint and the Go toolchain are not installed on this host, so its run in the sandbox is not proven (see `## Workflow follow-up` in tasks.md).

## Existing Tool Considered

- bubblewrap (`HostSandbox`) confines, `prlimit` of util-linux sets the limits, and `run_subprocess` of `core.process` starts and ends the command, as Part A (#1914) set up. The change adds a check of the host that starts the same programs, and no runner, no sandbox and no limit code of its own.
- The tools carry the rest: osv-scanner's `--download-offline-databases` and `OSV_SCANNER_LOCAL_DB_CACHE_DIRECTORY`, Trivy's cache and `TRIVY_CACHE_DIR`, Ruff's `RUFF_CACHE_DIR` and `--no-cache`, Semgrep's `--jobs`, and mypy's `MYPY_CACHE_DIR`. On Ubuntu, AppArmor's `userns` rule is the upstream answer for a host that refuses user namespaces.
- Internal code that the change deletes: the `outside` filter of `SandboxToolExecutor.command` (the binds are filtered in `HostSandbox` now), the `--cache-dir` argument of the mypy canary, and the `DirectToolExecutor` defaults of the orchestrator, of `run_mypy_scan` and of `run_tool_canary`.
