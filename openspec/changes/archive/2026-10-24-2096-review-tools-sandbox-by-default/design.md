# Design

## Context

Parts A to C of #772 made `ToolExecutor` the one seam of the review tools, `SandboxToolExecutor` the executor that confines, and the `ToolRun` the record of each run. Part 2 (#2098) made the orchestrator take its executor through its constructor. The review still ran its tools in `DirectToolExecutor`. The proposal lists what a run of each tool in the sandbox showed.

## Goals / Non-Goals

Goals:

- A review runs every analyzer, evidence tool and canary in the sandbox, from each command and from MCP.
- A host that cannot start the sandbox runs no tool and says why, one time.
- No option, config key or MCP parameter turns the sandbox off (decision 1 of #772).
- Each pinned tool that this host has runs in the sandbox with no network and gives its result.

Non-goals:

- A devops command that fetches the OSV database or the Trivy checks and database. The sandbox binds what a fetch got before; the fetch command is a follow-up.
- The sandbox for `devops scan` and the agent scan tools. They are not reviews, and a Trivy image scan there needs the network and the container engine.
- The named network profile for popeye (decision 2 of #772). Popeye is no review tool, and `devops k8s audit` still runs it in the direct executor, with the network that it needs. The profile is a follow-up.
- The Gitleaks report. Gitleaks finds a secret in the sandbox as outside it, but its command has no `--report-path`, so the review reads no report and the scan fails in both executors. #772 leaves that point to a person.

## Decisions

- **The command layer makes one sandbox executor for each review.** `_execute_review_workflow` makes it and gives it to the orchestrator, which gives it to each analyzer, evidence tool and canary. One executor checks the host one time, and its `refusal` tells the command layer at the end of the review what it found. The orchestrator, `run_mypy_scan` and `run_tool_canary` make a `SandboxToolExecutor` when they get no executor, so no review path runs a tool outside the sandbox. Rejected: the sandbox as the default of `BaseSecurityScanner`. `devops scan trivy` scans an image with the network and the engine socket, and `devops k8s audit` runs popeye against the cluster API, so the default would break the commands that are not reviews. Their callers can give an executor when a later item wants it.
- **No review runs a tool outside the sandbox (decision 1 of #772).** The owner accepted on 2026-10-22: "There is no opt-out flag and no unsandboxed fallback, because an escape that makes a check pass is not a check." So the review commands have no option that turns the sandbox off, no config key or environment variable does it, no MCP tool has such a parameter, and a host that cannot start the sandbox falls back to nothing. The words "without a person's choice" of #2096 contradict that decision, and the decision wins. A host that cannot start the sandbox reports a coverage gap for each tool, with the cause, and one message that says what a person can change on the host: install bubblewrap and util-linux, or let bubblewrap make user namespaces. Rejected: `--no-sandbox` for one run, a config key such as `review.sandbox`, an environment variable, and a fallback to the direct executor. Each one runs a review tool on an untrusted tree with no confinement.
- **The host check starts `prlimit -- true` in a sandbox of an empty directory, one time for each executor.** Only a start shows whether the kernel lets bubblewrap make a user namespace: on Ubuntu 24.04 AppArmor refuses it to a program with no `userns` profile, whatever `kernel.unprivileged_userns_clone` says. The check goes through `run_subprocess`, so a test fakes it with `process_fake`. The executor validates the request first and checks the host second, so a request that cannot run is refused before anything starts, on any host. Rejected: reading `kernel.apparmor_restrict_unprivileged_userns`. A profile can allow bubblewrap with the setting on, and other kernels refuse user namespaces in other ways. Rejected: reading the exit code and `bwrap:` prefix of each tool run. A tool also ends with 1, and a refused run would read as a tool failure.
- **A refusal is a coverage gap, and the review says it one time at its end.** The tool did not run, so a scan found nothing and is neither clean nor a tool failure: `_run_scanner_command` and the mypy scan report `coverage_gap` with the cause. A canary that did not run has no result and withholds no finding. The review prints one message with the cause and what a person can change on the host when the workflow ends, also when it ends with an error. Rejected: a message from each scan. The cause is the same for each tool, and the report already lists each gap. Rejected: stop the review. The model stages and the report stay useful without the tools.
- **The sandbox binds the program, and a virtualenv brings its Python installation.** A program in the `bin` of a virtualenv (`pyvenv.cfg` beside it) needs the virtualenv: its interpreter link and its packages. A native program is one file. `HostSandbox` binds, for each read-only bind that is a virtualenv, the installation that its `python` links to, behind the guard that the `.venv` of the tree has. uv links that `python` through the link of the minor version (`cpython-3.14` to `cpython-3.14.7`), and `pyvenv.cfg` names the same path, so the installation is bound at that path too, when that path resolves to the installation. Rejected: `--symlink` for each link of the chain. It needs a walk of each link, and a bind at the named path gives the same tree with one option. Rejected: the request names the installation. The reviewed repository aims the link of its `.venv`, so only the guard may decide what is bound.
- **The sandbox refuses a bind that would show too much.** A bind outside the tree comes from a path that a tool reads or writes, and the `.venv` of a reviewed repository can link to the home directory. A bind whose resolved path holds the home directory or the tree, or passes through a credential directory (`CONST_SANDBOX_SENSITIVE_SUBPATHS`), raises `SandboxValidationError`, so nothing starts. A bind that the system directories, the tree or an earlier bind show already is not bound again.
- **A request names the directories that its tool writes.** `ToolRequest.writable_dirs` is the one place outside the private HOME where a tool writes, and the sandbox binds each one read-write, last. Mypy writes its cache there through `MYPY_CACHE_DIR`. The mypy canary writes its cache in a directory of its scratch directory, which `MYPY_CACHE_DIR` names in place of `--cache-dir`, so the template of its command holds no path. Rejected: the private `/tmp` of the sandbox for the cache of mypy. It ends with the run, and the cache of a tree saves 69 s of each review (#2034).
- **A Ruff scan keeps its cache outside the tree, and the Ruff canary keeps none.** #772 Part D decides that Ruff gets a cache directory outside the tree. A review starts Ruff in a new scratch directory, which the sandbox binds read-only, so Ruff cannot write the `.ruff_cache` of its working directory there. `BaseSecurityScanner.cache_dirs` names, for each tree, a directory in the data cache directory, as the mypy cache is, and the request names it through `RUFF_CACHE_DIR` and as writable. The variable wins over a `cache-dir` that the config of the tree names, so the tree cannot choose where Ruff writes. Ruff keys its entries by the package of each file: for a tree with a Ruff config, three sandboxed scans from three scratch directories read and wrote one entry. The canary file is in a new scratch directory on each run, so a cache entry of the canary would never be read again: three runs left three entries and read none. So the canary keeps `--no-cache`. Rejected: one Ruff cache directory for all trees. A tool that one review runs could then write the entries of another tree (#972). Rejected: `--no-cache` for the scans. A tree with a Ruff config reads its cache again in each review.
- **Each tool gets the address space that it was measured to need.** `ToolLimits.for_tool` reads `CONST_TOOL_ADDRESS_SPACE_BYTES`: 8 GiB for Gitleaks, which needs 6 GiB, and 16 GiB for Semgrep, which needs 8 GiB with four jobs. Every other tool keeps the least, 2 GiB, which #772 set. Every Semgrep scan runs four jobs (`CONST_SEMGREP_JOBS`), because the address space of Semgrep grows with its jobs, and its default is one job for each processor. Rejected: one higher limit for every tool. A limit of 16 GiB on Bandit or kube-linter limits nothing that they do. Rejected: `RLIMIT_DATA` in place of `RLIMIT_AS`. It does not count the reservations of wazero, but Semgrep stops under it at 2 GiB too. Rejected: no address-space limit for Semgrep. #772 asks for one on every tool.
- **A scanner names the data that a fetch got before.** `BaseSecurityScanner.data_dirs` gives, for each directory, the variable that names it to the tool and the directory that the tool reads. The Trivy cache is both. osv-scanner reads `osv-scalibr` below the directory of its variable, so the sandbox binds the database alone and not the user cache directory, which holds the caches of other programs. Rejected: a bind of the user cache directory. It would show the cache of gh and other programs to every tool.
- **The host paths that a tool reads when it starts are a table.** The engine of Semgrep loads the CA bundle when it starts, and stops without it, though a scan uses no network. `CONST_TOOL_HOST_READ_ONLY_PATHS` names `/etc/ssl/certs` for Semgrep, and the executor binds it for the scans and the canary of Semgrep. Rejected: `/etc/ssl` for every tool in the policy of `HostSandbox`. It shows `/etc/ssl/private` too, and no other tool needs it.
- **Mypy reads its exit code.** Mypy ends with 0 or 1 when it checked its files. Any other code is a crash, a bad option or a program that did not start, and the scan reported it as a clean run before. In the sandbox, a program that is not bound ends with 127, so the scan must fail with the code.
- **The floor allows bubblewrap only in a test with the `bwrap` mark.** In the sandbox, a real tool starts as the program that bubblewrap confines, and the refusal of the floor by program name does not see it. So bubblewrap starts only in a test that runs the real sandbox and carries the mark. `scanner_fake` answers `SandboxToolExecutor` as it answers `DirectToolExecutor`, so a test of a review that gets no executor starts no sandbox.

## Risks / Trade-offs

- [A host without bubblewrap, such as macOS, or a GitHub-hosted Ubuntu runner without a `userns` profile] → The review runs no tool and reports a coverage gap for each one, with the cause. A person installs bubblewrap and util-linux, or a profile with the `userns` rule, on the host.
- [A tree with no Ruff config] → Ruff roots its default settings at its working directory, which is new in each run, so each review of that tree writes one more cache entry of about 190 bytes that no later review reads. The directory of the tree holds them, and `ruff clean` or a removal of the directory clears them.
- [A `.venv` of the reviewed tree that links out of the tree] → The sandbox does not show it, as it did not before for the `.venv` of the tree. Mypy then ends with 127 and the scan fails with that code.
- [Trivy with a checks bundle older than a day] → Trivy cannot update the bundle in the sandbox, and the record names the bundle that it read. A fetch command is a follow-up.
- [Four Semgrep jobs on a host with many processors] → A large batch can take longer than with one job for each processor. The measured batch of 100 files took the same time.
- [The address-space values were measured on one host with small inputs] → A larger input can need more. The values are about twice the need, and a tool that stops on its limit reports a failure with its error.
