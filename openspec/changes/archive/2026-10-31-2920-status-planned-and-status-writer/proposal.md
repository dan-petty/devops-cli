# Proposal

## Why

Issue #2920, part of the workflow tracker #2908. A roadmap item is `status/ready` while it is staged, while its plan waits for a merge, after the merge, and while a runner Job works on it. "Staged" and "Planned" live only in the hidden record of the issue body. A person cannot tell from a list of issues which Ready items have a plan, and which have a Job. On 2026-10-31 the items #2147 and #2747 were Planned and showed `status/ready`. Item #2739 showed `status/in-review` only when its pull request was ready.

The owner decided on 2026-10-31: add the label `status/planned`, and let the Service set the Status label from its record, as the single writer, with the rule of ADR 0016 that a job never reverts a person's change.

## What Changes

- The Status family gets a sixth label, `status/planned`, between `status/ready` and `status/in-progress`. `.github/labels.yml` declares it. ADR 0016 lists six Status labels and states the rule of the Service as writer.
- The new module `src/devops_cli/roadmap/status_sync.py` holds one function, `derive_status`. It maps the facts of an item to a Status: In Progress while a Job holds the item, else Planned when the plan is on the default branch, else Ready. The facts come from the job record and the plans on the default branch. The runner Job sets In Review when it marks its pull request ready, and `devops pr ready` does the same. The stop path of #2912 sets Blocked. The function derives neither, because no round can reach them: a Job that dies after it marked its pull request ready leaves the item In Progress, and the report of the Job stops it.
- `sync_status` writes the derived Status with the existing family replace of the store (`set_field`). It changes only an open item that holds Ready or Planned, and only when the label is the value that a job last wrote. A label that a person changed stays. It reads the issue again just before the write, so a view that is older than a change of a person, another lane or a close writes nothing. `sync_statuses` does this for every item of a round and reports each item that failed.
- Three places use the function, so label and record cannot drift. The row `implement` runs it after it reports the Jobs that ended, and again for the item whose Job it creates. The row `stage` runs it after it stages. The row `stage_ready` runs it for a plan pull request that it sees merged. A drift is repaired in the next round of any of them.
- The implement job takes a Planned item. The default filter adds `status=planned`. The plan accepts the Statuses Ready and Planned, and In Progress while the record names a Job that no round reported. A Job that the Service made then finds its own item.
- The report of a Job that ended counts a Planned item with no stop as a lost stop, as it does for a Ready item.
- `devops pr create` and `devops pr ready` replace Planned as they replace Ready. Refine holds a Planned item, as it holds an In Progress item.
- The state Blocked, the stop path that sets it, and its clearing on a new runner image are the work of #2912. This change adds no code for them.
- The workflow `clear-status` reads the labels that the closed issue holds when it runs, so a label that the Service wrote after the close is removed too.
- A consumer observes a new label, the rows and the plan of the implement job, so the change carries deltas for `roadmap-item-labels` and `roadmap-implement-job`.
- The change fits one pull request.

## Capabilities

### Modified Capabilities

- `roadmap-item-labels`: the Status family has six values, the Service sets the Status from its record, and a Status moves forward only through Planned.
- `roadmap-implement-job`: the job takes Ready and Planned items by default and leaves out the other Statuses.

## Feasibility

Checked on 2026-10-31 against the real system:

- ADR 0016 and `store.py`: the Status family is the five labels of `CONST_ROADMAP_STATUS_VALUES`, and `set_field` replaces the whole family in one `PATCH`. A sixth value needs one constant and one label. `field_label("Planned")` gives `status/planned`. No other code lists the five values: `grep` for `CONST_ROADMAP_STATUS_VALUES` finds the store only.
- The facts exist today. `PlannedChanges` (`planned.py`) holds the change folders of `origin/<default>` and is read once for each round by `stage` and by `implement`. `implement.job`, `implement.job_state`, `implement.pr` and `implement.stopped` are in the record. `PullStatus` has `state`, `draft` and `merged`. `stage_ready` already reads the stage pull request, which shows a merge.
- The rule "a job never reverts a person's change" can use the record. `set_field` writes the value it sets into the record, and `field_values` already tells a label that a job wrote from one that a person added. A label that differs from the value in the record was set by a person after the last job write. The seeded issues of the tests have no record, as an item that a person labeled by hand has none.
- The premise about the evidence holds: an item that refine set Ready keeps `status/ready` after its plan is on the default branch, because no code sets any other value. The implement job also refuses an item that is not Ready (`_Judge.judge`), so a Planned label needs the plan to accept it. This is part of the change.
- One more fact: the Service sets In Progress for an item before its Job starts. The Job runs `roadmap implement --item N`, which plans the item again, and `_Judge.judge` refuses an item that is not Ready. The plan must accept In Progress while the record names a Job that no round reported. A test replays this.
- The cost in requests is small. The sweep reads nothing for an item whose Status it does not change. For an item it changes, it reads the issue once more before the write.
- The In Review and Blocked states have no round that can reach them. A Job that marks its pull request ready sets In Review itself. A Job that dies first leaves the item In Progress, and `_report` sets it Ready with a stop. A first draft read the delivery pull request in the sweep for this case. A mutation test showed that no replay could reach that branch, so the code was removed.

The premise holds. No part of the item needs code that compensates for a missing tool.

## Existing Tool Considered

The store already covers the write: `set_field` replaces a label family, records the value and refuses a change of a person. `PlannedChanges`, `get_pull_status` and `write_each` cover the facts and the per-item failure. The GitHub label API needs no new client. There is no open library for a workflow of labels that fits this record, so the change builds the glue only: `status_sync.py` has about 130 lines. Cost: about 150 000 tokens to build it and its tests, about 40 000 tokens a year to keep it, and about 3 hours of elapsed time. It deletes no internal code.
