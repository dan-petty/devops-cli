# Design

## Decisions

- **The tool entry is `[python.ansible-core]`.** The tracker named it `[python.ansible]`. The table name of a Python tool is its PyPI package: `test_every_python_tool_pins_itself_in_its_hashed_requirements` checks `<name>==<version>` in the requirements, and the Renovate regex manager of `.github/renovate.json` looks up `[python.<name>]` on PyPI. PyPI `ansible` is the community package (14.x), not ansible-core, so `[python.ansible]` would fail the test and let Renovate write a wrong version. ansible-runner's pin is in `ansible-core.in`, and the pip-compile manager updates it.
- **Only `ansible-runner` goes on PATH.** The first install linked `ansible`, `ansible-config`, `ansible-galaxy`, `ansible-inventory` and `ansible-playbook` too, and replaced the links of a `uv tool` copy of the community `ansible` package on the workstation. That package holds the collections that the homelab plays use (`ansible.posix`, `community.general`, `kubernetes.core`), and the pinned environment holds none, so `make k3s` of homelab would have lost them. devops starts every Ansible command from the `bin` folder of the environment, so it needs no other link. The links of the community package were put back.
- **Where the environment is.** devops uses the install of `devops install-tools` under the user data root when its commands are there, else the folder of the `ansible-runner` on PATH. The devcontainer image installs each Python tool of the lock under `/usr/local/share/devops-tools/<name>` and links its commands into `/usr/local/bin` (`test_the_image_build_installs_the_tools_with_native_steps_under_usr_local`), so the image links `ansible-runner` there, and devops finds `ansible-config` and `ansible-inventory` beside the file that the link names.
- **Project facts are in the project profile, operational keys in the config.** Owner input of 2026-11-12 put the work under the generalization plan of #4627. The facts of an infra repo (its inventory, playbook folder, role folders, group of hosts out of service and Kubernetes folder) are fields of the profile type `ansible-k8s`. The config keeps `repo`, `path` and `agent_access`, and also `kube_context` and `ssh_key_prefix`: a kubeconfig context and a `devops ssh` key prefix name things on the workstation of the operator, not in the repository, as `k8s.context` and `ssh.key_prefix` already do. The design of #5120 had `kind`, `purpose` and `k8s_dir` in the config: `kind` is the profile type, `k8s_dir` is `[kubernetes] dir`, and `purpose` has no reader, so it is gone.
- **The smallest loader.** `resolve_profile(root)` merges four layers, low to high: the field defaults of `ProjectProfile`, the packaged type template, detection, and `.devops/project.toml`. A table merges by key, and a scalar or a list replaces the lower value. Each value records its source (`template: ansible-k8s`, `detected: ansible.cfg`, `.devops/project.toml`). The fifth layer of the model, operator overrides, has no key yet. Detection reads `ansible.cfg` with `configparser` (the parser that Ansible uses), with paths relative to the file and only paths in the repository. An invalid project file raises `ConfigurationError` that names the file. This slice reads the file of the checkout; the Service reads it at `origin/<default>` when #4635 adds the trusted read.
- **The project file row.** Row 2 is `present` when `.devops/project.toml` names the type, and lists every value with its source. With no file, it is `listed` with the values that differ from the type template, so a person can commit them. Onboarding writes nothing into the infra repo.
- **The offline group moves to the profile.** The design of #5120 read it from the inventory variable `devops_infra_offline_group`. It is a fact of the repository, so it is `[ansible] offline_group` (template value `offline`). `devops_infra_node_service` stays a host variable: it differs for each host, and the inventory is where Ansible keeps host facts.
- **The facts come from local tool output.** `ansible-config dump --format json --only-changed` gives the config file and the host key settings; a setting that it leaves out has its default. `ansible-inventory -i <inventory> --list`, with the inventory of the profile, gives the groups, with the hosts of their child groups, and the raw host variables. Both run in the root of the checkout with the child environment of `run_subprocess`, so no `ANSIBLE_` variable of the person changes them.
- **Host key checks read the config and the inventory.** A host key check is off when `host_key_checking` is false, or when `StrictHostKeyChecking=no` (or `off`) or `UserKnownHostsFile=/dev/null` is in `ssh_args`, `ssh_common_args` or `ssh_extra_args` of the `ssh` plugin, or in the host variables `ansible_ssh_args`, `ansible_ssh_common_args`, `ansible_ssh_extra_args`, `ansible_host_key_checking` or `ansible_ssh_host_key_checking`. The design named the config only. homelab set `ansible_ssh_common_args: "-o StrictHostKeyChecking=no"` in `group_vars/all.yaml` until homelab#24.
- **`devops_infra_node_service` is read raw.** Onboarding reads it from `ansible-inventory --list`, where a template is not rendered, and only checks that each host in service sets it. See the Feasibility section of the proposal for why the `debug` read waits for #5124.
- **YAML is composed, never constructed.** `yaml.compose_all` with the safe loader gives the node tree with line numbers, accepts tags such as `!vault`, and builds no object. A file is a playbook when it is one document that is a list of plays (each item has `hosts` or `import_playbook`). The tasks with `check_mode: false` and the collections in use come from the mappings that are list items (plays, tasks, handlers and blocks), so a dict of variables whose keys look like `net.ipv4.ip_forward` is not read as a module name. The live run on homelab found that case.
- **Rows.** The 17 rows are, in order: the tool environment, the project profile, `ansible.cfg` at the root, the inventory, the group of hosts out of service, playbooks, roles, pinned collections, host key checks, `known_hosts`, the `devops ssh` key, the kube context, a CI workflow, `devops_infra_node_service`, tasks with `check_mode: false`, Makefile targets that change a node, and the entry in `infra.repos`. A row that needs the tool environment or the inventory is `not readable` with the reason when the read cannot happen. Rows 14 to 16 are `listed`, not `missing`, because they name items for a person to read and do not stop the onboarding. The command exits 1 when a row is `missing`, as `devops roadmap onboard` does.
- **The target.** `<repo>` is `owner/name` when it has that form (`is_repository_name`), and then the checkout is `--path`, else the `path` of the entry, else `<repos.base_dir>/<owner>/<name>`. Any other value is the folder of a checkout, and its remote `origin` names the repository. The entry keeps `path` only when it differs from the default.
- **The access level.** `refuse_agent_raise` runs before the settings load: an agent (an agent tool that `detect_agent` names, an MCP call or a process in a pod) that gives `plan`, `safe` or `full` is refused with `INFRA_ACCESS_REFUSED`, which names `infra.repos[].agent_access`. With no `--agent-access`, the entry keeps its level, and a new entry is at `none`. A person may set any level.
- **One caller detection.** `core/caller.py` holds `agent_tool`, `in_mcp_call`, `mcp_call`, `runs_in_cluster` and `is_agent_caller`. `telemetry/usage_errors.py` and the MCP dispatcher import it from there.
- **One group callback.** Typer runs a group with one command and no callback as that command, so `devops infra onboard` would not parse. The group has an empty callback.

## Rejected alternatives

- **The facts of an infra repo in `infra.repos`.** The design of #5120 put `kind`, `purpose` and `k8s_dir` in the config. The profile model of #4627 keeps every project fact in the repository and only operational keys in the config, so one repository has one set of facts for every operator and for the Service.
- **The infra keys in `service.repos`.** See the Feasibility section of the proposal: it is a list of names with 14 readers, its entries turn on the Service rows, and it lives in the cluster.
- **A TOML writer for the values to declare.** No TOML writer is a dependency (`tomlkit` and `tomli-w` are not installed). The row lists `key = value` with the source, and the person writes the file, so no dependency comes in for a hint.

- **`[python.ansible]` with a field that names the PyPI package.** It would change the lock model, the Renovate regex and the research inventory for one name. The package name as the table name keeps every reader as it is.
- **Link every Ansible command of the pinned environment on PATH.** Rejected with the evidence above: it replaced the community package of the person and its collections.
- **`ansible -m ansible.builtin.debug` with the `tree` or `oneline` callback for the `devops_infra_` variables.** ansible-core 2.22.0 deprecates both for removal in 2.23 (`ansible-doc -t callback -l`), and no JSON callback ships with core. The ansible-runner event reader of #5124 is the place for a rendered read.
- **`yaml.safe_load` of each file.** It refuses `!vault` and other tags, and it gives no line numbers. Composition gives both without building objects.
- **Parse the Makefile with `make -pn`.** `make` evaluates `$(shell ...)` of the Makefile, which runs code. A line scan of the rule lines reads the targets and runs nothing.
