# Design

## Decisions
1. **One table maps each stack to its Applications.** `APPLICATIONS_BY_STACK` in `src/devops_cli/commands/k8s/stack_lifecycle.py` gives, for each stack, the names of the Argo CD Applications whose path sources deploy-stack builds and applies before the charts. The Applications come from `discover_argocd_applications(env.application_dirs)`, so the table reads the tree wherever it is: in devops-cli now, in dan-petty/homelab after #5134. A name that the tree does not hold stops the command with `ERRORS.k8s.application_not_found`, before it touches the cluster.
2. **A path stays where the build holds more.** The census of the proposal compares the objects of each row of `MANIFESTS_BY_STACK` with the build of the Application that holds them. An Application whose build holds the same objects goes into the table, and its rows leave `MANIFESTS_BY_STACK`. Each other row stays, with a comment that names the objects that the build adds. The issue states this rule for a stack. The change applies it to each Application: the builds of `argocd` and `otel` hold only the objects of their rows, and dan-petty/homelab#94 changes the build of `argocd`.
3. **The build reuses the sources of the deploy.** For each Application of the selected stacks, in the order of the table, `_path_builds` builds each source with a `path`, with the `SourceTrees` of the deploy (#6680). `path_source_folder` of `devops_cli.k8s.app_render` gives the local folder of the source: a source of the `origin` of the checkout reads the checkout, and a source of another repository is fetched at its `targetRevision` in the work folder of the deploy. A `path` that goes out of the folder of its repository raises `ApplicationSourceError` with `ERRORS.k8s.path_source_leaves_repository`, as `argocd_gate` refuses it, because Argo CD builds no such path. So no build reads a folder outside the checkout, and `devops k8s image-pins` and `devops k8s security-audit`, which build through `render_path_source`, refuse such a path too. `build_manifest_path` builds the folder. deploy-stack calls `_path_builds` right after `_collect_deploy_targets`, in the work folder, so a failed build or fetch stops the deploy before it touches the cluster. teardown-stack calls it after `_collect_teardown_targets`, so a failed build stops the teardown with exit 1 before it deletes an object.
4. **A build is a local read.** `build_manifest_path` gets the keyword `local_read`, which it gives to `run_subprocess` for `kubectl kustomize`. deploy-stack and teardown-stack set it, so the dry run builds the folders of the checkout, as the real run does. In a dry run they also set the keyword `offline` (decision 9). `render_path_source`, which `devops k8s image-pins` and `devops k8s security-audit` use, keeps the default: their dry runs build nothing, as before. A source of another repository gets no build in a dry run, because `SourceTrees` fetches nothing then.
5. **The deploy applies the build as one stream.** After the ConfigMap and the manifest paths of step 7, deploy-stack applies each build that holds an object with `kubectl apply -f -`, with the build as input. It replaces the template domain in the build as it does in a manifest file, so a build and a file give the same objects. A build with no object is not applied, as Argo CD applies nothing for it. When kubectl refuses a build, the deploy prints its reason and exits 1 before any chart, so no chart starts without the perimeter of its namespace. A file of `MANIFESTS_BY_STACK` keeps its unread result, as before.
6. **The teardown deletes the build.** `teardown-stack` makes the same `SourceTrees` in a work folder and builds the same sources. It deletes each build with `kubectl delete -f - --ignore-not-found`, in the reverse order of the deploy, after the post-Helm paths and before the manifest paths. A refused delete prints its reason as a warning, and the teardown goes on to the other objects.
7. **The dry run lists the objects.** The key `details.path_sources` of the deploy dry run maps the key `<application>: <path>` of each build to the objects of the build, in the order of the build. Each object is one string: `<kind> <namespace>/<name>`, or `<kind> <name>` for an object with no namespace in the build: an object of the cluster scope, or an object that kubectl applies in the namespace of the context. A string keeps the list inside the nesting depth of the details of a dry run. The objects are null for a source of another repository, whose fetch `details.source_fetches` lists, and for a build that fails in a dry run (decision 9). The teardown dry run gives the same entries in `details.path_source_deletes`, in the order of the deletes, and also `details.source_fetches` and `details.kustomize_fetches`.
8. **Tests.** A new test of `tests/commands/k8s/test_k8s.py` writes a tree under `tmp_path`: the fixture Application `logging` with the path source `env/logging`, whose kustomization takes the local component `env/components/perimeter`. The process fake gives the build of `kubectl kustomize`, because a test starts no program (ADR 0007): two NetworkPolicies, one of them from the component. The dry run lists both objects, and the real run applies the build with `kubectl apply -f -` and deletes it with `kubectl delete -f -`. A test of a refused build, of a source of another repository, of a missing Application and of a path out of the repository completes the set. `tests/support/k8s_tree.py` gives the folders of the table to the gate rows that read what deploy-stack applies (`network_policies.py`, `monitoring.py`), and `tests/gate/k8s_checks/deploy_stack.py` reads them for the ServiceMonitor check. The tests that start deploy-stack or teardown-stack on a tree with no fake of `kubectl kustomize` get the process fake, or an Application of the table. A teardown test gives an Application two path sources: the deploy dry run lists them in their order, and the teardown dry run in the reverse order. Another teardown test lets `kubectl kustomize` fail, or deletes the Application: the teardown exits 1 and starts no `kubectl delete` and no `helm`. For decision 9, a test with the process fake compares the environment of each `kubectl kustomize`: the dry runs give the environment of decision 9, and the real runs give none. Another test lets the build fail with a warning of Kustomize before an error of kubectl over several lines, as kubectl prints the config of a builtin transformer: both dry runs exit 0 and list the error as one line, with its cause. A test with `@pytest.mark.live("kubectl")` runs the real `kubectl kustomize` on the folder `env/logging` with each form of a remote target at `192.0.2.1`: a remote base by an https URL, a `git::` URL, an ssh URL, the SCP form and a path on `github.com`, the `path` of a PatchTransformer inline, in a local file and in `patches`, and a file and an env file of a ConfigMapGenerator, and also an ssh URL at the loopback address `127.0.0.1`. Each build fails within the bound of 30 seconds of the test (`_OFFLINE_BUILD_BOUND_SECONDS`, room for a loaded CI runner and far below the TCP connect timeout of an address with no route) with a proxy or transport error, and the dry run lists it in `details.kustomize_fetches`. A second live test serves a ConfigMap from a server of the test at `127.0.0.1`: the dry run downloads it and lists its object, because the environment of decision 9 does not block a loopback address. Where kubectl is not on the PATH, the marker skips these tests with the reason.
9. **A dry-run build has no route to a host that is not a loopback address.** The owner rule of 2026-10-04 says that a dry run makes no request. Kustomize fetches a remote target of a kustomization, and it has no option that refuses a remote load: `--load-restrictor` limits only local files. ADR 0032 plans remote bases, such as `https://github.com/dan-petty/infra//k8s/bases/valkey?ref=v0.1.0`. So in a dry run, `_path_build` builds the folder with `build_manifest_path(..., offline=True)`, which starts `kubectl kustomize` with the environment `CONST_K8S_KUSTOMIZE_OFFLINE_ENV`. Kustomize downloads a file with `net/http` of Go: its file loader uses an `http.Client` with the default transport. That transport takes the proxy of `HTTP_PROXY` or `HTTPS_PROXY`, or of the lower-case names, unless `NO_PROXY` names the host (`ProxyFromEnvironment` of `net/http`, `golang.org/x/net/http/httpproxy`). The proxy is `CONST_K8S_OFFLINE_PROXY_URL`, `http://127.0.0.1:9`, a port with no listener, and `NO_PROXY` and `no_proxy` are empty, so each download fails at once with `proxyconnect ... connection refused`. Go uses no proxy for `localhost` or a loopback address, and no environment key changes this. So the environment does not block an http or https download of a loopback address: a file, and also the URL of a remote base, which Kustomize first loads as a file. Such a request is not a read of the checkout. It can reach a server of the host, such as a `kubectl port-forward` to a cluster service or a tunnel. The owner rule of 2026-10-04 has no exception for it, and no owner decision accepts one, so the owner decides this exception. A network namespace with no listener, such as `unshare -rn` or bwrap `--unshare-net`, closes it where unprivileged user namespaces are available; the `RuntimeDefault` seccomp profile of a pod refuses `unshare` (`devops_cli.core.process_hardening`). Kustomize clones a repository with the `git` program, which gets the same environment (`gitRunner` sets no environment of its own). `GIT_ALLOW_PROTOCOL=file` makes git refuse each transport but `file`, also for a submodule (`protocol.allow` of git-config(1)). `GIT_SSH_COMMAND=false` fails an ssh connection, `GIT_TERMINAL_PROMPT=0` stops a prompt, and `GIT_CONFIG_NOSYSTEM=1` skips `/etc/gitconfig` (git(1)). `ALL_PROXY` and `all_proxy` give libcurl, the HTTP transport of git, the same proxy. The guard of `build_subprocess_env` accepts `GIT_ALLOW_PROTOCOL` and `GIT_SSH_COMMAND` only with these values (`CONST_GIT_LOCAL_ONLY_ENV`), because another value can enable the `ext::` transport or start a program. When a dry-run build fails, its objects are null, `details.kustomize_fetches` gives the error of kubectl as one line under the key of the build, and the dry run goes on. The line starts at the prefix `error: `, because a warning of Kustomize can come first, and it goes to the end, because the error of a builtin transformer holds its config on lines of its own and gives the cause last. The real run builds with the normal environment and stops on a failed build, as before. The block uses the documented behavior of Go and git and no rule of the Kustomize loader: about 60 lines, about 100k tokens and 1 hour to build, and a low cost to keep.

## Rejected alternatives
- **Keep the fixed list of a full stack when one Application differs.** Rejected: the census shows that the builds of `argocd` and `otel` hold the objects of their rows and no other object, and dan-petty/homelab#94 needs the build of `argocd` on a cluster without Argo CD.
- **Apply the build of `llm` and `argo-workflows-manifests` without the objects of `POST_HELM_BY_STACK`.** Rejected: the issue asks to keep the fixed list when a build holds more objects. A filter of the build by the post-Helm paths is a second list of the same objects, and the post-Helm step is not in the scope of the issue.
- **`kubectl apply -k <folder>`.** Rejected: a folder of another repository is in the work folder of the deploy, and a teardown after the deploy has no such folder. `apply -k` also does not take the domain of the templates, which `_apply_single_manifest` replaces in a file.
- **Build in the dry run with `local_read` as the default of `render_path_source`.** Rejected: the test `test_a_dry_run_renders_and_resolves_nothing` of `tests/k8s/test_image_pins.py` states that the dry run of `image-pins` renders nothing.
- **Skip an Application that the tree does not hold.** Rejected: a missing perimeter NetworkPolicy then goes away with no message. A chart with no Application stops the command in the same way (#6060).
- **Read the kustomization fields before a dry-run build, and build no folder that names a remote target.** Rejected: a parser of the loader rule of Kustomize misses cases. A review sent HTTP requests in dry runs through the `path` of a PatchTransformer and a file of a ConfigMapGenerator, inline or in a local file of `transformers`, and through an env file whose URL holds `=`, such as `?ref=main`. Each new field or form of Kustomize needs a new rule, and a missed rule sends a request. The environment of decision 9 blocks each of these cases by the behavior of Go and git.
