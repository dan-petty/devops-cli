# Design

## Decisions
1. **One table maps each stack to its Applications.** `APPLICATIONS_BY_STACK` in `src/devops_cli/commands/k8s/stack_lifecycle.py` gives, for each stack, the names of the Argo CD Applications whose path sources deploy-stack builds and applies before the charts. The Applications come from `discover_argocd_applications(env.application_dirs)`, so the table reads the tree wherever it is: in devops-cli now, in dan-petty/homelab after #5134. A name that the tree does not hold stops the command with `ERRORS.k8s.application_not_found`, before it touches the cluster.
2. **A path stays where the build holds more.** The census of the proposal compares the objects of each row of `MANIFESTS_BY_STACK` with the build of the Application that holds them. An Application whose build holds the same objects goes into the table, and its rows leave `MANIFESTS_BY_STACK`. Each other row stays, with a comment that names the objects that the build adds. The issue states this rule for a stack. The change applies it to each Application: the builds of `argocd` and `otel` hold only the objects of their rows, and dan-petty/homelab#94 changes the build of `argocd`.
3. **The build reuses the sources of the deploy.** For each Application of the selected stacks, in the order of the table, `_path_builds` builds each source with a `path`, with the `SourceTrees` of the deploy (#6680). `path_source_folder` of `devops_cli.k8s.app_render` gives the local folder of the source: a source of the `origin` of the checkout reads the checkout, and a source of another repository is fetched at its `targetRevision` in the work folder of the deploy. `build_manifest_path` builds the folder. deploy-stack calls `_path_builds` right after `_collect_deploy_targets`, in the work folder, so a failed build or fetch stops the deploy before it touches the cluster. teardown-stack calls it after `_collect_teardown_targets`, so a failed build stops the teardown with exit 1 before it deletes an object.
4. **A build is a local read.** `build_manifest_path` gets the keyword `local_read`, which it gives to `run_subprocess` for `kubectl kustomize`. deploy-stack and teardown-stack set it, so the dry run builds the folders of the checkout, as the real run does. `render_path_source`, which `devops k8s image-pins` and `devops k8s security-audit` use, keeps the default: their dry runs build nothing, as before. A source of another repository gets no build in a dry run, because `SourceTrees` fetches nothing then.
5. **The deploy applies the build as one stream.** After the ConfigMap and the manifest paths of step 7, deploy-stack applies each build that holds an object with `kubectl apply -f -`, with the build as input. It replaces the template domain in the build as it does in a manifest file, so a build and a file give the same objects. A build with no object is not applied, as Argo CD applies nothing for it. When kubectl refuses a build, the deploy prints its reason and exits 1 before any chart, so no chart starts without the perimeter of its namespace. A file of `MANIFESTS_BY_STACK` keeps its unread result, as before.
6. **The teardown deletes the build.** `teardown-stack` makes the same `SourceTrees` in a work folder and builds the same sources. It deletes each build with `kubectl delete -f - --ignore-not-found`, in the reverse order of the deploy, after the post-Helm paths and before the manifest paths. A refused delete prints its reason as a warning, and the teardown goes on to the other objects.
7. **The dry run lists the objects.** The key `details.path_sources` of the deploy dry run maps the key `<application>: <path>` of each build to the objects of the build, in the order of the build. Each object is one string: `<kind> <namespace>/<name>`, or `<kind> <name>` for an object of the cluster scope. A string keeps the list inside the nesting depth of the details of a dry run. The objects are null for a source of another repository, whose fetch `details.source_fetches` lists, and for a folder that reaches a remote target (decision 9). The teardown dry run gives the same entries in `details.path_source_deletes`, in the order of the deletes, and also `details.source_fetches` and `details.kustomize_fetches`.
8. **Tests.** A new test of `tests/commands/k8s/test_k8s.py` writes a tree under `tmp_path`: the fixture Application `logging` with the path source `env/logging`, whose kustomization takes the local component `env/components/perimeter`. The process fake gives the build of `kubectl kustomize`, because a test starts no program (ADR 0007): two NetworkPolicies, one of them from the component. The dry run lists both objects, and the real run applies the build with `kubectl apply -f -` and deletes it with `kubectl delete -f -`. A test of a refused build, of a source of another repository and of a missing Application completes the set. `tests/support/k8s_tree.py` gives the folders of the table to the gate rows that read what deploy-stack applies (`network_policies.py`, `monitoring.py`), and `tests/gate/k8s_checks/deploy_stack.py` reads them for the ServiceMonitor check. The tests that start deploy-stack or teardown-stack on a tree with no fake of `kubectl kustomize` get the process fake, or an Application of the table. A teardown test gives an Application two path sources: the deploy dry run lists them in their order, and the teardown dry run in the reverse order. Another teardown test lets `kubectl kustomize` fail, or deletes the Application: the teardown exits 1 and starts no `kubectl delete` and no `helm`. `tests/k8s/test_kustomize_remotes.py` tests the rule of decision 9 on kustomizations under `tmp_path`, and a test of `tests/commands/k8s/test_k8s.py` gives the folder `env/logging` a local base that names a remote base: both dry runs start no `kubectl kustomize` and list the remote base.
9. **A dry run builds no folder that reaches a remote target.** The owner rule of 2026-10-04 says that a dry run makes no request. Kustomize fetches a remote target of a kustomization, and it has no option that refuses a remote load: `--load-restrictor` limits only local files. ADR 0032 plans remote bases, such as `https://github.com/dan-petty/infra//k8s/bases/valkey?ref=v0.1.0`. So in a dry run, `_path_build` first calls `remote_targets` of the new module `devops_cli.k8s.kustomize_remotes` on the folder. The function reads the kustomization, and the kustomization of each local folder that it reaches through `resources`, `bases`, `components`, `generators`, `transformers` and `validators`, with the field names of the Kustomization schema. An entry of these fields is remote when it is an http or https URL (`loader.IsRemoteFile` of Kustomize), or a git repository in a form of `git.NewRepoSpecFromURL`: an ssh, https, http or file URL, after an optional `git::`, the SCP form with a user, or a path on `github.com`. A file field, such as the `path` of a patch or a file of a generator, is remote only as an http or https URL. A folder with a remote target gets no build: its objects are null, and `details.kustomize_fetches` lists its remote targets under the key of the build. The real run builds the folder, as before. No open Python library holds the loader rule of Kustomize; the module is about 150 lines, about 60k tokens and 1 hour to build, and a low cost to keep.

## Rejected alternatives
- **Keep the fixed list of a full stack when one Application differs.** Rejected: the census shows that the builds of `argocd` and `otel` hold the objects of their rows and no other object, and dan-petty/homelab#94 needs the build of `argocd` on a cluster without Argo CD.
- **Apply the build of `llm` and `argo-workflows-manifests` without the objects of `POST_HELM_BY_STACK`.** Rejected: the issue asks to keep the fixed list when a build holds more objects. A filter of the build by the post-Helm paths is a second list of the same objects, and the post-Helm step is not in the scope of the issue.
- **`kubectl apply -k <folder>`.** Rejected: a folder of another repository is in the work folder of the deploy, and a teardown after the deploy has no such folder. `apply -k` also does not take the domain of the templates, which `_apply_single_manifest` replaces in a file.
- **Build in the dry run with `local_read` as the default of `render_path_source`.** Rejected: the test `test_a_dry_run_renders_and_resolves_nothing` of `tests/k8s/test_image_pins.py` states that the dry run of `image-pins` renders nothing.
- **Skip an Application that the tree does not hold.** Rejected: a missing perimeter NetworkPolicy then goes away with no message. A chart with no Application stops the command in the same way (#6060).
- **Build each folder in the dry run, also one with a remote base.** Rejected: Kustomize then fetches the remote base, and a dry run makes no request (decision 9). The current tree holds no remote base, but ADR 0032 plans them.
- **Block the network of the `kubectl kustomize` child in a dry run.** Rejected: Kustomize downloads a file with its own HTTP client and clones with git, so each path needs its own block, such as a proxy setting and `GIT_ALLOW_PROTOCOL`. A blocked fetch also fails the build, and the dry run then cannot list what the build would fetch.
