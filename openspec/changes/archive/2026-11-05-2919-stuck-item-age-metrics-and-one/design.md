# Design

## Decisions

- **Read each issue's label events through `label_changes(number)`. Cache each item's times until a label changes.**: `GET repos/<repo>/issues/<number>/events` gives every label event of an issue in one page, for 78 of 78 open items (the most is 13 events, Feasibility 4). Reads only on a label change cost at most 209 requests in the busiest day measured, about 9 an hour. A read of every item in each round costs 360 an hour (Feasibility 5). The cache is a module variable of `src/devops_cli/github/metrics.py`, like `_sent_item_series`, and `tests/conftest.py` resets it after each test.
- **Put the read in the store, not in `metrics.py`.**: The row gets `store` from the Service (`_run_metrics_adapter` in `run.py`). `tests/roadmap/test_roadmap_run.py` runs it over `InMemoryRoadmapStore`. A `gh` call in the metrics module runs the real program in that test. `InMemoryRoadmapStore` already records a `labeled` change with its clock for each label that a write adds (`_relabel` in `memory_store.py`). So one method serves both adapters, and the contract suite `tests/roadmap/test_roadmap_store_contract.py` can pin them together.
- **Send the issue number as the value of `devops_cli_roadmap_oldest_item_number`, not as a label.**: The issue wants the item number in the alert message. The owner called an issue number as a label "unsafe" on #3069, and pointed to `bounded_label` (#2742). An alert annotation can read a second series with the `query` function, and promtool 3.15.1 accepted and tested that rule (Feasibility 7). So no label holds an issue number. The series set stays at 12 for each repository.
- **Send every pair of a status and a plan flag each round, with 0 for an empty pair.**: The pairs are a closed set: 6 statuses (`CONST_ROADMAP_STATUS_VALUES`) times 2 flags. A pair that sends 0 each round never keeps a stale age. So the age gauges need no "send 0 once" memory, as `_emit_item_counts` has. That memory serves `devops_cli_project_items`, whose labels (release, type, priority) form an open set. The cost is 25 points a round for a repository.
- **The `plan` flag is true when the job record of the item holds `stage.pr`.**: `docs/ROADMAP_WORKFLOW.md:82` names `stage.pr` as the record of a staged Ready item. Its plan pull request waits for a person (gate G1). The job record comes with the issue listing, so the flag costs no request. A check for the change folder on the default branch costs one `path_changed_at` request for each item.
- **Compute the age from the latest `labeled` event of the current label, with an injected clock.**: The age is the clock minus that time. An `unlabeled` event of the label cancels the earlier `labeled` event, because a person can remove a label and add it again. The clock is a parameter `clock: Callable[[], datetime]` of `collect_project_metrics_report`, the form that `InMemoryRoadmapStore(clock=...)` takes. The test of the issue needs no patch of the wall clock. It sets an event at T, a clock at T plus 3600, and expects a gauge of 3600.
- **A failed read of the events logs a warning and sends no age.**: `collect_project_metrics_report` catches `GitHubOperationError` around the age code only, so the report keeps the releases, the CI runs and the item counts. The adapter's own `except Exception` in `_run_metrics_adapter` would drop all of them for one failed issue. A blind `except` adds a site to the ceiling of `tests/fixtures/swallowed_failures_ceilings.json`. The gauges send no new point in that round. Prometheus ends an old series by staleness, so the dashboard shows no data, not 0.
- **The alert threshold is the literal 86400 seconds in the rule.**: Five of the six Service rules with a numeric threshold use a literal. They are 7200 seconds (`RoadmapServiceLaneStalled`), 352 (`RoadmapServiceModelRequestsHigh`), 20 (`RoadmapServiceWebhooksRejected`), 300 (`RoadmapServiceGitHubWritesHigh`) and 150 (`RoadmapServiceSelfDeliveriesHigh`), and the README table names each one. Only `RoadmapServiceGitHubRequestsHigh` follows a setting, which needs a field, a configmap key, a served series, two reference documents and a constant (Feasibility 8). The issue says "a set time" and gives no setting. So a person who wants another value edits one line of the rule and one line of its unit test.
- **Put the alert in a new group `roadmap-service-items`.**: The comment above the group `roadmap-service-activity` reads "what the Service writes, the deliveries of its own writes and its web search". Its requirement names its three alerts. An age alert is not Service activity. The plan of #2950 appends its alert to that group. A group of its own makes the two changes edit different spec requirements, different fixture files and different rule groups.
- **Put the panel at `x` 0 and `y` 34 in `project-metrics.json`, 12 wide and 8 high.**: The panels below it move down by 8. The items panels "Items by Release" and "Active Items by State" are in that row (`y` 26 to 34). `_PURE_DEVOPS_CLI_DASHBOARDS` lists the file. The owner asked to build the age panel so that it can sit next to the inbox panel, and not to wait for it (#2919). The free right half is for the inbox panel.
- **The alert reads the last sample of the last 30 minutes, with `last_over_time`.**: The metrics row sends each round, every 13 minutes by default. Prometheus drops a series that has no sample for 5 minutes, so an instant selector would flap. The webhook rule uses the same form (#2505). The window is longer than one round. So one missed round does not clear the alert.
- **The `plan` flag follows the job record as the store holds it.**: A person can close a stage pull request. The job record keeps `stage.pr` until the stage job writes the record again (`stage.py`, `StageRecordKey.PR`). The age then keeps counting in `ready` with a plan. The item does not change state on a close, so the rule cannot tell the two apart. The stage job writes the record again when it stages a new plan.
- **An item with a status label and no `labeled` event in its history gets no age in that round.**: The row logs a warning that names the item. The other items of the pair still count. A missing event is not an error that stops the round.
- **The cache keeps the time while the status and owner labels stay the same.**: A status that changes and changes back between two rounds keeps its first time, because the cache key does not change. The spec requires no read while the labels stay the same, so the cache cannot see that change. The cache keeps only the items of the repository of each round, so a closed item leaves it.
- **A stale pod can fire the alert for up to 30 minutes after it stops.**: Each pod sends its own series, with its own `service.instance.id`. `max by` over the window reads the last value of a pod that stopped, so a restart can keep an old number for the window. The Service runs one replica with the Recreate strategy, so only one pod sends at a time. A rule that drops a stopped pod needs a join on the instance label, which this change does not add. So the limit stays, and the two-pod promtool case is not in this change.

## Rejected alternatives

- **Read the repository events (`issues/events`), page by page, newest first, as `changes_since` does.**: It costs one page a round in the steady state, less than 9 an hour. The first round must read back to the oldest label event of each item. GitHub stops the listing at page 300 (HTTP 422 at page 301, Feasibility 3). Page 300 starts at 2026-09-09, so an item older than that gets no age. The per-issue read has no such limit, and it costs 78 requests once.
- **Read the events of every item each round.**: 78 items, each read 4.6 times an hour, cost 360 requests an hour, which is 72% of the budget of 500. ADR 0016 rejects "a read of each Item's timeline costs one request for each Item" (`docs/adr/0016-labels-hold-the-roadmap-items-fields.md:28`) for the actor of each event. This design keeps that cost low by reading the events once for each change of a label. The ADR consequence "a label change is an issue event" supports that read. The ADR has a note for this read (#2919).
- **Put the item number in a label `item`.**: That makes one new series for each change of the oldest item. The number of series is bounded by the number of issues (about 3,240 numbers so far). The owner called it unsafe (#3069). A value gauge has no such cost.
- **An info series `devops_cli_roadmap_oldest_item_info{item=...} 1` and a `group_left` join in the rule.**: It has the same label problem as the label `item`. The rule and its unit test would need a join on `repo`, `state` and `plan`.
- **A gauge of the time the item entered the state (`..._since_timestamp_seconds`) and `time() - x` in each query.**: Criterion 3 of the issue asks for the age, computed with a fake clock. The precedent `devops_cli_service_job_start_timestamp_seconds` shows the form. It would keep the age right while the Service is down. The age gauge does not. The issue and the refine decision chose the age.
- **Use `updated_at` or `created_at` of the issue.**: `updated_at` moves with any edit or comment (`IssueRecord` docstring in `store.py`). `created_at` is the age of the issue, not of the state.
- **Read the events of each issue in the metrics module through `gh`.**: See the second decision. It breaks the store seam that `tests/roadmap/test_roadmap_run.py:1375` uses.
- **Add a setting `service.item_stuck_hours` and send it as a series.**: See the threshold decision. It needs at least eight files for one number. The owner has not asked to change that number.
- **Add the age to `devops roadmap inbox`.**: The inbox is a list for a person. Its "age" is the time since the last update. The issue asks for a metric.
