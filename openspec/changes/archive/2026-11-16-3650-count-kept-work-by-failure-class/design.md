# Design

## Decisions

- **Emit the new counter `devops_cli_service_kept_work_total` with the labels `repo`, `class` and `outcome`, and change neither `devops_cli_service_implement_jobs_total` nor its requirement.**: The base requirement `Implement job outcome counter` counts each reported runner Job once, and #4703 and the success share that #3655 plans read that counter. A kept-work result on it counts a Job that starts from kept work more than once. The scenario "Counter selection follows #3069" of the issue asks for this counter when `devops_cli_roadmap_pipeline_implement_total` does not exist, and no file of the tree names that counter.
- **Give the counter no label `item_class`.**: The issue asks for the failure class and the outcome, and the jobs counter already splits the Jobs by item class. The counter has 3 label sets for each member of `FailureClass` and each repository.
- **Keep the class of the stop in `implement.continued`, written by the clear rule of the Service.**: `src/devops_cli/roadmap/stop_clear.py:320:ImplementRecordKey.FAILURE: None,` removes the class at the clear, and the clear runs before the Job is created, so no later read of `implement.failure` can give the class of the continued stop.
- **Write `implement.continued` only when the record holds `implement.wip` and `implement.failure` holds a member of `FailureClass`, and else remove it in the same write.**: The issue counts `continued` when the record holds the class of the stop, and an item with no kept work must count nothing. A class outside the enum gets no count, so the label `class` holds only the taxonomy and needs no `none`. The Service round holds no checkout to call `kept_commits`.
- **Count `continued` in `_create` only when the record holds `implement.continued` and `implement.wip`, after `jobs.create` returns, and remove an `implement.continued` with no `implement.wip` in the claim write.**: An old mark, such as that of an item that a person took back after the clear, must not count a Job with no kept work. The claim is a write that `_create` makes in any case, so the removal costs no request. A create that fails counts nothing.
- **Remove `implement.continued` in the release write of every report, and count one outcome at most.**: The report counts `blocked` with the class of the new stop when `_failure_of` gives one, and `finished` with the kept class when `_attempt_result(item)` is `ready`. A `yielded` or `returned` report clears the mark and counts no outcome: a yield is no stop and no ready mark, and a return to New ends the plan. So the count of `continued` less the counts of `finished` and `blocked` is the kept runs that yielded, returned or still run, and no report counts the same outcome twice.
- **Land the enum member, the row of `docs/ROADMAP_WORKFLOW.md` and the reader line of the record table in one group.**: `tests/invariants/test_roadmap_workflow_doc.py:158` and `tests/roadmap/implement/test_roadmap_implement_record_readers.py:72` each fail while the other side of the pair is missing.
- **Add the constant and its entry in `deferred_metrics` in the group that counts.**: `tests/grafana/test_grafana_dashboards.py:1012` reads each `CONST_SERVICE_METRIC_` constant that the set does not defer, so the constant fails that test until the set holds it. #3655 owns the dashboard and the alerts of the pipeline and already charts the deferred counters of #3069.
- **Prime each member of `FailureClass` for each outcome and each repository.**: Each increment writes a class of the enum, so each label set exists before the first count, and no label set exists that no increment writes.
- **Add the metric list as a new section at the end of `k8s/README.md`, with the link `../docs/CLUSTER.md#roadmap-service`.**: `k8s/README.md:602:## Alerting` and the other sections are sliced by their headings in the tests, so a new trailing section changes no parsed text. The README is in the folder `k8s/`, so the link goes up one folder.
- **Name the Service counter in the module docstring of `src/devops_cli/telemetry/instruments.py`, in a group of its own, and change no other module.**: `tests/telemetry/test_telemetry_instruments.py:81` binds the `devops_cli_` prefix to that path, so the group that satisfies the registry rule edits the instruments module and nothing else.

## Rejected alternatives

- **Add a label `class` and the results `continued`, `finished` and `blocked` to `devops_cli_service_implement_jobs_total`, as the first plan did.**: A Job that starts from kept work then counts once for its report and once more for each kept-work result, against #4703 and the success-share alert of #3655. The label sets of the counter grow from 33 to 990 for each repository.
- **Reuse `devops_cli_roadmap_pipeline_implement_total` with one more outcome.**: No file of the tree names that counter, so the condition of the issue for its reuse does not hold.
- **Read the class of the continued stop from `implement.failure` in `_create`.**: `src/devops_cli/roadmap/stop_clear.py:320:ImplementRecordKey.FAILURE: None,` removes the class at the clear, and `src/devops_cli/roadmap/implement/implement_submit.py:579:stops = clear_stops(` runs before `src/devops_cli/roadmap/implement/implement_submit.py:610:created = _create(store, api, repo, plan.selected[0], label, size)`, so the record holds kept work and no class at `_create`.
- **Count `continued` in `_create` whenever the record holds `implement.continued`.**: An old mark of an item with no kept work would count a Job that starts from nothing.
- **Prime and write the class `none` for a stop with no class.**: The issue counts a continued Job only when the record holds the class of the stop, and each stop that the runner or the Service writes holds a class. A `none` value adds label sets that no rule reads.
- **Call `kept_commits` in the Service round to find the kept work on the item branch.**: `src/devops_cli/roadmap/implement/implement_submit.py:def _report` takes a store, a client of the cluster and the item, and the Service round runs no git command, so it holds no checkout of the item branch.
- **Count only the terminal outcomes `finished` and `blocked`.**: The first acceptance criterion asks for a test of `continued` when the next Job starts from kept work, so the counter has to hold that outcome.
- **Chart the counter in the row "Roadmap Service" in this change.**: #3655 owns the dashboard and the alerts of the pipeline, and the issue asks for no panel.
- **Add the row of `implement.continued` to `docs/ROADMAP_WORKFLOW.md` in a later group, after the code.**: `tests/invariants/test_roadmap_workflow_doc.py:158` fails while the enum holds a key that the page does not name, so the key and the row land in one group.
- **Leave `src/devops_cli/telemetry/instruments.py` untouched, because the Service series live in the config constants.**: `tests/telemetry/test_telemetry_instruments.py:81` binds the `devops_cli_` prefix to that path, and the archived gate rule `openspec/changes/archive/2026-11-07-3254-list-the-registry-and-ratchet-entries/specs/roadmap-stage/spec.md:4` refuses a plan that adds a counted item and has no task whose text names the declared path.

## Security

Nothing crosses a trust boundary: the change adds one Service counter, adds one key to the job record and edits documents under `k8s/` and `docs/`. A person confirms that `k8s/README.md` and `docs/CLUSTER.md` list the counter with its label values and hold no secret, no internal host name and no private address, and that no label value holds an issue number. `uv run devops ci test tests/telemetry/test_service_counter_series.py` fails when a primed label value leaves the bounded set, `uv run devops ci test tests/roadmap/test_roadmap_stop_clear.py` fails when the clear stops keeping the class, and `uv run devops ci test tests/invariants/test_roadmap_workflow_doc.py` fails when the workflow page and the job record disagree.
