# Design

## Decisions

- **Run the stock `Coder` shell with no allowed command and no denied command, and keep the wait of `roadmap.implement.command_timeout_seconds`, the `run_command` tool and the environment of `shell_environment` in the new `step_shell` of `src/devops_cli/roadmap/implement/implement_shell.py`.**: The allowlist is the control that the issue identifies in the 40% success rate, and the runner pod is the sandbox. The wait and the environment are what the shell needs for the broker and the scratch home, and #4493 kept the blocking tool in place of the persistent `shell`.
- **Turn `repo_context` on and add the `Skills` capability over the skill folder of the repository.**: The issue states that the devcontainer harnesses succeed with the project instructions and the skills, and `AGENTS.md` is a file of the staged tree.
- **Add `RequireVerification` with the project checks and `WrapUpAtLimits`, and pass the checks through the new function `project_checks`.**: `RequireVerification` sends an unverified run back to its checks, and the verification commands of the group and the check of the preset are the checks that the step already runs at exit.
- **Carry one `Conversation` in a `StepConversation` that `run_step` fills and that the group loop of `src/devops_cli/roadmap/implement/implement_run.py:1104:outcome = run_step(` keeps for the item, instead of a field of the outcome.**: `src/devops_cli/roadmap/implement/implement_step.py:595:class StepOutcome(BaseModel)` is a pydantic model that the record of a step dumps, and a `Conversation` field would put model messages into that record; the carrier keeps the messages out of the outcome.
- **Move the verification reader, the negative-search word, the checkout prefix and `shown` to `src/devops_cli/roadmap/verification_command.py` before the shell policy goes, and move the tools table into the module that holds `src/devops_cli/roadmap/tools.py:def tool_names`.**: The stage gate, the plan reader, the step, the run, the tool log and the toolchain preset read them, and the shell policy is what the issue deletes, not the verification grammar or the tool table.
- **Rewrite the import of the verification reader in `tests/roadmap/test_roadmap_plan_rewrite.py` and `tests/roadmap/test_roadmap_step_files.py` in the group that creates `src/devops_cli/roadmap/verification_command.py`.**: `tests/roadmap/test_roadmap_plan_rewrite.py:10:from devops_cli.roadmap.implement.implement_shell_policy import Verification, read_verification` and `tests/roadmap/test_roadmap_step_files.py:10:from devops_cli.roadmap.implement.implement_shell_policy import verification_problem` import the deleted module, so the suite would fail at collection without them.
- **Build the known-program table of the tool log from the program table of the runner image, `RUNNER_TOOLS` of `src/devops_cli/roadmap/runner_tools.py`, through `src/devops_cli/roadmap/runner_tools.py:def tool_names`.**: `src/devops_cli/roadmap/tools.py:def tool_names` returns the agent tool names of a holder, such as `read_file`, `write_file` and `run_command`, so the log would mask every program of the image; `src/devops_cli/roadmap/runner_tools.py:119:RUNNER_TOOLS: tuple[RunnerTool, ...] = (` is the fixed table of the programs of the image.
- **Modify the base requirement Every tool call of a step writes one line to the Job log, and keep its ten scenarios with the runner program table and with the `refused` outcome of a call that repeats a failed call.**: The base text names the allowlist and `IMPLEMENT_SHELL_REPLACEMENTS`, which the change deletes, and `src/devops_cli/roadmap/implement/implement_tool_log.py:497:self._note(call.tool_name, program, ToolOutcome.REFUSED, digest=digest)` keeps the `refused` outcome for a repeated failed call.
- **Remove the refused count from the digest and from the stop reason, then the refusal path and the two refusal stops of the log, then the three refusal settings.**: `src/devops_cli/roadmap/implement/implement_step.py:904:refused=log.refused_text(), retried=log.retried` calls the method and `src/devops_cli/roadmap/implement/implement_tool_log.py:541:in_a_row = self.limits.max_consecutive_refusals` reads a setting, so a method and a setting go only after their last reader.
- **Remove the refused count from the digest of progress and keep the base scenario names of the requirements that state the extension rule while their counts become successful edits.**: A modified requirement keeps every scenario of its base requirement, and no refusal exists to count once the shell refuses nothing.
- **Keep the compaction controls of `Coder` and pass the conversation of one task group of an item to the next.**: The issue asks for one conversation with compaction, and `ClearToolResults` and `WarnNearLimits` already carry the context window of the task.
- **Give each version row of the grade report its all-attempt count and its infrastructure share.**: The second acceptance item says that every attempt counts and that the report gives the share of infrastructure failures, and `src/devops_cli/roadmap/job_grade_report.py:196:class VersionGrade(BaseModel)` holds the measure of the attempts with no cut only.
- **Leave `tests/module_durations.json` and `tests/fixtures/roadmap_eval` unchanged, where the name of the deleted module is history.**: The durations record is rewritten from the shard reports of CI, and the eval fixtures hold recorded plans and issues of earlier items that no test reads as a claim about the shell.
- **Leave the measurement of 30 graded attempts to the follow-up #6768 of the refine block.**: The attempts on the new version exist only after the merge, and the grade report that group 15 completes gives the share of infrastructure cuts over every attempt.

## Rejected alternatives

- **Keep the command allowlist and add a wider program table.**: `docs/ROADMAP_WORKFLOW.md:312:Any program that is not in the first table gets a refusal` shows that the allowlist is the control that the issue measures, and the issue records a 40% success rate over 7 days to 2026-11-20.
- **Keep the allowlist and the refusal limits behind a setting.**: The staged step holds the single shell path that a setting would duplicate, and the tests that cover only it: `tests/roadmap/implement/test_roadmap_implement_shell_policy.py` and `tests/roadmap/implement/test_roadmap_implement_shell_refusal.py`.
- **Build a new agent loop in place of the harness.**: `src/devops_cli/ai/knowledge_base/devops_cli/libraries/pydantic_ai_harness.md:77:capabilities=[LocalWorkspace("/path/to/checkout"), Coder(repo_context=False, sub_agents=False)],` shows that the harness already builds the loop, so a new loop adds code to build and keep.
- **Start a new conversation for each task group, as the step does now.**: `src/devops_cli/roadmap/implement/implement_run.py:1104:outcome = run_step(` runs one step per group and passes no conversation, so each group begins with no message of the earlier group.
- **Build the known-program table of the log from `src/devops_cli/roadmap/tools.py:206:return tuple(name for name, entry in TOOLS.items() if holder in entry.holders)`.**: That line returns the agent tool names of a holder, such as `read_file` and `run_command`, so `git status` would be written as `other:<digest>` and the test of a program of the image could not pass.
- **Keep the refused count of the digest and the refused window of the extension, and drop only the sentence of the added requirement.**: `src/devops_cli/roadmap/implement/implement_limits.py:def extends` reads the refused count, which no shell refusal can fill once the allowlist is gone, so the requirement would state a count that is always zero.
- **Add the conversation to the outcome of a step as a field.**: `src/devops_cli/roadmap/implement/implement_step.py:595:class StepOutcome(BaseModel)` is a pydantic model that the record of a step writes, so a `Conversation` field would put the model messages into that record.

## Unchanged references

- `tests/module_durations.json` (module name): It records the measured seconds of the deleted test modules, which no test reads as a claim about the shell, and the record is rewritten from the shard reports of CI.
- `tests/fixtures/roadmap_eval` (recorded plan): The eval fixtures hold recorded plans and issues of earlier items, so the name of the deleted module is history in them and no test asserts it.

## Security

The stock shell crosses the trust boundary of the step: it runs any program of the runner image in the pod, so the pod settings become the only control. A person must confirm that the runner pod keeps no Kubernetes token, that the installation token of the job names one repository, that the shell of a step gets none of the job's variables, and that the pod keeps `readOnlyRootFilesystem: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: ALL` and `runAsNonRoot: true`. The test `test_the_agent_of_a_step_is_stock_coder` fails if an allowlist or a refusal wrapper comes back, and `uv run devops ci --check --only k8s` fails if the pod settings or the cluster configuration change.
