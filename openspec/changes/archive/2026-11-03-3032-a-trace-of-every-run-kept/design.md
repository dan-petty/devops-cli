# Design

## Decisions

1. **A new module, `ImplementTrace`, and not a field of `RunTrace`.** `RunTrace.absorb` builds its record from the messages of a run after it ends (`agent_run.py:169-176`). An outcome such as `refused` is known only inside the hook, where `is_policy_refusal` reads the cause chain (`implement_tool_log.py`), and a check run is no message at all. The new module reuses the parts that fit: `bounded_text`, `mask_secret_named_values` through `argument_json` (the renamed `_argument_json`, which takes a `ToolCallPart`, as the hook has), `ToolOutcome` and `logged_reason`.
2. **The collector is an argument of `run_step`, and `ToolCallLog` carries it.** `run_step` has three callers: the job (`implement_run.py:454`), the eval (`implement_eval_run.py:274`) and the command (`commands/roadmap.py:530`). The argument is optional, so the other two record nothing. `ToolCallLog` already reaches the three places that need the collector: its hooks, `_run_turn` and `_exit_failure` (`log` is a parameter of both). The collector is not a field of `StepOutcome`: `render_outcome` prints that model as a table or JSON, and a trace of 100 events does not belong in it. It also survives an exception that leaves no outcome, such as a refused key.
3. **An event holds the digest of a call, not its argument.** The Job log writes no argument, because an argument can hold a path or a secret (`implement_tool_log.py`). The trace goes into an issue body, which every reader of the repository sees, so it keeps the same rule. A digest of 12 hexadecimal characters of the masked argument still shows that the model made the same call twice, which #3053 needs for "no attempt repeats a failed action unchanged". The digest is taken over `argument_json`, so a secret-named value never enters it.
4. **The value is JSON text under one key, `implement.trace`, with the count `dropped`.** The job record is a flat map of text (`JobRecord`, `store.py:219`). The refine text of the issue proposes a bare array. A count lets a reader tell a short run from a cut one. The bound is 8,192 characters: about 105 events at 78 characters, and 10,500 characters in the block, far under 65,536 (Feasibility 6).
5. **The newest events stay.** A run fails at its end. The stop already keeps the last retries and not the first (`CONST_ROADMAP_IMPLEMENT_STOP_REASONS`, `implement_tool_log.py`: a deque of the last reasons).
6. **The trace is written after each passed group, at the stop and at the ready mark, and cleared at the start.** `_record` already writes after each group at no new request. A Job that the Service ends for a stall never reaches `stop()` (`implement_deadline.py:17-19`). A trace left from the last run would show as the trace of this run until the first group passes, so the start clears it, as it clears `implement.stopped` and `implement.failure` (`_start`).
7. **`explain --trace` prints the trace and no verdict.** The verdict walk needs a clone and git (`read_remote_heads`, `read_planned_changes`). The trace is in the issue, which `store.item` reads once. This is why the requirement "The command makes no model call and no write" is MODIFIED: its second sentence says that `explain` reads the branches and the change folders.
8. **One renderer, `summary_table`, for both comments.** #3076 asks for the output of `follow` "in the same shape as the PR comment table". The two comments differ only in their rows: the pull request comment lists the steps since its mark, the stop comment lists them all.
9. **"Attempts" is `1 + repair_rounds`.** `StepOutcome.repair_rounds` counts the extra turns (`implement_step.py`, `_attempt`). A send again after a failed stream is not an attempt: it is a `retry` event.
10. **The last failing command is the command of the last `check` event with an exit status other than 0 in that step.** For a check of the pull request, which has no command, it is the name of the check (`_StopError.check`). The scoped checks carry their command already (`ScopedResult.command`) and gain `status`, the exit status, or none for a timeout.
11. **`mask_private_hosts` goes in `sanitizer.py` beside `mask_secrets`.** The patterns are there (`PRIVATE_HOST_PATTERNS`), and `mask_secrets` does not apply them (Feasibility 4). A second filter in the trace module would drift from the patterns that Logfire scrubs with.
12. **Test-first order is by dependency.** The masking function (group 1) and the trace module (group 2) have no caller. Group 3 gives them the step, group 4 the job, group 5 the comments, group 6 the command. Each group's tests run with only the groups before it.

The word "trace" is also the name of the span `implement.deadline` (spec "The trace shows each deadline change") and of the stage `RunTrace`. This change uses "the trace of a run" for `implement.trace` only.

## Rejected alternatives

- **OpenTelemetry spans as the store.** Rejected on a fact: Tempo keeps a span for 168 hours (`k8s/otel/tempo-values.yaml:32`), and a Blocked item waits for a person for longer. The record would need a trace id, and `explain` the Tempo URL (`commands/telemetry.py:360-382`). The issue gives another reason, "a dependency and a collector". That reason is wrong: the runner reaches the collector (`networkpolicy.yaml:38`). Spans for the same events stay possible later and need none of this code to change.
- **Extend `RunTrace`.** Rejected: see decision 1. It has no outcome, no duration and no check.
- **The masked argument text in the event, as `RunTrace` has.** Rejected: see decision 3.
- **4,096 characters, or no bound.** The refine text rejects both. The sample (Feasibility 6) gives 52 events at 4,096 characters, which is two groups of a short run. No bound would let a run of 138 requests write a block of tens of thousands of characters to the issue body at every group.
- **A flat log of lines, as the Job log has.** Rejected: the table needs the fields (the tokens of a step, the exit status of a check), and a line needs a parser to give them back.
- **The Job artifact.** Not built: no artifact store exists (Feasibility 8). #3105 plans one.
- **An external secret scanner for the masking.** The refine text rejects it because "the Runner pod has no network access by design". That is wrong: the runner reaches the gateway, the cache, the collector and public HTTPS (`k8s/devops/cronjob-runner.yaml:6`). It is rejected for another reason: `mask_secrets` already masks by the forms of the project (`sanitizer.py`), and a second scanner would give a second answer for the same text.
- **A table in the stop comment only.** Rejected: the issue asks for both comments, and the pull request comment already has one line for each step, so the table replaces that line and adds no second list.
