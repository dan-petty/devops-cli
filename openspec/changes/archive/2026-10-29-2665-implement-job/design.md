# Design

## Decisions

- **Three modules, in stage's shape.** `implement.py` selects and plans, and writes nothing. `implement_run.py` writes: it runs the items of a plan. `implement_pull.py` holds the calls to the pull request: the status, the body, the comment, the log of a failed check and `gh pr ready`. The command keeps `--plan` and `--confirm` as stage does, and a plain run is a plan with a note.
- **The job refuses outside a runner.** The setting `roadmap.implement.in_runner` is false by default and has an environment variable. `apply_implement` reads it first and raises `RoadmapImplementError` naming the setting. The step, run by a person with `--group`, is unchanged: a person who runs it owns the checkout. The setting is a statement of fact by whoever starts the pod, and the runner Job template of #2667 is the one place that sets it. A setting is the explicit switch the review asked for; the job tests no property of the host to guess a sandbox.
- **The credential stays with the job.** Every `git fetch`, `rebase`, `push`, every request to GitHub and `gh` call runs through `run_subprocess`, the session or `run_gh` in the job's process. The shell of the agent gets a scratch `HOME`, so no credential helper and no git configuration of the job's user. The job adds nothing to that shell. A process of the same user can read `/proc/<pid>/environ` of the job, so the Job pod of #2667 is the boundary, with a token for one repository. The job states this in its documentation and fixes it nowhere in code.
- **A worktree for each item.** `add_worktree` creates it on the staged branch and takes the branch over. The worktree and the local branch go when the item ends, as the stage job's do. The clone keeps its HEAD. A worktree that already holds the issue is an error for that item, and the job goes on to the next one.
- **Rebase, then push with a lease.** A rebase rewrites the branch, so a push needs `--force-with-lease=<branch>:<sha>` with the sha of `origin/<branch>` that the job read after its fetch. The App wrote every commit of the branch, so no work of a person is lost. A conflict aborts the rebase and stops the item.
- **A group is done when all its tasks are ticked.** The job reads `tasks.md` of the worktree with `parse_task_groups`. A group with an unticked task runs. A change that is partly done on the branch continues from the first group that is not done. The archive step is skipped when `openspec/changes/<change>` is gone from the worktree, and a commit step is skipped when the tree is clean, so a retry does not repeat a finished step.
- **The pull request body is the squash message.** CONTRIBUTING.md says so. The body is `Closes #N`, the text of `## Why` of the proposal on one line (`safe_text`, then `textwrap.shorten` to 1,000 characters), and the `Change:` line of the archived folder, which the job finds in the worktree after the archive. The stage job's `Plans #N` text is replaced whole. The comment on the pull request holds the outcome of each step.
- **The watch.** `monitor_pr` waits while a check runs. The job calls it with `require_reviews=False`, since a person reviews later, and `settle_timeout=0`. It accepts a status only when `head_sha` is the pushed commit; else it sleeps and reads again, for `CONST_ROADMAP_IMPLEMENT_HEAD_POLLS` reads. A head with no check yet reads as a pending check, which the monitor waits for. The sleep is a parameter of `apply_implement`, as the clock rule of docs/TESTING.md asks. A timeout, an unresolved thread, `mergeable` false and a dirty state each stop the item. A failed check goes to the fix step, once. A draft blocker and a blocked state do not stop it: a person approves later.
- **The fix step is the step.** `FixRequest(check, log)` makes a synthetic group numbered 0 with one task, "Make check `<name>` pass", and the verification commands of all groups. `build_step_inputs` adds the log under its own heading. The exit checks run in the same order: `HEAD` has not moved, `tasks.md` as it was, a change exists, the verification commands pass, the static checks pass. The job gives the step the first failed check only. The log is the tail of the run, because a failure shows at the end.
- **A stop pushes the work that passed.** The branch keeps the App's commits, and a retry or a person starts from them. The push uses the lease. If the stop is a push failure, the job does not push again.
- **A retry is a comment.** The record `implement.stopped` stays until a comment `implement: retry` by a trusted author is newer than the last comment that starts with the marker. `IssueComment` gets `author_association`. The run clears the record before the first step. The in-memory store gets `seed_comment` for the tests.
- **Spend is counted from the outcomes.** Each `StepOutcome` holds requests and tokens. The job sums them as JSON in `implement.spend`. The cost in money stays in the spend ledger, which the step already writes.
- **Status writes read the item again.** `set_field` refuses an item whose field changed since it was read. The job reads the item before each field write.
- **One item failing does not stop the run.** A write that fails is reported with the class of its error and the next item goes on, as stage does. Rejected GitHub credentials stop the run.
- **The step and the job share a command.** `--group` selects the step, as before, and its absence selects the job. `--source` is the checkout of the step, and the clone of the job.
- **A run that dies leaves its item In Progress.** The job takes only Ready items, so a pod that is killed mid-run leaves its item alone until a person sets the Status back. The job holds no lease, because the runner runs one item at a time (#2667). A model or GitHub error that the job can catch is a stop, not a death.

## Rejected alternatives

- **A host check in place of the setting.** The job could look for a read-only root or the Kubernetes service account. Each is a guess about the host, a pod of the Service has the same signs, and a test would need to fake the host. A setting set by the Job template is explicit and testable.
- **`devops pr monitor` as a subprocess.** It prints for a person and gives only an exit code. The library function gives the failed checks, the threads and the head commit, which the job needs.
- **A loop of fix steps.** AGENTS.md rule 2 stops on a second fix on a fix. One fix, with the log as evidence, then a person.
- **Push each step as it passes.** Each push would start the CI on a half-built change, and each rebase would rewrite more history. The job pushes once at the end and on a stop.
- **Clearing the stop by a label.** A comment is already the way a person talks to the job. A label adds a vocabulary and a workflow.
- **Mark ready through the REST client.** REST has no endpoint to mark a draft ready. GraphQL does, through `gh pr ready`, which `devops pr ready` uses.
- **A new fake for the pull request calls.** The calls go through the GitHub session and `gh`. Both have fakes already (`github_api`, `process_fake`), so the tests add no fake.
- **Archive in the step.** The step commits one group. The archive is the work of the whole change, so it belongs to the job.
