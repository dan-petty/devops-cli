# Design

## Decisions
- **A periodic thread calls `flush()`.** The thread starts with the meter, at the first metric of the process. It waits on an event for the interval, then calls `flush()`, which collects, queues the export and waits for it under `_flush_lock`. So a periodic export and the flush of the Service after a round run one at a time, in the order of their collection. The DELTA reader gives only what changed since the collection before, so two collections do not count a delta twice. The thread is a daemon thread. `shutdown()` sets the event and joins the thread before its last flush, so an idle thread ends at once and the exit does not wait for the interval.
- **The interval is OpenTelemetry's.** `OTEL_METRIC_EXPORT_INTERVAL` gives the milliseconds, and 60000 is the default of the SDK. A value that is not a number of milliseconds above zero, or that is infinite, gives the default and a warning. The SDK refuses a value of zero or less with an error, but a command must not stop for a telemetry setting.
- **The SIGTERM handler is set at the entry point.** `devops_cli.entry.main` runs once in the main thread of each `devops` process and calls `install_sigterm_export`. The handler exports in a thread of its own and waits for it for at most 5 s, because the main thread can hold a lock that the export needs when the signal comes. Then it calls the Python handler before it, keeps an ignored signal ignored, or sets the default action and sends SIGTERM again.
- **The handlers that a block sets stay as they are.** `sigterm_raises` of a stage Job, `capture_signals` of uvicorn in the Service and the stop signals of `devops ci` replace the handler while their block runs, and give it back after. A stage kill ends the command, and the `atexit` shutdown exports. uvicorn sends SIGTERM again after its stop, and the handler then exports.
- **The grace periods hold the bound.** The bound of 5 s is below the grace period of each pod: 30 s by default for a runner Job, 120 s for a stage Job and 660 s for the Service.
- **The instance id stays shared.** Job pods of one workload keep `service.instance.id=devops-cli-job` (#2039, #4697), so a new pod continues the series. No test shows a need for a change.

## Rejected alternatives
- **`PeriodicExportingMetricReader` of the SDK.** In opentelemetry-sdk 1.45.2, `MetricReader.collect` collects under the lock of the measurement consumer and calls `_receive_metrics`, which takes the `_export_lock` of the reader only for the export. Its tick and a flush of the Service can collect A, then B, and export B, then A. `deltatocumulative` drops a point whose time is not after the last point of its stream (`Aggregate` in opentelemetry-collector-contrib), so A is lost. The comment at `_flush_lock` in the tracer records the same rule.
- **SIGTERM raises `SystemExit`, so that `atexit` runs.** That changes how the process stops: each `finally` and `except BaseException` of the runner runs in the grace period, and the exit status is no longer that of the signal. The issue keeps the stop behavior.
- **The tracer sets the handler when it is built.** `get_tracer()` runs in any thread and in each test, and only the main thread can set a handler. The entry point runs once in the main thread of each process.
- **One `service.instance.id` for each pod.** Each pod would then start a new series, which `increase()` counts from its first sample on only with a start time. #2039 and #4697 chose one stream for each workload.
