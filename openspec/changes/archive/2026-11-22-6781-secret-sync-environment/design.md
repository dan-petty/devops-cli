# Design

## Decisions
1. **One path builder for both scopes.** `secrets_path(repo, environment)` in `src/devops_cli/github/secrets.py` gives `repos/{repo}/actions/secrets` with no environment, and `repos/{repo}/environments/{quote(environment, safe="")}/secrets` with one. `get_public_key_args`, `upload_secret_args`, `sync_secrets_requests`, `get_repository_public_key` and `sync_repository_secrets` take `environment: str | None = None` and build each path from it. Reason: the environment routes differ from the repository routes only in the prefix, so the seal, the upload body and the result stay as they are.
2. **The environment name is URL encoded.** `quote(environment, safe="")` encodes each character that is not unreserved, and so a slash becomes `%2F`. Reason: the GitHub documentation of `environment_name` asks for it. The command refuses an empty name with exit 2.
3. **One value from a file.** `--from-file <path>` (a `typer.FileBinaryRead`, so `-` reads stdin) gives the value of exactly one secret. The command refuses it with more than one secret name, and with `--source vault`, with exit 2 and before any read. The item of the secret names the source `file`. The library gets the text as `value`: `sync_repository_secrets(..., value=...)` refuses a value with more than one name. Reason: one file holds one value, and the onboarding command of #6773 reads `--release-key-file` itself and calls the library.
4. **One reader of a credential file.** `read_secret_input(source)` in `src/devops_cli/config/secret_input.py` reads up to `CONST_SECRET_FILE_MAX_BYTES` (64 KiB), decodes UTF-8, refuses an empty input, and keeps every line and the last newline. It raises `ValueError` with the messages of `MESSAGES.config` that `devops config set --from-file` already uses, and no message quotes the input. Both commands give the error as a usage error of `--from-file`. Reason: `devops config set --from-file key.pem` stores a PEM key with its lines as they are. When `gh secret sync --from-file key.pem` seals the same bytes, the value in the keyring and the value in GitHub agree.
5. **The value stays in memory.** The value goes from the keyring, Vault or the file to `encrypt_secret`, and the PUT body holds only `encrypted_value` and `key_id`. The item messages, the span attributes (`repo`, `source`, `environment`, `dry_run`, `count`), the log records and the error texts name the secret and the environment, never the value. Tests use the known value `known-test-value-6781` and assert that no output, no stdin of a `gh` call, no Python log record and no exported span or log record of the OTLP fake holds it.
6. **The dry run is a plan.** `--dry-run` and the root `--dry-run` print the planned `gh api` calls of the environment routes, with `<encrypted_secret>` and `<key_id>` in the body. They read no keyring, no Vault and no file content, and they start no process.
7. **A fake GitHub at the process edge.** The tests answer the `gh api` calls on `process_fake` with a small fake of the Actions secrets routes: it holds one key pair for each scope, answers 404 for an unknown environment, and opens each sealed PUT body with its private key, as GitHub does. Reason: ADR 0007 doubles only process edges, and the module calls `gh` through `run_gh`.

## Rejected alternatives
- **Call `gh secret set --env`.** Rejected: the dry run of devops-cli plans `gh api` calls, `run_gh` paces the writes, and the module already seals the value itself (see the proposal).
- **A second reader of the file in `src/devops_cli/commands/gh.py`.** Rejected: two copies of the limit, the decode and the empty check can drift, and `devops config set` already has them.
- **Strip the last newline of the file, as `gh secret set` does with stdin.** Rejected: `devops config set --from-file` keeps every line, and the two commands must store the same value. A PEM key reads the same with or without its last newline.
- **A new `--source file`.** Rejected: the issue names `--from-file`, and `devops config set` uses the same option name for the same input.
