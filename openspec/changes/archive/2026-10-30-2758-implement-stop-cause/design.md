# Design

## Decisions

- **One `Hooks` capability, built from a small class.** `ToolCallLog` in `implement_tool_log.py` keeps the two counters and holds the two hook methods. `Hooks(tool_execute=log._execute, tool_validate_error=log._invalid)` registers them. The agent of a step takes the capability next to `Coder`. The same object lives for the whole step, so the extra turn for the ticks adds to the same counts.
- **`wrap_tool_execute` sees every outcome.** It calls the handler. A return is `ok`. A `ToolRetryError` is a retry. An `UnexpectedModelBehavior` from the handler is the call that exceeded the limit, and it is a retry too. A `ToolFailedError` is `failed`. The hook re-raises each error, so pydantic-ai handles it as before. Any other error ends the run as before and writes no line.
- **A refusal is a `PermissionError` in the cause chain.** The shell of the harness turns a refused program, a refused operator and an interactive command into a `ModelRetry` that it raises from a `PermissionError`. pydantic-ai wraps that in a `ToolRetryError` (or `UnexpectedModelBehavior`) with `raise ... from`. The hook walks the `__cause__` chain once and says `refused` when it finds a `PermissionError`. This reads no message text.
- **The line holds the tool name and the program, never more.** The program is the first word of the `command` argument, read with `shlex.split` as the shell of the harness reads it. It is a name only when it is in `IMPLEMENT_ALLOWED_PROGRAMS`. Any other first word is written as "other", and so is a command that `shlex` cannot parse. A first word can be an assignment such as `API_KEY=hunter2`, a path or an escape sequence, and `mask_secrets` hides only the secrets that have a known form, so the code does not rely on it. A tool with no `command` argument, or a command with no word, gets no program. A line holds no other argument because an argument can hold a path or a secret. The line also holds no refusal text: the text of one refusal, "Interactive commands are not allowed. Command: ...", repeats the whole command.
- **The line has no reason for a refusal.** The issue asks for the outcome `refused` with the reason. A reason would need the text of the refusal or a parse of it, and both are ruled out above. The tool name and the program tell the cases apart: "shell, program other, refused" is a program that the shell does not allow, and a file tool has the outcome `retry`.
- **A refusal counts only for a shell command.** The file tools of the harness also raise `PermissionError` for a path outside the root, a protected path, a denied pattern and a symlink escape. The count is named "Refused commands", so a call counts as refused only when it has a shell command (a program word). Other `PermissionError` retries count as other retries.
- **A failed validation counts as a retry.** A model that sends arguments that fail validation reaches the same error as a model that is refused. `on_tool_validate_error` runs before the count of retries, so the hook writes a `retry` line there and re-raises the error. The line has no program, as the arguments are not valid.
- **The line goes to the standard error stream.** `print_muted(line, to_stderr=True)` is the console channel that `main.py` uses. The standard output of the command can be JSON (`--format json`), so the line stays off it. `safe=True` stops the console from reading a word such as `[red]` as markup.
- **The reason is built in one function.** `_stop_reason` joins the class name, the masked and cut message, and the counts. It is used where the step catches `UsageLimitExceeded` and `UnexpectedModelBehavior`. The message is masked first and cut after, as the diff is, so a cut cannot split a secret. The message is first cut to `CONST_ROADMAP_IMPLEMENT_ERROR_READ_CHARS`, a multiple of the limit, because the masking is slower than linear and the message of an error can hold a long reply of the model.
- **The table escapes the reason.** The reason holds the message of a pydantic-ai error, which can hold a bracket. `render_outcome` escapes the reason and the last message with `escape_text` before the table reads them as markup. The JSON and YAML formats need no escape.
- **The counts are in the reason, not in `StepOutcome`.** A person reads the reason in the stop comment, and the model of the comment already has one field for it. A new field would need a new place in the comment and the table.

## Rejected alternatives

- **A `logging` call at the level INFO.** The issue names the logger convention. A probe shows that a `devops` process drops INFO: the root level is WARNING and there is no handler. The Job log would hold nothing. Configuring the root logger for every command is a change of the whole CLI and out of scope. A call at the level WARNING would reach the log, but 240 lines of normal work are not warnings.
- **Count retries from the run messages.** `RetryPromptPart` carries the text of the refusal. To tell a refusal from another retry the code would match text such as "is not in the allowed list", which is the hand-rolled parsing that AGENTS.md rules out and breaks when the harness rewords it.
- **`on_tool_execute_error`.** pydantic-ai does not call it for a `ModelRetry`. Its documentation says to use `wrap_tool_execute` to intercept retries.
- **`after_tool_execute` and `before_tool_execute`.** `after_tool_execute` does not run for a call that raises, so a retry would write no line. `before_tool_execute` cannot know the outcome.
- **A subclass of `AbstractCapability`.** It gives the same hooks with more code. `Hooks` is the documented way for application code that needs a few hooks.
- **The text of the refusal in the line.** It is useful, and the harness words it well. It can also hold the whole command, with its arguments. The first word and the outcome are enough to see a model that asks for `pytest` six times.
- **Raise `CONST_ROADMAP_IMPLEMENT_TOOL_RETRIES`.** It would hide the loop and pay more requests for it. The issue asks for evidence, not for a longer loop.
