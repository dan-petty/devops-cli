# Proposal

## Why

Issue #2865. The stage job opens a draft pull request for each item it stages, and nothing marks the pull request ready. On 2026-10-31 the plan pull requests of #2147, #2735 and #2739 stayed drafts for more than an hour with all required checks passed. The plan in each one was complete when the job opened it. The owner could not tell whether work went on, and GitHub does not merge a draft.

The owner decision of 2026-10-31: a draft pull request is marked ready for review when work on the change is complete and all checks pass. The rule "the stage job never marks the pull request ready" is replaced.

## What Changes

- The status lane gets a row `stage_ready` after `implement`. It is due every 10 minutes and on a first run, and it needs no clone and no model. A round reads the open items that hold `stage.pr` and no `stage.ready` of the same number and no `implement.job`. With no such item it makes no request. Else, for each item, it reads the pull request once. A pull request that is not an open draft is only recorded in `stage.ready`, so that no later round reads it again. An open draft whose check runs have all ended and passed is marked ready with `mark_ready` of `implement_pull.py`, the function that the implement job already uses, and then recorded in `stage.ready`. A draft with a failed, cancelled, unread or running check stays a draft, and the Service does not retry the checks.
- Only the pull request that the stage job recorded for an item counts. The Service never reads the drafts of a person.
- The decision "ready to mark" is one function, `ready_to_mark` in the new module `src/devops_cli/roadmap/stage_ready.py`. It reads the checks today. #2867 replaces its body with a judgement of whether the work is complete, and changes no caller.
- `check_verdict.py` gets `read_check_runs`, which reads the check runs of a commit and not its commit statuses. See Feasibility for why.
- `PullStatus` gets the head commit of the pull request, `head_sha`.
- `StageRecordKey` gets `READY = "stage.ready"`, the number of the stage pull request that the Service has seen leave the draft state.
- `write_each` of `stage.py` loses its leading underscore, so that the new module reuses the way the stage job keeps one failed write from stopping the others.
- The texts that say the stage job never marks the pull request ready change: the header of `stage.py`, the help text of `devops roadmap stage`, `k8s/README.md`, `CONTEXT.md` and the requirement of `roadmap-stage`. The generated documents follow.
- A consumer observes the new row (the label `row` of `devops_cli_github_requests_total`, the due table) and a pull request that leaves the draft state, so the change carries spec deltas for `roadmap-stage` and `roadmap-implement-job`.
- The change fits one pull request.

## Capabilities

### Modified Capabilities

- `roadmap-stage`: the draft pull request of a staged item is marked ready by the row `stage_ready` of the Service when its checks pass, and the stage job still marks nothing.
- `roadmap-implement-job`: the status lane holds the rows `metrics`, `implement` and `stage_ready`.

## Feasibility

Checked on 2026-10-31 against the real system:

- GitHub's REST description (`api.github.com.json` of `github/rest-api-description`, fetched into a scratch directory) has no endpoint that marks a pull request ready. `PATCH /repos/{owner}/{repo}/pulls/{pull_number}` takes `title`, `body`, `state`, `base` and `maintainer_can_modify` only. The one way is the GraphQL mutation `markPullRequestReadyForReview`, which `gh pr ready` sends. So the Service needs `gh`, and `mark_ready` already runs it.
- The premise "the Service has no `gh`" is false. The `service` stage of the `Dockerfile` copies `/usr/local/bin/gh` from the builder, and the Service runs `gh` already for the store of the roadmap (`run_gh`). A pod that acts as the App gives its installation token to each `gh` child as `GH_TOKEN` (`k8s/README.md`, Roadmap service). So `mark_ready` works in the Service with no new code for the call, and the implement job and the new row use one function.
- The permission. The installation token holds `pull_requests: write` and `contents: write` (`CONST_GITHUB_APP_TOKEN_PERMISSIONS`). GitHub's documents list no permission for a GraphQL mutation. The reports of other projects agree with the grant: a refusal of this mutation to an installation token ("Resource not accessible by integration") comes from a token that lacks `pull_requests: write` (discopy/discopy#745), or `contents: write` (trmlabs/trm-gatehouse#71). Our token holds both. No Job of the cluster has reached `mark_ready` yet, so no run of this installation proves the call. The row therefore does not hide a refusal: a failed `gh pr ready` fails the round, the Service logs the masked output of `gh`, and the ledger of failed rounds suspends the row after three rounds in a row.
- The check read. `read_commit_checks` also calls `GET /repos/{owner}/{repo}/commits/{ref}/status`. GitHub's table "Permissions required for GitHub Apps" lists that endpoint under "Commit statuses: read", and the token holds no `statuses` permission. A refusal would make the read fail closed and the row would never mark a pull request. `GET .../commits/{ref}/check-runs` needs "Checks: read", which the token holds. The repository sets no commit status: the combined status of the head of a merged stage pull request has `total_count` 0. So `read_check_runs` reads the check runs only. It adds no permission to the App, which only a person may change.
- The budget. A round with no recorded draft makes no request of its own: the row reads `job_record` from `store.items()`, the one listing that the store keeps for the round and that the rows `metrics` and `implement` read already. For one draft the round sends one `GET pulls/{n}` and one `GET commits/{sha}/check-runs`, and for a pull request that it marks ready, one `gh pr ready` (a GraphQL read and a GraphQL mutation) and two requests to record `stage.ready`. A pull request that leaves the draft state is read once more and then never again. A draft with a running or failed check costs 2 requests every 10 minutes, 12 an hour, against `service.github_requests_per_hour` of 500 by default. Four drafts at the same time cost 48 an hour. The pacing of `run_gh` and of the session counts them, and the row is a row of the `devops_cli_github_requests_total` label `row`.
- The implement job takes a Staged item only when its pull request is an open draft (`_pull_reason` in `implement.py`). So a pull request that the row marked ready is not Staged for the job any more: the item becomes Planned when a person merges the plan, and the job takes it then. The row leaves an item alone when its record holds `implement.job`, so it never takes the pull request away from a Job that works on it. The order of the rows (`implement` first) gives a Staged item with a green pull request a Job in the same round.
- The premise holds. No part of the item needs code that compensates for a missing tool.

## Existing Tool Considered

`gh pr ready` and the existing `mark_ready` cover the call. `read_commit_checks`, `CheckVerdictSummary.is_passing` and `GitHubClient.get_pull_status` cover the read of the checks and of the draft state, `StageRecordKey` and `RoadmapStore.set_marks` cover the record, and the due table of `run.py` covers the row. The change builds the glue only: `stage_ready.py` is about 110 lines, `read_check_runs` about 12. It builds no GraphQL client and no check parser. It deletes no internal code; it makes `write_each` public instead of copying it.
