# Proposal

## Why

Issue #2910, part W3 of the tracker #2908. On 2026-10-30 an agent and a person fixed #2656 and #2745 by hand while the implement job held the plans and the branches of both items. The Service cannot know that someone else works on an item. An agent or a person cannot say so. `devops repos worktrees add` takes over a staged branch and marks nothing.

The owner decided on 2026-10-31: an item is claimed with one label of the family `owner/service`, `owner/agent`, `owner/human`. Any actor may claim an item. An item has one owner at a time. A person's claim beats the Service's claim. The Service never takes a claimed item.

## What Changes

- `ItemField` gets `OWNER`. Its values are `Service`, `Agent` and `Human`, and its labels are `owner/service`, `owner/agent` and `owner/human`. `Item` gets `owner`. The store reads and writes the family with the code of the other four families: a job sets it by replacing the family, the job record names the last value a job set, and a write refuses to revert a change a person made (ADR 0002). ADR 0016 names the new family.
- `.github/labels.yml` declares the three labels. The workflow `clear-status.yml` removes the `owner/*` labels of an issue when it closes, with its `status/*` labels, so a claim of a merged pull request does not stay. A test checks that the file declares the label of every value of every field.
- New module `src/devops_cli/roadmap/claim.py` holds the rule of a claim and the claims of the Service. `devops roadmap claim <issue> --as agent|human` and `devops roadmap release <issue>` call it. Both write only with `--confirm`, as `devops roadmap return` does.
- A claim of a free item succeeds. A claim by the owner that holds the item changes nothing. A person's claim takes an item that the Service holds. Every other claim of a held item is refused with `RoadmapClaimError` that names the owner.
- `devops repos worktrees add` claims the issue as `owner/agent` after it makes the worktree. A claim that fails (a held item, an issue that is no item, a failed write) is a warning in the report, and the worktree stays.
- The stage job and the implement job leave out an item that an agent or a person holds, with the reason "It is claimed by agent." or "It is claimed by human.".
- The Service sets `owner/service` in the same write that records the Job of an implement item, and takes it off when the round reports that the Job ended or the Job could not be created. A round never takes an item that a person or an agent claimed after the plan, and never takes off a claim of another owner.
- The implement job reads the item before each task group and before the push. When an agent or a person holds it, the job ends the item at once: it pushes nothing, opens no pull request, comments why, and leaves Status and the owner as they are. The round that reports the Job does not stop such an item.
- Observable behavior changes (two commands, the report of `worktrees add`, the output of two jobs, three labels), so the change carries spec deltas.
- The change fits one pull request.

## Capabilities

### New Capabilities

- `roadmap-item-claim`: the claim and release of an Item, the claims of the Service, and the end of a Job whose item a person claims.

### Modified Capabilities

- `roadmap-item-labels`: the owner label family, and the close of an issue clears the owner labels.
- `roadmap-stage`: the job leaves out a claimed item.
- `roadmap-implement-job`: the job leaves out a claimed item.
- `repos-worktrees-add`: the command claims the issue for an agent.

## Feasibility

Checked on 2026-10-31 against the real system:

- The evidence holds. The comments of #2656 and #2745 show a person's `implement: retry` comments between runner Jobs on 2026-10-30, and the repeated "Stopped at group" comments of the job on the same items. Nothing on those items says who else worked on them.
- `devops repos worktrees add` marks nothing. `add_worktree` in `src/devops_cli/git/worktree_add.py` runs git commands only, and its takeover of a staged branch (`_take_over`, #2657) writes no label and no comment. The stage job and the implement job call the same function, so the claim goes in the command and not in the function.
- The store can hold the family with no new mechanism. `set_field`, `relabeled`, `field_values` and `require_unchanged` in `src/devops_cli/roadmap/store.py` work on any `ItemField`, and the in-memory adapter and the GitHub adapter implement them once. The rule "a person's label wins" is in `field_values` already: a family with two labels has the value the job record does not name.
- The Service creates a runner Job in one place, `_create` of `implement_submit.py`, and learns that a Job ended in one place, `_report`. A claim can be set in the write that records the Job and cleared in the write that records its state, so no extra request is needed for a normal Job.
- The runner can see a claim at a group boundary. `_ItemRun._groups` in `implement_run.py` is the loop over the task groups, and `_fresh` reads the item again. The Job runs as the same GitHub App, so the read needs no new permission.
- Labels sync. `sync_repository_labels` in `src/devops_cli/github/labels.py` creates and updates the labels of the file and deletes none, so three new labels in the file are safe. A person runs the sync. GitHub also creates an unknown label when an issue write names it, so a write that runs before the sync does not fail.
- Intake label derivation. `title_labels.py` gives `type/*` and `scope/*` labels from the Conventional Commit title only. Intake sets the fields in `_fields` of `intake.py`, a fixed list of Status, Value and Effort plus Priority, and sets no owner. So intake needs no change, and no title can give an `owner/*` label. The test `FIELD_PREFIXES` in `tests/roadmap/test_roadmap_intake.py` reads `ItemField`, so it already leaves the new family out of the labels it compares.
- GitHub assignees do not fit. The REST page "Assignees" (docs.github.com/en/rest/issues/assignees) describes assignees as "people" and says "Only users with push access can add assignees". An assignee names a login, and the three owners are three kinds of actor, not three logins. The page does not list a GitHub App as an assignee.
- The premise holds. No part of the item needs code that compensates for a missing tool.

## Existing Tool Considered

GitHub labels cover the claim, as ADR 0016 already uses them for the other four fields. The change reuses `set_field`, `relabeled`, `field_values` and `require_unchanged` of the store, `StoreRequests` of `request_plan.py` for the dry run, `render_dry_run`, and the `--confirm` pattern of `devops roadmap return`. GitHub assignees were considered and rejected (see Feasibility and the design). The change builds only the rule of a claim (`claim.py`, about 190 lines) and the check at the group boundary. It deletes no internal code.
