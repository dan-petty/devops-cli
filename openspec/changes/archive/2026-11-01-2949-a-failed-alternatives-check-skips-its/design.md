# Design

## Decisions

- **The failure record is two keys in the item's job record.** `alternatives.failed_at` holds the time as an ISO string, and `alternatives.failed_error` holds the class of the error. The item is the record, so no field holds the number. The job record holds flat strings (`AlternativesRecordKey` in `src/devops_cli/roadmap/store.py`), and `RoadmapStore.set_marks` sets or clears several keys in one write. A written check clears both keys in its own `set_marks` call, so a later success leaves no stale failure.
- **The class of the error comes from the failure that exists.** `CheckFailure` gets two fields, `error_class` and `failed_at`. A failed model call gives `AIClientError`. A stopped run gives `InvestigationStopped.reason`, for example `UnexpectedModelBehavior` or `UsageLimitExceeded`. A refused reply gives one fixed name from a constant in `src/devops_cli/config/constants.py`, because a refusal has no exception class.
- **Every `CheckFailure` is recorded and delayed**, including a refused reply and a body with a marker that has no partner. An item that fails the same way in each round would otherwise hold the first place of the round and starve the other items of the limit of 5.
- **The delay is read in `select_items`.** An eligible item whose `alternatives.failed_at` is less than `retry_days` old is not selected. `--item` bypasses the delay, as it already bypasses the recheck window, so a person can check one item by hand. A value that is not a time is logged and ignored, as `_checked_at` does for `alternatives.checked_at`.
- **The default of `roadmap.alternatives.retry_days` is 3.** The issue names no number. The row runs every 719 minutes, so 1 day retries after two rounds, which is too soon after a provider outage such as the one of 2026-10-30. Three days lets an outage end and holds the cost to one slot of 5 for the item. The value is a setting, so a person can change it with no code change.
- **The row fails when the plan holds failures and no check.** `raise_for_failed_checks` returns when `plan.checks` is not empty or `plan.failures` is empty. A round that selects no item, because every item is current or in its delay, has no failure and succeeds. The command `devops roadmap alternatives` calls the same function, so its exit code follows the same rule. The failures of a round that fails are still recorded: the row and the command apply the plan before they raise.
- **The reason of a stopped run adds `InvestigationStopped.message`.** This is the "readable text" of #2922 and the retry reasons of #2875. The text is already masked and cut (`run_error_message` in `src/devops_cli/roadmap/agent_run.py`). The change adds no new helper.
- **The ledger of failed rounds does not change.** The Service counts a round that raises. With the new rule a round raises only when no item was checked, so `DEFAULT_SERVICE_MAX_FAILED_ROUNDS` (3) keeps its meaning.

## Rejected alternatives

- **A new dataclass `AlternativeFailure` with its own read and write helpers.** `CheckFailure` at `src/devops_cli/roadmap/alternatives.py` line 388 already holds the item and the reason, and `plan_alternatives` already collects it. A second type would give two failure paths.
- **A `try` block around each item check.** `_check_one` (line 677) already turns `AIClientError`, a stopped run and a refused reply into a `CheckFailure`. `AICredentialsError` must stay raised, because rejected credentials stop the run (base spec, "Rejected credentials").
- **A file or table of failed items next to the ledger.** The job record is where the job already keeps one item's state, and `set_marks` already takes its lock (`src/devops_cli/roadmap/store.py`). A second store would need its own cleanup.
- **Retry after 1 day.** The row runs twice a day, so the item would return after two rounds. A provider outage can last longer, and the item would fail again and take a slot.
- **Retry after 7 days.** The owner asked on 2026-10-31 to confirm that all issues are vetted (issue #2949). A week of delay for each failure works against that request.
- **Fail the row when a round checks zero items.** A round with no selected item also checks zero items, so the row would fail and be suspended after 3 rounds. The issue says the row fails when "no item could be checked", which means items were tried.
- **Keep the old rule (any failure fails the round).** It is the behavior that suspended the row on 2026-10-30.
