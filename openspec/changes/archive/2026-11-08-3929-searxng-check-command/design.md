# Design

## Decisions

- **A `devops k8s` command, not a live pytest test.**: The test floor fakes the network and `docs/TESTING.md` forbids a skip on the state of the host, so a live test cannot reach the service. The owner chose a command on 2026-11-07. The tests of the command use the process and HTTP fakes, and a person runs the command at each digest bump.
- **Two modules in `src/devops_cli/k8s/`, one of them the existing shared one.**: `service_probe.py` (#4108) holds the forward and the throwaway pod and stays as it is. `searxng_check.py` holds the rows, `reply_problems`, the engines that stay off and `SEARXNG_IMAGE`. The command module in `commands/k8s/` is a thin adapter: options, tables and exit code.
- **Six search rows with fixed names.**: `json-general`, `json-it`, `json-science`, `bang-off-engine`, `bang-external` and `unused-category`. The names are the keys of the report and of the tests. Six requests stay far under the limit of about 30 queries after which the upstream sites suspend an engine (`k8s/README.md`).
- **The categories come from `DEFAULT_SEARXNG_CATEGORIES`.**: The provider sends this value, so the check holds the provider to the pinned image. If a kept engine stops answering in a category, the row of that category has no hit and fails, and the fix is to change the default. The check reads the default and does not copy it.
- **`reply_problems(status, body, *, expect_hits=True, also_off=())` returns a list of texts.**: An empty list is a pass. `expect_hits` is false for the rows that need no hit, and `also_off` adds the engine that a bang names. The same function judges the three `json-` rows and the off-engine bang, so a missing key, a bad `unresponsive_engines`, a 403 (named as `search.formats`), a missing hit and an engine that stays off each have one place. A text names the key, the category or the engine, and the report prints it.
- **The engines that stay off are a prefix list.**: `brave`, `braveapi`, `google`, `bing`, `startpage`, `mojeek` and `qwant`, matched by prefix, because `brave` also covers `brave.news`. The list lives once in `searxng_check.py`, and `tests/invariants/test_k8s_searxng.py` imports it. The check reads both `results[].engine` and `unresponsive_engines[][0]`: an engine that is on and suspended shows only in the second.
- **The external bang is recorded and never followed.**: `http_client` follows redirects by default, so the command passes `follow_redirects=False`. SearXNG answers `!!g` with a redirect to the page of the external site, and the command must not send a request there: the request would leave the cluster under the name of a person. The row records the status and whether a `Location` header exists, and fails only on a fault. The provider already refuses such a query before it sends it.
- **The unused category is recorded and not asserted as an error.**: The source (`parse_category_form`) falls back to `general` for a category that is not loaded, so 200 with hits is the expected answer. The row fails on a status of 500 or more or on no answer.
- **Two pods for three connects.**: One pod with a neutral label tries port 8080 of the Service. One pod with the label `app.kubernetes.io/name=searxng` tries the metadata address and the ClusterIP of `roadmap-service`. The first proves that the ingress rule selects the client label and no other. The second proves the egress rule. The pods never become ready (`probe_from_pod`), so the Service sends them no traffic. The neutral label is not the label of `roadmap-service`, the only allowed client, and not the label of `searxng`.
- **The report names pods and targets by role.**: `<unlabeled-pod>`, `<searxng-pod>`, `<searxng-service>`, `<metadata>` and `<private-cluster-ip>`. The ClusterIPs are read at run time and never printed (rule 10 of AGENTS.md, rule 8 of `SECURITY.md`).
- **The image check extends the existing check of the `k8s` row.**: `tests/gate/k8s_checks/devops_runtime.py` today asserts only that the image of Deployment `searxng` starts with `docker.io/searxng/searxng:`. It now compares the full image with `SEARXNG_IMAGE`, as it does for Crawl4AI.
- **The reply fixture comes from the Publish stage.**: A saved reply needs the cluster. The Publish stage runs the command once, saves one reply of the pinned image with the masking of private data, and writes the image into a file next to it. The test of the fixture is part of the same group, so no stage between leaves a red suite.
- **The command is not an MCP tool.**: It starts pods, so it is not read-only. `--dry-run` has the class `request-plan`.
- **A changed behavior is not fixed here.**: If a row fails on the pinned image, the person files the evidence as an issue. The change adds no compensating code (AGENTS.md rule 2).

## Rejected alternatives

- **A live pytest test with a marker.**: `docs/TESTING.md` forbids a skip on the state of the host, and the owner rejected it on 2026-11-07.
- **Follow the redirect of `!!g`.**: The command would send a request to an external site, and a followed redirect hides whether the service redirects.
- **Assert an error for the unused category.**: The source falls back to `general`, so the assertion would fail on the correct image.
- **A third pod with the label of `roadmap-service` as a positive control.**: It would run under the label of the one allowed client and add a pod and a policy path that nobody asked for. The forward already proves that the service answers, and an exec that fails for another reason raises `ServiceProbeError` and does not read as `blocked`.
- **Read the kept engines from the ConfigMap file.**: The command would depend on the path of the repository. The reply shows the engines that run, and the list of those that stay off is short and fixed.
- **A second copy of the forward and pod code.**: `service_probe.py` was written for this reuse.
- **A new scanner.**: No open, maintained tool checks a running SearXNG for these points.
