# Design

## Decisions

- **The CronWorkflow names its cron expression in `schedules`.** `spec.schedules` is a list with the one value `"0 6 * * *"`. No time zone and no other field changes.
- **The WorkflowTemplate names its mutex in `mutexes`.** `spec.synchronization.mutexes` is a list with the one mutex `infra-drift`. The template sets no `mutex` and no `semaphore`. With `concurrencyPolicy: Forbid` of the CronWorkflow, the template keeps one holder, as WK2 of `docs/SERVICE_PATTERNS.md` asks.
- **The executor has its own account.** `spec.executor.serviceAccountName: argo-executor` gives the executor of the pod the account that the environment repository makes, with a Role for `create` and `patch` on `workflowtaskresults`. The pod keeps `serviceAccountName: devops-cli`, which has `automountServiceAccountToken: false` and no RoleBinding (`check_the_jobs_run_as_an_account_with_no_token_and_no_role` in `tests/gate/k8s_checks/runner.py`). So the drift container gets no token.
- **One policy lets each Workflow pod reach the API server.** `argo-workflow-egress` is a third document of `k8s/devops/networkpolicy.yaml`, as the design of #5289 names that file. So `devops k8s deploy-stack` applies it through the path `networkpolicy.yaml` of `PRODUCT_MANIFESTS_BY_STACK` (`src/devops_cli/commands/k8s/stack_lifecycle.py`), and Argo CD applies it through the root kustomization, with no new path. Its pod selector is a `matchExpressions` entry with the key `workflows.argoproj.io/workflow` and the operator `Exists`, the label that the controller sets on each Workflow pod. It has the type `Egress` only (`dual_type_problems`, `k8s/README.md`, NetworkPolicy). Its one rule is TCP 6443 to the ipBlock `0.0.0.0/0` with `169.254.169.254/32` excluded, the peer of `roadmap-service-egress`: the `kubernetes` Service resolves to the address of the node, which no namespace selector matches.
- **The gate check pins both API server policies.** `check_only_the_service_pod_and_the_workflow_pods_may_reach_the_api_server` in `tests/gate/k8s_checks/runner.py` pins the selector, the types and the rules of `roadmap-service-egress` and of `argo-workflow-egress`. It fails when another policy has an egress rule on TCP 6443, or when the perimeter gets one. `check_the_pods_of_jobs_carry_no_label_that_an_api_server_policy_selects` fails when the pod template of CronJob `devops-cli`, `devops-cli-runner` or `roadmap-stage` carries the label of the Service or the Workflow label.

## Rejected alternatives

- **Add TCP 6443 to `devops-default-perimeter-egress`.** The perimeter selects each pod of `devops` but five (`k8s/devops/networkpolicy.yaml`), so each Job pod would reach the API server. `check_only_the_service_pod_may_reach_the_api_server` on the base asserts that `_egress_to_port(perimeter, 6443)` is `[]`.
- **Select the Workflow pods by `app.kubernetes.io/name: devops-cli-job`.** The `podMetadata` of `k8s/devops/workflowtemplate-infra-drift.yaml` sets that label, but each Job pod of the Service has it too (the admission policy pins it, `docs/CLUSTER.md`, Admission policy). So the Job pods would reach the API server.
- **A policy for each WorkflowTemplate.** The label `workflows.argoproj.io/workflow` is on each Workflow pod, so one policy covers `infra-drift`, `rag-ingest` (#5289) and each later template. A policy for each template repeats the same rule.
- **A new file `networkpolicy-workflow.yaml`.** A new file needs a new line in `k8s/devops/kustomization.yaml` and in `PRODUCT_MANIFESTS_BY_STACK`, or `check_every_network_policy_of_the_product_base_has_both_apply_paths` fails. The design of #5289 names `k8s/devops/networkpolicy.yaml`, and that file has both paths already.
- **Mount a token on the pod account `devops-cli`.** The drift container would get the rights of the account. `check_the_jobs_run_as_an_account_with_no_token_and_no_role` asserts `automountServiceAccountToken: false` on `devops-cli`.
