# Design

## Decisions

- **Every OpenAI-compatible chat call streams.** The gateway, `openai` and `copilot` providers share `_openai_compat_messages`. The streamed path (`chat_messages_stream`) already sends `stream: true` with `stream_options.include_usage` to all three, so one read path serves them, and the blocking read is deleted. The Ollama provider is not changed: its native API has no keepalive, and no task of the default configuration uses it through the tunnel.
- **The SDK joins the chunks.** `ChatCompletionStreamState` gives a `ChatCompletion` with the content, the `reasoning_content` that Ollama models send, the model, the finish reason and the usage. The client reads that completion with the code that read the blocking reply. The state gets no `response_format`, so it does not parse or refuse the content; `chat_structured` validates the reply as before.
- **One frame watcher.** The streamed path watches the SSE frames of the SDK stream for `[DONE]`. The blocking path uses the same watcher, which also counts the decoded data of each frame against `DEFAULT_AI_MAX_RESPONSE_BYTES`. A stream that ends with no `[DONE]` and no finish reason fails with the error of the streamed path, "Provider stream ended before its final frame."
- **A late failure has the error of its status.** After the first ping, LiteLLM cannot change the status line, so a failure comes as a frame `{"error": {..., "code": "<status>"}}`. The SDK raises `openai.APIError` with that `code`. The client maps it as it maps an `APIStatusError` with the same status and the same body: 401 and 403 give the credentials error, and other statuses give "Provider request failed with HTTP <status>: <detail>".
- **A late failure is a failed attempt in the ledger.** `AttemptRecordingTransport` records a failed attempt when the status is 400 or more, or the read times out, inside the transport. A failure in the stream comes after the transport has returned a 200. The transport's recording becomes the module function `record_failed_attempt`, and the chat path calls it for a failure in the stream, so the ledger keeps one `error` row for each failed attempt.
- **The interval is 30 s.** It must be well under the 125 s edge timeout. A call whose first token comes in less than one interval is not wrapped, so it keeps the `x-litellm-*` headers that give the serving backend and the deployment model (#2031). With a streamed call, the first token is the first reasoning token, which comes after the prefill and any queue time, not after the reasoning. Thus only calls with a long prefill or a long queue lose the headers; their ledger rows record no serving backend.
- **The read timeout limits each wait for the next data.** For a streamed reply, httpx applies the read timeout to each read. While the gateway sends pings, the client does not stop a call. The deployment timeouts of the gateway (`router_settings.timeout` 1,500 s, `devops-background` 1,100 s) limit the time that the gateway waits for the next token of the backend, and then the gateway sends an error frame. The completion limit (`max_tokens`) limits the length of the reply.
- **No retry of a late failure.** The retry transport sees only the status line. A failure after it is not retried. The router of the gateway retried the call and used its fallbacks before it wrote the error frame.

## Rejected alternatives

- **WebSocket (Realtime API, or the WebSocket mode of the Responses API).** The backends are Ollama (`ollama_chat`), which has no realtime API, and the client uses Chat Completions. The SSE keepalive gives the same result with one gateway setting.
- **Turn off proxy buffering in the ingress.** The ingress is Traefik, not nginx, and the gateway route has no buffering middleware. The probe of 2026-10-27 shows no buffering: the largest gap was 1.7 s.
- **Increase the Proxy Read Timeout.** Only an Enterprise zone can do this.
- **A DNS-only host or a LAN path to the gateway.** This shows the origin and goes around the tunnel and Access. The cluster accepts external traffic only through the tunnel (`k8s/ingress/traefik-values.yaml`).
- **Status polling with an asynchronous job API.** Neither LiteLLM nor Ollama has one for chat.
- **Stop the retry of a 524.** This treats the symptom. After this change, a slow model cannot cause a 524 on a gateway chat call.
- **Stream only for the gateway provider.** This keeps two read paths for one SDK call. The `openai` and `copilot` providers already stream for `chat_messages_stream`.
- **A total deadline in the client.** The SDK yields no event for a ping comment, so the client cannot check a deadline while the gateway sends pings, unless it reads the raw bytes under the SDK. The LiteLLM stream timeout is a timeout for each read from the backend, so the request body cannot carry a total deadline either. The gateway's timeouts and the completion limit bound the call.
- **Turn off the keepalive for some deployments (`keepalive_seconds: 0`).** The gateway config has only Ollama deployments. A hosted deployment that replies fast keeps its headers at the 30 s interval.
