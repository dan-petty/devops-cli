# Design

## Decisions

- **Mount the aclfile from key `users.acl` of Secret `valkey-devops-auth` and start `valkey-server --aclfile /run/valkey/users.acl`.**: The owner's comment of 2026-11-21 asks for the form of the infra base `acl` component, which mounts an aclfile from a Secret, and the mount keeps every password off the command line and out of git. The manifest update lives in `dan-petty/homelab` because `tests/gate/k8s_checks/environment_freeze.py` keeps environment files in this repository frozen.
- **Keep the `default` user on with the password of key `password` and the patterns `~* &* +@all`.**: The owner's comment of 2026-11-21 keeps it on until a release ships `valkey.username`, because a pod that sends no user would otherwise fail AUTH; #6600 turns it off.
- **Define the four role users with one password each, give `sweep`, `brain` and `agent` the command set `+@all -@dangerous`, and give `metrics` the explicit commands of the scrape only.**: A pod that holds one role password reaches only that role's keys, a cache client never needs FLUSHALL or CONFIG, and a scrape needs no write command and no key pattern.
- **Give `metrics` the commands `INFO`, `CONFIG GET`, `DBSIZE`, `CLIENT LIST`, `SLOWLOG GET`, `MEMORY USAGE` and `PING` rather than a command category.**: The exporter reads `redis_config_maxmemory` and `redis_memory_used_bytes` from the live scrape of #4668, and the categories that hold `CONFIG` also hold FLUSHALL and SHUTDOWN.
- **Add `valkey.username` as a setting with the variable `DEVOPS_CLI_VALKEY_USER` and an empty default.**: It pairs with `valkey.password`, a client that sends it is released after this change, and an empty value keeps the default user, so a workstation Valkey that still uses `requirepass` needs no change.
- **Build `users.acl` as a derived entry of the same push, from the four role passwords and `password`.**: The push resolves derived entries after the generated ones, so the aclfile and the four keys hold the same values on every run, and the aclfile compares equal to its live value and changes nothing.
- **Write the `k8s/README.md` rows of the five new entries of `llm/valkey-devops-auth` in the group that adds them, and not in the documentation group.**: `tests/invariants/test_k8s_manifests.py` builds one row for each entry of `CLUSTER_SECRETS` and fails on a missing row, so a later group would leave that test red between the two steps.
- **Extend every fixed expected list of `tests/k8s/test_cluster_secret_push.py` that holds the cache Secret in group 3: the applied-key map of `test_apply_is_one_server_side_apply_of_a_list_on_stdin` takes the five new keys, and the keyring-write list of `test_a_generated_value_is_stored_in_the_keyring_before_the_apply` takes the four role keys.**: `tests/k8s/test_cluster_secret_push.py:370:sorted(backend.writes),` compares the exact list of keyring writes of the `--stack llm` push, and the derived `users.acl` entry adds none, so the four generated role keys are the whole addition to that list.
- **Extend the expected rows of `test_table_holds_each_secret_entry_with_its_source_and_restarts` in `tests/k8s/test_cluster_secret_plan.py` in group 3, in the step that adds the entries of the table.**: `tests/k8s/test_cluster_secret_plan.py:183:assert rows == [` compares every entry of `load_cluster_secrets_table()` with a fixed list, so the four role entries and the derived aclfile entry must join that list in the same step that adds them.
- **`src/devops_cli/roadmap/stores/listing_shared.py:754:class TieredSnapshotStore:` gains a `user` field whose default `_configured_valkey_user` reads `valkey.username`, and a private repository counts as shared only when that field gives `sweep`.**: The criterion of the issue asks for a test that the tiered cache writes the snapshot of a private repository only under the `sweep` user, and the ACL user of the process is the only fact that tells the `sweep` role from the others.
- **Let the `user` field keep its default in `tests/roadmap/test_roadmap_run_lanes.py` and `tests/server/test_server_service.py`, and leave `docs/roadmap/intake.md` as it is, because `src/devops_cli/roadmap/stores/listing_snapshot.py:275:def _tiered(local: SnapshotStore) -> SnapshotStore:` builds the store with `local` only.**: A defaulted field changes no caller that passes `local` alone, so only the test module that covers the private rule takes the new keyword.
- **Prove the manifest in `dan-petty/homelab` and the users with live checks of the pod.**: `docs/TESTING.md` forbids a test that asserts a value of a manifest or a config file, and `tests/gate/k8s_checks/environment_freeze.py` keeps environment manifests in this repository frozen, so the deployed state is proved by live checks and the table by `tests/k8s/test_cluster_secret_plan.py`.
- **Admit the snapshot of a private repository to the shared tier under `sweep` here, and leave the fact cache and the other roles to #6589.**: The acceptance criteria of the issue name the tiered snapshot, and the fact cache holds no private data, so the snapshot rule is the whole of the criterion.

## Rejected alternatives

- **Turn the `default` user off in this change, as the design of the body first proposed.**: The owner's comment of 2026-11-21 keeps it on until #6600, and `src/devops_cli/valkey/cache.py:245:return (pw,) if pw else None` shows the client sends no user today, so every pod would fail AUTH.
- **Render the aclfile in the shell at pod start and keep it on the memory volume.**: The owner's comment of 2026-11-21 asks for the aclfile form of the infra base `acl` component, which mounts it from a Secret, and `k8s/llm/valkey-devops.yaml:92:key: password` shows the pod already reads that Secret, so the mount needs no new Secret.
- **Define the users with `ACL SETUSER` from a client after start.**: `k8s/llm/valkey-devops.yaml:92:key: password` shows the pod already reads Secret `valkey-devops-auth`, so the mount needs no second client and no password in the process list, and a restart would lose every user that `ACL SETUSER` made.
- **Keep the `requirepass` default user as the only user.**: `k8s/llm/valkey-devops.yaml:6:It holds no data of a private repository until it has role ACL users (#4704).` names the defect: one password opens every key.
- **A person types each of the four role passwords.**: `src/devops_cli/k8s/cluster_secrets.py:496:generator=_DEVOPS_CACHE_VALKEY_GENERATOR,` shows the row generates its value today, and four typed values would put each in a shell history and add four person steps.
- **Every pod sends the `sweep` user.**: `src/devops_cli/config/constants.py:2874:CONST_VALKEY_BRAIN_PREFIX: Final[str] = "valkey:brain:v1"` shows the brain keys are a separate prefix, so the runner and the RAG pods would hold write access to the roadmap keys and no access to the brain keys.
- **Set `valkey.username: sweep` in `k8s/devops/configmap.example.yaml` in this change.**: `k8s/devops/roadmap-service/deployment.yaml:113:- name: DEVOPS_CLI_VALKEY_PASSWORD` shows the pod sends the default user's password and no user variable, so the pods would fail AUTH between the merge and the release; #6600 sets the user and the role password together.
- **Give the four role users one password.**: `src/devops_cli/k8s/cluster_secrets.py:495:_DEVOPS_CACHE_VALKEY_AUTH,` is the single password entry of the row today, and one leaked value would open every role with no way to revoke one.
- **Give the redis-exporter the `sweep` user.**: `k8s/llm/valkey-devops.yaml:137:key: password` shows the exporter reads the same key, and `sweep` holds write access on `valkey:roadmap:*`, which a scrape never needs.
- **One Secret for each role password.**: `src/devops_cli/k8s/cluster_secrets.py:499:restarts=(Workload("deployment", "valkey-devops"),),` shows one row holds this cache's keys and its restart of `deployment/valkey-devops`, and three more rows would repeat that restart and its labels.
- **Put the snapshot of a private repository under a second key prefix that the `default` user cannot reach.**: `src/devops_cli/roadmap/stores/listing_shared.py:183:def snapshot_key(repo: str) -> str:` gives every snapshot one key, and a second prefix would split the `sweep` pattern `~valkey:roadmap:*` from the read pattern of `brain`.
- **Write the `k8s/README.md` rows of the new keys in the documentation group, after the group that adds them to the table.**: `tests/invariants/test_k8s_manifests.py:130:assert [row for row in rows if row not in readme] == []` fails on a table entry whose README row is missing, so the tree stays red between the two groups.
- **Add the new entries of `llm/valkey-devops-auth` and leave the expected rows of `test_table_holds_each_secret_entry_with_its_source_and_restarts` to a later step.**: `tests/k8s/test_cluster_secret_plan.py:183:assert rows == [` compares the whole list of entries, so the group's own verify `uv run devops ci test tests/k8s/test_cluster_secret_plan.py` fails until the expected rows take the new entries.
- **Add the four role keys to the table and leave the expected keyring-write list of `test_a_generated_value_is_stored_in_the_keyring_before_the_apply` to a later step.**: `tests/k8s/test_cluster_secret_push.py:370:sorted(backend.writes),` compares the exact list of keyring writes of the `--stack llm` push, so the group's own verify `uv run devops ci test tests/k8s/test_cluster_secret_push.py` fails until that list takes the four role keys.
- **A test that renders the aclfile from `k8s/llm/valkey-devops.yaml` and asserts its lines.**: `docs/TESTING.md` forbids a test that asserts a value of a manifest or a config file, so the aclfile is proved by the live checks of the pod and by `tests/k8s/test_cluster_secret_plan.py`.

## Unchanged references

- `src/devops_cli/roadmap/stores/listing_snapshot.py` (constructor call): It builds the store with `local` only, so the new defaulted field needs no edit.
- `tests/roadmap/test_roadmap_run_lanes.py` (constructor call): It builds the store with `local` and keyword fields only, so the new defaulted field needs no edit.
- `tests/server/test_server_service.py` (constructor call): It builds the store with `local` only, so the new defaulted field needs no edit.
- `docs/roadmap/intake.md` (prose): It describes the store, whose constructor and key keep their shape.
- `openspec/specs/project-brain/shared-cache/spec.md` (living spec): The archive writes it from the spec delta of this change, and no group edits it.

## Security

Five passwords cross a trust boundary: they move from Secret `llm/valkey-devops-auth` into a read-only file in the pod, and each role user reaches only the key patterns of its role. A private repository's snapshot reaches the shared tier only when the process sends the `sweep` user, and the store removes it under any other user or none. A person must confirm that `uv run devops k8s push-secrets --only llm/valkey-devops-auth --plan` shows every key `unchanged` before the merge, and that the `default` user stays on until #6600. The case `test_a_private_repository_is_shared_only_under_the_sweep_user`, the live `NOPERM` probe of `agent` on `valkey:roadmap:*`, the `redis_up` scrape of the exporter and `uv run devops ci --check --only k8s` fail if a rule breaks.
