# Design

## Decisions

- **One source for the prices: the Service ConfigMap template.** The spend reports of the Service price a local token with `price_reference` of the pricing registry, from `ai.reference_model`, `ai.reference_embedding_model` and `ai.price_overrides` of the ConfigMap. The dashboard keeps its PromQL constant, because Grafana cannot read a ConfigMap. A test validates the `ai` settings of `k8s/devops/configmap.example.yaml`, builds the registry with them and compares each price with the constant. A change of a model or a price in one file fails the test until the other changes. A second test pins the owner prices of #4241.
- **Local tokens from the gateway counters by provider.** LiteLLM names the provider of each deployment: `ollama_chat` for the chat deployments and `ollama` for the embedding deployments of the gateway config. The provider gives the operation with two `label_replace` calls, so the price join on `operation` and `type` stays as it is. A test reads `k8s/llm/gateway/config.yaml` and fails when an in-cluster deployment names another provider, or an `ollama` deployment is not an embedding model.
- **Backend names from the deployment counter.** The token counters have `model_id` and no `api_base`. `litellm_deployment_total_requests_total` has both. The query takes the service name from `api_base` with `label_replace` before the join, so two `api_base` values of one host give one series, and selects `model_id!=""`. A deployment with no `api_base` takes `litellm_model_name` through `or on (model_id)`, which adds it only when the deployment has no series with an `api_base`. The right side is `increase(...[$__interval])` of the same window as the tokens, so a deployment with tokens in the window has a series there, and a gateway restart drops no bar.
- **The model names the embedding bar.** LiteLLM gives `ollama-24gib-embed-gpu0` and `-gpu1` no `api_base` on any series, and both have the model `qwen3-embedding:0.6b`, so one bar holds both. Their savings were $3.37 of $7.62 in 7 d. A label that names each embedding service needs a change of the gateway config or of LiteLLM.
- **Hourly bars as for spend.** Local savings: USD per hour and the bars by backend follow Spend: USD per hour and Spend by provider and model: USD per hour (#4724): `increase(...[$__interval])`, Min interval 1h, the bars by backend stacked. The rolling lines go.
- **A 7-day projection baseline.** The savings target is `rate(...[7d]) * 86400 * N`, as the spend target is, so both values of a projection have one baseline and the range picker changes neither.
- **Test checks read the query and not its strings.** The chart rule that finds a fixed window, and the gateway check that finds a raw read of a `litellm_` series, ignore the strings of a query, such as the regex `([^.:/]+)` and the label `litellm_model_name`. The gateway check accepts a grouping on a label that the query sets with `label_replace`. The promtool harness fills a constant variable of the dashboard, as Grafana does, and leaves `$1`, which Grafana also leaves.

## Rejected alternatives

- **Keep devops-cli's `local="true"` tokens.** For the 6 h to 01:35Z they hold 62.7 million hosted DeepSeek tokens (#5914). Only a 30-day wait would clear them, and a client label can be wrong again.
- **Generate the constant from the ConfigMap at deploy time.** The live ConfigMap is not under Argo CD and the dashboard is a static file that the sidecar loads. A generator adds a build step for four numbers, and the test gives the same guarantee.
- **Price by `model` of the token counters.** A model name of a local group can change with the gateway config. The provider is the field that the pricing registry already treats as local (`ollama`, `ollama_chat`).
- **Join with `group by (model_id, api_base)` as the issue proposes.** Live it fails: deployment `0c308e16...` has a series with and one without `api_base`, Gemini has two `api_base` values for one `model_id`, and some series have no `model_id`. Each gives "found duplicate series for the match group".
- **Name the embedding bars by a short `model_id`.** It gives two bars, but a hash names no service.
- **Hard-code a `model_id` to service map.** LiteLLM computes `model_id` from the parameters of the deployment, so a change of `num_ctx` or `order` breaks the map with no error.
