# Design

## Decisions

- **Name the dimension `row`, not `job`.**: The collector sets the Prometheus label `job` from `service.name` after it copies the data point attributes, so an attribute `job` is lost with no log (Feasibility 3). `devops_cli_github_requests_total` already uses `row` for the job row that did the work. The value is `stage`. A check in `tests/telemetry/test_telemetry_instruments.py` fails on an `emit()` that sends the attribute `job` or `instance`, so the clash cannot come back.
- **Read the outcome and the size of each call from the messages of the run.**: `RunTrace.absorb` already reads the messages after the run, in the `finally` of `investigate`, also when the run stops. A `ToolReturnPart` holds the answer after the cut of its tool and the `metadata` that the tool set. A `RetryPromptPart` holds a rejected call. A call with no answer is an error. This needs no wrapper of the tool functions and no hook, and it covers a call that failed in argument validation, which a hook on the execution does not see.
- **The tool sets the outcome of its answer.**: Only the tool knows if it found nothing or could not run. Every real tool answers both cases as text, so the text cannot give the outcome without a match on the words of each answer. A tool returns `ToolReturn(text, metadata=ToolOutcome)`, which is the pydantic-ai way to give the application data that the model does not read. `ok_answer`, `empty_answer` and `error_answer` build the three. `empty` is a call that ran and found nothing: a search with no match, a file with no symbols, a read past the end of a file. `error` is a call that could not run: an argument that is refused, a path that is missing or outside the repository, a binary or large file, a GitHub or OpenSpec read that failed, or a git command that ran out of time. A tool that sets no outcome gives `ok`, or `empty` for an answer with no non-whitespace character.
- **Annotate each tool with a bare `ToolReturn`.**: pydantic-ai builds the return schema of a tool when it makes the tool, from the return annotation. A union with `ToolReturn` builds the schema of its dataclass and took 20 ms for each tool. A bare `ToolReturn` gives an empty schema at once. So each tool of the stage planner returns `ToolReturn` on every path, `ok_answer` included. The schema is cleared before it reaches the model in both cases.
- **Keep the outcome and the size in `ToolCallRecord`.**: One list holds each call, in order. The comment line, the counter and the histograms all read it, so the three agree. `RunTrace.combined` joins the lists of two runs, as it does today.
- **Send the counts when a run ends, and the zero increments when it starts.**: A process sends its deltas when it flushes, so the order inside a run does not change the series. The start-of-run increments add 0 to `outcome="ok"` for every tool of the toolset, so each tool has a series before the run calls any. The end-of-run code adds 1 for each call, and observes the size of each answer, the calls of the run, and the limit.
- **Observe the calls of a run only when the run finished.**: A run whose model call failed made no plan run. If it counted as a run, a model that is down for a week would make the alert fire for every tool. `ToolboxClient` knows when `investigate` raised, so it tells `end_run` with `finished`. `trace.requests` cannot tell: a failed request leaves an interrupted reply with no parts in the messages, and `absorb` counts it. The calls that the run made before the failure still count.
- **Name the limit in `investigate`, once for each run.**: The hook that ends the tools knows which limit it hit. `_limit_reached` returns `calls`, `requests` or `window`, and `_offering` keeps the first one. A hard stop by `UsageLimitExceeded` has no hook call. The hook flags `requests` and `window` before the request that they can stop, so a hard stop with no earlier flag is one reply over the call budget. It is named `calls`. The message of the error is not read, as `_stopped` in `stage_toolbox.py` does not read it.
- **Put the alert in a new group `roadmap-service-tools`.**: The plan of #2950 changes the requirement of the group `roadmap-service-activity` with `MODIFIED`. Two changes never modify one requirement, and a tool alert is no Service activity. A group of its own adds a requirement and modifies none, as `roadmap-service-items` did (#2919).
- **The alert groups by `row`, `tool` and `toolset`, and reads no `row` filter.**: The implement job can send the same series later with `row="implement"`. The `on (row, toolset)` join makes the rule count the runs of the same row and toolset. A tool of `extended` is not "unused" in a week when only `base` ran, because no run of `extended` happened.
- **The alert needs a tool series that is older than 7 days.**: "No call in 7 days" cannot hold for a series that has lived for 3 days. Without this condition, each tool that the first run does not call would alert at once after a roll-out. The rule keeps a series that has a sample in the 7 days before the window: `count_over_time(x[7d] offset 7d) > 0`. So a new tool has 7 days. Because only such a series reaches the rule, `increase(x[7d])` needs no form for a series that starts in the window (#2505). `histogram_count(increase(...))` of the native histogram of the calls per run gives the number of runs. promtool 3.15.1 accepted the native histogram input (Feasibility 7).
- **A tool that leaves the registry keeps its alert until its series leaves the window.**: Its series has no new sample, so for up to 7 days its sum stays 0 while runs happen. A person who removes a tool knows the alert follows. The rule has no list of tool names, so it needs no edit for a new tool. A list would drift from the registry (rejected below).
- **Put the panel in a new row "Planner Tools" of `devops-cli.json`, at `y` 95, 24 wide and 8 high.**: `project-metrics.json` holds snapshot gauges, and a test of `tests/grafana/test_grafana_dashboards.py` asserts that it has no `increase(` query. `devops-cli.json` holds the counters of the Service. The row takes the ids 33 and 34, which the plan of #2950 does not use. The panel has two queries: the calls by tool and outcome on the left axis, and the mean answer size by tool on the right axis. Both filter `job="roadmap-service"` and `row="stage"`.
- **Use the unit annotations `{char}` and `{call}` for the two histograms.**: The collector uses `UnderscoreEscapingWithoutSuffixes`, so the unit does not change a name. The UCUM annotation says what the number counts.

## Rejected alternatives

- **Wrap each tool function, or add a pydantic-ai `Hooks` capability, to tally each result.**: The refined design of the issue chose a wrapper. The messages already hold each answer with its `tool_call_id`, and `RunTrace` reads them. A wrapper of 12 tool methods must keep each signature and docstring, because pydantic-ai builds the tool schema from them. A hook on the execution sees no call that fails in validation.
- **Parse the text of the `RunTrace` comment after the run.**: It holds no outcome and no answer size, and the text is for a person.
- **Query Prometheus from the comment path.**: The comment must not depend on the metrics backend.
- **A label `job` on the instruments.**: See the first decision. The value would never reach Prometheus.
- **One generic counter with a free-form label.**: A free-form label is unbounded and cannot support the panel or the alert. Each label here has a closed set: the tools of the registry, `stage`, `base` and `extended`, three outcomes and three limits.
- **A static `absent_over_time` list of tool names in the rule.**: The list drifts from the registry and needs one expression for each tool.
- **A separate gauge for the tools that a toolset offers.**: It adds a fifth instrument that the issue does not ask for.
- **A new Roadmap dashboard file.**: No such file exists, and a new dashboard needs its own provisioning.
- **The panel in `project-metrics.json`, with the assertion of `tests/grafana/test_grafana_dashboards.py` edited.**: The assertion says that file has no `increase(` query. An edit that lets one query pass is a lowered check, which only the owner can allow.
- **The raw return before the cut, or the tokens of the answer.**: The model reads the text after the cut, and no token counter exists for a tool return.
- **A threshold for `empty` such as an answer under 20 characters.**: A short answer can be valid, and the threshold is arbitrary.
- **`empty` only for an answer with no non-whitespace character, as the refined design of the issue says.**: A run of the 12 tools on edge inputs gave `ok` for 11 cases that found nothing or failed, so `empty` never occurred with a real tool (Feasibility 6). The counter would not show which tools return nothing, which is the purpose of the issue.
- **A match on the words of each answer, such as a text that starts with "No " or ends with "is outside the repository."**: It ties the metric to the wording of each answer, and a change of a word changes the series with no failing test. The outcome belongs to the tool.
- **A `str` subclass that carries the outcome.**: It keeps `-> str`, but `answer == "No match."` stays true whatever the outcome, so a test that compares the text cannot catch a wrong outcome. `ToolReturn` is a dataclass: a test compares text and outcome in one value. It is also the type that pydantic-ai documents for this use.
- **The annotation `str | ToolReturn` for each tool.**: It costs 20 ms for each tool when the tool is made (Feasibility 6).
- **Put the alert in the group `roadmap-service-activity`.**: It forces a `MODIFIED` of a requirement that #2950 modifies.
