# Design

## Decisions

- **The CronWorkflow names its cron expression in `schedules`.** `spec.schedules` is a list with the one value `"*/3 * * * *"`. No other field changes. The CronWorkflow has no `suspend` field, and this change adds none: with the executor account, the API server egress of `argo-workflow-egress` and the retry of exit 75, a run can end.
- **The WorkflowTemplate names its mutex in `mutexes`.** `spec.synchronization.mutexes` is a list with the one mutex `rag-ingest`. The template sets no `mutex` and no `semaphore`. With `concurrencyPolicy: Forbid` of the CronWorkflow, the template keeps one holder, as WK2 of `docs/SERVICE_PATTERNS.md` asks.
- **The executor has its own account.** `spec.executor.serviceAccountName: argo-executor` gives the executor the account that the environment repository makes, with a Role for `create` and `patch` on `workflowtaskresults`. The pod keeps `serviceAccountName: devops-cli`, which has `automountServiceAccountToken: false` and no RoleBinding (`check_the_jobs_run_as_an_account_with_no_token_and_no_role` in `tests/gate/k8s_checks/runner.py`). So the ingest container gets no token. This is the form of WorkflowTemplate `infra-drift` (#7364).
- **Only exit 75 retries.** The template `ingest` sets `retryStrategy` with `limit: "3"` and `expression: "asInt(lastRetry.exitCode) == 75"`. The default `retryPolicy` of Argo is `OnFailure`, and a container that exits 75 fails its node, so the policy and the expression are both true only for exit 75. JB4 of `docs/SERVICE_PATTERNS.md` retries exit 75 and faults of the infrastructure, never a refusal or a defect.
- **The check is a module of the `k8s` row that runs the offline lint of Argo.** `tests/gate/k8s_checks/argo_workflows.py` holds `argo_lint_problems`, which writes the objects to a file in a temporary folder, runs `argo lint --offline --output simple` on it, and returns one line for each problem. A lint that exits non-zero with no line of an object returns its output as the problem, so a missing or broken `argo` fails the row. The module holds cases that give the function small Argo objects in memory, and the check `check_each_argo_object_of_the_product_base_passes_the_offline_lint`, which gives it each object of `applied_documents(DEVOPS_DIR)`. `tests/gate/k8s.py` runs each module of `tests/gate/k8s_checks/` as the row `k8s`, so `uv run devops ci --check --only k8s` and the CI job run it. The form of a rule with cases in memory is that of `dual_type_problems` in `tests/gate/k8s_checks/network_policies.py`.
- **The lint reads each Argo object.** The function gives the lint each object of the render. The lint reads each object of the group `argoproj.io` and skips the others, such as a CronJob, which has `spec.schedule` too. A CronWorkflow or a Workflow that names a WorkflowTemplate gets it from the same file, so the offline lint resolves the reference.
- **CI takes `argo` from the devtools image.** `Static Analysis` runs the `k8s` row, and `Fail-to-Pass Check` replays it on the base and the head tree when a module of `tests/gate/k8s_checks/` changes. Both jobs run on the runner host, so they copy `argo` with `.github/actions/devtools-commands`, and the stage `devtools-bin` of `.devcontainer/Dockerfile` holds it. The digest of the devtools image pins the command, and Renovate moves that digest. No file of this repository names a version of `argo`.
- **ADR 0008 gets one line.** A dated Status History line in the `Fact out of date` form says that the controller runs namespaced in `devops` and that the manifests use `schedules` and `mutexes`. Section "One namespace watched" of the body says that `singleNamespace: true` makes the controller watch only `argo-workflows`. The body keeps its hash.

## Rejected alternatives

- **A rule of our own that walks the fields.** A first draft of this change walked `schedule`, `mutex` and `semaphore` in Python (about 50 lines). `argo lint --offline` of the devtools image names the same fields, as `strict decoding error: unknown field "spec.schedule"`, and each other field that the controller does not know, from the release of the controller. A rule of our own needs a change for each field that a release of Argo drops.
- **A row in the service catalog.** The issue names the catalog module (`CATALOG_TOML_NAME: Final[str] = "catalog.toml"` in `src/devops_cli/k8s/catalog.py`) and its test file. That module makes `catalog.toml` and `CATALOG.md` of the environment repository with `devops k8s catalog`. The `k8s` row does not run it: `tests/gate/k8s.py` runs only `tests/gate/k8s_checks/`. A rule there would not refuse a manifest of `k8s/devops` in CI.
- **A pytest test that reads the manifests.** `docs/TESTING.md` says that no test asserts a value of a manifest, and the `test-tree` row refuses a new test that reads one (`tests/gate/tree_checks/config_values.py`). The render of the `k8s` row is the validator.
- **A lint of `rag-ingest` only.** The controller refuses or ignores the singular fields of each Argo object, and the render holds 4 such objects. A check of one object lets the next template with `schedule` reach the cluster.
- **A kubeconform schema of the installed CRDs.** The CRDs set `x-kubernetes-preserve-unknown-fields: true` on `spec` (`kubectl get crd cronworkflows.argoproj.io`), so their schema accepts the singular fields.
- **Retry on each failure.** A defect then runs three more times and delays the alert `RagIngestBehind`. JB4 of `docs/SERVICE_PATTERNS.md` refuses it.
- **A second API server policy for `rag-ingest`.** `argo-workflow-egress` selects each pod with the label key `workflows.argoproj.io/workflow`, which the controller sets on each Workflow pod. `check_only_the_service_pod_and_the_workflow_pods_may_reach_the_api_server` in `tests/gate/k8s_checks/runner.py` refuses a third policy with TCP 6443.
