# Design

## Decisions

- **One comparison, in the store.** `GitHubRoadmapStore._answered(number, found)` takes each issue payload that answers a request of a number. It returns the payload when `_is_requested` holds: the `number` of the answer is the requested number, and the repository that the answer names is the repository of the store. Else it returns None. `_read_issue` wraps the read of `repos/<owner>/<name>/issues/<number>` with it, and `issue`, `_require_issue` and `pull_title` read through `_read_issue`. `_revalidate_issue` passes the answer of its conditional read, and `_send_edit` passes the answer of its `PATCH`.
- **The repository of an answer.** `_IssuePayload.repository` gives the repository of `repository_url`, else of `url`, else of the page URL `html_url`. `urlsplit` and `PurePosixPath` split the path. A REST URL names the repository in the two segments after `repos`. A page URL names it in its first two segments, and only when the path is `/<owner>/<name>/issues/<number>` or `/<owner>/<name>/pull/<number>`. `RepoRef` compares the names, so `Acme/Widgets` is `acme/widgets`. The number in a URL is not compared.
- **An answer that names no repository.** The comparison then uses the number only. The recorded listing answers of `tests/fixtures/roadmap/` hold `url` and `html_url`, so they name a repository. A payload whose `html_url` is no issue page, such as `https://example.com/issues/7`, names none.
- **What a refused answer gives.** It gives what a missing issue gives today. `issue`, `item` and `pull_title` return None. `_require_issue` raises `GitHubOperationError` with the message `#<number> is not an issue of <repository>.`, so `read_issue_body`, `write_issue_body`, `set_field`, `set_fields`, `set_marks`, `set_title` and `close` stop before any write request, and so do `add_sub_issue` and `add_blocked_by` when they read the issue. The store logs one warning with the requested number and the name of its own repository. The log holds no field of the answer.
- **The answer of a write.** `_send_edit` compares the answer of the `PATCH` of an issue in the same way. An answer that names another issue fails the write with the same error, and the store does not keep it in its listing or in the brain.
- **The conditional read.** A 200 answer is compared as a plain read. A 304 answer has no payload: the store gives the record of the brain entry. `_cached_issue` uses an entry only when its record names the requested number and the repository of the store, by the same `_is_requested`. It removes any other entry and gives None, so the store reads GitHub.
- **A number that is no issue of the repository leaves the store.** `_gone(number)` runs for a refused answer and for a 404 answer. It takes the record out of the listing of the store, tells the listing of the lane (`ListingRead.drop`) when the store held the record, and removes the brain entry (`forget_issue`). The store asks the listing only for a number that its own listing held, so a read of a number that never was an issue costs no more than one removal command.
- **The listing keeps the numbers that left.** `IncrementalListing` holds, for each repository, the numbers that `drop` named. `read` leaves their records out of the snapshot that it starts from, and so out of the listing and of the snapshot that it keeps. A number that GitHub lists as changed is an issue of the repository again, so `read` takes it back. A full read gives only the issues that the repository holds, so it clears the numbers. `service_jobs` gives one `IncrementalListing` to each round of a lane, so the numbers live as long as the worker of the lane.
- **The review listing drops nothing.** `_ReviewListing` of the project review implements `ListingRead` too. Its store reads no issue by number, so its `drop` does nothing.
- **Rows do not change.** A row gets None or the error of a missing issue. The Status sweep reads an item again before its write and leaves an item whose read gives None. The alternatives round reads the body of an item again before it writes the check, and the error ends that round, as the error of a deleted issue does. The next round of the lane does not select the item.

## What the change leaves

- **Each lane drops the record at its own first read of the number.** Each lane has a listing and a snapshot file of its own, and the shared tier takes the copy with the newest watermark. A lane that never reads the number keeps the record until its next full read, at most 24 hours after the last one.
- **A worker that starts again reads the record once more.** The numbers that left are in the memory of the lane. After a restart, the first read of the number drops the record again.
- **The count of sub-issues of a parent.** A dropped record that was a sub-issue leaves the count of its parent as it is until the parent changes or the listing is read in full.
- **The listings below a number.** `comments_on`, `label_changes` and `blocked_by` read a listing below `issues/<number>`, and `closures` and `last_renamed_at` read the timeline with GraphQL. Their answers hold no issue payload, and the GraphQL selection holds no number and no repository, so the comparison does not cover them. A read of the comments or of the events below the number of a transferred issue answered 404 (`gh api`, read on 2026-11-26). `blocked_by` already leaves out a blocker of another repository.
- **The writes that read no issue.** `comment`, `label_issue`, `unlabel_issue` and `edit_comment` send their request with the number that the caller gives, and take no issue payload. The change adds no read to them.
- **Status 410.** GitHub answers 410 for a deleted issue. `_read_or_none` raises for it today, and this change keeps that.
- **A renamed repository.** GitHub answers a read under the old name of a repository with the new name. The comparison refuses such an answer, so the name of a store must be the current name.

## Rejected alternatives

- **Compare the number only.** A transferred issue can get, at its new place, the number that it had. The fake answer of `test_an_answer_that_names_another_issue_reads_as_no_issue[another-repository]` holds number 7 and the repository `acme/other`, and a comparison of the number takes it.
- **Take the repository from `html_url` only.** `html_url` is the one required URL of `_IssuePayload`, so one field would serve each shape. But `repository_url` is the field that the REST API defines for the repository of an issue, and `_IssuePayload.parent` already reads it (`src/devops_cli/roadmap/stores/github_store.py:216`). The page URL is the last choice.
- **Remove the record from the snapshot at the time of the drop.** `IncrementalListing.drop` would load the snapshot and save it with no record of the number. `TieredSnapshotStore.load` (`src/devops_cli/roadmap/stores/listing_shared.py`) takes the shared copy when its watermark is newer than the local one, and each other lane saves its own copy, which still holds the record. `test_a_dropped_record_stays_out_when_another_copy_of_the_snapshot_holds_it` shows the case: a rewrite alone lists number 7 again in the next round. The load also parses the whole snapshot, about 38 MB of JSON for this repository (docstring of `listing_shared.py`), for one number.
- **A tombstone in the snapshot.** A field of `ListingSnapshot` with the numbers that left needs a new schema key, a field in `SharedMeta` and a merge rule for two copies, because the shared tier replaces a copy whole (`may_replace`). The full read of each lane removes the record after at most 24 hours with no new field.
- **Each row reads each selected item again before its work.** This adds one request for each item of each round, and `alternatives_requests` (`src/devops_cli/roadmap/request_plan.py:609`) and the plans of the other rows list each request of a row. The store refuses the write with no new request.
- **A new error class for a refused answer.** A row would catch it and go on with the next item. Each caller then has two classes for one fact, a number that is no issue of the repository, and `_require_issue` raises `GitHubOperationError` for a missing issue and for a pull request already.
- **Add the number and the repository to the GraphQL selections.** `_CLOSURES_QUERY` and `_RENAMES_QUERY` return times and reasons of timeline events and no text of the issue. The change of the two queries changes the request plans that list them (`closures_args`, `renames_args`) for no payload that the store keeps.
