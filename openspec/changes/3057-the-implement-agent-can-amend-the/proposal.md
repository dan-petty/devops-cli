# Proposal

## Why

Issue #3057: an implement step that finds a wrong plan can only stop. A stop sets the item Blocked, and the step discards its work. The plan of an item is written at one commit and implemented at a later commit, so some defects show only at run time: a file that moved, a group that grew past the window, a premise that the stage probe could not run. The issue asks for a bounded way to correct such a plan in the same pull request, and for a return of the item when the premise is false.

The count "34 of 37 plans had defects" comes from the issue. It was measured before #3177, #3178, #3176 and #3182 added checks at stage time, and it is not measured again here. What the stage checks cannot see is the part that remains for the implement step: the state of the checkout at run time.

The failure taxonomy (#3195) already names both actions. `plan_defect` has the default action `amend`, and `premise_false` has `return` (`src/devops_cli/roadmap/failure.py:79-80`). The job takes neither action today. This change makes the job take both.

## What Changes

- Add `src/devops_cli/roadmap/implement_amend.py`. It holds the request of an agent (`PlanRequest`), `parse_request` and `judge`. They are pure functions. The agent only asks. The job decides, with rules in code.
- A step that finds a defect changes no file and ends its last message with one fenced block `plan-request`. The step prompt says so. The step code does not change: the step stops as it does today, and `StepOutcome.last_message` carries the block to the job.
- The job (`implement_run.py`) reads the block of a stopped step. A request of the kinds `path`, `command` and `task` that passes its rules is applied to the `tasks.md` of the change. The job commits it in its own commit, records it in a new section `## Amendments` of `tasks.md`, runs the same group again, and lists it with its evidence in the pull request comment. The job applies one amendment for each group.
- A `premise` request with evidence returns the item to New with the evidence, through `apply_return`, and pushes nothing. A `scope` request, and a request that breaks a rule, stops the item with a question on the issue, and the item waits for a person.
- A group whose inputs measure more than the limit of the step is split once for each item, through a function that the stage job and the implement job share (`stage_split.py`). The job writes the new groups, renumbers the later groups and the `## Criteria` lines, and goes on.
- The stop comment names `amend` as the action taken after an amendment (`failure_lines` gets a `taken` argument), and the dry run of the job lists the new writes.
- The change fits one pull request. It has nine task groups. If it is too large for one pull request, groups 6 to 8 (the split of a group over the window) are the part to move to their own issue, and groups 1 to 5 and 9 still stand alone.
- The change carries spec deltas: it adds the capability `roadmap-plan-amendment` and ADDED requirements in `roadmap-implement-job`. Every delta is ADDED: no existing requirement becomes false (see the check in Feasibility).

## Capabilities

### New Capabilities

- `roadmap-plan-amendment`: what a request is, which changes the job may apply by itself, how it records them, and which requests wait for a person

### Modified Capabilities

- `roadmap-implement-job`: the job applies a request, comments it, returns an item whose premise is false, names the action taken, and splits a group over the window

## Feasibility

I checked each premise on `origin/main` (`80ffc5c1`, after #3250) in a scratch clone, with a temporary `HOME` and read-only commands. The probes are scratch scripts run with `uv run python`; none is committed.

1. A step can only stop on a wrong plan. `src/devops_cli/ai/tasks/roadmap_implement_step.md:12` says "If the path that a task names is wrong, write the file at that path anyway, or say in your last message why you did not." A probe of `classify_failure` printed: `'The agent changed no file.' -> plan_defect amend`; the over-window message `'The inputs of the step measure 50000 tokens. The limit is 40000 tokens...' -> plan_defect amend`; `'A task of the group is not ticked: 1.1' -> plan_defect amend`; and the same "changed no file" text with the agent saying "The premise is false" `-> premise_false return`. `docs/ROADMAP_WORKFLOW.md:144` says "The Job runs one action by itself: the fix rounds". So the classes exist and no action runs for them.
2. The step must not write the plan. `implement_step.py:765-777` (`_restore_tasks`): "The job owns the file: it reads the verification commands from the text before the run, so no edit of the file changes what judges the work." The scenario "The model rewrites a verification command to one that passes" (`openspec/specs/roadmap-implement-step/spec.md:468`) holds that the step runs only the original command. So the job, not the step, writes the amendment. The step code and spec stay as they are.
3. The job parses `tasks.md` once. `implement_run.py:446` reads `parse_task_groups(...)` before the loop `for group in tasks` (`:447`). An amendment or a split changes the file during the loop, so the loop must read the file again after each.
4. A job-side replacement works on the real parser. A scratch prototype took a `tasks.md` whose group 1 named `tests/commands/test_sample.py`, replaced the path with `tests/roadmap/test_sample.py` (a file of the checkout with the same name) in the text of group 1 only, and re-parsed. It printed `before commands: ('uv run devops ci test tests/commands/test_sample.py',)`, `after  commands: ('uv run devops ci test tests/roadmap/test_sample.py',)` and `group 2 text unchanged: True | criteria section kept: True`.
5. A section `## Amendments` is safe. `parse_task_groups` on `openspec/changes/archive/2026-11-02-3153-the-stage-job-verifies-its-plan/tasks.md` with a section `## Amendments` and a plain bullet appended printed `groups before/after an Amendments section: [1, 2, 3, 4] [1, 2, 3, 4] | last group text equal: True`. `src/devops_cli/roadmap/step_files.py:143` says that a `##` section that is not `<n>. <title>` is no group. The OpenSpec gate fails on unticked tasks (`src/devops_cli/openspec/gate.py:9`), so an amendment is a plain bullet with no checkbox.
6. A defect of the stage that this change meets: the step reads verification commands only from `Verification:` lines (`step_files.py:27`, `:55`), but the stage renders "and verify that `X` passes" in the task text (`stage_task_pass`, `src/devops_cli/lang/en/messages.py:2991`). A probe that renders a group with `group_text` and parses it with `parse_task_groups` printed `verification_commands=()`, and so did the fixture `tests/fixtures/roadmap_eval/implement/2175-dead-code-first-plan-group-1/plan/tasks.md` (five groups, all `()`). So a staged plan makes the step run no verification command. This is another defect and no part of this change. The `command` kind of this plan acts on the commands that the step reads, which are the `Verification:` lines. I wrote the tasks of this plan with both forms, so the step reads them. A second mismatch: the stage form admits a negative search (`_valid_verify('! git grep -n -w zzzz_not_there src/ tests/')` printed `True`), but the step refuses it (`commands_failure(Path('.'), ['! git grep -n -w zzzz_not_there src/ tests/'])` printed `The verification command ! git grep -n -w zzzz_not_there src/ tests/ is not allowed. ! is not one of: git, uv, ruff, mypy, grep, cat, ls, head, tail, find, openspec, devops.`). So the `command` kind accepts only a command whose first word the step may run, and the tasks of this plan use no negative search. I file both gaps in my report.
7. The split step is a model call on `StageGroup` objects. `stage.py:840-863` (`_Planner._fit`) asks once for each item (`_split_asked`, `:847`) with the request `{number, title, budget, groups: [model_dump + tokens + over_budget], criteria}` and the prompt `roadmap_stage_split.md`. The client is `get_llm_client(task="analysis")` (`stage.py:1051`). The implement job holds only `get_task_model("implement")` (`commands/roadmap.py:672`). A `StageGroup` has fields that `tasks.md` does not keep: the probe of a rendered group shows only the task lines and the `Reads:` and `Changes:` line, with no `kind`, `test` or `verify`. So the job cannot build the old request from the file. It sends the text of the group in place of the fields, and the reply type `StageSplit` stays. The reply is checked by `path_problems`, `form_problems` and `criterion_problems`, which are public and take a `StagedTree` (`StagedTree.read(source, operation=...)`, `stage_paths.py:76`).
8. The return path exists. `stage.py:1323-1330` (`_return_item`) calls `apply_return(store, plan_return(store, number, comment, repo))`, and `commands/roadmap.py:866` does the same for `devops roadmap return`. `apply_return` comments, then sets Status New (`return_item.py:55-62`).
9. The over-window refusal is a `RoadmapImplementError` with the code `ROADMAP_IMPLEMENT_REFUSED` (probe: `error code: ROADMAP_IMPLEMENT_REFUSED`), raised at `implement_step.py:297-305` before any request. In the job it reaches `_implement_item`, which stops the item (`implement_run.py:830-855`). A subclass keeps the code and the message, so the spec "A step refuses an input that does not fit the window" stays true.
10. The pull request comment and a merged plan. `_comment` (`implement_run.py:620`) lists the outcomes after a mark, and `_pull_request` (`:603`) posts it after the push, so a Planned item with no draft yet gets its comment when the draft exists. An amendment edits the active folder `openspec/changes/<issue>-<slug>/` on the branch of the implementation pull request. The job archives that folder in its last commit (`_finish_change`, `:474`), after the groups, so it never edits a change that is archived or merged as an archive. A merged plan is a folder on the default branch that the implementation branch starts from. The fix step runs after the archive and ticks no task, so it makes no amendment.
11. The check of the existing requirements. I listed the 44 requirements of `roadmap-implement-step` and the 51 of `roadmap-implement-job` (`grep -c '^### Requirement'`), and I read the text of those that concern `tasks.md`, the window, the stop, the comment, the record and the failure class. None says that a step stops with no other outcome for a wrong plan, or that the job reads `tasks.md` once. "A stopped item is Blocked" (`roadmap-implement-job/spec.md:163`) applies to a stop, and a return is no stop. "The stop comment names the failure class" has the scenario "A step that changed no file", which stays true for a step that sends no request. So every delta is ADDED.
12. The size of each group. I measured the nine groups with `measure_groups`-equivalent code (`count_tokens` of the issue and the change files, the group text, and `_read_tokens` of `stage_change.py`) on this folder. It printed totals from 29,243 to 37,366 tokens against the budget of 40,000, the largest being group 7 (37,366) and group 4 (37,346). The tokenizer cache was empty in the sandbox, so `count_tokens` fell back to its character heuristic (warning printed); the real counts may differ by a few percent. To stay under the budget, the tasks name a file in a code span only when the step needs its signatures (the step packs each such file up to 8,000 tokens, `step_files.py`), and the large `messages.py` is named in the `Changes:` line only.
13. The gates of this repository cannot run on a committed plan yet (#3201), so I ran them by hand on this folder: `openspec validate 3057-the-implement-agent-can-amend-the --strict` printed `Change '3057-the-implement-agent-can-amend-the' is valid`, and `uv run devops openspec check` printed `OpenSpec check passed.`. All 13 requirement texts are under 500 characters (the longest is 483).

Not verified: how often a real run meets each kind of request. The issue gives no count by kind. The tests replay a scripted model, and a real model may ask for a kind that the rules refuse. A refused request becomes a question, so the cost of a wrong guess is one stop that a person answers.

## Existing Tool Considered

- `openspec` 1.14.3 has the commands `change show`, `change list` and `change validate`, and no command that amends a change (`openspec change --help` printed these three and `help`). So no tool applies a correction to a `tasks.md`.
- `markdown-it-py` finds the fenced block. It is a dependency now (`step_files.MARKDOWN`), so the parser needs no regular expression and no new package.
- `pydantic` validates the request. It is a dependency now, as for `StageSplit`.
- `StagedTree` (`stage_paths.py:61`) answers "is this a tracked file" and "which tracked files have this name". The judge uses it, so an untracked scratch file is never a corrected path.
- Coding agents such as Aider and OpenHands revise a plan inside their own loop. I did not verify their code (no web search in this session). None of them applies a correction to an OpenSpec `tasks.md` under a rule table, reports it on a roadmap issue, or returns the item to a roadmap Status, so the rules would still be project code.

The change builds the judge, the record and the job loop. The cost is an estimate. To build: about 1.5 million input tokens and 150,000 output tokens over nine steps (the plan run of this item used 225,055 input and 4,759 output tokens for 8 requests; a step of #2175 used 2.8 million input tokens for 138 requests, as #3098 says), and about 5 hours of Job time with one review. To keep: about 5,000 tokens at each change of a request key or of a rule. To fix: about 30,000 tokens for a rule that refuses or accepts a request by mistake (one test and one rule).
