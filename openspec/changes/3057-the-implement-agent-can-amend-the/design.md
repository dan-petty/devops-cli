# Design

## Security and scope: what the agent may change, and what needs a person

This change lets the implement job edit a part of the repository that it did not edit before: the plan of the item. The agent never edits the plan. It asks, and the job decides with rules in code. The table says what the job may change by itself.

| Part | Who may change it | How |
| :--- | :--- | :--- |
| The text of an unticked group in `tasks.md` of the item's change: a missing path, the words of a verification command, one added task | The job, for a request that passes the rules of its kind | `judge` in `implement_amend.py`, one amendment for each group |
| The groups of `tasks.md` after a split, the group numbers, the `group N` of the `## Criteria` lines | The job, once for each item | The split step, then `path_problems`, `form_problems` and `criterion_problems` |
| The section `## Amendments` of `tasks.md` | The job | One plain bullet for each amendment |
| `proposal.md`, `design.md`, the files under `specs/`, the text of an acceptance criterion, the issue, a ticked task, a file outside the change folder | A person | A request that needs it is a question on the issue |
| The Status of the item | The job, to New, for a false premise with evidence | `apply_return`, which a person can undo by refining the item again |
| A check, a threshold, a verification command that drops a path | A person | AGENTS.md rule 5: never lower a check. The `command` rule keeps every path |

Four limits bound the power of an agent that is wrong or misled by the text of an issue:

1. The agent sends text only. The job reads it as data, masks secrets, puts it on one line and cuts it to `CONST_ROADMAP_IMPLEMENT_REASON_CHARS`.
2. The rules are deterministic, so an agent cannot talk the job into a change. A request that fails a rule changes nothing and becomes a question.
3. An agent cannot weaken its own check. A `path` request may only give a missing file the name of a tracked file with the same file name. A `command` request keeps the paths of the command. Neither request can touch the `## Criteria` section or a ticked task.
4. The bound is a count that the code holds: one amendment for each group, one split for each item. A second request for the same group stops the item.

The job also keeps its old limits. The item author must be trusted before the job takes the item (`implement.py`, `_Judge.judge`). The step shell is no boundary and the runner pod is (`implement_run.py` docstring). Every amendment is a separate commit, listed in the pull request comment, and the last task of this change keeps the plain bullet for the review of the diff by a person.

A premise return needs a person in one case only: the item goes back to New, and a person refines it again. The return trusts the claim of the agent. This is the same trust as the stage job, which returns an item at once when the planner reply sets `premise_failed` (`stage.py:682`).

## Decisions

- **The agent asks and the job decides. The step does not apply an amendment.** The step writes `tasks.md` back to its text before the run after each turn, and runs only the verification commands of that text (`implement_step.py:765-777`; the scenario "The model rewrites a verification command to one that passes" in `roadmap-implement-step/spec.md:468`). If the step applied the change, an agent could rewrite its own check. A job that writes between two steps changes the text that the next step reads, and the next step still cannot change it. The step code and its spec stay as they are.
- **The request is one fenced block at the end of the last message.** The step already returns the last text of the model in `StepOutcome.last_message`, and the job already reads it for a stop (`_stopped_by`, `implement_run.py:204`). A file would not work: `_stage` runs `git add -A` (`implement_step.py:946`), and the prompt says that the step keeps a new file under `src/`, `tests/`, `docs/` and `openspec/`, so a request file would be committed. A tool would add a part to the surface of the agent, which now has none of its own (`build_agent`, `implement_step.py:419`).
- **Five kinds: `path`, `command`, `task`, `premise`, `scope`.** The issue lists a wrong path, a missing task, a group over its budget and a wrong verify command, then a premise failure and a scope change. The group over its budget needs no request, because the job meets it before the step runs (`build_step_inputs` refuses at `implement_step.py:297`). So the agent has five kinds, and the sixth case is the split.
- **A `path` request gives a missing file the name of a tracked file with the same file name.** `StagedTree.same_name` already lists the tracked files with a file name (`stage_paths.py`, class `StagedTree`). A plan that names `tests/commands/test_sample.py` when the file is `tests/roadmap/test_sample.py` has a moved file. A different name could point a verify command at an unrelated test that always passes. The path must be tracked, so an untracked scratch file of the agent is not a correction. A path marked `(new)` in the `Changes:` line is not missing, so it is never replaced.
- **A `command` request keeps the paths of the command.** The result of `commands_failure` (`implement_step.py:810`) depends on the paths that the command names, and the program is the only free part. `pytest tests/x.py` to `uv run devops ci test tests/x.py` keeps the check. A command that drops a path, or adds one, is a different check, so it is a question. The new command must also pass the form of the stage gate: it starts with `uv run devops`, or it is a negative `! git grep` search, and its first word is a program of the verification list (`VERIFICATION_PROGRAMS`, `implement_shell_policy.py:111`).
- **One amendment for each group and one split for each item, and no new setting.** The stage job already splits once for each item (`_split_asked`, `stage.py:847`), and the fix rounds already have the setting `roadmap.implement.repair_rounds`. A counter in the job needs no constant, so it needs no entry in the table that `tests/roadmap/test_roadmap_limit_classes.py` keeps for each numeric limit. The total is at most the number of groups plus one.
- **The amendment is its own commit, `docs(openspec): amend the plan of group <n> (#N)`.** The step commits only `<group title> (#N)` (`_commit`, `implement_step.py:1042`), and the job already commits the documents and the archive in their own commits (`_commit_if_changed`). A separate commit shows the amendment in the diff, and a person who reviews the diff in tuicr sees it first.
- **The record is a section `## Amendments` of plain bullets.** `parse_task_groups` ignores a `##` section that is not `<n>. <title>` (`step_files.py:143`, and the probe in the proposal), and the OpenSpec gate fails on an unticked task (`gate.py:9`), so a bullet with no checkbox is safe. The bullet goes before `## Workflow follow-up`. It stays in the archive, so the reader of the merged change sees what the job corrected.
- **The split carries the text of the group.** A `StageGroup` has `kind`, `test`, `verify` and `process`, and `tasks.md` keeps none of them in a form that a parser reads back (the probe in the proposal). The job cannot rebuild the old request. It sends `{number, title, text, tokens, over_budget}` for the one group. The reply type `StageSplit` and the checks of the stage stay. The new groups replace the old group, and the later groups get new numbers. The criterion text must be equal to the text of the issue, which `criterion_problems` checks.
- **A new module `stage_split.py` holds the ask.** `stage.py` is a large file that many changes edit (#3250 did on 2026-11-02). The planner's `_fit` calls the function and keeps its own rule of one split for each item. The job calls the same function with its own client, `get_llm_client(task="analysis")`, which `apply_implement` gets as a keyword. The measure for the job is the limit of the step (the window less the reserve), not the budget of the stage, so the function takes the budget as an argument.
- **After a return the job leaves the branch and the draft pull request.** The stage job removes a staged branch only for a closed item that only the session identity wrote to (`Removal`, `stage.py:558`, `_reconcile`). A New item is not taken again until a person sets it Ready (`_takeable_status`, `implement.py`). So the plan pull request stays for a person to close. The job clears the marks `implement.group`, `implement.sha`, `implement.branch` and `implement.pr` of its run, because it pushed nothing. It sets no `implement.stopped`, because the item is not stopped.
- **A question is a stop with a class and an action left.** The job sets the class `plan_defect` and the action left `wait`, because a person decides. The Status is Blocked and the comment quotes the request. A person answers on the issue, changes the plan where the answer says, and comments `implement: retry`, which the job already reads (`retry_asked`). No new rule clears the stop.

## Rejected alternatives

- **The step applies the amendment, as the issue says ("a step can raise a plan amendment ... applied in the same pull request").** `implement_step.py:765-777` and the spec scenario at `roadmap-implement-step/spec.md:468` forbid a step to change what judges it. The job applies it, in the same pull request, so the issue is met.
- **A tool `amend_plan` for the agent.** `build_agent` gives the agent `Coder`, the shell and the hooks, and no tool of the project. A new tool is a new surface for the shell policy and the tool log (`ToolCallLog`), for one string that the last message carries already.
- **Any tracked file for a wrong path.** A different name can give a check that always passes. The same name is a moved file, which the probe in the proposal shows working.
- **A model call that judges the request.** `classify_failure` is a pure function by design (`failure.py`, module docstring), and a model judge would cost a request for each request and take instructions from the text of the plan. Rules in code are cheap and testable offline.
- **A second model pass that checks the evidence of a premise.** The stage job returns an item on the claim of the planner reply without one (`stage.py:682`). A return is not final: a person refines the item again. A pass would add a request for each return and a second agent that reads untrusted text.
- **A new split implementation in the job.** `StageSplit`, the prompt `roadmap_stage_split.md` and the checks `path_problems`, `form_problems` and `criterion_problems` exist and have tests. The new part is only the shared function and the text of the group in the request.
- **Amend a ticked group, `proposal.md`, a spec or a criterion.** The acceptance criterion 4 of the issue forbids it without a person, and AGENTS.md rule 5 forbids lowering a check. These cases are questions.
- **Close the plan pull request and delete the branch on a return.** The precondition of `_remove_staged` is that only the session identity wrote to the branch, which the stage job reads with `_reconcile`. The implement job has not read it, and a wrong delete loses a person's work. A person closes the plan pull request.
- **A new class `scope_change` in the taxonomy.** The class list is fixed, and `plan_defect` with the action left `wait` says the same (spec `roadmap-failure-taxonomy`, "The failure classes"). A new class changes the label of the metric `devops_cli_service_implement_failures_total`.
