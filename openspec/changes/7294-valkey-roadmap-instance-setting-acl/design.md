# Design

## Decisions

- **Build the base at a tag, with `nameSuffix: -roadmap`.** The base names each object `valkey`, and a prefix cannot give `valkey-roadmap`. The suffix gives the Deployment and the Service the name of ADR 0021 section 3. The other names follow the suffix: `valkey-data-roadmap`, `valkey-ingress-roadmap`, `valkey-egress-roadmap` and `valkey-exporter-ingress-roadmap`. Kustomize changes the references to the claim and to the generated ConfigMap. The pod keeps the label `app.kubernetes.io/name: valkey`, which is the only such label in namespace `devops`.
- **Patch the three Secret references of the base in the overlay.** A suffix does not change a reference to a Secret that is not in the build (README of the base, "Two stores in one namespace"). One Secret, `devops/valkey-roadmap-auth`, holds the aclfile and the password of each user. The volume `acl` reads its key `users.acl`, and the exporter reads its key `metrics`.
- **Give the container `valkey` an empty `VALKEY_PASSWORD`.** The base reads that variable from the key `password` of a Secret and writes it as `requirepass`. Valkey ignores `requirepass` when it reads an aclfile, and the aclfile turns the user `default` off. So the patch replaces the Secret reference with an empty value, and the Secret holds no password that opens nothing. The start script then writes `requirepass ""`, which Valkey 9.2.1 accepts.
- **The user `default` is off from the first start.** The instance has no old client. `valkey-devops` keeps its default user until #6600 only because its clients sent no user.
- **`brain` gets `~roadmap:v1:brain-* +@all -@dangerous`.** This is the form of the role users of #4704. The pattern holds each key of #4676: `brain-item`, `brain-tool`, `brain-ref`, `brain-sync` and `brain-events`.
- **`agent` gets `%R~roadmap:v1:brain-* +@read +@connection -@dangerous`.** The stage and implement containers run commands that a model writes, so the user holds read commands only. `+@all -@dangerous` would let it run `FUNCTION FLUSH`, which is no key write. The probe showed that the client of valkey-py connects with these commands: `AUTH`, `CLIENT SETINFO` and `SELECT` are in `@connection`.
- **`metrics` gets the 9 commands that the exporter sends, and no exporter option.** The component gives the exporter no option, and one more patch would hold a second place for the same fact. The aclfile is the one place. The set comes from `ACL LOG` of a probe, not from the aclfile of `valkey-devops`, which lacks 5 of the 9 and holds 4 that the exporter does not send (#6600).
- **No `router` and no `sweep` user.** A user with no key to reach gives no value and a pattern that nobody checked. They come with their first key (#4563).
- **The settings are `roadmap.state.url`, `roadmap.state.username` and the credential `roadmap.state.password`.** The section `roadmap.state` follows `roadmap.mcp`. The user takes the variable `DEVOPS_CLI_ROADMAP_STATE_USER`, as `valkey.username` takes `DEVOPS_CLI_VALKEY_USER`. The credential is no field of the config file. The URL has no default, so a workstation has no shared roadmap state (ADR 0023 section 2).
- **One accessor, `roadmap_state_tier()`, gives a `ValkeyCacheTier` or None.** It has the form of `shared_cache_tier()`. With no URL it gives None and writes no log line. With a URL that is not valid it gives None after one warning. While the store is down, the breaker of the tier is open and each read gives None. So a reader has a miss in each case and gets no error. A command waits `valkey.timeout`, and a connection waits at most 0.25 seconds, which are the bounds of ADR 0023 section 2.
- **`_ProcessTier` holds the one tier of a kind.** The cache tier kept a lock, a tier and a flag in module variables. A second copy of these for the roadmap state would repeat 30 lines, so both tiers use one small class. `_SettingsValkeyCredentialProvider` takes a function for the user and one for the password, so both tiers use it too.
- **Each process sends one user (#6600).** The Service pod keeps the listing and writes the brain index, so it sends `brain`. A container of a stage Job or of a runner Job (implement and fix-checks) only reads the index and sends `agent`, and only if it already holds the private key of the App (#6518): the container `agent` of a runner Job holds no App key, gets no password and has a miss. The MCP server sends `agent` when it gets a tool that reads the index. This change gives no pod a user: the change that adds the first client sets `DEVOPS_CLI_ROADMAP_STATE_USER`, reads `DEVOPS_CLI_ROADMAP_STATE_PASSWORD` from the key of the user with `secretKeyRef`, and adds the label `valkey-client: "true"` and an egress rule to the store.
- **Take `valkey` out of the default perimeter of namespace `devops`.** NetworkPolicies add their rules. `devops-default-perimeter-egress` selects each pod whose name label is not in its list, so it would give the pod of the store DNS, the gateway and public HTTPS. With `valkey` in the list, only `valkey-egress-roadmap` selects the pod for egress, and that policy has no rule.
- **Register the folder in `PRODUCT_MANIFESTS_BY_STACK`.** deploy-stack applies a folder of that table with `kubectl apply -k`, so a cluster with no Argo CD gets the store too.
- **Keep the volume placement of the README.** ADR 0021 section 3 puts the volume on the node of the sweep volume, which does not exist yet. The pod has the required node affinity of each pod on a claim, and `devops k8s volume move` moves the volume when the sweep gets its volume (#4563).
- **Extend one gate check.** `devops_runtime.py` holds the list of each container of the product base. It gets the two containers of the store in the form of the `crawl4ai` and `searxng` entries: each is a Deployment container whose image has a digest. No check, threshold or policy is made weaker.
- **Prove the manifest with the `k8s` row and with live checks.** `docs/TESTING.md` forbids a test that asserts a value of a manifest. The tests of this change cover the Secret table, the settings and the tier.

## Rejected alternatives

- **Copy the base into `k8s/devops`.** ADR 0032 section 2 keeps a template with two or more consumers in infra, and the README of the base names the Valkey stores of devops-cli as a planned consumer. A copy would also lose the image updates of Renovate in infra.
- **Add the label `app.kubernetes.io/instance` to the selectors (`includeSelectors: true`).** The README of the base says that Kustomize then adds the label to the client selector of `valkey-ingress`, "so each client pod also carries the label of its store". A client pod would carry `app.kubernetes.io/instance: valkey-roadmap`, which names another workload. Namespace `devops` holds 1 store of the base, so the selectors need no second label.
- **A fourth Secret key `password` for `requirepass`.** `src/devops_cli/k8s/cluster_secrets.py` would hold a generated value that Valkey ignores, and the criterion of the issue names one generated row for each user. The probe started Valkey 9.2.1 with `requirepass ""` and `user default off`, and a connection with no user got `NOAUTH`.
- **Read `VALKEY_PASSWORD` from the key `metrics`.** The value would be a real password in a config line that has no effect, and a later removal of the aclfile would make it the password of `default`.
- **`+@all -@dangerous` for `agent`.** In the probe, the user with this set and `%R~roadmap:v1:brain-*` could run `FUNCTION FLUSH`. With `+@read +@connection -@dangerous` the same command gave `NOPERM User agent has no permissions to run the 'function|flush' command`.
- **Turn `CLIENT SETNAME` off with `REDIS_EXPORTER_SET_CLIENT_NAME=false`.** The option covers 1 of the 5 commands that the user of #4704 lacks, so the aclfile would still need the 4 others. One line of the template holds all 9.
- **The command set of `metrics` in `valkey-devops`.** `DEVOPS_CACHE_VALKEY_ACL_TEMPLATE` in `src/devops_cli/k8s/cluster_secrets.py` holds `+dbsize +client|list +memory|usage +ping`, and `INFO commandstats` of the probe showed 0 calls of these 4 by the exporter. It lacks `slowlog|len`, whose error the exporter does not log, so `redis_slowlog_length` would be absent with no sign.
- **A client NetworkPolicy for the label `valkey-client` in this change.** No pod has the label, so the policy would select nothing. A policy file in the folder would also get the suffix: `tests/gate/k8s_checks/network_policies.py` compares the name of each policy in a file with the name in the build, so `check_every_network_policy_has_a_deploy_stack_path_or_an_owned_exemption` would fail. The first client adds its egress rule in a file of `k8s/devops`, as `searxng/networkpolicy-client.yaml` does for its client.
- **Patch `valkey-ingress` to name the Service pod.** No code of this change reads or writes the store, and #4676 decides its client pods. The label of the base lets that change add a client with no change of this folder.
- **Give the Service pod the user and the password now.** `k8s/devops/roadmap-service/deployment.yaml` would get a reference to a new Secret, and a missing key would stop the Service pod at its next start. With no reference, only the new pod waits for the Secret.
- **A new timeout setting for the roadmap state.** ADR 0023 section 2 gives one pair of bounds for the shared tier, and `valkey.timeout` with `DEFAULT_VALKEY_CACHE_CONNECT_TIMEOUT_SECONDS` already holds them.
- **Return a tier that always misses when no URL is set.** `shared_cache_tier()` returns None for a tier that is off, and each reader of it has the branch. A second form for the same case would be a new contract.
- **A pod affinity to the Service pod.** The sweep volume of ADR 0021 does not exist, and a required pod affinity would keep the store Pending while the Service pod is absent.

## Security

Three passwords cross a trust boundary: they move from Secret `devops/valkey-roadmap-auth` into a read-only file of the pod, and each user reaches only its keys and commands. No password is in git, in a manifest or in a log line: the push generates each value and prints no value. The store accepts no connection with no user, admits only labelled pods of its namespace, and has no egress. A person must confirm that `uv run devops k8s push-secrets --only devops/valkey-roadmap-auth --plan` shows each key `unchanged` before the merge. The case `test_valkey_roadmap_user_passwords_and_derived_aclfile`, `uv run devops ci --check --only k8s` and the live checks of the pod fail if a rule breaks.
