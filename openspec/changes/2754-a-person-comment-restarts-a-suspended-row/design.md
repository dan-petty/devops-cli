# Design

## Decisions

- **Read one repository listing of comments, newest first, and stop at the first comment of a person.**: A listing of the whole repository is one request for all the rows of a lane, and a read that stops at the first wanted comment costs one page. The first page of the real repository held 100 comments from 3 hours 28 minutes, and the first comment of a person was at position 6.
- **Make the read lazy in the store protocol.** `comments_since` gives an iterator, and `GitHubRoadmapStore` asks the session for a page only when the caller needs the next comment.: The policy of who counts as a person stays in `trust.py` and `run.py`, and the store only knows GitHub. A caller that stops sends no more request, and the session test pins that.
- **Give each failed row the time of the newest comment of a person, unless that comment is older than the last success of the row.**: The read starts at the oldest last success of the rows that failed, so the window depends on the other rows. The rule "older than my own last success counts as nothing" makes the digest of one row depend on that row only. Without it, a second row that starts to fail would widen the window and change the digest of a row that is already suspended.
- **Read only when a row that may run holds a failed round.** The rows are those that are due, and those with a cross-job predicate, which a row earlier in the round can make due.: A healthy lane sends no extra request. A dry run returns before the read. The Service sends no request for a row that nobody waits for.
- **Add the time to the digest only when it exists.**: The digest of a row with no comment of a person is the digest that the running version writes, so `service-failures.json` keeps its format and a suspended row stays suspended over an upgrade, unless a comment of a person is newer than its last success.
- **Use the creation time of the comment, not its update time.**: GitHub filters `since` on the update time, but sorts by creation. The first comment of a person in that order has the newest creation time, and an edit of an old comment gives no new time.
- **A person is an author with write access (OWNER, MEMBER or COLLABORATOR), whose login does not end in `[bot]`, and who is not the account of the process.**: The repository is public, so an account with no write access must not restart a row. The `implement: retry` check and `trusted_replies` use the same association rule. A bot with write access is no person. `changes_since(except_actor=...)` shows the same rule for the account of the process: a process that runs as a person must not restart a row with its own comment.
- **Count the comments on pull requests and on issues that are not Items too.**: The input of a round is repository-wide: the issue events of `changes_since` hold the changes of every issue and pull request. The comment listing has no field that tells a pull request from an issue, and the Items that a row reads are not known to the round. A comment of a person on a pull request so restarts a suspended row once, which costs at most `DEFAULT_SERVICE_MAX_FAILED_ROUNDS` rounds.
- **Read in `run_due_jobs`, before the rows run, and let a failed read end the round.**: `changes_since` is read there, and a failed read ends the round with its error and no failed round for a row. A read inside the loop would make the error a failed round of a row, or a clone failure for each row that needs a clone, and the stop of the Service would be counted. The error is not swallowed.
- **The request counts under the row `other`.**: The read happens outside the scope of a row, as the read of the issue events does. `k8s/README.md` says so.

## Rejected alternatives

- **Read the open Items updated since the last success, then the comments of each of them (the proposal of the issue body).**: A real read of 24 hours gave 100 Items on one full page, so a row would send 100 listings a poll. 24 polls an hour make 2,400 requests, and the budget is 500. The scenario of that proposal, three rows with ten Items each, is 33 requests in a poll and 792 in an hour.
- **Subscribe the consumer to `issue_comment` and refuse the comments of the App bot, of pull requests and of issues that are not Items.**: ADR 0009 left the event out after #1361 measured 940 triggers in one hour. Each repository hook needs a change that only a person can make, and each delivery starts a round of every lane.
- **Add a comment kind to `ChangeKind` and read the comments in `changes_since`.**: A change of that kind makes the due rules of the jobs fire, so a comment would start jobs that nobody asked to start. Only the input of a row that already failed needs the comment. Every reader of `Change` would also see a new kind.
- **Keep the time of the suspension in the ledger record and read the comments since then.**: The record would need a new field. A process of the running version reads the record with a fixed type and refuses to start on a record of another shape. The digest needs no new field.
- **Put the time of the round in the digest.**: Each poll would change the digest, and a suspended row would run at every poll again.
- **Filter the comments by `author_association` alone.**: A bot with write access would count as a person. The login suffix and the account of the process close that gap, and the association keeps out the accounts with no write access.
- **Filter by login alone, as `[bot]` and the current actor.**: Any account on a public repository could restart a failed row with one comment.
- **Use PyGithub.**: It lists the comments of one issue, so it brings the per-Item read, and it is a second GitHub client beside the session that holds the budget gate and the conditional requests.
