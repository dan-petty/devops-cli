# Proposal

## Why

Issue #2754: a comment by a person on an item does not start a suspended row again. A row that failed `DEFAULT_SERVICE_MAX_FAILED_ROUNDS` rounds in a row does not run until its input changes. The input of a round (`_round_input` in `src/devops_cli/roadmap/run.py`) is a digest. It holds the issue events since the oldest last success. For a trigger that is not a poll, it also holds the time of the round. A comment is neither. The Service takes only the `issues` webhook event, so an `issue_comment` delivery gets `no_subscriber`. A person who answers on an item of a suspended row must wait for an unrelated issue event.

[ADR 0009](../../../docs/adr/0009-one-webhook-router-delivers-each-event-to-the-consumers-subscribed-to-it.md) left `issue_comment` out on purpose, because #1361 measured 940 webhook triggers in one hour. This change must not bring that load back, and it must stay under `service.github_requests_per_hour`.

## What Changes

- The store protocol gets `comments_since(since)`. It gives the comments of the whole repository, on issues and pull requests, newest first, one page at a time as the caller asks. `GitHubRoadmapStore` reads `GET repos/<repo>/issues/comments?sort=created&direction=desc&since=<UTC time>`. `InMemoryRoadmapStore` gives its comments in the same order.
- `IssueComment` gets `on_pull_request`. The GitHub store sets it from the path of the `html_url` of the comment: `/pull/<number>` for a pull request, `/issues/<number>` for an issue. The `issue_url` field names `issues/<number>` for both. The in-memory store sets it for a comment seeded on a pull request.
- `trust.py` gets `is_person_comment(comment, actor)`. A comment is a person's when its author has write access (`author_association` OWNER, MEMBER or COLLABORATOR) and its login does not end in `[bot]`. The author is not the account that the process acts as. The comment is not on a pull request.
- `FailureLedger` gets `holds_failure(repo, job)`: whether the job failed a round that no success has cleared.
- A round that only polls, and has a row which may run and holds a failed round, reads the comment listing once. It starts at the oldest last success of those rows, or at the first comment when one of them never succeeded. It stops at the first comment of a person or after the newest 100 comments, which are one page. Each of those rows gets the time of that comment, unless the comment is older than the last success of the row.
- A round that a webhook started reads no comment. The time of such a round is already new input for every row.
- `_round_input` adds that time to the digest of the row only when the row has one. The digest of a row with no such comment is the digest of before. So the ledger file keeps its format, and a record written by the running version stays valid.
- A new person comment changes the digest, so the suspended row runs again and counts its failed rounds from one. These comments change nothing: a comment of a bot, of the account of the process, or of a person with no write access. A comment on a pull request or from before the last success also changes nothing. A poll with no new comment changes nothing.
- A comment of a person that 100 newer comments follow is not read. The row then has the digest it had before and runs again once. On 2026-11-05 the bots wrote about 14 comments an hour on this repository. So that takes about 7 hours with no other comment of a person.
- A round with no failed row reads no comment. A dry run reads no comment. A failed read ends the round with its error. It counts as no failed round of a row, as a failed read of the issue events does.
- The log line that suspends a row says that a comment of a person is also new input. `k8s/README.md` (step 11 of the Roadmap service setup) says the same, with the measured cost.
- The change carries a spec delta on `roadmap-service-limits`, because the Service behavior and the log line are observable.
- The change fits one pull request.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `roadmap-service-limits`: a comment of a person starts a suspended job again. The cost is one request for each lane in a round that only polls and holds a failed job.

## Feasibility

- **The premise holds.** `FailureLedger.suspended` compares the digest of the round with the digest of the last failure. `_round_input` holds the issue events and the round time only (read in `src/devops_cli/roadmap/run.py`). `CONST_ROADMAP_WEBHOOK_EVENTS` has no `issue_comment`. So a comment cannot change the digest today.
- **The design of the issue body does not fit the request budget.** The refine block of the issue reads the open Items updated since the last success of the row. It then lists the comments of each of them. Real system, 2026-11-05: `uv run devops gh api 'repos/dan-petty/devops-cli/issues?state=open&since=2026-11-04T18:24:45Z&sort=updated&direction=desc&per_page=100'` returned a full page of 100 open issues and pull requests changed in 24 hours. The Service polls every `DEFAULT_SERVICE_POLL_INTERVAL_SECONDS` (151 s), which is 24 polls an hour, and `DEFAULT_SERVICE_GITHUB_REQUESTS_PER_HOUR` is 500. One failing row with 100 updated Items would send 100 listings in each poll, which is 2,400 requests an hour. The test scenario of the refine block (three rows with ten Items each) is 33 requests in a poll and 792 in an hour. Both are over the budget. ADR 0016 already measured 775 requests for one read of the comments of every Item.
- **One repository listing fits.** `uv run devops gh api 'repos/dan-petty/devops-cli/issues/comments?since=2026-11-04T18:24:45Z&sort=created&direction=desc&per_page=100'` returned a full first page of 100 comments made in 3 hours 28 minutes. Each comment has `author_association`, `user.login`, `created_at` and `html_url`. Of the 100 comments, 49 are by a person with write access on an issue. 40 are by `devops-cli-service[bot]` and 2 by `dan-petty-release[bot]` (association CONTRIBUTOR each). The first comment of a person is at position 6. A read that stops at the first comment of a person is one request.
- **The read has two bounds, and the cost follows from them.** Without a bound, a window with no comment of a person reads every page. That window is a row that never succeeded, or a quiet repository where only bots comment. GitHub lists 100 comments a page, so each further 100 comments cost one more request. Measured on 2026-11-05: the 600 newest comments (25 hours) held 327 by `devops-cli-service[bot]`, 21 by `dan-petty-release[bot]` and 252 by a person. So about 14 comments an hour come from bots. The session raises `GitHubUnreadError` at `DEFAULT_GH_MAX_PAGINATED_PAGES` (100) pages. That would end every round of a row that never succeeded on a large repository. So the round takes at most `DEFAULT_GH_REST_PER_PAGE` (100) comments, which is one page. A webhook round is the second bound. `uv run devops gh api 'repos/dan-petty/devops-cli/issues/events?per_page=100'` (6 pages, 2026-11-05) held 600 events in 5.4 hours. The events of the kinds `opened`, `edited`, `labeled`, `unlabeled`, `closed` and `reopened` fell in 116 distinct minutes. So a lane has at most about 21 rounds an hour that a webhook starts, on top of 24 polls. The time of a webhook round is already new input for every row, so such a round reads nothing. What stays is the polls: at most one request for each lane in about 24 polls an hour. That is 72 requests an hour for 3 lanes and one repository, 14% of `DEFAULT_SERVICE_GITHUB_REQUESTS_PER_HOUR` (500). All repositories share that budget. `RequestBudget.admit` is hard (no hour holds more than the limit), so these requests cannot pass it. A round that costs more makes the polls slower (`RequestBudget.poll_interval`).
- **The listing tells a pull request from an issue.** `uv run devops gh api 'repos/dan-petty/devops-cli/issues/comments?sort=created&direction=desc&per_page=100'` (2026-11-05): 19 of 100 comments had an `html_url` with `/pull/<number>#issuecomment-<id>`, and the other 81 had `/issues/<number>#issuecomment-<id>`. The `issue_url` of both is `issues/<number>`. The issue asks to refuse the comments of pull requests, and the `html_url` path is the only field of the comment that says it.
- **The GitHub documents agree.** The page `https://docs.github.com/en/rest/issues/comments`, "List issue comments for a repository", says three things. `sort` is `created` or `updated`, `direction` is `asc` or `desc`, and `per_page` is at most 100. `since` filters on the time a comment was last updated. So `since` can only bound the read, and the order is by creation. The row digest uses the creation time of the comment, so an edit of an old comment starts nothing.
- **The session stops when the caller stops.** `GitHubSession.paginate` in `src/devops_cli/github/session.py` is a generator: "A consumer that stops early sends no further request". The test `test_a_consumer_that_stops_after_the_first_item_sends_one_request` in `tests/github/test_github_session.py` pins it.
- **The author is already read.** `IssueComment.author_login` and `author_association` exist (`src/devops_cli/roadmap/store.py`, requirement "Item and IssueRecord carry the author login" of `roadmap-author-trust`, test `test_a_comment_carries_its_authors_login_and_association`). The "Comment author is read" requirement of the refine block needs no new code and no new requirement.
- **The repository is public.** `src/devops_cli/roadmap/trust.py` says so. A comment of any account would let a stranger restart a failed row at will. So only a person with write access counts, as for the `implement: retry` comment.
- **The ledger needs no new field.** `FailureLedger.failed` starts the count at 1 when the input differs from the input of the last failure (`rounds + 1 if failed_on == current or rounds < limit else 1`). The existing test `test_a_job_reports_its_suspension_until_new_input_or_a_success_ends_it` shows it. So `service-failures.json` keeps its format.
- **The failing test first.** `uv run devops ci test tests/roadmap/test_roadmap_suspended_row_comment.py` must fail on the base, before the code of this change exists.

## Existing Tool Considered

The GitHub REST listing `GET /repos/{owner}/{repo}/issues/comments` covers the data. It takes `sort`, `direction` and `since`. The paginating session that the store already uses covers the early stop. The alternatives check of the issue named PyGithub (LGPL-3.0, last activity 2026-10-13, maintained). `Repository.get_issues_comments(sort, direction, since)` of PyGithub covers the same listing (it calls `GET /repos/{owner}/{repo}/issues/comments`; read in the PyGithub documents on 2026-11-05). It is not used. [ADR 0006](../../../docs/adr/0006-github-session-requests-go-through-gidgethub.md) keeps every GitHub request of the process in the gidgethub session, with its budget gate, egress check and request ledger. PyGithub sends its requests over `requests`, outside the egress-checked client and that ledger. The `issue_comment` webhook event is rejected by ADR 0009. The change builds the filter (`is_person_comment`) and the digest field. Cost: about 15,000 tokens to build, about 2,000 tokens for each fix to keep it, and one working day elapsed.
