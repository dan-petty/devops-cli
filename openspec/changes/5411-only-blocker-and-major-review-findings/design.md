# Design

## Decisions

1. **The reviewer gives the severity.** The reply of the pass has a required `severity` for each finding, with the four grades of the golden set. A person graded each golden defect from the same evidence that the reviewer reads, so the reviewer can grade a finding the same way, and the prompt gives one line for each grade with examples from the golden set. A required field goes back once in a reply that lacks it, as an unknown type does.
2. **One check in `open_findings`.** The first review, a later review, the eval, the stage job, the step `fix-plan` and the review of refine all take their open findings from `open_findings`. So the check `f.severity in OPEN_SEVERITIES` there applies the rule everywhere, and no caller filters again. `OPEN_SEVERITIES` holds `blocker` and `major`, the two severities that the recall floor of the eval counts.
3. **A placeholder finding follows the same rule.** A finding that reports a placeholder is open with any type, but it also needs a blocker or a major severity. A placeholder in a plan makes the plan unusable, so the reviewer grades it blocker or major. One rule for each finding is simpler than an exception.
4. **An earlier finding keeps its severity.** `earlier` holds only open findings, so each earlier finding is a blocker or a major finding. A later review gives a verdict and no new severity, and the earlier finding stays open as it is, as it keeps its locator (#5410).
5. **The comment line starts with the severity.** ``- major `false_premise` at ...`` reads as a phrase and keeps the type in its code span. `_FINDING_LINE` reads an optional severity before the type.
6. **An old comment line reads as major.** The open plan pull requests hold stage comments in the old form, and the step `fix-plan` gives the open findings of the last plan comment to the planner and lists them when it dismisses them. Each open finding of the old release kept the draft, as a major finding does now. This reads data that GitHub keeps; it is no second path of the code.
7. **The fix-plan comment lists the advice.** The stage comment already lists every finding that is not open. The comment of `fix-plan` lists the same advice when its plan stays on the branch: a pushed revision, or a plan that loses the label. A `dismissed` head with only minor findings then shows why it lost the label. The comment of a failed or a worse revision lists no advice, because its reviews judged no plan of the branch.
8. **The ceiling is a mean for each good plan.** A count of findings grows with the number of good plans that a run verifies, so a run with `--case` or a stopped run cannot compare with a full run. The mean of the returning findings for each verified good plan compares across runs. A run with no good plan states that the ceiling is not scored, as the floor does with no serious defect. The ceiling is a line of the report and does not change the exit code, as the floor does not.
9. **Refine follows the rule.** The review of refine sends the same pass, so a minor finding no longer refuses an item of a bot. A refusal costs a full round of refine, and a defect that one line fixes does not need one.

## Rejected alternatives

- **A severity for each type** (`criterion_dropped` is major, `other` is minor). The golden set holds each type at more than one severity: `false_premise` has 10 blockers, 27 major, 18 minor and 6 nits. A rule by type cannot tell a false premise of the whole plan from a stale line number.
- **A Jev decision on the severity of each finding.** It costs one call for each finding and a cuts file, and the reviewer already has the evidence. A decision model can screen the severity later, if the eval shows that the reviewer grades badly.
- **A recall that counts only blocker and major findings.** The match of the eval is by type and counts a defect found by any finding. A recall that also needs the severity changes the measure of the floor, and the issue asks for no such change. The pull request reports how many matched serious defects got a blocker or a major finding.
- **No read of the old comment line.** The first attempts of `fix-plan` after the release would then log a warning for each line of the comments of the open plan pull requests, give the planner fewer problems, and dismiss findings with no list.
