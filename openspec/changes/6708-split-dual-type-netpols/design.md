# Design

## Decisions
1. **Split, with the rules as they are.** Each policy with both types becomes `<name>-ingress` (type `Ingress`, the ingress rules) and `<name>-egress` (type `Egress`, the egress rules), with the pod selector, the labels and the rule comments of the old policy. Reason: kube-router enforces two single-type policies correctly (retest of 2026-11-22), so the split alone makes the ingress rules hold. The names say the direction, and the old name stays the prefix, so a search for the old name finds both.
2. **Narrow an in-namespace egress rule only to exact ingress ports.** An in-namespace egress rule with no ports gets ports only when the in-namespace ingress rules of its destinations give the exact ports. That is true in `gitea` only: the one in-namespace ingress rule admits TCP 3000, so the in-namespace egress rule gets TCP 3000. In `argocd`, `llm`, `logging`, `mattermost`, `monitoring` and `otel`, an ingress rule admits every pod of the namespace on every port, so no port list is exact, and the rule stays. In `object-store`, the rule already has the 9 ports of the ingress rule (#6707).
3. **The row refuses the shape, not each policy with both types.** `dual_type_problems` refuses a policy with both types when an egress rule reaches a pod that the policy selects on a port that no ingress rule of the policy admits from all the pods of the policy. Reason: this is the traffic that the controller lets past the ingress rules. A policy with both types whose egress rules reach no pod that it selects, or whose ingress rules admit its own pods on the same ports, gives no such path. The 4 policies of namespace `devops` with both types are of that kind, and they stay.
4. **Which peers reach the own pods.** An egress rule reaches the pods of its policy through: a rule with no `to`; a peer with a `podSelector` and no `namespaceSelector`; a peer whose `namespaceSelector` is empty or does not name another namespace by `kubernetes.io/metadata.name`; or an `ipBlock` that holds a private range (RFC 1918, or the shared range of RFC 6598) after its `except` list. The pod selector of the peer must be able to select a pod of the policy: two selectors are apart only when one label key has two values, or a `matchExpressions` entry refuses the value of the other selector. Reason: the rule fails closed, and kube-router matches an `ipBlock` against pod addresses (`k8s/llm/gateway/networkpolicy.yaml`).
5. **Which ingress rules admit the own pods.** An ingress rule admits all the pods of its policy when it has no `from`, or a peer with no `namespaceSelector` (or an empty one, or one that names the own namespace) and an empty pod selector, a selector equal to the pod selector of the policy, or a `matchLabels` selector that the pod selector of the policy holds. Its ports must cover the port of the egress rule: no `ports` covers each port; a port entry covers the same protocol and port, or a range with `endPort` that holds it. An egress rule with no `ports` needs an ingress rule with no `ports`. Reason: the rule gives credit only when the admission is sure.
6. **The row reads the whole environment tree.** The rule reads each NetworkPolicy document of each YAML file under `k8s/`, as the deploy path check of the module does. The policies that a Helm chart makes are not in the tree. The live query of the acceptance criteria reads them: on 2026-11-22 each of them has the type `Ingress` only.
7. **Fixture checks first.** Five `check_*` functions: two fixtures that the rule refuses (an in-namespace egress rule with no ports, and an ingress rule that limits the peer), one with an `ipBlock` and a rule with no `to`, one set of single-type and aligned policies that the rule accepts, and the scan of the tree.
8. **The checks and tests that name a policy read the new name.** `tests/gate/k8s_checks` (`argo_workflows`, `argocd_apps`, `deploy_stack`, `gateway_database`, `llm_gateway`, `object_store`) and the tests `tests/ai/benchmark/test_k8s_llm_gateway.py`, `tests/ai/test_ai_gateway_portkey.py` and `tests/k8s/test_k8s_argo_workflows.py` look up a policy by name. They read the new policy of the same direction. The rules do not change, so the expected values stay.
9. **Spec deltas.** One ADDED requirement in `k8s-network-policies` for the row. Ten MODIFIED requirements that name a split policy now name the new policy.

## Rejected alternatives
- **Refuse each policy with both types.** Rejected: the 4 policies of namespace `devops` with both types give no path past their ingress rules (Decision 3), and the issue scopes the split to the shape. A split of them changes 4 policies and about 30 references in documents and specs for no change of the paths.
- **Keep both types and give the egress rules the ports of the ingress rules.** Rejected: the controller still runs the egress rules in the chain of the destination pod, so each later egress rule to the own pods opens the same path again. Two single-type policies remove the cause.
- **Narrow each in-namespace egress rule with no ports.** Rejected: in 6 namespaces an ingress rule admits every pod of the namespace on every port, so no port list is exact, and a list would stop paths that work today. Single-type policies are enforced correctly, so the ingress rules of the destinations hold.
- **Leave the `ipBlock` peers and the rules with no `to` out of the row.** Rejected: kube-router matches an `ipBlock` against pod addresses, and a rule with no `to` reaches each pod, so the 4 policies of `argo-workflows`, `cert-manager`, `cloudflared` and `cnpg-system` have the same path on their egress ports. No pod there serves these ports today, but the row must stop the shape before a pod does.
- **A Kyverno or kube-linter custom check.** Rejected: Kyverno adds an admission controller and still needs a custom policy, and kube-linter has no check for this controller behavior, so a custom check is new code too.
- **A change to the controller.** Rejected for this item: the controller is part of k3s and is not in this repository. The private report upstream is a person step of #6708.
