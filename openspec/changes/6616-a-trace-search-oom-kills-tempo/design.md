# Design

## Decisions

- **Set Tempo's own search and concurrency limits in the chart values and keep the 2048Mi memory limit.**: Tempo cuts the bytes of a trace that a search reads, the result count, the search duration and the byte rate, and bounds the outstanding searches per tenant and the concurrent queries; a higher memory limit bounds no read and spends node memory (#6616).
- **Set the limits under `tempo.queryFrontend` and `tempo.querier`, and override no `tempo.config`.**: git_show f209f6c8 showed the removed template render `query_frontend` from `.Values.tempo.queryFrontend` and `querier` from `.Values.tempo.querier`, and `k8s/otel/tempo-values.yaml:2:# The chart builds the Tempo config from these values` says the same, while #1813 removed a `config` override that pinned one Tempo version's layout.
- **Cut every trace above 1000000 bytes when Tempo pushes it through `tempo.global_overrides.max_bytes_per_trace`, and bound a read of a trace by id with the querier concurrency limit of 4 and the 168h retention, never with a byte limit on the read.**: The per-tenant trace size cut applies at ingestion, so it cannot bound a trace that the store already holds: such a trace stays readable for `k8s/otel/tempo-values.yaml:32:retention: 168h`. Tempo offers no byte limit on a read by id in the values the chart takes, and `querier.max_concurrent_queries: 4` bounds how many reads hold memory at once.
- **Guard the search bound in a check of the `k8s` row, which needs no registration.**: Ten outstanding searches of fifty results of 1000000 bytes hold 500000000 bytes, under the 1073741824 bytes of half of the `2048Mi` limit; `tests/gate/runner.py:45:if name.startswith("check_") and function.__module__ == module.__name__` runs each function named `check_` of every module that `tests/gate/runner.py:32:def _check_modules(package: ModuleType) -> list[ModuleType]:` imports, so a new module joins the row.
- **Compare the restart count of pod `tempo-0` before and after the ten searches and the trace reads, and expect no increase.**: The issue records that the pod already restarted twice, "The restart count went to 2.", so a live check that expects a count of 0 would fail after the change; the criterion of the issue is that the count does not increase.
- **Keep the pod's restricted security context and the chart pin at 3.2.1.**: The `otel` namespace enforces PodSecurity restricted (#1627) and `k8s/argocd/apps/tempo.yaml:13:targetRevision: 3.2.1` fixes the chart, so the change alters no other field of the file.

## Rejected alternatives

- **Set only `max_bytes_per_trace` on the search path.**: It leaves the result count, the search duration, the byte rate and the concurrency unbounded, so ten reads can still exhaust the memory limit; the alternatives check of the issue records the same gap for the tool alone.
- **Add a proxy in front of Tempo that refuses a large read.**: It adds code to build and keep where Tempo ships the search limits, the per-tenant trace size cut and the concurrency limit, and the alternatives check of the issue gives the verdict in-use for grafana/tempo.
- **Raise the memory limit above 2048Mi.**: `k8s/otel/tempo-values.yaml:39:memory: 2048Mi` is the budget that the plan keeps, and a higher limit bounds no read.
- **Override the whole `tempo.config`.**: `k8s/otel/tempo-values.yaml:2:# The chart builds the Tempo config from these values`, and #1813 removed exactly such an override because it pinned one Tempo version's layout.
- **Patch a separate ConfigMap with the Tempo configuration.**: It adds a second source of Tempo configuration, and git_show f209f6c8 shows the chart already builds `query_frontend`, `querier` and `overrides` from its own values.
- **Claim that the per-tenant trace size cut bounds a read of a trace by id.**: The model review found the claim false: `tempo.global_overrides.max_bytes_per_trace` applies when Tempo pushes a trace, and a trace that the store already holds stays readable for `k8s/otel/tempo-values.yaml:32:retention: 168h`, so the plan bounds that read with the concurrency limit of 4 and the retention instead.
- **Write a pytest module that asserts the values of the Helm file.**: No test asserts a value of a manifest; the `k8s` row of `uv run devops ci` is the proof, as `tests/gate/k8s_checks/telemetry_resource.py:17:from tests.support.paths import REPO_ROOT` shows for a check of the `k8s` tree.
- **Bound a trace read by id with a byte limit of the querier.**: No input names such a key: git_show f209f6c8 renders the `querier:` block from `.Values.tempo.querier`, and search_code `queryFrontend` returned `No match.` because the chart is no file of the repository, so the plan sets no key that no input shows.

## Security

The change crosses no trust boundary: it sets limits in the Helm values of the trace store and adds no host, address, secret or account. A person must confirm on the cluster that the rendered Tempo configuration shows the six search and concurrency limits and the trace size cut, and must read the restart count of pod `tempo-0` before and after the ten searches and the trace reads of the issue: a read that still stops the pod is a defect of this change. The check `check_the_tempo_query_limits_stay_under_the_memory_limit` fails when a limit rises above half of the memory limit, when the querier admits more queries than the outstanding-search limit, when the trace size cut is missing, or when the memory limit changes, and `uv run devops ci --check --only k8s` fails with it.
