# Design

## Decisions

- **A row of the Service reads the releases, and no workflow comments.**: The "Live since" half needs the Deployment and the CronJob in the cluster. A job of `release.yml` has `permissions: {}` and no kubeconfig, and only the Service pod has a token for the API server (`k8s/devops/roadmap-service/role.yaml`). A workflow for the first half and a row for the second half would need the same release-to-issue code twice and two marker rules. A re-run of the failed jobs of `Release` (`RELEASE_CYCLE.md`) would post the first half again. One row has one code path, one marker and one ledger.
- **The row polls the list of releases, with no webhook.**: The roadmap consumer takes the `issues` event only (`CONST_ROADMAP_WEBHOOK_EVENTS`, Feasibility 5), and ADR 0003 makes the poll the source of truth. A `release` event would need a change of the repository hook, and only a person changes that. The row is due every 10 minutes. Image Updater checks the registry every two minutes (`k8s/README.md:1013`), so a roll is seen within the interval plus the Argo CD sync.
- **The pull requests come from the release body, and the issues from the body of each pull request.**: The release body names `(#N)`, and each `N` is a pull request (Feasibility 2). The changelog text `closes [#M]` named 6 of 26 closed issues of 12 releases, and the bodies of the pull requests named all 26 (Feasibility 3). `pull_form` already requires a `Closes #<issue>` line in the body of every pull request that `devops pr create` opens, so the body is the written rule of the project. `GET issues/<N>` gives the body of a pull request and the field `pull_request`, so the same request tells an issue from a pull request. GraphQL `closingIssuesReferences` is not used: it is not available in the session that wrote this plan, so the plan could not test it, and the REST body needs no new query form.
- **A comment is the record, and the ledger is a cache.**: The marker in the comment decides if a comment exists. The ledger (`release_comments.json` beside `schedule.json`) holds, for each release of the window, two flags: the `Released in` pass is done, and the `Live since` pass is done. It exists because a round without it costs 227 requests an hour at the release rate of 2026-11-02, and with it 6 (Feasibility 4). A flag is set only after every issue of the release holds its comment. A missing ledger reads as empty. A ledger that exists and cannot be read fails the row and names the file, as `read_intake_record` does (`src/devops_cli/roadmap/run.py`), because a silent empty read would hide a full disk or a bad write.
- **The window is 12 hours and the list is 30 releases.**: At 12 releases a day, 30 releases cover more than the window. A release older than 12 hours leaves the ledger and gets no comment. A Service that is down for more than 12 hours misses the releases of that time. That is the price of a bounded first run: a first run with no ledger comments on about 6 releases, not on 100. The cap and the window are constants with a class in `tests/roadmap/test_roadmap_limit_classes.py`.
- **The `Live since` time is the time of the round that first sees both digests.**: Argo CD sets no event that the Service can read, and a rollout condition of the Deployment would need more reads and tells only about one of the two images. The comment says the time in UTC to the minute. The error is the interval of the row, 10 minutes, plus the sync time.
- **Both images must match, and a newer rolled release covers an older one.**: The issue says "the Service and runner image digests of that release". `latest` moves with each release (Feasibility 6), so the cluster never runs the digest of `v0.46.1` after `v0.47.0` rolled. A rule that waits for the exact digest would leave an older release without its second comment for ever. The row takes the newest release of its list whose two digests the cluster runs, and treats it and every older release as live. A release that a failed read leaves unknown is not treated as live.
- **The Deployment is read through `ClusterJobs.deployment_digest`, with `get` on one named Deployment.**: `ClusterJobs.template_digest` already reads the runner CronJob the same way, with the same fake (`FakeCluster` in `tests/support/fakes/kubernetes.py`, used by `tests/k8s/test_k8s_cluster_job_api.py`). The Role rule names `roadmap-service`, so it grants no other Deployment. The object holds no secret value (Feasibility 7).
- **The registry is read with `tag_digest` and a shared client.**: `tag_digest` is the function that `devops argo cd apps status` uses through `check_pins` (`src/devops_cli/argo/image_pins.py:84`), and it reads the digest as an anonymous client. The client is `new_http_client(level=EgressLevel.PUBLIC)` with `DEFAULT_HTTP_TIMEOUT_SECONDS`, as `_check_image_pins` in `src/devops_cli/commands/argo.py:396-402` builds it. The row reads two tags for each release in the window that is not live yet, and it stops at the first release that is live (newest first).
- **A failure of the cluster or the registry fails the row after the `Released in` pass.**: The `Released in` pass needs only GitHub, so a cluster outage must not hold it back. The row collects the failed releases and raises `RoadmapRunError` once, naming them, when both passes are done. The failure ledger of the Service then counts the round (`_count_failure` in `run.py`). A catch that logs and goes on would hide a broken Role.
- **The time and the version text are fixed strings in `MESSAGES.roadmap`.**: The issue gives the words `Released in <version>` and `Live since <time>`. A test asserts the first line of each comment, and the marker makes the comment findable.

## Rejected alternatives

- **A job in `release.yml` that runs when `release_created` is true.**: It would know the tag from the output of the action and run once. But it cannot read the cluster (`permissions: {}`, no kubeconfig), it needs a second mechanism for "Live since", and a re-run of failed jobs posts the comment again unless the job also checks for a marker. See the first decision.
- **`apexskier/github-release-commenter` or a similar action on the `release` event.**: It covers one half, comments on pull requests too, and adds third-party code with `issues: write` (proposal, Existing Tool Considered).
- **Parse `closes [#M]` from the changelog text.**: It misses 20 of 26 issues in 12 releases (Feasibility 3). It also ties the row to the format that release-please writes, which ADR 0013 tells agents to leave alone.
- **GraphQL `closingIssuesReferences` of each pull request.**: `release.yml` uses it for the urgent-fix step, so it works in Actions. It is not available in the session that wrote this plan, so the plan could not test it, and the store has no query form for it. The REST body read returns the same numbers for the 26 issues of the probe.
- **Read the commits between two tags and the pull requests of each commit.**: It finds the pull requests of hidden types (`docs`, `test`, `ci`, `chore`), but it costs one `compare` read and one `commits/<sha>/pulls` read for each commit. A release of the probe had 6 pull requests, so about 12 requests more for each release. The issue says "in its changelog", and the changelog is the list of what the owner wants to see. An issue closed by a hidden type gets no comment, and the plan says so.
- **No ledger, only the markers in the comments.**: It costs 227 requests an hour at the rate of 2026-11-02, 45% of the budget (Feasibility 4).
- **A ledger on the issue of the release or in a label.**: A label per release adds one label for each of 12 releases a day, and the project keeps labels for fields (ADR 0016). The data directory already holds `schedule.json` and `intake.json` for the same kind of fact.
- **Read the image of the running pod (`imageID`) from the pods that the Role already lists.**: The Role grants `list` on pods, so no Role change would be needed. But `imageID` is the image id that the container runtime reports, and its form depends on the runtime. I did not verify that it equals the digest of the tag. The Deployment image is the value that Image Updater writes, and `devops argo cd apps status` already compares that value with `tag_digest`.
- **Watch the Argo CD Application instead of the Deployment.**: The Role of the Service is in namespace `devops` only, and a new right in namespace `argocd` is wider than one named Deployment in `devops`.
- **A scoped update on a webhook event.**: ADR 0017 and `SCOPED_UPDATES` run one item at once on a delivery. Releases are not in the events that the consumer takes, and a poll at 10 minutes is enough for a comment.
- **Split "Live since" into its own issue.**: It would need the same release-to-issue code, the same marker and the same ledger, so the second issue would copy half of the first or wait for it. Both halves share the code, and the group of the second half (groups 3 and 4) is the smaller part. If a person splits the issue, groups 3, 4 and 6 move with the second half.
