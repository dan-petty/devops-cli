# Proposal

## Why

Issue #3032: a Job that stops leaves a log of tool lines such as `Tool call: shell, program other, refused.` and a stop comment with one reason. A person cannot see what the agent tried, which model call failed, or how many tokens each step used. The stop comment on #2735 holds "Stopped at group 1.", one reason and a diff, with no token count and no attempt count (Feasibility 1). The issue asks for a trace of each run that the job keeps, that `devops roadmap explain <issue> --trace` prints, and that the stop comment and the pull request comment sum up in a table.

## What Changes

- New module `src/devops_cli/roadmap/implement_trace.py`. `ImplementTrace` collects the events of one run in order: `model` (model name, tokens in and out, seconds), `tool` (tool, program, digest of the masked argument, outcome `ok`, `refused`, `retry` or `failed`, and the reason of a retry), `check` (command, exit status) and `retry` (the reason of a repair round or of a send again). Every text goes through `bounded_text` and a new `mask_private_hosts`. It encodes the events as JSON and drops the oldest ones above `CONST_ROADMAP_IMPLEMENT_TRACE_CHARS` characters (8,192), with a count `dropped`. It also holds `summary_table`, the one renderer of the table below.
- `src/devops_cli/security/sanitizer.py` gets `mask_private_hosts`, built on `PRIVATE_HOST_PATTERNS`. `mask_secrets` leaves a private host as it is (Feasibility 4).
- `ToolCallLog` (`implement_tool_log.py`) adds the `tool` events: it is the one place that knows `refused` from `retry`. `implement_step.py` adds the `model`, `check` and `retry` events and takes the trace as an optional argument of `run_step` and `run_fix_step`.
- The job (`implement_run.py`) owns the trace of the run, adds the events of its own commands (documents, archive), of the scoped checks and of the checks of the pull request, clears `implement.trace` when a run starts, and writes it with each record of a passed group, with the stop and with the ready mark. `ImplementRecordKey.TRACE` is the new key.
- `devops roadmap explain <issue> --trace` prints the trace of the last run and no verdict. It reads the one issue.
- The stop comment gets a table of the steps (step, attempts, tokens in and out, last failing command). The comment on the pull request replaces its line for each step with the same table. `_outcome_line` and the template `implement_pull_comment_line` are deleted.
- The change carries spec deltas, because a command option, a comment and a record key are observable (`openspec/config.yaml`): `roadmap-implement-step` (events), `roadmap-implement-job` (record, comments), `roadmap-explain` (the option) and `secret-masking` (private hosts).
- Not in this change: the Job artifact of the issue text. No artifact store exists (Feasibility 8). #3105 plans one and waits for the go verdict of ADR 0008.
- The change fits one pull request: ten groups, none with more than six files. The inputs of each group measure from 22,738 to 38,892 tokens against the budget of 40,000 (Feasibility 12). Groups 4 and 9 are the closest to it. If the implement job stops one of them on the budget, split it.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `roadmap-implement-step`: A step records its model calls and its tool calls, A step records its checks and its retries, Every text of an event is masked
- `roadmap-implement-job`: The job keeps the trace of its run, The stop comment shows a table of the steps, The table cuts its rows and its cells, The job record (MODIFIED), The comment on the pull request shows the repair rounds and the scoped checks (MODIFIED)
- `roadmap-explain`: The trace option prints the trace of the last run, The command makes no model call and no write (MODIFIED)
- `secret-masking`: A private host name is masked

## Feasibility

Checked on `origin/main` 46ab3960, on 2026-11-02, in a plain clone, with the commands below.

1. The gap is real. `git grep -n "implement.trace\|ImplementRecordKey.TRACE" -- src tests docs` prints nothing. The template of the stop comment is `"{marker}\nStopped at {step}.\n\n{failure}\n\nReason:\n\n{reason}\n\nLast message of the agent: {last}{diff}..."` (`src/devops_cli/lang/en/messages.py:2570`): no tokens, no attempts, no command. The real stop comment on #2735 reads `Stopped at group 1. Reason: UnexpectedModelBehavior: Tool 'edit_file' exceeded max retries count of 5 ... Refused commands: 0. Other retries: 6. Last message of the agent: ...`, with nothing else (`gh api repos/dan-petty/devops-cli/issues/2735/comments`).
2. `RunTrace` does not cover an implement run. `RunTrace.absorb` reads only the `ModelResponse` and `ModelRequest` parts of the messages (`agent_run.py:169-176`), so a check run, a refusal by policy and a retry reason never reach it. `ToolCallRecord` holds the argument as masked text of 200 characters (`agent_run.py:137-141`), and the Job log writes no argument on purpose (`implement_tool_log.py` module text: "an argument can hold a path or a secret"). `RunTrace` is used by the stage and refine runs only (`git grep -n RunTrace -- src`: `stage.py`, `stage_toolbox.py`, `refine_investigation.py`). `mask_secret_named_values` hides `api_key` in an argument: `_argument_json(ToolCallPart('shell', {'command': 'curl https://db.corp.internal', 'api_key': 'hunter2'}))` printed `{"command":"curl https://db.corp.internal","api_key":"<redacted>"}`, and its SHA-256 starts `afc5c840d641`.
3. A model call has a duration. A scratch run of a pydantic-ai 2.59.0 agent on a `FunctionModel` that sleeps 0.2 seconds printed `ModelRequest 2026-11-02 18:00:33.616862+00:00` then `ModelResponse 2026-11-02 18:00:33.821452+00:00 function:fn: RequestUsage(input_tokens=51, output_tokens=4)`: the reply time minus the request time is 0.205 seconds, and the reply holds `model_name`. Not verified: the same on a streamed reply of a real provider.
4. `mask_secrets` does not mask a private host. `mask_secrets('curl https://db.corp.internal/x 127.0.0.1 and token ghp_... Bearer abcdefghijklmnopqrstuvwxyz0123')` printed `curl https://db.corp.internal/x 127.0.0.1 and token <masked-github-token> Bearer <masked-token>`. `re.sub('|'.join(PRIVATE_HOST_PATTERNS), '<host>', ...)` printed `curl https://<host>/x <host> ...`. The same pattern leaves `example.com 198.51.100.7 config.local_value` as it is. `PRIVATE_HOST_PATTERNS` (`sanitizer.py:352`) is used only as scrubbing patterns of Logfire (`telemetry/logfire.py:213`), so the issue needs one small function and not a new filter.
5. Two ratchets fail at once for the new key and the new limit. In a scratch edit I added `TRACE = "implement.trace"` to `ImplementRecordKey` and `CONST_ROADMAP_IMPLEMENT_TRACE_CHARS = 8192` to `constants.py` and ran `pytest tests/invariants/test_roadmap_workflow_doc.py tests/roadmap/test_roadmap_limit_classes.py`. Output: `AssertionError ... 'record key implement.trace is missing'` and `At index 0 diff: ['CONST_ROADMAP_IMPLEMENT_TRACE_CHARS'] != []` (2 failed). The edit is reverted.
6. The bound fits the record. A scratch script built 61 events in the compact form (30 `model`, 30 `tool`, 1 `check`): 4,776 characters, 78 characters an event, so 8,192 characters hold about 105 events. `encode_job_record` turned a 4,674-character value into a 5,992-character block (factor 1.28, `store.py:557`), so the worst case is about 10,500 characters. The body of #3032 is 6,871 characters and its record block 709, against the 65,536 characters of an issue body. A run of 138 requests, as #2175 made (#3098), keeps the newest part of its events and counts the rest in `dropped`.
7. The record is written without a new request. `_ItemRun._record` runs after each passed group (`implement_run.py:466`) and calls `set_marks`, one write of the issue. The Service ends a Job that stalls by setting its deadline (`implement_deadline.py:17-19`), and a Job that is killed does not reach `stop()`, so the trace must be in the record after each group and not only at the stop.
8. No artifact exists. `git grep -n -i artifact -- src/devops_cli/roadmap docs/roadmap k8s/devops` prints nothing. #3105 is open (`status/new`); its comment of the Service says the refine cannot set it Ready until the go verdict of ADR 0008 on #1535 exists. #1535 is closed with 3 comments and none holds a verdict.
9. `explain --trace` needs one read. `GitHubRoadmapStore.item` is "one read of its issue" (`github_store.py:597-601`), and `ImplementRecordKey` values are keys of `Item.job_record` (`store.py:287`). `explain_item` also reads the heads of `origin` and the plans of the default branch (`explain.py`, `read_remote_heads`, `read_planned_changes`), which a trace read does not need.
10. Spans cannot hold this trace. The runner reaches the OTLP collector (`k8s/devops/networkpolicy.yaml:38`) and sets `OTEL_SERVICE_NAME` (`k8s/devops/cronjob-runner.yaml:66`), so the issue text ("a dependency and a collector") is wrong for this repository. But Tempo keeps a span for 168 hours (`k8s/otel/tempo-values.yaml:32`), and a Blocked item waits for a person without a bound. `devops telemetry profile --trace-id` needs the id of a trace and the Tempo URL (`commands/telemetry.py:360-382`).
11. The neighbours were read. `classify_failure` reads `FailureEvidence(text, exit_status, check, agent)` (`failure.py:90`) and the stop already holds the class and `repair_rounds` (`implement_run.py:755-800`); the trace changes neither. `_StopError.check` names the failed check of the pull request (`implement_run.py:159`), which the table uses when no `check` event failed.

12. The groups fit the budget of a step. I measured them as `measure_groups` does (`stage_change.py:655`): the tokens of the issue and of the three documents of this change (11,466), the text of the group, the files that its tasks name, each packed as the step packs it, and the rules sections. `count_tokens` fell back to its character heuristic here (no tiktoken cache). The result for groups 1 to 10: 26,841, 36,687, 35,245, 38,892, 32,186, 35,122, 35,050, 31,764, 38,633 and 22,738 tokens. The files that a group creates are not in these numbers. Before the split, groups 4 and 7 measured 44,799 and 45,916, so they were split into groups 4 and 5, and 8 and 9.

Not verified: a real run of the new code (this is a plan); the duration of a streamed reply; the number of events of a real run.

## Existing Tool Considered

OpenTelemetry is already in the project (`get_tracer`, the collector, Tempo), and spans cover a trace of a run. They cannot be the store: Tempo drops a span after 168 hours, `explain` would need the Tempo URL and a trace id kept in the record, and the stop comment needs the table from data that the job holds at that moment. pydantic-ai can instrument its own model and tool calls, with the same sink and the same limit. Logfire is a hosted viewer and is not a store a person can read from `devops roadmap explain`. No open library writes a bounded event list into an issue body, a comment table and a masked record, so the change builds it, on `bounded_text`, `mask_secret_named_values`, `PRIVATE_HOST_PATTERNS`, `ToolCallLog`, `logged_reason` and `ScopedResult`.

Cost to build: about 150,000 tokens (ten groups of about 15,000 tokens: a masking function, the trace module, the events of a step, the record key, the job writes, the table, the two comments, the read of a trace, the option, the documents) and about 5 hours with two CI runs. Cost to keep: about 4,000 tokens each quarter. Cost to fix one miss: about 15,000 tokens. The change deletes `_outcome_line` and `implement_pull_comment_line`.
