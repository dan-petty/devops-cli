# Design

## Decisions

- **The dependency layers build from a lock export, not from `uv.lock`.** The uv Docker guide (intermediate layers) installs the dependencies from `uv.lock` before it copies `src/`. But each release changes the project version in `pyproject.toml` and in `uv.lock` (`release-please-config.json` names `uv.lock` in `extra-files`), so that layer builds again on each release. The `lock` stage runs `uv export --locked --no-emit-project` for the runtime and the dev requirements. Its output holds no project version, and BuildKit keys the cache of a `COPY --from` on the content of the copied files, so the stages that copy the two files keep their cache when only `src/` and the version change. The two exports carry the hash of each file, and the installs run with `--require-hashes`, as the `service-image-test` job of `ci.yml` already does.
- **The heavy layers sit in cached stages under each final stage.** `ci.yml` and `release.yml` build `service` and `runner` with `no-cache-filters`, so a build runs each instruction of those stages again, and a layer that it makes again is a new layer for each node. `runner-deps` and `service-deps` hold the apt packages, the Node runtime, gh, the user, the git configuration, the tool directory and the venv. The final stages build on them and add only two layers: the apt upgrade and the project. The final stage keeps `apt-get upgrade` with no cache, so the image still takes each security update, and the cached stages do not change that.
- **The project comes from `builder` in one `COPY --parents`.** The final stages copy the `devops_cli` package, its dist-info and `/app/.venv/bin/devops` to the same paths. The `RECORD` of the installed project lists these three paths and no other. The Service image holds no uv (the smoke test checks it), so it cannot install the project itself, and the Service test asserts that `devops_cli` loads from `/app/.venv/`.
- **The tools of `tools.lock` stay with `devops install-tools`.** OpenSpec (in `builder`) and promtool (in `runner-tools`) need the installed project, so they build again after a change of `src/`. Their files are the same, and the copy of the tool directory into `runner-deps` and `service-deps` keys its cache on the content, so it keeps its layer. #4361 moves these installs to native steps.
- **Each uv install mounts the uv cache of root.** The uv guide recommends a cache mount. No layer holds the cache, so the runner stage no longer deletes `/root/.cache/uv`, and the builder layer loses the cache that it held. The installs use `--link-mode copy`, because the cache mount is another file system.
- **npm stays in `builder`.** Only the OpenSpec install needs npm. `runner-deps` copies the `node` binary alone, so the runner image never holds npm, and no stage must delete it.

## Rejected alternatives

- **`uv sync --locked --no-install-project` from `uv.lock`, as in the uv guide.** Each release changes the project version in `uv.lock`, so the dependency layer builds again on each release, and the nodes pull it again. The build C of the measurement (a version change and a `src/` change) shows the dependency layers as kept with the lock export.
- **The whole venv in one layer of the final stage.** It is the cause of the 0.9 GB that each release changes in the Service image (`COPY --from=builder /app/.venv`).
- **The dependency installs in the final stages.** The final stages are never cached, so the installs would run on each build and give new layers.
- **A wheel directory with `UV_FIND_LINKS`.** `uv sync --locked --offline` does not read the find-links for a locked package. It stops with "Network connectivity is disabled, but the requested data wasn't found in the cache", with uv 0.13.6. `--no-index --find-links` resolves again for every platform and fails on `pywin32`. A read-only uv cache in the image fails with "Could not acquire lock ... Read-only file system". #4814 takes the offline venv, with a uv cache that the pod copies into its writable cache (measured: copy 9 s, offline sync 2 s).
- **`crane manifest` to measure the layers.** `crane` is not in `tools.lock`, and #2610 rejected a pin for it. The measurement compares the layer digests of `docker image inspect` and the sizes of `docker history`.
- **A pre-pull DaemonSet.** It treats the symptom. The issue keeps it for a pull that stays over 10 s after this change.
