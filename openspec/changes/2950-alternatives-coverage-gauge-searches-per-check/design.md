# Design

## Decisions

- **Record the two gauges in the Service row, at the start of the round, from a `Coverage` that `select_items` returns.**: The row calls `apply_alternatives` only `if plan.has_writes` (`run.py:616`), so a round with nothing to write would leave the last value. The start of the round also needs no guess about which writes succeed, since `apply_alternatives` skips a check when a person changed the body (`_unchanged_since_read`, `alternatives.py:871`). A gauge that is up to one round old (719 minutes) at the end of a round is enough for an alert that waits 3 days.
- **Count an item as "with no check" when the check can take it and the job record has no check time.**: `_is_eligible` (`alternatives.py:483`) takes an open item with Status New or Ready and a trusted author. An item that is In Progress or from an author with no write access never gets a check, so counting it would keep the alert up for ever. An item in the retry delay has no check, so it counts, although `select_items` skips it today.
- **Send the age gauge only when an eligible item has a check.**: With no check there is no age. The value 0 would read as a fresh check, and the alert on unchecked items already covers that case.
- **Make the Service row the only sender of the two gauges.**: The command `devops roadmap alternatives` runs on a workstation with another `job` label, and the alert selects `job="roadmap-service"` (the rule test requires it of the group). A second sender would put a workstation value beside the Service value for one repository on the dashboard.
- **Observe the histogram for every written check, and use `len(check.queries)` as the value.**: The value counts the searches that the tools ran, also a search that Firecrawl refused (`alternatives.py:259` appends before the call). A skip-class check observes 0 under `not-applicable`, and the model cannot give that verdict (`_refusal`), so the label separates the checks that could not search from the checks that did.
- **Write the alert as `sum by (repo) (last_over_time(<gauge>[7d])) > 0 and on() (sum(<searches in 3d>) or vector(0)) == 0`, with the count of searches in the form of `_window_count`.**: The three parts each fix a failure that I ran in promtool 3.15.1. `sum by (repo)` and `on()` give the two sides the same label set. `or vector(0)` makes the case with no search series fire. The `_window_count` form counts the first value of a series that starts in the window; plain `increase()` fired for a new `ok` series that held 3 searches. The 7 days of `last_over_time` keep the last known gauge when the row stops, which is the failure of 2026-10-30; a gauge sample 100 hours old fires and one 180 hours old does not.
- **Add the alert to the group `roadmap-service-activity`, and wait 1 hour.**: The group comment says it covers "its paid web search" (#2475), and its tests pin the rule list, so one rule joins an existing fixture file and an existing constant. The wait of 1 hour keeps one evaluation with a stale gauge from firing; the gauge changes twice a day.
- **Put the three panels in a row "Alternatives Check" of `devops-cli.json`.**: The file already holds the rows of the Service's GitHub requests, and the spec `metric-instruments` already holds a panel of this dashboard ("Embedding Cache Hit Share"). #3171 edits `project-metrics.json`, so the two plans change different dashboard files and their panel ids and `gridPos` values cannot collide.
- **Show the searches with `histogram_avg` and `histogram_count` of `increase(...[1d])`, by verdict.**: The existing review-duration panel reads its native histogram the same way (`devops_cli_review_duration_seconds` in `devops-cli.json`, panel 3), and `test_every_series_is_read_through_the_function_of_its_kind` accepts `increase(` for a histogram.

## Rejected alternatives

- **The alert expression of the issue, `increase(devops_cli_firecrawl_searches_total[3d]) == 0 and devops_cli_roadmap_alternatives_unchecked_items > 0`.**: I ran it in promtool 3.15.1 with the real label sets (`result="402"` on the counter, `repo="example/app"` on the gauge, 150 hours of samples). It gave no alert, because `and` needs equal label sets and the sets differ. It also reads one series per `result`, so a flat `402` series hides an `ok` search, and it returns no data when no series exists.
- **`sum(increase(devops_cli_firecrawl_searches_total{job="roadmap-service"}[3d])) or vector(0)` for the count.**: In promtool a new `ok` series that starts 10 hours before the evaluation and holds 3 searches gave `Labels:{alertname="Incr", repo="example/app", severity="warning"}`: a false alert. `increase()` does not count the first value of a series (#2505).
- **An alert on the sum of the new histogram, `histogram_sum(sum(increase(devops_cli_roadmap_alternatives_searches[3d])))`, so that a search of refine does not hide a check that does not search.**: The histogram gets an observation only for a written check. A round whose checks all fail after they searched writes none, which is the failure of 2026-10-30 (`raise_for_failed_checks`, `alternatives.py:918`), and the alert would then say that the check does not search. The counter sees every search. The panel "Alternatives Searches per Check" shows the checks alone, and the issue asks for the alert on any Firecrawl search.
- **Record the gauges in `apply_alternatives`.**: It runs only for a plan with writes (`run.py:616`), and the check being off or having nothing to do would keep an old value.
- **Count every open item, or every item without the `alternatives.checked_at` mark, for the unchecked gauge.**: `store.items()` holds items that the check never takes (In Progress, untrusted author). The gauge would not reach 0 and the alert would never clear.
- **A new rule group `roadmap-service-alternatives`.**: A group needs its own fixture file, a constant and an entry in `ROADMAP_SERVICE_GROUP_TESTS` (`test_k8s_monitoring_alerting.py:78`) for one rule. The existing group has the three pieces. The cost is a MODIFIED requirement, which the spec delta carries.
- **Put the panels in `project-metrics.json` beside the items panels, as #3171 does.**: Two plans would add panels at the same `gridPos` in one file. The Firecrawl searches are Service activity, which `devops-cli.json` already shows.
- **Wait for a Roadmap dashboard (#3069, #3240, #2968).**: None exists on `main` (`grep -il roadmap k8s/monitoring/dashboards/*` finds no dashboard with that title), and each of those issues is open. This change would block for an unknown time.
- **Fix the stale path `tests/test_telemetry_instruments.py` in `instruments.py` and `generator.py` in this change.**: It is a comment and a generated sentence. The change would touch the generator and the generated `docs/TELEMETRY.md` for a reason that is not the issue.
