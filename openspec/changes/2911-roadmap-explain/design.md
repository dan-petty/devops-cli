# Design

## Decisions

- **The jobs return the reason, and explain reads it.** Both judges already return the text of the first rule that fails. A second copy of the rules in `explain` would drift. So `explain` calls the selection of each job and reads the result. For the implement job this is `plan_implement`, which calls no model. For the stage job it is `read_stage_selection`, a function cut from `plan_stage`: it holds everything `plan_stage` does before it asks the model, and `plan_stage` calls it.
- **One walk, three outcomes.** `walk_named` is the one loop of both jobs. It judges the open items that the filter names, highest priority first, and returns the items taken (up to the limit), the items left out with their reasons, and the numbers of the items that pass every rule but come after the limit. After the limit, the walk judges no item, as before, except the item `probe` names. `explain` sets `probe` to its issue, so a run for the plan keeps its cost, and `explain` pays for the items ahead of its issue and for its issue only.
- **The order is the order of the code.** The issue lists the rules as: not an item, filter, owner, tracker, stop, plan and branch, budget, limit. The code checks them as: not an item or closed, filter, then (stage) Status, claim, `needs-split`, tracker, author, title, dependency, plan on the default branch, held, secret, recorded split; (implement) Status, claim, route, author, stop, branch, pull request. A second order for `explain` would name a rule that the job does not name first, and that is a wrong answer. So `explain` keeps the order of the code and the position of the filter and of the limit that the issue gives. The tracker rule exists in the stage job only: an implement item is already planned, and a tracker gets no plan.
- **The filter reason is a method of the filter.** `StageFilter.mismatch(item)` returns the text for the first family, in the order of the filter, whose labels the item lacks. `matches` is `mismatch is None`, so there is one rule. The text names the family, the values the filter takes and the value the item has, for example "The filter takes effort low. The item has effort medium.".
- **Texts live in one place.** The two reasons that stage and implement both wrote ("not an item", "closed") become `item_left_not_item` and `item_left_closed`, next to `item_left_claimed`. The new reasons are `item_left_filter` and `item_left_limit`. `explain` has no reason text of its own, only its labels and the words `yes` and `no`.
- **`--why` is a separate section.** The items that matched no filter are not "left out by a rule": they never reached a rule. A new field `unmatched` on `StagePlan` and `ImplementPlan` holds them, and a heading "Matched no filter" prints them. `stage_results` counts `left_out` as skipped for the metric `devops_cli_roadmap_stage_total`. Putting the unmatched items in `left_out` would add every open item to that metric when someone runs `--plan --why --confirm`. The default output does not change.
- **Not an item or closed is one answer for both jobs.** `explain` prints the same reason on both lines. The "yes or no" is per job, as the issue asks.
- **The limit is judged last.** An item that passes every rule is `no` only when the limit is filled by items ahead of it. The reason names the limit. The default limit of each job is the limit the Service uses: `roadmap.stage.limit` for stage and `DEFAULT_ROADMAP_IMPLEMENT_LIMIT` for implement. `--limit` replaces both.
- **The ledger is not read.** `FailureLedger` counts failed rounds per repository and job, in the memory and in a state file of the Service. It holds nothing per item, and a workstation cannot read it. The stop of an item is its record (`implement.stopped`, `stage.needs_split`), and `explain` reports it with the text of the job. The Service already shows a suspended job on `/metrics`.
- **A group over the budget comes from the record.** Only the model can find a first group over the budget, and `explain` calls no model. A stop that an earlier run recorded is `_recorded_split` of the stage judge, so `explain` reports it with the text of the job.
- **The dry-run class is `request-plan`.** `explain` reads GitHub and git. `--dry-run` makes no request and lists them. `explain_requests` builds the list from `implement_requests` (the clone, the listing, the branch heads, the change folders, the tasks, the authors and the pull request) and the read of an open blocker (stage). It lists no write.

## Rejected alternatives

- **A second rule list in `explain.py`.** Two lists drift: the next rule added to a judge would not show in `explain`, and `explain` would say `yes` for an item the job leaves out. The issue asks for no duplication.
- **A `Verdict` object with a rule code from every check.** The jobs and the tests use the text only. A code per rule adds a type and a mapping in 20 places and gives no output that the text does not give. The text is the one source (rule 8 of AGENTS.md: write as merged).
- **Put the unmatched items in `left_out`.** It changes the default output and the metric (see above).
- **Judge every item after the limit.** The plan would read more branches and pull requests at each round of the Service. The walk judges one item past the limit, the `probe`.
- **Read the ledger file of the Service.** It is on the volume of the Service. A read means a touch of the cluster, and the ledger holds no item.
- **Call the model to find a group over the budget.** The issue forbids a model call, and a model call is the cost the command exists to avoid.
- **A new open tool.** No open tool knows the filter, the claim and the stop of this roadmap.
