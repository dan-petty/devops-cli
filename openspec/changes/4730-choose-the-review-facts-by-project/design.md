# Design

## Decisions

- **Read the review tag pattern from the review table of the roadmap file of the checkout, with the default `v*`.**: A repository sets its own tag form in its own roadmap file, and `src/devops_cli/roadmap/project_profile.py:78:name = CONST_ROADMAP_IMPLEMENT_STEPS_FILE` shows that one file is the roadmap file of a repository.
- **Keep the default `v*` in one constant beside the name of the roadmap file.**: Two copies of the default would drift, and `src/devops_cli/config/constants.py:3777:CONST_ROADMAP_IMPLEMENT_STEPS_FILE: Final[str] = ".devops/roadmap.toml"` holds the name of the roadmap file in that module.
- **Accept the review table in the declaration of the roadmap file, so `resolve_profile` reads a repository file that holds it.**: `src/devops_cli/roadmap/project_profile.py:49:class _Declaration(BaseModel):` holds the only tables that the roadmap file declares, and `src/devops_cli/roadmap/project_profile.py:50:model_config = ConfigDict(extra="forbid", frozen=True)` refuses a table that the model does not hold, so a repository that writes the review table would fail the implement job.
- **Take the merged pull request titles from the `listing.merged_titles` fact of the catalog, which shares the one listing read of the run, and return `[]` when empty.**: `src/devops_cli/roadmap/project_review/readers.py:176:return [record.model_dump(mode="json", exclude={"body"}) for record in records]` keeps the title of each record, and `src/devops_cli/roadmap/project_review/dispatch.py:442:if fact.reader in _ONE_READ` shares one listing read between its facts, so the last fallback costs no request and returning `[]` yields `ok` with `n=0` instead of `review_no_value`.
- **Rank the hotspots by churn alone when the hot files hold no path that lizard reads.**: `src/devops_cli/roadmap/project_review/facts.py:223:read = [row for row in rows if lizard_languages.get_reader_for(row.path) is not None]` already asks lizard which hot files it reads, so the empty list is the one place that knows the repository holds no language that lizard reads.
- **Take the functional change from the CHANGELOG sections, then the feat and fix subjects, then the merged pull request titles, and name that step as the source of the fact.**: Each step costs more than the one before: the CHANGELOG is a file of the checkout, a subject is one line of a commit that the review already reads, and the titles come from the one listing read of the run.
- **Place the functional change fact after `lizard.complexity` and before the catalog facts, and modify the requirement that fixes the order of the facts.**: `src/devops_cli/roadmap/project_review/review.py:77:facts=[*facts, *result.facts],` puts the git facts before the catalog facts, so a fact that the review builds from the window belongs at that boundary and the requirement that lists the facts must name it.
- **List each repository of `service.repos` in a dry run that names no window, with the reason of each fact whose setting is unset and the text of each other condition.**: `src/devops_cli/roadmap/project_review/dispatch.py:def _setting` decides a setting with no read and `src/devops_cli/roadmap/project_review/dispatch.py:def _condition` renders each condition text, while `src/devops_cli/commands/roadmap_review.py:66:request = parse_window(version=version, since=since, until=until, week=week, last=last, now=now)` refuses a run with no window, so the listing decides each setting condition of every repository and sends no request.
- **List a `window:` or `path:` condition as its text, and modify the base requirement `A dry run of the review starts no program` to hold the no-window case instead of adding a requirement beside it.**: `src/devops_cli/roadmap/project_review/dispatch.py:210:commits = (window.base_sha, window.head_sha)` shows that a path condition is read at the commits of the window, and the base requirement already states what a dry run prints and that it starts no program, so a second requirement would repeat it.
- **Keep the recorded git transcript `tests/fixtures/git/review_window.json` unchanged.**: The default pattern builds the same `for-each-ref` command, and `tests/support/git_scenarios.py:610:for fact in review_facts(repo, resolved, tags)` shows that the transcript records the facts of `review_facts` and not the facts of `run_review`, so the functional change fact does not reach it.

## Rejected alternatives

- **Read the planning system and the languages from `resolve_profile` of the generalization plan.**: `src/devops_cli/roadmap/project_profile.py:52:project: _Project = _Project()` shows that the declaration holds the project table only, and `src/devops_cli/roadmap/project_profile.py:60:preset: ToolchainPreset` shows that the resolved profile holds the preset alone, so it holds no language and no planning system.
- **Call `resolve_profile` from the review to read the roadmap file.**: `src/devops_cli/roadmap/project_profile.py:79:listed = git(source, "ls-tree", "--name-only", ref, "--", name, operation=_OPERATION)` starts a git command that the review does not start today, and `tests/fixtures/git/review_window.json:25:refs/tags/v*` is the only tag read of the recorded transcript.
- **Hard-code the pattern `v*` in the review.**: `src/devops_cli/roadmap/project_review/git_read.py:24:_RELEASE_TAGS: Final = "refs/tags/v*"` is that fixed pattern, and a repository whose tags are `release-1.0` cannot change it.
- **Add a trait detector of the review, or probe each file with lizard.**: `src/devops_cli/roadmap/project_review/facts.py:223:read = [row for row in rows if lizard_languages.get_reader_for(row.path) is not None]` already asks lizard which hot files it reads, so a detector would copy that lookup.
- **Read the merged pull request titles with a second GitHub read in `functional.py`.**: `src/devops_cli/roadmap/project_review/readers.py:176:return [record.model_dump(mode="json", exclude={"body"}) for record in records]` already keeps each title, and `src/devops_cli/roadmap/project_review/dispatch.py:442:if fact.reader in _ONE_READ` shares one listing read, so a second read would send a request that the run already pays for once.
- **Insert the functional change fact after the catalog facts.**: `src/devops_cli/roadmap/project_review/review.py:77:facts=[*facts, *result.facts],` appends the catalog facts last, so a git fact of the window would sit after them and the fixed order of the review would break.
- **Decide the `path:` condition of the dry run from the working tree of a clone of each repository of `service.repos`.**: `src/devops_cli/roadmap/project_review/dispatch.py:210:commits = (window.base_sha, window.head_sha)` shows that the review reads a path at the commits of the window, so a working-tree check would print a skip that the run does not make.
- **Add a second dry-run requirement beside `A dry run of the review starts no program`.**: `openspec/specs/roadmap-project-review/spec.md` holds the requirement `A dry run of the review starts no program`, whose text already says what a dry run prints and that it starts no program, so a second requirement would repeat it.
- **Take the commit subjects before the CHANGELOG sections.**: The probe states: The path `CHANGELOG.md` is a file of the staging commit. A section of that file already groups the subjects of a release, so a subject is the coarser source.
- **Put the tag pattern in the config of devops-cli instead of the roadmap file of the repository.**: The probe states: The path `.devops/roadmap.toml` is a file of the staging commit, and `src/devops_cli/roadmap/project_profile.py:78:name = CONST_ROADMAP_IMPLEMENT_STEPS_FILE` reads the roadmap file of a repository, so the repository owns its pattern.
- **Route a private repository summary to its tracker issue in this change.**: `run_review` in `src/devops_cli/roadmap/project_review/review.py:74:return ReviewData(` builds `data.json` only and sends no external summary; HTML rendering and tracker-issue publishing belong to #4720, #4733 and #4624.

## Unchanged references

- `tests/fixtures/git/review_window.json` (snapshot file): The default pattern `v*` builds the same `for-each-ref` command, and the transcript records the facts of `review_facts` and not of `run_review`, so the recorded answer stays the same.
