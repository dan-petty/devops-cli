# Design

## Decisions

- **Keep the cached issue in `valkey-roadmap` under the brain key form `roadmap:v1:brain-<kind>:<owner>/<name>[:<id>]` that `RepoRef.valkey_key` builds, with the kind `brain-issue`.**: `src/devops_cli/github/repo_ref.py:201:def valkey_key(self, kind: str, ident: str | None = None) -> str:` builds the repository key of the store, and `src/devops_cli/github/repo_ref.py:212:def valkey_patterns(self) -> tuple[str, str]:` finds the keys of one repository and no other, because the repository part holds the only `/` of a key.
- **Hold the entry in the shared tier through `src/devops_cli/valkey/tiered.py:100:class TieredMapping[V](MutableMapping[str, V]):`, with the repository key of the issue as its prefix, and not in a new cache class.**: `src/devops_cli/valkey/tiered.py:109:def __init__(` takes `prefix` as an argument and `src/devops_cli/valkey/tiered.py:138:return f"{self.prefix}{_SEPARATOR}{key}"` builds the key from it, so the mapping gives the exact key form, the schema key, the oversize bound and the TTL with no new cache code.
- **Keep no in-process memory tier for the issue mapping (`entries=0`), so the shared tier is the only copy.**: `src/devops_cli/valkey/tiered.py:140:def __getitem__(self, key: str) -> V:` reads the memory tier first, and a memory copy would serve a record older than the webhook write that a lane of another pod made. A round is short, so the memory tier saves no request that the shared tier does not save.
- **Read the entry in the store's read of an issue by number, and in no row.**: `src/devops_cli/roadmap/stores/github_store.py:836:def issue(self, number: int) -> IssueRecord | None:` is the one read of an issue by number, and `src/devops_cli/roadmap/stores/github_store.py:830:def item(self, number: int) -> Item | None:` follows it, so each row takes the cache with no change of its own.
- **Write the entry where the store keeps the answer of GitHub, and in each label write.**: `src/devops_cli/roadmap/stores/github_store.py:1394:def _kept(self, issue: _IssuePayload) -> IssueRecord:` receives the issue of a `PATCH`, and `src/devops_cli/roadmap/stores/github_store.py:1186:self._write(label_args(self._repo, number, label), f"label #{number} {label}")` keeps no issue, so the label writes store the record that the store holds with the new label set.
- **Revalidate a stale entry with a conditional read of the same endpoint, carrying the `ETag` that the entry holds.**: The `ETag` in the entry survives a pod restart, and a `304` leaves the stored issue and the entry unchanged, as `src/devops_cli/github/rate_limiter.py:805:with 304 does not count against its primary rate limit, so `count_request` calls `refund`` states. A full read would spend one primary-limit unit an hour for each object.
- **Send the conditional read through `gh api --include` with `-H If-None-Match`, and read its status line with the stdlib header parser.**: `src/devops_cli/github/client.py:1045:def api(self, endpoint: str, paginate: bool = False, include: bool = False) -> str:` and `src/devops_cli/github/hook_deliveries.py:94:def _next_endpoint(` already read the status line and the headers that `gh api --include` prints, and the store's requests go through `gh` (`src/devops_cli/roadmap/stores/github_store.py:771:runner: GhRunner = run_gh,`).
- **Write the entry in the roadmap consumer of the existing webhook router, before it wakes a lane, and add no second route.**: `src/devops_cli/server/routes/webhooks.py:277:def deliver(` enqueues the wake at its end, so the write at its top lands before the row runs, and ADR 0009 builds one router with one consumer for each subscriber.
- **Count a hit and a miss with a new counter `devops_cli_brain_cache_total{row,result}`, beside `devops_cli_github_requests_total`.**: The issue asks for a cache count for each row, and `src/devops_cli/github/request_scope.py:63:return {"repo": scope.repo, "row": scope.row}` gives the bounded row. The existing `devops_cli_brain_reads_total` carries `store` and `result` only, so a row label there would change every series of the brain and its spec.
- **Take the fallback to GitHub from the shared tier's own answer, with no new code.**: `src/devops_cli/valkey/cache.py:259:def shared_cache_tier()` gives the one tier of the process and `src/devops_cli/valkey/tiered.py:140:def __getitem__(self, key: str) -> V:` counts `fallback` and raises `KeyError` when the tier is down, so the store reads GitHub and its round returns its normal result.
- **Cache issue objects only, and leave the pull request and check objects to #6630.**: `src/devops_cli/config/constants.py:4023:CONST_ROADMAP_WEBHOOK_EVENTS: Final[frozenset[str]] = frozenset(` holds the `issues` events of the intake batch keys only, and another event needs a new subscription and a person's change of each repository hook, which would hold the core cache back.
- **Set the key's life to 24 hours and the revalidation age to one hour.**: A key that expires at the revalidation age would leave no entry to revalidate, so a missed webhook would cost a full read. With a one-day life, the stale read repairs a missed delivery within the hour and the key still leaves the store.

## Rejected alternatives

- **A hand-built cache class over the shared cache tier, instead of the tiered mapping.**: `src/devops_cli/valkey/tiered.py:109:def __init__(` takes the prefix and `src/devops_cli/valkey/tiered.py:136:def shared_key(self, key: str) -> str:` builds the key, so a class of its own would repeat the schema key, the oversize bound, the TTL and the two counters of the mapping.
- **A separate hourly reconcile row that reads each cached object.**: The read of an object older than an hour is the only place that needs the object fresh, and it is already in `src/devops_cli/roadmap/stores/github_store.py:836:def issue(self, number: int) -> IssueRecord | None:`. A row would add a due mark, a command and a read of an object that no row needs at that minute.
- **A `row` label on `devops_cli_brain_reads_total`.**: The counter carries `store` and `result` and its spec fixes those labels for the snapshot, the fact and the new issue store; a `row` label would change every series of the brain. A second counter with the row keeps both sets bounded.
- **The validator only in the in-process store of the gidgethub session.**: `src/devops_cli/github/session_transport.py:363:count_request(resource, method.upper(), status, labels)` counts the session's answers, whose ETag store dies with the pod, so the first revalidation after a restart reads each object in full. The entry keeps the ETag and survives the pod.
- **A JSON file in the Service home for the cache.**: Each lane and each pod needs the same object, and a file has one writer on one host, while `src/devops_cli/valkey/cache.py:259:def shared_cache_tier()` gives every lane of the process one client behind one breaker.
- **Webhooks only, with no revalidation after a limit.**: GitHub never retries a failed delivery, so a missed event would leave an entry wrong with no repair. The one-hour revalidation repairs it at the next read of that issue.
- **A second webhook route for the cache.**: `src/devops_cli/server/routes/webhooks.py:277:def deliver(` is the one consumer of the roadmap events, so a second route would deliver the same event twice.
- **hishel as the cache.**: The alternatives block of the issue records its verdict as rejected under ADR 0023: hishel covers a conditional HTTP answer with an ETag validator and has no webhook write, no GitHub issue schema and no per-row read-through.
