# Design

## Decisions

1. **The generator imports every module of devops-cli, and no list of modules exists.** `DocGenerator._import_all_exception_modules` takes the `.py` files of the directory of the `devops_cli` package with `Path.rglob`, gives each file its dotted name with `module_name` of `devops_cli.core.import_graph`, and imports it with `importlib.import_module`. Then `DevOpsCLIError.__subclasses__` holds each error class, through any chain of bases and any import name. Reason: the hand list is the cause of #6815. A file list has no entry that a person can forget.
2. **The names come from the files, not from `pkgutil.walk_packages`.** Reason: `walk_packages` skips a directory with no `__init__.py`. The probe of the proposal shows that it skips the 6 modules of `devops_cli.docker`, so an error class there would be missing from the catalog with no failed check. The file list holds all 964 modules.
3. **The cost is about 2.3 s for each `devops docs generate`.** When the catalog runs, 565 modules are loaded, and the other 399 are new imports. The median of six runs of the command is 5.95 s on the base and 8.24 s with the change, on one workstation. The output files are the same. No module fails to import, and the imports happen in the function, so the `startup-imports` row of `devops ci` does not change. An import that fails still stops the docs stage with the name of the module.
4. **The guard test runs in a fresh interpreter and checks each module, not only each error class.** A pytest worker holds the modules that the earlier tests imported, so a check in the worker gives a result that changes with the shard layout. The child runs the import step of the generator, then imports the module of each `.py` file of the package that is not loaded yet. It prints those modules and the error classes that they added, and the test expects neither. A check of the error classes alone passes on ec5b16bdc, where the list names each module with an error class today, and it fails only when the next module misses the list. The module check fails on the base: 218 modules are not loaded. On 676e10721 the child also prints the four onboard classes.
5. **A new capability, `docs-error-catalog`, holds the rule.** No base spec holds a rule of `docs/ERRORS.md`. `docs-cli-reference` holds the rules of `docs/CLI_REFERENCE.md`, and `command-error-exit` holds the rules of how a command reports an error.

## Rejected alternatives

- **Keep `CONST_DOMAIN_EXCEPTION_MODULES` and add a test that fails when a module with an error class is not in it.** Rejected: the test must import every module too, so it costs the same time in the test run. A person still edits the list for each new module, and the list is the cause of #6815.
- **Find the error classes with an `ast` scan for `class X(DevOpsCLIError)`.** Rejected: a class whose base is another error class, from another module or under another name, needs name resolution that the scan must build again. That is a parser of our own, and the import of the modules gives the answer with the standard library.
- **Import the modules that `pkgutil.walk_packages` gives.** Rejected: it skips the namespace package `devops_cli.docker` (decision 2).
- **Move every error class into `devops_cli.exceptions`.** Rejected: 21 classes of 16 modules would move, with the imports of their callers. That is a refactor of its own, and a new module could still define an error class elsewhere with no failed check.
