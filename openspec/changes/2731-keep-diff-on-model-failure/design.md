# Design

## Decisions

- **One clause, one place.** `_run_agent` already holds everything a stopped outcome needs: the messages of the failed run, the replies, and the log of the tool calls. It catches `ModelAPIError` in the `except` clause that follows the clause of `UsageLimitExceeded` and `UnexpectedModelBehavior`. A refused key is told first, with `model_call_error`, which stays the one function that maps a `ModelHTTPError` to `AICredentialsError`. Then the clause either keeps the error to raise after the `finally` block, or sets the reason with `_stop_reason`. The `finally` block runs in both cases, so the ledger holds the spend of a failed turn.
- **A refused key raises.** The key is the same for every item and every step, so a run with a rejected key can do no work. The spec and the old behavior agree. The raise comes after the `finally` block, outside the `except` clause, so a logged traceback holds no text of the reply (the reason of the comment in the code today).
- **The reason is the reason of any stopped run.** `_stop_reason` gives the class, the masked and cut message, and the counts of refused and retried tool calls. The status of an HTTP reply and the name of the model are in the message of a `ModelHTTPError`, so a person can tell a 503 from a 429 without a Job log. Both turns share one `ToolCallLog`, so the counts cover both.
- **`_attempt` and `_implement_item` stay as they are.** `_attempt` builds the stopped outcome with `_discarded_diff` for any run with a reason. `_stopped_by` carries the diff to the comment. `_Run.then` adds the partial spend of the extra turn to the first turn, and takes the last text of the first turn when the failed turn has none.
- **The classification stays.** Item-level: every `ModelAPIError` that is not a refused key (rate limit, quota, unavailable, server error, connection error, timeouts, context window), `UsageLimitExceeded` and `UnexpectedModelBehavior`. Run-level: `AICredentialsError` and `GitHubUnauthenticatedError`. A rate limit or a quota could in theory hit every item. But the next item takes its own turn, `apply_implement` runs the items one after the other, and a stopped item returns to Ready with the reason in its comment. That is the behavior today for the same errors, and the issue asks to keep it.

## Rejected alternatives

- **Catch the error in `_attempt`.** `_attempt` would need the partial spend and the last text, which only `_run_agent` holds (the messages live in its `capture_run_messages` block). A second capture in `_attempt` would count the replies twice and record the spend twice.
- **Add the diff in `_implement_item`.** The checkout is reset by then (`run_step` resets it in its `finally` block), so the diff is gone. The diff must be read in the step, before the reset.
- **Carry the partial result in the exception.** A new field on `AIClientError` that `_attempt` reads would add a second path for a stop next to the stop with a reason. The `_Run` already is that carrier.
- **Treat a rate limit or a quota as a stop of the whole run.** It changes the classification, which the issue asks to keep. A run that stops its items one by one with a reason each is no worse than today, and no evidence shows that a stop of the run is better.
- **A reason built from `model_call_error`.** Its text ("The step's model call failed (ModelHTTPError).") holds no status and no body on purpose, as its other users (refine, alternatives) log it. The stopped item is masked and cut, as the stop for `UnexpectedModelBehavior` is, so the richer text is safe and a person needs it.
