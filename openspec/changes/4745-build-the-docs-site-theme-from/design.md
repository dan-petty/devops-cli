# Design

## Decisions

- **Put extra_css in the [project] table of zensical.toml, above [project.theme].**: extra_css is a top-level site setting, and _staged_config spreads each key of the [project] table into the staged config (src/devops_cli/docs/site.py:301: **config,), so a nested key would never reach the site.
- **One docs dark token file, docs/assets/css/tokens-dark-docs.css, built from design/sd/dark-docs.json with the selector :root[data-md-color-scheme="slate"].**: Zensical sets data-md-color-scheme and never sets data-theme, so the data-theme selectors of the shared dark platform never match a docs page (design/sd/dark.json:19: "@media (prefers-color-scheme: dark)",).
- **Add the docs config to the design-tokens target of Makefile and commit the output that the build writes.**: make design-tokens is the one build path (Makefile:11:design-tokens:), and style-dictionary is NOT_IN_RUNNER, so the Design Tokens job is the check that the committed file is the build (.github/workflows/ci.yml:933: git diff --exit-code -- docs/assets/css src/devops_cli/design k8s/monitoring/dashboards).
- **The hand-written theme CSS sits in its own folder, docs/assets/css/site/theme.css.**: The gate holds each rule against its tree glob (tests/gate/construct_gate.py:205: held.setdefault(violation.rule, []).append(f"{violation.tree}/**")), so a rule over the whole docs CSS folder would also report the hex values of the generated token CSS.
- **Map the documented role set of the theme variables: page and surface background, body and muted text, link, accent, code background and code text, primary color and footer.**: Each mapped variable takes a token that docs/DESIGN.md:254:| Docs site | Map the token CSS variables of gives a contrast rule, so the offline contrast case covers every mapped pair, and a variable with no token would need a color literal.
- **One css2 request loads Source Serif 4, Source Sans 3 and Source Code Pro with display=swap, and theme.font names Source Sans 3 and Source Code Pro.**: The issue requires the three faces through the same css2 API, and Zensical builds its font stack from theme.font, so the sans and the mono need that setting as well (docs/DESIGN.md:254:| Docs site | Map the token CSS variables of).
- **The code roles go through the code highlight variables of the theme, one declaration for each role.**: Zensical gives each code class one of those variables, so the map needs one declaration for each role and no list of classes.
- **Extend the existing css-color-literal rule, the rule-file constant and the scan-root constant, and change the hook command with them.**: The gate reads one map of rule files (tests/gate/construct_gate.py:97: "css-color-literal": CONST_DESIGN_CSS_FILES,), one tuple of scan roots (src/devops_cli/config/constants.py:5169:CONST_AST_GREP_SCAN_ROOTS: Final[tuple[str, ...]] = ("src", "tests")) and one hook command, and compares them, so the changes belong to the same steps.
- **The gate case of the docs theme glob gives the check canned input, and the scan of the committed CSS runs in the constructs row.**: The case module holds that git and ast-grep do not start (tests/invariants/test_construct_gate_check.py:4:(#2164). These cases give it a small tree and the names of its tracked files, so git and ast-grep), and the row runs the one scan (tests/gate/construct_gate.py:244:["ast-grep", "scan", "--json=compact", *CONST_AST_GREP_SCAN_ROOTS],).
- **Each extra_css path and the favicon path keep the docs/ prefix.**: The stage copies docs/ into the pages folder and sets docs_dir to that folder, so the site paths keep the repository prefix (src/devops_cli/docs/site.py:def _copy_pages).
- **One SVG favicon at docs/assets/favicon.svg, set by theme.favicon.**: A vector file keeps its shape at each size and follows the theme, where the emoji is a font glyph whose color does not follow the theme (docs/DESIGN.md:254:| Docs site | Map the token CSS variables of).
- **The theme test module is tests/config/test_docs_theme.py, and the stage case goes in tests/docs/test_site.py.**: tests/config holds the settings cases and tests/docs holds the cases of src/devops_cli/docs/site.py, so each case sits beside the code it reads.
- **The headless layout check runs in the Docs Site Build workflow, not in a group verify.**: Playwright and Chromium are NOT_IN_RUNNER, and the workflow already runs the real site build on this pull request (.github/workflows/docs-site.yml:71: run: uv run devops docs site build --strict).

## Rejected alternatives

- **Rewrite docs/assets/css/style.css and remove the dark default of docs/_layouts/default.html, as the issue body asks.**: The probes answer that `docs/assets/css/style.css` and `docs/_layouts/default.html` are no file of the staging commit: commit 64b71991 (#5183) deleted both.
- **A pytest case that runs the ast-grep scan over the docs theme CSS.**: `tests/invariants/test_construct_gate_check.py:4:(#2164). These cases give it a small tree and the names of its tracked files, so git and ast-grep` gives the module contract, and `docs/TESTING.md:76:A check of committed files or of tool configuration is a row of` gives the row rule, so the case of group 5 passes canned input and the constructs row scans the committed CSS.
- **One selector set for both the package and the docs site.**: design/sd/dark.json:12: "buildPath": "docs/assets/css/", writes one block for each config, and tests/design/test_tokens.py:89: if (DOCS_TOKEN_CSS_DIR / f"tokens-{file}.css").read_bytes() compares the docs copy with the package copy byte for byte.
- **A script that copies data-md-color-scheme to data-theme.**: It depends on the DOM of Zensical, it can flash the wrong theme before it runs, and no offline test can check it: tests/support/design_tokens.py:def css_variables reads the built CSS files with no browser.
- **The Zensical default palette.**: docs/DESIGN.md:254:| Docs site | Map the token CSS variables of gives the docs site the token colors, and the default palette holds no token value.
- **Every theme variable of Zensical.**: Many have no token role, and a value with no token is a color literal that the rule refuses: .ast-grep/rules/css-color-literal.yml:25: regex: '^(?i:aliceblue lists the 148 CSS named colors.
- **Self-hosted font files.**: docs/DESIGN.md:254:| Docs site | Map the token CSS variables of keeps the Google Fonts css2 API, and the type section of the same document gives the three Source faces.
- **One color for all code.**: It loses the string and the keyword roles that the palette defines in docs/DESIGN.md:254:| Docs site | Map the token CSS variables of.
- **A second ast-grep rule for the docs folder.**: The gate reads one map of rule files (tests/gate/construct_gate.py:97: "css-color-literal": CONST_DESIGN_CSS_FILES,), and the design spec names one rule for hand-written CSS.
- **Put the theme CSS beside the generated token CSS.**: tests/gate/construct_gate.py:205: held.setdefault(violation.rule, []).append(f"{violation.tree}/**") holds a rule against its tree glob, so the rule files would cover the generated token CSS and report its hex values.
- **Keep the emoji favicon.**: The emoji is a font glyph, and its color does not follow the theme; docs/DESIGN.md:254:| Docs site | Map the token CSS variables of gives the docs site one SVG favicon.
- **Leave the headless layout check to a person.**: Playwright is NOT_IN_RUNNER, and the Docs Site Build job runs the real build (.github/workflows/docs-site.yml:71: run: uv run devops docs site build --strict), so one more step of that job runs the browser over the built site.
- **Build the docs dark token CSS with Style Dictionary inside the runner step.**: style-dictionary is NOT_IN_RUNNER, and npm ci --ignore-scripts needs the network, so the Design Tokens job rebuilds and compares (.github/workflows/ci.yml:920: run: make design-tokens).
