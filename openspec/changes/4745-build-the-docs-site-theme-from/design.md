# Design

## Decisions

- **Put extra_css in the [project] table of zensical.toml, above [project.theme].**: extra_css is a top-level site setting, and _staged_config spreads each key of the [project] table into the staged config (src/devops_cli/docs/site.py:301: **config,), so a nested key would never reach the site.
- **One docs dark token file, docs/assets/css/tokens-dark-docs.css, built from design/sd/dark-docs.json with the selector [data-md-color-scheme="slate"].**: The theme puts data-md-color-scheme on the body element (zensical_ui 0.0.43, templates/base.html:123) and never sets data-theme. The shared dark CSS matches each page under a dark system theme (design/sd/dark.json:19: "@media (prefers-color-scheme: dark)", with :root:not([data-theme="light"]) on line 20), so it follows the system theme and not the choice of the reader in the palette toggle. The docs site thus loads its own dark file and not the shared one.
- **Model design/sd/dark-docs.json on design/sd/dark-explicit.json, with the docs platform only.**: That config holds one selector string and outputReferences true (design/sd/dark-explicit.json:18: "selector": ":root[data-theme=\"dark\"]",), so the output of the docs config is the explicit dark file with another selector on line 5. The selector of design/sd/dark.json is an array with an @media wrapper, which gives another file shape.
- **Add the docs config to the design-tokens target of Makefile and commit the output that the build writes.**: make design-tokens is the one build path (Makefile:11:design-tokens:), and style-dictionary is NOT_IN_RUNNER, so the implement step writes the file as a byte copy of docs/assets/css/tokens-dark-explicit.css with the new selector line, and the Design Tokens job is the check that the committed file is the build (.github/workflows/ci.yml:944: git diff --exit-code -- docs/assets/css src/devops_cli/design k8s/monitoring/dashboards).
- **The hand-written theme CSS sits in its own folder, docs/assets/css/site/theme.css.**: The gate holds each rule against its tree glob (tests/gate/construct_gate.py:205: held.setdefault(violation.rule, []).append(f"{violation.tree}/**")), so a rule over the whole docs CSS folder would also report the hex values of the generated token CSS.
- **Map the documented role set of the theme variables: page and surface background, body and muted text, link, accent, code background and code text, primary color and footer.**: Each mapped variable takes a token that docs/DESIGN.md:254:| Docs site | Map the token CSS variables of gives a contrast rule, so the offline contrast case covers every mapped pair, and a variable with no token would need a color literal.
- **Declare the map under [data-md-color-scheme="default"], [data-md-color-scheme="slate"], and the link variable again under [data-md-color-scheme="slate"][data-md-color-primary].**: The theme declares its variables on those selectors of the body element, so a rule on :root loses to them and would read the light tokens in the dark scheme. The palette CSS of zensical_ui 0.0.43 holds [data-md-color-scheme=slate][data-md-color-primary=indigo]{--md-typeset-a-color:#5488e8}, a rule of 2 attribute selectors that wins over a rule of 1.
- **One css2 request of the theme CSS loads Source Serif 4, Source Sans 3 and Source Code Pro with display=swap, theme.font is false, and the theme CSS sets --md-text-font and --md-code-font.**: With a font name in theme.font, the theme adds its own request to the older css API with display=fallback and the weights 300, 400, 500 and 700 (zensical_ui 0.0.43, templates/base.html:94 to 102). The sans and the mono would then load twice, and the theme request holds no weight 600, which docs/DESIGN.md:175 requires. The theme reads its font stacks from --md-text-font and --md-code-font (templates/base.html:102), so the theme CSS sets them from the token variables.
- **The reading text (.md-typeset) takes Source Serif 4, and each font size is its size token divided by 1.25.**: docs/DESIGN.md:169:| Source Serif 4 | Reading text of reports and docs pages | gives the face, and docs/DESIGN.md:199 gives 16 px under 40rem and 18 px from 40rem. The theme sets html{font-size:125%}, so 1rem is 20 px, and var(--font-size-lg), which is 1.125rem, would give 22.5 px. From 100em the theme sets the root to 137.5 %, and the text then grows with the rest of the theme.
- **The code roles go through the code highlight variables of the theme, one declaration for each role.**: Zensical gives each code class one of those variables, so the map needs one declaration for each role and no list of classes.
- **Extend the existing css-color-literal rule, the rule-file constant and the scan-root constant, and change the hook command with them.**: The gate reads one map of rule files (tests/gate/construct_gate.py:97: "css-color-literal": CONST_DESIGN_CSS_FILES,), one tuple of scan roots (src/devops_cli/config/constants.py:5160:CONST_AST_GREP_SCAN_ROOTS: Final[tuple[str, ...]] = ("src", "tests")) and one hook command, and compares them, so the changes belong to the same steps.
- **The gate case of the docs theme glob gives the check canned input, and the scan of the committed CSS runs in the constructs row.**: The case module holds that git and ast-grep do not start (tests/invariants/test_construct_gate_check.py:4:(#2164). These cases give it a small tree and the names of its tracked files, so git and ast-grep), and the row runs the one scan (tests/gate/construct_gate.py:244:["ast-grep", "scan", "--json=compact", *CONST_AST_GREP_SCAN_ROOTS],).
- **Each extra_css path and the favicon path keep the docs/ prefix.**: The stage copies docs/ into the pages folder and sets docs_dir to that folder, so the site paths keep the repository prefix (src/devops_cli/docs/site.py:def _copy_pages).
- **One SVG favicon at docs/assets/favicon.svg, set by theme.favicon.**: A vector file keeps its shape at each size, and the site of today shows the default icon of the theme, the PNG assets/images/favicon.png (zensical 0.1.3, zensical/config.py:823), which is no mark of the project (docs/DESIGN.md:254:| Docs site | Map the token CSS variables of).
- **The theme cases go in the modules of tests/design that exist: the docs dark case in test_tokens.py, the contrast case in test_contrast.py and the other cases in test_design_spec.py, whose breakpoint case takes the docs theme CSS.**: The Design Tokens job runs only that folder (.github/workflows/ci.yml:949: run: uv run pytest tests/design -n 0 --timeout 60), and tests/design/test_design_spec.py:def test_each_media_width_is_a_breakpoint_token already compares each @media width with the breakpoint tokens. The stage rule puts a new test module of this plan in tests/config, the mirror of src/devops_cli/config/constants.py, so the plan adds no test module.
- **No case reads zensical.toml: the scenarios of the site config name the build, the config check and the layout step.**: docs/TESTING.md:61 holds that no test asserts a value of a manifest or of a config file, so `uv run devops docs site build --strict`, `uv run devops gh pages verify` and the layout step of the Docs Site Build job are the proof.
- **The headless layout check runs in the Docs Site Build workflow, starts the Google Chrome of the runner image through the Playwright channel chrome, and installs nothing.**: The implement Job has no browser, and the workflow already runs the real site build on this pull request (.github/workflows/docs-site.yml:71: run: uv run devops docs site build --strict). The runner image ubuntu-26.04 holds Google Chrome 157 (actions/runner-images, Ubuntu2604-Readme.md), and the job installs each package of the docs dependency group from the lock (.github/actions/setup-toolchain/action.yml:73: uv sync --locked --all-groups --all-extras).
- **axe-core computes the contrast of each text pair, and the script compares each ratio with 4.5.**: The rule color-contrast of axe-core gives the text color, the background color and the ratio of each text element, so the script holds no contrast code. The rule accepts 3:1 for large text, and the issue requires 4.5:1 for every pair, so the script reads the ratio and does not take the verdict of the rule.
- **The job limit of Docs Site Build goes from 5 to 10 minutes, and the layout step gets a limit of 3 minutes.**: The job holds timeout-minutes: 5 with no step limit (.github/workflows/docs-site.yml:51), and the 12 views with one axe run each get a limit of their own. A limit of 10 minutes is above the sum of 5 and 3, and it is the limit of the same build in .github/workflows/pages.yml:48. tests/invariants/test_workflow_contracts.py:def test_every_job_has_a_limit_and_each_step_limit_is_under_it requires each step limit under the job limit.

- **A pytest case that runs the ast-grep scan over the docs theme CSS.**: `tests/invariants/test_construct_gate_check.py:4:(#2164). These cases give it a small tree and the names of its tracked files, so git and ast-grep` gives the module contract, and `docs/TESTING.md:76:A check of committed files or of tool configuration is a row of` gives the row rule, so the case of group 5 passes canned input and the constructs row scans the committed CSS.
- **One selector set for both the package and the docs site.**: design/sd/dark.json:12: "buildPath": "docs/assets/css/", writes one block for each config, and tests/design/test_tokens.py:89: if (DOCS_TOKEN_CSS_DIR / f"tokens-{file}.css").read_bytes() compares the docs copy with the package copy byte for byte.
- **The selector :root[data-md-color-scheme="slate"] for the docs dark file.**: zensical_ui 0.0.43 puts the attribute on the body element (templates/base.html:123), so the selector matches no element and the dark scheme would show the 38 light token values.
- **A script that copies data-md-color-scheme to data-theme.**: It depends on the DOM of Zensical, it can flash the wrong theme before it runs, and no offline test can check it: tests/support/design_tokens.py:def css_variables reads the built CSS files with no browser.
- **The Zensical default palette.**: docs/DESIGN.md:254:| Docs site | Map the token CSS variables of gives the docs site the token colors, and the default palette holds no token value.
- **Every theme variable of Zensical.**: Many have no token role, and a value with no token is a color literal that the rule refuses: .ast-grep/rules/css-color-literal.yml:25: regex: '^(?i:aliceblue lists the 148 CSS named colors.
- **Self-hosted font files.**: docs/DESIGN.md:254:| Docs site | Map the token CSS variables of keeps the Google Fonts css2 API, and the type section of the same document gives the three Source faces.
- **theme.font names Source Sans 3 and Source Code Pro, as the issue proposes.**: zensical_ui 0.0.43 then adds a second font request (templates/base.html:94 to 102) with display=fallback and the weights 300, 400, 500 and 700, so 2 of the 3 faces load twice and the request holds no weight 600.
- **The size tokens with no division.**: The theme sets html{font-size:125%}, so font-size: var(--font-size-lg) gives 22.5 px and not the 18 px of docs/DESIGN.md:182, and var(--font-size-sm) gives 17.5 px and not 14 px.
- **One color for all code.**: It loses the string and the keyword roles that the palette defines in docs/DESIGN.md:254:| Docs site | Map the token CSS variables of.
- **A second ast-grep rule for the docs folder.**: The gate reads one map of rule files (tests/gate/construct_gate.py:97: "css-color-literal": CONST_DESIGN_CSS_FILES,), and the design spec names one rule for hand-written CSS.
- **Put the theme CSS beside the generated token CSS.**: tests/gate/construct_gate.py:205: held.setdefault(violation.rule, []).append(f"{violation.tree}/**") holds a rule against its tree glob, so the rule files would cover the generated token CSS and report its hex values.
- **Keep the default icon of the theme.**: zensical 0.1.3 gives theme.favicon the default assets/images/favicon.png (zensical/config.py:823), a PNG of the theme; docs/DESIGN.md:254:| Docs site | Map the token CSS variables of gives the docs site one SVG favicon.
- **A new test module tests/design/test_docs_theme.py, or the module in tests/config.**: The stage rule refuses a new test module outside the mirror of the changed source, which is tests/config for src/devops_cli/config/constants.py, and the Design Tokens job runs only tests/design (.github/workflows/ci.yml:949: run: uv run pytest tests/design -n 0 --timeout 60), so a module in tests/config would not run in that job.
- **A case in tests/docs/test_site.py that asserts the theme settings of the staged config.**: docs/TESTING.md:61 holds that no test asserts a value of a manifest or of a config file, and the settings of zensical.toml are such values.
- **Leave the headless layout check to a person.**: Playwright is NOT_IN_RUNNER, and the Docs Site Build job runs the real build (.github/workflows/docs-site.yml:71: run: uv run devops docs site build --strict), so one more step of that job runs the browser over the built site.
- **Install Chromium on the runner with playwright install --with-deps, and take Playwright with uv run --with.**: docs/SDLC.md:225 holds that every CI job runs with no package install on the runner, uv run --with takes a package outside uv.lock, and the runner image ubuntu-26.04 already holds Google Chrome 157.
- **Contrast code in the script.**: axe-core holds the rule color-contrast, and axe-playwright-python 0.1.9 runs it in the Playwright page, so own code would copy an open tool (rule 3 of AGENTS.md).
- **Build the docs dark token CSS with Style Dictionary inside the runner step.**: style-dictionary is NOT_IN_RUNNER, and npm ci --ignore-scripts needs the network, so the Design Tokens job rebuilds and compares (.github/workflows/ci.yml:931: run: make design-tokens).

## Security

Two packages enter the docs dependency group and uv.lock: Playwright and axe-playwright-python, which carries axe-core. No package enters the runtime dependencies, and no module of devops-cli imports them. Only the layout step of the Docs Site Build job runs them. That job holds the permission contents: read and gets no secret, and it installs the packages from the lock with the malware check of uv on. The step installs no browser: it starts the Google Chrome of the runner image. The browser opens the built site on a loopback port, and each page asks the Google Fonts css2 API for the fonts, as the published site does. A person must confirm in the diff of uv.lock that the two packages and the packages that they need are the only new ones.
