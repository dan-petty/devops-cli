# Design

## Decisions

- **The suite replays a record. Pytest starts no server.** `docs/TESTING.md` lines 75, 76, 78 and 87 refuse a system program in a test, a skip on host state and a live service. The real side is a real valkey-py client that talks to `RecordedValkey`, which replays the answers of a real `valkey-server`. Each case runs on each host, and nothing skips.
- **The form follows the Docker engine suite.** `tests/support/valkey_scenarios.py` holds the scenarios, `tests/support/valkey_recording.py` records them, `tests/support/valkey_replay.py` replays them, and `tests/valkey/test_valkey_contract.py` runs each scenario on both sides. A reader of one suite can read the other.
- **A scenario takes a client and returns what it read.** Each scenario takes a valkey-py client: a `FakeValkey` on a fresh `FakeServer` on the fake side, and a `valkey.Valkey` on `RecordedValkey` on the real side. The test compares the two returns. Where the project `ValkeyClient` is the seam of the code under test, a scenario can take a `ValkeyClient` on the same connection pool.
- **The request bytes are stable.** `SET EXAT` uses a fixed absolute time far in the future. A `Lock` gets an explicit `token=` and a fixed `timeout`. A scenario reads the expiry back with `EXPIRETIME` or as a bounded fact, such as "the TTL is between 1 and 60", and never returns a value that changes with the clock.
- **Each scenario starts from a clean server.** It uses its own key prefix, sends `SCRIPT FLUSH` before it uses Lua, and deletes its keys at the end. The `NOSCRIPT` path of valkey-py (`SCRIPT LOAD`, then `EVALSHA`) then occurs on both sides, in each order in which pytest runs the cases.
- **The Lua cases record what valkey-py really sends.** valkey-py 6.2.0 answers `NOSCRIPT` with `SCRIPT LOAD` and a second `EVALSHA`, not with `EVAL`. One scenario uses `register_script`, and a separate scenario sends `EVAL`.
- **The record holds one exchange list for each scenario.** The recorder runs each scenario on a new connection through a proxy in front of the server, and keeps each request (the RESP command array) and each reply. The connection handshake of valkey-py (`CLIENT SETINFO LIB-NAME` and `LIB-VER`) stays in the record, because a real client sends it.
- **The replay is strict.** `RecordedValkey` binds a loopback TCP port or an `AF_UNIX` socket in the test process, which the hermetic floor allows. It serves the recorded replies of one scenario in order. A request that is not the next recorded one gets a RESP error reply and stays in `unexpected`. `remaining` counts the replies that no request took. The real side asserts `unexpected == []` and `remaining == 0`.
- **A record of another valkey-py version fails the suite.** The record keeps the server version and the valkey-py version. The suite compares the valkey-py version with the installed version and fails (it does not skip) when they differ, as the Docker suite does for its SDK. The recorder docstring gives the record command and says when to record again: a change of the valkey-py pin in `uv.lock`, or a change of a scenario.
- **The record holds no host data.** The server runs on `127.0.0.1` with no persistence. The record keeps no hostname, path, address or run ID of the host. A reply that holds such data does not go in a scenario.
- **The recording server comes from a downloaded package.** `apt-get download valkey-server valkey-tools` and `dpkg-deb -x` put the binary in a scratch folder. It starts with `--bind 127.0.0.1 --port <free port> --save '' --appendonly no --protected-mode yes` and stops when the recording ends. The host gets no package, and the change commits no binary.
- **`limits` waits for #4563.** `limits` is not in `uv.lock`. #4563 adds it, and it adds the moving-window case to this suite.

## Rejected alternatives

- **Start `valkey-server` from `PATH` in pytest and skip when it is missing (the issue body).** `docs/TESTING.md` line 75 refuses a system program in a test, line 78 refuses a skip on host state, and the floor (lines 264 and 278) fails a connect to a port that the test did not bind. `command -v valkey-server` finds nothing in the devcontainer, so the real side would never run there.
- **A row of `devops ci` that runs the real server.** Line 76 allows it, but the binary is not on the devcontainer or on a stock GitHub runner, and the owner rule gives a GitHub-hosted runner no package install. The row would skip on every host that runs it today.
- **`pytest-redis` or `testcontainers`.** Both start a real server or a container from pytest. Lines 75 and 87 refuse a system program and a live service in a test.
- **A recording against a cluster Valkey.** The cluster Valkey holds live Service state. A recording must not touch it, and line 87 refuses a live service.
- **A Lua shim in the fake.** fakeredis documents the `lua` extra for `EVAL` and `EVALSHA`. A shim duplicates a maintained library.
- **The `limits` moving-window case now.** It needs a new runtime dependency that #4563 adds with its own review. This change does not add a dependency that no code uses.
