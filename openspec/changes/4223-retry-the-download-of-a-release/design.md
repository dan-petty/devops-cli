# Design

## Decisions

- **One retry in the installer client.** `_download_client` passes `retries=8` to `http_client`. The wait of the retry transport is 123 seconds in all, so an outage of GitHub that ends within two minutes needs no rerun. The test `test_install_retries_for_at_least_one_minute_of_outage` serves 504 answers until the clock has waited 60 seconds, so a future change of the count cannot make the retry time shorter than one minute without a failing test. The tests use the clock fake, so no test waits.
- **A 4xx answer is an error at once.** The retry transport retries 429, 5xx and transport errors only. A wrong URL fails on the first try (`test_a_404_answer_is_not_retried`). The final error is `httpx2.HTTPStatusError`, whose message holds the status and the URL. `_install_single_target` prints it as `<tool>: <message>`.
- **A body that is not the archive is named before the checksum.** After the download and before `_verify_sha256`, `install_binary` calls a check for the formats `gzip`, `tar.gz` and `zip`. The check reads the first bytes: gzip starts with `1f 8b`, and `zipfile.is_zipfile` tests a zip. When the body fails, the check raises `ToolDownloadError(url, reason, tool_name=...)`. The reason reads `the body is not a <format> archive (HTTP <status>, content-type <type>)`, so a person sees the URL, the status and the cause. The status that reaches the check is the one of the last response, so `_download` returns the response data that the check needs. The format `binary` has no magic bytes: it keeps the checksum check alone. A real archive with other bytes than the lock still fails the checksum (`test_an_archive_with_other_bytes_than_the_lock_still_fails_the_checksum`).
- **The `Dockerfile` fetches `gh` with `curl` in the builder stage.** A `RUN` step installs `curl` from apt with `-o Acquire::Retries=5`, fetches the tarball with `curl -fsSL --retry 8 --retry-all-errors --retry-delay 2`, checks the pinned SHA-256 with `sha256sum -c`, and installs `gh`. The two pinned checksums and the release URLs stay in the `Dockerfile`, so the pin tests of `tests/invariants/test_service_image.py` and `tests/roadmap/test_roadmap_runner_tools.py` keep reading them. The builder stage is not shipped, so the apt package adds nothing to an image that Trivy scans.
- **The guard reads the files, not the history.** `tests/ci/test_release_download_retries.py` parses the `Dockerfile` with `tests.support.dockerfile.stages`, the workflows and composite actions with `yaml`, and `install_tools.py` with `ast`. It splits each shell script into commands and flags a `curl` without `--retry` and a `wget` without `--tries`. A test of the finder itself proves the split on nine scripts.

## Rejected alternatives

- **A `[binary.gh]` entry in `tools.lock`, installed in the builder with `devops install-tools --tool gh`.** It would give `gh` the retry of the installer. Evidence against: `tools.lock` entries are classified in `src/devops_cli/roadmap/runner_tools.py` (`ToolSource`, `NOT_IN_RUNNER`), and the tests of that table and of the Service image read the `gh` release from the `Dockerfile`. `devops install-tools` with no `--tool` would also install `gh` in the devcontainer, where the `github-cli` feature installs it. That is three more places to change for one download. It stays an option for a later change if `gh` is needed outside the image.
- **`ADD --checksum` kept, and the build rerun.** BuildKit `ADD` has no retry option, and the rerun is the cost that the issue names (about 30 minutes each).
- **A retry loop in shell or Python of our own.** `curl --retry` and the tenacity transport of the project cover the need (AGENTS.md rule 3).
- **Trivy in this change.** The scan steps use `aquasecurity/trivy-action`, which has no retry input. Setting `skip-setup-trivy` needs `uv` in six jobs and a change to the contract test of the Trivy version. That is work of its own, and #4229 holds it.
- **A smaller count with the default of 5 tries.** It waits 15 seconds in all and does not cover an outage of minutes.
