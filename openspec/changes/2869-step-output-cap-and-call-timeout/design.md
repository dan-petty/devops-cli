# Design

## Decisions

- **Two constants, set as model settings of the agent.** `build_agent` passes `model_settings` to the `Agent`. The settings merge over those of the model, so they hold for the gateway model, the Ollama model and a fallback model. The numbers are `CONST_ROADMAP_IMPLEMENT_MAX_OUTPUT_TOKENS` (16384) and `CONST_ROADMAP_IMPLEMENT_REQUEST_TIMEOUT_SECONDS` (600). The proposal shows how they follow from the measured sizes and rates. The cap is the first limit that a runaway call meets: at the lowest measured rate it ends in 431 s. The deadline is above that, and so it catches only a call that is stuck, or a tier that is too slow.
- **`request_timeout`, not `timeout`.** The `timeout` setting is the timeout of the HTTP client for each attempt, and on a stream it limits the wait for one chunk. The runaway call of #2739 sent a chunk every 15 ms for 25 minutes, so `timeout` would never fire. `request_timeout` is one clock over every attempt and the read of the stream to its last chunk, and Pydantic AI enforces it for every model, also for the `FunctionModel` of the tests.
- **A hook ends the run at the first cut reply.** `output_cap_hooks` is an `after_model_request` hook. It raises `OutputCapReached` when `response.finish_reason == 'length'`. Without it, the run goes on: Pydantic AI runs a tool call that the cap cut when the harness accepts its arguments, and the next request can reach the cap again, up to the request limit of the step (80 requests of up to 7 minutes). The hook reads a field that the library reports, and no text. The run drops a reply that a hook rejects, so the error holds the reply, and `_run_turn` adds it to the spend of the turn. The class is a subclass of `UnexpectedModelBehavior`, so the existing handler of the turn catches it, and the reason has the shape of the other stop reasons: `OutputCapReached: The model reply reached the output cap of 16384 tokens, so the call ended.`
- **No resend for these stops.** The loop in `_run_agent` sends again only a `ModelHTTPError` with the status 400 inside a stream. A `ModelRequestTimeout` and `OutputCapReached` are not that error, so they get no resend. One path stays: Ollama can fail a tool call that the cap cut with a parse error, which reaches the client as that 400. The resend is bounded by `CONST_ROADMAP_IMPLEMENT_MODEL_RESENDS`, so such a call takes at most (1 + that value) times the cap time. The step cannot tell this 400 from another: the usage of a streamed reply arrives in its last chunk, which an error replaces, and a match on the text is not allowed. A test pins the bound.
- **The deadline is per request, so the retries of the client fit inside it.** `request_timeout` covers every attempt of the client (`ai.max_retries`), so a timeout is never retried by the client and then by the router for another 600 s.
- **The instructions say that a reply has a cap.** One bullet tells the model to write a long file in parts with `edit_file`. It names no number, so the text and the constant cannot differ.
- **The reason of the deadline names the seconds.** `_model_call_reason` adds "no complete reply in N seconds" for a `ModelRequestTimeout`, from the `timeout` field of the error.
- **No change of the gateway.** The evidence is in the proposal: the step is the only client of the route in the repository, and a route cap would also cap `devops-reasoning`, which falls back to this route.

## Rejected alternatives

- **`ai.tasks.implement.max_tokens`.** The setting reaches the model only on the Ollama path of `pydantic_ai_bridge.py`. The gateway path ignores it, and its default is none, so the step would run without a cap unless a person sets it.
- **`max_tokens` in `litellm_params` of the route.** It would cap the clients that reach the route through a fallback with a number that belongs to the step, and it would put the same number in a second place. Rule 3 of AGENTS.md and the issue ask for one place.
- **The `timeout` model setting.** It limits the wait for one chunk, so a model that streams all the time never meets it (see above).
- **`asyncio.timeout` around `run_sync`.** It would cover the tool calls and the shell commands of the turn too, which have their own limit (`CONST_ROADMAP_IMPLEMENT_COMMAND_TIMEOUT_SECONDS`), and it needs hand-made code for what the library does for one request.
- **A cap in the model of the tier.** A cap in the Modelfile (`PARAMETER num_predict`) would hit every client of the model, reviews included, which make replies of 11,634 tokens.
- **Raise `OLLAMA_NUM_PARALLEL`.** It would let a runaway call and a good call share the tier, but the runaway call still runs for 25 minutes and fills the VRAM of the tier with a second context. The cause stays.
- **Match the text of the Ollama error to tell a capped tool call from another 400.** Text of a provider is not a contract, and the project does not match it (design of #2794).
