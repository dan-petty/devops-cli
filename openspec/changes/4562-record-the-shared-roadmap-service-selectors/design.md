# Design

## Decisions

- **Use Prometheus recording rules and promtool, and write the three rules by hand.**: The tool is in use, it covers the rule groups and the naming practice, and the project already runs its pinned promtool (`tests/support/promtool.py`).
- **Add the group `roadmap-service-recording` to `serverFiles.devops_cli_alerting_rules.yml` of `k8s/devops/monitoring/prometheus-rules-values.yaml`.**: The product-monitoring-content spec puts every group that selects a `devops_cli_` series in that file, and the monitoring tests load it through the merged `serverFiles`.
- **Record the three covered row work selectors only: the failed jobs of the last hour, the budget used ratio and the suspended rows.**: These three are shared by an alert, the dashboard and the start page, and the router keeps its own job.
- **Match `job=~"roadmap-service|roadmap-.+"` in each recording rule, and drop the `job` label with `sum by` or `max by`.**: One recorded series then reads the Service's series and the row pods' series, before and after the move.
- **Keep the `result` label of the jobs counter in `repo_lane_row:devops_cli_service_jobs_total:increase1h`, so the alert compares the error series with the success series of one `repo`, `lane` and `row`.**: `k8s/devops/monitoring/prometheus-rules-values.yaml:60:sum by (repo, lane, row) (increase(devops_cli_service_jobs_total` compares those two results today, and one rule for both keeps one rule for the selector.
- **Record one ratio over the spent requests and the limit, sum each side to one series, and name it `service:devops_cli_service_budget_requests_per_limit:ratio`.**: The two gauges label the scrape and the OTLP stream differently, and the dashboard panel already reduces each side to one series.
- **Name each rule `level:metric:operations`, with `_per_` and `ratio` for the ratio.**: The body requires it and the Prometheus practice page documents the level, the unchanged metric name and the operations.
- **Move the row work selectors only and keep the router health selectors on `job="roadmap-service"`.**: The router keeps the job, so its own series do not break at the move.
- **Land the recording group, its case file and its test wiring in one group, and the three alerts in the group after it.**: `_group` fails on a name that no rule file holds, and the two promtool checks read `rule["alert"]` over every group of `RULE_GROUP_TESTS`, so a group that wired the recording group first would fail its own check.
- **Verify each group with `uv run devops ci test tests/prometheus/test_k8s_monitoring_alerting.py`, and never with a case file.**: `_map_test_tree_path` selects a test only for a test module or a `.py` file, so a fixture path runs nothing and a broken rule file would pass.
- **Add each record name and `CONST_SERVICE_METRIC_BUDGET_SPENT` to `SERVED_SERIES`, and add the group to `RULE_GROUP_TESTS` with its case file.**: The tests check each selector against `SERVED_SERIES` and run `promtool test rules` for each group of `RULE_GROUP_TESTS`, and the spent gauge is absent from the list today.
- **Keep a recording rule out of the alert-rule checks with `rule.get("alert")`.**: A recording rule holds no `alert` key, so the two checks that read `rule["alert"]` fail on it, and a recording rule needs no severity and no Alerting table row.
- **Keep each requirement text under 500 characters, and carry the rule names, the ratio division and the new pod's 2 hours in its scenarios.**: The plan check refuses a requirement text over 500 characters, and a scenario holds the detail that a test asserts.
- **Give the scenario of the modified product values file requirement the test command as its `when`, and name the environment values file without a code span.**: A scenario that names a command proves itself, and the check refuses a scenario that names a config path with no behavior test.

## Rejected alternatives

- **Write a selector-to-rule generator.**: The change writes 3 rules once, and the product file holds one `serverFiles` key (`k8s/devops/monitoring/prometheus-rules-values.yaml:15:devops_cli_alerting_rules.yml:`), so a generator adds code to build and keep.
- **Add `serverFiles.recording_rules.yml` to `k8s/monitoring/prometheus-values.yaml`.**: `openspec/specs/product-monitoring-content/spec.md:23:no environment group SHALL select one` keeps a `devops_cli_` group out of the environment file, and the chart already names `/etc/config/recording_rules.yml` there at `k8s/monitoring/prometheus-values.yaml:198:- /etc/config/recording_rules.yml`.
- **Add a second `serverFiles` key to the product rule file.**: `openspec/specs/product-monitoring-content/spec.md:23:SHALL hold only` keeps the product file to the one key.
- **Add a separate PrometheusRule resource.**: The chart loads its rules from `serverFiles` (`k8s/devops/monitoring/prometheus-rules-values.yaml:14:serverFiles:`), and `k8s/devops/alerts/inbox.yaml` shows that a PrometheusRule needs the operator and another Application path.
- **Record all 32 `job="roadmap-service"` lines.**: The `references` tool counts 32 such lines in the product rule file, and the router keeps the job: `k8s/devops/monitoring/prometheus-rules-values.yaml:37:devops_cli_service_identity_refused_total` reads the Service's own counter.
- **Record the 6 lane alerts that the sweep item removes.**: The sweep removes the lane poll and the lanes, so those 6 alerts and their series go with them and the design records no rule for them.
- **Record the pending work selectors here.**: The body's `Moved to new items` names #4606 for that part, so 32 minus 3 covered lines stay out of this change.
- **Match `job="roadmap-service"` only in a recording rule.**: The job is named after the pod, as `k8s/devops/monitoring/prometheus-rules-values.yaml:18:k8s-monitoring's annotation autodiscovery scrapes its /metrics and` states, so a row pod gets another job name and the rule would stop reading the rows.
- **Match all jobs in a recording rule.**: It counts the workstation's series, which `docs/CLUSTER.md:51:the GitHub requests of the last hour` does not count.
- **Average the per-repo ratios.**: `src/devops_cli/server/service.py:216:GLOBAL_METRICS.set_gauge(CONST_SERVICE_METRIC_BUDGET_SPENT` sets one spent gauge for the whole Service, and an average of ratios is not the whole budget.
- **Record each side of the ratio and divide in the dashboard.**: The alert and the start page cannot read a Grafana division, and `k8s/devops/dashboards/devops-cli.json:322:max(last_over_time(devops_cli_service_budget_spent_requests{job=~` divides inside the panel only.
- **Aggregate each side of the ratio with `without (instance, pod)`.**: `k8s/devops/monitoring/prometheus-rules-values.yaml:133:so their instance labels differ and on() joins the two sums` shows the two sides do not share a label set, so each side is summed instead.
- **Keep free-form rule names, or separate the three parts with underscores.**: The body's acceptance criterion requires the `level:metric:operations` form for each of the 3 rules, and an underscore-separated name hides the 3 parts that the 2 colons separate.
- **Keep the budget alert on the router job.**: The budget gauges are the Service's own (`src/devops_cli/server/service.py:216:GLOBAL_METRICS.set_gauge(CONST_SERVICE_METRIC_BUDGET_SPENT`), and the rows spend them.
- **Add the recording group to `RULE_GROUP_TESTS` in the step before the rule file holds it.**: `tests/prometheus/test_k8s_monitoring_alerting.py:339:(rules,) = [group["rules"] for group in _groups() if group["name"] == name]` fails when the group is absent, so that step's own check would fail.
- **Verify a rule file or a case file with `uv run devops ci test tests/fixtures/prometheus_rules/roadmap_service_tests.yaml`.**: `src/devops_cli/commands/ci.py:1907:if path.endswith(CONST_PYTHON_FILE_SUFFIX):` maps no test for a `.yaml` path, so the command runs nothing and exits 0.
- **Keep the rule names in the text of the requirement on the recording group.**: That text then holds 747 characters, and the plan check refuses a requirement text over 500 characters.
- **Leave the scenario of the product values file requirement with `k8s/monitoring/prometheus-values.yaml` in a code span and no command.**: The plan check reports `Scenario 'The product file holds the groups that watch a devops_cli series' names `k8s/monitoring/prometheus-values.yaml` with no behavior test.`

## Security

The recording rules widen a selector from `job="roadmap-service"` to `job=~"roadmap-service|roadmap-.+"`, so a rule can read the series of any job whose name starts with `roadmap-`. A person must confirm, before the group reaches the cluster, that only the roadmap Service's pods and the `roadmap-<row>` pods carry such a job name. The rules read no credential, no private address and no secret, and the docs edit adds no address. `test_every_alert_rule_selects_only_series_the_stack_serves` and `test_each_covered_row_work_selector_has_one_recording_rule` fail if a rule reads a series that no scrape serves, and `test_each_recording_rule_name_has_three_parts` fails if a name leaves the three-part form.
