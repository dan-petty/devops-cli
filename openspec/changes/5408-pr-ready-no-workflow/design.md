# Design

## Decisions
1. **One module decides a workflow file.** `src/devops_cli/github/workflow_triggers.py` holds `PULL_REQUEST_TRIGGERS`, the `PullRequestChange` tuple (the base branch, and the changed paths or None) and `starts_on_pull_request(text, change)`. The function is pure, so the tests give it a workflow text and a change with no GitHub fake. `GitHubClient.pull_request_workflow_at(repo, ref, change)` keeps the reads of `.github/workflows` at the head commit and calls the function for each file. Reason: the client reads GitHub, and the rules of GitHub's filters are no read.
2. **The triggers are read as before.** A bare `on` key that YAML 1.1 reads as `True` is read too. A string or a list under `on:` names events with no filter, so a `pull_request` or `pull_request_target` entry there can start a check. A mapping gives each event its own filters. An event with no mapping under it, such as `pull_request:` with no value, has no filter. A file that is not valid YAML raises `GitHubUnreadError`, so the verdict keeps the pending check.
3. **The filters follow GitHub's documented rules.** For each pull request event of a mapping, the branch filter and the path filter must both take the pull request. `branches` takes it when the base branch is included, and `branches-ignore` takes it when the base branch is not included. `paths` takes it when one changed path is included, and `paths-ignore` takes it when one changed path is not included. So a pull request with no changed path is taken by neither, as GitHub starts no run for an empty diff. "Included" is the ordered rule of the docs: each pattern that matches sets the value to included, or to excluded for a pattern that starts with `!`, and the last match decides. Source: the reusables `triggering-workflow-branches1`, `3`, `4` and `triggering-a-workflow-paths1`, `3`, `4`, `5` of github/docs.
4. **wcmatch matches each glob.** `wcmatch.glob.globmatch(path, pattern, flags=GLOBSTAR | DOTMATCH | FORCEUNIX)`: `*` does not cross `/`, a `**` segment crosses any number of folders, a file or folder whose name starts with `.` matches (GitHub has no hidden files, and `.github/renovate.json` is a real change), and `/` is the separator on each host. The change does not set `BRACE` or `EXTGLOB`, because GitHub documents neither braces nor extended globs, and it does not set `NEGATE`, because decision 3 applies the `!` patterns in order.
5. **A filter that the change cannot judge takes the pull request.** Then the workflow can start a check, and the verdict waits, as before this change. The cases: the changed paths are unread, or the compare answer holds GitHub's limit of `CONST_GITHUB_COMPARE_FILES_LIMIT` files, so the list can be short; the payload names no base branch; a filter value is no list of strings; a workflow sets both forms of one filter, which GitHub refuses; a pattern holds `?` or `+`, or a `**` that shares a path segment with other characters. GitHub reads `?` and `+` as quantifiers of the character before them and `**` as any characters also inside a segment, and wcmatch does not: the probe of the proposal gives a different answer for `'*.jsx?'`, `'**.js'`, `v[12].[0-9]+.[0-9]+` and `releases/**-alpha`. Reason: a wrong "no CI" marks a pull request ready before its checks start, and a wrong wait is the behavior of origin/main, which `--force` overrides.
6. **The changed paths come from the compare read that the verdict already makes.** `assess_merge_readiness` calls `read_changed_files` before `_judge_checks` and gives the same read to the item rules later. A renamed file gives its new and its old path. Both paths make a match of `paths` more likely and make "every path is ignored" less likely, so the wait stays where GitHub may count either path. The compare of the base branch and the head commit is the three-dot diff that GitHub filters (#2530).
7. **The no-CI line names both causes.** `MESSAGES.pr.readiness_no_ci` and `MESSAGES.pr.ready_no_ci` say that no workflow of the repository can start a check on the pull request, because each workflow does not run on a pull request or its branch and path filters skip it. The line stays apart from the lines of pending and failing checks.
8. **The `types` filter stays out of the decision.** A `pull_request` event with a `types` list that holds none of `opened`, `synchronize` and `reopened` also starts no check on a new head. The issue and its comments name only the branch and path filters, and `ready_for_review`, which `pr ready` itself causes, can start a check after the command runs. The verdict keeps the wait for such a workflow.

## Rejected alternatives
- **pathspec, already a dependency.** Rejected: its gitignore rules match a pattern with no slash at each depth. The probe gives a match of `*.md` for `docs/hello.md`, but the cheat sheet of GitHub says that `'*.md'` does not match `docs/hello.md`.
- **The `NEGATE` flag of wcmatch with the whole pattern list.** Rejected: it ignores the order of the patterns. The probe gives no match of `['*.md', '!README.md', 'README*']` for `README.md`, but the cheat sheet says that `README*` includes it again.
- **Translate GitHub's patterns to regular expressions, as `pkg/workflowpattern` of nektos/act does in Go.** Rejected: that is a matcher of our own, which the issue refuses, and act has no Python package.
- **Read the workflow runs of the head commit.** Rejected: a workflow that a filter skips makes no run, so no run is the same answer as a slow workflow. The refine block of the issue rejected the wait for runs for that reason.
- **Read the required status checks of the base branch from the rulesets.** Rejected: a repository with no required check and a workflow that does run gets no wait, and the verdict marks the pull request ready before its checks start. The rulesets say what a merge needs, not what starts.
- **Read the workflows at the base branch.** Rejected: GitHub runs the `pull_request` workflow of the head, and the `pr-merge-readiness` spec reads the head commit. The refine block of the issue records the same decision.
