# Design

## Decisions
1. **One table maps each stack to its Applications.** `APPLICATIONS_BY_STACK` in `src/devops_cli/commands/k8s/stack_lifecycle.py` gives, for each stack, the names of the Argo CD Applications whose path sources deploy-stack builds and applies before the charts. The Applications come from `discover_argocd_applications(env.application_dirs)`, so the table reads the tree wherever it is: in devops-cli now, in dan-petty/homelab after #5134. A name that the tree does not hold stops the command with `ERRORS.k8s.application_not_found`, before it touches the cluster.
2. **A path stays where the build holds more.** The census of the proposal compares the objects of each row of `MANIFESTS_BY_STACK` with the build of the Application that holds them. An Application whose build holds the same objects goes into the table, and its rows leave `MANIFESTS_BY_STACK`. Each other row stays, with a comment that names the objects that the build adds. The issue states this rule for a stack. The change applies it to each Application: the builds of `argocd` and `otel` hold only the objects of their rows, and dan-petty/homelab#94 changes the build of `argocd`.
3. **The build reuses `render_path_source`.** For each Application of the selected stacks, in the order of the table, deploy-stack builds each source with a `path` with `render_path_source` and the `SourceTrees` of the deploy (#6680). A source of the `origin` of the checkout reads the checkout; a source of another repository is fetched at its `targetRevision` in the work folder of the deploy. The builds happen in `_collect_deploy_targets`, so a failed build or fetch stops the deploy before it touches the cluster.
4. **A build is a local read.** `build_manifest_path` and `render_path_source` get the keyword `local_read`, which they give to `run_subprocess` for `kubectl kustomize`. deploy-stack and teardown-stack set it, so the dry run builds the folders of the checkout, as the real run does. `devops k8s image-pins` and `devops k8s security-audit` keep the default: their dry runs build nothing, as before. A source of another repository gets no build in a dry run, because `SourceTrees` fetches nothing then.
5. **The deploy applies the build as one stream.** After the ConfigMap and the manifest paths of step 7, deploy-stack applies each build that holds an object with `kubectl apply -f -`, with the build as input. It replaces the template domain in the build as it does in a manifest file, so a build and a file give the same objects. A build with no object is not applied, as Argo CD applies nothing for it.
6. **The teardown deletes the build.** `teardown-stack` makes the same `SourceTrees` in a work folder and builds the same sources. It deletes each build with `kubectl delete -f - --ignore-not-found`, in the reverse order of the deploy, after the post-Helm paths and before the manifest paths.
7. **The dry run lists the objects.** The key `details.path_sources` of the deploy dry run gives, for each build, the Application, the `path` of the source and the objects of the build: `kind`, `namespace` (null for an object of the cluster scope) and `name`, in the order of the build. The objects are null for a source of another repository, whose fetch `details.source_fetches` lists. The teardown dry run gives the same entries in `details.path_source_deletes`, in the order of the deletes, and also `details.source_fetches`.
8. **Tests.** A new test of `tests/commands/k8s/test_k8s.py` writes a tree under `tmp_path`: the fixture Application `logging` with the path source `env/logging`, whose kustomization takes the local component `env/components/perimeter`. The process fake gives the build of `kubectl kustomize`, because a test starts no program (ADR 0007): two NetworkPolicies, one of them from the component. The dry run lists both objects, and the real run applies the build with `kubectl apply -f -` and deletes it with `kubectl delete -f -`. `tests/support/k8s_tree.py` gives the folders of the table to the gate rows that read what deploy-stack applies (`network_policies.py`, `monitoring.py`), and `tests/gate/k8s_checks/deploy_stack.py` reads them for the ServiceMonitor check. The tests that start deploy-stack or teardown-stack on a tree with no fake of `kubectl kustomize` get the process fake, or an Application of the table.

## Rejected alternatives
- **Keep the fixed list of a full stack when one Application differs.** Rejected: the census shows that the builds of `argocd` and `otel` hold the objects of their rows and no other object, and dan-petty/homelab#94 needs the build of `argocd` on a cluster without Argo CD.
- **Apply the build of `llm` and `argo-workflows-manifests` without the objects of `POST_HELM_BY_STACK`.** Rejected: the issue asks to keep the fixed list when a build holds more objects. A filter of the build by the post-Helm paths is a second list of the same objects, and the post-Helm step is not in the scope of the issue.
- **`kubectl apply -k <folder>`.** Rejected: a folder of another repository is in the work folder of the deploy, and a teardown after the deploy has no such folder. `apply -k` also does not take the domain of the templates, which `_apply_single_manifest` replaces in a file.
- **Build in the dry run with `local_read` as the default of `render_path_source`.** Rejected: the test `test_a_dry_run_renders_and_resolves_nothing` of `tests/k8s/test_image_pins.py` states that the dry run of `image-pins` renders nothing.
- **Skip an Application that the tree does not hold.** Rejected: a missing perimeter NetworkPolicy then goes away with no message. A chart with no Application stops the command in the same way (#6060).
- **Find the remote bases of a kustomization before a dry-run build.** Rejected: Kustomize has no option that refuses a remote base, and a parser of the kustomization fields would copy the loader of Kustomize. The current tree holds no remote base (`git grep` of `://` and `?ref=` in the kustomization files finds none). A kustomization of the checkout that names a remote base makes Kustomize fetch it, also in a dry run.
