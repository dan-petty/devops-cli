# Design

## Decisions

- **One class for one fact.** `GitHubNotAnIssueError(repo, number, operation=...)` in `src/devops_cli/exceptions/git.py` is the error of a number that is no issue of the repository. It is a `GitHubNotFoundError`, so each handler of a 404 takes it. It keeps the message `#<number> is not an issue of <repository>.` and the details `repo` and `number`, and it holds `number` as an attribute. `GitHubRoadmapStore._not_an_issue` makes it for each case that raised `GitHubOperationError` with that message: a missing issue, a pull request, a refused answer of a read and a refused answer of a `PATCH`. A caller has one class for the fact, with no second class for a refused answer.
- **Left out is a result of the item.** A row that works on many items catches `GitHubNotAnIssueError` at the loop of its items and compares `number` with the number of the item. For that item it records no check, no write and no failure, and goes on. An error that names another number is a failure of the item as before. The store has dropped the record before it raises, so the next round does not select the item.
- **The statuses of one issue number.** `NO_ISSUE_STATUSES` of `src/devops_cli/github/issue_answer.py` holds 404, 301 and 410, the statuses that the REST reference of "Get an issue" gives for an issue that is no issue of the repository. `_read_issue` and `_revalidate_issue` of the store, the read of the release feed and `GitHubClient.get_issue` take them as no issue. `_listing_below` takes them only as a reason to read the issue. `_listing`, `_read`, `_write` and each other call of `_read_or_none` keep their statuses, so a listing of the repository or another route that answers 301 or 410 fails.
- **A renamed repository is this repository.** GitHub redirects each route of a repository that was renamed or moved to another owner. An issue answer under the old name then holds the requested number and the new name. With the comparison of #7331 alone, each such answer read as "the issue left", each record was dropped, and with this change no row failed: the rounds were green and did nothing. So `CurrentName` reads `repos/<configured name>` for the first answer that holds a requested number and another repository name, one time in the life of a store, a feed or a client. GitHub redirects that read to the same repository, so its `full_name` is the name of that repository now. When it is the repository of the issue answer, the answer is the requested issue: the reader takes it and logs one warning that the configured name is old. This keeps the guarantee of #7331. That guarantee is that an answer for another issue never becomes the record of the requested number. An issue is one number of one repository, and a rename changes neither. The answer of a transferred issue names a repository that is not the configured one under any name, so `full_name` differs and the answer stays refused, also when the issue kept its number. When GitHub gives no repository for the name (404), or `gh` does not follow the redirect of the name read (301), nothing proves the rename, and the answer is refused.
- **Why the status 301 is safe when a repository is renamed.** When `gh` does not follow a redirect, the read of an issue under the old name ends with 301 and gives no issue, and the name read ends with 301 too. No write goes to an issue, because each write reads the issue first, and the store logs each number that it leaves out, so the cause is in the log. The listing of the issues is read through the session: a record that a store dropped comes back at the next full read of a store with the right name.
- **A status of no issue below a number is checked.** `_listing_below` reads the listing of `comments_on`, `label_changes` and `blocked_by`. GitHub answers such a listing with 404 for a transferred issue and with 410 for a deleted one, and the session puts the status in the details of its error (`says_no_issue`). For a status of `NO_ISSUE_STATUSES` the store reads the issue with `_read_issue`. No issue of the repository: `_gone` ran, and the call raises `GitHubNotAnIssueError`. An issue or a pull request of the repository: the error of the listing is raised again. So one 404 of a comments route drops no record of an issue that the repository holds. The read also gives the place of a transferred issue for the log line. `comment` reads `comments_on` for a job comment before it posts, so such a comment is refused before the write.
- **One log line.** `_gone(number, answer, status=...)` logs one warning for a number in the life of a store (`_left`): when the listing of the store held the record, when the payload of another issue came for it, when the read answered 301 or 410, which say that the number was an issue, and when the store read no listing. So the store of a stage Job, whose new listing does not hold a transferred issue, logs the change folder that it leaves out. The one case with no line is a 404 for a number that the listing of the store does not hold. The line is `#7 is no issue of acme/widgets now: GitHub answers with acme/other#12. The store leaves it out.` The place is `RepoRef.display` and the `number` of the payload model, two validated values. No other field of the answer is in a log line. A row adds no line. This replaces the two warnings of #7331 and its rule that no log line holds a field of the answer: the acceptance criteria of #7337 ask for the new repository and the new number in the line.
- **The webhook path.** `issue_left(event, action)` of `src/devops_cli/models/webhooks.py` holds the event `issues` with the actions `transferred` and `deleted`. For such a delivery the route calls `forget_issue` with the visibility of the delivery, and writes no entry from the payload. The route refuses a delivery of the bot of the App before it reads the event name, and it brings the entry up to date from that payload: `GitHubWebhookPayload.says_issue_left` tells such a payload by its issue, its action and no comment, and the route removes the entry there too. `RepoWorker.enqueue` puts the subject of such a trigger in `TriggerBatch.left`, and `service_job` calls `listing.drop` for each number before it opens the store, with one log line for each. The worker of a lane is the one writer of its listing, so the drop needs no lock, and it costs no GitHub request. `IncrementalListing.read` already takes a number back when GitHub lists it as changed, so a wrong delivery repairs itself.
- **One comparison for three readers.** `answered_repository` and `answers_request` move from `github_store.py` to `src/devops_cli/github/issue_answer.py`. `GitHubReleaseFeed._issue` gives None for an answer of another issue and for a status of `NO_ISSUE_STATUSES`. `GitHubClient.get_issue` raises `GitHubNotAnIssueError` for an answer of another issue, for the status 410, and for a 301 that the session does not follow. Its 404 stays the `GitHubNotFoundError` of the session. `IssueView` and the payload of the feed get the three URL fields.
- **The stage job.** `open_plan_creates` and `issue_listing` take None of `store.item` as no open plan and as no record of the listing, and the status 301 now gives None, so no code of these two reads changes. The planner reads the comments of each item first. `item_left` tells an error of `ITEM_ERRORS` that is the error of no issue for the number of the item: `_plan_each` then gives the item no result and plans the next one, and `_decide` of `prepare` ends the run of the Job with no result. Before, the error made a `StageFailure` with the class `ci_infra`, and the mark write of that failure raised and ended the round.
- **Fakes.** `GitHubFake.move_issue(..., followed=False)` answers the issue route with `gh: HTTP 301`. `RunnerSession` raises `GitHubNotFoundError` for a 404 of a listing, as the real session does. `InMemoryRoadmapStore` raises `GitHubNotAnIssueError` and reads the class from the module of the errors, because a replay of the tests on the base tree loads the fake with a source tree that has no such class.

## What each row does for an item that is no issue of the repository

| Row | Result |
| --- | --- |
| `alternatives` | Left out by this change (`_settled`). |
| `implement` | The Status sweep, the clear of the closed issues and the stop pass leave it out (`write_each`). The plan (`retry_asked_on`), `_note_needs_fix` and `service_claim` raise as before, one time for each item of the listing: the store drops the record at that read. The report of an ended Job raises `LookupError` (`_fresh`) while the cluster holds the Job of such an item, because the Job gives the number and the listing does not. |
| `stage` | The planner and `prepare` of the stage job leave it out (`item_left`). The removals of `StageWriter.begin` leave it out (`write_each`), and the recovery of a Job did so before (`stage_job.py`). A rejection raises as before, one time: `plan_return` raises a plain `DevOpsCLIError` for an item that the store does not give, and the record of that failure then raises. `service_claim` of `_submit` raises as before, one time. |
| `mark_stage_ready`, `devops roadmap repair` | Left out (`write_each`). |
| `plan_drift` | Left out by this change: the row reads the issue of a plan through `GitHubClient.get_issue`. |
| `release_comments` | The feed names no such number now, so the row writes no comment for it. |
| `metrics` | `_read_item_ages` catches the error of the label read for the whole read, so the row does not fail. The store now drops the record at that read, so one round has no item ages. |
| `watch`, `open` | A `set_marks` of an item raises as before, one time for each item of the listing. `sync_status` leaves the item out as before. |
| `refine`, `retitle`, `fix_plan` | A read or a write of the item raises as before, one time for each item of the listing: the store now drops the record at a 404 of the comments too. |
| `intake` | The first read of a candidate is `closures`, a timeline read, which drops no record (see below). Its placement writes record a failure for the item as before. |
| `github_status`, `cloudflare_status` | They read no item. |

## What the change leaves

- **The rows that still raise one time.** The table names them. Each needs a handler at the loop of its items and a test of its own. With the webhook path the lane drops the record before a row reads the item, so these rows see such an item only when the delivery did not arrive.
- **The timeline reads.** `closures` and `last_renamed_at` read the timeline with GraphQL. Their failure for a missing issue has no HTTP status, and a test of the text of an error would be a second rule. Intake, refine and retitle call them.
- **The writes that read no issue.** `label_issue`, `unlabel_issue` and `edit_comment` send their request with the number of the caller. `comment` reads the comments only for a job comment.
- **The fields of `changes` of a `transferred` delivery.** The log line of a delivery names no new place, because the documentation gives no form for these fields.
- **The CLI readers.** `get_repository_issue` and `resolve_updated_labels` of `src/devops_cli/github/issues.py` (`devops gh issue view`, `devops gh issue edit` and `devops openspec new`), the answers of the issue writes of `src/devops_cli/commands/gh.py` and `src/devops_cli/commands/pr.py`, and the funnel of `devops roadmap eval` (`src/devops_cli/roadmap/job_funnel.py`) read one issue number for a person at a terminal and compare nothing. They run in no row and in no Job.
- **An orphan plan pull request.** `run_plan_drift` leaves out a plan pull request whose issue read raises `GitHubNotFoundError`. That class is wider than the left case: it also holds a 404 of an issue that never was one. No row closes a plan pull request whose issue left, so the row logs one warning for it in each round.
- **The two change folders.** The active change folders of the two transferred issues stay on the default branch. Their removal is a separate cleanup.

## Rejected alternatives

- **Catch the error of a row in the row runner and run the row again.** `run.py` has one `except Exception` for each row (`_run_due_rows`). A handler there for `GitHubNotAnIssueError` would cover each row with one change. But a row that ends in the middle has done a part of its work, and a second run repeats its reads: the selection of `refine` lists the comments of each Ready item (`refine.py`, `raw_comments_on`). The result of the item would also be an effect of the runner and no result of the row.
- **Give `[]` for a 404 of `comments_on`.** The caller then works on the item with no comment and writes: the alternatives round would call the model for an item that is no issue. `test_an_alternatives_round_leaves_out_an_item_whose_comments_answer_404` asserts that the model sees no request.
- **Drop the record at each 404 below a number, with no read of the issue.** The 404 of a comments route does not say why, and the answer gives no new place. The acceptance of #7337 needs the new repository and number in the log line for the case "redirect on the issue route, 404 on the comments route", which only the issue read gives.
- **Carry the drop of a delivery with a registry of the listings of the process.** `IncrementalListing` keeps the numbers that left for each lane (`_left`), and a full read of one lane clears only its own set (`listing_snapshot.py`). A set that the lanes share would let the full read of one lane list the record again in another lane. The batch gives each lane its own drop.
- **Read each subject of a batch again to find the numbers that left.** A deleted issue answers 410 and a transferred one costs one request for each lane. The delivery already says which number left.
- **Take each answer with the requested number.** #7331 rejected it: a transferred issue can get, at its new place, the number that it had. `test_a_transferred_issue_that_kept_its_number_is_refused` holds four such cases.
- **Read the name of the repository when a store starts.** A store lives for one round of one lane, so this costs one request for each round of each lane. `CurrentName` reads the name only for an answer with the number and another repository name, which a repository with its configured name does not give: `_name_reads` of the store tests counts one read for many answers and none for an answer of the configured name.
- **Follow the redirect in the store.** The answer of a followed redirect is the issue at another place, which #7331 refuses. A second request would give the same result as the status 301 alone.
