# Design

## Decisions

- **The memory bound of `valkey-devops` is `--maxmemory 256mb` inside a container limit of `384Mi`.**: The owner comment of 2026-11-19 on #4668 found four targets that do not agree (ADR 0023 line 134, #4624 item 6, the refined design of #4624, and the body of #4668). Only 256mb inside 384Mi keeps the owner decision 6 of #4624 (256 MB) and the rule of `openspec/specs/llm-valkey/spec.md` that `--maxmemory` is at most three quarters of the limit: 256 MiB is two thirds of 384Mi. The pull request comment on #4668 names this target and says that 240mb/320Mi and 256MB/320Mi in the bodies are replaced. The bodies of #4668 and #4624 stay as they are.
- **ADR 0023 does not change.**: Its line 134 already says that the item raises the `maxmemory` of `valkey-devops` from 96 MB to 256 MB, which is the decided bound, and it names no limit. `docs/adr/README.md` forbids an edit of the body of an accepted record, and `tests/invariants/test_adr_records.py` fails on a changed body hash. A Status History line is only for a fact that a change makes wrong, and no fact of the record becomes wrong. The limit is a value of the manifest and of the spec of this change, as the length rule of the ADR README asks.
- **The memory bound has a validator command and a live check as its proof, and no test.**: `docs/TESTING.md` forbids a test that asserts a value of a manifest, and the `test-tree` row refuses one (`tests/gate/tree_checks/config_values.py`). The proof is `uv run devops ci --check --only k8s` before the merge, and after the Argo CD sync `kubectl -n llm get deployment valkey-devops -o jsonpath=...` (the `--maxmemory 256mb` argument and the `384Mi` limit) and `redis_config_maxmemory{job="valkey-devops"}` at 268,435,456.
- **`TieredMapping` is a `MutableMapping` over a `cachetools.TTLCache` and the `ValkeyCacheTier`.**: No library gives a mapping over an in-process LRU and a Valkey tier with a breaker, a schema check and a bound for each value. As a `MutableMapping`, it plugs into `cachetools.cached`, so `_read_pypi` and `_linked_packages` keep their bodies and get a decorator. `__iter__` and `__len__` cover the in-process tier only, because a scan of the shared tier for each call has no use.
- **A read goes memory, then Valkey, then the source, and a hit fills the tiers above it.**: ADR 0023 section 2 sets this order for content-addressed data. A write goes to Valkey and then to memory. A failed Valkey write is a later miss, never an error of the caller.
- **The mapping encodes each value through a pydantic `TypeAdapter` of its value type, and stores the schema key of that type in front of the value (`<schema key>:<JSON>`).**: The facts are small JSON texts, so the mapping does not compress them; the snapshot store compresses its records itself. The keys are text, so each `cachetools.cached` read gives a `key` function. A reader that finds another schema key, or a key of an older kind version, treats it as a miss, reads the source and writes the value under the current key. This is the rule of T6. The schema key is the first 16 hex characters of the sha256 of the JSON schema of the type, as `LISTING_SCHEMA_KEY` already does for the snapshot.
- **A value over 1 MiB stays in the in-process tier.**: The mapping measures the encoded value before it sends it. Over the bound, it sends no command, keeps the value in memory and counts `devops_cli_brain_writes_total{result="oversize"}`. ADR 0023 section 2 says that a value over 1 MiB stays local. `cachetools.cached` ignores a `ValueError` on a write, so the mapping does not raise one.
- **Each key has a TTL.**: Each write of the mapping sends `SET ... EX <ttl>`, and each write of the snapshot store ends with `EXPIRE` in the same MULTI/EXEC. The facts get 24 hours (`DEFAULT_BRAIN_FACT_TTL_SECONDS`) and the snapshot 7 days (`DEFAULT_BRAIN_SNAPSHOT_TTL_SECONDS`). A temporary key of a full write gets 600 s, so a killed writer leaves no key without an end.
- **`ValkeySnapshotStore` is the Valkey implementation of the `SnapshotStore` protocol.**: The protocol of #4552 is the seam that `IncrementalListing` reads, so no caller changes. `FileSnapshotStore` keeps one JSON file and cannot hold a shared copy. The hash `valkey:roadmap:v1:snapshot:<owner>/<name>` holds the field `meta` (`schema`, `full_at`, `watermark`) and one zlib JSON `IssueRecord` for each issue number. One field for each record keeps each value under the bound: the snapshot of devops-cli is 14.13 MB with zlib, and its largest record is 23,700 B with zlib.
- **`TieredSnapshotStore` combines the local and the shared store.**: ADR 0023 section 2 says that a reader loads the local and the shared copy, drops a copy with another schema or a full read older than 24 hours, and takes the copy with the newer watermark. The rule needs both copies at one place, so it is a store of its own and not a change of `IncrementalListing`. A save writes the shared tier first and then the local file, the order of ADR 0023 section 2.
- **The newest watermark wins.**: A writer WATCHes the snapshot key, reads `meta`, and writes in one MULTI/EXEC only when its watermark is not older than the stored one, or when the stored copy has another schema. An EXEC that another client made fail writes nothing, and the writer does not retry: the other writer is newer or equal. This is the safe stop of ADR 0023 section 4.
- **A save writes only the changed fields when it can, and a full write goes through a temporary key and RENAME.**: The store keeps a digest of each record that it loaded from or wrote to the shared tier in this process. When the stored `meta` is the `meta` that the store last saw, it sends `HSET` for the changed records, `HDEL` for the removed ones and the new `meta`. In every other case (a full read, no shared copy in this process, or a changed `meta`) it writes all records to `<key>:next:<token>` in pipelined batches and then, under the WATCH of the snapshot key, RENAMEs the temporary key onto it and sets its TTL. A full read so removes each issue that left the repository.
- **A load reads `meta` first, then the records with `HSCAN COUNT 500`, within a budget of 20 s.**: The budget (`DEFAULT_BRAIN_SNAPSHOT_LOAD_BUDGET_SECONDS`) is checked between two scans. Past it, the load is a miss: the reader takes the local copy or reads GitHub, and the store counts `devops_cli_valkey_cache_errors_total{op="hscan",error="budget"}`. Each command keeps the 2 s bound of `valkey.timeout`, which is shorter than the budget, as ADR 0023 section 2 asks. The values come back as bytes through `NEVER_DECODE`.
- **The shared tier holds data of public repositories only.**: ADR 0023 section 8 keeps a private repository in the local tier until `valkey-devops` has role ACL users (#4704). `TieredSnapshotStore` asks a visibility check before it uses the shared tier for a repository. The check reads `isPrivate` through the GraphQL query of `is_private_args`, once for each repository and process in each hour (`DEFAULT_BRAIN_VISIBILITY_TTL_SECONDS`). A failed read counts as private and is not kept. The store reads the visibility only after the shared tier answered the read of `meta`, so a run with no reachable Valkey, such as a workstation, sends no visibility read. For a private repository the store drops what that read gave, reads no record, writes no key and counts `result="private"`.
- **The fact cache reads public sources only.**: PyPI and deps.dev answer the same text to each client. The key is `valkey:brain:v1:fact:pypi:<name>` with the name in the canonical form of `packaging.utils.canonicalize_name` (ADR 0023 section 6), and `valkey:brain:v1:fact:deps-dev:<project>` with the deps.dev project key in lower case. An answer of "no such package" is a fact too, with the same TTL. A failed read raises as before and keeps nothing.
- **The tier commands that this item needs go into `ValkeyClient` and `ValkeyCacheTier`.**: `hget`, `hset`, `hdel`, `hscan`, `expire`, `unlink`, `rename` and `watch_and_write`. The tier keeps one client, one pool and one breaker for each process, so the new stores share the cooldown of the embeddings and the threat-intel caches: while Valkey is down, the process makes one connection attempt in each cooldown.
- **The read of a binary value uses `NEVER_DECODE`.**: The pool of `ValkeyClient` decodes each reply as UTF-8 with `encoding_errors="replace"`, which spoils zlib bytes. valkey-py gives the per-command option `NEVER_DECODE`, and fakeredis 2.40.0 honours it. A write of bytes needs no option, because the encoder sends bytes as they are.
- **Four counters, each with bounded labels.**: `devops_cli_brain_reads_total{store,result}` with `store` in `snapshot`, `fact` and `result` in `memory`, `shared`, `source`, `fallback`, `private`. `devops_cli_brain_writes_total{store,result}` with `result` in `shared`, `skipped`, `oversize`, `older`, `private`. `devops_cli_valkey_cache_errors_total{op,error}` with `op` the command and `error` in `timeout`, `connection`, `auth`, `reply`, `open`, `budget`. `devops_cli_brain_github_requests_saved_total{store}` with `store` in `snapshot`: a load that takes the shared copy when the local copy is missing or unfit adds the page count of the full read that it saves (the record count over `DEFAULT_GH_REST_PER_PAGE`, rounded up). The body names three counters. The fourth counts the skipped writes that the body asks to count ("each write is skipped and counted").
- **The error counter has no label `instance`.**: The collector sets the labels `job` and `instance` from the resource after it copies the attributes, so an attribute `instance` never reaches Prometheus, and `test_no_emit_sends_an_attribute_that_the_resource_sets` (`tests/telemetry/test_telemetry_instruments.py:480`, #3240) refuses an `emit` that sends one. Each process has one cache tier, so the label would hold one value.
- **The load time of the shared snapshot is measured against a temporary Valkey pod.**: The build starts a hardened pod of `valkey/valkey:9.1.4-alpine` (the image tag of the live `valkey-devops`) in namespace `llm`, with `activeDeadlineSeconds`, forwards a loopback port to it, writes the 6,571 records of the local devops-cli snapshot through `ValkeySnapshotStore`, and times a cold load. Then it deletes the pod and stops the port-forward. It never reads or writes the live `valkey-devops`. The same pod records the new contract scenarios.
- **The live drill waits for the release.**: The drill (`valkey-devops` at 0 replicas for 10 minutes; no job fails; the share of `result="fallback"` shows in Prometheus) needs the merged code in the cluster. The pull request body names it as the live check after the release, and `tasks.md` names it as a check for a person.

## Rejected alternatives

- **The bound 240mb inside 320Mi (the refined design of #4668).**: It breaks the owner decision 6 of #4624, which sets 256 MB.
- **The bound 256mb inside 320Mi (#4624 item 6).**: 256 MiB is 80 % of 320Mi, over the three-quarters rule of `openspec/specs/llm-valkey/spec.md:20`.
- **Keep 96mb inside 128Mi.**: The old pod peaked at 95.97 MiB and evicted 3,600 keys in 7 days before this item adds about 15 MB of snapshots.
- **Edit line 134 of ADR 0023.**: `docs/adr/README.md` ("An accepted record does not change") forbids it, and the body hash test fails on it.
- **One JSON value for the whole snapshot.**: 14.13 MB with zlib, over the bound of 1 MiB.
- **One key for each issue.**: A load of 6,571 keys costs 6,571 commands or one MGET of 6,571 keys with no TTL for the set, and a full read cannot remove a gone issue in one step. A hash reads 500 fields in each `HSCAN` and renames as one key.
- **Base64 text in place of bytes.**: It adds a third to each value (14.13 MB to about 18.8 MB) and to each load. `NEVER_DECODE` gives the bytes with no second pool.
- **A second connection pool with `decode_responses=False`.**: It doubles the connections and splits the breaker of the process.
- **`Valkey.transaction()` of valkey-py.**: It retries on `WatchError`. An older writer must lose, not retry.
- **A Lua script for the watermark check.**: ADR 0023 section 4 names WATCH, MULTI/EXEC and RENAME, and a script would carry the 14 MB of a full write as its arguments.
- **A `SET NX` lock key for the writer.**: A killed pod leaves the lock, and its TTL can end while a writer holds it.
- **The last writer wins.**: A pod that started earlier can write over a newer snapshot and lose issues.
- **Change `IncrementalListing` to read two stores.**: The protocol of #4552 already isolates the place of the snapshot. A store that implements it keeps every caller and the tests of `IncrementalListing` as they are.
- **Replace `FileSnapshotStore`.**: The local tier is the fallback when Valkey is down, and a workstation has the local tier only.
- **hishel as the cache of the GitHub answers.**: It is a shared cache by default, and the GitHub answers are private with `Vary: Authorization` (ADR 0023, Considered Options).
- **Page ETags for the listing.**: Each new issue changes the ETag of every page (#4552).
- **Search and page caches on the mapping in this item.**: SearXNG (`search.searxng_url`) and Crawl4AI (`crawl4ai.url`) run in the cluster and count no request against a quota, and `DEFAULT_SEARCH_PROVIDERS` asks SearXNG first. #4672 records that SearXNG carries the check and that Firecrawl answered 0 searches in 7 days. A shared cache of their answers saves no counted request.
- **Caches of GitHub answers (the SBOM of the inventory, the ADR index, the repository facts) on the mapping.**: ADR 0023 section 2 keeps the stored GitHub answers in the process until the two-token probe of ADR 0021 section 6 passes. The conditional item of #4624 holds them.
- **A per-process LRU only for the facts.**: Each release restarts the Service, and each Job is a new process, so an LRU alone is cold at each start.
- **The label `instance` on `devops_cli_valkey_cache_errors_total`.**: The collector replaces it with the label of the resource, and the test of #3240 refuses it, as the decision above says.

## Unchanged references

- `src/devops_cli/commands/roadmap.py` (`intake_listing(full=full)`): The factory keeps its signature and gives the tiered store.
- `src/devops_cli/roadmap/run.py` (`intake_listing(state_dir)`, `lane_listing(state_dir, lane)`): The factories keep their signatures. Each lane keeps its own local file, and the lanes of one repository share one shared copy under the newest-watermark rule.
- `src/devops_cli/server/routes/webhooks.py` (`intake_listing(state_dir)`): The scoped intake keeps its call.
- `src/devops_cli/roadmap/stores/github_store.py` (`IncrementalListing.read`): The store keeps its call of `read(repo, read_issues)`.
- `src/devops_cli/ai/rag/embeddings.py`, `src/devops_cli/ai/rag/library_store.py`, `src/devops_cli/security/vulnerability_lookup.py` (`ValkeyCacheTier.get`, `set`): They keep the two methods that they use, and share the breaker with the new commands.

## Security

The shared tier gets the listing records of public repositories and the facts of public packages. Each client of `valkey-devops` uses one password and the default user until #4704 adds the role ACL users. So the store writes no key of a private repository and never uses a shared copy of one: it reads only the `meta` field of the key before the visibility check, and drops it. A failed visibility read counts as private. `test_no_key_of_a_private_repository_is_written` fails if this guard widens. The keys hold the repository name and the package name, never a token, a body of a private issue or a hostname. The values that a reader loads are untrusted: each one goes through the pydantic model of its type, and a value that does not parse is a miss. A person must confirm that the visibility check fails closed and that the store sends no write and no record read for a private repository.
