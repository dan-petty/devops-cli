# Design

## Decisions

- **Write the names on one `Adds:` line under the line of the kind and the files of the group, each name in a code span and separated by a comma.**: `group_text` already writes one structured line per group, and the plan reader already reads the kind and the files from that line, so one writer and one reader hold the fact and the stage prompt asks for one more line of the same shape.
- **Parse the line once in `TaskGroup.added_names` and `adds_problem` of `src/devops_cli/roadmap/step_files.py`.**: The plan reader and the implement job both read `parse_task_groups`, so one parser decides the names for both and two parsers cannot disagree about one plan.
- **Hold the names in the `adds` field of `StageGroup`, which `render_change` writes and `read_change` reads back.**: `file_facts` compares the reply of the model with the files of the change folder, and a fact that no field holds is lost in that comparison.
- **Add the `adds` field, write the line, and name the field in `roadmap_stage_change.md` and `roadmap_stage_split.md` in one group.**: Two prompt tests compare each prompt with the fields of `StageGroup` (`test_a_stage_prompt_names_each_kind_and_each_field_of_a_group` and `test_the_keys_of_a_group_in_the_prompts_are_the_fields_of_a_group`), so a field with no prompt line fails them and a prompt line with no field fails them too.
- **Refuse a malformed `Adds:` line in `read_change`, and refuse `adds` on a group that is not a behavior group in the schema of `StageGroup`.**: `check_proposal` takes a validated `StageProposal`, so the schema judges the reply of the model and the reader judges a hand-written file; the plan check reports the refusal of the reader as a read problem of `tasks.md`.
- **Keep `false_premises` and change it to read `TaskGroup.added_names`, delete `added_guard` with its two patterns, and delete its table test and the guard-add fixtures that read the prose rule in the same group.**: One function holds the check and three test modules hold its cases, so the prose rule and every test that reads it go together and the verify command of the group passes.
- **The shared fixture `_guard_tasks` writes the `Adds:` line of its argument, not a fixed name.**: The helper builds the group of a false premise from `_delivery_title` and the group of a true premise from `_missing_guard`, so a fixed name would return the item of the true premise.
- **Skip a code span of the line that is no identifier.**: `definition_lines` reads the definition of one identifier, so a span such as `TaskGroup.added_names` gets no check, as the prose rule skipped such a span before.
- **Keep the check for a behavior group only, and keep the return to New with the definition line.**: A group of another kind adds no product guard, and a person needs the definition line to judge the return.

## Rejected alternatives

- **Keep the prose rule of `added_guard` and add more add verbs and words to it.**: `src/devops_cli/roadmap/premise.py:def added_guard` reads a fixed list of add verbs and the word guard or check directly before one code span, so a task that writes the guard with no such word names no added identifier, and a task that names a guard beside the change returns the item for no defect.
- **Write the names in YAML front matter of the group or of the change folder.**: The reader of `src/devops_cli/roadmap/plan_read.py` reads markdown lines of the group text and no parser of the plan reads front matter, so a second parser would decide the names and the stage prompt would ask for a form that the writer does not hold.
- **Read the names from the reply of the model only, and write no line in `tasks.md`.**: The implement job reads the plan at the branch tip through `parse_task_groups` of `src/devops_cli/roadmap/step_files.py`, so a name that no line of the tasks file holds is not there for it.
- **Add the `adds` field in one group and change the stage prompts in a later group.**: `tests/roadmap/stage/test_roadmap_stage_kind.py:def test_a_stage_prompt_names_each_kind_and_each_field_of_a_group` and `tests/roadmap/stage/test_roadmap_stage_prompt_rules.py:def test_the_keys_of_a_group_in_the_prompts_are_the_fields_of_a_group` read `StageGroup.model_fields` against both prompts, so the field alone fails them and the prompt alone fails them too.
- **Add a test that a behavior group whose `Adds:` line names an undefined guard runs the group, with no other guard in the task text.**: The base runs such a group already, because `added_guard` finds no guard in its prose, so the test passes on the base and proves nothing about the `Adds:` line; the plan's test names the defined guard `_delivery_title` in the task text as well, so the base returns the item and the test fails on the base.
- **Leave the guard-add fixtures of `tests/roadmap/implement/test_roadmap_implement_checkpoint.py` and `tests/roadmap/implement/test_roadmap_implement_typed_result.py` as they are, and let them keep the prose rule.**: `read_file` of both modules shows a behavior group whose task text says `Add the guard _delivery_title` with no `Adds:` line, so once the prose rule goes `false_premises` reads no name and `test_the_check_withdraws_the_checkpoint_of_group_one` and `test_typed_result_a_return_to_new_writes_returned_as_its_last_mark` fail.

## Unchanged references

- `src/devops_cli/roadmap/implement/implement_run.py` (import): The module imports `false_premises`, which stays, and never names `added_guard`, so the deletion changes only the docstring of `_check_premise`.
