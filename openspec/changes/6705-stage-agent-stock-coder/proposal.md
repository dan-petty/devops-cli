# Proposal

## Why

The stage planner is a custom engine: its own read tools (`stage_tools.py`), a toolbox (`stage_toolbox.py`), gate returns, a gate extension and a schema retry (#6705). The owner decided that stage runs on the stock `Coder` agent of pydantic-ai-harness with upstream `RequireVerification` (#6528, comment 7053539044). On 2026-11-23 the owner decided that #6705 builds the `Coder` agent together with the phases `prepare`, `agent` and `publish` of the stage Job, as one design (#6705, comment 7090472687). The `Coder` agent has a real shell, so it runs only in an `agent` phase that holds no GitHub credential. CronJob `roadmap-stage` runs the whole Job in one container with the App key until #6814 splits it, so `--phase all` keeps the current engine in one process until then.

## What Changes

- `devops roadmap stage --job-item <n> --confirm` takes `--phase prepare|agent|publish|all` and `--work <folder>`. `all` stays the default and runs `run_stage_job` in one process with no run file, as on `main`. A phase other than `all` needs `--job-item`, `--confirm` and `--work`. `--source` goes only with `prepare` and `all`.
- `prepare` holds the App key and runs no agent. It reads the round of the item, makes the writes that need no model, and decides the job-time premise, the false premise of the body probe and the blocker of an open plan. It makes a full clone at the tip of the default branch, writes the scaffold of the change folder with its own date, and writes `state/` and the inputs of the agent.
- `agent` holds the model key only. It refuses the App key, `GH_TOKEN`, `GITHUB_TOKEN` and a gh login. It runs stock `Coder` with `LocalWorkspace` at the clone and `RequireVerification` with the checks `devops openspec check`, `openspec validate` and `devops roadmap plan-recheck --source . --branch HEAD`, and `exempt_paths=()`. It writes the patch of the change folder, the body candidate and `outcome.json`.
- `publish` holds the App key. It reads `state/` and the outputs of the agent as data. It ends an unverified run as `plan_defect`. Before any push it refuses a path outside `openspec/changes/<change>/`, a secret and another date, and it runs the three checks again on the new tree. It builds the title, the body, the commit message and the labels with `staging_title`, `pull_request_body` and the closing-keyword stop, writes the plan with the writer of `--phase all`, and checks in.
- `devops roadmap plan-recheck` with `--branch` exits 1 when a folder that the branch adds or changes has a result other than `ok`. `--issues <file>` reads the issues from a listing file and sends no GitHub request.
- `safe_text` runs once on each text. The stage writer removes the control characters other than the line feed from the body and from each comment that it posts, and cuts each comment to 65536 characters.
- The new prompt `roadmap_stage_coder.md` tells the agent how to write the plan, commit it and run the three checks.
- This change deletes no code of the old engine. `--phase all` uses that engine until #6814 is live, so a follow-up item deletes the custom tools, the toolbox, the gate returns, the gate extension and the schema retry. The second acceptance criterion of #6705 moves to that item.
- The change fits one pull request.

## Capabilities

### New Capabilities

- `roadmap-stage/phases`: The stage Job takes a phase and a run folder, The default phase runs the stage Job in one process, Prepare decides what needs no model, Prepare writes the run of the agent, The agent phase holds no GitHub credential, The stage agent is stock Coder with the three checks, The agent phase hands over only what publish reads, An unverified run ends as plan_defect, Publish checks the plan files again before any push, Publish builds the texts of the plan with the stage functions, Each comment text is clean and fits GitHub, The same plan gives the same publish in both forms, The separate phases share one time budget and one request budget

### Modified Capabilities

- `roadmap-plan-recheck`: A branch run fails on a folder that the branch changes, The recheck reads the issues from a listing file

## Feasibility

- The premise holds for the phases and fails for the deletion. `k8s/devops/cronjob-stage.yaml:86` has the one container `stage`, and lines 105 and 110 give it `DEVOPS_CLI_SERVICE_GITHUB_APP_PRIVATE_KEY` and `DEVOPS_CLI_AI_API_KEY`. The Service starts each Job with `roadmap stage --repo <repo> --job-item <n> --confirm` and no `--phase` (`src/devops_cli/roadmap/stage/stage_submit.py:325`). So a shell of the agent in `--phase all` runs next to the App key, and `--phase all` must keep `run_stage_job` (`src/devops_cli/roadmap/stage/stage_job.py:446`) until #6814 is live. The engine that `--phase all` uses cannot go in this pull request: the deletion is re-scoped to a follow-up item.
- The old engine has other users that the deletion item must handle: the fix-plan row (`src/devops_cli/roadmap/run.py:815` builds `ToolboxModel(get_task_model("fix_plan"))`), `devops roadmap step fix-plan` (`src/devops_cli/commands/roadmap_step_fix_plan.py:98`), and the golden-set runs (`src/devops_cli/roadmap/stage/stage_eval_run.py:55` imports `ToolboxClient`).
- `RequireVerification` of pydantic-ai-harness 0.71.0 (`pyproject.toml:41`) does not run the checks. It reads the shell commands of the agent: `verification_commands` are patterns, and a run is verified when at least one check ran after the last edit and each recorded check passed (`require_verification/_capability.py:281`). `exempt_paths` defaults to `('*.md', '*.mdx', '*.rst')` (line 137), so the plan files count as edits only with `exempt_paths=()`. A run that ends unverified emits `CompletionUnverifiedEvent` with `failed_commands`. So the agent can end verified with only one of the three checks, and `publish` must run all three again.
- `devops roadmap plan-recheck --branch` exits 0 when the branch adds refusals: `tests/commands/test_roadmap_plan_recheck_cmd.py:165` asserts exit 0 for a branch with new refusals, and the command raises no exit after `render_recheck` (`src/devops_cli/commands/roadmap.py:1149`). On 2026-11-23, `uv run devops roadmap plan-recheck --source . --branch HEAD` on the first commit of this plan gave its own folder the result `new-plan` and exited 0. As a check of `RequireVerification`, it always passes. This change makes `--branch` exit 1 for a folder that the branch adds or changes and that is not `ok`.
- `plan-recheck` reads the open issues from GitHub: `src/devops_cli/commands/roadmap.py:1143` opens the store and `src/devops_cli/roadmap/plan_recheck.py:456` calls `store.open_items()`. On 2026-11-23, `env -i` with a scratch `HOME` and no token ran `devops roadmap plan-recheck --source . --branch HEAD` with exit 0 in 157 s and marked closed issue #1327 `cleanup`, so it read the public repository with no credential. An agent phase must read GitHub data only from the files of `prepare` (#6705, comment 7090472687), and a private repository gives no such read. So `prepare` writes the issue listing and `plan-recheck` reads it with `--issues`.
- `uv run devops roadmap plan-recheck --source . --branch HEAD` took 166 s on `main` at 5467e2250 in the devcontainer, and `uv run devops openspec check` took 15 s. The persistent `shell` tool of `Coder` returns after at most 270 s (`shell/_persistent.py:26`: `MAX_FOREGROUND_WAIT: float = 270.0`), and a check that is still running records no result. The stage container has a CPU limit of 1 (`k8s/devops/cronjob-stage.yaml:158`). So the agent shell uses the blocking `run_command` tool, as the implement step does.
- pydantic-ai stops a run after 50 requests by default (`pydantic_ai/usage.py:559`: `request_limit: int | None = 50`). The agent run passes `UsageLimits(request_limit=None)`, and the time budget of the Job bounds it.
- `devops openspec check` regenerates the skills in a scratch copy (`src/devops_cli/openspec/skills.py:22`: `openspec update --force`), and `CONTRIBUTING.md:60` says that the regeneration needs access to github.com. The agent container of #6814 needs that egress with no credential.
- `PhaseOutputError` and `PublishRefusedError` are `RoadmapImplementError` (`src/devops_cli/exceptions/roadmap.py:70` and line 76), which `CLASS_BY_EXCEPTION` maps to `ci_infra` (`src/devops_cli/roadmap/failure.py:183`). `RoadmapStageError` maps to `plan_defect` (line 179). So `publish` ends each refused output with `RoadmapStageError`, and gets no `ci_infra` retry.
- The plan reader gives no summary for the title: `read_change` sets `summary=_READ_SUMMARY` (`src/devops_cli/roadmap/plan_read.py:665`). So the summary comes from the body candidate. The round leaves out an item whose title summary does not fit (`src/devops_cli/roadmap/stage/stage.py:769` and `long_title_reason` at line 890), so the summary of the issue title always fits as the fallback.
- `pull_request_body` calls `safe_text` itself (`src/devops_cli/roadmap/stage/stage_change.py:3699`), so `publish` gives it the masked text and calls `safe_text` no second time.
- Reusable parts from the closed PR #6822 (branch `refactor/6813-stage-three-phases`, comment 7090465365): the options `--phase` and `--work`, `StageWriter.resume`, the failure of the item on a failed read in `prepare`, `finds_github_login` in `src/devops_cli/core/process.py`, the store fake `fail_read` for `comments_on`, and the test probes of `tests/roadmap/stage/test_roadmap_stage_job_phases.py`.
- The first checks against the real system: `uv run devops ci test tests/commands/test_roadmap_plan_recheck_cmd.py` fails on the base at the exit code of a branch with a refused folder, and `uv run devops ci test tests/roadmap/stage/test_roadmap_stage_agent.py` fails on the base because `devops_cli.roadmap.stage.stage_agent` does not exist.

## Existing Tool Considered

pydantic-ai-harness 0.71.0 covers the agent: `Coder` gives the file tools, the shell and the context controls, `LocalWorkspace` gives the clone, `RequireVerification` sends an unverified run back to its checks, and `Hooks` gives the event of an unverified end. The implement step already uses `Coder` and `LocalWorkspace` (`src/devops_cli/roadmap/implement/implement_step.py:783`). The phases of ADR 0030 (`src/devops_cli/roadmap/phases/`) cover the run folder, the read of the outputs as data, the patch and the push with a lease. The change builds only the stage glue of the three phases, the prompt and two options of `plan-recheck`: about 1,500 lines of source and 1,500 lines of tests, about 3 million tokens and 2 working days to build and fix. This pull request deletes no internal code. The follow-up item deletes `src/devops_cli/roadmap/stage/stage_tools.py` (511 lines), `src/devops_cli/roadmap/stage/stage_toolbox.py` (348 lines), the gate returns, the gate extension and the schema retry of `src/devops_cli/roadmap/stage/stage.py`, and the settings `roadmap.stage.gate_returns`, `roadmap.stage.gate_return_extensions`, `roadmap.stage.verify_repair_rounds` and `roadmap.stage.verify_repair_rounds_ceiling`.
