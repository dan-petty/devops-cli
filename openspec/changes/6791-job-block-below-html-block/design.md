# Design

## Decisions

- **The job blocks at the end of the body end an HTML block that only a blank line ends.**: The jobs write their blocks at the end of the body. A person can remove the blank line between an HTML line and a job block. The start marker then becomes a line of that HTML block. The rule of an open block (#6736) already ends a block at the job blocks at its end (`_are_job_blocks`). `_html_block_end` uses the same test for an HTML block of kind 6 or 7.
- **No text may follow the job blocks, and the cut must leave no block open.**: A person can write a marker in an HTML block, such as a `<details>` block with a start marker and text. GitHub hides the marker, but it shows the text around it. The first rule of this change ended the block at each marker line. The review of `926baff4d` found two results. The writers took text of the person into the section, or they added a blank line in the block of the person. GitHub then rendered the block in a new form. A fence line after the marker opened a code fence to the end of the body. A lone alternatives start marker in a `<div>` block stopped the alternatives write. With the two conditions, each of these bodies reads and writes as on the base.
- **A job block that text of a person follows stays unread when its start marker is in such a block.**: This is the cost of the narrow rule, and the base gives the same result. On 2026-11-23, 3 of the 783 open bodies with a refine section held text of a person after the job blocks. A line of the person after the end marker can belong to a block of the person. So can text after the job blocks. The body cannot tell the two cases apart.
- **Only the last marker lines of the body are candidates.**: The job blocks have four marker lines at most. So `_html_block_end` tests at most four lines, as `_open_block_end` does, and each test parses the rest of the body two times at most (`close_open_block`).
- **The rule goes in `_parts`, so each reader uses it.**: `_parts` already starts a new part at a marker line that ends an open block (#6736). `block_marker_spans`, `job_block_bounds`, `extract_section_and_outside` and `close_blocks_before_markers` read the parts. `body_dependencies` and `closed_body` read the closed body. So no reader gets a second rule.
- **The part before the line keeps its tokens up to the HTML block only.**: The tokens of a part are the tokens of the text from its start to the end of the body. An open block runs to the end of the body, so it is the last token of its part. An HTML block of kind 6 or 7 ends before the end of the body. Without the cut, `_spans` reads each later marker two times.
- **`block_marker_of` does not change.**: The new part starts at the marker line, so CommonMark parses the marker there as an HTML block of its own. A token test for a line of an HTML block would read the marker a second time.
- **Only a top-level HTML block ends at a marker line.**: The jobs write their blocks and the record at the top level. A new part starts at the start of a line, so a cut in a list item or a quote would break that container. `_open_block` also reads only the last top-level token (#6736).
- **The writers put a blank line before the marker line.**: `_closed` writes the close of each part that ends before a new part, and then a blank line. `close_open_block` gives no close for these kinds, so only the blank line is new. CommonMark then ends the HTML block at the blank line. The lines above the blank line are the lines of the person, and the lines below it are the job blocks.
- **`ends_at_a_blank_line` tells the kinds by `_HTML_BLOCK_CLOSES`.**: The table holds the end text of kinds 1 to 5 by the start of their first line. Each other HTML block that the parser gives is of kind 6 or 7. So the function copies no list of the block tags of CommonMark.
- **The record line on the last line of such a block reads as the record.**: `split_record` already parsed the body, and its last top-level block holds the record line. `ends_at_a_blank_line` of that block decides with no new parse. The probe of `close_open_block` runs only for the other kinds, as before (#6785). A body that does not hold the record opener is not parsed (#4445). A body whose last block is the record gets one parse. On 2026-11-23, `split_record` over the 833 open issue bodies took 0.865 s on the base. It took 0.871 s with this change (least CPU time of 10 runs). A second run put `<details>` directly above each of the 831 records. The change read each record in 0.98 s, and the base read none in 2.81 s (median wall time of 10 runs).
- **The read keeps the line break before the record line.**: No separator of the writer is there to take out. The next write (`with_record`) adds a blank line, so the record is then an HTML block of its own. The next read then gives the same body, so the lost-edit checks of the GitHub store see no change (#6729).
- **A quote of the record with a JSON object on the last line of such a block reads as the record.**: GitHub shows the line as a comment, so a person sees no quote. A quote in an open block reads the same way (#6785).
- **`CONST_ROADMAP_REFINE_RULES_SINCE` does not move.**: The change can change the blockers that `body_dependencies` reads. A live check read the open issue bodies of 2026-11-23 with the base and with this change. It found no difference in the records, the refine sections, the alternatives blocks, the blockers and the body hashes. So no item gets another model round. A second run put `<div>x</div>` directly above the start marker of each of the 783 refine sections. The change found 780 sections, and the base found none. The other 3 bodies hold a part of a person after the job blocks, so the narrow rule leaves them unread.

## Rejected alternatives

- **End the HTML block at its first marker line (the first rule of this change, `926baff4d`).**: The review found that it took text of a person as a job block. Three refine rounds removed `person *text*` and `</details>` from a `<details>` block of a person. A refine write replaced a line of the person between a marker pair in a `<div>` block. Each write added a blank line in a block of a person. The GitHub Markdown API then rendered `person <em>text</em>` in place of the plain text.
- **Bound a marker on the last line of such a block only, as on the last line of a comment.**: The start marker of each job is a middle line of the block, because each job writes text directly below it. A scratch script on `c7e40970d` found no block for `</details>` or `<div>x</div>` above each job block. It found only the end marker, and a lone end marker that bounds stops the alternatives write.
- **Read each marker line in such a block as a bound in `block_marker_of`, and make no new part.**: The read then finds the block, but `close_blocks_before_markers` writes no blank line. The lines of the job below the marker stay raw HTML. So GitHub shows `## Proposed design` as plain text, and the next read again needs the rule.
- **Write a list of the block tags of kinds 6 and 7.**: That list copies CommonMark (AGENTS.md rule 3). `_HTML_BLOCK_CLOSES` already tells the other kinds.
- **Put a blank line before each block in each writer, and keep the readers.**: Each writer already puts a blank line before its block. The defect is the edit of a person after the write, so only the read can find the block.
- **Read the record with `_parts` of `body_hash.py`.**: The record is no job block, and `_parts` parses each part again. So each body of a listing would cost more parses. #6785 rejected this for the same reason.
