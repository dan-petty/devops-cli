# Design

## Decisions

- **Read the ADRs through the store, in `plan_alternatives`, once for a run and only when the run checks an item that is no skip class.**: `plan_alternatives(store, repo=...)` has no checkout, and the command `devops roadmap alternatives` takes no `--source`. The store already reads one file of the repository (`repository_file`). So a second method that lists one directory (`repository_files`) is the smallest addition. A run of skip-class items makes no model call, so it reads no ADR. The ADRs are the same for every item of a run. One read serves up to `roadmap.alternatives.first_pass_limit` items: 1 listing and 17 file reads.
- **Send the title, the status lines and the `Considered Options` section of each ADR, and nothing else.**: The rejection in the evidence ("Temporal and Hatchet: rejected.") is a bullet of that section. Every ADR of the project records its chosen and rejected tools there. The title states the decision in one line. The status lines are the paragraphs right under the title that name another ADR and say that it supersedes or amends. They tell the model that a decision changed. The 17 ADRs hold about 64,000 tokens in all, and the entries hold about 5,000.
- **Leave out an ADR that a later ADR supersedes in whole.**: An ADR that another ADR replaced no longer decides anything. ADR 0011 rejected release-please for now, and ADR 0012 then adopted it. A model that read ADR 0011 could cite it as a rejection. The ADRs have no structured status field, so the job reads two sentences. The older ADR says "ADR NNNN supersedes this ADR". The newer one says "supersedes ADR NNNN". A clause that is superseded, as in ADR 0003, and an amendment match neither sentence, so those ADRs stay with their status lines. The model reads the status lines for any wording that the two sentences miss.
- **Send the ADRs as one text under the key `decisions`, the highest number first, cut by whole entries to `CONST_ROADMAP_ALTERNATIVES_MAX_ADR_TOKENS` (8,192).**: A newer ADR can supersede an older one, so the oldest go first. The cut never ends inside an entry. An entry that does not fit is left out, and a smaller older entry can still fit. The job logs one warning that names each ADR it leaves out. The job confirms only the ADRs that the model saw, so the model cannot cite an ADR it never read. The key is left out when the repository has no ADR, so a repository with no `docs/adr/` sends the request of before this change.
- **Let the model propose `rejected` and `in-use`, and let the job only confirm them.**: Whether a sentence rejects a tool is a judgment over prose, and so is whether an item uses a tool. A name match cannot decide either. Two reviews showed it on this repository. ADR 0011 names release-please in a rejection that a later ADR reversed. The words `just`, `task` and `requests` name a tool in no sentence. So the reply has `adr` for the first and `in_use` for the second. Each is a proposal that comes with the tool of a `covers` or `partly` verdict. The verdict of the reply stays the base verdict.
- **Drop a proposal that the job cannot confirm, and keep the verdict of the reply.**: A refusal would fail the whole check and skip the item for `roadmap.alternatives.retry_days`. The model is likely to repeat the same citation, so the item would stall, and #2951 makes a verdict a condition of Ready. A dropped proposal costs only the extra verdict. The check is written with `covers` or `partly` and refine asks its question, as before this change. The job logs the drop at info level.
- **Confirm `adr` with the ADRs that the model saw: the number is among them, and the title or the options name the tool.**: The test reads the title and the options, not the status lines, which name other ADRs and no tool. The job tests the repository name or the package name from the facts, and `tool_name`, the name that the reply writes for the tool. The display name matters because an ADR writes "DBOS Transact" for the repository `dbos-transact-py`. The job does not test whether the ADR rejects the tool. The model reads the sense, and a person sees the ADR number in the comment.
- **Confirm `in_use` with the title and the body of the item, outside the block of the check and outside the refine section.**: The block of the check names the tool of the earlier check. The refine section holds the open question "The alternatives check found that `<url>` covers this item". A rule that read either would turn each later `covers` check of an item into `in-use`. The question would close with no answer from a person. `Item.body` holds no record block, so the record is no part of the text.
- **Name a tool by forms, with the markdown parser of the project.**: `names` reads the text with markdown-it-py, as `section_text` does. The full `owner/name` counts anywhere. A name of two words or more, such as `argo-workflows`, counts anywhere as a whole word. A name of one word counts only inside a code span, a link or strong emphasis. A word such as `just`, `task`, `rich` or `act` is also a word of prose. The ADRs bold the name of each option, so `**Temporal and Hatchet**` names `temporalio/temporal`. A fenced block counts as prose. The list of forms is short and has no word list. A word list or a fuzzy-match library would add a dependency for a gate that a form already serves.
- **Add `rejected` and `in-use` to `Verdict`, and refuse them from the model after one retry.**: The record, the counter `devops_cli_roadmap_alternatives_total` and the `alternatives` key of refine all carry the verdict. So two values reach each of them with no new field. The first reply with a verdict that only the job sets goes back to the model once. This is the output check that already sends back a reply with no search. A natural reply such as `in-use` then costs one turn and no skipped item. The job refuses a second reply, as it refuses `not-applicable` before this change.
- **Give `rejected` priority over `in-use`, and apply both to `covers` and `partly`.**: An ADR is a fact about the project. An item that names a rejected tool most likely names it to dismiss it. A `partly` verdict for a rejected tool, or a tool that the item uses, is as wrong for a person as a `covers` verdict. It costs no branch, because both go through `_TOOL_VERDICTS`.
- **Let a failed read of `docs/adr/` stop the run, and let a missing directory mean no ADR.**: A swallowed read error would bring back the unneeded questions with no sign. A missing directory is the normal state of a repository with no ADR. So `GitHubFileNotFoundError` is the one error that the reader turns into an empty list. A rate-limit error already stops a run.
- **Write one line about the basis, in the comment and in the block: `Rejected by ADR 0008. A newer fact can change an ADR.` for `rejected`, and `The item already names this tool.` for `in-use`.**: The comment keeps the tool line with the URL, so a person can see the tool and the ADR number. The ADR number has four digits, as in the file name.
- **Change nothing in refine.**: `covers_question`, `_covering_tool` and `_needs_second_look` read the verdict `COVERS` only, so no question follows a `rejected` or `in-use` check. A test pins it. The prompt of refine names the two verdicts, so the model of refine reads them.

## Rejected alternatives

- **Decide `rejected` with code: a bullet of `Considered Options` that holds the tool name and the word "rejected".**: The ADRs word it in many ways ("rejected", "rejected for now", "not chosen"), and a pattern over prose decides some of them wrongly. The model proposes it. The job checks the one fact that code can check: the ADR is in force, was seen and names the tool.
- **Decide `in-use` with code alone, from a whole-word match.**: This was the first version. It named `just` in "just add it", and the verdict `in-use` then hid a real `covers` question. The model flag and a marked form stop that.
- **Refuse a reply when the job cannot confirm its ADR.**: The check would fail, nothing would be written, and the same citation could repeat after 3 days.
- **Narrow the `verdict` field of the reply so that the model cannot write `rejected`.**: A narrowed type would change the reason that the job records for a refused `not-applicable`. The spec and the tests of that reason exist. The one-retry output check serves all three verdicts with one rule, and it needs no new type.
- **Read the ADRs from a clone with `inspect_checkout` and `collect_context`, as refine does.**: The alternatives row has no clone and the command has no `--source`. Adding one turns the row into a clone job, which is a larger change than the issue names.
- **Send the full text of each ADR.**: The ADRs hold about 64,000 tokens, which is more than the window of a run.
- **Send the titles only.**: The title of ADR 0008 does not say that Temporal was rejected. The bullet does.
- **Match only a URL or `owner/name` in the text.**: The items of the evidence say "Grafana" in bold and "notifications-engine" in prose, and hold no URL. Few would match.
- **Read the text outside the block of the check only, as `_request` does.**: It makes the refine question close itself (see the decision above).
- **Add a word list or a fuzzy-match library, such as rapidfuzz or wordfreq.**: A fuzzy match names a tool that the item does not name. A word list adds a dependency, and the `wordfreq` project no longer updates its data. A marked form needs the markdown parser that the project already has.
- **Add a structured status field to each ADR.**: It changes 17 files and a convention that no issue asks for. The job reads the sentence now. A later change can add the field and delete the two patterns.
- **Keep the ADRs in a cache between runs.**: The row runs about twice a day and the read costs 18 requests, so a cache adds an invalidation rule for no gain.

## Risks

- A name of one word that appears in plain prose only never confirms `in-use` or `rejected`. The check then keeps `covers` and refine asks its question, as before this change. That is the safe direction.
- The model may cite an ADR that names the tool but does not reject it. For example, ADR 0008 chose Argo Workflows, and its options also say "Adopt Argo Workflows without measuring: rejected". The job confirms that the ADR names the tool, not the sense. The model reads the sense, and the comment names the ADR and keeps the tool URL, so a person can see a wrong `rejected`.
- The two supersession sentences miss an ADR that words it another way. Such an ADR stays in `decisions` with its status line, and the model reads the line.
- The model can write a `tool_name` that is a common word of an ADR, and so confirm an ADR that does not concern the tool. The tool URL, the ADR number and the model's own reading limit the harm to one wrong `rejected` verdict that a person can see.
