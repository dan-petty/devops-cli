# Design

## Decisions

- **The attempt number selects the strategy: `strategy_for` gives `planned` on attempt 1, `repo_map` on attempt 2, and `tier` on attempt 3 and each later attempt, and an attempt that follows a failure which selects `change_tier` has the strategy `tier`.**: Each attempt then tries something that the earlier attempt did not, so a second failure of the same class cannot repeat the strategy that failed, and an attempt on a new tier says so.
- **The second attempt adds a `# Repository map` section built from the files that the failure names and the files of the group, at most `CONST_ROADMAP_STAGE_MAP_MAX_FILES` = 40 of them.**: It names the code that the failure touches and it stays small; the whole map of a directory is not bounded by the failure.
- **The map line reuses `parse_file_symbols` and the form of the `repo_map` tool of the stage planner.**: The planner already renders a file as its path and its top-level names, and the step adds no second form for the same fact.
- **The third attempt moves to the next healthy tier and spends no repair round, as the ladder move of a provider or parser failure does.**: The issue's chosen design keeps the ladder move free of the repair rounds, and a new model starts from a known state after the step discards the failed work.
- **The third attempt opens a new conversation whose message is the repair message of `_extra_ask`, so it carries the failure text and the paths that the round may change.**: The first turn of the tier loop sends `inputs.message` again, so a move that kept that message would repeat the step and lose the reason of the failure.
- **The third attempt happens only while a repair round is left, so `roadmap.implement.repair_rounds` stays the one bound on the extra turns of a step.**: A ladder of many tiers cannot extend a step past its bound, and a step with one repair round makes two attempts, as the acceptance criterion of the issue states.
- **The third attempt discards the checkout back to the last `wip:` commit before it starts.**: The tree keeps the work of the failed attempt, and the kept work of the passed tasks stays in the branch.
- **A stop whose failure selects `change_tier` on a ladder of one tier ends its reason with one line that names `roadmap.implement.ladder` and the tier.**: A person sees the setting to change and the value that the failure cannot move past, without a second stop record.
- **The plan adds no second ask for a smaller group at the second attempt.**: The stop of class `plan_defect` already asks for a smaller replacement of the group, and a step whose inputs or spend exceed their limits already stops with `limit_reached` and names the setting.
- **The change to `docs/roadmap/implement.md` carries no spec delta of its own.**: A document is not behavior that a consumer observes, so the requirements of the change are the trace, the message and the two stops.
- **The map section reuses `CONST_ROADMAP_STAGE_MAP_MAX_FILES` and adds no constant, and group 2 names `tests/roadmap/test_roadmap_limit_classes.py` although it changes it not.**: The registry of the `CONST_ROADMAP_` prefix keeps one entry for the whole prefix, so a plan that cites a name of that prefix must show that it left the registry alone.
- **Each group that changes an existing module names that module in a plain code span of its task text.**: A step packs the existing files that its task text names, so a task that cites a file only by a symbol or a line span starts with none of the files that it changes.
- **The section is built in `_extra_ask`, which gains the `source` and the `inputs` that its caller `_repair_rounds` already holds, and the third attempt takes the message that `_extra_ask` builds.**: The map reads files of the checkout and the group, and the caller holds both, so the section needs no second read of the step inputs and the new conversation needs no second copy of the failure text.

## Rejected alternatives

- **The failure class selects the strategy of the round.**: A second failure of the same class repeats the strategy, which is the defect of the issue: the class of a failed test is `test` on every attempt.
- **The second attempt sends the whole repository map of the checkout.**: `src/devops_cli/ai/repomap.py:def generate_repo_map` walks a whole directory, so its answer is bounded by the size of the directory and not by the files that the failure names.
- **The third attempt continues the conversation of the earlier attempts on the new tier.**: The tree keeps the work of the failed attempt, and the step discards it before a tier move, `src/devops_cli/roadmap/implement/implement_step.py:2085:keeper.discard()`.
- **The third attempt sends `inputs.message` again on the new tier.**: The first turn of the tier loop sends that message, `src/devops_cli/roadmap/implement/implement_step.py:2051:agent, tier_model, log, inputs.message, source=source, usage_limits=usage_limits`, so the reason of the failure would never reach the new tier.
- **A setting names the strategy of each round.**: It adds a setting to keep and to document, and it does not stop a repeated strategy by itself: the same value repeats until a person changes it.
