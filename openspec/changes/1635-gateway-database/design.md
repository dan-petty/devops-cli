# Design

## Decisions

- **CloudNativePG runs the database, in the form of the Mattermost database.** The operator is in the cluster, and `k8s/mattermost/database.yaml` is the model: `instances: 1`, image `ghcr.io/cloudnative-pg/postgresql:17.2`, `local-path`, `Prune=false,Delete=false`, `enableSuperuserAccess: false`. The volume is 5 GiB, not 10 GiB: the database holds keys and spend rows of one gateway.
- **The operator generates the Secret.** With no `bootstrap.initdb.secret`, CloudNativePG creates `llm-gateway-db-app` with a generated password and a `uri`. The Deployment reads `DATABASE_URL` from `uri` with `secretKeyRef`. The `uri` uses the scheme `postgresql://`, which Prisma accepts. No full URL and no password is in git, and `CLUSTER_SECRETS` has no row.
- **The secret guard derives the exemption, and does not list it.** `test_every_secret_referenced_under_k8s_has_a_table_row` removes `<cluster>-app` for each `Cluster` that names no `initdb.secret`. A hand-written list of exempt names would be an escape. A second test holds both directions: a `Cluster` with `initdb.secret` is not exempt.
- **No `LITELLM_SALT_KEY`.** The issue text asked for a generated salt key in the keyring. LiteLLM uses the salt key to encrypt values that it stores in the database, such as provider keys of models added at run time, and falls back to the master key. A virtual key is a SHA-256 hash and does not use it. With `store_model_in_db: false` nothing is encrypted. A salt key would need a generated `CLUSTER_SECRETS` row and a person's push before the gateway starts, which the change avoids. The README states the one rule: set a salt key before the first change that stores a credential in the database.
- **The database is a post-Helm path of stack `llm`.** The `Cluster` needs the CRD that the operator's chart installs. deploy-stack applies manifests before the Helm releases, so `gateway-db.yaml` joins `_POST_HELM_BY_STACK["llm"]`, as the `ServiceMonitor` of the gateway does. A gateway pod that deploy-stack starts first waits for the Secret. The file lists the policy first, so the policy exists before the operator makes the pod.
- **The operator moves to stack `infra`.** Stack `llm` now needs the operator, and stack `chat` needed it before. A release listed in both would install twice with `--stack all`. Stack `infra` already installs the `prometheus-operator-crds` that the operator's `podMonitor` needs, and the `ServiceMonitor` of the gateway already needs a CRD from `infra`. The values file stays in `k8s/mattermost/`, because Argo CD's Application `cloudnative-pg` names it.
- **The policy selects on `cnpg.io/cluster`.** The operator puts that label on every pod of the `Cluster`. The Mattermost policies select on it. `llm-default-perimeter` gets a second `NotIn` expression for it. The database pods then answer to `llm-gateway-db-perimeter` alone.
- **Egress to the API server keeps the Mattermost form.** The API server has a node address, and no pod selector names it. The rule is `0.0.0.0/0` except the metadata address, on 443 and 6443, as `mattermost-db-api` has it.
- **A `startupProbe` protects the migration.** The proxy opens port 4000 after `prisma migrate deploy`. The liveness probe starts at 15 s and kills a pod after about 60 s without an answer. A `startupProbe` of 60 tries every 10 s holds the other probes back for ten minutes.
- **`allow_requests_on_db_unavailable` stays unset.** The default is `false`. The gateway is reachable from outside the cluster, so a key it cannot check is refused. The config gets a comment, and a gate check holds the value.

## Rollout

Argo CD applies the merge. It creates the policy and the `Cluster`, and a new gateway pod beside the old one: one replica, so the default `maxSurge` is 1 and `maxUnavailable` is 0. The new pod waits for Secret `llm-gateway-db-app`, restarts until the database accepts connections, migrates the empty database, and passes its readiness probe. Then Kubernetes stops the old pod. The old pod answers every request until then, so the gateway has no downtime, and no person plans a window. The new pod may restart a few times. A person can see this in `kubectl -n llm get pods`.

## Rejected alternatives

- **A StatefulSet of the `postgres` image with a generated password in `CLUSTER_SECRETS` (the text of the issue).** It builds a second way to run Postgres, with its own security context, claim protection and secret row, when the operator runs the first one. The operator also creates the Secret, so no person step is needed. The cost to keep it is the only reason it was proposed.
- **A `CLUSTER_SECRETS` row for a user-supplied initdb secret (the Mattermost form).** It needs a push from a person's keyring before the database starts. Mattermost has it only because its connection string is a derived entry. The gateway needs none.
- **Egress only to DNS for the database.** The CloudNativePG documents state that the instance manager calls the API server. A policy without that rule stops the instance.
- **Keep `cloudnative-pg` in stack `chat`.** `--stack llm` alone on a cluster without Argo CD would then have a gateway that never starts, because its Secret never exists.
- **Move the operator values file to a shared folder.** It changes the path in Application `cloudnative-pg` and in the Helm release for no behavior. A later change can do it.
- **A daily `pg_dump` CronJob in this change (the text of the issue).** The cluster has no backup target that is off the node. A dump into a claim of the same node does not meet the owner's rule for backups, and #2144 is choosing the target for Gitea. A backup issue holds it, so the cluster gets one design.
