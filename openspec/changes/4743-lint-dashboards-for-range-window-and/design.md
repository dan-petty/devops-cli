# Design

## Decisions

- **Apply the range rule to the targets of time series, graph and bar chart panels that are not instant, and the window, fallback, label and histogram rules to the targets of those panels that are not instant.**: An instant target reads a range on purpose, and a stat or table panel draws no time axis, as `k8s/devops/dashboards/ai-spend.json:292: "expr": "count(sum by (server, backend) (increase(devops_cli_ai_requests_total{cached=\"false\"}[15m])) > 0) or vector(0)",` shows in a panel whose `k8s/devops/dashboards/ai-spend.json:285: "type": "stat",` draws one value.
- **Rule 2 reports a fixed window of a rate, irate, increase or delta in a non-instant target, except in a target that divides two windowed aggregates over one window, which is a share or a burn rate.**: The 1 h and 6 h burn rates of `k8s/monitoring/dashboards/devops-roadmap-service.json:488: "legendFormat": "1 h burn rate",` and `k8s/monitoring/dashboards/devops-roadmap-service.json:493: "legendFormat": "6 h burn rate",` are the SLO windows of the page lines, and `src/devops_cli/grafana/service_dashboard.py:258:def error_ratio` builds a share over one window from the request selector of one service, so a recording rule cannot carry them.
- **Bind a label when the dashboard defines a template variable of that label's name and the target expression holds a positive matcher for it.**: A rule over the bare matcher reports a dashboard that has no selector for the label, and fixing an upstream dashboard is outside the files of the issue; the narrowed rule still catches a query that ignores the selector the dashboard offers.
- **Check the panel unit and a field override that sets the unit of the refId for a histogram count, and move the AI spend override from the legend regexp to `byFrameRefID`.**: `src/devops_cli/grafana/schema.py:class FieldConfig` holds `overrides`, and `k8s/devops/dashboards/ai-spend.json:924: "options": "^calls "` sets the unit of one series by its legend, which a rule over the panel unit alone would refuse.
- **Flatten the panels of a collapsed row for the panel id, target and datasource checks, and keep the overlap check on the top-level panels.**: A collapsed row hides its panels, so an overlap across a hidden row is no defect, while a duplicate panel id and a bad query are defects wherever they sit.
- **Resolve the datasource of a target from the panel when the target declares none.**: The builder writes the datasource on the panel only, so `k8s/monitoring/dashboards/devops-sre-service.json:1724: "labelSelector": "{service_namespace=\"$namespace\", service_name=\"$workload\"}",` and the Loki targets of the same dashboard would be read as Prometheus once the nested panels are checked.
- **Check a Pyroscope target by its label selector and profile type, and delete the expression that `k8s/monitoring/dashboards/pyroscope.json` carried only for the linter.**: `k8s/monitoring/dashboards/pyroscope.json:45: "expr": "process_cpu:cpu:nanoseconds:cpu:nanoseconds{service_name=~\".*$service.*\"}",` is a copy that only the empty-query check needed.
- **Add the five rules before the dashboard fixes, and give each fix group a census case in `tests/grafana/test_grafana_dashboard_rules.py`.**: A fix group whose verify runs `tests/grafana/test_grafana_dashboards.py` passes before and after it, because that test reads every dashboard at once; the rules first make each fix group's verify fail until its own files are clean.
- **Time the two new rule functions alone over the 21 shipped dashboards, and assert that their total elapsed time is under 2 s.**: `tests/grafana/test_grafana_dashboards.py:90: report = lint_dashboard_file(dashboard_file)` already lints every shipped dashboard on the base, so the cost of the whole run is not the cost that the five rules add; the other checks of `src/devops_cli/grafana/linter.py:def lint_dashboard` stay unchanged, so timing `_check_graph_queries` and `_check_histogram_units` alone measures what the rules add.
- **Each shipped dashboard lints clean, with no per-file and no per-rule exemption.**: An exemption hides the next defect of the same kind, and the issue forbids one.
- **The lint test covers the 21 dashboard files of both folders, not the 16 of the issue.**: `tests/grafana/test_grafana_dashboards.py:31: for directory in (_REPO_DASHBOARDS, _PRODUCT_DASHBOARDS)` builds the list from the environment folder and the product folder, and `list_files` shows 16 JSON files in `k8s/monitoring/dashboards` and 5 in `k8s/devops/dashboards`, so a rule that skips the product base ships a defect.

## Rejected alternatives

- **Apply every rule to every panel type.**: `k8s/devops/dashboards/ai-spend.json:292: "expr": "count(sum by (server, backend) (increase(devops_cli_ai_requests_total{cached=\"false\"}[15m])) > 0) or vector(0)",` is a target of a panel whose `k8s/devops/dashboards/ai-spend.json:285: "type": "stat",` draws one value, and it reads a fixed window and a fallback on purpose, so a rule over every panel refuses it.
- **Report every `by()` clause or legend of the label set that has no positive matcher.**: `k8s/monitoring/dashboards/otel-collector.json:413: "expr": "max by (pod) (otelcol_process_memory_rss)",` names a label that no dashboard variable offers, so the rule would need an exemption list or a change to an upstream dashboard.
- **Check only the panel unit for a histogram count.**: `k8s/devops/dashboards/ai-spend.json:924: "options": "^calls "` sets the unit of the count series by its legend, so a rule over the panel unit alone refuses a panel that renders correctly.
- **Leave the panels of a collapsed row unchecked.**: `k8s/monitoring/dashboards/cloudnative-pg.json:5403:cnpg_pg_stat_database_xact_commit` holds a fixed window inside a collapsed row, and the linter passes it today.
- **Move the burn-rate windows of the generated service dashboards into a recording rule.**: `src/devops_cli/grafana/service_dashboard.py:class ServiceSpec` holds the request and error selectors of one service, and `src/devops_cli/grafana/service_dashboard.py:273:def burn_rate` takes the window from that spec, so a shared recording rule cannot carry them for every service.
- **Adopt grafana/dashboard-linter v0.4.0 and its rules instead of the linter of this repository.**: Its target-rate-interval rule covers only a `rate()` without `$__rate_interval` and it takes no custom rule, so it reports none of the five rules; the rules here cost about 100k tokens to build and 2 hours elapsed.
- **Fix the eight dashboards before the group that adds the rules.**: `tests/grafana/test_grafana_dashboards.py:84:def test_repository_dashboards_lint_clean(dashboard_file: Path) -> None:` passes before and after such a fix, so a step cannot tell whether a window moved.
- **Time the whole lint run over the 21 dashboards and assert that it finishes under 2 s.**: `tests/grafana/test_grafana_dashboards.py:84:def test_repository_dashboards_lint_clean(dashboard_file: Path) -> None:` already lints every shipped dashboard on the base, so a case that times the whole run passes whatever the five rules cost and measures no part of the criterion.

## Security

The plan changes files under `k8s/`, so it touches a security trigger path. Nothing new crosses a trust boundary: each rewritten query reads the same Prometheus series over a window that Grafana chooses, the linter reads local JSON files only and makes no request, and no dashboard names a host, a credential or a private address. A person must confirm that no rewritten query adds a host or a datasource, that the moved unit override still matches the count series, and that the Pyroscope selector still names the same service. The census case in `tests/grafana/test_grafana_dashboard_rules.py` fails when a shipped dashboard stops linting clean, and `uv run devops ci --check --only k8s` fails when the dashboard ConfigMaps stop rendering.
