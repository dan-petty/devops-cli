# Proposal

## Why

The owner asked on 2026-11-11 that the Service dashboard show the service jobs, the branch and the work log (#4621). A person cannot see which Service Job runs, for which repository and item, on which branch and working copy, or what it wrote, without kubectl and a hand-written Loki query. The Service dashboard is Grafana as code, so the view belongs in its generated panels and in the Job metadata that kube-state-metrics exports.

## What Changes

- Add the annotations roadmap.devops-cli/branch and roadmap.devops-cli/worktree to each stage Job and each implement Job of an item, from the branch of the target and the clone path of the round that submits the Job.
- Build the Service jobs table and the Work log panel in the template of `src/devops_cli/grafana/service_dashboard.py`, behind a `jobs` field of `src/devops_cli/grafana/service_specs.py` that defaults to false. The table has nine columns, two GitHub data links and a link of the job column that sets the job variable. The Work log panel reads the Loki data source.
- Give the two panels the titles `Service jobs: branch, worktree and state` and `Work log: lines of the selected job`, because the dashboard test refuses a title that is not in the form `Signal: measure`. Each description holds the words of the issue: the Service jobs table and the Work log panel.
- Offer the repo, item and job variables, filter the table on all three and the log panel on job.
- Add a rule and its cases to `tests/grafana/test_service_dashboard.py`: the dashboard test fails and names the panel and the key when a query of a Job panel reads a family that is no kube_job family, or a Job label or annotation that the Service does not set.
- Add a case to `tests/telemetry/test_service_counter_series.py` that primes the Service counters and reads the label sets of the metrics registry, so no Service series carries a label named item, branch or worktree.
- Describe the Job panels in the section Grafana Dashboards of `k8s/README.md` and the two annotations in the sections Runner Jobs and Stage Jobs of `docs/CLUSTER.md`, and update the Service dashboard row of `docs/DESIGN.md`.
- Change no file of the environment. dan-petty/homelab holds the monitoring folder of the cluster since step 11 of the homelab switch, and the check `environment-freeze` of the `k8s` row refuses a branch that changes a file there. dan-petty/homelab#263 sets the kube-state-metrics allowlists for the Job labels and annotations, sets `jobs = true` for the Roadmap Service and regenerates its dashboard, after the release that holds this change.
- Leave out the 4 gate panels and the 3 alerts that the comment of 2026-11-11 on #4621 adds. They read the metrics of #4698: gate runs, queue time, fallbacks and disagreements with GitHub. No such series exists in this repository. The run history link is #7272, and the annotations of Argo Workflows are #7273.
- The change fits one pull request.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `service-dashboard-template`: The Service jobs table shows the live Jobs of the Service, The Work log panel shows the lines of the selected Job, The Job panels filter on the repo, item and job variables, The Job panels read only the Job keys that the Service sets
- `roadmap-stage/job`: The stage Job names its branch and its lane clone
- `roadmap-implement-job/runner-job`: The runner Job names its branch and its lane clone
- `metric-instruments`: The item, branch and worktree values stay off the Service series

## Existing Tool Considered

kube-state-metrics, in use, covers the export of the Job labels, annotations and status series: dan-petty/homelab#263 sets its label and annotation allowlists, and the default allow list of the k8s-monitoring chart keeps its kube_job families. Grafana and Loki, both in use, draw the table and the log panel. The PromQL reader `devops_cli.prometheus.promql`, in use, gives the series and the label names of a query to the new rule of the dashboard test. The change builds its own panel template code instead of a tool: about 150 lines of template code and 4 cases, an estimated 60k tokens and half a day (4 hours) to build, keep and fix. It deletes no internal code.
