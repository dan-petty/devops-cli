# Design

## Decisions

- **One base for each reader.** `RESULT_LINES` of `job_grade_report.py` holds the selector, the line filter and the parse of the two forms. `_lines` adds the field parse to it, and each query starts with `_lines`. The four queries of the dashboard row `Roadmap Job Success` start with the same text, and a dashboard test compares them with the constant. So a change of the selector is one edit and one failing test.
- **The container names the unit.** The selector is `{namespace="devops", container=~"service|stage|fix-plan"}`: the Service, a stage Job and a fix-plan Job. The container name is the same for each pod of a unit, also for the fix-plan Jobs that an agent made with the label `roadmap-fix-plan-validation`, which no manifest of the repository sets. A new unit that writes result lines adds its container to the one constant.
- **Parse with LogQL.** `| json message` gives the label `message` for a JSON line and the error label for a plain line. `| drop __error__, __error_details__` removes the error, so Loki does not refuse the metric query. `| line_format "{{ or .message __line__ }}"` then gives the message, or the full line when no message is there. The line filter `|~ "^roadmap job result: "` then keeps only a line that starts with the prefix. A line that does not match the field regexp still counts in `count_over_time` with no labels, so the filter keeps a JSON line with no `message` key, and a plan report line that holds the prefix in the title of an issue, out of each count.
- **The writer of the check-in writes the line.** A stage attempt can end in the Job or in the recovery of the Service. The Job checks in first, and logs its result line only when its check-in found its check-out. When the check-in finds no check-out of the Job, the Service ended the attempt and wrote the line of a failed end, or wrote no line for a free eviction. When the check-in of the Job fails, the Job writes no line, and the recovery writes the line of the `failed` end. A pod with no Job name (a person who runs `--job-item` with no `roadmap.stage.job`) has no check-out that the Service can recover, so it writes its line.
- **A stderr handler in each Job command.** `job_lines_to_stderr` of `job_result.py` adds one plain handler to the loggers `devops_cli.roadmap.round_log` and `devops_cli.roadmap.job_result` for the length of the attempt. `devops roadmap step fix-plan` and `devops roadmap stage --job-item` use it. The Service keeps its JSON handler.
- **A fake Loki that evaluates.** `tests/support/fakes/loki.py` holds streams of labels and lines, and evaluates the stream selector, the line filters, `json`, `drop`, `line_format`, `regexp`, the label filters, `unwrap`, and the metric forms of the report. It refuses a metric query whose pipeline leaves `__error__`, as Loki does. It counts each line in each window.

## Rejected alternatives

- **Every container of the namespace, or every container but `runner`.** Loki holds the containers `implement` (the pods `roadmap-implement-check`) and `runner` in the namespace. Both run a coding agent and its tests, and the captured stderr of a failed test prints result lines at the start of a line. The stream of the Kubernetes events has the label `namespace` and no container.
- **A list of app labels.** The fix-plan Jobs of 2026-11-13 have the label `roadmap-fix-plan-validation`, which an agent set by hand, and a stage Job has the label `devops-cli-job` of the runner too. The label alone does not keep the runner out.
- **One regexp over the raw line.** A regexp that also matches `"message":"roadmap job result: ...` inside a JSON line parses JSON by hand. The LogQL `json` parser is the tool for it (owner rule: fixes use libraries).
- **Two queries, one for each form, added with `+`.** A binary operation of LogQL keeps only the series that are on both sides, so a job with lines in only one form loses its count. `or` does not add the counts.
- **The Job logs before its check-in, and the Service skips its line when the log of the pod holds one.** The Service then must read the log of each pod for each end. The order of the Job gives the same rule with no read.
- **Recorded replies only.** The replies of `tests/fixtures/roadmap/job_grades/replies.json` answer by the text of each query, so they pass for any selector and any parse. They stay for the hand count of the measures, and the fake Loki tests the selector and the parse.
