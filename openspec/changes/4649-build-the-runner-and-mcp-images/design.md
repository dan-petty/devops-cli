# Design

## Decisions

- **Merge the jobs `runner-image` and `mcp-server-image` of `.github/workflows/ci.yml` into one job that builds both targets with one `docker/bake-action` step.**: The issue asks for one job and one bake call, and the account runs at most 20 hosted jobs at one time; since #4361 the `mcp-server` target builds on the Service chain, so the merge removes one hosted job and the setup it repeats.
- **Write the bake definition to `docker-bake.hcl` in a step before `docker/bake-action` in `.github/workflows/ci.yml`.**: `docker/bake-action` expects file paths in `files`, not inline HCL. Writing the file dynamically in the job keeps the change in `.github/workflows/ci.yml`, commits no static bake file to git, and expands `${{ github.repository }}`.
- **Keep the id `mcp-server-image` and the name `Runner Image` on the merged job.**: The requirement `The release gate equals the pull request gate` of `openspec/specs/mcp-server-image/spec.md` names job `mcp-server-image` of `ci.yml`, and the requirement `The scan of the runner image reports and stops no build` of `roadmap-implement-runner` names the Runner Image job of `ci.yml`; a new id or name makes one of them false and needs a spec delta that the paths of this change cannot carry.
- **Keep the `cache-from` ref of each target in `.github/workflows/ci.yml`, inside the generated HCL, as `cache-from = ["type=registry,ref=ghcr.io/${{ github.repository }}/runner:buildcache"]` and its `mcp-server` sibling.**: The requirement `Each image build keeps its own registry cache` of `container-image-layers` asks for that ref of each target and bans `type=gha`; the step text sits in the workflow, so the `${{ github.repository }}` expression expands and no literal repository path is written.
- **Set `no-cache-filter` on the `mcp-server` target only.**: `Dockerfile:179:RUN apt-get update && apt-get upgrade -y && rm -rf /var/lib/apt/lists/*` is the final stage of `mcp-server`, and the runner stage runs no upgrade of its own, as `docs/CLUSTER.md:76:the runner runs no` says.
- **Set `timeout-minutes: 18` on the merged job, 12 on the bake step and 4 on each scan step.**: The Runner Image job took 4:15 and 6:27 cold (comment 5) and the MCP server build's median is 118 s (comment 4), so the merged job runs about 9 minutes; `.github/workflows/ci.yml:36:# Each job limit is about two times the longest run of the job, and 5 minutes at least, so a hung` asks for about two times, and `tests/invariants/test_workflow_contracts.py:95:def test_every_job_has_a_limit_and_each_step_limit_is_under_it` refuses a step limit that is not under its job's.
- **Keep the runner smoke test, the runner scan, the MCP server smoke test and the MCP server scan unchanged in the merged job, with their scripts, the categories `trivy-image-runner` and `trivy-image-mcp-server`, and exit code 0 for the runner scan.**: The base requirements hold the runner smoke text equal to the release's, the MCP smoke text equal to the release's, the two categories and the runner exit code 0, so a changed text, category or exit code would make one of them false.
- **Keep one `Detect Image Content Changes` step with the same `IMAGE_CONTENT_PATHS` list in the merged job.**: `tests/invariants/test_architectural_invariants.py:689:def test_image_path_filter_covers_dockerfile_sources` requires the filter of the image job to cover every path that the `Dockerfile` copies, and both targets build from that one `Dockerfile`.
- **Update `tests/invariants/test_runner_image.py`, `tests/invariants/test_mcp_server_image.py`, `tests/invariants/test_architectural_invariants.py` and the run-step allowlist of `tests/commands/test_ci.py` to read the merged job.**: `tests/invariants/test_runner_image.py:36:job = _workflow("ci.yml")["jobs"]["runner-image"]` reads the deleted job, `tests/invariants/test_mcp_server_image.py:30` reads the step `Build and Load MCP Server Image`, and `tests/commands/test_ci.py:1775:allowlist: dict[tuple[str, str], str] = {` refuses a run step that its allowlist does not name.
- **Plan no spec delta.**: The change edits a workflow and tests, and each base requirement that the workflow serves stays true with the kept id, name, smoke texts, categories, exit code and cache ref, so no requirement text changes.

## Rejected alternatives

- **Keep the two `docker/build-push-action` steps and put them in one job.**: `.github/workflows/ci.yml:599:uses: docker/build-push-action@c3c9e263c25d99ce0380d002d59b67737d91b0dc` and `.github/workflows/ci.yml:704:target: mcp-server` show one build per step, so the shared build graph of one bake call is lost, and the issue names `docker buildx bake`.
- **A matrix over the two images.**: `.github/workflows/ci.yml:539:runner-image:` and `.github/workflows/ci.yml:640:mcp-server-image:` are one hosted job each today; a matrix entry gets its own runner, so it removes no hosted job.
- **Commit a static `docker-bake.hcl` at the repository root.**: A static file cannot expand the `${{ github.repository }}` expression directly and widens the change to a path that the issue does not name.
- **Run `docker buildx bake` in a `run` step of the job.**: `tests/commands/test_ci.py:1775:allowlist: dict[tuple[str, str], str] = {` refuses a run step that the allowlist does not name, and a run step loses the load and cache handling of the action.
- **Rename the merged job to the id `image-build` with the name `Container Images`.**: The requirements `The release gate equals the pull request gate` of `openspec/specs/mcp-server-image/spec.md` and `The scan of the runner image reports and stops no build` of `roadmap-implement-runner` name the job `mcp-server-image` and the Runner Image job of `ci.yml`, so a new id and name would make both false.
- **Merge the Service image job into the same job.**: `.github/workflows/ci.yml:504:no-cache-filters: service` shows that the Service target has its own final stage that runs `apt-get upgrade`, and the issue scopes the merge to the `runner` and `mcp-server` targets.
- **Keep `timeout-minutes: 12` on the merged job, or raise it to 24.**: `.github/workflows/ci.yml:546:timeout-minutes: 12` is the limit of the runner job, whose longest cold run was 6:27; the merged job runs the work of both, and 24 holds a runner twice as long as that run when a build hangs.
- **Pin `docker/bake-action` by a version tag such as `docker/bake-action@v8`.**: `tests/invariants/test_workflow_contracts.py:519:def test_every_remote_action_is_pinned_to_a_commit_sha` refuses a remote action that no 40-character commit SHA pins.
- **Set `no-cache-filter` on the `runner` target too.**: `Dockerfile:79:through Renovate, so the runner runs no` shows that the runner stage runs no `apt-get upgrade` of its own, so it has no final stage that a cached layer would keep stale.
- **Write the cache ref as a literal repository path, such as `ghcr.io/dan-petty/devops-cli/runner:buildcache`.**: The requirement `Each image build keeps its own registry cache` of `container-image-layers` names `ghcr.io/${{ github.repository }}/<target>:buildcache`, and the workflow step expands that expression, so the ref keeps its form and no literal path is written.
- **Keep two jobs and join them with a shared `needs`.**: `.github/workflows/ci.yml:539:runner-image:` and `.github/workflows/ci.yml:640:mcp-server-image:` are two hosted jobs today, so a shared `needs` keeps both runners per push, which is the cost this item removes.

## Unchanged references

- `openspec/specs/mcp-server-image/spec.md` (job id in a requirement): The merged job keeps the id `mcp-server-image`, the MCP server smoke text and the category `trivy-image-mcp-server`, so the requirements `The release gate equals the pull request gate` and `MCP server image gate` stay true.
- `openspec/specs/roadmap-implement-runner/spec.md` (job name in a requirement): The merged job keeps the name `Runner Image`, the runner smoke text, the action `.github/actions/image-scan`, exit code 0 and the category `trivy-image-runner`.
- `docs/CLUSTER.md` (job name and cache form in a document): The Runner Image job still scans the runner image with exit code 0, the runner target still sets no `no-cache-filter`, and each target still reads the registry cache of its own name.
