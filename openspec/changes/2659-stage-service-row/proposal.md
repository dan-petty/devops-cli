# Proposal

## Why

Issue #2659, a part of #2653: the Service does not run `devops roadmap stage`, so a person must run it by hand. The Service image also cannot run `openspec validate`: it holds no Node runtime and no OpenSpec. #1848 was not planned because the release cut no longer archives, and that reason does not apply to a job that writes a change.

## What Changes

- `src/devops_cli/roadmap/run.py` gets the row `stage` in `MODEL_LANE_ROWS`, after `refine`. It is due by its interval (`DEFAULT_ROADMAP_STAGE_INTERVAL_MINUTES`, 60), on a first run, and in a round where refine set an item Ready. `JobOutcome` gets the field `set_ready`, which the refine job fills from `RefineApplied.readied_count`.
- The row runs the stage job with the model clone of the lane: the plan, the writes, and the failure report that `devops roadmap stage --confirm` uses.
- `RoadmapStageConfig` gets `roadmap.stage.filter` (a list of `family=value`) and `roadmap.stage.limit`, each with its variable. An entry that is not `family=value` over a known label family is refused, and the message names the entry. `devops roadmap stage` reads both settings when `--filter` or `--limit` is not given.
- `src/devops_cli/telemetry/instruments.py` gets `devops_cli_roadmap_stage_total{result}`. Each item of a round counts once, with the result `staged`, `skipped`, `needs_split` or `failed`.
- `Dockerfile` carries the Node runtime and the pinned OpenSpec in the service stage. The builder stage runs `devops install-tools --tool openspec`, which runs `npm ci` on the lockfile of `src/devops_cli/tools_lock/openspec`. The service stage copies the tool directory and the `node` binary, puts `openspec` on `PATH`, and turns off the telemetry and the update check of OpenSpec. The smoke test of the image, in `ci.yml` and `release.yml`, runs `openspec --version`.
- `CONTEXT.md` ("Lane"), `k8s/README.md` ("Roadmap service") and `k8s/devops/configmap.example.yaml` name the row and the settings.
- The row, the settings, the metric and the image are observable, so the change carries spec deltas for `roadmap-stage` and `roadmap-service-deployment`.
- The change fits one pull request.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `roadmap-stage`: the Service runs the job, the settings name the filter, the limit and the step budget, and each item counts once by its result.
- `roadmap-service-deployment`: the Service image runs the pinned OpenSpec.

## Feasibility

Checked on 2026-10-29 against the real system:

- `docker run python:3.14-slim-trixie sh -c 'command -v node npm'` finds neither. So the image needs a Node runtime, as the issue says.
- The official image `node:24-trixie-slim` (digest in the Dockerfile) holds `node` v24.22.2 at `/usr/local/bin/node`. Copied alone into `python:3.14-slim-trixie`, the binary runs and prints `v24.22.2`. It links only to `libc`, `libstdc++`, `libm`, `libgcc_s`, `libdl` and `libpthread`, which the base image has.
- The cost of the runtime is about 122 MB on disk: `du -sm /` of the base image reads 125, and 246 with the binary. In the built service image the layers are 127 MB for `node` and 18 MB for `/opt/devops-tools`, in an image of about 1.67 GB, of which the virtual environment is 874 MB.
- The locked OpenSpec 1.14.3 declares `"node": ">=20.19.0"`. The `.node-version` of the repository is 24, and CI and the devcontainer run it. The Node of Debian trixie is 20.19.2 (`apt-cache policy nodejs`). The change does not use it: upstream ended Node 20 in 2026, and the image would then run another major version than CI.
- `docker build --target service` of the new Dockerfile succeeds. In the image, as user 1000, `which openspec` prints `/opt/devops-tools/bin/openspec`, `openspec --version` prints `1.14.3`, and `openspec list --specs` exits 0 in a scratch project. `OPENSPEC_TELEMETRY`, `OPENSPEC_NO_UPDATE_CHECK` and `DO_NOT_TRACK` are set.
- The first build showed that the installer makes the version directory mode 0700 (it stages in a temporary directory), so user 1000 got `Permission denied`. The builder stage runs `chmod -R a+rX /opt/devops-tools` after the install, and the second build runs as user 1000.
- `trivy image --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed` on the built image reports 0 findings for the `Node.js` and the `usr/local/bin/gh` and `Python` targets. The findings it reports are Debian packages of an earlier cached `apt-get upgrade` layer, which a fresh CI build refreshes.
- `MODEL_LANE_ROWS` and `JobRow.cross_job_predicate` already exist for refine. `apply_refine` returns `RefineApplied.readied_count`, so the row needs one new field on `JobOutcome` and no change to refine.
- `RoadmapStageConfig` already holds `step_tokens` with its variable (#2654). `SettingVariables` reads a list setting from a JSON list or comma-separated values, so `filter` needs no parser of its own.
- The premise holds. No part of the item needs code that compensates for a missing tool.

## Existing Tool Considered

OpenSpec's pinned npm lockfile and `devops install-tools` (#1842) cover the install: the Dockerfile runs the same command that CI and the devcontainer run, so the Service gets the same version, with the same sha512 checks. The official `node` image covers the runtime, and Renovate bumps its digest as it bumps the other base images. The due table of `roadmap/run.py`, the settings declarations and `instruments.py` cover the row, the settings and the metric. Nothing new is built except the glue of the row, about 40 lines, and `stage_filter.py`, which moves the check of a filter entry out of `stage.py` so the settings can use it without loading the model client. The change deletes no internal code.
