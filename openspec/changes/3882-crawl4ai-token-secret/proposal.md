# Proposal

## Why

Issue #3882: the Crawl4AI service, planned in the next issues, listens beyond loopback only when `CRAWL4AI_API_TOKEN` is set. No credential, cluster Secret row or README table entry for this token exists. A person must be able to run `devops k8s push-secrets` to create the Secret before the service starts.

## What Changes

- `src/devops_cli/config/env.py`: add the credential `crawl4ai.api_token` with the alias `CRAWL4AI_API_TOKEN`. It has no field in the settings and no getter, so no tool parameter and no MCP option takes it.
- `src/devops_cli/k8s/cluster_secrets.py`: add the row `devops/crawl4ai` (key `CRAWL4AI_API_TOKEN`, generated with `SecretGenerator("urlsafe", 32)` when the keyring lacks it). Add the key `DEVOPS_CLI_CRAWL4AI_API_TOKEN` (not required) to the row `devops/devops-cli`. Both read the keyring value `crawl4ai_api_token`. The row `devops/crawl4ai` comes first in the table, so one push makes the value before the second entry reads it.
- The row `devops/crawl4ai` restarts no workload. The gate test of restart targets accepts a workload only when a manifest holds it, and Deployment `crawl4ai` does not exist yet. The manifests issue (#3884) adds `deployment/crawl4ai` to the row.
- `k8s/argocd/apps/projects.yaml`: add Secret `crawl4ai` to the orphaned resources that Argo CD ignores, as a gate test requires for each row.
- `k8s/README.md` and `docs/ENV_VARS.md`: list both rows and the variable.
- The change creates no Secret and pushes none. A manifest is not touched.
- The secret table and a credential are observable, so the change carries a spec delta for the new capability `crawl4ai-api-token`. The change fits one pull request.

## Capabilities

### New Capabilities

- `crawl4ai-api-token`: the keyring value of the Crawl4AI token and the two cluster Secret entries that it feeds.

### Modified Capabilities

None.

## Impact

- Source: `src/devops_cli/config/env.py`, `src/devops_cli/k8s/cluster_secrets.py`.
- Manifests: `k8s/argocd/apps/projects.yaml`.
- Documentation: `k8s/README.md`, `docs/ENV_VARS.md`.
- Tests: `tests/k8s/test_cluster_secret_plan.py`, `tests/k8s/test_cluster_secret_push.py`, `tests/invariants/test_k8s_manifests.py`, `tests/commands/test_config_audit_keys.py`.

## Feasibility

- The entrypoint of Crawl4AI v0.9.5 (`deploy/docker/entrypoint.sh`, read on 2026-11-07) binds `127.0.0.1` when `CRAWL4AI_API_TOKEN` and `CRAWL4AI_JWT_ENABLED` are both unset, and binds all interfaces when the token is set. So the service needs the token.
- `ClusterSecret`, `SecretEntry`, `SecretGenerator` and `KeyringSource` already express the rows. The rows `valkey_devops_password` and `grafana.password` use the same pattern, and the push test of the notifier shows that a value generated by one row feeds a later entry of the same push.
- The test of restart targets (`test_every_restart_target_is_a_manifest_workload_or_helm_release`) refuses `deployment/crawl4ai` before a manifest holds it. So the restart moves to #3884. This is the only difference from the text of the issue.

## Existing Tool Considered

- The existing table of `cluster_secrets.py` and the command `devops k8s push-secrets`. The change adds no mechanism and deletes no code.
- A JWT (`CRAWL4AI_JWT_ENABLED`) was rejected: it needs a signing key and a token call, and gives nothing for two internal callers.
