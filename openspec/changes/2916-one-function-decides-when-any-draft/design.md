# Design

## Decisions

- **`draft_readiness(draft, extra_checks=())` is a pure function in `implement_pull.py`. Its one input is `Draft`: the kind, the pull request (`PullStatus`), the recorded item, the check runs (`CheckVerdictSummary | None`), the change folder (`ChangeFacts | None`: archived or not, and the text of `tasks.md`) and `declared`.**: `stage_ready.py:40` already imports `mark_ready` from this module, so the row, the job and the commands reach both functions in one import, and a pure function takes a table test of eight rows with no fake. Reading GitHub or a file is the work of the caller.
- **The answer is `Readiness(answer, reason)` with `Answer.READY`, `WAIT` or `REFUSE`.**: The three callers act on three different results. The row leaves the draft for both `wait` and `refuse`. `devops pr ready` exits 1 for `refuse` and 8 for `wait`, the codes it has today. The job stops for both.
- **Complete means: stage plan, always; implement, every group of `tasks.md` ticked and the change archived; agent and person, `declared`. Then the checks: `exit_code` 1 refuses, 8 waits. Then each entry of `extra_checks`, in order, and the first answer that is not ready wins.**: The incomplete answer comes first, so the refusal names the group and not a failed check. For the implement kind the unticked groups are tested before the archive, so a plan that is not archived yet still names its groups.
- **The checks rule is `CheckVerdictSummary.exit_code`, and `checks=None` skips it.**: `exit_code` (`check_verdict.py:106-120`) is the rule that `is_passing` and the buckets of `_judge_checks` already follow, so the row, the job and `pr ready` keep their results. `check-readiness` reports the checks as its own blockers, so it passes `None` and gets no second line for the same failed check.
- **`declared` is the word of the author, and the caller gives it. `devops pr ready` gives true, because the author ran it. `check-readiness` gives `not draft`.**: A label or a comment marker needs a reader, and none exists: the stage row never reads the draft of a person (`stage_ready.py` module text), and the job works only on the pull requests it made. A person who marks a draft ready in the browser needs no code to say so. The `wait` answer for these kinds exists for the table test and for the later evaluator.
- **`kind_of(item, pull)` reads the record, in this order: `owner/agent` gives agent, `owner/human` gives person, `implement.pr` equal to the pull request gives implement, `stage.pr` equal to it gives stage plan, else person.**: A claim must beat the record, because the issue says the claim of an agent or a person beats the Service's: a staged branch that an agent took over (`devops repos worktrees add`) keeps `stage.pr` but is no plan any more. The title is no signal, since the job rewrites it (`implement_run.py` `_pull_request` calls `client.update_pull(... title=self._delivery_title() ...)`).
- **`read_draft` finds the item by the head branch with `issue_of_branch`, then one `store.item(n)` read.**: A plan pull request closes no issue, so `read_closing_issues` (the GraphQL read of `merge_readiness.py`) gives nothing for it. The branch form `<type>/<issue>-<slug>` is checked by a hook (CONTRIBUTING.md section 5), and a branch that breaks it (a bot's branch) gives no item and so a person's kind, which behaves as `pr ready` does today.
- **For the implement kind, `read_draft` takes the path of `tasks.md` from the files of the pull request and reads it at the head with `get_file_at`: the archived folder first (`CONST_OPENSPEC_ARCHIVED_FOLDER_RE`), else the active folder of the issue.**: `openspec archive` writes a dated folder, so the path is known only from the file list. The tick state of an archived change is the final one, and the active folder names the groups of a pull request that is not archived yet.
- **The job reads the pull request and the check runs once more in `_ready`, and stops with the reason on any answer but ready.**: `Watch` holds only a kind, a reason and the first failed check (`implement_pull.py:43-49`), so the check runs are not in hand. Two reads per item, once, cost less than the watch. A stop is the answer the taxonomy already has: the group phrase is added to the `plan_defect` rule (`failure.py:176-179`), whose action is `amend`, and a wait or a missing archive falls to `ci_infra`, whose action is one retry. A retry runs `_finish_change` again and so archives.
- **`devops pr ready` asks the function in place of `_ready_check_blockers`. Its warnings for the other blockers stay. `--force` still skips the whole question.**: Two deciders in one command would break the rule of the issue. `tests/commands/test_pr.py:420-446` keeps the exit codes honest: the same five scenarios must give the same codes.
- **`check-readiness` builds the blocker in `commands/pr.py`, with a new `BlockerKind.READINESS`, and appends it to the verdict with `dataclasses.replace`.**: `assess_merge_readiness` cannot import the function (the import cycle in the Feasibility section). `monitor` and `pr ready` never see the kind, since they build the verdict without it.

## Rejected alternatives

- **A new module `roadmap/pr_readiness.py`.**: The issue's own design rejects it, and the fact holds: both callers of `mark_ready` import `implement_pull.py` today. The import cycle does not need a new module, since the commands are the only callers outside the roadmap package.
- **Call the function from `assess_merge_readiness`.**: `ImportError ... circular import` (run in the Feasibility section). A lazy import inside the function would hide the cycle, and `pr monitor` would then judge a kind that it never maps to an exit code.
- **Keep `ready_to_mark` as a one-line call of `draft_readiness`.**: `openspec/specs/roadmap-stage/spec.md:412` says it is the only function that decides. Two names would make two places that a test replaces. The project keeps no shim before `1.0.0`.
- **Take the kind from the title or the body (`Plans #N` against `Closes #N`).**: The job rewrites both when it takes over a staged pull request, and an agent does the same. The record of the item does not change by itself.
- **Give the function the `Watch` of the job as its checks.**: `Watch` has no check list (`implement_pull.py:43-49`). Adding one changes the watch for a gain of two requests.
- **Wait in the job when the answer is `wait`.**: The watch has just ended with every check passed. A new running check at that instant is a race that a retry handles, and a loop in `_ready` would need its own timeout setting.
- **Drop the duplicate blocker of an unarchived pull request in `check-readiness`.**: `archives_its_change` (`grounding.py:232`) already blocks a pull request with no archived folder, and the new blocker adds a second line only for a pull request with all groups ticked and no archive. One more rule to hide a line in a rare case costs more than the line.
- **Let `check-readiness` call a helper that only counts unticked groups.**: The issue asks that the command calls the one function, and the evaluator of #2867 must reach `check-readiness` through the same function when it is added.
