# Design

## Decisions

- **Add the two profiling fields to the declared `customMetrics` list and let Argo CD roll the DaemonSet, instead of a skip-reconcile window with a hand-edited DaemonSet.**: The list already asks for five profiling fields, and the cards without profiling support serve no line for them without losing their other GPU metrics; a hand edit is cluster drift that a person must restore, and the failure in the issue came from a second profiling client on the Tesla PG500-216, not from an unsupported field.
- **Set `checksum/counters` to the SHA-256 of the new list in the same group, and confirm the hashing convention by reproducing the staged digest before the edit.**: The chart mounts `customMetrics` with `subPath`, so a running exporter never reads a new list, and `k8s/monitoring/dcgm-exporter-values.yaml:41:checksum/counters: "f636a5dfff8c116f098785682de1789ee698a46ab69bbde4c79fed13963665a6"` is what makes the pod template change and the DaemonSet roll.
- **Keep the modified `dcgm-exporter` requirement text under 500 characters and carry the mount path and the type detail in its scenarios.**: The staged requirement text is 470 characters, and the two SM fields would push it past the 500-character limit that the plan check enforces, so the new text names the SM fields and the checksum, and the scenarios keep the mount path, the argument rule and the family census.
- **Change no test with the counter list.**: `tests/ai/test_llm_pool_metrics.py:def test_the_dcgm_exporter_runs_on_every_gpu_node_without_extra_privileges` reads the values file for the runtime class, the node selector, the tolerations, the capabilities, the rolling update and the ServiceMonitor, and `search_code` for `checksum/counters` found no test of the digest, so two more counter lines change no test.
- **Use `percentunit` with min 0 and max 1 for the two targets.**: DCGM defines both fields as a ratio from 0 to 1, so Grafana draws the percentage with no multiplication in the query, and the `nvidia-dcgm` dashboard already draws the profiling ratio `DCGM_FI_PROF_PIPE_TENSOR_ACTIVE` that way.
- **Aggregate each target with `avg by (hostname, gpu, modelName)`.**: The value is a utilization ratio, and the profiling panel of the same row groups by the same three labels at `k8s/monitoring/dashboards/llm-stack.json:1399:"expr": "max by (hostname, gpu, modelName) (DCGM_FI_PROF_PCIE_RX_BYTES)"`, so the mean of duplicate series keeps the ratio and one line is drawn per card.
- **Place the panel at y 83 of the GPU row with id 39, and move the row `Qdrant` and the panels after it down by 8.**: The last panel of the GPU row ends at `k8s/monitoring/dashboards/llm-stack.json:1379:"y": 75` plus its height of 8, and the row `Qdrant` sits at `k8s/monitoring/dashboards/llm-stack.json:1423:"y": 83`; the dashboard lint refuses an overlap, so one later block of rows moves and no other panel changes.
- **Add no metrics fixture and no test that asserts a value of a manifest, and give the two queries a promtool case file instead.**: `tests/fixtures/metrics/dcgm-exporter.yaml` is no file of the staging commit and the tests that read it are gone, while `tests/prometheus/test_dashboard_queries.py:def query_mismatches` already compares a case query with its panel target, so the case file gives the two queries a check without adding a test module that reads the dashboard.
- **Deliver the counter list and the panel in one pull request.**: The panel reads two families that the list must ask for, so the two changes prove each other, and the project delivers one item by one pull request that delivers nothing else.
- **Deliver the third acceptance criterion through group 2, whose verify runs the dashboard check at its current home, and keep no `pending-person` entry for it.**: `tests/test_stack_dashboards.py` is no file of the staging commit, and `docs/TESTING.md:62:The `test-tree` row of `devops ci` refuses a new test that reads a committed manifest or config file` refuses a new module that reads the dashboard, so the criterion's check lives in `tests/prometheus/test_dashboard_queries.py`, which group 2 makes fail before the panel and pass after it.

## Rejected alternatives

- **A manual skip-reconcile window that annotates the Argo CD Application and edits the DaemonSet by hand.**: It is cluster drift that a person must restore, and the failure in the issue came from a second profiling client on the Tesla PG500-216, not from an unsupported field; the declared list already holds five profiling fields that the cards without profiling support skip.
- **A second exporter pod to capture the two fields.**: The DCGM profiling module serves one client per GPU, and the deployed exporter pod is that client; the temporary pod of the same image got no profiling field, and on the Tesla PG500-216 node its GPU collector failed with `error watching fields: The third-party Profiling module returned an unrecoverable error`.
- **Unit `percent` with a factor of 100 in each query.**: It adds a multiplication to each target and hides the ratio from 0 to 1 that DCGM reports, while `percentunit` draws that ratio as a percentage.
- **Unit `short`.**: It draws a bare number with no percentage, and the two fields are ratios of time and of resident warps.
- **`max by (hostname, gpu, modelName)` on each target.**: It can draw the highest sample instead of the mean of a ratio, and the profiling panel of the same row aggregates with `max by` only because its value is a byte rate, not a ratio.
- **No aggregation on the two targets.**: A second series for one GPU would draw a second line for the same card, because the exporter may serve more than one series per field and card.
- **Invent a label set for the two families.**: The panel query and the live series would disagree, while the other GPU panels already group by `hostname`, `gpu` and `modelName` at `k8s/monitoring/dashboards/llm-stack.json:1399:"expr": "max by (hostname, gpu, modelName) (DCGM_FI_PROF_PCIE_RX_BYTES)"`.
- **Add a metrics fixture from a capture of the two fields.**: No capture of the two fields exists, the fixture `tests/fixtures/metrics/dcgm-exporter.yaml` is no file of the staging commit, and a test that reads a committed capture is a value test that the `test-tree` row refuses.
- **Recreate `tests/test_stack_dashboards.py` so the third criterion's command runs.**: `docs/TESTING.md:62:The `test-tree` row of `devops ci` refuses a new test that reads a committed manifest or config file` and `tests/gate/tree_checks/config_reads.toml:6:No line is added.` refuse a new module that reads the dashboard, so the plan plans no code that compensates for the deleted path and delivers the check in `tests/prometheus/test_dashboard_queries.py`.
- **Split the counter list into its own pull request.**: The panel queries a family that the list must ask for, so a split leaves the panel without the field that it charts and adds a second pull request for one item.

## Security

Nothing new crosses a trust boundary. The dcgm-exporter DaemonSet keeps `runAsUser: 0`, the `SYS_ADMIN` capability and its access to the GPUs of each node, and the two added counter lines only make it collect two more profiling gauges of the same cards. A person confirms after the rollout that the pod still carries its `securityContext` and that its log holds no `Failed to watch DCGM fields`. The `k8s` row of the pull request fails if the values no longer render, and the manual digest step fails if the list and `checksum/counters` disagree.
