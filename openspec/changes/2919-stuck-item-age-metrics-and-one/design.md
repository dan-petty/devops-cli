# Design

## Decisions

- **Read the label events of one issue, through a new store method `label_changes(number)`, and keep the time of each item in the process until its status or owner label changes.**: `GET repos/<repo>/issues/<number>/events` gives every label event of the issue in one page for 78 of 78 open items (the most is 13 events, Feasibility 4). A read only when the label changes costs at most 209 requests in the busiest day measured, about 9 an hour, against 360 an hour for a read of every item each round (Feasibility 5). The cache is a module variable of `src/devops_cli/github/metrics.py`, like `_sent_item_series`, and `tests/conftest.py` resets it after each test.
- **Put the read in the store and not in `metrics.py`.**: The row gets `store` from the Service (`_run_metrics_adapter` in `run.py`), and `tests/roadmap/test_roadmap_run.py` runs it over `InMemoryRoadmapStore`. A `gh` call in the metrics module runs the real program in that test. `InMemoryRoadmapStore` already records a `labeled` change with its clock for each label a write adds (`_relabel` in `memory_store.py`), so the same method serves both adapters, and the contract suite `tests/roadmap/test_roadmap_store_contract.py` can pin them together.
- **Send the issue number as the value of `devops_cli_roadmap_oldest_item_number`, with the labels `repo`, `state` and `plan` only.**: The issue wants the item number in the alert message. The owner called an issue number as a label "unsafe" on #3069 and pointed to `bounded_label` (#2742). An alert annotation can read a second series with the `query` function, and promtool 3.15.1 accepted and tested that rule (Feasibility 7). So no label holds an issue number, and the series set stays at 12 for each repository.
- **Send every pair of a status and a plan flag each round, with 0 for an empty pair.**: The pairs are a closed set, 6 statuses (`CONST_ROADMAP_STATUS_VALUES`) times 2 flags. A pair that sends 0 each round never keeps a stale age, so the age gauges need no "send 0 once" memory like `_emit_item_counts` has. That memory serves `devops_cli_project_items`, whose labels (release, type, priority) are an open set. The cost is 25 points a round for a repository.
- **The `plan` flag is true when the job record of the item holds `stage.pr`.**: `docs/ROADMAP_WORKFLOW.md:82` names `stage.pr` as the record of a Ready item that is Staged, an item whose plan pull request waits for a person (gate G1). The job record comes with the issue listing, so the flag costs no request. A check for the change folder on the default branch costs one `path_changed_at` request for each item.
- **Compute the age as clock minus the time of the latest `labeled` event of the current label that no `unlabeled` event of the same label followed.**: A person can remove a label and add it again, and the item then entered the state at the second event. The clock is a parameter `clock: Callable[[], datetime]` of `collect_project_metrics_report`, the form that `InMemoryRoadmapStore(clock=...)` takes, so the test of the issue (an event at T, a clock at T plus 3600, a gauge of 3600) needs no patch of the wall clock.
- **A failed read of the events logs a warning and sends no age.**: `collect_project_metrics_report` catches `GitHubOperationError` around the age code only. The report keeps the releases, the CI runs and the item counts. The adapter's own `except Exception` in `_run_metrics_adapter` would drop all of them for one failed issue, and a blind `except` adds a site to the ceiling of `tests/fixtures/swallowed_failures_ceilings.json`. The gauges then go without a new point that round. An old series ends by the staleness of Prometheus, and the dashboard shows no data, not 0.
- **The alert threshold is the literal 86400 seconds in the rule.**: Of the six Service rules with a numeric threshold, five use a literal: 7200 seconds (`RoadmapServiceLaneStalled`), 352 (`RoadmapServiceModelRequestsHigh`), 20 (`RoadmapServiceWebhooksRejected`), 300 (`RoadmapServiceGitHubWritesHigh`) and 150 (`RoadmapServiceSelfDeliveriesHigh`). The README table names each one. Only `RoadmapServiceGitHubRequestsHigh` follows a setting. A setting needs a field, a configmap key, a served series, two reference documents and a constant (Feasibility 8). The issue says "a set time" and gives no setting. A person who wants another value edits one line of the rule and one line of its unit test.
- **Put the alert in a new group `roadmap-service-items`.**: The group `roadmap-service-activity` is "what the Service writes, the deliveries of its own writes and its web search" (`prometheus-values.yaml`, comment above the group), and its requirement names its three alerts. An age alert is not Service activity. The plan of #2950 appends its alert to that group. A group of its own makes the two changes edit different spec requirements, different fixture files and different rule groups.
- **Put the panel in `project-metrics.json` at `x` 0, `y` 34, 12 wide and 8 high, and move the rows below it down by 8.**: The items panels "Items by Release" and "Active Items by State" are in that row (`y` 26 to 34), and `_PURE_DEVOPS_CLI_DASHBOARDS` lists the file. The owner said to build the age panel so it can sit next to the inbox panel and not to wait for it (#2919). The free right half is that place.
- **The alert reads the last sample of the last 30 minutes, with `last_over_time`.**: The metrics row sends each round, every 13 minutes by default. Prometheus drops a series that has no sample for 5 minutes, so an instant selector would flap. The webhook rule uses the same form (#2505). The window is longer than one round, so one missed round does not clear the alert.
- **The `plan` flag follows the job record as the store holds it.**: A stage pull request that a person closes keeps `stage.pr` until the stage job writes the record again (`stage.py`, `StageRecordKey.PR`). The age then keeps counting in `ready` with a plan. The item does not change state on a close, so the rule cannot tell the two apart. The stage job writes the record again when it stages a new plan.
- **An item with a status label and no `labeled` event in its history gets no age in that round.**: The row logs a warning that names the item. The other items of the pair still count. A missing event is not an error that stops the round.
- **The cache keeps the time while the status and owner labels stay the same.**: A status that changes and changes back between two rounds keeps its first time, because the cache key does not change. The spec requires no read while the labels stay the same, so the cache cannot see that change. The cache is pruned to the items of each round, so a closed item leaves it.
- **A stale pod can fire the alert for up to 30 minutes after it stops.**: Each pod sends its own series, with its own `service.instance.id`. `max by` over the window reads the last value of a pod that stopped, so a restart can keep an old number for the window. The Service runs one replica with the Recreate strategy, so only one pod sends at a time. A rule that drops a stopped pod needs a join on the instance label. This change does not add that join, so the limit stays, and the two-pod promtool case is not in this change.

## Rejected alternatives

- **Read the repository events (`issues/events`), page by page, newest first, as `changes_since` does.**: It costs 1 page a round in the steady state, less than 9 an hour, but the first round must read back to the oldest label event of each item, and GitHub stops the listing at page 300 (HTTP 422 at page 301, Feasibility 3). Page 300 starts at 2026-09-09, so an item older than that gets no age. The per-issue read has no such limit and costs 78 requests once.
- **Read the events of every item each round.**: 78 x 4.6 = 360 requests an hour, 72% of the budget of 500. ADR 0016 rejects "a read of each Item's timeline costs one request for each Item" (`docs/adr/0016-labels-hold-the-roadmap-items-fields.md:28`) for the actor of each event. This design keeps that cost low by one read for each change of a label, and the ADR's consequence "a label change is an issue event" supports reading the event. The ADR needs no amendment.
- **Put the item number in a label `item`.**: One new series for each change of the oldest item, bounded by the number of issues (about 3,240 numbers so far), and the owner called it unsafe (#3069). A value gauge has no such cost.
- **An info series `devops_cli_roadmap_oldest_item_info{item=...} 1` and a `group_left` join in the rule.**: It has the same label problem as the label `item`, and the rule and its unit test need a join on `repo`, `state` and `plan`.
- **A gauge of the time the item entered the state (`..._since_timestamp_seconds`) and `time() - x` in each query.**: Criterion 3 of the issue asks for the age, computed with a fake clock. The precedent `devops_cli_service_job_start_timestamp_seconds` shows the form. It would keep the age right while the Service is down, which the age gauge does not. The issue and the refine decision chose the age.
- **Use `updated_at` or `created_at` of the issue.**: `updated_at` moves with any edit or comment (`IssueRecord` docstring in `store.py`), and `created_at` is the age of the issue, not of the state.
- **Read the events of each issue in the metrics module through `gh`.**: See the second decision: it breaks the store seam that `tests/roadmap/test_roadmap_run.py:1375` uses.
- **Add a setting `service.item_stuck_hours` and send it as a series.**: See the threshold decision: at least eight files for one number that the owner has not asked to change.
- **Add the age to `devops roadmap inbox`.**: The inbox is a list for a person. Its "age" is the time since the last update, and the issue asks for a metric.
