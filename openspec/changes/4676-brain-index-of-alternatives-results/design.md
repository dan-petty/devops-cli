# Design

## Decisions

- **The alternatives row writes the index, after its checks.** The owner decision of 2026-11-13 keeps the scope in the alternatives step. `sync_alternatives_round` (`src/devops_cli/roadmap/brain_sync.py`) takes the plan of the round and the store. `_run_alternatives_adapter` calls it after `record_coverage` and before `raise_for_failed_checks`, so a round whose checks all failed still copies the changes of other issues. The command `devops roadmap alternatives` writes no index: a workstation names no store, and the next round of the row copies its checks from the watermark.
- **The step reads the issues of the store of the round.** They are the listing snapshot that `IncrementalListing.read` gave for the selection, with each issue that a write of the round returned. So the step sends no GitHub request, and it sees the checks of its own round.
- **Three modules.** `brain_entries` reads one issue into a `BrainEntry` and holds no I/O. `brain_index` holds the keys and the commands of the store. `brain_sync` holds the step: the watermark order, the bound, the join across items and the instruments. Each is under 300 lines.
- **The record gives the facts, and the block gives the name.** The record holds the verdict, the time, the two hashes, the URL of the tool and its canonical id as text that a machine wrote. The block gives the name that the check wrote for the tool, read from the tool line by the template `alternatives_block_tool`. A record with no block is no check, as `recorded_check` of refine decides. The two sections of the reference step (#4672) and its line `Class: <type>, no model call.` change no field that the index reads.
- **The record is read by the text of its keys.** `alternatives.refs` and `alternatives.brain_used` are keys of #4672 and #4682. `decode_job_record` keeps only the keys that `AlternativesRecordKey` declares, so an entry gets them when their issues declare them, with no change of this code.
- **A reference is a GitHub repository.** The key is `brain-ref:<owner>/<name>:<h16(repository URL)>`. `project_of` gives the repository of a permalink, and a documentation page outside GitHub names no repository. An entry keeps each repository one time and at most 3.
- **The near items come from the tool.** The near items of an entry are the other items of the repository whose check names the same canonical tool, the newest check first, at most 5. The snapshot gives them with no request and no embedding call. #4682 can replace them with the nearest items of the aggregate.
- **`uses` holds the entries of `alternatives.brain_used`.** It is a fact of the check of the item, as each other field of the item hash is. A count of the uses of an entry is a read over the item hashes, which a later item can keep.
- **One WATCH transaction for each item, through `watch_and_write`.** The transaction watches the item key and reads its `checked_at`. Each hash is written whole with `HSET` and gets its TTL again with `EXPIRE`, so no field of an older check stays and no `DEL` is necessary.
- **The newer check wins by `checked_at`.** The callback of the transaction sends no command when the held `checked_at` is after the one of the block. An equal time is a write, so a change of the state of an issue reaches the entry.
- **The stream is one for each repository, with a TTL.** `roadmap:v1:brain-events:<owner>/<name>` matches the ACL pattern and the patterns of `RepoRef.valkey_patterns`, so the data of one repository stays together. Each `XADD` bounds it with `MAXLEN ~ 10000`, and an `EXPIRE` in the same transaction gives it the TTL of the hashes, so only the watermark key has no TTL.
- **The watermark is a hash with the place and the sync time.** `changed` and `number` are the `updated_at` and the number of the last issue that the step examined, and `synced_at` is the end of the last sync. The pair orders issues that changed in the same second, so a bound inside such a group loses no issue. `ValkeyCacheTier.set` always sets a TTL, so the key is a hash that `hset` writes with none.
- **A sync that fails keeps its place and writes no sync time.** The step stops at the first write that the store does not answer, writes the place of the last copy when the store accepts it, and counts one `fallback`. The lag of the next sync then shows the gap.
- **The bound counts transactions.** One round sends at most 500 item transactions. `limit` is a parameter of `sync_brain_index`, so a test shows the bound with 3 issues.
- **`fallback` is a result of `devops_cli_brain_reads_total` with the store `brain_index`.** The counter and the value exist since #4668. `devops_cli_brain_writes_total` counts each copy as `shared`, `older` or `skipped`.
- **The first read is counted at the write.** `Written.NEW` says that the index held no entry of the item. The step counts it for an item that the round checked. `devops_cli_brain_first_reads_total` has the label `row`, and the step sends its count, 0 included, in each sync that completes.
- **The gauges name the store and the repository.** One Service keeps several repositories, so `devops_cli_brain_entries` and `devops_cli_brain_sync_lag_seconds` have the labels `store` and `repo`, with `RepoRef.key` as the value.
- **The egress rule is in `roadmap-service-egress`.** The policy already selects the Service pod and has the type `Egress`. `check_only_the_service_pod_may_reach_the_api_server` compares its whole egress list, so the gate holds the new rule to the pods of the store and TCP 6379.
- **The ConfigMap names the user, and the Deployment gives the password.** `roadmap.state.username: brain` is in `k8s/devops/configmap.example.yaml`, and `DEVOPS_CLI_ROADMAP_STATE_PASSWORD` comes from key `brain` with `optional: true`. A pod with no password sends no user. A pod that reads the index later sets `DEVOPS_CLI_ROADMAP_STATE_USER` to `agent`, which wins over the file: a load of the settings with both sources gave `agent`.

## Rejected alternatives

- **Write the index entry from the `Check` in `AlternativesWriter.settle`.** Rejected: the index then has two builders of an entry, the `Check` of a round and the block of a snapshot, and ADR 0023 section 3 names the block and the record as the one durable copy. `sync_brain_index` reads `IssueRecord` only.
- **A method `hgetall` or a second WATCH method on the tier, to read the whole held entry.** Rejected: `watch_and_write` (`src/devops_cli/valkey/cache.py:215`) reads the one field that the rule needs, `checked_at`. The tier gains 1 method, `scan`.
- **`KEYS` or a set of item numbers for the count of entries.** Rejected: `KEYS` is in the category `dangerous`, which the user `brain` does not hold (`+@all -@dangerous`), and a set is one more key with no TTL. `SCAN` with `MATCH roadmap:v1:brain-item:<owner>/<name>:*` needs no new key, and the store holds only the keys of the index.
- **One stream `roadmap:v1:brain-events` for the Service.** Rejected: `RepoRef.valkey_patterns` (`src/devops_cli/github/repo_ref.py:214`) finds only keys that hold the repository, so the removal of a repository would leave its entries in a shared stream.
- **A new policy file for the egress rule.** Rejected: `k8s/devops/roadmap-service/networkpolicy-egress.yaml` holds the one `Egress` policy of the Service pod, and its gate check compares the whole rule list. A second policy would hold a rule that no check reads.
- **The nearest items by embeddings in the sync.** Rejected: the step would call the embedding model for each changed item, and #4682 names the aggregate as the source of the nearest items.
- **A fixed bound of 600 s for the lag.** Rejected: the alternatives row runs about six times a day (`docs/roadmap/alternatives.md`, "Which items a run takes"), so the lag is about 4 hours. The description of the instrument gives the bound as the interval of the row and the time of one round.

## Security

- The index holds data of public repositories only: the check is off for a private repository, and a round whose check is off makes no sync.
- An entry holds a verdict, ids, hashes, URLs, the name of a tool and item numbers. It holds no body text and no credential.
- The password of `brain` reaches only the container `service` of Deployment `roadmap-service`. No Job template and no container `agent` gets a key of the store or the label `valkey-client`.
- The egress rule names the pod selector `app.kubernetes.io/name: valkey` and TCP 6379. It is no wider than the ingress rule `valkey-ingress-roadmap` of the store.
