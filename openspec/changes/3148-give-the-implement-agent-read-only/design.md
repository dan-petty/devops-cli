# Design

## Decisions

- **Take the tool names of the step from `TOOLS` through `tool_names(HOLDER_IMPLEMENT)`, and add the implement holder to `read_file` and `list_files`.**: The registry is the one source that the stage tools and the MCP role tables already read, and the two read tools serve both hosts, so a second hand-written set would drift from the registry.
- **Reach the symbol graph and the repository map through the shell commands `uv run devops ai ast graph` and `uv run devops ai repomap`.**: On the MCP server a path is a path of the server tree, and the role tables name no path tool, so those commands read the job's checkout at HEAD, including the uncommitted edits of the agent.
- **State the tool counts in one new line beside the table of the steps in the comment of the Job, and write no rule over the table itself.**: The criterion names the PR comment of a Job, and `src/devops_cli/roadmap/implement/implement_run.py:1531:def _comment(self, pull: int) -> None:` already writes that comment; the table keeps its last failing command, which is a command line with paths, so a rule over the whole comment would make a Job with a failed check contradict it.
- **Drop `security_intel_network` and `security_intel_package` from the implementation role, keep them in the planning and review roles, and state the counts 28, 15 and 16 in the two tests that count the roles.**: The criterion holds that a tool of the agent cannot reach the network, and both lookups send a value the model gives to an outside service; a plan and a review look up an advisory, and the step reads its own code. So the implementation role becomes the smaller of the two, and its two count tests state that.
- **Keep the `("ai", "ast")` row of `LOCAL_COMMANDS` and give it access read with a use text that names no `--output`.**: The base requirement holds that name, so a replacement would contradict the living spec; the read access and the printed forms give the agent the same tools.
- **Add no filter of `PATH_CONFINEMENTS` to `tools_for_role`.**: `src/devops_cli/ai/mcp/roles.py:70:ROLE_IMPLEMENTATION: _GITHUB_READS | _SECURITY_INTEL | {"pr_describe"},` shows the role's three name sources, and the plan adds no name to them, so a filter would decide no member that the role holds; a model review of the earlier plan found that claim false and the plan drops it.
- **Keep the RAG query of the project documents out of the step.**: The shell policy names the reason at `src/devops_cli/roadmap/implement/implement_shell_policy.py:163:A command that needs a key or a cluster is not here (#3562, #3563).` so no scoped token exists for the shell, and the change adds no RAG tool.
- **Add `--no-tools` to `devops roadmap eval implement`, as `--no-toolbox` does for the stage eval.**: One model on one fixture set in two runs keeps the scoring path the same, and the report states the mode so that two reports compare.
- **Allowlist the 15 tools that stay in the implementation role: the 14 GitHub reads and `pr_describe`, and remove the two lookups.**: Each of the 15 is marked read-only in the exposure table and reads the job's own repository, the two lookups send a model-given value to an outside service, and the count test states 15 so a member that the plan has not decided fails it.
- **Keep the prompt edit to one new placeholder, `{{tools}}`, and leave the three tables that #4645 rewrites as they are.**: #4645 replaces the program, local-command and refusal tables with a preset, so this change adds its table and touches no other placeholder of `src/devops_cli/ai/tasks/roadmap_implement_step.md`.
- **Assert the tool counts of the pull request comment in `tests/roadmap/implement/test_roadmap_implement_job.py`, with one failed check whose command names a path.**: That module runs the Job of `src/devops_cli/roadmap/implement/implement_run.py`, which builds the comment, and the failed check shows that the table keeps its command while the line of the counts holds no path.
- **Keep the two security lookups in the catalogue, the planning role and the review role, so the files that name them stay unchanged: the tool in `src/devops_cli/ai/mcp/server.py`, its spec `openspec/specs/threat-intel-lookup-outcome/spec.md`, the persona map `src/devops_cli/ai/tools/registry.py`, the exemption table `src/devops_cli/ai/mcp/path_confinement.py`, the tool list `docs/MCP_TOOLS.md`, the listing snapshot `tests/ai/mcp/__snapshots__/test_mcp_tool_listing/test_the_tool_listing_matches_the_snapshot.json`, and the tests that call the tools directly.**: Only the role table and the registry holders change: a person and the planning and review roles keep both lookups, and the direct tests of the tools keep their subject.
- **Write group 6 against the registry holders and the role table as they are at the staged commit, and treat #3244 as an overlap and not as work that merges first.**: Issue #3244 is open and changes the same two paths; the two lookups leave the implementation holder in `TOOLS` either way, so the later of the two changes rebases on the other and no task states an edit that a merged #3244 would have removed.
- **Keep the text of the modified requirement under 500 characters by moving the list of the five commands into the scenario that asserts it, and name the workflow document in its scenario with no code span.**: The check refuses a requirement text over 500 characters, and it refuses a scenario that names a file with no behavior test that names that file; the scenario still asserts the table of the document through `local_commands_table()`.
- **Cite the base requirement of the command table by its spec path alone, and name no line of it.**: The heading of that requirement holds a phrase that reads as a command of the CLI, so a path:line:text citation of it fails the check of the cited commands; the spec path identifies the requirement and group 7 verifies it.

## Rejected alternatives

- **Keep the two security lookups in the implementation role, and state that the server makes the network call and not the agent.**: `src/devops_cli/ai/mcp/server.py:113:Check IP or domain threat intelligence via Shodan and Cloudflare Radar.` shows that `security_intel_network` sends the `target` that the model gives to two outside services.
- **Add a filter of `PATH_CONFINEMENTS` to `tools_for_role`, as the earlier plan did.**: `src/devops_cli/ai/mcp/roles.py:70:ROLE_IMPLEMENTATION: _GITHUB_READS | _SECURITY_INTEL | {"pr_describe"},` names no tool of the table at `src/devops_cli/ai/mcp/path_confinement.py:23:PATH_CONFINEMENTS: Final[Mapping[str, frozenset[str]]] = {`, so the filter would decide no member of the role and a model review found the claim behind it false.
- **Give the step the MCP tools `ai_ast_graph`, `ai_repomap` and `ai_rag_query`.**: `src/devops_cli/ai/mcp/roles.py:8:The tables name only tools that need nothing from the files of the job.` On the server a path is a path of the server, so those tools read the server tree and not the job's checkout.
- **Write a second AST graph and repository map inside the implement step.**: The project already ships both: `src/devops_cli/roadmap/implement/implement_shell_policy.py:172:("ai", "repomap"),` and `src/devops_cli/roadmap/implement/implement_shell_policy.py:177:("ai", "ast"),` are the two commands, so a second implementation would copy code the project already ships.
- **Filter the tool list in the MCP client only, and keep the server role table as it is.**: `src/devops_cli/ai/mcp/roles.py:def tools_for_role` is the one place that decides the tools of a connection; a client-side filter is bypassable, and the MCP client gives no read-only guarantee.
- **Replace the `("ai", "ast")` row of `LOCAL_COMMANDS` with `ai ast parse` and `ai ast graph`.**: The base requirement holds the name `ai ast`, so a replaced row would contradict the living spec after the archive.
- **Write the arguments of each tool call into the Job log or the comment.**: `src/devops_cli/roadmap/implement/implement_tool_log.py:class ToolCallLog` builds the line from the tool name, the program and the outcome only, because an argument can hold a path or a secret.
- **State in the new requirement that the whole pull request comment holds no path, as the earlier plan did.**: The comment holds the table of the steps, whose header is `src/devops_cli/lang/en/messages.py:3759:| Last failing command |` and whose command comes from `src/devops_cli/roadmap/implement/implement_trace.py:345:def summary_table(rows: Iterable[SummaryRow]) -> str:`, so a Job with a failed check would contradict that rule; the new requirement covers the line of the tool counts only.
- **Run both tool modes in one invocation of `devops roadmap eval implement`.**: `src/devops_cli/commands/roadmap_eval_implement.py:122:check_only: Annotated[` and the options beside it each select one mode of one run; a second mode in one run would double the model spend with no person's choice.
- **State the tool counts in the issue comment of a finished Job instead of its pull request comment.**: The criterion names the PR comment of a Job, and `src/devops_cli/roadmap/implement/implement_run.py:1531:def _comment(self, pull: int) -> None:` already writes the steps of the run on the pull request, so the issue comment would state the run twice.
- **Assert the tool counts of the comment only in `tests/roadmap/implement/test_roadmap_implement_job_result.py`.**: That module tests the Service's row and its result line from a fake Kubernetes Job; the comment is built inside the run, so the assertion belongs in `tests/roadmap/implement/test_roadmap_implement_job.py`, which runs the Job.
- **Cite the base requirement of the command table as a path:line:text citation, as the earlier plan did.**: The heading of that requirement holds the phrase that the check reads as a command of the CLI, so the citation fails the check of the cited commands; the spec path alone identifies it.
- **Keep the whole text of the base requirement and add the two read-access sentences, and keep the document path in the scenario that names it.**: The check refuses a requirement text over 500 characters, and the scenario that names `docs/ROADMAP_WORKFLOW.md` would need a behavior test that names that path, so the text is cut and the scenario names the document with no code span.

## Unchanged references

- `src/devops_cli/ai/mcp/server.py` (tool name): The tool stays in the catalogue and the planning and review roles; only the implementation role drops its name.
- `docs/MCP_TOOLS.md` (tool name): The list states each tool with its read flag and names no role, so the role change leaves it as it is.
- `src/devops_cli/ai/tools/registry.py` (tool name): The persona map of the chat tool sets names the tool for a persona, and no persona is a job role.
- `src/devops_cli/ai/mcp/path_confinement.py` (tool name): The exemption table keeps the `target` of `security_intel_network` as no file path, because the tool stays for the planning and review roles.
- `tests/ai/mcp/test_mcp_argument_refusal.py` (import): The test calls the tool function directly, with no role server, so the role table does not reach it.
- `tests/ai/mcp/__snapshots__/test_mcp_tool_listing/test_the_tool_listing_matches_the_snapshot.json` (snapshot file): The snapshot holds the whole catalogue and no role, and the catalogue keeps both tools.
