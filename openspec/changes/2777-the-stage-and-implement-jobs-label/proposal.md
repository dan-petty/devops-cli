# Proposal

## Why

Issue #2777: the stage job and the implement job open and update pull requests through their own client, not through `devops pr create`. So their pull requests get no `type/*` and no `scope/*` label from the title. The latest 100 pull requests of the repository show it: the 43 that the App opened hold 0 labels, and the 42 of the owner hold labels in 23 cases. #2748 gave `devops pr create` the labels of the title. The two jobs must give them too.

Two facts shape the work. The title of a Staged item changes: the stage job opens `docs(openspec): plan #N ...` and the implement job later sets the title of the issue. So the implement job must also take off the labels that the staging title gave. And the stage job runs with a rule from #2753: rejected credentials stop the run, so a label failure must not hide them.

## What Changes

- The stage job adds the `type/*` and `scope/*` labels of the title of its draft, after it records the item and before it posts its comment. A refused label is a note in that comment. The branch, the draft and the record stay.
- The implement job adds the labels of the new title after it sets the title and the body, for a Staged item and for a Planned item. It removes each `type/*` or `scope/*` label that the pull request holds, that the old title gave and that the new title does not give. A refused label is reported in a comment on the pull request and does not stop the item.
- `RoadmapStore` gains the write `unlabel_issue`: one `DELETE` of one label of an issue or a pull request, with the GitHub store, the in-memory store and the request plan.
- `GitHubClient.get_pull` also returns the labels of the pull request, so the implement job reads the old title and the held labels in one request.
- `read_title_labels` and `add_pull_labels` take the store of the caller, not a repository name. `add_pull_labels` lets rejected credentials (HTTP 401) pass, and `pull_labels` gains `remove_pull_labels` and `stale_labels`.
- `devops roadmap stage --dry-run` and `devops roadmap implement --dry-run` list the new requests.
- `docs/roadmap/stage.md` and `docs/roadmap/implement.md` say what the jobs label.
- The change carries a spec delta in `roadmap-stage` and `roadmap-implement-job`: the labels of a pull request and the comment of a job are observable behavior of a service.
- The change fits one pull request.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `roadmap-stage`: the draft pull request gets the labels of its title, and a failed label does not stop the item
- `roadmap-implement-job`: the pull request gets the labels of the new title, and the labels of the old title that do not fit go

## Feasibility

Checked on `origin/main` 69234732 with the commands below. Each premise has its output.

- The jobs do not label. `git grep -n "label_issue\|add_pull_labels\|read_title_labels" -- src/devops_cli/roadmap/stage.py src/devops_cli/roadmap/implement_run.py` prints nothing (exit 1). The pull requests have three openers: `git grep -n "create_draft_pull\|\.update_pull(" -- src` gives `stage.py:1184` (the stage draft), `implement_run.py:561` (`_publish`, the draft of a Planned item) and `implement_run.py:613` (`_pull_request`, the title and body). `gh api repos/dan-petty/devops-cli/pulls/3169 --jq .labels` prints `[]` for this plan, a pull request of the stage job. Of the latest 100 pull requests, `--jq` printed `{"prs":43,"with_labels":0}` for the App and `{"prs":42,"with_labels":23}` for the owner.
- #3198 and #3213 did not do it. `git grep -n "pull_labels" -- src` shows the callers `commands/pr.py:1040-1041`, `pull_describe.py:27` and `inbox.py:45`, and none in `stage.py` or `implement_run.py`. #3215 asks the jobs to use `pull_form` for the text only.
- One call in `_pull_request` covers both implement paths. `execute` runs `pull = self._push()` then `self._pull_request(pull)` (`implement_run.py:380-381`). `_push` returns `self._publish()` for a Planned item (`:493`) and the recorded pull request for a Staged item. `_pull_request` is called nowhere else.
- The labels of the two titles differ. A probe with the real `.github/labels.yml` printed `docs(openspec): plan #2777 Label the stage and implement pull requests -> ('type/docs', 'scope/openspec')` and `feat(roadmap): the stage and implement jobs label their pull request... -> ('type/feature', 'scope/roadmap')`. So a Staged item needs the removal of two labels. (The `...` in the second title is the cut that #3215 removes.)
- The in-memory removal is the act of a person, not a job write. A probe on the unchanged tree: `store.label_issue(pr, "type/docs")` gave `job_writes: ['label_issue']`; `store.remove_label(pr, "type/docs")` on that pull request raised `#1 is not an issue of example/repo.`; `remove_label` on an issue added no job write. The code agrees: `add_label`/`remove_label` sit under "What a person does on GitHub" (`memory_store.py:257-268`), beside the job write `label_issue` (`:373`). `git grep -n "remove_label" -- tests` finds 9 lines, all in `tests/roadmap/`, that call it as the act of a person. So the job write needs its own name, `unlabel_issue`, as `label_issue` has next to `add_label`.
- GitHub allows the call with the token of the App. In `server-to-server-permissions.json` of `github/docs` (raw.githubusercontent.com, main), the keys `issues` and `pull_requests` each list `post /repos/{owner}/{repo}/issues/{issue_number}/labels` and `delete /repos/{owner}/{repo}/issues/{issue_number}/labels/{name}` with access `write`. ADR 0015 gives the App Issues write and Pull requests write. A read-only check of the path form: `gh api 'repos/dan-petty/devops-cli/labels/type%2Fdocs' --jq .name` printed `type/docs`, so a slash in a label name is sent as `%2F`. I did not send a `DELETE`: it would change a real pull request. The code reads `_segment` (`github_store.py:407`) for that encoding.
- A `GET` of a pull request returns its labels, so one request gives the old title and the held labels. `get_pull` (`client.py:282`) reads a `PullRequest` of title, head and base (`:58-63`) and ignores the rest. The test `test_a_pull_request_is_read_with_its_title_and_both_commits` (`tests/github/test_github_client.py:104`) uses a recorded pull request with `"labels": []`, so a new field with an empty default keeps it green.
- Rejected credentials are a subclass of the error that `add_pull_labels` catches. `GitHubUnauthenticatedError(GitHubOperationError)` is at `exceptions/git.py:177`. `add_pull_labels` (`pull_labels.py:53-70`) catches `GitHubOperationError` for each label and joins the reasons. So it would hide a 401. The stage job stops the run on that error (`_STOP_THE_RUN`, `stage.py:1329`; #2753) and the implement job re-raises it (`implement_run.py:523`).
- The jobs need the store they hold. `tests/support/roadmap.py:27-38` makes `get_roadmap_store` raise in any test that did not ask for the `roadmap_store` fixture, and `test_roadmap_stage_apply.py` passes its own `InMemoryRoadmapStore` to `apply_stage`. `tests/roadmap_faults.py:20-28` wraps a store passed in, and `tests/roadmap/test_roadmap_run.py:1544` already fails `label_issue` that way. A function that opens its own store by repository name can do none of this.
- The dry runs list the writes. `stage_requests` (`request_plan.py:459`) and `implement_requests` (`:571`) list the pull request writes; the spec says the dry run lists "the requests that a run makes". `tests/roadmap/test_roadmap_dry_runs.py` has 39 tests of the plans.
- The base is green. `uv run devops ci test tests/roadmap/test_roadmap_stage_apply.py tests/roadmap/test_roadmap_implement_job.py tests/roadmap/test_roadmap_dry_runs.py` printed `106 passed in 79.09s`.
- The change works, in a scratch clone (reverted, nothing of it is in this pull request). Stage: I changed `read_title_labels` and `add_pull_labels` to take the store, added `_label_pull` after `set_marks` in `_stage_one`, and ran `uv run devops ci test tests/roadmap/test_roadmap_stage_apply.py tests/roadmap/test_roadmap_stage_job.py tests/roadmap/test_roadmap_stage_reconcile.py tests/commands/test_pr_title_labels.py tests/commands/test_pr_form_check.py`: `80 passed`. Implement: I added `PullRequest.labels`, `remove_pull_labels`, `stale_labels`, `unlabel_issue` (in-memory only) and the new `_pull_request`. - The issue has no list of acceptance criteria that a person wrote. The block `Acceptance criteria` of the issue body is inside `devops-roadmap-refine`, which `acceptance_criteria` (`src/devops_cli/roadmap/stage_criteria.py`) cuts off. So the tasks carry no `## Criteria` section.

## Existing Tool Considered

No library covers this: PyGithub and gidgethub call the same endpoints with the same permissions, and the project already has the pieces. Reused as they are: `title_labels`, `declared_labels`, `RoadmapStore.label_issue`, `GitHubClient.get_pull` and `update_pull`. Not reused: `resolve_updated_labels` (`src/devops_cli/github/issues.py:575`). It runs `gh` without the store, ignores a failed read (`curr_labels` stays empty), and then `devops gh issues edit` writes the whole label list with one `PATCH`. A job that used it could erase every label of a pull request after one failed read, and it would write over a label that a person added between the read and the write. The change builds `unlabel_issue` (a single `DELETE` of one label), the `labels` field and three small functions. Cost to build and test: about 150,000 tokens and 3 hours of elapsed time (the stage job measured the inputs of four groups at 85,806 tokens, and this plan has seven). Cost to keep: about 6,000 tokens a year, one store write, one field and two call sites. Cost to fix: a wrong choice fails a named test. The change deletes no internal code.
