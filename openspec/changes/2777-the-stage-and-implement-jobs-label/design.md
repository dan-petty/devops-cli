# Design

## Decisions

- **The stage job labels after `set_marks` and before the comment, outside the `with _worktree(...)` block and outside `_open_pull`.**: `_open_pull` deletes the remote branch when GitHub refuses the pull request (`stage.py:1191-1192`). A label call inside it, or inside the worktree block, could reach that delete or skip `set_marks`. After the marks, an error in the label code cannot unset them. Before the comment, the failure note joins the one comment that the job already posts (`{notes}` of `stage_comment_staged`), so a person reads it where they look.
- **The stage job catches `GitHubOperationError` and re-raises `GitHubUnauthenticatedError`.**: The unauthenticated error is a subclass of the first (`exceptions/git.py:177`), and `write_each` stops the run on it (#2753). A plain `except GitHubOperationError` would turn a rejected token into a note in a comment.
- **`add_pull_labels` lets `GitHubUnauthenticatedError` pass, and it takes the store of the caller.**: Today it catches every `GitHubOperationError` for each label and joins the reasons (`pull_labels.py:60-62`). A 401 is not a fact about one label: every next label fails too. And a job holds a store already, which a test can double and which `StoppingStore` can fail; `get_roadmap_store(repo)` in a test raises (`tests/support/roadmap.py:27-38`). `read_title_labels` takes the store for the same reason. `devops pr create` passes the store it opens once, so its behavior stays.
- **The implement job reads the old title and the held labels with `get_pull` before `update_pull`, and removes only a label that the pull request holds and the old title gave.**: One `GET` gives both (the field `labels` is new in `PullRequest`). The old title alone is not enough: when the stage job could not add a label, a `DELETE` of that label returns 404. The held labels alone are not enough either: a `scope/*` label that a person added would go. The intersection removes what the stage title gave and nothing else. The issue says "that the old title gave", and this keeps it.
- **A job removes a label only after it added the new labels.**: If the add fails, the removal does not run, so a pull request never loses a label without its replacement. `add_pull_labels` tries every label and reports the refused ones, as it does for `devops pr create`.
- **A label failure in the implement job is a comment on the pull request, and the item goes on.**: `_pull_request` is followed by the watch of the checks and the ready mark (`execute`, `implement_run.py:381-383`). A label is a convenience, and a stop would leave a draft that no job watches. The comment is separate from the comment of the steps: that comment is the outcome of each step, and a label is no step.
- **One call in `_pull_request` labels the Planned and the Staged path.**: `_publish` opens the draft of a Planned item with the delivery title already (`implement_run.py:561-566`), and `execute` then calls `_pull_request` for both paths. For a Planned item the old title equals the new one, so only the add runs.
- **The removal is a new job write, `unlabel_issue`, a single `DELETE` of one label.**: A `PATCH` of the whole label list (the way of `resolve_updated_labels`) writes over a label that someone adds between the read and the write. `label_issue` is already a `POST` of one label. The `DELETE` has the same shape and the same permission (Issues write, or Pull requests write).
- **The in-memory store gets `unlabel_issue` next to `label_issue`, and `remove_label` stays.**: The pair `add_label` and `label_issue` exists already: the first is the act of a person (no job write, issues only), the second the job write (`pull_request=True`, logged in `job_writes`). `unlabel_issue` is the second half of that pair. Renaming `remove_label` would change 9 lines of tests that act as a person, and the job write would still be missing, because `remove_label` logs nothing and refuses a pull request (probe in Feasibility). A label that the pull request does not hold raises in both stores, as GitHub answers 404.
- **The dry run lists the new requests.**: The spec says the dry run lists the requests of a run, and `request_plan` builds them with the argument builders of the store so that the plan cannot drift from the run. The stage plan gets the read of `.github/labels.yml` and the label request. The implement plan gets the read of the pull request, the read of the labels file, the label request and the removal request.

## Rejected alternatives

- **Delete the remote branch when the label call fails in the stage job.**: `_open_pull` deletes the branch only when GitHub refuses the pull request. After the pull request is open, the delete would leave an open pull request with no branch.
- **Rename `remove_label` to `unlabel_issue` in the in-memory store, as the review of this plan asked.**: `git grep -n "remove_label" -- tests` finds 9 lines, and they act as a person through `as_actor`. A person's write must not reach `job_writes` (`memory_store.py:6-8`), and a job write needs the pull request (`pull_request=True`).
- **Use `resolve_updated_labels` and a `PATCH` of the whole list.**: It runs `gh` outside the store, and on a failed read it computes the new list from an empty set (`issues.py:584-591`), which would erase the labels of the pull request.
- **Remove every `type/*` and `scope/*` label that the new title does not give.**: A `scope/*` label that a person added is not a label of the old title. The issue limits the removal to the labels that the old title gave.
- **Read the labels with a new store method for a pull request.**: `get_pull` is read already in the same step for the old title. A store method would add a protocol member, an in-memory member and a request builder for a value that the `GET` of the pull request holds.
- **Stop the implement item when a label fails.**: The item would stop after the title and the body are set and before the checks are watched. The labels do not decide whether the code is right.
- **Add the label step to `_publish` and to `_pull_request` both.**: `_pull_request` runs after `_publish` in every path, so the second call would repeat the first.
- **Call `devops pr create` from the jobs.**: `openspec/changes/archive/2026-10-29-2654-roadmap-stage/design.md` records that the command works on the checked-out branch and runs `gh` in a child process, which the jobs cannot use.

## Relation to the existing requirements

The new stage requirement adds to "A failed write stops one item": a failed label write is the one write that does not stop its item, so that requirement gets a MODIFIED entry. The new implement requirement adds to "The pull request that delivers the code has the type of the issue" (`openspec/specs/roadmap-implement-job/spec.md:333`) and to "The job rewrites the pull request after the push". It changes neither: the title, the body and the one comment of the steps stay as they are, and the label failure comment is a separate comment.
