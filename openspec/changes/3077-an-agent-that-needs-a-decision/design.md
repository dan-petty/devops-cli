# Design

## Decisions

- **One module, `src/devops_cli/roadmap/owner_question.py`, renders and reads the owner-question frame, and refine, stage and implement call it.**: Three copies of the hidden block and the hash rule would drift, and `src/devops_cli/roadmap/trust.py:def is_person_comment` is the model for one module that every reader of one rule uses.
- **The hidden block of the frame holds the question hash and lives in the new module, and no new job marker joins `CONST_ROADMAP_JOB_COMMENT_MARKERS`.**: Each frame starts with the marker of the job that posts it, so the reply readers and the comment cap already treat it as a job comment, and `tests/roadmap/stores/test_comment_repeat.py` holds `COMMENT_JOBS` and that tuple equal.
- **The three record keys are one family, `OwnerQuestionRecordKey`, in `src/devops_cli/roadmap/stores/store.py`, joined to `JobRecord`, `_JOB_RECORD_KEYS` and `__all__`.**: The job record is one hidden block of the issue body and every job writes into it, so one family lets refine, stage, implement and the inbox read the same three keys; a key outside `_JOB_RECORD_KEYS` is dropped by the next write.
- **The open frame is the marker of a question that waits, and no status label is added.**: ADR 0016 fixes the status family at six values (`src/devops_cli/config/constants.py:3754:CONST_ROADMAP_STATUS_VALUES: Final[tuple[str, ...]] = (`), and a seventh label would change the workflow-document invariant for a marker that the open frame already gives.
- **The plan adds no limit constant and no entry to the registry of `tests/roadmap/test_roadmap_limit_classes.py`, and group 1 reads that test and names it in a task.**: That registry collects the `CONST_ROADMAP_` prefix and refuses a limit that no constant holds, and the hidden-block prefix is a text of the new module, not a limit, so the registry stays as it is and the group that touches the store shows it.
- **A round asks one question and ends; refine's comment cap bounds the comments on one item.**: `CONST_ROADMAP_REFINE_MAX_COMMENTS_PER_ITEM` is 2 in 24 hours (`src/devops_cli/config/constants.py:3305:CONST_ROADMAP_REFINE_MAX_COMMENTS_PER_ITEM: Final[int] = 2`), and the frame starts with refine's marker, so the cap counts each frame and each link.
- **Refine reads the reply once and writes the answer into the record of each covered item.**: The record carries the answer to an item that holds only a link comment, so no job needs a second reader of the thread, and the inbox reads the same record with no comment read.
- **The stage step asks at the over-budget stop and the implement step asks at a stop of class `plan_defect`.**: Those are the two places where the job already tells a person that it needs a decision, so the form replaces a guess with one question and one frame.
- **The `owner` kind of `InboxKind` is the 14th member, and the split of `read_inbox` puts its line in the people's list beside `InboxKind.PERSON`.**: An owner question waits for a person, and `read_inbox` splits the people's waits from the jobs' waits on `InboxKind.PERSON` alone (`src/devops_cli/roadmap/inbox.py:414:jobs=tuple(line for line in ordered if line.kind is not InboxKind.PERSON),`).
- **The generated page `docs/commands/roadmap.md` is regenerated in its own group with `uv run devops docs generate`, and the plan edits no generated page by hand.**: The `--kind` help and the `InboxKind` member change that page, and the `docs` row of the gate runs `devops docs check`, so a stale page fails `uv run devops ci docs`.
- **No per-item setting limits the questions.**: The accepted scope of #4780 child 10 holds none, and the one-question rule with the comment cap bounds the questions on an item.

## Rejected alternatives

- **Adopt LangGraph as a dependency for the pause and the resume.**: The alternatives check gives `partly`: LangGraph pauses a run and resumes it with a value, and it has no GitHub transport, no inbox line, no trust check and no hash rule. The job record and the Service already hold the state.
- **Add a `status/needs-input` label for an item that waits on an owner answer.**: The accepted scope says the open frame is the marker and no status label is added, and `src/devops_cli/config/constants.py:3754:CONST_ROADMAP_STATUS_VALUES: Final[tuple[str, ...]] = (` holds six values, so a seventh label would change the workflow-document invariant for no gain.
- **Post a question frame on every item that asks the same question.**: The owner would answer one question many times, and `devops roadmap inbox` would show many rows for one decision; the record holds the hash, so one frame and a link per other item is enough.
- **Let refine, stage and implement each read the replies of their own questions.**: Three readers of one thread give three places to get `trust.is_person_comment` wrong, and the accepted scope says a reply resumes the item through refine.
- **Add the two marker strings as limit constants and give each an entry in the registry of `tests/roadmap/test_roadmap_limit_classes.py`.**: `tests/roadmap/test_roadmap_limit_classes.py:47:("prefix", "CONST_ROADMAP_", "tests/roadmap/test_roadmap_limit_classes.py"),` registers a prefix of numeric limits, and a text marker is no limit, so a string entry makes that test red.
- **Add a new job comment marker for the frame to `CONST_ROADMAP_JOB_COMMENT_MARKERS`.**: `tests/roadmap/stores/test_comment_repeat.py:190:[marker for marker, _ in COMMENT_JOBS] == list(CONST_ROADMAP_JOB_COMMENT_MARKERS),` holds the two lists equal in order, and the frame already starts with the marker of the job that posts it.
- **Give `read_inbox` a new argument for the owner line and change the caller with it.**: The open question is the job record of the item, and `read_inbox` already reads every open item with its record (`src/devops_cli/roadmap/inbox.py:384:def read_inbox(`), so the line needs no new read and no new argument.
- **Edit `docs/commands/roadmap.md` by hand after the help text changes.**: It is a generated page that `uv run devops docs generate` writes, and the `docs` row of the gate runs `devops docs check`, which refuses a page that is not the output of its generator.
