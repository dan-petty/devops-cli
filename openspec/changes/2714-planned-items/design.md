# Design

## Decisions

- **One read of the plans, one module.** `roadmap/planned.py` fetches the default branch, reads `openspec/changes/` and `openspec/changes/archive/` of `origin/<default>` with one `git ls-tree --name-only`, and keeps the issue number of each folder in two maps. Both jobs call it once for each round. A folder matches by its issue number, so a slug that differs from the title of the issue does not matter. The grammar comes from the constants of `config/constants.py`, which `grounding.py` already uses.
- **Planned and archived are two reasons.** An active folder means the plan is on the default branch: stage leaves the item out, and implement can take it. An archived folder means the work is done: both jobs leave the item out. The reasons name the folder.
- **The plan decides the route of an implement item.** An item with a recorded branch that is on `origin` is Staged, whatever the default branch holds. Else an item with a plan on the default branch is Planned. Else an item with a recorded branch that is gone keeps the old reason, and an item with no record is "not Staged". So a branch that is still on `origin` keeps its draft pull request and its commits, and a merged plan with no branch starts a new branch.
- **The recorded pair.** The branch and the pull request come as a pair: `implement.branch` and `implement.pr` when both are set, else `stage.branch` and `stage.pr`. After a Planned run opens its pull request, a retry finds the new pair and takes the branch over like a Staged item. The old stage pair, whose pull request is merged, is not used again.
- **The Planned branch.** The type comes from the title of the item, with `_commit_type` made public as `commit_type`, and the slug from the change folder. The folder `<issue>-<slug>` gives the branch `<type>/<issue>-<slug>`. `add_worktree` makes it at `origin/<default>` because `origin` holds no branch for the issue. A folder name or a title that gives no valid branch leaves the item out with a reason.
- **Publish at the first push.** A pull request needs a commit past its base, so the job pushes a Planned branch with `-u` and opens the draft in one method, `_publish`, when it first has a commit past the default branch. A stop before any commit pushes nothing, so no branch without a pull request stays on `origin`. A draft that fails to open takes the branch off `origin`, as the stage job does. Every later push is the push with a lease.
- **The first draft body holds no closing keyword.** It says that the job works on the issue. The body `Closes #<issue>` comes after the archive, as for a Staged item, so a person who merges early closes nothing.
- **One title for the delivery.** `delivery_title` turns the title of the issue into the title of the pull request: the type and the scope of the issue and its summary shortened to 60 characters. The implement job sets it for both paths with one `update_pull` call that also sets the body. The staging pull request had the type `docs(openspec)`, and the delivery must not keep it.
- **The staging title is shortened, not refused.** `staging_title` is `docs(openspec): plan #<issue> <summary>`, and `textwrap.shorten` cuts the summary at a word so that the whole part after the colon has at most 60 characters. A reply is not sent back to the model for a long summary: the cut is deterministic, and it costs no model call. The prompt asks for at most 40 characters.
- **A failed read stops the stage round.** If `git fetch` or `git ls-tree` fails, the round raises `GitOperationError` with the reason of git, before it selects an item. It is better to stage nothing than to stage an item that may already be planned.
- **All ticked means nothing to run.** A Planned item whose `tasks.md` on the default branch has no unticked task is left out. The job reads the file with `git show` and `parse_task_groups`, and reads it only for an item that it would take.

## Rejected alternatives

- **A GitHub search for merged plan pull requests.** The tree of the default branch is the fact that matters: a plan can arrive by any pull request or commit. The search needs the GraphQL quota, which memory notes as scarce, and a title match. `git ls-tree` makes no request and needs no match of text.
- **The `stage.pr` state in the record.** The record would say "merged", and a person who edits the issue or clears the record would break it. The folder on the default branch cannot go out of date.
- **Reuse the stage branch name from the record.** The branch is deleted after a merge, and the record holds no slug of the folder. The folder name is the source of the slug.
- **A recursive `git ls-tree -r`.** It lists every file of every archived change, which is thousands of lines. The two-directory listing has one line for each folder.
- **Refuse a long summary and ask the model again.** It adds a model call to fix a cosmetic fault, and a second refusal fails the item. `textwrap.shorten` is in the standard library and never fails.
- **Keep the type of the issue on the staging pull request and add `Plans #N`.** CONTRIBUTING.md and the changelog rule say a plan-only commit has no changelog line. Only the type decides that, so the type must be `docs`.
- **A shim that reads old staging pull requests.** The project is alpha and keeps no old path.
