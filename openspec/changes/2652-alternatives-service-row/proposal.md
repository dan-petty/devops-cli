# Proposal

## Why

Issue #2652, sub-issue 2 of #2648. `devops roadmap alternatives` (#2650) checks open items for an open, maintained tool. The Service does not run it, and refine does not read what it records. So the check runs only when a person starts it, and a covering tool never reaches the plan of the item.

## What Changes

- A row `alternatives` in `MODEL_LANE_ROWS` of `src/devops_cli/roadmap/run.py`, after `refine`. It is due every `DEFAULT_ROADMAP_ALTERNATIVES_INTERVAL_MINUTES` (1440) and on a first run. It runs `plan_alternatives` and `apply_alternatives` with `--limit` from the new setting `roadmap.alternatives.limit` (default 5). `devops roadmap run` runs the row in its round, and `devops roadmap run --dry-run` lists it. The row calls the model, so it is on the model lane, which runs one row at a time.
- `devops roadmap alternatives` reads the same setting when `--limit` is not given.
- Refine reads the recorded check of the item: the block of the item's body, the verdict and tool of its job record, and the job's latest comment. They are the `alternatives` key of the proposal request and of the investigation request. The prompts say that "Existing Tool Considered" names the recorded tool and what it lacks, or says that no check has run.
- A `covers` verdict is a key question that only a person answers: adopt the tool, or keep the item with a reason. The question is open, and so the next step of the item is `PERSON` and the Ready check does not set Ready, until a person replies after the job's comment and the proposal answers the question. A `partly` or `none` check reaches the proposal and changes no rule of the Ready check.
- Refine records the covering tool it asked about (`refine.alternatives_asked`). A Ready or waiting item whose record holds a covering tool that refine has not asked about is refined again in the next round, as a reply makes a waiting item refined again. A re-check that finds the same tool does not ask again.
- Refine records the hash of the body outside the job's block and its own section, as `_is_unchanged` compares it. Before this change it hashed the body with the block, so an item with a block never read as unchanged.
- The metric `devops_cli_roadmap_alternatives_total{verdict}` in `INSTRUMENTS`: one count for each check the job writes.
- New setting `roadmap.alternatives.limit`. `Verdict` moves to `src/devops_cli/roadmap/store.py`, next to the record keys that hold its values, so refine reads a verdict without importing the job.
- `CONTEXT.md` ("Lane"), `k8s/README.md` ("Roadmap service") and the generated documents name the row and the metric.
- The change fits one pull request. It is a behavior a consumer observes (a Service row, a refine rule, a metric and a setting), so it carries spec deltas.

## Feasibility

Each part of the premise was checked against the merged code on 2026-10-29.

- The due table: `JobRow` in `src/devops_cli/roadmap/run.py` has `interval`, `first_run_due` and a `runner` that gets `store`, `repo`, `clone_path`, `repo_dir`, `changes`, `batch` and `now`. `_Poll.is_due` makes a row with an interval due on a first run and after the interval. `_simulate_dry_run` lists every due row of the table, so a row in `MODEL_LANE_ROWS` appears in `devops roadmap run --dry-run` with no other change. `service_jobs` hands `MODEL_LANE_ROWS` to the model lane, whose rows run one after the other, so the new row adds no second model call in a lane.
- The job: `plan_alternatives`, `apply_alternatives` and `raise_for_failed_checks` of `src/devops_cli/roadmap/alternatives.py` take a store and a repository, and return the plan that the row needs. `plan_alternatives` returns a plan with `off_reason` and no check when the repository is private or no Firecrawl key is set, so the row is a no-op there.
- Refine reads the body and the job record of each item (`Item.body`, `Item.job_record`), and the comments of an item it refines (`store.comments_on`). The check of the job is in all three: the block in the body, `alternatives.verdict` and `alternatives.tool` in the record, and a comment with `CONST_ROADMAP_ALTERNATIVES_COMMENT_MARKER`. Refine needs no new read.
- One fault of the merged code was found by reading it: `refine_one_item` records `hash_text(outside)` where `outside` still holds the job's block, and `_is_unchanged` compares that record with `_body_hashes`, which removes the block. An item with a block therefore never reads as unchanged, and refine would refine it, and comment on it, in every round. Task group 3 writes the failing test for it and fixes it at the source.
- Selection of a Ready item: `_refinable` takes a Ready item only when its record holds no refine section. A Ready item that gets a `covers` check needs a second look, so the selection needs a signal that costs no comment read. The job record gives it (`alternatives.verdict`, `alternatives.tool`, and the new `refine.alternatives_asked`).

The premise holds. No part needs code that compensates for a missing feature.

## Existing Tool Considered

The due table and the lanes of `roadmap/run.py`, and refine's `replies` and `body_questions` paths. The row is one `JobRow`, and the `covers` question is one more entry of the numbered key questions that refine already validates (`validate_proposal`). No new library is needed: the metric uses `Instrument` and `emit`, and the setting uses `pydantic` as every setting does. Nothing new is built beyond the glue, about 300 lines of code and tests.
