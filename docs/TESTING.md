# Testing

The vocabulary devops-cli's tests are designed and organised in, and the conventions every test follows. [ADR 0007](adr/0007-tests-double-only-process-edges.md) records why tests double only edges.

## Vocabulary

### Test doubles

**Edge**:
A point where devops-cli reaches beyond its own process to something a test must not touch for real: another machine, a long-lived daemon, any program, the keyring, or the wall clock.
_Avoid_: boundary, external dependency, integration point

**Seam**:
The one place in devops-cli that supplies an edge's real implementation, and where a test installs a fake instead.
_Avoid_: hook, injection point, patch target

**Fake**:
A working in-memory stand-in for one edge that answers like the real thing and records what it was asked.
_Avoid_: mock, stub, dummy, test double

**Contract suite**:
One set of tests run against both a fake and the real implementation of its edge, the real side against recorded responses or a local tool, never a live service.
_Avoid_: parity tests, conformance tests

### Isolation

**Hermetic floor**:
The isolation every test runs inside, whatever its package: no edge reached without a fake, process-wide state reset after it, its own data directory, config and gh config, a throwaway kubeconfig for the run, and no way onto the session bus.
_Avoid_: global fixtures, autouse setup

### Kinds of test

**CLI test**:
A test that drives a `devops` command and checks only what the command layer owns: argument parsing, wiring, output and exit code.
_Avoid_: command test, end-to-end test

**Invariant test**:
A test whose subject is a committed file of this repository (the source tree, docs, change folders, workflows, manifests or dashboards) rather than the behaviour of devops-cli.
_Avoid_: architecture test, hygiene test, consistency test

**Ratchet**:
An invariant test that holds a count of something being retired to a ceiling that may only go down.
_Avoid_: ceiling test, baseline, allowlist

### Test data

**Builder**:
A function that makes one valid domain object from defaults, named after its [CONTEXT.md](../CONTEXT.md) term.
_Avoid_: factory, fixture, helper

**Snapshot**:
The stored expected text of an output whose whole text is the contract, such as a command's output, a rendered manifest or a prompt. It is regenerated, never edited by hand.
_Avoid_: golden file, golden

## Conventions

Every new test follows these rules. Some of them name a path, fixture or check that does not exist yet; each such name is marked *(target)*, and [Until the migration ends](#until-the-migration-ends) says what exists today and what a new test does meanwhile.

### Which change gets a test

- A change that adds or changes what the code does gets a test. Write it first, and see it fail on the base. A fix pull request cites its `devops ci fail-to-pass --base <ref>` run.
- Every other change gets no test: a document, a manifest, a workflow, a deletion or a refactor that keeps behavior, an edit of tests only, or data. It names one command that can run again and gives the same answer, such as `uv run devops ci docs`, `uv run devops openspec check`, `! git grep -n <name> src/ tests/` (a command that exits 0 when it finds nothing), or `uv run devops k8s image-pins`. When no command exists, it gives the steps of a repeatable manual check. The `! git grep` form has a fixed shape. The step runs it as a list of words, never as a shell. It takes the options `-n -I -F -i -w -l -c -q`, then one plain literal and relative paths. Or it takes one or more `-e` options, each with a plain literal, then `--` before the relative paths. A literal after `-e` must not start with `-`. A pipe, `;`, `&&`, a redirect, `-E`, `-P` and any other option are refused.
- A task group of a plan has the same two kinds, `behavior` and `other`, and a third, `manifest`, for a rule, a dashboard or a case file whose failing case a command runs (`GroupKind`). The stage job refuses a `test` on an `other` group, and refuses a `behavior` group that changes no path under `src/`. The line under the heading of each group in `tasks.md` starts with `Kind: <kind>.`, and the plan reader reads the kind from it. A test compares the prompts of the job with these kinds.
- A plan that adds a field to `StageProposal` changes the reply-key bullets and the rule in `src/devops_cli/ai/tasks/roadmap_stage_change.md`, and the `prompt_keys` gate refuses a plan that leaves the update out.

### Doubles

- A test doubles only edges. Everything inside the process runs for real.
- **Faked edges**: every program (git, kubectl, helm, minikube, the docker and podman CLIs, the scanners), with the lookup of the program on PATH part of its fake; all network, meaning HTTP on any client stack, raw sockets and DNS; GitHub's API, through the GitHub session; model and embedding providers; the Kubernetes API; the Docker engine; Valkey; Qdrant; OTLP export; the keyring and D-Bus.
- **Real**: the filesystem under `tmp_path`; environment and config, through the hermetic floor and the `config` fixture; in-process servers, such as FastAPI's `TestClient` and loopback servers; randomness; host identity; and stdin, through `CliRunner(input=...)`.
- A test of `src/` starts no system program. Real child processes stay only in the contract suite of the process runner (`tests/core/test_process_contract.py` and the process-group tests of `core/process.py`).
- Every other real tool goes to one of two places: a contract suite that replays recorded transcripts of the tool, or a row of `devops ci`. A check of committed files or of tool configuration is a row of `devops ci`, not a pytest test. The code of these rows is in `tests/gate/`, one module for each row, outside `tests/support/` because a pytest process imports a support module that imports pytest or another support module, and it runs none of these checks. The rows are `lint` (the settings of Ruff), `constructs` (`ast-grep test` and the construct gate), `k8s` (the `kubectl kustomize` renders of the committed manifests, each rendered once), `test-tree` (the invariants that read every Python file of `src/` and `tests/`), `startup-imports`, `swallowed-failures`, `domain` (no commit of the branch names a configured domain) and `roadmap-stage-eval-commits` (the base commit of each golden stage eval case is a commit of the repository). A check is a function named `check_*` that asserts, and the runner `tests/gate/runner.py` runs it as pytest would, with `parametrize` marks and `tmp_path`. A test of the logic of a check gives it a small tree or canned output and starts no program.
- The bwrap cases are an opt-in contract suite: a default test run deselects them, and `-m bwrap` selects them. The `bwrap` row of `devops ci` runs them where the host can make the sandbox of a review: in the devcontainer, and in `Static Analysis` on its GitHub-hosted runner, with no install. On a host that cannot, the row starts no test and shows as skipped with the cause. The row gives each test a bound of 60 s, shorter than the limit of the gate step of `Static Analysis`. A bwrap case that reads the process table of the host starts `ps` under `@pytest.mark.live("ps")`, because the floor keeps the test process out of `/proc`.
- A test must not skip based on host state. A test that cannot run the same on every host is a contract case or a `devops ci` row.
- No test starts a real gh, which would act as the developer's own login: a gh command a test reaches goes to a fake, and the floor fails a test that starts gh.
- No test starts a real security scanner either: a scanner fetches rule packs and advisories from a child process the network block does not see. The floor refuses gh and the binary of every scanner the security scanner registry holds, names `tests/support/refused_programs.py` reads from the registry when the run starts, so a scanner added there is refused with no list to edit. The refusal sits at `subprocess.Popen`, beneath every seam, and fails the test with `pytest.fail`, which no `except Exception` in the code under test hides. A test whose code starts a scanner asks for `scanner_fake`, which answers the scanner's request to the tool executor with the scanner's run recorded from the real tool.
- No test of `src/` starts a real sandbox. A review runs its tools in the bubblewrap sandbox by default, so a real scanner would start as the program that bubblewrap confines, where the refusal by name does not see it. The floor refuses bwrap in tests. The bwrap cases are an opt-in contract suite that the `bwrap` row of `devops ci` runs. A test of the sandbox executor fakes the process edge with `process_fake`.
- No test starts sudo, which changes the host, or uv installing or syncing from PyPI, and the floor refuses both. The gate's own `uv audit`, `npm audit`, `uv tree --outdated` and `uv check` are its intended network checks, run by `devops ci`, never by a test.
- A detached child, which runs on after the command that started it, such as the forward of `devops k8s tunnel start` or of `devops k8s port-forward`, starts through the process runner's `spawn_detached`. `process_fake` records it as a call with `detached` set, and answers with the `process` of its `ProcessAnswer`: a process that the test started itself, such as `git hash-object --stdin` in a session of its own, or a callable that takes the call and returns one. With no `process`, the child has ended at once. A call also records `extra_allowed_env`, the names of ambient variables that the caller lets the child inherit besides the base set, so a test can assert that a program gets only the variables it needs.
- git has one seam, the process runner: every start of git in `src/devops_cli` goes through `run_subprocess`, and no module imports GitPython or starts git with `subprocess`, which an invariant test enforces. The `git_fake` fixture installs `GitFake` (`tests/support/fakes/git.py`) through that seam. `GitFake` is a `ProcessFake` that answers a git command from a transcript, a file of `tests/fixtures/git/` that records one scenario of `tests/support/git_scenarios.py` with the real git: the arguments, the directory, the standard input, the environment that the caller sets, the exit code, the standard output and the standard error of each command, and the result the scenario gave. The fake finds a record by the first four, so a commit with another message, author or date has no record. It does not see the files of a directory: a test that checks what a file holds reads the file under `tmp_path`, and tests start no real git. A test names the scenarios it needs with `git_fake.replay(...)`, and puts the repositories of a scenario at the same names under `tmp_path`, which stands in for `{root}`. A git command with no record fails the test and names the command. A test with the fixture cannot start a real git. A transcript holds no host path, user name, host name or e-mail address except `example.com`, and the recorder runs git with no user or system configuration file. A test that needs a command with no record adds a scenario and records it again with `uv run python -c "import sys; from tests.support.git_recording import main; sys.exit(main([]))"`; the `git` row of `devops ci` records every scenario again on the stock runner and fails when a transcript differs.
- Each edge has one seam in `src/devops_cli`: a Protocol, plus the one place that supplies the real implementation *(target for most edges)*. The clock's seam is the sleep and clock parameters the libraries take, with no Protocol, as [Clock](#clock) describes. A test installs the edge's fake through the seam's fixture, or through a constructor or parameter the domain code already takes.
- Each edge has one fake, in `tests/support/fakes/<edge>.py`, shared by every test that reaches the edge. A test does not build its own double of an edge.
- Every fake has a contract suite, run against the fake and against the real implementation over recorded responses or a real local tool, never a live service. A fake without a contract suite does not merge.
- Patching a stdlib or SDK object itself, such as `subprocess.run` or `time.sleep`, is a fallback for stdlib edges only.
- No test patches a devops-cli module, class, function or attribute, and no test imports a private name (one that starts with `_`) from `devops_cli`. A test reaches private code through the public interface that uses it.
- An invariant test (`tests/invariants/test_source_tree.py`) holds `tests/commands/` and `tests/invariants/` to no string patch of a `devops_cli` name.
- Product code holds nothing for tests: no `unittest.mock`, no `PYTEST_CURRENT_TEST` check, no check for a mock's attributes, and no module shaped so that a test can patch it. Fakes, and in-memory implementations that production does not use, live in `tests/support/` and never ship in the wheel.

### Layout

- `tests/` mirrors the package tree of `src/devops_cli` at full depth *(target)*: the tests of `src/devops_cli/ai/review/` sit in `tests/ai/review/`. No test file sits at the top of `tests/`. Each package directory has its own `conftest.py` for that package's fixtures.
- A new test file sits in the mirror directory of the source module it tests, as `tests/<package path>/test_<module>.py` for `src/devops_cli/<package path>/<module>.py`. This is the one rule for a new test file: it never goes to the top of `tests/`, and no flat file is added. `devops new test <module>` writes the file at that path, and `devops new command <group> <command>` writes the test of a command in `tests/commands/`.
- A package is tested through its public interface, in one file per behaviour, named after the behaviour, such as `tests/roadmap/test_duplicate_candidates.py` *(target)*; not in one file per source module. A test of behaviour that crosses packages goes to the package that owns the behaviour.
- A file is never named after the work that produced it: a review session, an issue, a pull request, a batch or a hardening pass. A regression test joins the file of the behaviour it pins.
- `tests/invariants/` is the only place for test files outside the mirror. It holds the invariant tests, one file per subject: `test_adr_records.py`, `test_agents_md.py`, `test_architectural_invariants.py`, `test_change_folders.py`, `test_cli_elapsed_line.py`, `test_committed_addresses.py`, `test_configmap_rollout_rule.py`, `test_configured_domain_check.py`, `test_construct_gate_check.py`, `test_devcontainer_config.py`, `test_dry_run_class_ratchet.py`, `test_guidelines.py`, `test_hermetic_floor.py`, `test_host_path_roots.py`, `test_image_layers.py`, `test_k8s_argocd_apps.py`, `test_k8s_crawl4ai.py`, `test_k8s_manifests.py`, `test_k8s_mcp_server_policies.py`, `test_k8s_searxng.py`, `test_living_specs.py`, `test_mcp_server_image.py`, `test_pull_request_template.py`, `test_roadmap_eval_fixtures.py`, `test_roadmap_stage_eval_commits_check.py`, `test_roadmap_stage_measure_doc.py`, `test_roadmap_workflow_doc.py`, `test_runner_hooks.py`, `test_runner_image.py`, `test_service_image.py`, `test_skills.py`, `test_source_tree.py`, `test_suite_refuses_real_programs.py`, `test_swallowed_failures_check.py`, `test_task_prompts_check.py` and `test_workflow_contracts.py`. A new invariant test goes into its subject's file, created if absent, never into a parallel file.
- `tests/support/` holds what tests share, and no test module or conftest lives in it, which the registration enforces: the fakes in `fakes/<edge>.py`, the builders in `builders.py`, and shared fixtures. Every submodule and subpackage under it is registered as a plugin, so a fixture added there needs no conftest edit: the root conftest's one `pytest_plugins` entry names `tests.support.bootstrap`, which isolates HOME and then registers the rest, so a support module that imports devops-cli binds its paths under the isolated HOME. The root conftest marks `tests.support` for assertion rewriting first and imports it only inside functions, and `PytestAssertRewriteWarning` is an error, so a support module imported too early fails the run. A support module defines no `pytest_*` name that is not a hook, and defines each fixture it registers with `pytest.fixture` rather than importing another module's or handing one out by a module-level `__getattr__`: the registration fails a run whose support module holds a fixture or hook its source does not show. An invariant holds the top level and the class bodies of every helper module under `tests/` to docstrings, imports at the top level, defs, classes, assignments to names alone and `if TYPE_CHECKING:` blocks with no `else`; the values bound to names, decorators, default arguments, base classes and metaclasses still run on import unchecked. A module imports from a support module with `from tests.support[.x] import ...`, and no module but `bootstrap` holds `tests.support` or a package under it, which another invariant enforces, so none reads a support module it does not import.
- A test finds the repository root and its test data through `tests.support.paths`: `REPO_ROOT`, `TESTS_ROOT`, `FIXTURES` (`tests/fixtures/`) and `GOLDEN` (`tests/golden/`). It never builds a path from its own `__file__`, so it reads the same paths at any depth.
- A test file imports what it shares from `tests/support/`, never from another test file or from a conftest. One check over every Python file under `tests/` but `tests/fixtures/` fails the full gate on a module that reads `__file__` outside `tests/support/` or imports a test module or a conftest, naming each as `path:line`: an imported module under `tests`, or a top-level one, is a test module when pytest collects its file by the `python_files` patterns; `from X import n` imports the module `X.n` when `X` is a package or `X/n.py` exists; and a relative import is resolved against the importing module's package, one past the top-level package being reported too. It runs as part of the `test-tree` row of `devops ci` (`tests/gate/tree_checks/module_independence.py`), which parses each file once.
- The root `tests/conftest.py` holds only the hermetic floor *(target)*. Domain fixtures live in their package's conftest or beside their fake.

### Names and assertions

- A test is named after the behaviour it checks, in [CONTEXT.md](../CONTEXT.md) glossary terms: `test_blocked_item_is_not_started`. The name never names a helper, a private function or a double, and it uses the glossary term, never a word the glossary lists under _Avoid_.
- An assertion compares whole values: `assert result == expected` against a complete expected model, or `assert fake.requests == [...]` for what an edge was asked.
- A test of an error path checks the `DevOpsCLIError` subclass raised, with its exit code and machine-readable error code.
- Tuple equality is only for picking fields out of an object whose other fields are noise, such as generated ids or timestamps.
- Consecutive asserts are fine. Ruff's C901 does not count them, so they do not raise a test's complexity.

### CLI tests

- A CLI test invokes a command through the shared `cli` fixture, not through a `CliRunner` it builds itself.
- It checks only what the command layer owns: argument parsing, wiring, output and exit code. Every CLI test sits in `tests/commands/` *(target: a few do today)* and reaches edges only through its fakes.
- A domain rule is tested once, through its domain package. Logic behind a private helper in `commands/` moves into its domain package behind a public function and is tested there, and the command becomes a thin adapter. Until it moves, it is tested through the CLI with edge fakes.

### Config

- A test sets configuration through the `config` fixture. The fixture writes the overrides into the test's own `config.yaml`, the file `DEVOPS_CLI_CONFIG` names, and resets the settings cache.
- A test of the global config file writes it through the `global_config` fixture, which keeps the file under the run's own HOME and removes it after the test.
- No test patches `load_settings` or `CONFIG_PATH`.

### Test data

- A test builds a domain object with a builder: one per glossary term, named after it (`make_finding`, `make_verdict`, `make_item`, `make_candidate`), in `tests/support/builders.py`. A builder is a plain function that builds a valid object through the real constructor or parser, with its validation, from valid defaults, and takes keyword-only overrides; a model's builder refuses a key that is no field of the model with `TypeError` naming it, so a typo or an alias fails rather than being dropped.
- An output whose whole text is the contract, such as a command's output, a rendered manifest or a prompt, is checked against a snapshot that syrupy stores. Any other expected value is a literal written in the test. A Pydantic model is snapshotted through `model_dump()` or syrupy's Amber Pydantic plugin.
- A snapshot is regenerated, never edited by hand, with `uv run pytest <test-file> --snapshot-update --snapshot-file-lock`, and the commit says why it changed. The file lock is required: without it, an update under xdist can lose entries from a shared `.ambr` file ([syrupy issue 1237](https://github.com/syrupy-project/syrupy/issues/1237)).

### Dashboard queries

- `tests/prometheus/test_dashboard_queries.py` evaluates the queries of the Grafana dashboards on fixture series with the pinned promtool, and skips where promtool is not installed. A file `tests/fixtures/dashboard_queries/<dashboard>.yaml` holds the cases of `<dashboard>.json` in `k8s/devops/dashboards/` (the product dashboards) or in `k8s/monitoring/dashboards/`. promtool runs once for each file.
- A file with the key `spec` holds the cases of the dashboard that the SRE template (`devops_cli.grafana.service_dashboard`) builds from that spec, not of a committed file. Use it for a spec that `k8s/monitoring/dashboards/services.toml` does not hold, such as another SLO target. `service-template.yaml` is an example.
- A file has the format of a promtool unit test file with no rule file. To add a case, add a `promql_expr_test` entry with these keys: `panel` (the panel title), `ref_id` (the target refId), `expr` (the query of the target, copied from the dashboard with its variables), `variables`, `eval_time` and `exp_samples`.
- `variables` gives `__range` and `__interval` as durations, such as `24h`, and each dashboard variable as the text that Grafana puts in its place, such as `(devops-cli|roadmap-service)` for All. Give `__interval` as Grafana calculates it for the panel, not less than the Min interval of the panel. The test calculates `__range_s`, `__range_ms`, `__interval_ms` and `__rate_interval` as Grafana does: `$__rate_interval` is max(`$__interval` + scrape interval, 4 x scrape interval), and the scrape interval is the Min step of the target, else the `timeInterval` of its data source in `k8s/monitoring/grafana-values.yaml`.
- Put the series in a test group with `interval`, `input_series` and `shape`, the series shape that the group models: `sparse_counter`, `zero_start`, `counter_reset` or `snapshot_gauge`. Give the value that the panel must show in `exp_samples`, and say in a comment how you got it from the series.
- For a bar panel, such as an hourly bar of `increase(...[$__interval])`, add `bars`, the range that the bars cover, such as `24h`, and `total`, what the series add in that range. The test adds up one bar each `__interval` of the range, at the multiples of the interval, as Grafana aligns the steps, and gives promtool the sum. It fails when an expected sum is not within 1 % of `total`.
- When you change a covered query, change the `expr` of its cases in the same pull request. The test fails with the dashboard, the panel title and the refId of each case whose `expr` is not the query of its target.

### Hosts, sockets and the shared container

- A mock host is `example.com`, with no subdomain.
- Bandit scans `tests/` (`devops ci security`). A test binds a socket to `127.0.0.1` or `::1`, and writes under `tmp_path`. Use `# nosec BXXX` only on a literal that the test examines.
- No test sets `RLIMIT_NPROC`, which Linux counts for every process of the user in the container, and no test starts processes without a bound ([ARCHITECTURE.md](../ARCHITECTURE.md), section 7).
- Every test runs in the devcontainer and on a stock GitHub-hosted runner, and needs no package install or host change on either. A test that needs a capability of the host, such as bubblewrap or a container engine, skips where the host does not have it, and its skip reason names the missing capability.

### Property tests

- State machines, such as the roadmap lifecycle, and pure functions over open-ended input, such as parsers, policy evaluation and redaction, are tested with Hypothesis properties.
- Every run loads Hypothesis's built-in `ci` profile through `--hypothesis-profile=ci` in `addopts`, the profile that GitHub Actions loads by itself. It has no deadline and no `too_slow` health check, because a loaded host stretches the time of an example and a time bound then fails correct code, as [Clock](#clock) says. It is derandomized, so each run tries the same examples, and it keeps no example database. A property sets no deadline of its own.
- Everything else is tested with examples.

### Clock

- Wall-clock reads are faked with time-machine *(target)*. freezegun is not used: it is unmaintained, and its frozen monotonic clock hangs asyncio and tenacity.
- Waiting goes through the sleep and clock parameters the libraries already take, such as tenacity's `sleep=` and the `sleep` of pydantic-ai's retry configuration, and one place in `src/devops_cli` supplies the real ones *(target)*. A direct `time.sleep` is patched at the stdlib, the fallback for stdlib edges. devops-cli has no Clock type of its own.
- No test bounds elapsed wall-clock time from above. A loaded machine stretches the time, and the bound then fails correct code. A test shows the behaviour without the clock: it waits for the event (next section), counts something that the run decides, or asserts on the waits of the `clock` fixture. A test that must change the world while the code under test waits, such as a Workflow that finishes or a file that an editor saves, gives the `clock` fixture an action with `after_each_sleep`. An operation that does not stop fails at the hang bound of pytest-timeout. A budget counts something the run decides: the startup budget, the `startup-imports` row of `devops ci` (`tests/gate/startup_imports.py`), counts the modules that `--version`, the root `--help` and a few commands' `--help` import, and fails on any heavy module that any command group's `--help` imports, never on seconds. Each argv starts one fresh interpreter, and every check on that argv reads that one run.
- The ast-grep rule `test-elapsed-upper-bound` in `.ast-grep/rules/` holds `tests/` to this. Elapsed time is a clock reading minus an earlier time, and remaining time is a time minus a clock reading. A clock reading is a call of the `time` or `datetime` module that reads the current time, or a local name bound to one. The rule fails an assert that bounds elapsed time from above or remaining time from below, in the assert itself or through a local name. The `constructs` row of `devops ci` and the `ast-grep-scan` commit hook run it. A lower bound, such as a contract case that shows a real wait lasts at least its duration, holds on a loaded machine, and the rule allows it.

### Waiting for another thread

- A test that waits for something another thread or process does waits with `THREAD_HANDOFF_BOUND_SECONDS` from `tests/support/waits.py`, through `Event.wait`, `Queue.get`, `Thread.join`, `Barrier(timeout=...)` or `wait_until`, never with a deadline of its own. The wait returns as soon as its event happens, so only a failing test waits the bound out; a 1 or 2 s deadline failed correct code while a loaded host kept a ready thread waiting for a CPU.
- A test that waits for an event of a process that it started, such as a fresh `devops` that starts a child, waits through `wait_while_running` until the event comes or the process exits, and waits for the exit of that process with no timeout. Neither wait has a bound of its own. The start of a fresh interpreter that imports devops-cli is the step that a loaded host stretches the most, and it took longer than `THREAD_HANDOFF_BOUND_SECONDS` in a full run (#2092). A process that does neither fails the test at the hang bound of pytest-timeout.
- Anything a test relies on to stay alive or blocked, such as a sleeping child process or a job held until the test releases it, outlives the bound of every wait that observes it, or records whether the test ended it and asserts that it did. A hold on its observer's bound runs out inside the observer's window, and the test passes with the bug it checks for.
- A wait that checks that nothing happens keeps a short window of its own, opened only after a bounded, asserted wait shows the competing thread has reached the point where the event would happen. A comment at the window says so.
- A Textual test waits through its pilot. `pilot.press` and `pilot.pause()` return once the app has handled what was queued and the process has gone idle. A state the app reaches later is read again every `POLL_INTERVAL_SECONDS`, with `pilot.pause(POLL_INTERVAL_SECONDS)` between reads, under `THREAD_HANDOFF_BOUND_SECONDS`, never with `wait_until`, which would block the event loop the app runs on. The root conftest turns Textual's animations off (`TEXTUAL_ANIMATIONS=none`), so no wait sits out an animation.
- Every test runs under pytest-timeout's per-test bound, `timeout` in `[tool.pytest.ini_options]`, with `timeout_method = "signal"`, so a test that hangs fails in its own process, naming itself, and the run and its xdist worker carry on. The bound is a hang bound, far above the slowest test on a loaded host and above every wait's bound; a test that needs longer says so with `@pytest.mark.timeout(<seconds>)`.

### Which tests a narrowed run selects

- `devops ci test <paths>` runs only the tests a change reaches, and so does `devops test run --changed`, over the files changed since the branch left `main`, committed or not. A test module is reached when it is named for a changed module, at any depth, or imports it. A test module that only sits in the directory mirroring the module's package is not reached.
- `devops ci test` takes a directory too. A directory of `tests/` runs the test modules (`test_*.py`) inside it at any depth, and not its helper modules. A directory of `src/` selects tests for the Python modules inside it, as for a list of files. It refuses a path that does not exist, a directory that gives no module, and a directory outside `src/` and `tests/`, with exit status 1 and an error that names the path, whatever `--fallback` says. A file that exists and maps to no test, such as `README.md`, still exits 0 with a note, and a trigger file that is gone, such as a deleted `conftest.py`, still forces the full run (#2868).
- Given no `-n`, a narrowed `devops ci test` collects the tests that it selects before it starts them. The collection command is `uv run pytest -n 0 --collect-only -q`, with the same target list and `-k` filter as the run. The run is serial, `-n 0`, for up to `DEFAULT_CI_TEST_SERIAL_MAX_TESTS` (50) collected tests, where the start-up of xdist workers costs more than it saves. It runs on `DEFAULT_CI_TEST_NARROWED_WORKERS` workers above that. The `-k` filter changes the count, so a selection of 399 tests that `-k slow` narrows to 5 runs serially. A collection that exits 5, the exit pytest gives when no test matches, is a count of zero. That run is serial and prints no warning. A collection that fails or times out prints a warning that names the command and the reason, and the number of test modules then decides. Up to `DEFAULT_CI_TEST_SERIAL_MAX_FILES` (12) modules run serially, and more run on `DEFAULT_CI_TEST_NARROWED_WORKERS` workers, so a failed collection over 13 target files runs on 4 workers. A given `-n`, a run with no paths, a dry run and a `--repeat` run make no collection call and keep their worker choice. The full suite, and the fallback to it, run on `addopts`' `-n logical`. A direct `uv run pytest` with `-n logical` or `-n auto` waits for a gate slot in the `pytest_xdist_auto_num_workers` wrapper of the root conftest, and starts at most the CPUs of one slot (#4525). Any run with workers distributes its tests with `addopts`' `--dist worksteal`: a worker that runs out of tests takes half the tests another worker has not started, so a block of slow tests handed to one worker late in the run no longer keeps the others waiting for it. It runs pytest in a session of its own, so a timeout, Ctrl-C, SIGTERM or SIGHUP stops pytest and its workers with `uv`: a timeout with SIGTERM, a signal by first forwarding the SIGINT a terminal would have sent, so pytest runs its teardown, then SIGTERM and SIGKILL, which a second signal brings forward and cannot skip. The run takes over all three signals through `loop.add_signal_handler`, so each one wakes the run's event loop wherever it lands, only cancels the run, and raises no KeyboardInterrupt in the middle of the stop. A test that drives `devops ci test` doubles `asyncio.create_subprocess_exec` with `record_spawns` from `tests/support/session_spawns.py`, and asks for `refuse_nested_test_runs`, which fails any real `uv` or pytest it would start. The collection starts through that same edge, so a test that answers the run answers the collection too. A helper that reads the pytest run skips the child that holds `--collect-only`.
- A test module that replays a shared set computes the replay once in a module-scoped fixture and gives each case its own parametrized item, so a narrowed run stays inside the budget and xdist can distribute the cases.
- With a fresh coverage index (`devops ci coverage --build-index`), `devops ci test` selects the test modules that executed each changed module the index holds, in place of name-and-import matching. A module the index does not hold, a missing or stale index, and `devops test run --changed` select by name and import. So a test that should run for a module executes the module's code inside the test, not only on import, and names the module or imports it.
- A change that can alter tests that never import it runs the whole suite: `conftest.py`, `pyproject.toml`, `uv.lock`, `.python-version`, and a helper module under `tests/` that reaches every test, as the next rule says. `devops ci test`, and so the commit hook, runs the whole suite for any `conftest.py` it is given, at any depth, and under `--no-fallback` refuses any of these files instead. `devops test run --changed` narrows a conftest below `tests/`: one that only defines fixtures selects its own directory, and one that binds a `pytest_*` hook, which pytest calls for every test, selects the whole suite.
- A helper module is a Python file under `tests/` that is neither a test module nor a conftest, the modules of `tests/support/` included. One reaches every test when it defines a fixture or binds a `pytest_*` name, or when a conftest or such a helper imports it, directly or through other modules, inside a function too; and when it is deleted, renamed away or cannot be read, since what it registered can no longer be known. Any other helper selects the test modules that import it, directly or through other modules, and a package's `__init__.py` those importing any of the package's modules. `devops test run --changed` lists a rename as its old path deleted and its new path added, so a helper renamed away reaches every test. The registration fails a run whose support module holds a fixture or hook this rule cannot see in its source, such as one made by a decorator factory or imported under a new name.
- A check that parses every file under `tests/`, as the check against `__file__` and test-module imports does, runs only in the full gate: its module imports nothing from devops-cli and no module under `tests/`, spells no devops-cli module's dotted name and is named for none, so no change to a source or helper module selects it, and a narrowed run reaches it only when given its module or when it runs the whole suite (`tests/commands/test_test_selection.py` checks both). With a coverage index, every test module is credited with what the root conftest's function-scoped autouse fixtures run in its setup and teardown, so a change to one of those modules selects the check's module with every other test module.
- A narrowed run does not see what a helper does on import to tests that do not import it. The invariant above refuses every top-level or class-body statement but those that bind names, and what still runs unchecked, a value bound to a name, a decorator, a default argument, a base class or a metaclass, is caught by the full suite, which the `Tests & Coverage` check of CI and `uv run devops ci` run, not by the narrowed run.
- The commit hook runs `devops ci test` on the staged Python files only, so `pyproject.toml`, `uv.lock` and `.python-version` never reach the whole suite through it. They do when given to `devops ci test` or listed by `devops test run --changed`, and through the full suite of `uv run devops ci` and of the `Tests & Coverage` check of CI. Nor does the hook get a deleted path or a rename's old path: without a coverage index that knew the helper, a test module still importing its old name runs only in the full gate; with one, the index drift finds the gone helper and the hook runs the full suite.
- A trigger file that changed only since the coverage index was built leaves the index stale, and `devops ci test` selects by name and import until the index is rebuilt. A helper module the index knew that is gone runs the whole suite instead, or is refused under `--no-fallback`.

### Run time

- The `Tests & Coverage` check must average under 300 s (AGENTS.md, rule 5). The owner allows 60 s of tolerance for the variation of the runners (2026-10-23), so the limit of the alarm is 360 s. `devops ci job-time` reads the time of the check in the last 20 completed pushes to `main` from the Actions API and fails when their mean is over the limit. The time of a run is the run time of the slowest shard job `Tests & Coverage (shard <n> of <total>)` plus the run time of the job `Tests & Coverage`, which joins the shards. The time that the jobs waited for a runner is shown on its own line and is not counted, because the queue depends on the other runs of the account, not on the tests. It counts a job that passed, failed or timed out, whatever the run concluded, so a slow run that failed stays in the mean. The `Test Job Duration` job of `ci.yml` runs it every day and on a manual run, not on a push, so a push to `main` is green when its tests pass. A pull request cannot show the mean, so the check reads the history of `main`, not the pull request. A mean over the limit is a P0 bug: find the change that made the check slow, and fix it or revert it. Do not narrow or skip a needed check to hide the time. The job runs the check with `--file-issue`: over the limit, it comments on the open issue whose body holds the alarm line of the check, or files one with the labels `type/bug`, `scope/ci`, `status/new` and `priority/p0-critical` when none is open. The issue holds a Priority, so intake does not place it, and the Status New lets refine read it. So one breach has one issue, also after a person changes its title or labels, and the next breach after the issue closes files a new one.
- The budget measures the mean of the `Tests & Coverage` check on `main`, not the test step of one local run. A local `uv run devops ci` runs the whole suite on every logical CPU of a host, and the gates of other agents share that host, so a local full gate can pass the budget on a shared host. When the test step of a local run goes above `CONST_CI_TEST_BUDGET_SECONDS` (300 s), the gate prints the time of the step and the slowest tests against the budget. It fails no test on the time.
- The same suite took 355 s on a fast runner and 528 s on a slow one (2026-11-04), so no cut of constant work holds the bound on every runner. The test row runs in four shards, one quarter of the recorded test time on each runner (`devops ci --only test --shard <n> --shards 4`). When `Test Job Duration` nears the bound, write the record again first (`uv run devops ci durations`, below), then add a number to the matrix of the job `test-shard`. A test must not depend on a test that runs before it in the same process, since a shard holds only some of the tests.
- A shard measures a part of the tree, so it checks no coverage floor and prints no report. The job `Tests & Coverage` combines the coverage data of the shards and checks `fail_under` on the whole.
- A shard collects only its own test files. Pytest collects every file it gets, in every xdist worker. A split plugin that deselects tests after collection makes each worker collect the whole suite. That cost 31.8 s of CPU in each of 16 workers, which is 13.5% of the CPU of a run (2026-11-05, 16-CPU host, 19,074 tests). Now `devops ci --shard <n> --shards <total>` passes the paths of the test modules of the shard to pytest. A quarter of the files collects in about two thirds of the CPU time of the whole suite, not a quarter. The imports of shared modules stay. In the same run, worker start was 2.8% of the CPU and the controller was 1.4%. A preload fixture gave no saving. A test must not depend on a test of another file, because a shard holds only some of the files. For the same reason a `conftest.py` below `tests/` imports no devops-cli module at its top: a run that names a file below its directory loads it before the root conftest isolates HOME, and devops-cli binds its paths under HOME when it is first imported.
- The split weighs each test module by its recorded seconds in `tests/module_durations.json` (#5247). It deals the modules, heaviest first, to the shard with the least weight so far. A module that the record does not hold weighs its lines at the recorded seconds per line, so a new test module joins a shard with no other step. A module that the record holds and the tree does not is in no shard. A stale record only unbalances the shards and drops no test, and every runner reads the same record from the same commit. The split by lines put a short module with slow tests in one shard, and each change of the tree moved modules between shards: in one run of 2026-11-13 the four shards took 160 s to 341 s, and the mean of the check over 20 runs was 316 s. A replay of the last 20 runs of `main` with weights from the other 19 runs gives a mean of 284 s. `uv run devops ci durations` writes the record: it reads the JUnit report of each shard of the last 20 push runs of `main`, which `ci.yml` uploads in the artifact `coverage-shard-<n>` and keeps for 7 days, and writes the mean seconds of each module over the runs that ran it. Write it again when `Test Job Duration` nears the bound, or after a change moves much test time, and commit the file.
- An autouse fixture runs before each of the 14,000 tests, so it does no work that most tests do not need. A fixture that loads settings, opens a database or lists a directory belongs to the tests that ask for it. A numbered directory made for every test, such as `tmp_path_factory.mktemp("run")`, is slow: pytest lists every entry of the base directory to find the next number.
- `tmp_path_retention_policy = "failed"` in `pyproject.toml` deletes the directory of a test that passed, so the base directory stays small. A later test can therefore get the path of an earlier one. A cache that is keyed by a path and holds the content of a file is wrong in such a run: key it by the content.
- The root conftest raises the young threshold of the garbage collector to `GC_YOUNG_THRESHOLD`. The default made the collector a tenth of the run time. A test that needs the collector calls `gc.collect()`.
- `tests/support/typer_commands.py` builds the click command of a Typer app once for each state of its registered commands and groups, not once for each `CliRunner.invoke`. Building the `devops` command reads the signature of 4,800 functions and took a tenth of the CPU of the run. A test that adds a command to an app after it has invoked the app gets a new command; a test that changes a registered command in place calls `typer.main.get_command(app)` itself.
- Measure a change to the run time with CPU time on pinned CPUs (`taskset -c 0-3`, as many as the runner has), and with the time that one part of the run takes, such as the setup of all tests. The wall time of a shared host varies by more than the change.

### Coverage

- The coverage floor is 85% of the lines and branches of `src/` (`fail_under` in `pyproject.toml`). The aggregate CI job keeps `.data/coverage.xml` as an artifact for 7 days. A pull request must also cover 90% of its changed lines: the `Changed-Line Coverage` step of `ci.yml` fails below that.
- A line that no public behaviour reaches is dead code. It is deleted, not covered by a test that reaches past the public interface.

### Floor and ratchets

- Every test runs inside the hermetic floor, which the root conftest supplies: the network block, which refuses a connect or a datagram (`sendto`, `sendmsg`) to a host that is not loopback and a lookup of `socket` that needs a DNS query, also refuses a loopback connect to a port no socket in the test process binds, and fails the test that made it, even when the code under test swallowed the refusal; the git config of the isolated HOME, which refuses each git transport but the local one, so a real git child fails at once on an https, ssh or git remote (a test that sets its own HOME does not get this config); the host path guard in `tests/conftest.py`, which fails a test that opens a file outside the checkout, the run's temporary directory and the interpreter. `tests/support/host_paths.py` holds the allowed roots. For a linked worktree it adds the common git directory. So a test in a worktree outside its main checkout can read the `HEAD` file of its own git directory. Such a worktree is the replay tree of `devops ci fail-to-pass` or the worktree of a runner. `tests/invariants/test_host_path_roots.py` holds the roots; the refusal to start a real gh or security scanner; the test's own data directory, config and gh config, with no way onto the session bus; the removal of `DEVOPS_CLI_ROADMAP_IMPLEMENT_IN_RUNNER`, which the pod of a runner Job sets and which wins over the config of the test, so a test is in a runner only when its config sets `roadmap.implement.in_runner`; a pinned GitHub identity, so a gh or git child gets a placeholder token, never the developer's login; a throwaway kubeconfig for the run; the config write guard, which fails a test when it opens a config file for writing, renames a file onto one or removes one outside the run's temporary directory, and names the test and the stack; the spend ledger write guard, which fails a test when it writes to the spend ledger outside the run's temporary directory; the home write guard, which fails a test when it opens a file for writing, renames a file onto one or removes one under the real home, the HOME that the floor replaces, outside the run's temporary directory, the checkout and the interpreter, and names the test and the stack; the refusal of a support helper to write outside the run's temporary directory, or at all outside a pytest run; and the workspace tripwire, which fails the run when a test writes to the workspace's `config.yaml` or to a tracked file.
- The floor fails a test that reaches a faked edge without its fake, with an error naming the edge.
- A dry-run test adds no block of its own for programs, DNS or external hosts, because the floor refuses them. It asks for `refuse_requests` (`tests/support/dry_run_requests.py`), which also refuses a socket connect or an httpx2 request that a fake would answer, and checks the dry-run classes of its table with `misclassified` (`tests/support/dry_run_classes.py`). The ratchet `tests/invariants/test_dry_run_class_ratchet.py` keeps each classified command out of `tests/fixtures/dry_run_gaps.json`, so a test file does not check again that its commands are out of the gaps file. `tests/commands/test_global_dry_run.py` tests the root `--dry-run` on each shape of argv, so a test file does not run each of its commands again under the root flag.
- A test that checks a service that is down refuses it through `refusing_port`, a loopback port the test binds and never listens on, so the kernel refuses each connect as a stopped service would, and the service's retry waits return at once, as [Clock](#clock) says. A test that needs a service's answers fakes it at its edge, such as the model through `model_fake`.
- After every test, the floor calls the public reset of every process-wide cache and singleton, and an invariant test fails a module-level cache or `global` in `src/devops_cli` that has no reset there.
- A command that passes its dispatch timeout leaves its worker thread running, and a worker that ends after the floor resets the tracer builds a tracer from the real settings, which exports to port 4318 during another test. At the end of each test, while the test's isolation holds, the floor waits for the dispatch workers (`finish_abandoned_dispatch_workers`). A test that does not release its hung command fails in its own teardown, not in a later test.
- Telemetry export and the Valkey cache, best-effort side channels that nearly every test reaches, go to a loopback port the floor binds for the run, `unserved_side_channel_port`, which refuses them as a workstation that serves neither does.
- Telemetry export is off unless a test opts in with the OTLP fake: the `otlp` fixture installs `FakeCollector` as the process's exporter, with export on, and each read of the fake waits for the exports the tracer queued.
- Bans hold each retired rule: `tests/invariants/test_source_tree.py` bans patches aimed at devops-cli internals, bans imports of private `devops_cli` names, bans test accommodations in `src/` (`unittest.mock`, `PYTEST_CURRENT_TEST`, replaced `subprocess.run` detection, mock-attribute checks, and `unreachable` calls), bans test files outside a mirror directory or `tests/invariants/`, bans loose `.py` files directly in `tests/` other than `conftest.py` and `__init__.py`, bans module-level `CliRunner()` instances in invariant files, and bans unlisted invariant test files. `tests/invariants/test_agents_md.py` bans retired test rules from `AGENTS.md`. Ratchets hold each thing being retired to a ceiling that may only go down: `test_suppressions_stay_under_their_ceilings` in `tests/invariants/test_architectural_invariants.py` holds the suppression comments, the `# noqa: C901` markers among them, and the `swallowed-failures` row of `devops ci` (`tests/gate/swallowed_failures.py`) the swallowed failures. A change that passes a ceiling is fixed, and the ceiling is never raised; a ratchet at zero becomes a ban.
