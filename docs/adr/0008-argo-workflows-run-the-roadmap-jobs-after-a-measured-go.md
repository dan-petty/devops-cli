# Argo Workflows runs the roadmap Service's queued and scheduled work, after a measured go

The roadmap Service hand-rolls its engine: a worker thread and queue per repository, trigger coalescing, a five-minute tick, a pause until the GraphQL reset and an in-memory delivery cache. Each planned change (#1386, #1533, #1534) would add more queueing, scheduling or locking of the same kind, and a queued trigger does not survive a pod restart. The owner chose Argo Workflows as the engine on 2026-10-09 (#1535): it fits the Argo CD toolset and brings templated mutexes, CronWorkflows, ConfigMap semaphores and retries with no database. It also turns every job into a pod, which costs seconds where a thread costs milliseconds (an estimate, not yet measured) and puts more churn on the API server of a single k3s cluster. Step 1 of #1535 therefore installs the controller and measures both before any job moves onto it, and steps 2-6 are filed only after a go.

- **Engine.** Argo Workflows, from argo-helm's `argo-workflows` chart, pinned at 2.0.13 (app v4.1.5) in Application `argo-workflows` and in deploy-stack's `infra` stack. The controller runs alone: one replica, no argo-server, no Argo Events, no database and no workflow archive. Its locks are ConfigMap-based, its metrics reach Alloy through a ServiceMonitor, and its OTLP traces move to step 2.
- **What is measured.** WorkflowTemplate `devops-cli-version` in namespace `argo-workflows` runs `devops --version` in the Service image. `--version` exits in its eager callback before any command runs or any tracer is built, so a run makes no GitHub request, mounts no Secret and exports no telemetry (`DEVOPS_CLI_TELEMETRY_ENABLED=false` keeps it so if its arguments ever change). It costs what every later job will cost and nothing else: scheduling a pod, starting its containers and the controller's bookkeeping. `devops roadmap metrics` was the first candidate and was dropped, since `devops roadmap` has no `metrics` command and the metrics job reads its clone and GitHub.
- **Go/no-go.** Go when, from a Workflow's creation to Succeeded, the warm p95 is at most 30 seconds, and a burst of 20 Workflows finishes with no 429 or 5xx from the API server. The warm p95 is taken over the 19 runs that follow the first of 20 sequential Workflows, as the nearest-rank percentile (the value at position ceil(0.95 x 19) = 19 of the sorted durations, so the slowest warm run); the first, cold run (any image pull included) is reported apart. Thirty seconds keeps half of the one minute that a merged pull request's close workflow is allowed from start to finish, for the job itself. The same run records the p50, the API-server requests per Workflow (the change in `apiserver_request_total` across each batch) and the controller's CPU and memory; the verdict does not use those three. The verdict and the numbers go on #1535 as a comment.
- **Namespace and perimeter.** The controller and its pods run in `argo-workflows` under Pod Security `restricted`, as `devops` does, with `Prune=false,Delete=false`; a bare `argo` would be easy to confuse with `argocd`. The perimeter admits ingress only for the metrics scrape from `monitoring`, and egress only to DNS and to the API server on 6443 through an ipBlock that excludes the cloud metadata address. It admits no public HTTPS and no OTLP. Because the controller cannot reach a registry, the template names its `command` (`devops`) itself: left out, the controller looks the image's entrypoint up over HTTPS and the Workflow fails.
- **One namespace watched.** `singleNamespace: true` makes the controller watch only `argo-workflows`, with a Role in place of a ClusterRole. The chart's `controller.workflowNamespaces` does not restrict the watch, and Argo Workflows has no list of watched namespaces. Step 2's jobs need Secret `devops-cli`, and a pod mounts only the Secrets of its own namespace, so step 2 chooses between cluster mode with Workflows in `devops` (a ClusterRole that watches every namespace) and a copy of the Secret in `argo-workflows`. Step 1 needs neither, and its executor ServiceAccount can only create and patch `workflowtaskresults`.
- **Minimal CRDs, kept.** The chart installs its minimal CRDs (`crds.full: false`) with `crds.keep: true` and the same `ServerSideApply=true,Prune=false,Delete=false` sync options as Argo CD's CRDs. The chart's default, `crds.full: true`, applies the full CRDs from a pre-install hook Job whose ClusterRole may create, patch and update every CRD in the cluster, and `crds.annotations` reaches only the minimal ones.
- **Pins.** Values set `images.tag: v4.1.5` explicitly, and a test ties it to the argo CLI pin in `tools.lock`, since the measurement submits its Workflows with that CLI and the chart's app version is not in the repository to check offline. A chart bump moves the chart version, `images.tag` and the CLI pin together.
- **One controller, never two.** At one replica the chart renders `strategy: Recreate` and `LEADER_ELECTION_DISABLE=true`. A restart of the controller (a chart bump, a node drain) interrupts running Workflows until the new pod is up. Step 1's runs last seconds and accept that; step 2's CronWorkflows replay a run missed in a restart with `startingDeadlineSeconds`.
- **Events counted.** The chart's defaults for `nodeEvents` and `workflowEvents` write a Kubernetes Event per node and per Workflow. The measurement keeps them, so the requests it records include them.
- **Later steps.** After a go, steps 2-6 are filed as splits with `budget/borrowed`, each depending on the step before it and on step 1's go: lanes, mutexes and CronWorkflows; the router submitting Workflows; the `github-graphql` semaphore; the background enhancement lane; cleanup. All of them also wait for the GitHub App identity that in-cluster jobs act as. After a no-go, the owner chooses between re-scoping the engine and the runner-up below.

## Considered Options

- **DBOS Transact in-process** (runner-up): rejected for now. It adds no server, but it has no queue pause, which the GraphQL hold needs, and its community is small.
- **RQ on Valkey**: rejected. `rq suspend` matches the hold, but it needs a persistent Valkey and about 16 worker processes, and its keyed concurrency is unreleased.
- **Temporal and Hatchet**: rejected. Each needs a new Postgres and 3-6 pods.
- **Argo Events**: rejected. It adds NATS without providing serialization or a hold.
- **Celery, Dramatiq, Taskiq, Prefect, Restate, Inngest, Huey, SAQ, arq and APScheduler 4**: not chosen, after the same comparison against the requirements: events and schedules, one round at a time per repository lane, a global hold until the GraphQL reset, durable queued work, observability, and a reputable, maintained project.
- **Keep the hand-rolled engine**: rejected. Each planned change would add more of it, and queued work would stay in memory.
- **Adopt Argo Workflows without measuring**: rejected. A pod per job and the API server's churn are the risks the choice rests on, and steps 2-6 are large.
- **Measure `devops roadmap metrics` instead of `--version`**: rejected for the reasons above, and because it would need GitHub and the Service's volume in step 1, which holds neither.
- **A cluster-wide controller now**: rejected for step 1. It would watch every namespace and carry a ClusterRole, for a template that needs only its own.
- **Full CRDs from the chart's hook Job**: rejected, as above.

## Consequences

- Two Argo CD Applications and one deploy-stack release carry it: `argo-workflows` (the chart) and `argo-workflows-manifests` (`k8s/argo-workflows/`, with the perimeter and the template; it skips the dry run until the chart's CRDs exist). deploy-stack applies the perimeter before the charts and the WorkflowTemplate after them, deletes the template before uninstalling, and lists it in a dry run.
- The Workflow CRDs stay after an uninstall or a teardown (`crds.keep`), as the `prometheus-operator-crds` CRDs do, since deleting a CRD deletes every Workflow and WorkflowTemplate. Argo CD's `homelab` project ignores the Workflows named `devops-cli-version-*` that the CLI submits, which it would otherwise report as orphans.
- Tests run offline. They read the values file and render `k8s/argo-workflows/` with `kubectl kustomize`; none runs helm. The executor Role is the chart's, so only a live `kubectl auth can-i` check proves it.
- The template's image is the Service image, untagged, with `IfNotPresent`. Image Updater rolls only Application `devops`, so a run uses whichever `latest` image its node already holds, and the cold first run includes any pull.
- Nothing in namespace `devops` changes, and `roadmap-service` stays at 0 replicas. A go does not move any job: each of steps 2-6 is its own item and pull request.
- The controller's resource requests and limits are starting values. The measured CPU and memory are what a later change sizes them from.
- #1533's ADR records only the scoped updates, since the engine is recorded here.
