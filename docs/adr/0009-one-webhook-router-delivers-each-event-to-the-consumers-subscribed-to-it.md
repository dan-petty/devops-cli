# One webhook router verifies each sender its own way and delivers each event to the consumers subscribed to it

The roadmap Service had one webhook route, built for one sender and one consumer. It checked GitHub's signature, read the payload with `.get` chains, and put every accepted delivery into a round of both lanes, though no job is due on a `push`, an `issue_comment` or a `create` (#1361 measured 940 webhook triggers in one hour). It wrote no record of what arrived, and its counter could not tell deliveries apart. Planned items need more senders (#1387, #1395) and a second consumer of GitHub's events (#1389). #1386 builds one receiver they extend instead of each adding a route.

- **One router, one route per provider.** Every sender comes in through `create_webhook_router`, which registers `POST /webhooks/<provider>` for each member of `WebhookProviderName`. A provider nothing declares has no route, so it gets 404 from routing. A provider is a frozen declaration, `WebhookProvider`: its verifier, the headers its event name and delivery id come from, its payload model, the event that only asks whether the Service listens (a `ping` gets `pong`), and its exposure. Every provider takes the same steps: refuse while draining (503), require `application/json` (415), cap the body at `CONST_SERVICE_MAX_BODY_BYTES` (413, by the length it declares, whatever its digits, or by the bytes it streams), verify (401), validate the typed payload (400), answer a ping, acknowledge an event without a subscriber, drop a repeated delivery id, and deliver.
- **Each provider authenticates itself.** Network policy is not authentication: the monitoring namespace already reaches every route on port 8000. `HmacSha256` checks GitHub's `X-Hub-Signature-256` with `hmac.new` and `hmac.compare_digest`, against the secret of each managed repository, and a repository with no secret refuses every request with 401. The check happens before the body is parsed, so a sender without a secret learns nothing of the schema. Other verifiers arrive with their first user: `AuthorizationToken` with #1395.
- **Typed payloads.** `GitHubWebhookPayload` (`models/webhooks.py`) is a pydantic v2 model with `extra="ignore"` that declares only the fields the Service reads: `action`, `repository.full_name` and `sender.login`. A body that does not validate gets 400 naming the failing fields' paths, cut to 256 characters, and no value from the body. One model serves every event. GitHub's per-event actions are an open set a model would have to list, and a list would answer 400 to the first action it lacks.
- **Consumers subscribe.** A `WebhookConsumer` is a declaration: a name, a provider, the events it takes, an optional refusal that narrows them by the typed payload, and its delivery target. The roadmap consumer takes the events the roadmap jobs' batch keys name (`issues`, `pull_request`, `milestone` and `release`, derived from `CONST_ROADMAP_*_BATCH_KEYS`), and refuses the machine account's own writes, which the roadmap must not answer. The refusal belongs to that consumer alone, so it hides the machine account's events from no other consumer. A consumer takes a payload only when its refusal is None. When every subscribed consumer refuses, the router answers 200 with the first refusal's status, `ignored_machine_account` for the roadmap. Every other event, `push` included, gets 200 `no_subscriber` and starts no round.
- **One seam into the workers.** A consumer's delivery target receives the repository, event and action. The roadmap consumer's target is `ServiceManager.enqueue_trigger`, which enqueues on each lane's `RepoWorker`. The router calls nothing else in the workers, so replacing the lane workers with Workflow submits (#1535 step 3) changes that target and nothing in verification, validation, subscription, logging or counting.
- **Each delivery is logged and counted.** Every request writes one INFO record with `provider`, `event`, `action`, `delivery`, `repo` and `outcome`, and never the body, the signature or an Authorization header's value. `devops_cli_service_webhook_deliveries_total` carries `provider`, `event` and `outcome` on every path, with `no_subscriber` as an outcome. The event label is the event when a consumer subscribes to it (or it is the provider's ping), and `other` otherwise, so a sender's choice of event name grows no series. The text a sender chooses (the event name and delivery id) is cut to 256 characters in the record.
- **Exposure is pinned.** A provider is reached `tunnel` (through the public Ingress) or `cluster` (only at `http://roadmap-service.devops.svc.cluster.local:8000/webhooks/<provider>`). `tests/test_k8s_roadmap_service.py` checks that the Ingress routes exactly the paths of the `tunnel` providers. Only GitHub is public today, so ADR 0003's single public path holds. A cluster sender's route is not hidden from a request through Traefik: a check on forwarding headers would trust headers that any in-cluster caller can set.
- **A sender gets a provider only once a consumer or a responder acts on its events.** Alertmanager and Argo CD post to Mattermost with their own integrations (#1392, #1393), and the Service posts its own release events (#1394), so neither sends to the Service. Argo CD records deployments through its own GitHub App, Deployments only, and has no provider here. The only chat sender the router takes is Mattermost's slash command (#1395), as a `cluster` provider. Gitea (#1081), Grafana alerting, Cloudflare Notifications, the LLM gateway, Statuspage, Prometheus rules, Qdrant, Valkey, the OpenTelemetry collector and the in-cluster registry have no consumer, so none gets a provider.
- **No consumer depends on a single delivery.** Each consumer has a poll (ADR 0003), or its sender re-sends until it is acknowledged, so a missed or dropped delivery only delays a round to the next poll.

## Considered Options

- **A route per sender**: rejected. Each would copy the body cap, the content-type check, the draining refusal, the delivery cache, the log record and the counter, and drift from the others.
- **A model per GitHub event** (`issues`, `pull_request`, `milestone`, `release`): rejected. Declaring only the fields the Service reads makes them identical, and a literal list of each event's actions would be a subset of an open set.
- **githubkit's `verify` and `parse`**: rejected. It brings hishel and every GitHub REST and webhook model for three fields. Revisit if consumers start reading many event types.
- **A webhook gateway (Convoy) or Argo Events in front of the Service**: rejected. Each adds a stateful service for one public sender and one in-cluster sender.
- **CloudEvents or Standard Webhooks as the envelope**: rejected. None of these senders emits either.
- **Narrowing the roadmap consumer by action**: rejected. An action no batch key names, such as `labeled`, still makes a job whose change predicate matches due at once, instead of at the next poll. #1361 owns the cost of each round.
- **Routing a default-branch `push`**: moved to #1389's cluster lane, its first user.

## Consequences

- A hook that sends every event, or only pushes, is harmless: the Service acknowledges it and starts no round. Only `issues`, `pull_request`, `milestone` and `release` start a round before the next poll, so repositories whose hook sends only pushes get roadmap rounds from the poll alone.
- `verify_webhook_signature` is gone. `HmacSha256.verify` replaces it and compares the digest as bytes, so a signature header that carries non-ASCII text is refused with 401 and no longer fails the request.
- A repeated delivery id is dropped by the same `DeliveryLRUCache`, but only for an event a consumer takes, so an unsubscribed event never uses its capacity. Deleting the cache with the lane workers is #1535 step 3's.
- The ping and an event with no subscriber are answered after the signature and the payload check, as before, so only a sender with the repository's secret gets any answer but 401.
- A consumer given to `create_service_app(consumers=...)` replaces the roadmap consumer, which tests use to record deliveries without patching a name.
- The setup step in `k8s/README.md` says that events without a subscriber start no round. `replicas: 0` for `roadmap-service` is unchanged, and the live checks (a redelivered `issues` and `issue_comment` delivery in Loki and in the counter) wait for the Service to run again.
