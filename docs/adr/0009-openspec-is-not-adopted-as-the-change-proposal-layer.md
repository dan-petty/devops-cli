# OpenSpec is not adopted as the spec and change-proposal layer

Issue #1753 asked whether OpenSpec ([Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)), a Node tool that records a change as a proposal, spec deltas, a design and tasks, and archives it into a living specification, should replace the issue body, the refine plan and the per-item task file as the record of how a change is specified and planned. It is not adopted. The project is healthy and licensed for it, so the decision rests on fit and cost: a change folder is a heavier second copy of what the issue and the task file already hold, its lifecycle needs a proposal committed ahead of its code, which AGENTS.md does not allow a task file to be, the archive step writes to a file every change to a capability shares and conflicts when two changes do, and replacing task files means rewriting the code, tests and documents that read and prescribe the task files (573 on 2026-10-22, inventoried under Consequences). The evidence was gathered on 2026-10-22 against OpenSpec 1.14.3 (published 2026-10-17), in scratch directories outside the repository with telemetry and the update check off. The task files, the issue, `changelog.d/` fragments and the readiness check stay as they are.

- **Health (question 1).** MIT licensed: the [registry entry](https://registry.npmjs.org/@fission-ai/openspec), the GitHub API and the [`LICENSE`](https://github.com/Fission-AI/OpenSpec/blob/v1.14.3/LICENSE) in the package (the same file as in the repository at the v1.14.3 tag) agree. `@fission-ai/openspec` has 54 versions since 2025-09-06, 1.0.0 on 2026-01-26, and 12 releases from 1.8.0 (2026-08-05) to 1.14.3 (2026-10-17), about one a week, each with notes on the [releases page](https://github.com/Fission-AI/OpenSpec/releases). Earlier the cadence was uneven: no release from 2026-02-23 to 2026-04-11, and none from 2026-04-21 to 2026-06-01. The repository (created 2025-08-05) is not archived, was pushed to on 2026-10-21, and shows about 72.7k stars and 205 open issues and pull requests. The package has one npm maintainer account. The contributors API lists 147 contributors on its two pages (100 and 47), 5 of them bots, with 996 contributions in all; the top two hold 710 (71%) and the top one alone 521 (52%). Registry signatures verified for all 57 installed packages, 22 of them with attestations, and `npm audit` found no vulnerabilities. This meets the policy of reputable, maintained dependencies.
- **Runtime and pinning (question 1).** It needs Node 20.19 or later. The devcontainer has Node 24.22 from the devcontainers `node` feature, but the repository has no `package.json`, no lockfile and no npm step in its workflows (`codeql.yml` names `actions/setup-node` only in a comment). `npm install --ignore-scripts @fission-ai/openspec@1.14.3` in an empty directory added 57 packages (12 direct dependencies, 18 MB) in 2 s, and the package declares no install scripts. 1.13.2, four weeks older, installed 70 packages from 10 direct dependencies, so the tree moves between releases. `src/devops_cli/tools_lock/tools.lock` pins 14 binary tools by sha256 and 2 Python tools by hashed requirements, with no npm kind, so a pinned install needs a new kind or a root `package.json` and lockfile. A pin is not optional. `validate --strict` fails on warnings, and minor releases add warnings: unrecognized keys in `.openspec.yaml` (1.14.0), a requirement over 500 characters (1.14.1), an archive-written Purpose placeholder (1.11.0), and text in a delta that archive would drop (1.14.2). An unpinned CLI would turn a green check red with no change in the repository.
- **Telemetry (question 1).** On by default: `isTelemetryEnabled()` in `dist/telemetry/index.js` of the [1.14.3 package](https://registry.npmjs.org/@fission-ai/openspec/-/openspec-1.14.3.tgz) is true unless an opt-out applies. It posts the command name, the OpenSpec version and a random UUID kept in the user's config to a PostHog proxy at `edge.openspec.dev`, after a first-run notice on stderr, and the version check asks `registry.npmjs.org`. `DO_NOT_TRACK=1`, `OPENSPEC_TELEMETRY=0`, a truthy `CI` or `openspec config set telemetry.enabled false` turn off both requests (`OPENSPEC_NO_UPDATE_CHECK` turns off the check alone). `.devcontainer/devcontainer.json` already sets `DO_NOT_TRACK=1`, but a contributor's host shell, a cloud agent's sandbox and any other environment an agent runs in would each need it set, as AGENTS.md's telemetry opt-out rule requires wherever the tool runs. This was read from the source, not observed: no run was allowed to send an event.
- **ADR 0001 (question 2).** It fits. A change folder holds `.openspec.yaml`, which has a schema name and a creation date, and `skip_specs` or a `goal` when set. It has no status, milestone, priority, issue number or pull request, so [ADR 0001](0001-github-is-the-roadmap-source.md) is not contradicted, and the issue would keep status, milestone, priority and the discussion. What would move into the folder is what the refine plan and the task file hold today: why, behaviour, design and tasks. Nothing links the folder to its issue except a name: `openspec new change 1805-release-tag-guard` is accepted, and archive prefixes the folder with the archive date.
- **Task files (question 3).** An OpenSpec change could carry what a task file carries, but it does not replace the rules around it.
  - *Lifecycle.* `/opsx:propose` writes the planning artifacts and stops, apply follows in a later request, archive moves the folder. AGENTS.md has a task file written only by the pull request that delivers the item, as it will read when merged, with no unchecked box. A proposal committed ahead of its code has `- [ ]` tasks, and OpenSpec's apply step tracks progress by them (`tests/test_agent_task_files.py` reads only `docs/agent/tasks/task-*.md`, so it would not catch them, but the rule would be broken). Committing only the finished, archived folder keeps the rule and collapses propose, review and apply into one pull request, which discards what OpenSpec adds. Archive does not replace author-as-merged: it moves the folder, which still has to be complete when the pull request merges.
  - *Readiness and closing.* `_writes_task_file` and `_changes_its_task_file` in `src/devops_cli/commands/pr.py` require the pull request to touch `docs/agent/tasks/task-<issue>-*.md`, and `acceptance_criteria` and `task_files` in `src/devops_cli/roadmap/close.py` quote that file's `## Acceptance Criteria` into the closing comment. An archived change has no such name and its acceptance criteria are scenarios inside a spec delta.
  - *Items without behaviour.* `openspec validate --strict` refuses a change with no spec delta unless its `.openspec.yaml` sets `skip_specs: true` (tried with a one-line docs change). That is a flag written into each change that has no behaviour to specify. CI, manifests, tooling, documentation and refactors are a large part of the work here (the share was not measured), and for them the folder is a proposal, a design and a task list with its spec artifact skipped by design.
  - *Weight.* See the trial below: a six-file folder of 569 words for an item whose task file is one file of 303 words, with the changelog fragment needed either way.
- **Agents (question 4).** Slash commands and skills, written per tool. `openspec init --tools claude,gemini,github-copilot` generated 6 commands and 6 skills for each: `.claude/commands/opsx/*.md` and `.claude/skills/openspec-*/SKILL.md`, `.gemini/commands/opsx/*.toml` and `.gemini/skills/`, `.github/prompts/opsx-*.prompt.md` and `.github/skills/`. That is 36 files, 7,830 lines, about 560 KB, plus `openspec/config.yaml`, and each skill allows `Bash(openspec:*)`, so the CLI must be on the agent's path. The package has adapters for about 50 tools. Init left `AGENTS.md` and `CLAUDE.md` untouched (run on a scratch repository with both, `--tools agents,codex,cursor`), so adoption does not shrink them. The most it would retire is the three AGENTS.md rules about the task file ("Author All Code, Documentation, Status & Wording as Merged/Committed", "Task Files Written by Delivering PR" and "Modular Per-Task Tracking Architecture"), which on 2026-10-22 were 2.8 kB of the file's 39.7 kB (7%), part of which (the changelog fragment rule and the board field reconcile) stays; the security, git, test and release rules all stay. `.gitignore` ignores `.claude/*` except `settings.json`, so the generated Claude files would stay out of the repository unless the ignore changed, and each clone would run `openspec init` itself. A version bump regenerates them: init output of 1.13.2 and of 1.14.3 differs in 34 of 39 files (324 lines), because each skill embeds `generatedBy` and the instructions change.
- **Conflicts (question 5).** A change folder per issue does not conflict, but archive does. Two unarchived changes on two branches merged cleanly. Two changes that each added a requirement to the capability `release-publishing` and were archived on their own branch from one base gave `CONFLICT (content) in openspec/specs/release-publishing/spec.md` when merged, both appending after the same last requirement. Deferring archive avoids that: the same two changes merged unarchived and then archived one after the other gave a spec with both. But deferral needs one serial archive step, such as the release cut (`devops roadmap close` or `devops release prepare`), which is new machinery in a step that already writes the shared files, with the Service behind one of the two suspended (#1562), and it leaves the living spec behind the code until then. Other findings: the first archive of a capability writes `Purpose: TBD - created by archiving change ...`, which fails `validate --specs --strict` until someone edits the shared spec by hand, and a `MODIFIED` requirement needs a spec that already exists, so `openspec/specs/` starts empty and an existing system is specified one touched capability at a time unless it is backfilled. The conflicts behind the issue were `Part of #N` pull requests sharing one task file (#1750, #1725), and a change folder shared by several pull requests would conflict the same way. One pull request per issue, which #1750 decides, removes them without a tool.
- **Trial.** The delivered item #1805 (the release job stops when its tag is on another commit, #1809) was specified again as an OpenSpec change in a scratch repository, so its task file and fragment are the comparison. A person or agent writes the artifacts: the CLI scaffolds the folder and prints instructions, and `validate` checks structure, not meaning or the code. The four artifacts took 73 lines and 555 words (proposal 185, spec delta 146, design 130, tasks 94), 569 words with the generated README, in a folder of six files with `.openspec.yaml`, against one task file of 15 lines and 303 words. The fragment (2 lines, 48 words) is needed either way. `validate --strict` passed and archive wrote `openspec/specs/release-publishing/spec.md`. The item still needed its changelog fragment and its closing keyword, and under today's readiness its task file, so the folder is additive. Delivered as an OpenSpec change, the item adds 8 files: the six of the archived folder (`.openspec.yaml`, `README.md`, `proposal.md`, `design.md`, `tasks.md` and the spec delta `specs/release-publishing/spec.md`), the living spec `openspec/specs/release-publishing/spec.md` that archive wrote, and the fragment `changelog.d/1805.md`. Delivered as it was, it added 2: the task file `docs/agent/tasks/task-1805-release-tag-guard.md` and that fragment. With the task file that readiness still requires, the OpenSpec way is 9 files against 2. Friction: naming a durable capability with no inventory to reuse; the spec scenarios restate the task file's description and the test; `design.md` is optional but restates the context; Purpose is a placeholder; and the dated archive folder carries no issue number. Wall time of the tool was small (install 2 s, init 0.24 s) and is not the cost; the artifacts were written directly from the CLI's printed instructions, not through an agent's `/opsx:propose` run, so the effort is counted in files and words, not minutes.

## Trial

Every command ran in directories under `/tmp`, with `HOME` and `XDG_CONFIG_HOME` inside the scratch tree, `DO_NOT_TRACK=1`, `OPENSPEC_TELEMETRY=0` and `OPENSPEC_NO_UPDATE_CHECK=1`, a git identity of `Trial <trial@example.com>`, Node 24.22.0, npm 11.19.1 and git 2.55.0. No global OpenSpec config was written, so no anonymous id was created. The registry and GitHub were read through their public metadata only.

```
npm view @fission-ai/openspec --json
devops gh api repos/Fission-AI/OpenSpec   # also /contributors, /commits, /releases
npm install --save-exact --ignore-scripts @fission-ai/openspec@1.14.3   # and @1.13.2 in another directory
npm audit signatures   # also reads Sigstore's public trust root
openspec init --tools claude,gemini,github-copilot --no-copilot-cloud --no-animation
openspec new change release-tag-guard --description "..."
openspec validate release-tag-guard --strict
openspec archive release-tag-guard --yes
openspec validate --specs --strict      # fails: Purpose is still a placeholder
openspec new change fix-a-typo-in-docs  # validate --strict fails until skip_specs: true
openspec init --tools agents,codex,cursor --no-animation   # in a repository with AGENTS.md and CLAUDE.md
git merge   # two archived changes to one capability: CONFLICT; two unarchived, archived in turn: clean
```

## Considered Options

- **Adopt OpenSpec and retire the task files** (the issue's proposal): rejected for the reasons above. The migration is large, and the result adds files to every item, repeats the issue and the tests, and brings a shared file that conflicts.
- **Adapt: keep the task files and add OpenSpec's `openspec/specs/` as a behaviour layer**: rejected. `validate` checks a spec's structure, not the code, and AGENTS.md already makes the tests the contract (test-first development), so the spec would be a prose copy of them that nothing keeps in step. It also brings the shared-file conflict, the Purpose placeholder and the unpinned-tool cost without retiring anything.
- **Adapt: take only its proposal, design and tasks layout into the task file**: left to #1750. Which per-change records stay in the repository is that issue's question, and a layout change inside one file needs no tool.
- **Wait for #1750 before deciding**: rejected. The rejection holds either way. If #1750 drops in-repo records, OpenSpec would add records where there are none. If it keeps them, they stay task files unless a revisit condition below holds.
- **Reject** (chosen): the issue, the task file and the changelog fragment stay the record of a change.

## Consequences

- Nothing changes in AGENTS.md, in readiness (`devops pr check-readiness`), in the closing comment or in the task-file tests. The pull request adds this ADR, `docs/agent/tasks/task-1753-openspec-evaluation.md` and `changelog.d/1753.md`.
- Had it been adopted, everything that reads, checks or prescribes the task files would have been rewritten. On 2026-10-22 `git grep -l 'agent/tasks' -- src tests` finds 11 files (4 in `src/`, 7 in `tests/`), and a search of the same trees for the path constants and the words "task file" finds the others, which reach the directory without naming it. The total is 10 files in `src/devops_cli/`, 7 test files with one fixture, and 14 documents:
  - *Readiness.* `src/devops_cli/commands/pr.py`: `_base_has_task_files` lists `docs/agent/tasks` at the base, `_writes_task_file` and `_changes_its_task_file` require the pull request to change the file of its one issue, and the `check-readiness` help says so. `grounding_task_file_missing` in `src/devops_cli/lang/en/messages.py` is the blocker text.
  - *Closing comment.* `task_files` and `acceptance_criteria` in `src/devops_cli/roadmap/close.py` read the file at the merge commit and quote its `## Acceptance Criteria`, and `src/devops_cli/roadmap/request_plan.py` plans that read. `close_criteria_heading`, `close_comment_task`, `close_comment_no_criteria`, `close_comment_no_task` and the `task_file` plan condition in `messages.py`, and the `roadmap close` help in `src/devops_cli/lang/en/help.py`, word it.
  - *Constants and review routing.* `CONST_AGENT_TASKS_DIR`, `CONST_AGENT_TASK_FILE_RE` and `CONST_REVIEW_ROUTED_PATH_PATTERNS` in `src/devops_cli/config/constants.py`. The last keeps `docs/agent/tasks/**` off review blocks, through `is_secret_scan_only` in `src/devops_cli/review/targets.py`, which `src/devops_cli/ai/review/runner.py` and `src/devops_cli/review/diff.py` call and which need no edit.
  - *Generated and taught instructions.* `src/devops_cli/ai/instruction_generator.py` writes two lines that name `docs/agent/tasks/` and the task file's `**Feasibility**` field into the `AGENTS.md` that `devops ai agents` generates. The knowledge base guides `src/devops_cli/ai/knowledge_base/devops_cli/tasks/ai_code_review.md` (path routing, and "Modular Task Tracking Architecture") and `github_project_management.md` (task files carry no status) teach the same rules to the review and the chat.
  - *Tests.* Four test files depend on the layout: `tests/test_agent_task_files.py` (parses every task file against the contract, with the 488-line `tests/fixtures/task_files_baseline.txt`), `tests/test_pr_cmd.py` (readiness, and the pull request template's task path), `tests/test_roadmap_close.py` and `tests/test_review_path_routing.py`. Three only carry a task path as sample data or message text, so an adoption would touch their wording and not their logic: `tests/test_roadmap_github_store.py` (the files of a merged pull request), `tests/test_architectural_invariants.py` (two assertion messages) and `tests/test_consolidation_security_sanitizer.py` (names that secret masking must leave alone).
  - *Documents.* Eight are written by hand: AGENTS.md, `.github/pull_request_template.md`, CONTEXT.md, `docs/SDLC.md`, `docs/ROUTINE_TASKS.md`, `docs/SELF_IMPROVEMENT.md`, `docs/agent/README.md` and `docs/agent/tasks/README.md` (the template). Six are generated from the help text and docstrings above by `devops docs generate --sync-readme`: README.md, `docs/CLI_REFERENCE.md`, `docs/MCP_TOOLS.md`, `docs/commands/gh.md`, `docs/commands/pr.md` and `docs/commands/roadmap.md`.
  - *The task files.* The 573 task files (3.5 MB, counting this item's own) would stay as history or be converted. A new npm kind in `tools.lock`, an archive step in the cut, and `DO_NOT_TRACK` in every agent environment would have been added.
- Anyone may try OpenSpec on their own machine. The repository takes no dependency on it and carries none of its files.
- Revisit this decision, re-running the trial against the then-current release since releases are weekly, if any of these holds:
  - #1750 decides to keep per-change records in the repository and wants a proposal reviewed before its code is written, the stage the one-pull-request flow does not have;
  - archive stops writing to a file that changes to one capability share, or the same two-archive merge test passes;
  - the repository pins npm tools for another reason, which removes the pinning cost;
  - the project decides to keep behaviour specifications apart from its tests.
