# OpenSpec is the spec and change-proposal layer

Issue #1753 asked whether OpenSpec ([Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)), a Node tool that records a change as a proposal, spec deltas, a design and tasks and archives it into a living specification, should replace the per-item task file as the record of how a change is specified and planned. The owner decided on 2026-10-22 that it does, so that project planning is consistent across agent workflows: Claude Code, Gemini CLI and Copilot read one set of planning conventions, `openspec/config.yaml`, through one command, `openspec instructions`, and every item is planned as the same artifacts in `openspec/changes/<issue>-<slug>/`. The in-cluster roadmap jobs join that source only in the last two steps of the sequence; until then the refine job keeps its own prompt and reply schema. The project's ways of working change to fit the tool, not the reverse: AGENTS.md, the readiness check, the closing comment, the docs inventory and the tests are rewritten, the task files and the code and tests that read them are deleted, and nothing supports both systems. The tool's defects (a shared spec file that conflicts, a placeholder Purpose, silent last-write-wins between two changes, telemetry on by default, a per-user profile, generated skills that stop after planning) are met with the design decisions below, each tried against OpenSpec 1.14.3 (published 2026-10-17) in scratch repositories on 2026-10-22. The cost of rewriting our own enforcement is not a reason to keep it; Consequences lists it.

## Decision

- Every roadmap item is one OpenSpec change, `openspec/changes/<issue>-<slug>/`, committed as the first commit of the item's draft pull request: the proposal, the spec delta (or `skip_specs: true`), a design when needed, and the tasks.
- The living specification, `openspec/specs/<capability>/spec.md`, is written only by `openspec archive`, which the pull request that closes a change runs for its own folder, as its last commit. A pull request that says `Part of #<issue>` archives nothing.
- `openspec/config.yaml` carries the planning conventions for every agent, and skills-only delivery of a `custom` profile (propose, explore, apply and update; `--tools claude,agents`: eight identical `SKILL.md` files, no archive or sync skill) gives every agent the same entry points. An agent with a single turn runs the `openspec` commands the skills call, because a generated skill stops after planning.
- OpenSpec 1.14.3 is an `npm` tool pinned in `tools.lock`, installed with `npm ci` from a lockfile, run with telemetry off, audited by the `audit` row of `devops ci` and validated by one `openspec` row.
- Readiness (which also refuses a closing pull request with an unticked task, or whose folder is not archived), the closing comment and review routing read change folders by path. The task files, their tests and the code that reads them are deleted in one switch.
- AGENTS.md is rewritten (Rules That Change) and ends at 39,984 of its 40,000 characters.

## Evaluation

Evidence from 2026-10-22, against OpenSpec 1.14.3, in directories under `/tmp` with `HOME` and `XDG_CONFIG_HOME` inside the scratch tree, the opt-outs set, and a git identity of `Trial <trial@example.com>`. Each defect found is followed by the decision that resolves it.

- **Health (question 1).** MIT licensed: the [registry entry](https://registry.npmjs.org/@fission-ai/openspec), the GitHub API and the [`LICENSE`](https://github.com/Fission-AI/OpenSpec/blob/v1.14.3/LICENSE) in the package agree. `@fission-ai/openspec` has 54 versions since 2025-09-06, 1.0.0 on 2026-01-26, and 12 releases from 1.8.0 (2026-08-05) to 1.14.3 (2026-10-17), about one a week, each with notes on the [releases page](https://github.com/Fission-AI/OpenSpec/releases); the cadence was uneven earlier (no release from 2026-02-23 to 2026-04-11, nor from 2026-04-21 to 2026-06-01). The repository (created 2025-08-05) is not archived, was pushed to on 2026-10-21, and shows about 72.7k stars. The package has one npm maintainer account, and the top two of 147 contributors hold 71% of the contributions. Registry signatures verified for all 57 installed packages, 22 with attestations, `npm audit` found nothing, and the repository's own osv-scanner read the lockfile (57 packages, no issues). This meets the policy of reputable, maintained dependencies. *Resolved by:* weekly releases make a bump a recurring chore, so a bump is one deliberate pull request with a runbook, and Renovate's `npm` manager is disabled (it can edit neither `tools.lock` nor the generated files, and no pull request by Renovate was found). A bump rewrites the eight `SKILL.md` files the project generates (18 insertions and 16 deletions from 1.14.2, 48 and 34 from 1.13.2), because each embeds `generatedBy` and the instructions move.
- **Runtime and pinning (question 1).** It needs Node 20.19 or later. The devcontainer's `node` feature floats to LTS (24.22 today), and the repository has no `package.json`, lockfile or npm step. `npm install --ignore-scripts` of the pin added 57 packages (12 direct dependencies, 11 MB apparent size, 2,094 files) in 2 s, and the package declares no install scripts. The root tarball's sha512 covers 1 of the 57 packages and 11 of the 12 direct dependencies are caret ranges (`cross-spawn` is an exact pin): the same pin resolved on 2026-10-17 differs in 12 `@inquirer/*` packages from the resolution of 2026-10-22. `tools.lock` has binary and Python kinds only. *Resolved by:* an `npm` kind whose integrity data is a `package-lock.json` beside the lock. `npm ci` checks the sha512 of every package: one flipped integrity character failed with EINTEGRITY (and left a partial `node_modules` when the package was the first or the last in the lock, which is why the installer stages the install and renames it only on success), and two clean installs gave the same tree hash.
- **Telemetry (question 1).** On by default, and observed, not only read from the source (a request log in an empty network namespace): in text mode `validate`, `list`, `update` and `version --check` each tried to POST to the PostHog proxy at `edge.openspec.dev` on every run, and `update` and `version --check` also asked `registry.npmjs.org`. `--json` sent nothing. `DO_NOT_TRACK=1`, `OPENSPEC_TELEMETRY=0` or a truthy `CI` stop both requests, `OPENSPEC_NO_UPDATE_CHECK=1` alone stops only the update check, and `openspec config set telemetry.enabled false` run without one of them first sends one event. `devops` builds a sanitized child environment: with `DO_NOT_TRACK` and the `OPENSPEC_*` variables set in the parent, the child saw none of them. *Resolved by:* the opt-outs are set explicitly wherever the tool runs (Design, Telemetry and regeneration).
- **ADR 0001 (question 2).** It fits. `.openspec.yaml` holds the schema name, the creation date and, when set, `skip_specs`; it has no status, milestone, priority, issue number or pull request, so [ADR 0001](0001-github-is-the-roadmap-source.md) is not contradicted. The issue keeps status, milestone, priority, the discussion and the refine plan; the folder holds what the task file holds today: why, behaviour, design and tasks. The folder name is the only link to the issue: `openspec new change 1900-widget-export` is accepted (uppercase and underscores are refused), and an unknown key in `.openspec.yaml` is a warning that `validate --strict`, which the gate runs, turns into a failure (the message says to prefix a tool-specific key with `x-`).
- **Task files (question 3).** A change carries everything a task file carries. What its lifecycle and the rules around the task file imply is settled as follows.
  - *Lifecycle.* Propose-then-apply writes unticked tasks before the code, which the old rule (a task file is written only by the delivering pull request, as it will read merged) did not allow. *Resolved by:* the plan is the first commit of the draft pull request and is reviewed there, and the rule is kept in a new form: every statement in the folder is true of the tree at merge, a tick means the work is in the merged tree, and the closing pull request leaves nothing unticked. Archive does not replace the rule; it moves a complete folder.
  - *Readiness and closing.* `_writes_task_file` and `_changes_its_task_file` in `src/devops_cli/commands/pr.py` require a task file named for the issue, and `acceptance_criteria` in `src/devops_cli/roadmap/close.py` quotes its `## Acceptance Criteria`. *Resolved by:* both read the change folder by path (Design, Readiness, closing and the roadmap jobs).
  - *Items without behaviour.* `openspec validate --strict` refuses a change with no spec delta unless its `.openspec.yaml` sets `skip_specs: true`. *Resolved by:* that flag is the declaration, made in the proposal and reviewed on the draft pull request, for a change that alters nothing a consumer observes: a test, a CI workflow, documentation or a refactor that keeps behavior. This repository's product is tooling, so a `devops` command, option or message, a manifest and a service's behavior are observable and carry a delta. Read by title, 23 of the 54 task files added since v0.2.37 are of the first kind (tests, CI workflows, dependency and image pins, and documentation) and would set it (43%); the other 31 change CLI, review, service or manifest behavior. The archived `.openspec.yaml` files give the counts.
  - *Weight.* See the trial: a folder of 569 words against a task file of 303. The folder also replaces the refine plan's copy in the repository and carries the acceptance criteria as scenarios; `design.md` is optional, and a new change is only `.openspec.yaml` until its artifacts are written.
- **Agents (question 4).** Skills are the open Agent Skills format. Gemini CLI reads them from `.agents/skills` (or `.gemini/skills`) and Claude Code from `.claude/skills`; GitHub documents `.github/skills`, `.claude/skills` and `.agents/skills` as the project skill paths for Copilot and says the supported locations depend on the surface (documentation read on 2026-10-22). `openspec init --tools claude,agents` with delivery `skills` and a `custom` profile of four workflows, propose, explore, apply and update (`openspec config set profile custom`, then `openspec config set workflows '["propose","explore","apply","update"]'`), writes 12 files, 127 KB: two trees of four `SKILL.md` that are byte-identical, `.agents/skills/.openspec-target`, `openspec/config.yaml` and two `.gitkeep`. The `core` profile adds the sync and archive skills, which write `openspec/specs/`; item pull requests must not, so the project does not generate them. Initialising `claude`, `gemini` and `github-copilot` writes 21 files with commands only and 39 with commands and skills, and a different slash spelling per tool; agents call skills by name, so the commands are not generated. Every skill calls `openspec instructions <artifact> --change <n> --json`, which injects `context` and the artifact's `rules` from `config.yaml`: markers put in the file appeared in the output for proposal, specs, design and tasks (rules only for their own artifact) and as guidance for apply and archive, and in none of the generated skills, so editing a convention regenerates nothing. `init` left `AGENTS.md` and `CLAUDE.md` untouched. A generated skill stops after planning (the propose skill says "Do not start implementation in the same response" and "Wait for a new user request"), asks the user when a request is ambiguous, and has no branch for a missing `openspec` binary; `openspec instructions ... --json` carries none of that, so an agent with a single turn uses the commands (Design, Agent files). Not verified: that Gemini CLI and Copilot follow `config.yaml` rules (only that the instructions carry them), which Copilot surface reads which skill path, and how Copilot treats identical skills found in two trees.
- **Conflicts (question 5).** A folder per issue does not conflict: two unarchived changes on two branches merged cleanly, and ticks in different `## <n>.` groups of one `tasks.md` merge in every combination tried (adjacent lines conflict). Archive does conflict: two changes that each added a requirement to one capability, archived on their own branches from one base, gave `CONFLICT (content)` in `openspec/specs/<capability>/spec.md`. A union merge driver merges two `ADDED` cleanly but interleaves two edits of one requirement, duplicates its scenario, and still passes `validate --strict`. *Resolved by:* the pull request that closes a change archives it, and a conflict in `spec.md` stops the second of two such pull requests until its author updates the branch, resolves the conflict and keeps both requirements (Design, Archive in the closing pull request).
- **Trial.** The delivered item #1805 (the release job stops when its tag is on another commit, #1809) was specified again as an OpenSpec change, so its task file and fragment are the comparison. The four artifacts took 73 lines and 555 words (proposal 185, spec delta 146, design 130, tasks 94), 569 words with a generated README, in a folder of six files against one task file of 15 lines and 303 words; the fragment (2 lines, 48 words) is needed either way. `validate --strict` passed and archive wrote the living spec. The folder is the heavier artifact, and the owner accepts that weight for one planning format across agents. Friction, each answered: naming a capability with no inventory (`config.yaml` says to run `openspec list --specs` and reuse one); scenarios that restate the description and the test (it says to write only scenarios a test can assert offline); a placeholder Purpose (the delta that creates a capability starts with one, and `validate --all --strict` fails a spec that keeps the placeholder); a dated archive folder with no issue number (the `<issue>-<slug>` name keeps it: `2026-10-22-1900-widget-export`).

## Trial

Every command ran in directories under `/tmp`, with the opt-outs set, Node 24.22.0, npm 11.19.1 and git 2.55.0. The registry and GitHub were read through their public metadata only.

```sh
npm view @fission-ai/openspec --json
devops gh api repos/Fission-AI/OpenSpec   # also /contributors, /commits, /releases
npm ci --ignore-scripts --no-audit --no-fund --engine-strict --replace-registry-host=never   # from the pin's package-lock.json
npm audit signatures   # also reads Sigstore's public trust root
openspec config set delivery skills   # in an empty config, with telemetry.enabled false
openspec config set profile custom
openspec config set workflows '["propose","explore","apply","update"]'
openspec init --tools claude,agents --no-animation
openspec new change 1900-widget-export
openspec instructions proposal --change 1900-widget-export --json   # also specs, design, tasks, apply
openspec validate --all --strict      # and, as a separate run: openspec validate --archived
npm audit --package-lock-only --prefix <dir of the pin>   # no install needed
openspec archive 1900-widget-export --yes --json
openspec validate --specs --strict    # fails when Purpose is the archive placeholder
git merge   # two archived changes to one capability: CONFLICT; two unarchived, archived in turn: clean
```

## Design

- **Layout and names.** `openspec/config.yaml`; `openspec/specs/<capability>/spec.md`, written by archive; `openspec/changes/<issue>-<slug>/` with `.openspec.yaml` (`schema`, `created` and, when set, `skip_specs`), `proposal.md`, a delta `specs/<capability>/spec.md` per capability, `design.md` when the change needs one, and `tasks.md`; and `openspec/changes/archive/<date>-<issue>-<slug>/`. One folder per issue: an issue too large for its pull request is split into issues, as today. The issue number is unpadded. Each closing pull request archives one folder, so no code orders the folders. Readiness matches the active folder with a closed grammar the project defines, `openspec/changes/(?P<issue>\d+)-[^/]+/.+`, and the archived folder with a second one, because the date prefix would make the first read the year as the issue.
- **Lifecycle.** The folder is the first commit of the draft pull request and passes `openspec validate <name> --strict`; the plan is reviewed on the draft, the stage the Two-Stage PR Lifecycle already has, and the code follows on the same branch, each task ticked in the commit that completes it. A plan is not merged ahead of its code: it would sit on the release branch and ship to `main` if the item left the milestone. An item delivered as several pull requests keeps one folder. `tasks.md` has one `## <n>. <Part title>` group per pull request and each ticks only its own; part 1 carries the whole folder (it may be plan-only when parts must run in parallel) and later parts open after it merges; the closing pull request ticks its group, adds `changelog.d/<issue>.md` and archives the folder as its last commit with `openspec archive <name> --yes` (Archive in the closing pull request). An item whose earlier part merged before the switch has only a task file, deleted with the directory: its next part creates the whole folder, with the groups of the earlier parts already ticked. Work not done is a plain bullet under `## Workflow follow-up` and a check only a person can run is a plain bullet starting `Pending a person:`; OpenSpec counts neither as a task. A folder whose item leaves the release, or closes as not planned, after a part merged stays active, and deleting it is an ordinary docs pull request. A worktree on a branch that predates the scaffold has no `openspec/`, and `openspec` then takes the nearest one, the primary checkout's, and writes there: such a branch is rebased before it plans.
- **Specs start empty.** A change specifies a capability when it first touches it: ADDED requirements, and a `## Purpose` of at least 50 characters in the delta that creates the capability, so archive never writes `TBD`. A capability that another active change creates is extended with ADDED requirements and no Purpose of its own, because two Purposes for one capability keep the first without a signal (tried). `MODIFIED`, `REMOVED` and `RENAMED` are legal only once the capability's spec exists when the change archives (archive aborts with no file written otherwise), so a change that modifies a requirement another active change adds names that issue as a blocker and archives after it; a change that removes a capability's last requirement sets `retire_capabilities: true`. There is no bulk backfill of the code's behaviour. `skip_specs: true` is for a change that alters no behavior a consumer observes: a test, a CI workflow, documentation or a refactor that keeps behavior. This repository's product is tooling, so a `devops` command, option or message, a manifest and a service's behavior carry a delta. There is no list of exempt kinds; the author declares it with the reason in What Changes, the draft pull request reviews it, and no open tool links a delta to code, so review is the only check that a behaviour change was not mislabelled.
- **Archive in the closing pull request.** Change folders are the fragments of the living spec. A pull request that says `Closes #<issue>` runs `openspec archive <name> --yes` for its own folder as its last commit, with every task ticked, and commits the result; the `openspec` row of `devops ci` passes on the result. A pull request that says `Part of #<issue>` archives nothing, and its folder stays in `openspec/changes/`. The tool writes the date prefix (tried against 1.14.3: `archivedAs: 2026-10-22-1912-export-widgets`). `--yes` archives a change with unticked tasks and only warns, so check 2 of the gate (`validate --archived`) fails that archived change. No `--skip-specs` is passed, since a `skip_specs` change archives without it. The release cut does not archive, and `cut_release` and `_cut_makes` hold no OpenSpec code. Two pull requests that archive into one capability conflict in `spec.md` after the first merges. GitHub blocks a merge with a text conflict, so the second author updates the branch, resolves the conflict and keeps both requirements. The `main` ruleset also has the strict up-to-date policy, which binds once ADR 0012 lists the required checks. The generated skills already tell an agent to run `openspec archive` when every task is done. Archiving costs 0.3 to 0.8 s per change (0.27 to 0.75 s across three runs on 16 cores).
- **One gate.** A `devops ci` row `openspec` runs `uv run devops openspec check`, a small module that runs the pinned tool, with the opt-out environment (Telemetry and regeneration), for five things. (1) `openspec validate --all --strict`, in which an unknown key in `.openspec.yaml` is a failure. (2) `openspec validate --archived`, a separate run because `--archived` replaces `--all` instead of combining with it, which fails an archived change with unticked tasks. (3) A regeneration of the skill files with `openspec update --force` under the isolated config described below, in a temporary copy, compared with the tree: the tool has no project-level profile pin, and a developer's wider global profile rewrote six of the eight skill files and added the archive and sync skills and a commands tree. A skill tree deleted whole is a finding as well, because `openspec update` finds an agent by the skills it holds and wrote nothing where none exist (tried: 1.14.3 printed "No configured tools found"), so the gate fails any glob of the generated files that matches no file and says to restore it from git. (4) `openspec instructions` for the proposal, specs, design, tasks and apply operations of a probe change in that copy, failing on any output to stderr, where the tool reports with exit 0 a mapping-shaped rule, a rule under an unknown artifact id and a context over 50 KB. (5) The overlap check: it reads `openspec show <name> --json --deltas-only` for each active change and fails when one (capability, requirement) is `MODIFIED`, `REMOVED` or `RENAMED` by two active changes, because the later archive overwrites the earlier with no signal (tried: both archive, the spec keeps one text, and neither `validate` nor `doctor` said so). It is the one piece of bespoke code the lifecycle needs besides the module itself: OpenSpec's bulk-archive conflict detection is an agent skill, not a command, so no open tool does it, and the check is deleted when one does. A clash is fixed by folding the two items or by ordering them by a blocker, so that the second waits until the first archives. The gate does not rehearse `openspec archive`, because the cut no longer archives. A rehearsal per change would fail a change that modifies a requirement another active change adds, until that change archives. Three cases then show only in the closing pull request, where the author fixes them in the same commit. A missing Purpose: archive exits 0 and writes a placeholder, which check 1 fails on the archived spec. A `MODIFIED` of a spec that does not exist: archive refuses it and changes no file. A duplicate `ADDED`: archive refuses it and changes no file. The gate reads one pull request's tree, and the release ruleset requires no status check (its rules are `non_fast_forward`, `pull_request`, `code_scanning`, `code_quality` and `code_coverage`, so ADR 0004 is not applied to it) while CI does not run on a push to a release branch: two separately green pull requests can merge into a red release tip. The repair is a fix item whose pull request folds the clashing changes. Across three runs on 16 cores `validate --all --strict` took 0.4 to 1.5 s with 40 to 50 changes and 1.7 to 5.5 s with 600, beside a 300 s test row, so the row runs in every `devops ci` and in the `static` job with no path filter and no exemption. The `static` job uses the default checkout, because the gate reads no git history. A pre-commit hook runs `uv run devops ci --only openspec` with `files: ^(openspec/|\.claude/skills/|\.agents/skills/)` and `pass_filenames: false`. Diagnostics read `cap-000/spec.md: ...` with no line number, which does not meet the `file:line` convention; a parser for them would be new machinery, so they stay as they are.
- **Delivery.** `tools.lock` gains an `npm` kind. `[npm.openspec]` pins 1.14.3 beside `src/devops_cli/tools_lock/openspec/package.json` (the exact version) and `package-lock.json` (57 packages, all sha512, all on `registry.npmjs.org`, none with an install script), and `tools_lock_digest()` covers both. `devops install-tools` stages beside the version directory, copies the two files and two empty npmrc files, runs `npm ci --ignore-scripts --no-audit --no-fund --engine-strict --replace-registry-host=never` in the sanitized environment plus an explicit `npm_config_cache`, `npm_config_userconfig` and `npm_config_globalconfig` (npm refuses user and global config that are one file, and a configured registry would otherwise rewrite the lock's URLs), renames into `<user_data_root>/tools/openspec/1.14.3` and links `node_modules/.bin/openspec` into `~/.local/bin`. `devops devcontainer post-create` (the devcontainer's `postCreateCommand`) already installs every lock tool, and the prototype took 4.9 s cold. It reports a failed bootstrap, a missing `npm` or a failed `npm ci`, as a warning, so the hard failure is `devops install-tools`, which fails early with `require_binary("npm", ...)` since the installer provisions no runtime, Python's included, and the gate row. `.node-version` holds `24`, the devcontainer's `node` feature is pinned to `24`, a contract test keeps the two equal, and CI's `static` job runs `actions/setup-node` pinned to v7.1.0 (`949feb2413d6458794dcd2491c4babbbce0c15c1`, resolved with `devops gh api`) and `uv run devops install-tools --tool openspec --only-missing` before the gate. The `audit` row of `devops ci` gains `npm audit --package-lock-only --json --prefix src/devops_cli/tools_lock/openspec` beside `uv audit` (tried against the pin: no vulnerabilities, no install needed), so a vulnerable pin fails the gate; nothing signals a stale one. npm exits 1 for a finding and for an audit that could not run, such as an unreachable registry, so each command is read by its own signal: uv by its exit status (1 against 2), npm by its JSON report (`metadata.vulnerabilities` counts against an `error` object). The bump runbook in the `tools.lock` header: set the version in `tools.lock` and `package.json`; run `npm install --package-lock-only --ignore-scripts`; run `uv run devops openspec regenerate` and commit the skills; run the gate; run `npm audit signatures` and `osv-scanner scan source --lockfile package-lock.json`; run the lock and installer tests; run `devops install-tools --check`. The pin never goes below 1.14.3, which fixes `validate --all` hanging under pre-commit (from its release notes; not reproduced). The `Dockerfile` service stage gains a digest-pinned Node stage and `npm ci --ignore-scripts` from the same lockfile (step 6), because the refine job of step 8 runs `openspec instructions` there when the roadmap Service runs (#1562 suspends it).
- **Where the binary comes from.** The devcontainer gets it from post-create and CI's `static` job from its install step. The Copilot cloud agent gets it from `copilot-setup-steps.yml`, which GitHub runs only from the default branch: until the release that carries the file merges to `main`, that agent finds the committed skills and no binary. Claude Code in the cloud and a Gemini CLI host shell get it from `uv run devops install-tools --tool openspec --only-missing`, which needs Node 24, and AGENTS.md says so. Every generated skill starts with `openspec list --json` and has no branch for a missing binary, so AGENTS.md also tells an agent that cannot install it to write the artifacts by hand from `openspec/config.yaml`, and CI validates them.
- **Telemetry and regeneration.** Telemetry is off in every environment. The gate and hook module sets `DO_NOT_TRACK=1`, `OPENSPEC_TELEMETRY=0`, `OPENSPEC_NO_UPDATE_CHECK=1`, `OPEN_SPEC_INTERACTIVE=0` and `XDG_CONFIG_HOME` in the child's environment (the `env` argument of `run_subprocess`, not `extra_allowed_env`, which only keeps a variable the parent already has), because the sanitized child environment of `devops` (the allowlist in `src/devops_cli/core/process.py`) keeps `HOME` and `CI` but none of these, and without `XDG_CONFIG_HOME` the tool would read the developer's real `~/.config/openspec`. The devcontainer sets `OPENSPEC_TELEMETRY=0` and `OPENSPEC_NO_UPDATE_CHECK=1` beside its `DO_NOT_TRACK=1`, and its template and test follow. CI sets `DO_NOT_TRACK: "1"` at the top of the workflow, though the runner's `CI=true` already suffices. The committed `.claude/settings.json` gains an `env` block with the same variables. A host shell or another agent's cloud environment runs `OPENSPEC_TELEMETRY=0 openspec config set telemetry.enabled false` once, a person step, with the prefix, since the command sends an event first. The skills are regenerated only against an isolated config: `uv run devops openspec regenerate` makes a temporary `XDG_CONFIG_HOME`, sets `telemetry.enabled false`, `delivery skills`, `profile custom` and the four workflows in it, and runs `openspec update --force` in the tree (which changed no file on a second machine; the same command under the `core` profile would also add the archive and sync skills); a bare `openspec update` is forbidden because it takes the user's global profile.
- **Agent files and `openspec/config.yaml`.** The generated skills are committed: a cloud agent or fresh clone never runs an install but reads the checkout. `.gitignore` re-includes only `.claude/skills/openspec-*/` (`!.claude/skills/` then `.claude/skills/*` then `!.claude/skills/openspec-*/`, tried: other skills, `settings.local.json` and `worktrees` stay ignored). A hermetic test requires `metadata.generatedBy` in all eight `SKILL.md` to equal the pin, and the two trees to be identical. The `.claude/settings.json` allowlist gains the verbs the four skills call (`openspec status`, `list`, `instructions`, `context`, `show`, `schemas`, `validate` and `new change`), and no bare `Bash(openspec *)`. ## Considered Options

- **Adopt OpenSpec and delete the task files** (chosen): one planning format that every agent reads from one place, at the price of a Node tool, a lockfile, a gate and a one-time rewrite of our enforcement.
- **Adopt OpenSpec beside the task files**: rejected. Two sources of truth for one item are what the owner wants removed, every agent would still learn the home-grown format, and the readiness check, the closing comment and the tests would each read both.
- **Keep the task files**: rejected. Planning stays a format every agent must learn from AGENTS.md, and the task file keeps conflicting when several pull requests touch one item (#1750).
- **Wait for #1750**: rejected. #1750 decides one pull request per issue and which records stay in the repository. The owner's reason does not depend on the answer: if #1750 drops in-repo records, the folder is the only one, and if it keeps them, they take OpenSpec's format. This ADR settles only the planning record. If #1750 retires `Part of #N`, the multi-pull-request rules in AGENTS.md and the task-group rule in `openspec/config.yaml` are deleted and nothing else here changes.
- **Archive in the pull request that closes the change** (chosen, owner, 2026-10-22): the spec changes with the code that changes it, and no code orders the changes. Archive writes `spec.md`, which conflicts when two archived changes touch one capability. The conflict stops the second merge until its author resolves it. A union merge driver is not used, because it hides a lost edit.
- **Archive at the release cut, serially in merge order**: rejected (owner, 2026-10-22). It needs code that orders the folders by the commits that added them, a rehearsal of that order in the gate, a full-history checkout in CI and an archive step in the cut, which ADR 0012 removes. Archiving a change that `MODIFIED` a requirement before the change that `ADDED` it aborts with nothing written (tried), so a change archives after the change it depends on.
- **The `core` profile with the archive and sync skills**: rejected. Those skills write `openspec/specs/`, which only the pull request that closes a change may; the `custom` profile of four workflows omits them, and readiness stays the backstop for a hand-run `openspec archive` in another pull request.
- **A forked schema with a `feasibility` artifact**: rejected. `openspec schema` is experimental and a fork drifts from every weekly template change; the heading test enforces the section, and `validate --strict` reads no proposal prose.
- **A root `package.json`, a global install or `npx`**: rejected. The first is a second install path outside `tools.lock` with a 2,094-file `node_modules` at the root, the others float.

## Revisit Conditions

Revisit this decision, re-running the trial against the then-current release, if any of these holds:

- OpenSpec adds a deterministic check for two changes that edit one requirement, or a project-level profile and delivery pin, which would let us delete the overlap check and the isolated regeneration;
- OpenSpec stops releasing for 90 days, changes its license, turns on an install script, or makes telemetry impossible to switch off by environment;
- the gate, run beside the 300 s test row, becomes the slowest row (`validate --all --strict` took 1.7 to 5.5 s with 600 changes);

## Decisions Taken

Two decisions the sequence depends on, confirmed by merging this ADR and reversible by a later ADR:

- **The switch lands in the release after the one that holds steps 1 to 3**, as that release's first item pull request. Landing it in v0.2.39 instead would convert that release's task files by hand (27 had been added or changed at `b2d362ff`) and delay the release's other items.
- **The roadmap Service image carries Node**: a digest-pinned Node stage and `npm ci` from the same lockfile (about 138 MB apparent size: the 127 MB `node` binary and 11 MB of packages), so the Service can run `openspec instructions` for the refine job of step 8 once #1562 is reverted. The alternative, a Service image without Node, leaves step 8 with no `openspec`.
