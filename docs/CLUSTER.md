# devops-cli in the cluster

This document tells how devops-cli runs in a Kubernetes cluster: the roadmap Service, its runner Jobs, the services that it calls, and how its images are pinned and updated. [k8s/README.md](../k8s/README.md) tells how to set up the cluster: its stacks, its Secrets, its alerts and Argo CD. [docs/SRE.md](SRE.md) sets the SLOs of these services, their incidents, backups and capacity, and the gaps with their issues.

`k8s/devops/` runs devops-cli as cluster Jobs, so agents drive it with kubectl and never handle keys. It is managed by `devops k8s deploy-stack --stack devops` (and `--stack all`), the only command that creates its ConfigMap `devops-cli-config`, which it renders from `config.yaml`; `devops k8s apply k8s/devops/ --template` applies the rest without it, and the pods wait for that ConfigMap. Each Job reads its credentials from Secret `devops/devops-cli` through `envFrom`, its configuration from ConfigMap `devops-cli-config` (provider `gateway` at `http://llm-gateway.llm.svc.cluster.local:4000/v1`), holds no Kubernetes API token, accepts no ingress, and reaches only DNS, the gateway, the OpenTelemetry collector in namespace `otel`, public HTTPS and the MCP server (TCP 8001, by the policies `mcp-server-ingress` and `mcp-server-clients`). Commands that need Qdrant, Prometheus, Grafana, Argo CD or a repository checkout do not run there yet.

```bash
devops config set service.repos <owner/name>             # the repositories the service works for
devops config set service.github_app.app_id <app-id>    # the GitHub App the jobs act as (ADR 0015)
devops config set service.github_app.installation_id <installation-id>
devops config set service.github_app.slug devops-cli-service
devops config set service.github_app.private_key --from-file <key.pem>
devops k8s deploy-stack --stack devops --context <context>
devops k8s push-secrets --context <context> --plan       # reads the keyring and the cluster: key names and states, never a value
devops k8s push-secrets --context <context>
devops k8s run-job --context <context> -- --version      # follows the log, exits with the Job's exit code
devops k8s run-job --context <context> --no-wait -- ai gateway status --format json
```

`run-job --dry-run` reads nothing, not even the CronJob, and prints the kubectl requests a run would make. `run-job` creates the Job from suspended CronJob `devops-cli` (`--template default`) or, with `--template runner`, from suspended CronJob `devops-cli-runner` (Runner Jobs), changing only the container's args, the name (`devops-cli-<UTC time>-<hex>`, and `devops-cli-runner-<UTC time>-<hex>` for a runner Job) and the label `app.kubernetes.io/name: devops-cli-job`. A Job never retries (`backoffLimit: 0`), stops after two hours and is deleted a day after it finishes. Follow or clean up Jobs with kubectl:
```bash
kubectl -n devops get jobs -l app.kubernetes.io/name=devops-cli-job
kubectl -n devops logs -f job/<name>
```

The spans and the log records of devops-cli name the cluster in `k8s.cluster.name` and the namespace in `k8s.namespace.name`. The tracer reads them from the environment values `K8S_CONTEXT` and `POD_NAMESPACE`. With no `K8S_CONTEXT`, it uses the setting `k8s.context`, whose default is `minikube`. So each devops-cli container in `k8s/devops/` sets `K8S_CONTEXT` to the cluster name of the monitoring stack (`cluster.name` in `k8s/monitoring/k8s-monitoring-values.yaml`) and `POD_NAMESPACE` to the namespace of its pod, from the Downward API. The runner template `devops-cli-runner` sets the namespace as a plain value, because the admission policy `roadmap-service-jobs` refuses `valueFrom` in a Job of the Service. The check `tests/gate/k8s_checks/telemetry_resource.py` of the `k8s` row of `devops ci` fails when a container does not set both (#4512).

## Roadmap service

`deployment/roadmap-service` runs one replica. The Service acts as GitHub App `devops-cli-service`, which the personal account owns ([ADR 0015](adr/0015-roadmap-jobs-act-as-a-github-app-on-the-personal-account.md)), on each repository in `service.repos`. Labels and milestones hold the roadmap state ([ADR 0016](adr/0016-labels-hold-the-roadmap-items-fields.md)). Argo CD self-heals the deployment, so only a change in git changes its replica count. A scale by hand stays only after the stop switch turns off automated sync. The Roadmap service container `service` requests `768Mi` and limits `3Gi` of memory. The raise is a stopgap for a working set that grows 100 to 150 MiB each hour (#4116 holds the analysis, #4125 the flat check), and `RoadmapServiceMemoryNearLimit` fires before a kill.

1. Create the GitHub App on the personal account (Settings > Developer settings > GitHub Apps > New GitHub App): name `devops-cli-service`, webhook off, "Only on this account". The roadmap jobs need these repository permissions: Issues read and write, Pull requests read and write, Contents read and write, Checks read, Actions read, Metadata read, Workflows read and write, Webhooks read (the metrics row reads the deliveries of the hooks, #5017), Administration read (the `metrics` row reads the repository traffic, #4757). The owner's App has read and write on every repository permission ([ADR 0015](adr/0015-roadmap-jobs-act-as-a-github-app-on-the-personal-account.md) records the risk). Each installation token that the Service and the Jobs mint is scoped to the permissions above, whatever the App grants, so the App must grant at least those: GitHub refuses a token with HTTP 422 when the installation does not grant one of them. The token of a runner Job does not ask for Webhooks read or Administration read, because no step reads the hooks or the traffic (#5058). Install it on each managed repository, and generate a private key. The App page shows the App ID, and the installation's settings page has the installation ID at the end of its URL.
2. `uv run devops config set service.repos <owner/name>` (each repository the service works for), then `uv run devops config set service.webhook_secrets` (hidden prompt; a JSON object mapping `owner/name` to its secret). Set the App with `uv run devops config set service.github_app.app_id <app-id>`, `service.github_app.installation_id <installation-id>`, `service.github_app.slug devops-cli-service` and `service.github_app.private_key --from-file <key.pem>`, then delete the downloaded key file. deploy-stack refuses the devops stack until `service.repos` and the App's settings are set.
3. `uv run devops k8s push-secrets --stack devops`. It writes the App's private key to Secret `devops/devops-cli`. deploy-stack also pushes it once namespace `devops` exists.
4. Check that the GHCR `service` package is public (#741 made it so): `DOCKER_CONFIG=$(mktemp -d) docker pull ghcr.io/dan-petty/devops-cli/service:<tag>`.
5. `devops cloudflare tunnel routes`. If no route covers the webhook host, add one in the dashboard, not with `tunnel sync` (#794).
6. `devops cloudflare access status`, then add a Bypass application for `hooks.<domain>/webhooks/github`. Its Bypass policy must let each delivery of GitHub through. A policy that lists source ranges must hold each range of `uv run devops gh api meta --jq .hooks`: GitHub adds ranges with no notice, and Access answers a delivery from a range that the policy does not hold with HTTP 403 (#5017). `RoadmapServiceWebhookDeliveriesFailed` shows such refusals (Webhook route).
7. `devops k8s deploy-stack --stack devops` (or `--stack all`).
8. Add each repo's webhook: `https://hooks.<domain>/webhooks/github`, `application/json`, that repo's secret, and only the Issues event. The roadmap consumer takes the Issues event. An issue that opens, edits or reopens runs intake of that one issue on the triage lane at once and queues no full round. After an edit, or after intake places a critical fix or a P0 item, the Service wakes the model lane alone, so `refine` and `retitle` run at once (#4412). A label change or a close makes `refine`, `stage` and `implement` due ([ADR 0017](adr/0017-each-subscribed-webhook-event-runs-the-update-scoped-to-it.md), #1533). The 5-minute poll reconciles board edits and lost deliveries. The Service acknowledges an event with no subscriber, a push included, and starts no round for it, but each such delivery uses the rate limit of the route (Webhook route) and writes a log line. Check the hooks of each repository: `uv run devops gh api repos/<owner>/<name>/hooks --jq '.[]|{id,active,events,code:.last_response.code}'`. Each hook must be `active`, its `events` must be `["issues"]`, and after its first delivery its `code` must be 200 or 202. Change a hook in the repository's settings (Settings > Webhooks). `devops` has no command that changes a hook.
9. To rotate a credential, update it in the keyring: `uv run devops config set service.webhook_secrets`, or, for the App, generate a new private key and run `uv run devops config set service.github_app.private_key --from-file <key.pem>`. Then run `uv run devops k8s push-secrets --only devops/devops-cli --rotate`. It restarts `roadmap-service`. Delete the old private key on the App's page after the restart.
10. Run one service per set of repos. While it runs, use `devops roadmap run --dry-run` (#981).
11. The Service keeps four files in `/home/devops/.data/roadmap/` on volume `roadmap-service-home`, beside the `schedule.json` of each repository: `service-halt.json` (GitHub refused the identity), `service-budget.json` (the GitHub requests of the last hour), `service-failures.json` (the jobs that failed rounds in a row) and `service-consecutive-failures.json` (the stops in a row of the same failure class, #3069). A restart reads them back, so a restart does not clear a halt, the budget or a suspended job. Intake also keeps there the snapshot of the issue listing of each repository, `listing/<owner>/<name>.json` (#3670). The status lane keeps its own snapshot, `listing-status/<owner>/<name>.json`, so each file has one writer (#4854). A snapshot is a copy of GitHub: when you remove it, the next round of its lane reads the whole listing and writes it again. A round that ends because the Service is stopping, for example in a rollout, does not count as a failed round: the count of its job stays as it was. A job that failed `service.max_failed_rounds` rounds in a row (default 6, #4802) is suspended until its input changes, or until its retry time (#4065). The file keeps, for each job, the count, the input of the last failed round, the failure class of each failed round (the value of `FailureClass`, for example `provider`) and the retry time. The retry time is the time of the last failed round plus the wait of its class in `RETRY_AFTER` (`provider`, `plan_defect` and `ci_infra` 1 hour, `parser` 6 hours, `head_moved` none; an error that is no error of the project is `ci_infra`). After it, the job runs one probe round with the same input. A probe round that fails sets a new retry time. A probe round that works clears the entry. Only the triage lane reads changes, so the retry time changes the row `intake` alone: the rows of the status lane and of the model lane have the hour in their input, and run again each hour (#2757). The log line that suspends a job names the failure class of each of its failed rounds in a row and the retry time. An entry that an earlier version wrote has no retry time, so it stays suspended until its input changes; a round that an earlier process counted reads as `unknown`. **Rollback:** an older image cannot read an entry that has a retry time. Remove the file before you roll back: `kubectl -n devops exec deploy/roadmap-service -- rm /home/devops/.data/roadmap/service-failures.json`. The Service then counts the failed rounds again from zero. A comment of a person is new input for a job that failed a round (#2754). A person has write access (the association OWNER, MEMBER or COLLABORATOR), is no bot, and is not the account of the Service. A comment on a pull request does not count. So the answer of a person starts a suspended job again, and the job counts its failed rounds from one. A comment from before the last success of the job changes nothing. A poll with no new comment changes nothing. The Service takes no `issue_comment` event ([ADR 0009](adr/0009-one-webhook-router-delivers-each-event-to-the-consumers-subscribed-to-it.md)). A round that only polls reads the comments instead, when a job that may run failed a round before. It reads the comments of the repository from the oldest last success of those jobs, newest first. It stops at the first comment of a person, and after the newest 100 comments. So each lane that reads sends one request. A comment of a person that 100 newer comments follow does not count. The job then has the input it had before, and runs again once. A round that a webhook starts reads no comment, because the time of that round is already new input. A round with no such job, and a dry run, read no comment. At the default poll interval of 151 seconds, one repository costs at most 72 requests an hour: 3 lanes and about 24 polls. The budget `service.github_requests_per_hour` (500 by default) is for all repositories together, and it is hard, so these requests cannot pass it. They count under `row="other"` in `devops_cli_github_requests_total`, as they run outside a row. A rate limit that one request gets stops the requests of all workers until its wait ends. When GitHub refuses the identity, for example because the App's installation is suspended, the Service halts and logs `GitHub refused the identity`. To clear the halt after you fix the cause, remove the file and restart the Service: `kubectl -n devops exec deploy/roadmap-service -- rm /home/devops/.data/roadmap/service-halt.json`, then `kubectl -n devops delete pod -l app.kubernetes.io/name=roadmap-service`.
12. The Service's `/metrics` shows the budget and the suspended jobs (#2475): `devops_cli_service_budget_limit_requests` (the hourly budget), `devops_cli_service_budget_spent_requests` (the GitHub requests of the last hour, not counting the answers with status 304, which GitHub does not count against its rate limit), `devops_cli_service_budget_holds_total` (one count each time a hold begins), `devops_cli_service_job_suspended` (1 while a job of a repository, by `repo`, `row` and `class`, waits for its retry time or for new input after it failed `service.max_failed_rounds` rounds in a row; `class` is the failure class of its last failed round, or `unknown` for an entry that an earlier version wrote; when the class changes, the series of the old class is set to 0), `devops_cli_service_job_retry_after_seconds` (the seconds before the next probe round of the job, by `repo`, `row` and `class`, as of its last failed round or check; 0 when the job has no retry time; #4065), `devops_cli_service_state_unkept` (1 while the last write of a state record failed, by `record`: `budget`, `halt` or `ledger`; 0 after the next write that works; #4048), `devops_cli_service_webhook_delivery_failures` (the deliveries of the hooks of a repository that got no 2xx answer in the last 15 minutes, by `repo` and `code`, as GitHub records them; the metrics row sets it; #5017), `devops_cli_service_implement_jobs_total` (one count for each reported runner Job, by `repo`, `item_class` and `result`: `failed` for a Job that left a stop, else the state of the Job, `succeeded`, `failed` or `gone`, because a runner that writes its stop exits 0; a round also reports the Job of a closed item while the cluster holds that Job; #3069, #4703), `devops_cli_service_implement_repair_rounds_total` (one count for each repair round of a reported runner Job, by `repo` and `item_class`; #3069), `devops_cli_service_implement_tokens_total` (tokens spent by a reported runner Job, by `repo` and `item_class`; #3069), `devops_cli_service_implement_consecutive_failures` (gauge of stops in a row of the same failure `class` for `repo`, kept in `service-consecutive-failures.json`; #3069) and `devops_cli_service_implement_failures_total` (one count for each runner Job that left a stop, by the failure `class` and `repo`, when a round reports the Job; #3065; the values of `class` are the classes in [docs/ROADMAP_WORKFLOW.md](ROADMAP_WORKFLOW.md), The failure classes, and a panel or rule matches no other value, #3476). Each counter of the Service starts its label sets at zero (#3495, [docs/TELEMETRY.md](TELEMETRY.md)), except `devops_cli_service_identity_refused_total`, whose label set starts with the first refusal. Each GitHub request counts in `devops_cli_github_requests_total` under its `method`, its `status` (the HTTP status of the answer, or `none` for a gh command or an attempt with no answer), the `repo` of the worker that sent it and the job `row` (`metrics`, `intake`, `refine`, `retitle`, `stage`, `implement`, `stage_ready` or `alternatives`); a request outside a worker or a row counts as `other`. To find what spent the budget, run `sum by (repo, row, method) (increase(devops_cli_github_requests_total{job="roadmap-service"}[1h]))` in Grafana Explore. A delivery of the App bot's own write counts as outcome `self` in `devops_cli_service_webhook_deliveries_total`.
13. A refine round writes at most 2 comments on one item in 24 hours. A round that finds 2 refine comments of the last 24 hours on an item leaves the item alone, with no model call and no comment. The item waits on a person and takes no place under the round's limit, so the round refines the next item. For each newest comment on the item that the cap leaves with no answer, the round records the time of that comment in the item's job record (`refine.capped_after`), logs `Refine left #<number> alone and wrote no comment`, and adds 1 to `devops_cli_roadmap_refine_comments_capped_total`. A later round that finds no newer comment does not log or count the item again. A person refines the item at the cap with `devops roadmap refine --item <number> --confirm`. A web search asks the providers of `search.providers` in order (`searxng`, `duckduckgo`, `firecrawl` by default, #3925). A provider that is not configured is skipped: `searxng` without `search.searxng_url`, and `firecrawl` without its key. A provider that fails (a timeout, HTTP 401, 402, 403, 429 or 5xx, or a reply that is not readable) or returns no hit passes the search on at once, with no retry and no wait. The first provider with a hit answers. Each request goes through the HTTP entry point. DuckDuckGo and Firecrawl use the public level (the public HTTPS rule of policy `devops-default-perimeter`, no new rule). SearXNG sends `GET <search.searxng_url>/search` with `format=json` at the configured level: loopback, or private with `ai.allow_private_network`. The client follows no redirect and reads at most 1 MiB, and a reply with no result while an engine did not answer counts as `degraded`. An address that the egress check refuses counts as `refused` and passes the search on. Each attempt counts in `devops_cli_web_searches_total` by `backend` (a provider name, or `none`) and `result`: `ok`, `empty`, the HTTP status of a refused search, `degraded` for a reply that cannot be read, `error` for no answer, `refused` for a query that the guard stopped or an address that the egress check refused, or `exhausted` for a search that no provider answered. A failed attempt logs `A web search failed on <backend>` with the status or the error class, and never the key or the query. The guard refuses an empty query, a query over 400 characters or 50 words, a query that starts with `!` or `:`, and a query that holds a secret, an e-mail address, a private address or an internal host name; it sends no request. DuckDuckGo needs no key, so a round on a public repository has web search with the default providers. Firecrawl stays the last provider for one release cycle. When `crawl4ai.url` is set, the run also has the tool `fetch_page`, which reads the text of one page through the Crawl4AI service. It takes an https URL that a search of the same run returned or that the item text names, and no other URL; it sends no request for any other URL. A run fetches at most 3 pages. The tool frames the text as data from an outside page, never an instruction, and names the source URL and the fetch date so that a comment can cite them. A failed fetch is a tool answer and uses one fetch. Each call counts in `devops_cli_roadmap_page_fetches_total` by `toolset` (`refine` or `alternatives`) and `result` (`ok`, `refused`, `limit` or `error`). The tool is off with no `crawl4ai.url`. The tool needs the Crawl4AI service and its token. It reads pages from the web, which is new egress, so a person sets `crawl4ai.url` in the live ConfigMap to enable it.
14. The row `alternatives` of the model lane runs after `refine`: on a first run, and 719 minutes after its last success. It runs `devops roadmap alternatives --confirm` for the repository. A round checks at most `roadmap.alternatives.first_pass_limit` items (20 by default) while an item has no check, and at most `roadmap.alternatives.limit` items (5 by default) after. The row runs about twice a day, so a first pass of 141 items takes about 4 days. A round takes first the items with no check, then the items whose check is older than `roadmap.alternatives.recheck_days` (30 by default) or whose text changed. A webhook makes the row due at no other time. The row changes no label and closes no issue. It does nothing, and logs `The alternatives check of <repo> is off`, for a private repository and when no search provider is configured. If the check of an item fails, the row records the failure in the item's job record (`alternatives.failed_at` and `alternatives.failed_error`, the class of the error), writes the other checks and succeeds. The row fails, and counts toward the suspension after 3 failed rounds, only when it tried items and checked none. A round takes a failed item again after `roadmap.alternatives.retry_days` (3 by default). Each written check adds 1 to `devops_cli_roadmap_alternatives_total` by `verdict`: `covers`, `partly`, `none`, `not-applicable`, `rejected` or `in-use`. Each round also sends two gauges by `repo` at its start, before it checks any item, also when it checks none (#2950): `devops_cli_roadmap_alternatives_unchecked_items` (the items that the check can take and has no check for, an item in the retry delay too) and `devops_cli_roadmap_alternatives_oldest_check_age_seconds` (the age of the oldest check among those items, sent only while one has a check). Each written check observes `devops_cli_roadmap_alternatives_searches` by `verdict`: the searches the check ran, 0 for a skip class. The row Alternatives Check of the dashboard `devops-cli Telemetry` shows the three, and the alert `RoadmapServiceAlternativesNotSearching` warns when the Service made no web search in 3 days while an item has no check. An item of the type `test`, `docs`, `refactor`, `chore`, `ci` or `perf`, and a `fix` with a Python traceback in its body, gets `not-applicable` with no model call; every other item must run a search before the check accepts a verdict, and gets one more turn to search. Once for each round, the check reads the ADRs of `docs/adr/` that are in force. An ADR that a later ADR supersedes is left out. The model sees the number, the title, the status lines and the `Considered Options` section of each ADR. A check records the hash of these ADRs (`alternatives.adr_hash`), and an item whose hash differs from the ADRs at HEAD is checked again. The model proposes `rejected` with the number of an ADR, and `in-use` when the item names the tool. The job gives either verdict only when the text confirms it: `rejected` needs an ADR whose rejected options alone name the tool. Once for a round that checks an item of no skip class, the check also reads the SBOM of the dependency graph and the deployed paths of the lane's clone (`roadmap.alternatives.inventory_paths`), and gives `in-use` with no proposal for a tool that the repository already uses. It asks deps.dev (`api.deps.dev`) for the packages of the tool's GitHub project only when the SBOM holds a package and neither source holds the tool; a failed read skips the item. It drops a proposal that it cannot confirm and keeps the verdict of the reply. A cut by the token cap leaves out whole ADRs and logs a warning. A `covers` verdict makes refine ask a person to adopt the tool or to keep the item with a reason. A `rejected` or `in-use` verdict asks nothing. The item waits on a person until a reply answers the question, and Ready items with a new covering tool go back to New. Refine records the tool it asked about in the job record (`refine.alternatives_asked`). `devops roadmap run --dry-run` lists the row when it is due.
15. The row `retitle` is the first row of the model lane (#3535). It is due on a first run and every 61 minutes. It shortens the long title summary, or corrects the title type that the branch types do not list (#4508), of at most 25 open items, as `devops roadmap retitle --confirm` does, with the model of the `triage` task. It needs no clone, and it reads and writes only the issues of the repository. The row `stage` follows `retitle` and comes before `refine` on the model lane (#2659, #4796), so the stage job reads the new titles in the same round, and the first round of a new pod stages before refine takes its items. A round of 7 refine items takes 35 to 65 minutes, so with refine first a restart often left stage no turn. It runs `devops roadmap stage --confirm` in the model clone: it is due every 37 minutes, on a first run, and after a round in which `refine` set an item Ready. That round writes a `stage_due` timestamp to `schedule.json`, and the next round runs the row. It stages the Ready items that `roadmap.stage.filter` names, at most `roadmap.stage.limit` in a round, plans only items with the priority `P0-Critical` or `P1-High` while the count of open Planned items is at `roadmap.stage.planned_limit` (#3487, #3692), and splits a task group over `roadmap.stage.step_tokens`. Each task group has a kind (#3005): a `behavior` group has a failing test and changes a path under `src/`, a `manifest` group has a failing case of a rule, a dashboard or a case file (#3981), and an `other` group has no test but a command or the steps of a manual check that prove it. The job writes the kind on the `Kind:` line of each group, and the plan reader reads it back (#5205). The job sends a reply that breaks this rule back to the model, `roadmap.stage.gate_returns` times at most (default 3, #4802), as each reply that the checks refuse. The settings load refuses a value above 3, because each return is one more plan run (#4900). A reply that the checks refuse at the last return gets one more return when no finding of the reply before stays and no finding has the fix class `never`, once for each item (#4851). The model review of a plan sends the plan back to the planner `roadmap.stage.verify_repair_rounds` times at most (default 2, variable `DEVOPS_CLI_ROADMAP_STAGE_VERIFY_REPAIR_ROUNDS`), and once more for each review that marks more earlier findings `gone` than it opens new findings (#5409). No item gets more than 4 repair rounds (`CONST_ROADMAP_STAGE_VERIFY_REPAIR_ROUNDS_CEILING`), so the settings load refuses a value above 4, and no round starts after the Service stops (#5066). It leaves out an item whose change folder is on the default branch or in its archive (#2714): a round reads that tree once with `git ls-tree`, so a merged staging pull request never makes a second one. The pull request it opens is a draft with the title `docs(openspec): plan #<issue> <summary>`. The job does not mark it ready: the row `stage_ready` does (step 18). Before it opens one, it checks each path of the plan (`reads`, `changes`, the code spans of the tasks and `verify`) against the tracked files of the commit it plans, read with one `git ls-files` for the round (#3010). A path that is no file there, and that no group up to its own creates, goes back to the model with the files of the same name. When a later group creates the path, the problem names that group and tells the model to move it before the group that names the path (#3017). A second reply with a missing path stops the item, so no draft opens and the implement Job never meets a wrong path. `k8s/devops/configmap.example.yaml` holds the five settings, and `devops k8s deploy-stack --stack devops` applies them; each also has a variable, `DEVOPS_CLI_ROADMAP_STAGE_FILTER`, `DEVOPS_CLI_ROADMAP_STAGE_LIMIT`, `DEVOPS_CLI_ROADMAP_STAGE_PLANNED_LIMIT`, `DEVOPS_CLI_ROADMAP_STAGE_STEP_TOKENS` and `DEVOPS_CLI_ROADMAP_STAGE_TOOLSET`. The setting `roadmap.stage.toolset` is `extended` by default (#3238): a plan run then has three tools more than the nine that read the staged commit. `references` counts a text in every file of the commit. `read_issue` and `find_issues` read issues and pull requests of the repository on GitHub, as GET requests with the token of the Service and no other permission. `base` leaves them out. Each item of a round counts once in `devops_cli_roadmap_stage_total` by `repo` and its `result`: `staged`, `skipped`, `needs_split`, `failed` or `degenerate`. The label `reason` names the rule that left a `skipped` item out, such as `title_type`, `held`, `failed_lately`, `queue_full`, `returned` or `rejected`, and is `none` for the other results (#4521). The Service logs the reason of a left-out item with the line `stage left out: repo=<owner/repo> item=#<n> reason=<kind> detail=<text>` once, and again only when the kind changes, so a person sees why a repository is idle with no clone. An item is `degenerate` when its plan reply holds a placeholder such as `x` in every text (#4204): the job sends no second request. A reply that the checks refused at least once logs `stage gate returns: repo=<owner/repo> item=#<n> returns=<n> result=<passed|refused> gates=<gate>:<n>,... codes=<code>:<n>,... version=<version>` when it passes or stays refused, with the gates and the codes of the findings of the last refused reply (#4846). After it, each of the first 20 findings of that reply logs `stage gate refused finding: repo=<owner/repo> item=#<n> returns=<n> result=<passed|refused> finding=<place>/<count> gate=<gate> code=<code> subject=<subject> version=<version>` (#5433). The subject is the path, the tool or the command that the message of the finding names, as a JSON string: `redact_text` (the mask of `mask_secrets`) masks it, and then the line keeps its first 200 characters. A finding whose message names none of them has `subject=none`. The line holds no other text of the plan or of the finding, so a person can tell a fault of the plan from a fault of the gate, such as a read that the trace gate did not see. The code of a finding is the key of its message in `MESSAGES.roadmap`, such as `stage_problem_missing_test_file`. Each reply after a return logs `stage gate findings: repo=<owner/repo> item=#<n> return=<n> in=<n> gone=<n> stuck=<n> new=<n> version=<version>`: the findings of the reply before it, those that the reply no longer has, those that it has again (the same gate and the same text, with the digits masked), and its other findings. A reply that the checks refuse at the last return logs `stage gate extension: repo=<owner/repo> item=#<n> returns=<n> in=<n> gone=<n> stuck=<n> new=<n> never=<n> result=<extended|used|first|stuck|never> version=<version>`, and its extra return logs `stage gate extension end: repo=<owner/repo> item=#<n> returns=<n> result=<passed|refused|ended> version=<version>` (#4851). Each reply that the checks judge observes the count of its findings in `devops_cli_roadmap_stage_gate_problems` by `repo` and `reply` (0 for the first reply, 1 more for each return). Each model review logs `stage review round: repo=<owner/repo> item=#<n> round=<n> findings=<n> returned=<n> open=<n> version=<version>` (round 0 is the first review), a repair round past `roadmap.stage.verify_repair_rounds` first logs `stage review extended: repo=<owner/repo> item=#<n> round=<n> fixed=<n> added=<n> version=<version>` with the earlier findings that the last review marked `gone` and the new open findings that it opened (#5066, #5409), and each item that a round failed logs `stage item failed: repo=<owner/repo> item=#<n> step=<step> class=<class> version=<version>` (#4535). The release workflow builds the Service image only for a release, so the version names one image digest. The error line of a failed round keeps the first 256 characters of each error and then names every failed item. A refused reply is logged with the line `stage reply refused: item=#<n> request=<n> input_tokens=<n> tools_offered=<bool> result=<refused|degenerate>`, and an item that fails in the plan keeps its refused replies, their problems and the gate, the code, the path and the text of each finding in `roadmap/stage/<owner>/<repo>/<n>.refused.json` beside its plan file, until the item is staged. `src/devops_cli/roadmap/stage/stage_finding_classes.json` holds the seed fix class and fix rate of each code, from 42 refused plans of 2026-11-10 and 2026-11-11. Each call of a step sends its seconds to `devops_cli_roadmap_step_seconds` by `repo`, `row`, `step` and `result` (#4066): the steps `select`, `plan`, `gate`, `review` and `apply`, and the results `ok` and `error`. A gate that refuses a reply adds 1 to `devops_cli_roadmap_stage_gate_refusals_total` under the name of the gate. A failed item is recorded in its job record with the class of its error and the time (#3493), and the job leaves it out while it takes the other items: 1 hour for a `provider`, `plan_defect` or `ci_infra` class, 6 hours for a `parser` class, and no time for `head_moved` (`RETRY_AFTER` in `roadmap/failure.py`, #4060). A record with no class, or an unknown class, waits as `ci_infra`. The row fails a round only when it tried items and staged, stopped or returned none, or when a failure belongs to no item; three such rounds on the same input suspend the row. The ledger file keeps the class of each error, and a round that the stop of the Service ends counts as `stopped`, not as an error. The image carries the pinned OpenSpec and a Node runtime, so the job validates each change before it pushes: `kubectl -n devops exec deploy/roadmap-service -- openspec --version` prints the locked version.
16. The row `implement` follows `metrics` on the status lane (#2667, #2757). It calls no model, so a model-lane round that has not ended never delays it. It is due every 7 minutes and on a first run, in the clone of the status lane. The Service runs no step: a round only talks to the Kubernetes API, in three moves. It reports each Job that ended, with a comment on the item that holds the state and the last 40 lines of the log of the Job's pod, masked of secrets, and records `implement.job_state` as `succeeded`, `failed` or `gone`. It also logs the line `implement attempt: repo=<owner/repo> item=#<n> state=<state> class=<class|none> repair_rounds=<n> tokens=<n> digest=<runner digest|none> version=<version>` for each Job that ended (#4535). It moves the deadline of each Job that has not ended (#3063, below). It waits while a Job of the repository has not ended. Else it makes one Job from CronJob `devops-cli-runner` for the first Staged or Planned item that the default filter names (a Planned item has its change folder on the default branch and no branch: a person merged the staging pull request, and the job makes the branch and the draft itself), with the args `roadmap implement --repo <repo> --item <number> --confirm` and the item's number as the only item text, and records the name of the Job in `implement.job`, and the digest of the runner image that the CronJob template names in `implement.job_digest`. The same write sets the label `owner/service` on the item (#2910), and the report of the Job removes it. The comment that reports the Job names the digest. The Service makes no Job for an item that an agent or a person claimed, and a claim of an agent or a person ends a running Job at its next group boundary, with no push and no pull request. A round also sets the Status label of the items from their record (`status_sync.py`): it reads the plans on the default branch once for the sweep and for the plan, writes `status/planned` once a plan is merged, and writes `status/in-progress` as soon as the record names a Job, and again after it makes one. It writes only an open item that holds Ready or Planned with the label that a job last recorded, so a label that a person set stays. The rows `stage` and `stage_ready` use the same function. The Jobs of a repository carry the label `implement-repo`, whose value is a digest of the repository name, so the API is the lock and a restart of the Service loses nothing. A Job that leaves its item In Progress, or Ready or Planned with no stop, is a stop that the runner could not write, such as a pod that the kernel killed for its memory, unless an agent or a person claimed the item. The round then sets the item Blocked (`status/blocked`) and records `implement.stopped` as `job`. No Job is made for it before a clear rule runs. A stop that the runner writes sets Blocked in the same way, with the step in `implement.stopped`. After the report, the round clears the stop of each item that it set Blocked. It uses one of three rules, and a comment names the rule that ran. Rule `retry`: a comment `implement: retry`, made after the report by the owner, a member or a collaborator, clears the stop at once, whatever the image. Rule `continue` (#3721): three things must hold. The stop is `job`, which the round records for a Job that ended with no result. Examples are a pod that the kernel killed or evicted, a stalled Job that the Service ended, and a Job that no longer exists. The class in `implement.failure` has the action `retry` in `ACTION_BY_CLASS`. The count `implement.continuations` is less than the setting `roadmap.implement.continuations_per_item` (default 2, 0 turns the rule off). Kubernetes never restarts a Failed Job: `activeDeadlineSeconds` takes precedence over `backoffLimit`, and the template sets `backoffLimit: 0` on purpose. So a continuation is a new Job from the Service. The clear adds 1 to `implement.continuations`, a count and no other data, which stays after a clear. A retry of a person does not reset it. The comment says "continuation n of N", and at the limit it adds "No continuation is left". The rule runs before `digest`, reads no template and spends no clear by digest. The new Job takes the branch from `origin`. So it keeps the `wip:` commits that the run pushed for a group with more than one task (#3054). A group of one task that passed, and that no push kept, runs again. A class with another action, such as `oom` (`raise_limit`), waits for a retry, because a second run on the same limit ends the same way. Only a sign in the log gives the class `oom`. The Service reads no pod status, so a kill with no text in the log is continued as `ci_infra` (follow-up #3727). A stop that the runner wrote, with a step in `implement.stopped`, is no continuation. At the limit, a new runner image still clears the stop by the rule `digest`, within its limits. Rule `digest`: the digest in the template of CronJob `devops-cli-runner` is not `implement.job_digest`, so a new runner image has rolled out since the stop, and the class in `implement.failure` has the action `retry` in `ACTION_BY_CLASS` (#3481). A new image cannot fix a plan, a premise, a refused tool or a failed test, so a stop of another class, and a stop with no class on record, wait for a retry. Each clear by digest adds the class, the new digest and the time to `implement.digest_clears`, and the list stays after the clear. The settings `roadmap.implement.digest_clears_per_class` (default 1) and `roadmap.implement.digest_clears_per_item` (default 3) bound the entries; a stop at a limit stays Blocked until a retry, also for `ci_infra`. The comment of a clear by digest shows at most one time in 24 hours for an item (`implement.digest_clear_commented_at`), and the clear is recorded either way. The rule reads no image content: the Service holds digests and no map from a digest to commits. A clear sets Ready or Planned and removes `implement.stopped`, and the same round can make a Job for the item. The new Job overwrites `implement.job_digest`, so a second stop on the same image waits for a retry. A continuation is the exception, and `implement.continuations` bounds it. So the round makes no Job in a loop. A stop with no digest on record is cleared by a retry only, except a stop `job`, which a continuation clears with no digest. Inside one priority, a round takes an item with no digest clear before an item with one, and a retried item of a higher priority still goes before a new item of a lower priority. A Blocked stop that no rule clears costs one request in the first round after a start of the Service, the listing of its comments. A later round lists the comments again only when the `updated_at` of the issue moved, as a new comment moves it (#4854). The round reads the issue again only when a rule holds, and reads the template at most one time. The round clears no item that a Job holds, that an agent or a person claimed, or that a person labeled Blocked by hand. The failures ledger is unchanged: three failed rounds on the same input still suspend the row. If CronJob `devops-cli-runner` does not exist, the round fails with a message that names it: run `devops k8s deploy-stack --stack devops`, or wait for Argo CD. A Job that cannot pull its image (the package `runner` is not public, or no release published it) has an empty log, so it ends by its stall after 70 minutes, and the next round records the stop. Read the Jobs with `kubectl -n devops get jobs -l implement-repo`. The Job runs the checks that a person runs at a commit and at a push (#3043). Before the first step it runs `pre-commit install-hooks`, with `PRE_COMMIT_HOME` in the cache directory of the data directory, on the home volume. The two remote hook repositories come over public HTTPS (9 s and 51 MB, measured). A failed install stops the item at the step `hooks`, before any model request. Each step then runs the `pre-commit` stage on its staged changes as its last exit check. The child is `uv`, which holds no token. The Job installs no git hook, because git runs a hook with the token of the session, and the agent can edit the hook configuration. For the same reason every hook run gets `--config` with a copy of the configuration of the default branch, so an edit of the agent skips no hook. A hook run that runs out of time stops the step. A failed hook goes to the agent as a repair turn with its output. The setting `roadmap.implement.repair_rounds` (variable `DEVOPS_CLI_ROADMAP_IMPLEMENT_REPAIR_ROUNDS`, default 3) bounds the extra turns of a step for `ruff`, `mypy` and the hooks. Only a used budget stops the step. After the last group, the docs, the archive and the final rebase, and before the push, the Job runs the scoped checks: the `pre-push` stage of the hooks, `devops ci --check --only constructs,docs,openspec`, and `devops ci test` with the test modules that cover the changed Python files of `src/` and `tests/`. Above 30 test modules, which a change to a shared module gives, the tests check runs only the changed test modules, and it does not run when no test covers the change. A failed check starts a fix step, up to `repair_rounds` times for all scoped checks. The Job generates the docs again after each fix. It pushes a finished item only after all of them pass. A stop in this phase (a used budget, a fix step that stops, an error, a command that runs out of time) pushes the commits that passed to the item branch, as any other stop does, and the draft pull request stays a draft (#3645). The comment on the pull request shows the repair rounds of each step, and each run of a scoped check with its seconds. The extra run time of an item is about 10 s of hooks for each step, 9 s for the install, 35 s for the first two scoped checks, and at most about 3.5 minutes for the tests (12 test modules of the roadmap ran in 88 s on 2 CPUs). So it is 2 to 5 minutes in a Job that runs about an hour. The workflow checks `actionlint` and `zizmor` run in the `pre-push` stage only when the push changes a workflow, because the runner image holds no `actionlint`. A failed check of the pull request after the push gets a fix step, a push and a new watch, up to `repair_rounds` times, with a comment on the pull request for each round.

22. A rollout, a scale to 0 or a node drain stops the pod in two bounded phases (#4485). The rounds in flight get 600 s (`CONST_SERVICE_STOP_DRAIN_SECONDS`) to end. A round that the stop ends writes the items it did, counts no failed round, and leaves its other items and rows to the next pod. The pod's `terminationGracePeriodSeconds` is 660 (`CONST_SERVICE_STOP_GRACE_SECONDS`), and it has no preStop hook, because uvicorn starts the drain on SIGTERM. With the `Recreate` strategy the new pod starts only when the old pod has stopped, so an idle pod stops at once, and a pod with a round in flight stops in at most 11 minutes. The log line "The drain wait of 600 s is over" tells that a round ran past the drain wait.
23. The row `fix_plan` follows `stage` on the model lane (#5061). It runs the step `devops roadmap step fix-plan` in the model clone, in the mode of `roadmap.fix_plan.mode` (ADR 0021, section 8): `off` sends no request, `plan` selects one plan pull request and logs it with no model call and no write, and `on` runs the attempt. The mode starts in `plan`, and a person sets `on` in the ConfigMap `devops-cli-config`. The row is due every 53 minutes and on a first run. A round takes at most one open draft plan pull request that holds `plan/needs-fix`, whose item is Staged and has no runner Job and no claim, with fewer than 2 attempts on its head, no attempt in the last 6 hours and fewer than 3 revisions of the step. The row never skips the wait: only a person's named run with `--skip-wait` does (#5413). The attempt stops before any write when the branch moved after the read or holds a commit of another author. It reads the plan of the head before the attempt marks: a plan that the plan reader refuses ends `unreadable`, writes only `fix_plan.at` and `fix_plan.result`, logs one warning and no result line, and waits 6 hours. The checks judge the plan of the head at the latest default branch, and a plan that they refuse gets a new gated plan from the stage planner. In each attempt the verification pass reviews the plan that passed the checks, and the last plan comment of the item adds its open findings. The stage planner gets that plan and each open finding, and the row reviews the revision with the normal repair rounds. A revision that is not the same plan, and whose reviews fixed more open findings of the head than they added (#5409), becomes one commit on the latest default branch (`revised`, or `cleared` with no open finding), which the row pushes with `--force-with-lease` on the head that it read. Else a gated plan that is not the plan of the head is pushed the same way (`regated`). A head with no open finding in its review keeps its plan (`dismissed`). The label goes for `cleared` and `dismissed`, and for `regated` only after a review of the gated plan with no open finding. A false premise, an open blocker or a head over the budget ends `stopped`, and the label stays. The setting `roadmap.fix_plan.time_budget_seconds` (default 3600) starts with the round: once it is spent, no plan run and no review starts, and the attempt ends `timeout` with no push and with the label kept (#5363). Each review logs one line `fix-plan progress:` with its open findings, the tokens and the seconds so far. The row posts one comment with the marker `<!-- devops roadmap fix-plan -->` on the issue for each attempt that ends `revised`, `cleared`, `regated`, `dismissed`, `stopped` or `timeout`, records `fix_plan.key`, `fix_plan.attempts`, `fix_plan.revisions`, `fix_plan.at`, `fix_plan.result`, `fix_plan.version` and `fix_plan.evicted`, logs one result line with `job=fix_plan`, and adds 1 to `devops_cli_roadmap_fix_plan_total` by `repo` and `result`. No attempt starts once the Service stops, and an attempt that the stop ends at its next safe point is `evicted`: it does not count, for 3 such attempts on a head ([the fix-plan step](roadmap/stage.md#the-fix-plan-step), Kills). An attempt spends at most the model limits of one stage item, plus one review and one repair of the head plan.

### Runner Jobs

The implement job runs tests, `ruff`, `mypy` and OpenSpec, which the Service image does not hold. A step runs `ruff check` on every changed Python file. It runs `mypy` with the options of `devops ci typecheck` on the changed files under `src/`, and no type check on a test file, because the gate checks `src` only (`src/devops_cli/ci/typecheck.py` is the one definition). Its steps run in a runner Job (#2667). `devops roadmap implement --item <number> --confirm`, run on a workstation, makes one by hand for that item and follows its log (`--no-wait` prints the Job's name, `--dry-run` prints the Job). It refuses an item that an agent or a person claimed, an item that is neither Ready nor Planned, and a repository that has a runner Job that has not ended. It makes the Job with the code of `devops k8s run-job --template runner --repo <owner/name> -- roadmap implement --repo <owner/name> --item <number> --confirm`, which is the way to pass `--filter` or `--limit` to the job. Both commands label the Job and its pod `implement-repo=<digest of the repository>`, the label that the row `implement` lists its Jobs by, and make no Job while a Job with that label has not ended. The label is a digest of the lower-case repository name. The lock is best effort: each command lists the Jobs just before it creates one, so a Job that starts between the two calls is not seen. If the App is not installed on the repository, the Job fails in its pod, and the error in its log names the repository. `--repo` is required with the runner template: it sets `service.github_app.token_repository` on the Job, and the job runs no step unless that setting equals the repository it acts on. The Service makes one for each Staged or Planned item in the row `implement` (Roadmap service, step 16).

- **Image.** Stage `runner` of the `Dockerfile` builds on stage `runner-deps`, which adds to the runtime venv of stage `deps` git, the dev dependencies of `uv.lock` (pytest, ruff, mypy, bandit, deptry, ast-grep, zizmor, pre-commit), the Node runtime, and the tools that the gate and the hooks need (#3072): `curl` and `jq` from apt, and promtool at the pin of `tools.lock`, which stage `runner-tools` installs with `devops install-tools`. The dependencies lie in their own layers (#4550). `deps` and `runner-deps` install the requirements that stage `lock` exports from `uv.lock` with `--no-emit-project`, and a release changes only `src/` and the project version, so it keeps those layers. Stage `runner`, which no build caches (`no-cache-filters`), adds only the apt upgrade and the project: the `devops_cli` package, its dist-info and `bin/devops`. The Service image has the same split (`service-deps` and `service`). Measured with local builds: a change of `src/` changes 32 MB of layers in each image (1,747 MB in the runner image and 1,219 MB in the Service image before #4550), and a change of `src/` and of the version also changes 32 MB. The table `RUNNER_TOOLS` in `src/devops_cli/roadmap/runner_tools.py` lists every tool with the reason it is there and its version command, and `NOT_IN_RUNNER` lists each program that the image leaves out, with the reason (no cluster tool, no scanner that the gate does not install, no npm, no tool that fails the image scan). The image holds neither `actionlint` nor `shellcheck` nor Trivy: the image scan fails on the newest release of each (Go standard library 1.27.0 in `actionlint` 1.17.0, go-jose 4.1.5 in Trivy 0.76.1), so a Job cannot run the `actionlint` row or the IaC scan, and without npm it cannot run the `audit` row. The pull request runs them. #3108 tracks their return. The apt tools have no pin, because Debian gives the version and a pin would fail the build on each security update; the image holds `git` 2.47.3, `curl` 8.14.1 and `jq` 1.7. The last step of the stage runs `python -m devops_cli.roadmap.runner_tools`, so an image that lacks a tool or holds it at another version than its pin does not build. Tests fail when a `devops ci` row, a hook of `.pre-commit-config.yaml`, a required job of `ci.yml`, a live-marked test or an entry of `tools.lock` needs a program that is in neither table, and when a pin of the table differs from a Dockerfile. The Service image holds none of the added tools. `trivy image --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 --ignorefile .trivyignore` on the built stage exits 0. The measured growth is 56 MB compressed (522 MB to 578 MB, as `docker save` output through `gzip -1`) and about 70 MB in the new layers, which adds the transfer of those layers to the first pull on a node (about 5 s on 100 Mbit/s). The promtool step of the build takes 19 s. The smoke test of `ci.yml` and `release.yml` runs the same check on the loaded image and fails when `docker image inspect` reports more than 3000000000 bytes (2.43 GB measured). The release publishes the image as `ghcr.io/dan-petty/devops-cli/runner`, next to the Service image, and Image Updater keeps it on the digest of `latest` (Service Image Updates). Each Job runs `uv run` in its own worktree, with the uv cache on the home volume.
- **Template.** Suspended CronJob `devops-cli-runner` has 2 CPU, 4 Gi of memory requested and 8 Gi at most (the default of a manual run; the Service sets the size of its Jobs, see Size), an `emptyDir` home of 4 Gi, an `emptyDir` `/tmp` of 1 Gi, `ephemeral-storage` of 2 Gi requested and 6 Gi at most, `activeDeadlineSeconds: 7200` and `backoffLimit: 0`. It sets `DEVOPS_CLI_ROADMAP_IMPLEMENT_IN_RUNNER=true`, which no other pod sets, and `PYTEST_XDIST_AUTO_NUM_WORKERS=2`, the CPU limit, because `pytest-xdist` counts the CPUs of the node and not of the pod (about 280 MB for each worker). It uses ServiceAccount `devops-cli`, which mounts no token, and the Secret `devops-cli` through `envFrom`. A Job is made from the template and changes only the args, the name, the labels, the environment values `DEVOPS_CLI_SERVICE_GITHUB_APP_TOKEN_REPOSITORY` and `PYTEST_XDIST_AUTO_NUM_WORKERS`, the deadline and the CPU and memory values of `resources` (see Size and Deadline).
- **Role.** ServiceAccount `roadmap-service` is the account of the Service pod. Role `roadmap-service-jobs` in namespace `devops` allows `create`, `get`, `list` and `patch` on `jobs`, `get` on CronJob `devops-cli-runner`, `get` on Deployment `roadmap-service` (#2917), `list` on `pods` and `get` on `pods/log`, and nothing else. Kubernetes limits `create` and `list` to no name, and the name of each Job is new, so those two and `patch` cover the namespace. The `patch` moves the deadline of a Job (see Deadline); the admission policy checks a patch as it checks a create. A holder of the Role can make any pod that Pod Security `restricted` admits in namespace `devops`, and such a pod can take Secret `devops-cli`. The Service pod holds that Secret already, so the Role gives no new secret. That holds only while namespace `devops` holds no Secret but `devops-cli`, so the admission policy below pins the Jobs of the Service. The Service pod mounts a projected token that expires after one hour; the client reads it again as the kubelet renews it. A Job pod mounts no token.
- **Admission policy.** ValidatingAdmissionPolicy `roadmap-service-jobs` and its binding (`k8s/devops/roadmap-service/admissionpolicy.yaml`, #2696) refuse a `CREATE` or an `UPDATE` of a Job in namespace `devops` unless the Job has: one container and no init container, with no `command`; the image `ghcr.io/dan-petty/devops-cli/runner`, alone or followed by `:` or `@`; ServiceAccount `devops-cli` with `automountServiceAccountToken: false`; only Secret `devops-cli` in `envFrom` and no `valueFrom` in `env`; only the volumes `tmp`, `home` and `config` of the template; no `hostNetwork`, `hostPID` or `hostIPC`; no `priorityClassName`, `nodeName`, `imagePullSecrets` or `manualSelector`; the pod label `app.kubernetes.io/name: devops-cli-job`, because the NetworkPolicies select pods by that label and a Job pod with the label of the Service would take its egress to the API server; `completions` and `parallelism` of 1 or not set; `backoffLimit: 0`; an `activeDeadlineSeconds` of 14400 at most (`CONST_ROADMAP_IMPLEMENT_DEADLINE_CAP_SECONDS`, the most that the setting `roadmap.implement.deadline_ceiling_seconds` may be; a test holds both); and a CPU request that equals the CPU limit and is 1 with a memory request of 2Gi, or 4 with 6Gi (the table of Size), a memory limit, and a `PYTEST_XDIST_AUTO_NUM_WORKERS` that equals the CPU limit. The policy applies only to the user `system:serviceaccount:devops:roadmap-service`. It never evaluates a Job of another identity, such as the CLI user (`devops k8s run-job`), Argo CD or the CronJob controller. It runs in the API server, so no webhook can be down. `failurePolicy` is `Fail`: if an expression errors, the Job of the Service is refused, the create raises an error, and the next round tries again. Argo CD syncs the policy with the other manifests of the stack, and AppProject `homelab` already admits the two cluster-scoped kinds. The gate check `tests/gate/k8s_checks/job_admission_policy.py` (row `k8s` of `devops ci`) runs the expressions against the Job that CronJob `devops-cli-runner` makes, so a change of the template that the policy refuses fails in CI. To check the live policy, make a Job as the Service with `kubectl --as=system:serviceaccount:devops:roadmap-service create --dry-run=server -f <job>`. These are not pinned: the tag or digest of the image, the `args`, the plain `env` values but the worker count, the memory limit, `nodeSelector`, `tolerations`, `hostUsers`, the security context (Pod Security `restricted` checks the pod) and the number of Jobs. A person with an admin role can delete the policy, and Argo CD restores it.
- **Network.** Policy `roadmap-service-egress` admits the Service pod, and no other pod, to TCP 6443, with the cloud metadata address excluded. A Job pod keeps the egress of `devops-default-perimeter`: DNS, the gateway, the cache, the OTLP collector and public HTTPS. No policy admits it to the API server.
- **Size.** The Service sizes the CPU and the memory request of a Job from its plan (#3193). It counts the distinct file paths in the code spans of `tasks.md`, read from `origin/<default branch>` for a Planned item and from the branch of a Staged item, and takes a row of the table `RUNNER_SIZES` in `src/devops_cli/roadmap/implement/implement_size.py`: at most 10 files, 1 CPU (request and limit) and 2 Gi of memory requested; more than 10 files, 4 CPU and 6 Gi. Each row names its measured sample: 2 Gi is above the 1.24 GB peak of the 10 Jobs that did not run out of memory, and 6 Gi is above the 4.13 GB that the killed Job had reached (#2806). The Service sets `PYTEST_XDIST_AUTO_NUM_WORKERS` to the CPU limit of the same Job, so the two cannot differ. The memory limit of every Job is the setting `roadmap.implement.max_memory_limit` (default `8Gi`, a whole number of Gi, not below 6Gi), which the admission policy does not pin. A change of a row is a change of the table and of the policy in one pull request: a gate check admits each row and every pair of a grid around them, and expects that only the rows pass. A Job from `devops k8s run-job` or `devops roadmap implement --item` keeps the size of the template.
- **Deadline.** The Service makes the Job with `activeDeadlineSeconds` set to `roadmap.implement.deadline_extension_seconds` (default 5400) and the annotation `roadmap.devops-cli/progress-at` (#3063). The CronJob template keeps 7200 for `devops k8s run-job`. In each round the Service reads the last 20 lines of the log of each such Job that has not ended. The runner writes one line for each tool call, so a log that changed since the last round is progress. The Service then sets the deadline to the seconds since the Job started plus the extension step, up to `roadmap.implement.deadline_ceiling_seconds` (default 14400). It never lowers a deadline on progress. It keeps the digest of the log and the time of the progress in the annotations `roadmap.devops-cli/progress` and `roadmap.devops-cli/progress-at` of the Job, so a restart loses nothing. A log that stays the same for `roadmap.implement.deadline_stall_seconds` (default 4200) is a stall: the Service sets the deadline to the seconds since the start and the annotation `roadmap.devops-cli/stalled`, the Job controller ends the Job with the reason `DeadlineExceeded`, and the report on the item names the stall. Each change is a span `implement.deadline` with the Job, the old and the new deadline and the reason (`progress`, `progress, ceiling` or `stall`). The defaults come from the longest wait in which the runner writes no line: the watch of the checks of a pull request, 3600 s. The stall is 600 s above it. The extension is above the stall by a row (7 minutes) and a tick of the Service (151 s), so the Service sees a stall before the deadline passes; a test holds both. The settings validate: the stall is not above the extension, the extension is not above the ceiling, and the ceiling is not above 14400. The memory limit stays the 8 Gi of the template.
- **Guarantees.** The shell of a step has none of the variables of the job, except the uv paths and the worker bound of the test runner. A step cannot read the environment or the memory of the job process, because the job clears its dumpable flag. The installation token of the job names one repository (`service.github_app.token_repository`), and the job runs no step unless that setting equals its repository and the process acts as the GitHub App. A Job ends by its deadline, 14400 s at most, and is not retried. The token is in the environment of a `git` or `gh` child of the job while that child runs, and a process of the same user can read it through `/proc`. A pod cannot hide it: the default seccomp profile refuses the user namespace that a sandbox for the shell needs. So the job guarantees an order: it adopts the orphans of its children, and when a step ends it kills every process the step left, also a daemon in a session of its own, before it runs any `git` or `gh`. A process that survives stops the item. These properties are not guaranteed: public HTTPS is open, so a step can send the clone to a public host; and a step runs as the same user as the job, so it can change the files that the job reads later, such as the clone, `.git/config` and the hooks of the worktree. A hook runs inside a `git` child of the job, with the token in its environment. The token limits the harm to one repository, to the permissions of ADR 0015 and to one hour. Those permissions include workflow files, so a workflow on a pushed branch can run with the secrets of the repository before a person reviews it. A real sandbox for the shell is planned (see Person steps). A person merges every pull request.
- **Person steps.** After the first release that publishes the runner image, a person makes the GHCR package `runner` public, as the package `service` is. The Job takes the whole Secret `devops-cli`. A narrower Secret for the runner is the better end state, and a person makes secrets. A follow-up is filed: a real sandbox for the shell of a step ([#2695](https://github.com/dan-petty/devops-cli/issues/2695)). After the first sync of the admission policy, a person checks once that the Service's Job passes it, with the `kubectl --as` command of the policy above.

### Webhook route

The Ingress `devops/roadmap-service` publishes `POST /webhooks/github` at `https://hooks.<domain>`.

Traefik limits the requests to the route before they get to the Service. The Ingress names the Middleware `devops/roadmap-service-rate-limit` (`k8s/devops/roadmap-service/middleware.yaml`), which lets 60 requests a minute through, with a burst of 60, in one bucket for the host. Traefik answers a request above the limit with HTTP 429. GitHub does not send a failed delivery again, but the next poll starts the round that the delivery would have started. To see the answers of the route, the 429 of the rate limit included, use `sum by (code) (increase(traefik_router_requests_total{service="devops-roadmap-service-8000@kubernetes"}[15m]))`. Traefik counts `traefik_service_requests_total` only for the requests that get to the Service, so that series does not show a 429 of the rate limit.

The route refuses a delivery before it reads the body when:

- the Service drains: 503;
- the content type is not `application/json`: 415;
- the `X-GitHub-Event` or `X-GitHub-Delivery` header is missing: 400;
- the `X-Hub-Signature-256` header is missing or empty: 401 `missing signature`;
- the `Content-Length` is more than 25 MiB: 413.

Then the route reads the body. It refuses a body of more than 25 MiB (413), a signature that no secret in `service.webhook_secrets` made (401 `invalid signature`), a payload that does not validate (400), and a repository that is not in `service.repos` or that did not sign the body (401). Each refusal counts under the outcome `rejected` of `devops_cli_service_webhook_deliveries_total`. `RoadmapServiceWebhooksRejected` fires when the route rejects more than 20 deliveries in 15 minutes (Alerts).

The Cloudflare edge answers before Traefik and the route. An Access application that does not let a delivery through answers HTTP 403 with the header `Server: cloudflare` and the page `Error ・ Cloudflare Access` (step 6). Such a refusal never gets to the route, so `devops_cli_service_webhook_deliveries_total` and the Traefik counters cannot show it. GitHub records the answer of each delivery. Each time the metrics row runs (every 13 minutes), it reads the active hooks of its repository and the newest 100 deliveries of each hook, and sets `devops_cli_service_webhook_delivery_failures` by `repo` and `code` to the deliveries of the last 15 minutes that got no 2xx answer. The reads cost one request for the hooks and one for each active hook, about 10 an hour for a repository with one hook, and they count against `service.github_requests_per_hour`. The installation token of the Service reads them with the permission Webhooks read (step 1). A failed read fails the metrics row, and the gauge keeps the value of its last read. `RoadmapServiceWebhookDeliveriesFailed` fires when more than 5 deliveries of one repository failed in 15 minutes (Alerts) (#5017). To read the failed deliveries of a hook, run `uv run devops gh api 'repos/<owner>/<name>/hooks/<hook-id>/deliveries?per_page=100' --jq '[.[]|select(.status_code<200 or .status_code>=300)|{delivered_at,event,action,status_code}]'`. To read the answer of one delivery, run `uv run devops gh api repos/<owner>/<name>/hooks/<hook-id>/deliveries/<delivery-id>` and read `response.headers`. gh's `--jq` rounds the long delivery IDs, so take the ID from the output of the command without `--jq`.

### Mattermost slash command

The `/roadmap` slash command in Mattermost inspects each repository's roadmap service state, answered in-cluster through the service's webhook router (#1395).

### Go-live check

Argo CD applies the deployment, but not ConfigMap `devops-cli-config`. Only `devops k8s deploy-stack --stack devops` renders that ConfigMap, from `k8s/devops/configmap.example.yaml` and the active config. On a cluster that Argo CD manages, deploy-stack applies the ConfigMap but does not restart the pod. Until a pod reads the ConfigMap of the current template, it can send each model call five times, not two ([k8s/README.md](../k8s/README.md#llm-gateway-llm-gateway), LLM Gateway). So when Argo CD has synced the deployment, do these steps from a checkout of `main`. Do them again each time a change to the template merges.

```bash
uv run devops k8s deploy-stack --stack devops
kubectl -n devops get cm devops-cli-config -o jsonpath='{.data.devops-cli\.yaml}' | grep max_retries   # max_retries: 1
kubectl -n devops rollout restart deployment/roadmap-service
```

A change that removes, renames or tightens a setting that `k8s/devops/configmap.example.yaml` or the live ConfigMap names says in its OpenSpec proposal and in a comment on its pull request how the live ConfigMap changes first: apply the ConfigMap with `deploy-stack`, then let the image roll. Git does not hold the live ConfigMap, so a test cannot read it. `deploy-stack` loads its rendering into `Settings` before it applies it, and `tests/k8s/test_k8s_configmap_keys.py` fails if the example names a key that no setting declares.

Then do these checks, and do them again every 15 minutes for the first 2 hours. If a check fails, do the stop switch. If an alert of the rule group `roadmap-service` or `roadmap-service-webhooks` fires, do what its row in Alerts says. Select each series of the Service with `job="roadmap-service"`, as the alert rules do.

1. The pod runs: `kubectl -n devops get pod -l app.kubernetes.io/name=roadmap-service` shows one pod `Running`, with no restart and no `OOMKilled`.
2. Prometheus scrapes the pod: `up{job="roadmap-service"}` is 1.
3. A test delivery gets to the Service. Get each hook's ID with `uv run devops gh api repos/<owner>/<repo>/hooks --jq '.[]|{id,active,events}'`, then send a ping with `uv run devops gh api -X POST repos/<owner>/<repo>/hooks/<id>/pings`. `uv run devops gh api repos/<owner>/<repo>/hooks/<id> --jq .last_response` shows code 200, and `devops_cli_service_webhook_deliveries_total{job="roadmap-service",event="ping"}` counts one `ignored` delivery. Code 401 tells you that the hook's secret is not the one in `service.webhook_secrets`.
4. The first rounds stay inside the budget: `sum(increase(devops_cli_github_requests_total{job="roadmap-service"}[1h]))` has a value within 15 minutes and stays below `devops_cli_service_budget_limit_requests{job="roadmap-service"}`, the budget `service.github_requests_per_hour` (500 by default). At the start, each lane that is due runs, so the first hour costs the most.

### Stop switch

Do these steps in this order. Step 1 does not need the cluster.

1. Suspend the App's installation. Only a person can do this, and only in the web interface: open https://github.com/settings/installations, select `devops-cli-service`, select Configure, then select Suspend. The next token mint fails, and the Service halts as a refused identity. Until that mint, GitHub refuses each request, but the Service does not halt.
2. Turn off automated sync from the top down ([k8s/README.md](../k8s/README.md#pausing-an-application), Pausing an Application): `bootstrap`, `cluster`, then `devops`. All three self-heal, so without this step Argo CD sets the replica count back to the value in git. `ArgoCdAutoSyncDisabled` fires after 15 minutes, which is expected.
   ```bash
   for app in bootstrap cluster devops; do
     kubectl -n argocd patch application "$app" --type merge -p '{"spec":{"syncPolicy":{"automated":{"enabled":false}}}}'
   done
   ```
3. Stop the pod: `kubectl -n devops scale deployment roadmap-service --replicas=0`. The pod ends its round in flight first, in at most 11 minutes (item 21 of Roadmap service).
4. Stop the cluster Jobs, which use the same key: `kubectl -n devops get jobs -l app.kubernetes.io/name=devops-cli-job`, then `kubectl -n devops delete job <name>` for each Job that runs.
5. Turn off each repository's webhook: `uv run devops gh api -X PATCH repos/<owner>/<repo>/hooks/<id> -F active=false`.
6. If the private key leaked, generate a new key and delete the old one (step 9). A token minted with the old key stays valid until it expires, up to one hour after its mint.
7. To keep the Service stopped, open a pull request that sets `replicas: 0` in `k8s/devops/roadmap-service/deployment.yaml`. After a person merges it, turn on automated sync for `bootstrap` again: it restores `cluster`, and `cluster` restores `devops` from git.

Do not restart the pod to clear a halt before you know its cause. A restart clears the halt, the hourly budget and the count of failed rounds.

## Crawl4AI

`deployment/crawl4ai` runs [Crawl4AI](https://github.com/unclecode/crawl4ai) 0.9.5 (Apache-2.0), a service that renders a web page in Chromium and returns its text as Markdown (`POST /md`). Upstream ships no Helm chart and no Kubernetes manifest, so `k8s/devops/crawl4ai/` follows its compose file: one replica with the `Recreate` strategy, a read-only root, an `emptyDir` for each of the six paths that the compose file mounts as tmpfs, 1 Gi of shared memory at `/dev/shm`, and 4 Gi of memory. The pod meets Pod Security `restricted` and runs as user 999, the ID of `appuser` in the image. It mounts no service account token. Service `crawl4ai` answers on port 11235 inside the cluster. No Ingress, Traefik route or tunnel entry names it.

- **Access.** Only the pods of `roadmap-service` may call it (`crawl4ai-perimeter` and `roadmap-service-to-crawl4ai`). A Job pod cannot. Every route but `/health` needs the bearer token in Secret `crawl4ai`. Without the token the server binds the loopback address only, so the Secret must exist before the pod starts. A person creates it with `devops k8s push-secrets --stack devops` (see [Cluster Secrets](../k8s/README.md#cluster-secrets)).
- **Egress.** The pod reaches CoreDNS and public TCP 80 and 443. The ranges that the rule removes are those of `devops-default-perimeter`: private, shared, link-local, cloud metadata and special-purpose addresses. This policy is the main control against a request to an internal address. The filter inside Crawl4AI is the second control, and it had bypasses in 0.8 and 0.9. `devops-default-perimeter` skips this pod, so the pod has no path to the gateway or to the cache Valkey.
- **Switches that stay off.** The Deployment sets none of `CRAWL4AI_ALLOW_INTERNAL_URLS`, `CRAWL4AI_HOOKS_ENABLED` and `CRAWL4AI_EXECUTE_JS_ENABLED`, and it holds no key of a model provider. A test holds this.
- **The pin.** The image names a release tag and the digest of its multi-platform index. Renovate reads `k8s/**/*.yaml` and bumps the tag and the digest in one pull request. `devops k8s image-pins` resolves the pin. The CI job `image-pins` runs it, and the image scan reports the third-party digest without failing the pull request.
- **The advisory watch.** The project has had many security advisories since 2026-06, and the fixes arrive as releases. Read the [advisories](https://github.com/unclecode/crawl4ai/security/advisories) before you merge a bump, and merge a bump that fixes an advisory without delay. Only 0.9.x gets fixes.
- **A workstation.** An agent on a workstation reads a page with `devops ai fetch-page <url>` or the MCP tool `ai_fetch_page` of the `devops-cli` server. Both are read-only. Run `kubectl port-forward -n devops svc/crawl4ai 11235:11235`, then `devops config set crawl4ai.url http://127.0.0.1:11235`. Store the token once with `devops config set crawl4ai.api_token`: it comes from the keyring, and the command and the tool have no option for the token, the service address or a file path. `devops ai fetch-page --dry-run <url>` makes no request and prints the request. The tool is not in the tool set of any job role until a person approves the egress (#3243). No MCP client file changes.
- **The check.** `devops k8s crawl4ai-check` tests the three controls on the running cluster. Through a `kubectl port-forward` and the token of the keyring, it sends each of the routes `/md`, `/html`, `/screenshot`, `/pdf` and `/llm/{url}` to five internal targets (the metadata address, localhost, the Kubernetes API, the service itself and the roadmap Service) and expects a refusal: HTTP 400 or 403 and a body with the one key `detail`. It sends each route once without the token and expects 401 or 403. It also starts a throwaway pod with the label of the service, tries a connect to the metadata address and to a private ClusterIP, and deletes the pod. The pod runs as `restricted` and never becomes ready, so the Service sends it no traffic. The report names each target by a role and never prints the token. A person runs the command at each bump of the digest. Until `CRAWL4AI_IMAGE` in `src/devops_cli/k8s/crawl4ai_check.py` names the new image, the `k8s` row of `devops ci` fails. If a route serves a page of an internal target, do not add code for it: file the evidence upstream and on #3884. `devops k8s crawl4ai-check --dry-run` lists every call and makes none.
- **The log.** `kubectl -n devops logs deploy/crawl4ai` shows supervisord, Redis and the app. A blocked request shows as `URL blocked (SSRF protection)` with HTTP 400. The first start is slow because the image is 2.3 GB.
- **The limits.** The first limits are 1 Gi of memory as the request and 4 Gi as the limit, 500m and 2 CPUs, and 2 Gi of ephemeral storage. On a workstation, one idle container used about 500 MiB, and four pages at once used under 750 MiB and two CPUs. Measure on the cluster, then change them.

## SearXNG

`deployment/searxng` runs [SearXNG](https://github.com/searxng/searxng) (AGPL-3.0), a metasearch service that asks public search engines and returns the hits as JSON (`GET /search?q=<query>&format=json`). The roadmap Service uses it as the first provider of web search (`search.providers`). Upstream ships no Helm chart and no Kubernetes manifest (`searxng-docker` is archived), so `k8s/devops/searxng/` follows `container/docker-compose.yml` of the main repository: ConfigMap `searxng-settings`, Deployment, Service `searxng` on port 8080 and two NetworkPolicies. One replica. The pod meets Pod Security `restricted` and runs as user 977, the ID of `searxng` in the image, with a read-only root, two `emptyDir` volumes (`/tmp` and `/var/cache/searxng`) and no service account token. No Ingress, Traefik route or tunnel entry names it.

- **The license.** AGPL-3.0. The project runs the image as it is and calls it over HTTP. It patches no SearXNG code, so the duty to offer source (section 13) does not apply. A patch is a new decision: do not patch the image.
- **Access.** There is no limiter and no login: the limiter needs Valkey and refuses a plain machine client. Only the pods of `roadmap-service` may call the pod (`searxng-perimeter` and `searxng-clients`). A Job pod cannot. The pod reaches CoreDNS and public TCP 443 only, with the ranges that `devops-default-perimeter` removes. `devops-default-perimeter` skips this pod, so the pod has no path to the gateway or to the cache Valkey.
- **The secret.** Secret `searxng` holds `SEARXNG_SECRET` (see [Cluster Secrets](../k8s/README.md#cluster-secrets)). A person creates it with `devops k8s push-secrets --stack devops` before the first sync. The settings file holds no secret.
- **The address.** The pod serves nothing to the Service until `search.searxng_url` is set in the live ConfigMap `devops-cli-config`, with `ai.allow_private_network`. Without it the provider `searxng` is skipped and the search goes to the next provider. `k8s/devops/configmap.example.yaml` holds the line.
- **The engines.** `keep_only` in `searxng-settings` keeps nine engines that need no key: `duckduckgo`, `wikipedia`, `github`, `stackoverflow`, `askubuntu`, `superuser`, `arxiv`, `mdn` and `docker hub`. The scraping engines of Google, Bing, Brave, Startpage, Mojeek and Qwant are not kept: their upstream sites suspended them in October 2026 (SearXNG issues 6866 and 6819). The keyed Brave engine is not used either. A test holds this. A request that names no category asks only the `general` engines (`duckduckgo`, and `wikipedia` as an infobox with no result); the technical engines answer when the request names `it` (`github`, `stackoverflow`, `askubuntu`, `superuser`, `mdn`, `docker hub`) or `science` (`arxiv`). The provider asks `general,it,science`. `pypi` is not kept: `pypi.org` serves a Client Challenge page to a scraper, and in the live check of 2026-11-07 the engine returned no hit for any query, with no error. `github` and `duckduckgo` refused the address of the test host after about 30 queries within minutes (`Suspended: access denied` and `CAPTCHA`), and answered again later; the rate that a cluster node address gets is not known. SearXNG suspends a refusing engine (CAPTCHA and access denied for 86400 s, too many requests for 3600 s), but `duckduckgo` raises its CAPTCHA with no suspension, so the next query asks it again. The settings add no retry loop.
- **The pin.** The image names a date tag with the commit and the digest of its index. Renovate reads `k8s/**/*.yaml` and bumps the tag and the digest in one pull request. SearXNG publishes many tags a day and has no release feed, so Renovate proposes a new tag only on Monday, also for a patch. A tag has no minimum release age (Dependency Versions in [`CONTRIBUTING.md`](../CONTRIBUTING.md#1-development-philosophy--core-invariants)), and the pull request text tells the person to refresh the engine names. To bump by hand or to review a bump:
  1. Choose the newest tag that passes the tests of step 4 (the tag list of `https://hub.docker.com/r/searxng/searxng/tags`). Take a tag with a security fix or a bug fix on the day it is published.
  2. Set the tag and the digest in `deployment.yaml`.
  3. Refresh `tests/fixtures/searxng/default_engine_names.txt` (the first line names the tag): `docker run --rm --entrypoint cat <image> /usr/local/searxng/searx/settings.yml | python3 -c "import sys, yaml; print(*sorted(e['name'] for e in yaml.safe_load(sys.stdin)['engines']), sep='\n')"`. If a name of `keep_only` is gone, a test fails: read the notes of the release for the new name.
  4. Run `devops ci test tests/invariants/test_k8s_searxng.py`, then run `devops k8s searxng-check` against the new image (see the next bullet) and set `SEARXNG_IMAGE` in `src/devops_cli/k8s/searxng_check.py`.
- **The check.** `devops k8s searxng-check` tests the running service for the points that a new digest can change. Through a `kubectl port-forward` it sends six `GET /search` requests with `format=json` and no credential: one for each category of the provider (`general`, `it`, `science`), a query `!google ...` that must stay text, a query `!!g ...` whose redirect is recorded and never followed, and a category that no kept engine serves. It fails a row when a reply lacks one of the seven keys (`answers`, `corrections`, `infoboxes`, `query`, `results`, `suggestions`, `unresponsive_engines`), when HTTP 403 shows that `json` is not in `search.formats`, when a category has no hit, or when an engine that must stay off (Brave, Google, Bing, Startpage, Mojeek, Qwant) shows in `results` or in `unresponsive_engines`. It also starts two throwaway pods and tries three connects: a pod that is not a client of the service must not reach port 8080, and a pod with the label of the service must reach neither the metadata address nor a private ClusterIP. The report names each pod and target by a role. A person runs the command at each bump of the digest. Until `SEARXNG_IMAGE` names the new image, the `k8s` row of `devops ci` fails. The query count stays at six, below the about 30 queries after which the upstream sites suspend an engine. If a row fails on the pinned image, do not add code for it: file the evidence as an issue. `devops k8s searxng-check --dry-run` lists every call and makes none.
- **The log.** `kubectl -n devops logs deploy/searxng` shows the engines that failed. A line `CAPTCHA` from `duckduckgo` or `Suspended: access denied` from `github` means that the engine refused the pod address for a while. The pod answers with the other engines, and the search passes to the next provider when no engine gives a hit. The start prints a warning that `/var/cache/searxng` is not owned by `searxng:searxng`: the group of the volume is 977 (`fsGroup`), and the pod writes to it.
- **The limits.** Measured with the pinned image under the controls of the pod: it idles at 114 MiB, 20 queries one after another peak at 117 MiB, and 10 at once peak at 122 MiB and 0.8 CPU. On the cluster the worker grows about 50 MiB a day (160 MiB to 364 MiB in 4 days, nearly all resident memory), and the old limit of 384 Mi OOM-killed it on 2026-11-12 (#4939). `GRANIAN_WORKERS_MAX_RSS` (512 MiB) makes Granian replace the worker before the limit. The Deployment asks for 256 Mi and 50m, with the limits 1 Gi and 1 CPU: the main process (about 35 MiB), the resource tracker (about 15 MiB), a worker at 512 MiB and the new worker while Granian replaces it fit under the limit.

## MCP server

Deployment `mcp-server` (`k8s/devops/mcp-server/`) runs `devops mcp serve --transport streamable-http --port 8001 --allow-remote` with one replica. Each job role has its own endpoint, `/<role>/mcp`, for the roles `planning`, `implementation` and `review`, and an endpoint holds only the tools of its role (`src/devops_cli/ai/mcp/roles.py`). [SECURITY.md](../SECURITY.md#mcp-server-on-the-network) gives the bearer token, the NetworkPolicies and the role tables. A client reads the base URL from `roadmap.mcp.url` and stops a tool call after `roadmap.mcp.timeout_seconds` (default 30). [Cluster Secrets](../k8s/README.md#cluster-secrets) tells how a person makes the token.

## Image Pins

`devops k8s image-pins` renders each Argo CD Application of the environment tree as Argo CD does, and resolves each image that the rendered objects name in its registry, as an anonymous client, without pulling it. A path source renders with `kubectl kustomize`, and a chart source with the pinned `helm` and the value files that its `$<ref>` sources name, so a tag that a value file sets is checked too. A git source of the repository that holds the tree reads the checkout. A git source of another public repository, such as the product base of devops-cli that an infra repo names, is fetched at its `targetRevision` (a shallow `git fetch`, https only, that adds no credential of its own: a private repository resolves only where the git configuration of the host gives one). `devops k8s image-pins k8s/devops` renders one kustomization folder in place of the Applications. A folder holds no `ImageUpdater` object, so `--managed <repository>` names each repository whose tag the deploy sets, such as the images of devops-cli in the product base, and the check does not refuse or resolve their images. The chart render leaves out the chart's test manifests (`--skip-tests`), because Argo CD does not apply a Helm test hook. It does not resolve the images that an `ImageUpdater` object names, because Image Updater moves them ([Service Image Updates](#service-image-updates)), or the images of a registry that only the cluster or the host reaches. Before it resolves an image, it fails on each image that has no digest and the `latest` tag or no tag, unless an `ImageUpdater` object names it: each pull of such an image can get a different image. The CI job `image-pins` runs it on each pull request that changes `k8s/`, so a wrong tag fails the pull request and not the sync. It resolves each image with a HEAD request of its manifest, which Docker Hub does not count as a pull.

## Service Image Updates

Application `argocd-image-updater` runs [Argo CD Image Updater](https://argocd-image-updater.readthedocs.io/en/stable/) in namespace `argocd`, from the argo-helm chart pinned to a version like the other chart Applications. Its one ImageUpdater, `devops` in `k8s/argocd/image-updater-values.yaml`, keeps the `devops` Application on the digests that `ghcr.io/dan-petty/devops-cli/service:latest`, `ghcr.io/dan-petty/devops-cli/runner:latest` and `ghcr.io/dan-petty/devops-cli/mcp-server:latest` point at. The text below describes the Service image; the runner image of CronJob `devops-cli-runner` and the image of Deployment `mcp-server` are handled in the same way. The release publishes each of the three, and a test fails when a manifest names an image of this repository that no job of `release.yml` pushes (#4324). After the first release that publishes the MCP server image, a person makes the GHCR package `mcp-server` public, as the package `service` is, or the pod stays in `ImagePullBackOff`:

- Every two minutes it reads that digest. When the Application runs another one, it writes `ghcr.io/dan-petty/devops-cli/service:latest@sha256:<digest>` into the Application's `spec.source.kustomize.images`, and Argo CD rolls roadmap-service and CronJob `devops-cli` onto it. Git names the image untagged, and that entry sets its tag and digest.
- It updates the image also when no pod runs it, because the image sets `forceUpdate: true`. Without it, Image Updater updates only the images that a pod in the Application's tree runs, and no such pod runs this image: CronJob `devops-cli` is a suspended template, `roadmap-service` can be at 0 replicas, and the Jobs that `devops k8s run-job` starts are outside the tree. ImageUpdater `devops` then stays Ready with `imagesManaged: 0` and updates nothing. When the Application already names the digest, it writes nothing.
- It commits nothing to git. The `cluster` Application leaves `spec.source.kustomize` on `devops` alone, as it does for the host patches, and deploy-stack's merge patch replaces only `kustomize.patches`. If the `devops` Application is re-created, it renders the untagged image (`latest`; with `IfNotPresent` a node pulls it only when missing) until the next poll writes the digest again.
- Both containers set `imagePullPolicy: IfNotPresent`, so a node pulls a digest once, and a registry outage does not block a restart onto an image the node holds.
- It acts only on Argo CD Applications, so a native `devops k8s deploy-stack` installs no release of it: a cluster without Argo CD has no Application to update, and its devops stack runs the untagged image, `latest`.

Read what it deployed:

```bash
kubectl -n argocd get imageupdater devops          # Ready, and when it last checked
kubectl -n argocd get imageupdater devops -o jsonpath='{.status.recentUpdates}'
kubectl -n argocd get application devops -o jsonpath='{.spec.source.kustomize.images}'
devops argo cd apps status devops                   # exits 1 when the pinned digest is not the one latest names
kubectl -n argocd logs deploy/argocd-image-updater-controller --tail=50
```
