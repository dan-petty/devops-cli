# Service design patterns

This document gives the design patterns of each service and workload of devops-cli in the cluster. Each pattern has a rule, the reason for the rule, and the check that holds it. Use it when you design a new service, a new Job or a new Workflow, and when you change one.

This document is the project profile of the patterns (owner, 2026-11-13: a spec holds general guidelines, a project profile and generated facts). The [guidelines](guidelines/index.md) hold the general rules, and this document links them and does not copy them. The patterns add the decisions of this project, from the [ADRs](adr/README.md) and the owner decisions on issues. Commands and checks give the facts. This document holds no measured value and no state of a workload ([Audit](#audit)).

## Scope

- **In scope.** Each workload of `k8s/devops/` and the code of devops-cli that runs in it. Also the LLM gateway and the services that it uses in `k8s/llm/`: Portkey, the gateway database, Qdrant and the Valkey instances.
- **Out of scope.** A cluster tool that a vendor chart deploys and that runs no devops-cli code. Examples are Argo CD, the Argo Workflows controller and the monitoring stack. The [Kubernetes guideline](guidelines/kubernetes.md) covers their resources. The workstation is also out of scope.
- **Other documents.** [docs/CLUSTER.md](CLUSTER.md) tells how each workload runs, and [k8s/README.md](../k8s/README.md) tells how to set up the cluster. The [production readiness guideline](guidelines/production-readiness.md) gives the checklist of a new service. [ARCHITECTURE.md](../ARCHITECTURE.md) gives the patterns of the code.

## Use this document

1. Read the groups of each part that you design or change.
2. Meet each pattern. If a workload cannot meet a pattern yet, write its behavior and the reason in its section of `docs/CLUSTER.md` or `k8s/README.md`. Link the issue that removes the reason.
3. In the pull request, name the check of each pattern ([How a pattern is checked](#how-a-pattern-is-checked)).
4. To change a pattern, first get its source: an ADR, an owner decision on an issue, or an upstream document. Then change the row in the same pull request as the code.
