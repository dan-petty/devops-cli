# Task: The Embedding Benchmark Takes No Endpoint From an MCP Client and Counts Failed Embeddings as Failures (#954)

**Issue**: [#954](https://github.com/dan-petty/devops-cli/issues/954)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p2-medium
**Scope**: scope/ai

## Description
A triage of review session `20261001-224227` against `release/v0.2.25` (c279c18) confirmed two defects in the benchmarks. Each is fixed as the issue's **Fix** line says, with the differences noted below, and each has regression tests that fail on e3ff98c, this branch's base, and pass here.

- **An MCP client chose the server, and the AI key went with it.** MCP `benchmark_embeddings(provider, model)` checked only for a leading hyphen, and `devops ai benchmark` reads `model@endpoint` as a server to send that model's requests to. `_engine_for_model` then built an `EmbeddingsEngine` with the client's provider, the client's endpoint as `api_base_url` and `get_ai_api_key(settings)`, so `provider="openai", model="x@https://<host>"` sent `POST https://<host>/v1/embeddings` with the configured key as its bearer token.
  - **The MCP check** (`ai/mcp/server.py`). `benchmark_embeddings` calls `_validate_mcp_benchmark_target`, which raises `ValidationError` before anything is dispatched: `field="provider"` for a provider outside `CONST_AI_PROVIDER_IDS`, and `field="model"` for a model holding any of `CONST_MODEL_ENDPOINT_MARKERS` (`@`, `://`), anywhere in the string, so a comma-separated list cannot slip one in. The messages are `ERRORS.mcp.unknown_provider` and `ERRORS.mcp.model_names_endpoint`. `CONST_AI_PROVIDER_IDS` (`config/constants.py`) holds the five ids `devops ai config --provider` takes; it replaces `_PROVIDERS` in `commands/ai.py`, which is removed without an alias. The tool's description says it runs on the configured servers.
  - **The key helper** (`ai/benchmark/runner.py`). `_key_for_endpoint(settings, client_config)` returns the configured AI key only when the client sends it to the configured `ai.api_base_url`, `ai.gateway_url` or the configured provider's own API (`CONST_AI_PROVIDER_API_BASES`, new), compared by scheme, host and port (`_url_origin`, with the scheme's default port), and `''` anywhere else. `EmbeddingBenchmarkRunner._engine_for_model` and `BenchmarkRunner._client_for_model` use it. It differs from the issue's `_key_for_endpoint(settings, endpoint)` in one respect: it reads where the key goes from the client's config instead of taking the override URL. A gateway client sends only to `gateway_url` (the LLM client's `_api_base` and the engine's `_openai_compatible_base_url` both do), so judging the override would have stripped the key from every `--provider gateway` chat benchmark, whose servers are Ollama URLs. Other providers send to `api_base_url`, which is the override when there is one, or to the provider's API.
  - **`''` is no key.** No engine or client change was needed. `EmbeddingsEngine` falls back to `OPENAI_API_KEY` or the keyring only for `api_key is None`, and `_embed_openai` sends `Authorization` only for a non-empty key. `LLMClient` stores `api_key or ""` and looks nothing up when it is given a config. The regression test pins this with `OPENAI_API_KEY` set.
  - **No suite.** `suite._client_for_model` and the MCP `benchmark_suite` tool are gone since #950, so the MCP check covers `benchmark_embeddings` only and the helper has the two callers above.
- **Failed embeddings were scored.** `evaluate_model_on_server` caught every embedding failure, logged it and scored the model anyway. With every call failing, `p50 = 0.0` earned full latency points and `run()` named the model the lowest-latency and, at dimension 0, the most memory-efficient. Since #945, `embed_texts` raises `EmbeddingsError` for every failure and returns no hash vectors, so `EmbeddingVector` and `is_fallback` no longer exist. The issue's `is_fallback` check therefore has nothing to read, and the fake engine in the regression test raises `EmbeddingsError`, as the engine does for an unreachable node or a model it does not serve.
  - **The result** (`models/benchmark.py`). `EmbeddingBenchmarkResult` gains `failed: bool = False` and `error: str | None`, and `latency_ms_p50` and `latency_ms_p95` are `float | None`, default `None`. `EmbeddingServerSummary.avg_latency_p50_ms` is `float | None` too, for a server none of whose runs timed a request.
  - **The run** (`ai/benchmark/embedding_runner.py`). Building the engine and every request sit in one `try`. The first `DevOpsCLIError` (an `EmbeddingsError`, or a refused endpoint's `InvalidURLError`/`SSRFBlockedError`) returns `_failed_result`. That result has the error cut to `CONST_MAX_ERROR_DETAIL_LENGTH`, the latencies of the probes that succeeded before it, or `None`, `is_normalized=False` and no scores, and it prints `✗ <model> on <server> | <error>`. No request follows the failure. The issue asks only that latency come from successful calls; stopping at the first failure is this change's choice, since a failed run is not scored and more requests would only load a server that already failed. Before, a dead server got every probe, the corpus and the queries. A scored run with no timed request, which happens only with no evaluation pairs, now earns no latency points instead of full ones.
  - **The report.** `run()` records any other exception from a run as a failed result instead of logging it and dropping the model. It sorts by `(failed, -overall_score)`. `_server_summaries` and `_recommendations` read only scored runs, and "Lowest Latency" picks among runs with a latency. The table and Markdown leaderboards give a failed run `✗` instead of a medal, `-` for every metric and `failed` for the score (`_rank_badge`, `_leaderboard_metric_cells`, `_markdown_leaderboard_row`). The Markdown report lists each failed run with its error under "✗ Failed Runs", and the category table leaves failed runs out. A missing latency prints `-`.
- **Docs.** The `--models` help says a `model@url` server gets the AI key only when it is the configured `api_base_url`, `gateway_url` or provider API, regenerated into `docs/CLI_REFERENCE.md` and `docs/commands/ai.md`. `docs/MCP_TOOLS.md` carries the tool's new description. No other doc or knowledge-base page described the override or how a failed model was scored.
- **Left as they were.** The gateway config, the models and `k8s/`. The embedding runner still builds a fresh `AIConfig` whose `gateway_url` is the default rather than the configured one, so a `--provider gateway` embedding benchmark keeps the key only where the two match. That is unchanged by this item and only narrows where the key goes.
- The changelog entry is `changelog.d/954.md`.
