# Task: Release pushes run git with the person's environment, so the configured credential helper answers instead of "could not read Username" (#1124)

**Issue**: [#1124](https://github.com/dan-petty/devops-cli/issues/1124)
**Status**: Done
**Milestone**: v0.2.29
**Priority**: priority/p1-high
**Scope**: type/bug, scope/release, priority/p1-high

## Description
`devops release pr`, `devops release prepare --create-pr` and `devops release tag --push` ran their pushes through `run_subprocess`'s sanitized environment. It drops everything a credential helper needs: the devcontainer's `!gh auth git-credential` helper, set in `GIT_CONFIG_COUNT` and `GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>`; VS Code's helper socket (`REMOTE_CONTAINERS_IPC`); the keyring's session bus; and an SSH agent. #767's pinned `GH_TOKEN` reached git, but in the devcontainer no helper was left to read it, so git asked for a username on a terminal it did not have and failed with "could not read Username".

The git calls in `src/devops_cli/commands/release.py` that reach origin now go through `_run_remote_git_or_exit`: the cut branch push, the release tag push, and the cut's fetch of `origin/release/v<version>`. It calls `run_subprocess(..., isolate_env=False, env=CONST_GIT_NO_TERMINAL_PROMPT_ENV)`. Git gets the person's whole environment, as their own `git push` does. `_pin_github_token` still gives it the session's token as `GH_TOKEN` and no `GITHUB_TOKEN`, or no token at all when gh has no login (#767). `GIT_TERMINAL_PROMPT=0` stops git from asking on the terminal. An askpass program the person configured (`GIT_ASKPASS`, `core.askPass` or `SSH_ASKPASS`, such as VS Code's) still runs, and when none answers, git fails with "terminal prompts disabled". When git fails, `_run_remote_git_or_exit` prints git's reason with credentials masked (`mask_secrets`) and its text shown as written, and exits 1. A failed push opens no pull request, and a failed fetch cuts nothing from a stale `origin/release/v<version>`. `release tag --push` now pushes `refs/tags/v<version>` alone instead of every local tag. Every other git call keeps the sanitized environment.

## Decisions and deviations
- **`run_subprocess(isolate_env=False)` instead of GitPython push functions.** The issue proposed `push_branch` and `push_tags` on GitPython's `Remote.push` with `Git.custom_environment`. `custom_environment(NAME=None)` only drops GitPython's own override and never removes an inherited variable. Checked with GitPython 3.2.0: with `GITHUB_TOKEN=other` in the environment, `custom_environment(GITHUB_TOKEN=None)` still handed the child `GITHUB_TOKEN=other`. So that route could not keep #767's rule: `GH_TOKEN` pinned, no `GITHUB_TOKEN`, and no token when the lookup fails. `run_subprocess` already applies that rule to a copy of the environment. It also keeps the subprocess span, metric and timeout, and the existing `run_subprocess` patches in the tests keep any push off the network. No new function was added to `git/operations.py` or `core/process.py`.
- **Not `CONST_GIT_NONINTERACTIVE_ENV`.** Its `GIT_SSH_COMMAND=ssh -o BatchMode=yes` would override a person's own `core.sshCommand`. `CONST_GIT_NO_TERMINAL_PROMPT_ENV` sets `GIT_TERMINAL_PROMPT=0` only, so an askpass program the person configured still answers.
- **The fetch is included, and fails closed.** `_fetch_remote_release_tip`'s `git fetch origin release/v<version>` has the same root cause for a private repository: under the sanitized environment it failed silently, and the cut trusted a stale or missing `origin/release/v<version>`. Its exit status is now read, and a failed fetch stops the cut with git's reason before `rev-parse` or any checkout. This is what #1366's "The cut's branch check fails closed" criterion asks for. #1366 keeps the Service clone's checkout rule.
- **Git's text is shown as written.** The error is printed with `safe=True`, as `_close_release_milestone_safe` prints its warning, so Rich does not read git's or a hook's text as markup. `! [remote rejected]` keeps its brackets, and a `[/bold]` in a remote message cannot raise `MarkupError`.
- **Narrower tag push.** `refs/tags/v<version>` replaces `--tags`, so a release no longer publishes stray local tags or fails on one, and an error concerns exactly one ref.
- **What the inherited environment means.** Every variable of the person's environment reaches git, the helpers they configured, and their own hooks (this repository installs pre-commit's `pre-push` stage). Their own `git push` runs the same programs with the same environment. Scanners, linters and other tools that run on trees devops-cli does not trust keep the sanitized environment. One limit follows: git's own location variables are inherited too. An exported `GIT_DIR` or `GIT_WORK_TREE` (git exports `GIT_DIR` to the hooks it runs in a linked worktree) points the push and the fetch at that repository, while the cut's other git calls, in the sanitized environment, use `--root`. `devops ci` runs its checks in the sanitized environment, so its tests are not affected. The limit is left to #1397.
- **Timeout unchanged.** As before, a push that overruns `DEFAULT_SUBPROCESS_TIMEOUT_SECONDS` stops only git itself (`subprocess.run`), not a helper or hook it started. That is true of every `run_subprocess` call and is not changed here.
- **What works after this item.** From an agent's shell, `release pr` and `release tag --push` authenticate. `release pr`'s push repeats the remote release branch unchanged. This repository's tags come from `.github/workflows/release.yml` when the release merges, not from `release tag --push`. `release prepare --create-pr` and the automatic cut push a new commit to `release/v<version>`. The repository's `release*` ruleset refuses that push, so they now stop with GitHub's GH013 refusal instead of "could not read Username", until #1280 moves the cut's push target. #1280 should push through `_run_remote_git_or_exit`.
