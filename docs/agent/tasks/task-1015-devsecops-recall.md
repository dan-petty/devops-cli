## Description
#951 (38517a8) made the DevSecOps persona almost silent. Session `20261002-205520` (S5), the first branch review with its prompts, was cold: 367 of 380 persona replies held no finding, and on the 270 files identical to session `20261002-180320` persona candidates fell from 139 to 16. None of the four real findings that sessions S1 to S4 had reported was generated, and all four are still in the code at 38517a8: ingress from `0.0.0.0/0` in `k8s/monitoring/networkpolicy.yaml:18-20` (#953) and to the Jaeger UI in `k8s/otel/networkpolicy.yaml:31-32` (#913's planned follow-up), a broad `except` at `src/devops_cli/ai/rag/investigator.py:293` (#423), and the `trust_remote_code` claim at `docs/VISION.md:12` (#921). Each file got one page and a complete reply with `"findings": []`.

The persona prompt asked every finding for a path from an untrusted source to a sink, said "Most files have no security defect", and excused "a choice the manifests or conventions document as deliberate"; the monitoring policy's comment restates its world-open rule. A NetworkPolicy, a broad `except` and a false claim in the docs have no source-to-sink path, and *Where to Look* had no class for network exposure or error handling. Both NetworkPolicies are configuration pages, whose page prompt #951 also rewrote: it named no exposure class and said "A setting the workload does not need is not a defect". This change fixes those rules in place and keeps what #951 gained: the threat model, the evidence bar, no advisory identifier from memory, and no findings on roadmaps, changelogs, task files and decision records.

### Prompts
- `personas/devsecops/prompt.md` (3,332 to 4,423 characters):
  - **A misconfiguration** is a setting or line you can quote, and what it exposes or permits that its job does not need. It needs no untrusted source. A choice the manifests or conventions justify, by saying why it is safe, is not a finding. A comment that only restates the rule or names its sources is not a justification. The vulnerability definition is unchanged. The justification is part of the definition, so it reaches every misconfiguration class; in the **Container & Kubernetes** bullet, where #951 had "document as deliberate", it did not reach **Network Exposure**. That bullet now reads as #951 left it, without the sentence.
  - **Return no finding** when you can quote no vulnerability, no misconfiguration, no false security claim in a document and no other defect a *Where to Look* class names. "Most files have no security defect" is gone. The false security claim keeps the documentation prompt's rule reachable for this persona, which reviews documentation pages too, and the last clause covers a broad `except`, which is none of the first three. After the first measurement the line also says "A value that reaches no sink you can quote is not a vulnerability, and most code has none": dropping the base rate had raised false findings on Python files from 1 to 6, none of them in a restored class.
  - *Where to Look* adds **Error Handling**: a broad `except` that hides an unexpected error from the operator by logging it below warning or not at all, or that swallows one on a path where failing closed matters, such as authentication, verification, a security check or data integrity. Report it as LOW, and higher only with a quoted consequence such as a skipped check. (Revised after the first measurement: "LOW at most" read as a ceiling on a class the model already treats as minor, and it found no broad except in 9 samples.)
  - *Where to Look* adds **Network Exposure**: a NetworkPolicy, Ingress, Service, firewall rule or security group that admits `0.0.0.0/0`, every namespace or every pod to a port whose known consumers are fewer than that. A port the manifests or conventions say must face every source, and say why that is safe (an ingress controller, an API that authenticates every request), is not exposure; a port open to every address without that reason is. Egress to every address with cloud metadata (`169.254.169.254`) blocked is not exposure, and no NetworkPolicy rule is SSRF. A NetworkPolicy does not publish a port: before calling a port public, the finding quotes the node port, load balancer, host port or Ingress route that publishes it; without one, MEDIUM at most. (Revised after the first measurement: all six network findings claimed internet reach behind ClusterIP Services and came in HIGH, and a false metadata-SSRF finding was reported on an egress rule that already blocks the address.)
- `personas/devsecops/role.md`: evidence is "where an untrusted value enters and the line where it does harm, or the setting that permits more than its job needs". It framed evidence only as the untrusted path, the same rule as the prompt's.
- `tasks/config_review_prompt.md` (1,333 to 1,538 characters): **Network Exposure**, a NetworkPolicy, Ingress, Service or firewall rule that admits more sources to a port than its consumers need, such as `0.0.0.0/0` or every namespace. *Resource Bounds* keeps #951's decision but says what it meant: "A missing setting the workload does not need, such as a CPU limit, is not a defect". Read as written, "A setting the workload does not need is not a defect" excused the world-open rule the persona's misconfiguration definition reports, in the page prompt both NetworkPolicies get.
- `tasks/docs_review_prompt.md` (1,323 to 1,667 characters): #951 did change this. Before it, *Technical Accuracy & Consistency* asked reviewers to check what the documentation cites against the code. After it, *What Counts* needs "the code line" that contradicts the text, which a claim about a control the code lacks, such as `VISION.md:12`, cannot give. *What Counts* now lists "a false security claim", and **Security Claims** defines it: a statement that the program applies a security control, such as a check, a gate or a guard, is a claim about the code, false when the code contradicts it or applies no such control; quote the document line, and the code line that contradicts it or the code read that lacks the control. *Plans and Records* is unchanged.

### Measurement protocol
`docs/SELF_IMPROVEMENT.md` gains *Scoring recall on known findings (#1015)* after #951's corpus A/B:
1. Worktrees for A (38517a8), B and T (the set's revision, whose files and `.devops/review.md` both arms review).
2. Three rounds of `devops review path "${files[@]}" --no-cache --no-static-scan --no-verification`, alternating arms, both arms pinned to one model, each arm with its own `DEVOPS_CLI_DATA_DIR`. The paths are a quoted array, so zsh, the devcontainer's shell, passes each as its own argument. No scanners run, so every candidate is the model's.
3. A scoring script. A match names a file of the set and cites a line inside its range; the script prints found and reported counts per finding, each match's location and title, and then every other candidate on the set's files.
4. The bar: each finding found in at least 2 of 3 samples, counting a sample only when one of its matches describes the set's defect. The person labels the unmatched candidates.
5. The precision guard on S5's 15 reported files (at most 33 false or opinion findings, 1.5 times S5's 22), with the scanners S5 ran. Bandit failed in S5 (#1009), so its findings are counted apart.
6. A review from both arms, fresh and without scanners, of the files the restored classes reach: every NetworkPolicy, Ingress and Service manifest at T, `tf/aws/main.tf` (routes to `0.0.0.0/0`), `SECURITY.md`, `ARCHITECTURE.md` and `docs/VISION.md`. Each arm's false and opinion counts go in the PR.

### Review follow-up
A review of this change found six defects, each verified before it was fixed:
- **The configuration page prompt** contradicted the restored rule for both NetworkPolicies, and the class test accepted any class the persona names, so it could not see that. `classify_file_context` returns `configuration` for both policies. Fixed as described under *Prompts*. The class test now builds the page each entry gets and fails when that page carries a rule from `_SILENCING_RULES`, which gains the old sentence. Red: `[('k8s/monitoring/networkpolicy.yaml', 'A setting the workload does not need is not a defect'), ('k8s/otel/networkpolicy.yaml', 'A setting the workload does not need is not a defect')]`.
- **The scoring windows** were the cited line widened by three. Run on S1, S3, S4 and S5, the old script scored the monitoring and investigator findings 0/4, although the evaluation records them reported in four sessions and in S3 and S4. It also matched S3's false finding at `VISION.md:7-9` to `:12`. The ranges are now the defective constructs with no widening, and the script lists every other candidate on the set's files. Run on the same four sessions, it scores monitoring 3/4, otel 3/4, investigator 2/4 (S3, S4), VISION 3/4, and each `pricing.py` except 1/4 (S5), and lists the four neighbouring `VISION.md` findings of each old session as unmatched. Red: the score test expected monitoring 18-47 found 2/2 (the 46-48 port list among them) and got 18-20 found 1/2, with no unmatched list.
- **Error Handling** read as a closed list ("matters: authentication, …") that the investigator's grounding lookup is not on, and the no-finding line named only three kinds of finding, none of them a broad `except`. The issue's measurement requires the investigator finding, so the paths are examples and the rule names the hidden-error case; the no-finding line covers any defect a *Where to Look* class names. "where failing closed matters: authentication" is in `_SILENCING_RULES`.
- **Network Exposure** had no justification of its own: "justify, by saying why it is safe" sat in the Kubernetes bullet. At 38517a8 the gateway policy admits any source to 4000 and says why that is safe, and the otel policy admits every namespace to its OTLP ports, which every workload uses. The justification is now part of the misconfiguration definition, and the rule fires only where the known consumers are fewer than the sources admitted, or on a port open to every address without a reason. The monitoring policy's comment names its sources and gives no reason, so it stays a finding.
- **The precision guard** held no NetworkPolicy, Ingress, firewall rule or security document, so it could not show noise from Network Exposure or Security Claims. Step 6 reviews those files from both arms.
- **The review loop** expanded an unquoted `$files`, which zsh passes as one argument: each review would have found no files, exited 0 and written no session. `zsh -c 'files="a b c"; printf "[%s]\n" $files'` prints `[a b c]`, and bash prints three lines. The loop uses an array, in the doc and below. Red: `re.findall(r"\$files\b", section)` returned `['$files']`.
