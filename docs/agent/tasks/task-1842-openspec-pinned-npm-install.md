# Task: OpenSpec Installs From a Pinned npm Lockfile With Telemetry Off (#1842)

**Issue**: [#1842](https://github.com/dan-petty/devops-cli/issues/1842)
**Scope**: type/feature, scope/security, scope/ci
**Feasibility**: Checked on 2026-10-22 against OpenSpec 1.14.3, Node 24.22.0 and npm 11.19.1, in scratch directories under `/tmp` with a scratch `HOME` and telemetry off. `npm install --package-lock-only --ignore-scripts` of the pin gave a lockfile of version 3 with 57 packages, every one with a sha512 on `registry.npmjs.org` and none with an install script; run again in a directory named `openspec`, it differs from the first resolution only in the root `name`, which npm takes from the directory. `npm ci --ignore-scripts --no-audit --no-fund --engine-strict --replace-registry-host=never` with an explicit user and global configuration and cache installed all 57 in 2 s, and the `.bin/openspec` link is relative, so the tree still ran (`openspec --version` printed 1.14.3) after it was renamed to another directory. One flipped character in the first package's integrity, and again in the last, failed with `npm error code EINTEGRITY`, and the last left a partial `node_modules` (`zod`), which is why the install is staged. Without `CI=true` and with a fresh cache npm asked the registry for a newer npm and printed a notice, so the installer and the audit command switch the update notifier off; the devcontainer already sets `npm_config_update_notifier=false`, which the sanitized child environment of `devops` drops. `npm audit --package-lock-only --prefix <dir>` needs no install: it printed `found 0 vulnerabilities` for the pin and exited 1 for a lockfile with `lodash` 4.17.15. It exits 1 for an audit that could not run as well: with `--json`, a registry that refused the connection and one that answered the advisory request 404 each gave exit 1 and a report with an `error` object and no `metadata`, while a registry that answered with an advisory gave exit 1 and `metadata.vulnerabilities.total` 1, and one that answered with none gave exit 0 and a total of 0 (all four recorded against loopback registries in `tests/fixtures/npm_audit/`). uv's exit status keeps the two apart, 1 for a finding and 2 for an audit that could not run. `npm audit signatures` needs an installed tree (it found no packages to audit without one) and verified 57 packages after `npm ci`. `osv-scanner scan source --lockfile package-lock.json` read the 57 packages and found no issues. The installer ran end to end into a scratch data root: 2.5 s, the link resolved into `tools/openspec/1.14.3/node_modules/.bin/openspec`, `devops install-tools --check` reported the pin, a flipped integrity failed with exit 1 and left `tools/openspec` empty, and with `npm` off `PATH` it failed first naming `npm`. The `static` job needs no Node step for `npm audit`: the `ubuntu-24.04` image the job runs on (version 20261012.334.1, its README and `install-nodejs.sh` in `actions/runner-images`, read through `devops gh api`) installs Node.js 22.23.3 and npm 10.9.9 as the default Node.

## Description

OpenSpec is a Node tool, and `tools.lock` had binary and Python kinds only. This adds the third kind and everything that makes the tool installable, reproducible and silent, so the later steps of [ADR 0010](../../adr/0010-openspec-is-the-spec-and-change-proposal-layer.md) can use it. Nothing is removed: the Python and binary kinds are as they were, and no second install path is added.

- **The Node kind.** `tools.lock` has `[npm.openspec]` with the version, description, source and the command, and `NpmTool` (frozen, `extra="forbid"`) is the model beside `BinaryTool` and `PythonTool`. A Node tool's integrity data is the directory beside the lock that is named for it, here `src/devops_cli/tools_lock/openspec/`: `package.json` names the one dependency at the exact version and `package-lock.json` records every package, so npm checks the sha512 of all 57 where the root tarball's covers one. `installed_commands` finds the command in `node_modules/.bin` through a `command_dir` each kind declares instead of an `isinstance` test, and `tools_lock_digest()` covers both files of each Node tool, so a change to either changes the digest a review records. The header of `tools.lock` carries the bump runbook for a Node tool.
- **The installer.** `install_npm_tool` fails first, naming `npm`, when it is not on PATH (`require_binary`), since the installer provisions no runtime, Python's included. It stages beside the version directory, copies the two locked files into the stage, and runs `build_npm_ci_cmd()` there through `run_subprocess`. The environment names an empty user and an empty global npm configuration (npm refuses them as one file, and a registry in the caller's configuration would rewrite the lockfile's URLs), a cache of its own, `npm_config_update_notifier=false` and `npm_config_loglevel=error`. The configuration and cache paths live in a scratch directory that goes when the install ends, so the version directory holds only the two locked files and `node_modules`. The stage is renamed into `<user data root>/tools/openspec/1.14.3` and `node_modules/.bin/openspec` is linked into `~/.local/bin`, as for the other kinds. When npm fails, the error carries the first 256 characters of its output, which at log level `error` are its error lines and lead with the code (`EINTEGRITY`); the tail, which the uv runner reports, would be a pointer to npm's log. `install_tool` dispatches the three kinds through a table keyed on the model type.
- **Post-create.** `devops devcontainer post-create` already installs every lock tool, and `install_managed_tools` reports a tool that cannot install as one warning line, so a missing `npm` or a failed `npm ci` is a warning there, and `devops install-tools` is the hard failure.
- **Node.** `.node-version` holds `24`, the `node` feature of `.devcontainer/devcontainer.json` and of the scaffolding template `devcontainer.json.j2` is pinned to `24`, and a contract test keeps all three equal and the feature in `.devcontainer/devcontainer-lock.json`. The lock records the feature, not its options, so it needed no change.
- **The opt-outs.** `OPENSPEC_TELEMETRY=0` and `OPENSPEC_NO_UPDATE_CHECK=1` sit beside `DO_NOT_TRACK=1` in the `containerEnv` of the devcontainer and of the template, `ci.yml` sets `DO_NOT_TRACK: "1"` for every job, and the committed `.claude/settings.json` has an `env` block with the three. `AGENTS.md` names `OPENSPEC_TELEMETRY=0` in its telemetry list and ends at 39,943 of its 40,000 characters. The variables the gate module passes through the `env` argument of `run_subprocess` belong to the scaffold item.
- **The audit.** `CheckSpec` carries `also_cmds`, commands the check runs after `cmd`, each as its own process and without a shell, and `commands` lists them all. The `audit` check is `uv audit` and `npm audit --package-lock-only --json --no-update-notifier --prefix src/devops_cli/tools_lock/<tool>` for each Node tool in the lock. The gate runs both and merges their output, `devops ci audit` runs both and lists them as one plan in a dry run, and `devops ci maintain` runs both too. A vulnerable pin fails all three. `audit_verdict` in `src/devops_cli/core/dependency_audit.py` reads a run by the kind of command it started, with one table keyed on the program: uv by its exit status (1 is a finding, 2 an audit that could not run) and npm by its JSON report (`metadata.vulnerabilities` counts and no `error` object is a finding; an `error` object, no report or a report of none is an audit that could not run). `devops ci audit`, `devops ci maintain` and the gate's row read every audit command through it, show the output of one that failed and say whether it found vulnerabilities or could not run, naming the tool, and a failed audit never stops the other.
- **Renovate.** `.github/renovate.json` turns its `npm` manager off: it can edit neither `tools.lock` nor the files a bump regenerates, and a bump is one deliberate pull request with the runbook.
- **Documents.** `SDLC.md`, `RELEASE_CYCLE.md`, `ROUTINE_TASKS.md`, `TESTING.md`, `DEVCONTAINER_USAGE.md`, the README, ADR 0010 and the knowledge-base pages that list the gate's audit say that the audit and the checksum check cover Node tools, and the generated CLI reference carries the new help line of `devops ci audit`.
