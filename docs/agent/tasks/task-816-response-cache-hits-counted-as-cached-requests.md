# Task: Response-Cache Hits Are Counted as Cached Requests (#816)

**Issue**: [#816](https://github.com/dan-petty/devops-cli/issues/816)
**Status**: Done
**Milestone**: v0.2.29
**Priority**: priority/p1-high
**Scope**: scope/ai, scope/telemetry

## Description
`LLMClient.chat_messages` returned a response-cache hit without recording it. Only a dispatch called `track_request_spend`, the one route to the spend ledger, the `devops_cli_ai_requests_total` counter and the review profiler, so the ledger's cached count, the counter's `cached="true"` series and every `profile.json`'s `cached_calls` stayed 0. Review sessions in which the cache answered 69% of requests reported none. The client now records a hit at its hit return, after the cached entry passed the client's check, as one cached request with no tokens and no cost. Spend reports and the ledger's Prometheus exporter leave hits out of what counts backends and executed requests, the three single-point `devops_cli_llm_cache_*` gauges are gone, and the AI spend dashboard charts the hit share.

## Key Changes
- **Client** (`ai/client/unified.py`). `_record_cache_hit` calls `track_request_spend(cached=True)` with 0 prompt and 0 completion tokens, server and `backend_info` `cache`, no `served_by`, `request_type` `chat_cache_hit`, and the stage from the running `stage_scope`. `chat_messages` calls it inside `if hit is not None:`, so `chat`, the persona agent (`ai/agents/agent.py`) and the verifier (`ai/review/verification.py`) all record through it. The dispatch recorder is not reused: it estimates missing tokens and would parse a server out of `backend_info`. Like the dispatch recorder, it imports `track_request_spend` from `devops_cli.ai.spend` when called, so tests that patch it there still see every call.
- **What is not a hit.** A cached entry the client rejects (empty content, an error payload, a failed validator) and the append-cache starting-point lookup both go on to a dispatch, which records the call once with `cached=false`. Counting at the cache layer would have counted both, because `LLMResponseCache.get` raises its counters before the client checks the entry.
- **Constant.** `CONST_RESPONSE_CACHE_SERVER = "cache"` (`config/constants.py`) is the `backend_info` of a hit and the server of its ledger row.
- **Ledger** (`ai/spend/ledger.py`). The overall and per-provider server counts are `COUNT(DISTINCT CASE WHEN cached=0 THEN server END)`, as the "Active AI Backends" panel already filters `cached="false"`. The provider breakdown reads a count of 0 as 0; it turned 0 into 1, so a provider whose rows were all hits showed one server. The `cache` server is never local, so hits under a local provider do not add to `local_requests`. The model breakdown carries a cached count, `ModelSpendSummary.cached_requests`.
- **Exporter** (`ai/spend/prometheus.py`). `devops_cli_ai_requests_total` emits `request_count - cached_requests`, the requests sent to a model, as its help text says. `devops ai spend report` tables still count every request, so the model table matches "Total Requests Processed".
- **Gauges removed** (`ai/response_cache.py`). The four `record_metric("devops_cli_llm_cache_*")` calls and their import. Each sent a gauge of 1.0 from a short-lived process, so it counted nothing, and no dashboard, test or document read them. The cache's own `hit_count` and per-process counters behind `devops ai cache status` are unchanged.
- **Dashboard** (`k8s/monitoring/dashboards/ai-spend.json`). "Response Cache Hit Share" (id 19, below the token row): `(sum(increase(devops_cli_ai_requests_total{cached="true"}[1h])) or sum(increase(devops_cli_ai_requests_total[1h])) * 0) / sum(increase(devops_cli_ai_requests_total[1h]))`, in the "Command Error Share" pattern, with the `increase()` limits in its description. "AI Requests in Range" and "Request Rate by Model" now say they include cache answers, since they rise by the hit volume. "Active AI Backends" keeps its `cached="false"` filter.
- **Tests.** The `spend_ledger` fixture moved from `tests/test_ai_spend_dispatch.py` to `tests/conftest.py`, since three modules now need a tmp ledger behind the client. `Captured` in `tests/test_telemetry_instruments.py` keeps only metric payloads, because an LLM call also exports spans.

## Decisions
- Recording sits in the client, not the cache, per the issue's key question: one place covers every caller, and it counts only replies the client returns. The assessment's plan and the skeptic agree.
- The provider server count got the same filter as the overall count (assessment amendment 2), and the `or 1` fallback became `or 0` (skeptic): with the filter alone, a provider with only hits still showed one server.
- Amendment item 5 offered leaving hits in `local_requests` for #482 or excluding them. They are excluded in `_tally_and_annotate_servers` with one condition, since the cache ran no model and the rest of the change keeps hits out of backend counts.
- The exporter subtracts a cached count rather than redefining `request_count` (assessment amendment 3).
- Tests sit where the skeptic placed them: the client-level hit test in `tests/test_telemetry_instruments.py` (it checks OTLP points and uses `captured`), the rejected-entry and append-cache test in `tests/test_ai_spend_dispatch.py`, with the moved `spend_ledger` fixture rather than a copy.
- The review test reruns the same review instead of building cache keys by hand: the first run records each request's key, the cache then keeps page 1's reply and the verifier's, and the profiled run sends only page 2. It reviews a YAML file with static scanners off and runs from the target directory: payload set-up probes the working directory for manifests and network references, which scanned this repository and took about 1 s. It stubs RAG and the tokenizer load. Its call phase takes about 0.4 s.
- #1150 and #1151 will delete the verifier and persona stages; the review test goes with them. The client-level tests cover chat and analysis, which keep the response cache.
