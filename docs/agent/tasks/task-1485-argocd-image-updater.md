## Description

The owner asked on 2026-10-09 for Argo CD Image Updater to deploy the Service image, `ghcr.io/dan-petty/devops-cli/service`, with the digest strategy on `:latest` and no commits back to git. It is the only image in the cluster whose lifecycle this repository controls: Application `devops` runs it in the `roadmap-service` Deployment and in CronJob `devops-cli`. This item installs and configures Image Updater. #1486 removes the custom tag process (the cut's `newTag` bump, `devops release check`'s pin check and release-branch publishing) in v0.2.32, so the two never reach `main` in the same merge.

- **Install.** A new Application, `argocd-image-updater` (`k8s/argocd/apps/argocd-image-updater.yaml`), follows the repository's chart pattern: project `homelab`, the argo-helm chart `argocd-image-updater` pinned to 1.3.1 (app v1.3.0, built against Argo CD 3.5), values from `$values/k8s/argocd/image-updater-values.yaml` on `main`, destination namespace `argocd`, automated prune and self-heal, retry 5, and the resources finalizer. The `cluster` app-of-apps picks it up from `k8s/argocd/apps/`. AppProject `homelab` already admits `https://argoproj.github.io/argo-helm`, namespace `argocd` and every cluster-scoped kind, which covers the CRD and the ClusterRoles. Image Updater talks only to the Kubernetes API and selects Applications in its own namespace, so it runs in `argocd`.
- **Configuration.** `k8s/argocd/image-updater-values.yaml` holds one ImageUpdater, `devops`, in the chart's `extraObjects`: `applicationRefs` selects `namePattern: devops`, with image alias `service`, `imageName: ghcr.io/dan-petty/devops-cli/service:latest` and `updateStrategy: digest`. It has no `writeBackConfig`, so the default `argocd` method writes `service:latest@sha256:<digest>` into Application `devops`'s `spec.source.kustomize.images`, and nothing is committed. Every other chart value keeps its default: a 2-minute poll, no registry entry (the GHCR package is public), no webhook, and no metrics Service or ServiceMonitor (the controller still serves metrics on :8443).
- **Precedence.** Argo CD adds `spec.source.kustomize.images` to the kustomization it builds, which outranks the `newTag` pin in `k8s/devops/kustomization.yaml`. That pin stays until #1486, so the render is never an untagged `latest`, and a re-created `devops` Application renders the pin until the next poll.
- **Self-heal.** The `cluster` app-of-apps already ignores `/spec/source/kustomize` on `devops` with `RespectIgnoreDifferences=true` (`k8s/argocd/bootstrap/cluster.yaml`), so its self-heal keeps the digest. That file's comment now names Image Updater as the second writer of the field.
- **Pull policy.** Both containers already set `imagePullPolicy: IfNotPresent`. Kubernetes defaults a reference tagged `latest` to `Always`, even with a digest; with the digest, `IfNotPresent` is exact and a registry outage does not block a restart.
- **Docs.** `k8s/README.md`'s GitOps section counts 21 leaf Applications (13 Helm), has a new "Service Image Updates" subsection naming the Application and showing how to read the deployed digest, and its "When a release merges into `main`" steps 3 and 4 now describe the rollout through `latest`'s digest instead of the pin and the manual `rollout restart`.

## Decisions and Deviations

- **The ImageUpdater ships in the chart's `extraObjects`.** It syncs in the same sync as its CRD (`templates/crd-imageupdaters.yaml` in the chart), and Argo CD skips the dry run of a resource whose CRD is part of the same sync, so the Application needs no `SkipDryRunOnMissingResource`. `k8s-monitoring` and `dcgm-exporter` need that option because their ServiceMonitor CRD comes from another Application. Since #1130 dcgm-exporter renders no ServiceMonitor and its Application drops the option. `k8s-monitoring` uses `extraObjects` the same way.
- **No native `deploy-stack` release (AGENTS.md's stack-path rule).** Image Updater acts only on Argo CD Applications, and a cluster without Argo CD has none for it to update; its devops stack applies the raw manifests, which name the untagged image, `latest`. Registering the chart in `_HELM_RELEASES_BY_STACK` would also fail on a fresh native cluster: chart 1.3.1 ships its CRD in `templates/`, not `crds/`, and Helm builds every object of a release before it applies any, so the ImageUpdater fails with `ensure CRDs are installed first`. On the Argo CD-managed homelab, `devops k8s deploy-stack` delegates to Argo CD, and the `cluster` app-of-apps syncs the new Application from git with no manual step. Traefik and `gpu-feature-discovery` have no native release either. AGENTS.md's sentence names only `_MANIFESTS_BY_STACK` and `_HELM_RELEASES_BY_STACK`, and this change leaves it as it is: whether it names Argo CD-only add-ons is the owner's decision.
- **The CronJob already set `IfNotPresent`.** The issue says the CronJob gets it, but `k8s/devops/cronjob.yaml` has set it since v0.2.26, and the live CronJob runs with it. No manifest changed; the render test pins both workloads.
- **Chart defaults stay.** These include the controller's own `imagePullPolicy: Always`, the chart's ClusterRoles (`createClusterRoles: true`) and the `crds.keep` policy. The chart's appVersion (v1.3.0) lags the app's v1.3.1 by one patch; v1.3.0 already has the GHCR pagination fix and is built against Argo CD 3.5.
- **The custom tag process stays.** The `newTag` pin, the cut's bump, `devops release check`'s pin check and release-branch publishing stay until #1486. Until then the pin only decides what a re-created `devops` Application renders before Image Updater's next poll.
- **The release that carries this.** When it merges, `main`'s sync moves the pin to the new tag before Image Updater runs, and the image exists because the release branch published it. Image Updater's first poll then writes `latest`'s digest. If that poll comes before `release.yml`'s run on `main` points `latest` at the new image, roadmap-service runs the previous release for a few minutes until the next poll. Even when the digest is the same image, the reference changes from `service:vX.Y.Z` to `service:latest@sha256:<digest>`, so the pod restarts once.
- **The merge-patch test runs real kubectl.** `kubectl patch --local` applies a patch to a file the way the API server applies it to an object, and makes no request. The same suites already run `kubectl kustomize` and git for real.
