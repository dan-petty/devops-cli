# Task: Verdicts Land on the Finding Shown, Record Who Gave Them, and Machine-Invalidated Candidates Can Be Overturned (#949)

**Issue**: [#949](https://github.com/dan-petty/devops-cli/issues/949)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p1-high
**Scope**: scope/review

## Description
A person could not reliably give a review verdict, and the record did not say who gave one. `devops review findings --status/--verified` renumbered the filtered list from 1 while `verify --index` indexed the unfiltered findings.json, the MCP `verify_finding` tool accepted 0, and `--title` took the first substring match. Candidates the machine invalidated never reach findings.json, so no command could show or restore one. Every CLI and MCP caller was stamped `human`, `--status` defaulted to INVALIDATED, and a reset to UNVERIFIED left the learned-catalog and ledger entries its verdict created. Found while analysing review session `20261001-224227`.

- **Adjudication** (`ai/review/adjudication.py`, new): `Verdict(status, adjudicator, reason, perimeter, regression_test)`, which `_record_verdict` applies through `apply_verdict`. `numbered_finding` resolves a 1-based number and `number_by_title` resolves a title substring that exactly one finding contains, raising `ValidationError` otherwise. `judge_reported(reported, candidates, number, verdict, changes)` records the verdict on a finding in findings.json and on each candidate it reports, and `judge_candidate(candidates, reported, number, verdict, changes)` on a candidate and its copy in findings.json, so the two files agree. The copy in findings.json holds the catalog and ledger ids of both, so each id is held by one finding and a reset of either withdraws it once. Without a copy, a VERIFIED or MITIGATED verdict on a candidate appends one, marked `moved_from_candidate` with the candidate's number, unless `review_schema._are_findings_duplicate`, the consolidator's own test, run with each reported finding's status, matches a reported finding. Then it raises `ValidationError` naming that finding's number for `--index`, before either file changes: a candidate merged away by consolidation, or another persona's report of a defect findings.json already holds, is never added twice. The perimeter and reason helpers moved here from `commands/review.py` unchanged.
- **Which candidate a finding reports** (`_CandidateIndex`): a copy a verdict moved names its candidate. A finding the pipeline reported is the candidate of the same first persona, location and title, as consolidation keeps the first report it merges and lists the other personas after it; of several such candidates, the ones with its description, or all of them when none has it. So a verdict on one persona's candidate no longer lands on the finding another persona reported with the same title at the same location. A candidate whose copy reports other candidates as well, which nothing tells apart from it, is refused with `candidate_copy_ambiguous`, naming the finding to judge with `--index`, which records the verdict on each of them.
- **One verdict at a time** (`adjudicating`, `write_session_files`): `review verify` holds an exclusive `fcntl.flock` on `<session>/.verify.lock` (`CONST_REVIEW_VERDICT_LOCK_FILENAME`) from reading the session files to writing them, so verdicts given on one session at once, as an MCP client's parallel calls give them, take turns instead of writing over each other. `EntryChanges` collects what the verdict does to the catalog and ledger. A person's verdict records its entries before the files are written, so the files hold their ids, and `RecordedEntries` keeps each entry it updated as it was before; when the block raises, `undo` puts each of those back, every field included, and removes each entry the verdict created. A reset only releases the ids its findings held, and `settle` withdraws them after the files are written. `write_session_files` puts back the files it already wrote when a later one fails, and the CLI reports `session_write_failed` and exits 1.
- **Side effects**: only a `human` verdict calls `auto_record_invalidated_finding` (INVALIDATED) or `record_mitigated_finding` (MITIGATED). The finding keeps one id for each entry the call wrote, created or added to; a builtin catalog entry it matched is left out. `SavedFinding` gains `learned_catalog_ids` and `mitigation_ledger_ids` for them. They are not on `Finding`, so no model reply can set them. `MitigatedFindingEntry` (`ai/review/mitigations.py`) gains `verdict_count`, which `record_mitigated_finding` raises by one when it updates an entry; a learned catalog entry's `occurrence_count` already counted. A reset to UNVERIFIED releases each id and withdraws it once the session files are written, through `load_common_hallucinations`/`save_common_hallucinations` and `load_mitigated_findings`/`save_mitigated_findings`: the entry's count drops by one, and an entry at its last count is removed, so a reset never takes away what another finding's verdict, another session's, or a machine invalidation also recorded. Then both lists are cleared. Other verdicts append, so a later reset withdraws everything earlier verdicts recorded. Because every finding whose person's verdict created or updated an entry holds its id, a reset never removes an entry another finding's verdict still depends on: the review's two probes, the same finding INVALIDATED by a person in two sessions and MITIGATED in two sessions with `--regression-test`, now give both findings the id, and resetting the first leaves the entry at count 1 behind the second. What an INVALIDATED verdict teaches the catalog is unchanged and left to #950.
- **Provenance**: `Adjudicator` (`ai/review/verdicts.py`) is a `StrEnum` of `human` and `agent`, `VerifiedBy` gains `"agent"`, and `CONST_VERIFIED_BY_AGENT` joins `CONST_VERIFIED_BY_HUMAN` in `config/constants.py`. The MCP `verify_finding` tool records `agent`: it appends `--adjudicator agent` last, so an earlier argument cannot override it. `_record_verdict`, `judge_reported` and `judge_candidate` refuse an agent's verdict on a finding whose `verified_by` is `human`, on a finding whose candidate is one, and on a candidate whose copy in findings.json is one, before anything changes, so an agent can neither replace a person's verdict nor withdraw what it recorded; only a person's verdicts hold ids, so no agent's reset withdraws any. History ranking (`ai/review/history.py`) counts `verified_by == "human"` in its first tier, taking the larger of the counts in findings.json and candidates.json: every verdict on a reported finding with a candidate reaches candidates.json too, and a verdict on a candidate kept out of findings.json is only there, while a persona-loop session has no candidates.json. So a newer machine re-run never displaces a session where a person judged candidates, which keeps #607's guarantee for the verdicts this item adds; deferring it to #771 would have left the new `--candidate` verdicts outside that guarantee, for a one-line change. Its second tier, findings with any verdict, leaves out `agent` verdicts as well, so an agent's verdict never raises its session's rank; the module docstring says so, and the `review stats` comment no longer calls findings.json the only file verdicts are written to. `FeedbackRecord.verified_by` defaulted to `"human"` and now defaults to `CONST_VERIFIED_BY_UNKNOWN`, so the exporter labels a record `human` only when the finding says a person judged it.
- **CLI** (`commands/review.py`): `review findings` keeps each finding's place in the file as its number whatever the filter, and `--candidates` lists candidates.json. `review verify` takes exactly one of `--index`, `--title` and `--candidate`. `--status` is a required keyword-only option, and `--adjudicator` defaults to `human`. The table, details and status-filter code moved into `_listed_status`, `_finding_row` and `_print_finding_details`, and the now-unused module logger is gone. `path`, `branch` and `pr` each drop their second `load_settings()`.
- **Docs**: `verify` and `findings` have multi-paragraph docstrings, which describe the two files kept in step, the refused ambiguous candidate and verdicts taking turns, and new help strings (`lang/en/help.py`), and `docs/commands/review.md`, `docs/commands/ai.md`, `docs/CLI_REFERENCE.md`, `docs/MCP_TOOLS.md` and the README matrix are regenerated. `AGENTS.md` tells agents to record verdicts with `--adjudicator agent` or the MCP tool, which records `agent`, never to record `human`, and that `review verify` refuses an agent's verdict on a finding a person judged. It does not claim MCP clients cannot record `human`: see below. The knowledge base (`cli_command_reference.md`, `tasks/ai_code_review.md`) describes the numbering, candidates, provenance and resets, and its `verify <session> 1` examples, which used a positional index that does not exist, use `--index`. `docs/KNOWN_ISSUES.md`'s example gains the session and index it lacked.
- The changelog entry is `changelog.d/949.md`.
- Left as they were: `verify_finding` records `agent`, but the MCP server as a whole does not stop a client recording `human`: `telemetry_profile(command=...)` runs any command line it is given, so a client can run `devops review verify` itself. That hole predates this item, and #980 closes it. An agent's verdict that replaces or resets a machine verdict lowers its session's second-tier count, because the machine's verdict is not kept beside it; keeping both is #771. For the same reason a reset of a candidate a verdict moved into findings.json leaves the copy there as UNVERIFIED, and neither file keeps the machine's INVALIDATED verdict; removing the copy would also renumber the findings after it, which `--index` takes. The lock is per session: verdicts on different sessions at once, and the review pipeline's own invalidations, still write the learned catalog and the ledger without a shared lock, as they always have, so a count can be lost between them, and putting back an entry a failed verdict updated also takes back what another session's verdict wrote to it in the meantime; one write path for machine and human verdicts with their side effects is #771. A verdict on a finding consolidation merged from several personas' reports reaches only the candidate of its first persona in candidates.json; the others keep their own verdicts there. A reset withdraws counts only: the keywords or resolution another verdict's update widened in a learned entry, and the mechanism and perimeter it wrote to a ledger entry, stay. A direct INVALIDATED to VERIFIED change keeps the catalog entry until the finding is reset to UNVERIFIED, as this item scopes reverts to resets. `_prepare_path_content`, `_prepare_branch_content` and `_get_reviews_base_dir` still read settings themselves, through the cached file parse. `docs/SELF_IMPROVEMENT.md` still calls `review verify` automated verification; its rewrite belongs to the docs-truthfulness items.

## Acceptance Criteria
- [x] **Stable numbering.** `test_a_filtered_listing_numbers_findings_as_verify_does` (`tests/test_review_adjudication.py`) writes statuses [UNVERIFIED, VERIFIED, VERIFIED]. `findings --verified` lists the two VERIFIED findings as `2` and `3`, and `verify --index` with the number shown for the second makes the statuses [UNVERIFIED, INVALIDATED, VERIFIED]. On the unchanged code the list showed `1` and `2`, and the verdict landed on the first finding. `test_the_mcp_tool_counts_findings_from_one` asserts the MCP tool refuses index 0 without running the CLI; on the unchanged code it did not raise.
- [x] **Candidates can be judged.** `test_a_machine_invalidated_candidate_a_person_verifies_moves_into_findings_json`: `findings --candidates --invalidated` lists the dropped candidate as `2`. `verify --candidate 2 --status VERIFIED` adds it to findings.json after the reported finding, with `verified_by="human"`, and records the same verdict in candidates.json. `test_a_candidate_judged_again_updates_its_copy_in_findings_json`: a second verdict, UNVERIFIED, changes that copy instead of adding another. `test_a_candidate_reset_also_removes_entries_its_copy_was_given`: a person's `--index` INVALIDATED verdict on a reported finding creates a learned entry, and resetting its candidate with `--candidate` removes it; it also failed on an earlier draft that overwrote the copy's ids. All three failed on the unchanged code, which had no such options: the first two exited 2, and the third stopped on the missing `learned_catalog_ids` field. `test_a_candidate_whose_defect_is_reported_is_never_added_twice` (an invalidated duplicate marked VERIFIED, the same marked MITIGATED, and a VERIFIED candidate consolidation merged away) asserts exit 1, a message naming `--index 1`, and both files unchanged; on the earlier draft of this change each exited 0 and appended a second finding for the defect. `test_a_verdict_by_number_reaches_the_candidate_the_finding_reports`: an `--index` VERIFIED verdict on a reported finding, then `--candidate 2 --status MITIGATED` and `--index 2 --status UNVERIFIED` on the moved copy, leave both files with `[VERIFIED/human, UNVERIFIED/None]`, no ledger ids and an empty ledger; before, candidates.json kept the machine's verdict on the first and `MITIGATED`/`human` on the second. `test_candidates_of_one_title_and_location_are_told_apart`: a `qa` candidate with the title and location of the reported `devsecops` finding, reset with `--candidate 2`, leaves that finding `VERIFIED`/`llm`; before, it became `UNVERIFIED`. `test_a_candidate_that_cannot_be_told_from_another_is_judged_through_its_finding`: with two candidates of one persona, title, location and description, `--candidate 2` exits 1 naming `--index 1` and changes neither file, and `--index 1 --status INVALIDATED` then records the verdict on both candidates; before, `--candidate 2` exited 0 and overwrote the reported finding. `test_an_agent_cannot_change_a_persons_verdict_through_a_candidate` now also asserts the person's `--index` verdict reached the candidate.
- [x] **Provenance.** `test_the_mcp_tool_records_an_agent_verdict_that_history_ranking_ignores` runs the MCP tool's command through the CLI on the older of two sessions of one subject. The command ends `--adjudicator agent`, the finding records `("VERIFIED", "agent")`, and history counts the newer session. On the unchanged code the finding recorded `human` and history counted the older session. Its `without-candidates-json` case, a persona-loop session, and `test_an_agent_verdict_on_a_candidate_leaves_history_ranking_alone` (`--candidate 1 --status INVALIDATED --adjudicator agent` over candidates [UNVERIFIED, INVALIDATED]) assert the newer session still counts; on the earlier draft both counted the older one, because the second tier counted the agent's verdict. `test_an_agent_cannot_change_a_persons_verdict`: after a person's INVALIDATED and MITIGATED verdicts, an agent's `--index` reset and the MCP tool's reset exit 1 and say an agent cannot change the verdict, and both verdicts, the learned entry and the ledger entry stay. `test_an_agent_cannot_change_a_persons_verdict_through_a_candidate`: an agent's `--candidate` verdict whose copy a person judged is refused and neither file changes. On the earlier draft the resets exited 0 and emptied the catalog and ledger. `test_a_persons_verdict_on_a_candidate_kept_out_ranks_its_session`: a person's `--candidate 2 --status INVALIDATED` on the older of two sessions of one subject makes history count the older session; before, it counted the newer one. `test_an_agent_verdict_writes_neither_the_catalog_nor_the_ledger`: `--adjudicator agent` INVALIDATED and MITIGATED verdicts record `agent` and leave the learned catalog and the ledger empty. `test_the_exporter_labels_a_record_human_only_when_a_person_judged_it`: an exported agent verdict stays `agent`, and a `FeedbackRecord` built without an adjudicator is not `human`; it was on the unchanged code.
- [x] **No default verdict.** `test_verify_requires_a_status`: `verify --index 1` without `--status` exits 2 and leaves the finding UNVERIFIED; on the unchanged code it exited 0 and invalidated it as `human`.
- [x] **Ambiguous titles.** `test_a_title_matching_several_findings_is_refused`: `--title hardcoded` over two matching titles exits 1, names `#1, #2`, and changes neither. On the unchanged code it invalidated the first.
- [x] **Resets undo their side effects.** `test_a_reset_removes_the_catalog_and_ledger_entries_its_verdict_created` starts with one learned entry and one ledger entry already on disk. A person's INVALIDATED verdict adds a learned entry and a MITIGATED verdict adds a ledger entry. Resetting both findings to UNVERIFIED leaves only the two earlier entries and clears both id lists. On the unchanged code a probe of the same steps left `HALLUCINATION-AUTO-*` in the catalog and `Unbounded upload buffer` in the ledger after the resets. `test_a_reset_keeps_a_ledger_entry_another_verdict_still_records`: two `Unbounded upload buffer` findings in one file, both MITIGATED by a person, share one ledger entry, which stays after the first reset (the second finding still `MITIGATED`/`human`) and goes with the second. `test_a_reset_keeps_a_learned_entry_another_sessions_verdict_still_teaches`: one session's `--index` and another's `--candidate` INVALIDATED verdict give one learned entry `occurrence_count` 2; the candidate's reset, which its copy mirrors, leaves 1, and the other reset removes it. On the earlier draft the ledger was empty after the first reset, and the counts went [1], [2], [2], [] instead of [1], [2], [1], [].
- [x] **Verdicts given at once.** `test_verdicts_given_at_once_on_one_session_all_land` starts four threads behind a barrier on one session, two `--index` INVALIDATED verdicts by a person that teach the catalog and two `--candidate` VERIFIED verdicts, with each session read held open 20 ms. All four verdicts land in findings.json and candidates.json, and the learned catalog's counts equal the ids the findings hold. Before, one verdict of four survived, and the same test with only the `flock` call removed from the fixed code fails the same way. `test_a_failed_session_write_leaves_the_catalog_and_ledger_as_they_were` makes the findings.json write fail: a person's INVALIDATED and MITIGATED verdicts exit 1 and leave the catalog and ledger empty, and resets of both exit 1 and leave the verdicts, the learned entry and the ledger entry in place. Before, the verdicts left their entries behind and the resets removed them while findings.json still held their ids. `test_a_failed_session_write_leaves_entries_a_verdict_updated_as_they_were` starts with a learned entry and a ledger entry already on disk that the person's INVALIDATED and MITIGATED verdicts update, with a new reason, two new keywords, a new perimeter and a new regression test. With the findings.json write failing, both exit 1 and every field of both entries is as it was; given again once the files can be written, both exit 0 and raise those entries' counts to 2. On the code before this fix only the counts went back: the learned entry kept the new resolution and keywords, and the ledger entry the new mechanism, reason, perimeter and regression test.
- [x] **One settings load.** `test_each_review_command_loads_settings_once` (path, branch, pr) counts one `load_settings` call in each command; the unchanged code made 2.
- [x] **Tests.** All 14 tests first written failed on the unchanged code (`14 failed`, run with `-o pythonpath=` pointing at a `git archive HEAD src` copy) and pass after the change.
