# Task: Gateway requests stay within the backend slot count in every command (#1354)

**Issue**: [#1354](https://github.com/dan-petty/devops-cli/issues/1354)
**Scope**: scope/ai, scope/review
**Feasibility**: Verified against the code at 3dd7fa6. `execute_multi_persona_review` (`src/devops_cli/ai/review/pipeline.py`) sized its file pool at `max(DEFAULT_GATEWAY_REVIEW_CONCURRENCY, len(ollama_urls) * ollama_max_parallel)` in gateway mode and honoured any explicit `--concurrency`. Each file runs its personas through `MultiAgentPipeline.run_parallel` (`src/devops_cli/ai/agents/pipeline.py`, up to 8 threads). Every gateway chat call reaches `_openai_compat_messages` or `_openai_compat_stream` (`src/devops_cli/ai/client/openai.py`) through the provider dispatch in `src/devops_cli/ai/client/unified.py`, so one limiter there covers persona calls, group analysis, roadmap intake and the `devops ai` chat commands. Only the `gateway` provider sends chat calls to the gateway: with `ai.gateway_enabled` and another provider, `_api_base` and the provider dispatch send chat to that provider, and only embeddings go to the gateway (`src/devops_cli/ai/rag/embeddings.py`). The new tests were run against the base source (3dd7fa6 with this change's tests); what they got there is under Red Then Green.

## Description

In gateway mode a review sized its file workers by `ai.ollama_urls`, although gateway traffic goes only to `gateway_url`, and each file ran its personas in parallel. With three URLs the persona stage reviewed 6 files at once, so far more requests than the gateway's 3 backend slots could be in flight, which rebuilds the backend queue #1069 meant to prevent.

**One limiter per process.** `src/devops_cli/ai/client/network.py` holds `gateway_slots`, a `threading.BoundedSemaphore(DEFAULT_GATEWAY_REVIEW_CONCURRENCY)`, and `acquire_gateway_slot()`, a context manager beside `acquire_ollama_slot` that yields the seconds it waited. A wait longer than `DEFAULT_GATEWAY_SLOT_TIMEOUT_SECONDS` (900 s, the bound of an Ollama lease) raises `AIClientError` naming the slot count. `uses_gateway_slots(config)` is the one test of whether a client's chat calls take a slot: `provider == "gateway"`. `OpenAICompatProviderMixin._gateway_slot()` returns `acquire_gateway_slot()` when it holds and `nullcontext(0.0)` otherwise. `_openai_compat_messages` holds the slot for the request, and `_openai_compat_stream` holds it until the generator closes. One logical call takes one slot, held across the transport's own retries. The limit is per process: a second CLI process or the in-cluster Service takes slots of its own. Model listing, the gateway's health and model-info probes and embeddings take no slot, and the pydantic-ai direct path, which no command uses and #1001 removes, is left alone.

**The wait is seen, and kept out of inference time.** The wait is an INTERNAL `ai.llm.gateway_slot` span under the call's `ai.llm.dispatch` or `ai.llm.stream` span, with `llm.gateway.slots` and `llm.gateway.slot_wait_seconds`, and an observation of the `devops_cli_ai_gateway_slot_wait_seconds` histogram (`AI_GATEWAY_SLOT_WAIT`, `src/devops_cli/telemetry/instruments.py`), labelled `outcome` `ok` or `timeout`. A plain call's `wall_seconds` starts once it holds the slot. A stream's clock starts before its generator first runs, so the stream records its wait in the `stream_slot_wait` ContextVar, as it does the serving backend, and `LLMClient._stream_seconds` takes it off the time to first chunk, `llm.wall_seconds` and the spend's `duration_seconds`. `docs/TELEMETRY.md` describes the span and the metric.

**Worker pools with the gateway provider.** The sizing lives in helpers in `pipeline.py`. `_review_batch_capacity(config)` is the slot sum when `uses_gateway_slots(config)`, whatever `ai.ollama_urls` and `ai.ollama_max_parallel` hold, so the file pool is `min(total_files, DEFAULT_GATEWAY_REVIEW_CONCURRENCY)`. `effective_review_concurrency(config, requested)` is the file workers an explicit `--concurrency` gives: at most the slot sum through the gateway, and what was asked for otherwise. `_review_worker_count(config, total_files, requested)` returns the worker count and the request when the slot sum lowered it, and `execute_multi_persona_review` then prints `ReviewMessages.gateway_concurrency_clamped` once, for example `--concurrency 8 is above the gateway's 3 backend slots; using 3`. `execute_multi_persona_review` keeps its existing `# noqa: C901` and gains no branch. `devops review benchmark` records `effective_review_concurrency` in its run's setup, so a gateway benchmark asked for 8 records the 3 its reviews ran at. A file's personas still run in parallel; the limiter keeps the requests in flight at or under the slot sum. Ollama and the other providers keep their sizing and an explicit `--concurrency`, with or without `ai.gateway_enabled`. Group analysis keeps its existing clamp (`src/devops_cli/review/analysis.py`), and pre-analysis sizing, which calls no model, is unchanged.

**A structured reply builds no model class.** `fix_llm_response` (`src/devops_cli/ai/response_repair.py`) returned `FormattedLLMResponse[T](...)`, which made pydantic build a parametrized class that its generic cache holds only weakly. After any garbage collection the next reply rebuilt the class's whole schema, about 30 ms of CPU on the development host, and much of a review persona call's own work. It now returns a plain `FormattedLLMResponse`; the return annotation still carries `T`.

## Risks and Notes

- `DEFAULT_GATEWAY_REVIEW_SLOTS` and `DEFAULT_GATEWAY_REVIEW_CONCURRENCY` keep their names. They describe the backends the review and chat groups route to. A chat call to a group served elsewhere, such as `devops-background`, still takes a slot, which errs on the side of fewer requests, never more.
- The limit is per process, so two processes, or a process and the in-cluster Service, can together keep more than 3 requests in flight.
- A slot is held through the transport's backoff between retries. That lowers throughput only while the backend is already refusing, and never lets the count exceed the slot sum.
- A stream holds its slot until its generator closes, so a caller that keeps an unfinished stream open keeps the slot. Every stream consumer in the code reads its stream to the end before it makes another call.
- The review-level test builds its payloads directly and stubs the spend ledger, the tokenizer and span export, and runs without the shared response cache, since none of them is under test and their writes and first loads dominated its run time. It runs two personas a file, not five: two still overfill the slots without the limiter once the file pool is 3, and twelve calls keep the call phase under 1 s.
