# Task: Run-Identity Review History With a Leave-One-Out Baseline (#607)

**Issue**: [#607](https://github.com/dan-petty/devops-cli/issues/607)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p1-high
**Scope**: scope/review

## Description
Every review report has a "Historical Baseline FP Rate" column (#434), which compares the session's false-positive rate per category with earlier sessions. The figure was wrong three ways. The session counted itself, because `generate_consolidated_report` writes findings.json before it builds the report and the baseline read the session's parent directory. Repeat sessions counted again, because the baseline, `devops review stats` and the feedback export summed every session directory, and `ReviewSessionPayload` recorded nothing about what was reviewed (pydantic dropped the `target=` and `timestamp=` the tests passed). And the two sides counted different findings: the session side counted every finding raised, the history side only the reported, non-invalidated findings in findings.json. Sessions now record their subject, and history is read through one reader that leaves out the current session and counts each subject once. This ships in one PR.

- **Subject** (`ai/review/history.py`): `review_subject(target_type, target_ref, pages)` returns `{"type", "ref", "input"}`, where `input` is the first 16 hex characters of the SHA-256 of the review pages joined by `"\n"`. One rule covers PRs, branches, working-tree diffs and paths, with no git or GitHub call. `subject_key(subject)` is `run_store.digest(subject)`, or None for an empty subject, so sessions written before this change never collapse under `digest({})`. `ReviewSessionPayload.subject` defaults to empty.
- **Writers**: `_execute_review_workflow` builds the subject once and hands it to `ReviewPipelineOrchestrator(subject=...)`, which writes it to findings.json and candidates.json, and to `_run_persona_loop(subject=...)`, which passes it through `_write_summary` to `_save_findings_json`. `_save_findings_json` now stamps `generated_at` in UTC, as the pipeline does. `devops review verify` rewrites the whole payload, so the subject survives a human verdict.
- **Reader** (`load_review_history(reviews_dir, exclude=None)`): lists the sessions with a findings.json. For each it returns a `ReviewSessionRecord` with its path, subject key, profile.json target, `generated_at`, the findings in findings.json and every finding it raised (candidates.json, or findings.json without one). It drops `exclude` before repeats collapse, then counts one session per subject key, ranked by human verdicts in findings.json, then findings raised with a verdict (any status but UNVERIFIED), then the newest `generated_at`, then the directory name. Sessions without a subject each count on their own, reported as target-only with a profile.json and unkeyed without. An unreadable findings.json leaves a session with no findings and no subject, still counted. A stamp without an offset, as the persona loop wrote before this change, is read as local time. The reader parses `HistoryFinding`, which holds the seven fields the figures read and normalizes status through the same `normalize_finding_status` as `Finding`.
- **Baseline** (`ai/review/category_metrics.py`): `collect_historical_category_metrics(reviews_dir, exclude)` returns the per-category metrics over every finding raised by the counted sessions, and the `ReviewHistory`. `format_category_baseline_markdown` takes `exclude`, and `_build_category_baseline_section` passes `self.session_dir`. The `total_sessions > 1` gate became "a counted earlier session has this category", which is the metric being present, since the current session is no longer in history. A line under the table reads `_Baseline: {counted} earlier session(s), {repeats} repeat session(s) collapsed, this session excluded._`.
- **Stats** (`devops review stats`): reads through the reader, and its tables count the findings.json findings of the counted sessions. `Total Sessions` became `Sessions: {total} (counted {counted}: {repeats} repeat sessions collapsed, {target_only} target-only, {unkeyed} unkeyed)` (`MESSAGES.review.sessions_counted`, replacing the unused `total_sessions_count`). `_tally_single_session_findings` and `_load_sessions_data` became `_tally_findings`. Stats keeps findings.json, because `devops review verify` writes human verdicts only there, so its category table counts reported findings and will differ from the baseline.
- **Constants**: `CONST_REVIEW_FINDINGS_FILENAME` and `CONST_VERIFIED_BY_HUMAN` (`config/constants.py`).
- **Tests**: the dropped `ReviewSessionPayload` arguments are replaced with `generated_at=` and `subject=` in `tests/test_category_metrics.py`, `tests/test_review.py` and `tests/test_review_runner.py`, and the dropped `summary=` is removed from `tests/test_mitigated_perimeter.py`. `tests/conftest.py` gains `write_review_session`, which writes a session as the pipeline lays it out, and `review_history`, criterion 3's fixture.
- The changelog entry is `changelog.d/607.md` (#933), whose Fixed entry carries the #434 correction. `docs/ROADMAP.md` is left to `devops roadmap render` (#739).
- Out of scope, as the issue decided: the feedback export still sums every session (#877); human verdicts do not reach the baseline for sessions with a candidates.json, and which file holds every finding with every verdict is #771; there is no history window; `run_store` records are unchanged. A path review's ref is the resolved absolute path, so the same files in another worktree are another subject, and a change to paging or redaction re-keys every subject.

The reader was also timed on one workstation's history, read-only: 26 sessions, 2,237 reported and 4,090 raised findings, all target-only. The issue measured 1.7 s and 3.4 s for the full parse and 0.23 s for the slim one on a quieter machine. Over those sessions the slim model's status, category and `verified_by` equal the full parse's on all 6,327 findings, and `compute_category_metrics` gives the same figures from both.
