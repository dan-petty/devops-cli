# Task: Embeddings Through the LLM Gateway, With Embedding Model Evaluation (#481)

**Issue**: [#481](https://github.com/dan-petty/devops-cli/issues/481)
**Scope**: scope/ai
**Feasibility**: Parts 1 and 2 read the gateway ConfigMap (`k8s/llm/gateway/configmap.yaml`) as YAML. Its only embedding group was `bge-m3:latest`: one deployment on `ollama-48gib-slow` with `model_info.mode: embedding`. It has no wildcard route, so it refuses a model name that it does not list. The embedding task's default is `qwen3-embedding:0.6b` (`DEFAULT_RAG_EMBEDDING_MODEL`). The gateway did not serve this model until part 3. Gateway embeddings need no code: `provider: gateway` is handled by `EmbeddingsEngine` (`src/devops_cli/ai/rag/embeddings.py`) and the benchmark's `model@endpoint` specs, so pointing the task at the gateway is a setting in the user's own `config.yaml`. The READMEs still named `embeddinggemma:300m`, which #1064 removed from the gateway. For the code-chunk benchmark, the runner's metrics were read in `EmbeddingBenchmarkRunner.evaluate_model_on_server` (recall@1/3/5, MRR, nDCG@5, latency, throughput and dimension take any `SectionRetrievalTask`, whose `target_section_index` is the corpus index it ranks), and `SemanticChunker.chunk_file` was run over a temporary tree to see which chunks carry symbol names: Python (functions, classes as `Class` plus `Class.method`, and a `<module>` marker on a file's preamble), Go, Rust, TypeScript, Java, Terraform and SQL (a declaration pattern at the start of a line), and YAML (`kind` and `name` values) do; shell scripts are split into line windows and carry none; Markdown carries its heading and is documentation. The same probe over the rest of the chunker's languages (one small file each: functions, a class or struct, a method) found names for JavaScript (functions, classes and an arrow function bound to a `const`, not a class's methods) and Kotlin (top-level functions and classes, not a class's methods); C# carries none; C carries only its `struct` names, so `static void helper(int x)` and `int main()` have none; C++ is read as C, so a class has its name and `Foo::baz` none, and a header declares only its structs. A `--code` directory of C#, C or C++ therefore gives few targets and mostly distractors. The default benchmark model list was `nomic-embed-text:latest`, which nothing serves.

## Description

The issue compares embedding models for retrieval over this repository and moves the embedding task to the gateway. The owner's 2026-10-03 comment retargeted the comparison to the two models worth running: `bge-m3:latest`, which the gateway then served, and `qwen3-embedding:0.6b`, the code default. Both produce 1024-dimension vectors, but the vector spaces differ, so the winner needs a re-index, which #1066 enforces by refusing a collection indexed by another model.

The item is delivered in parts. The first fixed what the READMEs tell a reader: the gateway section and the profiles excerpt named `embeddinggemma:300m`, a group the gateway no longer serves, and the example `ai.tasks.embedding` configuration pointed the task at it. A request for a model the gateway does not serve fails, and RAG is off for the rest of the run.

The second gives the comparison an instrument that fits it. The embedding benchmark ranked 100-word Markdown sections, while the index serves chunks of code that a lookup finds by their path and symbol names. `devops ai benchmark --type embedding --code <dir>` builds its corpus from the code chunks under a directory, split by the chunker and the file collection the index uses, and queries each chunk the way the index is queried: by its path relative to the directory and its first five symbol names. The target of a query is the chunk it came from. Nothing is labelled by hand, written by a model or scored by a constant, and the runner's recall@k, MRR, nDCG, latency, throughput and vector size score it unchanged. A runner built without models now benchmarks the two candidates, but `devops ai benchmark` always passes the models it parsed, so the recorded run names its models.

The third part serves the winner. A person ran the comparison on 2026-10-22, and `qwen3-embedding:0.6b` won (see Measurement). The gateway group `bge-m3:latest` becomes `qwen3-embedding:0.6b` on the same deployment. Both READMEs, the two registries of gateway models and the example configuration of the in-cluster jobs follow. The gateway keeps no group for `bge-m3:latest`. A cluster deployed before this change holds a `devops-cli-config` that still names `bge-m3:latest`, until a person deploys the `devops` stack (see the `Pending a person` bullets).

## Trade-offs
- The test reads no list of embedding models. Whether a README names a model the gateway lacks is decided against the ConfigMap, whatever the model is called, so it does not depend on the RAG embedder's dimension table, which is only the embedder's fallback when probing the live model fails.
- It reads two places, and only those. First, the YAML fences anywhere in either README: the names in a `model_list` and the model the example sets for `ai.tasks.embedding`. Second, the inline code spans under a heading that names the gateway: `LLM Gateway` in `k8s/README.md` and `Gateway Routing Integration` in `k8s/llm/profiles/README.md`, each through the next heading at its level or above. A README with no such section fails the test, so its spans are never silently unread.
- It does not read a model named outside those places: in prose with no code span, in a fence that is not YAML, or in a section whose heading does not name the gateway. Outside its gateway section `k8s/README.md` has `name:tag` spans only for the service image and Traefik's `host:port`. The hardware matrix in `k8s/llm/profiles/README.md` names the chat model each GPU class runs (`qwen2.5-coder:14b` among them, which the gateway does not serve) and is left unread for the same reason.
- The scan stops at the gateway sections because the shape `name:tag` cannot tell a model from an image or an endpoint: `k8s/README.md` names the image `service:latest` and `service:vX.Y.Z` in its GitOps sections, and any README may name `host:port`. A span of that shape added to a gateway section fails until it is worded otherwise.
- The gateway's embedding groups are required as well as permitted: a README that drops the one it serves fails.
- A code query is the chunk's own path and symbol names, verbatim, with no label to keep in step with the code. The path is relative to the `--code` directory, so `--code .` from the repository root queries by the paths the index stores, and `--code src` queries by `devops_cli/...` where the index holds `src/devops_cli/...`; the recorded A/B runs from the root. A Python file's preamble chunk is never a target: before it was excluded, 8 of the 100 tasks over `src` were `<path> <module>` queries that no content could answer.
- Targets are spread evenly across the files in sorted order rather than drawn at random, so a run repeats exactly and reaches every directory. A chunk is a target only when it defines a symbol and its query is unique, which leaves out the line-window chunks of languages without a declaration pattern and the pieces of one function the chunker's size cap splits; both stay in the corpus as distractors.
- The runner ranks each query against every chunk in pure Python, so a run costs the queries times the corpus in cosine calls: `--samples 100` over `src` (7,699 chunks) is about 770,000 per model, measured at 57 s, and over the repository root (18,025 chunks here) about 1.8 million, about 2 minutes by the same rate. The embedding of the corpus itself took 19 and 24 minutes in the recorded runs. Follow-up issue #1928 removes the 2 minutes of ranking.
- A code run is recorded under a digest of the files its corpus is drawn from, not of the chunks: a change to the chunker or to the indexer's collection rules changes the corpus without changing the digest, and the record's `commit` field holds the devops-cli commit that told them apart.
- The category table's columns are the categories the results scored, so a code run shows `code`, `iac` and `config` where a document run shows its documentation domains. A dry run's synthetic results still carry the five documentation domains.
- The published numbers pointed the same way, and the run agrees with them. On MTEB(Code, v1) (nDCG@10, average of 12 tasks) Qwen3-Embedding-0.6B scores 75.41 and BGE-M3 (dense) 58.22. On MTEB multilingual retrieval they score 64.64 and 54.60 (the Qwen3 Embedding paper, arXiv 2506.05176, Table 9 and Table 2). Those tasks are natural-language-to-code searches with the Hugging Face weights, not path and symbol lookups through the Ollama builds that the gateway serves. The run gave the margin and the latency, and a person takes the cosines after the re-index. The benchmark leaves documentation out, so it measures only the code half of a lookup.
- The default model list is used by a runner built with no models. The command passes `ai.model` when `--models` is omitted, so a person-run benchmark names its models, as the commands above do.
