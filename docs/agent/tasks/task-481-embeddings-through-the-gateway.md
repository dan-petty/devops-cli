# Task: Embeddings Through the LLM Gateway, With Embedding Model Evaluation (#481)

**Issue**: [#481](https://github.com/dan-petty/devops-cli/issues/481)
**Scope**: scope/ai
**Feasibility**: Read the gateway ConfigMap (`k8s/llm/gateway/configmap.yaml`) as YAML: its only embedding group is `bge-m3:latest`, one deployment on `ollama-48gib-slow` with `model_info.mode: embedding`, and it has no wildcard route, so a model name it does not list is refused. The embedding task's default is `qwen3-embedding:0.6b` (`DEFAULT_RAG_EMBEDDING_MODEL`), which the gateway does not serve. Gateway embeddings need no code: `provider: gateway` is handled by `EmbeddingsEngine` (`src/devops_cli/ai/rag/embeddings.py`) and the benchmark's `model@endpoint` specs, so pointing the task at the gateway is a setting in the user's own `config.yaml`. The READMEs still named `embeddinggemma:300m`, which #1064 removed from the gateway. For the code-chunk benchmark, the runner's metrics were read in `EmbeddingBenchmarkRunner.evaluate_model_on_server` (recall@1/3/5, MRR, nDCG@5, latency, throughput and dimension take any `SectionRetrievalTask`, whose `target_section_index` is the corpus index it ranks), and `SemanticChunker.chunk_file` was run over a temporary tree to see which chunks carry symbol names: Python (functions, classes as `Class` plus `Class.method`, and a `<module>` marker on a file's preamble), Go, Rust, TypeScript, Java, Terraform and SQL (a declaration pattern at the start of a line), and YAML (`kind` and `name` values) do; shell scripts are split into line windows and carry none; Markdown carries its heading and is documentation. The same probe over the rest of the chunker's languages (one small file each: functions, a class or struct, a method) found names for JavaScript (functions, classes and an arrow function bound to a `const`, not a class's methods) and Kotlin (top-level functions and classes, not a class's methods); C# carries none; C carries only its `struct` names, so `static void helper(int x)` and `int main()` have none; C++ is read as C, so a class has its name and `Foo::baz` none, and a header declares only its structs. A `--code` directory of C#, C or C++ therefore gives few targets and mostly distractors. The default benchmark model list was `nomic-embed-text:latest`, which nothing serves.

## Description

The issue compares embedding models for retrieval over this repository and moves the embedding task to the gateway. The owner's 2026-10-03 comment retargeted the comparison to the two models worth running: `bge-m3:latest`, which the gateway serves, and `qwen3-embedding:0.6b`, the code default. Both produce 1024-dimension vectors, but the vector spaces differ, so the winner needs a re-index, which #1066 enforces by refusing a collection indexed by another model.

The item is delivered in parts. The first fixed what the READMEs tell a reader: the gateway section and the profiles excerpt named `embeddinggemma:300m`, a group the gateway no longer serves, and the example `ai.tasks.embedding` configuration pointed the task at it. A request for a model the gateway does not serve fails, and RAG is off for the rest of the run.

The second gives the comparison an instrument that fits it. The embedding benchmark ranked 100-word Markdown sections, while the index serves chunks of code that a lookup finds by their path and symbol names. `devops ai benchmark --type embedding --code <dir>` builds its corpus from the code chunks under a directory, split by the chunker and the file collection the index uses, and queries each chunk the way the index is queried: by its path relative to the directory and its first five symbol names. The target of a query is the chunk it came from. Nothing is labelled by hand, written by a model or scored by a constant, and the runner's recall@k, MRR, nDCG, latency, throughput and vector size score it unchanged. A runner built without models now benchmarks the two candidates, but `devops ai benchmark` always passes the models it parsed, so the recorded run names its models.

## Key Changes
- **`k8s/README.md`**: the gateway section lists `bge-m3:latest` as the one embedding model, and the example `ai.tasks.embedding` sets `model: bge-m3:latest`.
- **`k8s/llm/profiles/README.md`**: the gateway excerpt no longer carries the `embeddinggemma:300m` group.
- **`tests/test_k8s_llm_gateway.py`**: `test_a_gateway_readme_names_exactly_the_embedding_groups_the_gateway_serves` compares what each README names with what the ConfigMap names. The ConfigMap supplies every model it names (each group's `model_name` and each backend's `litellm_params.model` without its provider prefix) and its `model_info.mode: embedding` groups. From each README the test takes the models set in its YAML fences (`yaml` and `yml`, every mapping document: the `model_list` entries and the `ai.tasks.embedding` model) and the inline code spans of every section whose heading names the gateway. A code span is a model when Docker's reference parser (`docker.utils.parse_repository_tag`, a convention Ollama's model references follow) splits its one word into a name and a tag. Every model a README names must be one the ConfigMap names, and every embedding group the ConfigMap serves must be named. Fences and spans come from `tests/support/markdown_examples.py` (`fences`, `headings`, `code_snippets`). A parametrized test runs the same check over synthetic READMEs: a stale model in a span, a list item, a subsection, a `yml` fence with an info string and the second document of a fence is found; an empty fence, a valueless `embedding:` key and documents that are no mapping are skipped.
- **`src/devops_cli/ai/benchmark/code_chunk_corpus.py`**: `load_code_chunk_corpus(code_dir, sample_count)` collects the files with `WorkspaceIndexer.collect_files`, splits them with `SemanticChunker.chunk_file` and keeps every chunk that is not documentation as the corpus. A chunk is a target when it defines a symbol and no other chunk has the same query, since a query with two right answers has no single target (a function defined twice, or a function split by the chunker's size cap). `sample_count` targets, evenly spaced, become the `SectionRetrievalTask`s: the id is `code-task-<n>`, the heading is `path:start-end`, the passage is the chunk and the category is the chunk's. A Python file's preamble chunk (its imports and docstring, whose only symbol is the chunker's `<module>` marker) is never a target: its content has neither its path nor a name to find it by, so it stays in the corpus as a distractor. A directory with no target is refused with a `ValidationError` that names it. `code_tree_digest(code_dir)` digests each indexed file's path relative to the directory and its bytes.
- **`src/devops_cli/ai/benchmark/embedding_runner.py`**: `EmbeddingBenchmarkRunner` takes `code_path`, and `_load_corpus` picks the code corpus or the document corpus and describes it in the report's header line, naming the directory `--code` resolves to (`--code .` is the repository root's name). The category table has a column for each category any result scored, named by the category key as the JSON report holds it, with a dash where a model scored none.
- **`src/devops_cli/commands/benchmark.py`**: the `--code` option, which takes an existing directory and is refused together with `--document`; a corpus the loader refuses is reported as the command's error (exit code 1 with the directory named), and a recorded code run carries `code_tree_digest` of its directory in its subject, as a document run carries `file_digest` of its document (a document run's subject is unchanged, so its baselines still match). `--samples` counts code chunks under `--code`.
- **`src/devops_cli/ai/rag/indexer.py`**: `WorkspaceIndexer.collect_files` is a static method, since it reads nothing from the indexer, so the benchmark lists the files the index would without opening Qdrant or an embedder.
- **`src/devops_cli/config/defaults.py`**: `DEFAULT_EMBEDDING_BENCHMARK_MODELS` is `bge-m3:latest` and `qwen3-embedding:0.6b`. In `config/constants.py`, `CONST_INDEX_LOOKUP_SYMBOLS` (5) is the symbol count that `ai/analyze/outlines.py` takes after a file's path for its index lookup and the benchmark takes for a code query, and `CONST_CHUNK_MODULE_PREAMBLE_SYMBOL` (`<module>`) is the marker `ai/rag/chunker.py` puts on a preamble chunk and the benchmark leaves out of its targets. Outlines and the chunker read them in place of a literal.
- **`tests/test_embedding_benchmark.py`**: the task lists for a temporary source tree are asserted whole (queries, targets, headings, passages, the corpus), as are the even sampling, the shared-query exclusion, the five-symbol cap and the refusal of a directory with no symbol; the preamble distractor, the digest (the same for a directory spelled two ways and for a copy of it, different once a file changes) and the equality of a code query with the lookup `outlines` makes (nine symbols, five kept) are asserted; a run through the real engine, with only the HTTP post of the embedding request answered, shows an embedder that places a text on the symbols it names scoring recall@1, MRR and nDCG of 1; the category table of a code run is read back from the printed report; the CLI tests cover `--code`, `--code .` from inside the directory, its refusal beside `--document`, the exit code and message of a directory with nothing to query by, and the digest a recorded run carries.

- Pending a person: re-index with the winner, `devops ai rag clear --force && devops ai rag index --force && devops ai rag index-kb`, then recalibrate `ai.rag.score_threshold` (0.35) against the cosine `devops ai rag query` prints for known path and symbol pairs. Estimated at 250k to 400k tokens and about an hour for one build and review, in a follow-up with no issue yet.

## Trade-offs
- The test reads no list of embedding models. Whether a README names a model the gateway lacks is decided against the ConfigMap, whatever the model is called, so it does not depend on the RAG embedder's dimension table, which is only the embedder's fallback when probing the live model fails.
- It reads two places, and only those. First, the YAML fences anywhere in either README: the names in a `model_list` and the model the example sets for `ai.tasks.embedding`. Second, the inline code spans under a heading that names the gateway: `LLM Gateway` in `k8s/README.md` and `Gateway Routing Integration` in `k8s/llm/profiles/README.md`, each through the next heading at its level or above. A README with no such section fails the test, so its spans are never silently unread.
- It does not read a model named outside those places: in prose with no code span, in a fence that is not YAML, or in a section whose heading does not name the gateway. Outside its gateway section `k8s/README.md` has `name:tag` spans only for the service image and Traefik's `host:port`. The hardware matrix in `k8s/llm/profiles/README.md` names the chat model each GPU class runs (`qwen2.5-coder:14b` among them, which the gateway does not serve) and is left unread for the same reason.
- The scan stops at the gateway sections because the shape `name:tag` cannot tell a model from an image or an endpoint: `k8s/README.md` names the image `service:latest` and `service:vX.Y.Z` in its GitOps sections, and any README may name `host:port`. A span of that shape added to a gateway section fails until it is worded otherwise.
- The gateway's embedding groups are required as well as permitted: a README that drops the one it serves fails.
- A code query is the chunk's own path and symbol names, verbatim, with no label to keep in step with the code. The path is relative to the `--code` directory, so `--code .` from the repository root queries by the paths the index stores, and `--code src` queries by `devops_cli/...` where the index holds `src/devops_cli/...`; the recorded A/B runs from the root. A Python file's preamble chunk is never a target: before it was excluded, 8 of the 100 tasks over `src` were `<path> <module>` queries that no content could answer.
- Targets are spread evenly across the files in sorted order rather than drawn at random, so a run repeats exactly and reaches every directory. A chunk is a target only when it defines a symbol and its query is unique, which leaves out the line-window chunks of languages without a declaration pattern and the pieces of one function the chunker's size cap splits; both stay in the corpus as distractors.
- The runner ranks each query against every chunk in pure Python, so a run costs the queries times the corpus in cosine calls: `--samples 100` over `src` (7,699 chunks) is about 770,000 per model, measured at 235 s, and over the repository root (18,025 chunks here) about 1.8 million, about nine minutes by the same rate, beside the embedding of the corpus itself. The follow-up above removes that wait.
- A code run is recorded under a digest of the files its corpus is drawn from, not of the chunks: a change to the chunker or to the indexer's collection rules changes the corpus without changing the digest, and the record's `commit` field holds the devops-cli commit that told them apart.
- The category table's columns are the categories the results scored, so a code run shows `code`, `iac` and `config` where a document run shows its documentation domains. A dry run's synthetic results still carry the five documentation domains.
- The published numbers point the same way and do not replace the run. On MTEB(Code, v1) (nDCG@10, average of 12 tasks) Qwen3-Embedding-0.6B scores 75.41 and BGE-M3 (dense) 58.22, and on MTEB multilingual retrieval 64.64 and 54.60 (the Qwen3 Embedding paper, arXiv 2506.05176, Table 9 and Table 2). Those tasks are natural-language-to-code searches with the Hugging Face weights, not path and symbol lookups over this repository's Python, YAML and Terraform through the Ollama builds the gateway serves, and they give neither a margin here, the latency on the slow tier, nor a cosine to recalibrate `ai.rag.score_threshold` (0.35) against. The benchmark leaves documentation out, so it measures the code half of a query that may also be answered from documentation.
- The default model list is used by a runner built with no models. The command passes `ai.model` when `--models` is omitted, so a person-run benchmark names its models, as the commands above do.
