# Task: Changelog Fragments So Open PRs Never Conflict on CHANGELOG.md or docs/ROADMAP.md (#933)

**Issue**: [#933](https://github.com/dan-petty/devops-cli/issues/933)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p0-critical
**Scope**: scope/cli

## Description
Every PR into a release branch added its entries at the top of `## [Unreleased]` in `CHANGELOG.md`, and most also ticked its entry in `docs/ROADMAP.md`. Any two open PRs edited the same lines, so each merge made every other open PR conflict, and each then had to be rebased, pass the pre-push gate again and run GitHub CI again. In v0.2.25, #928 and #932 each conflicted twice in one hour. The release ruleset has no "up to date with base" rule, so these two files were the only reason a PR into `release/*` needed a rerun after a merge.

- **Fragments.** A PR's changelog entry is `changelog.d/<issue>.md`, a new file no other PR writes, holding house-style entries under Keep a Changelog's `###` categories (`CONST_KEEP_A_CHANGELOG_CATEGORIES`: Added, Changed, Deprecated, Removed, Fixed, Security). `changelog.d/README.md` says what a fragment is.
- **Collection.** `src/devops_cli/release/changelog_fragments.py` reads and collects them. `read_changelog_fragments` checks every file before returning any: a name other than `<issue>.md`, digits only (`CONST_CHANGELOG_FRAGMENT_NAME_RE`), or anything else but `README.md`, including a directory or a link, is refused by name. So is text outside a category, any heading but a known `### <category>` (a `##` would open a version section of its own), and a fragment with no entry. Each refusal is a `ValidationError` naming the file and line, with the messages in `ERRORS.release`. `collect_changelog_fragments` merges the entries into `## [X.Y.Z] - <date>`: categories in Keep a Changelog order, fragments in issue order within each (numeric, so #100 follows #12), each fragment's lines unchanged. They join the version's section when it is already open, otherwise a new section under `## [Unreleased]`, which stays as an empty heading, otherwise a new section above the newest release. Entries already under the joined heading come first, and they are checked like a fragment.
- **At the cut.** Both callers of `_update_changelog_header`, `devops release prepare` and `devops release changelog --update`, now plan the collection first (`_plan_fragment_collection`), before the version bump or any other write, and exit 1 on a refusal. `_write_version_changelog` writes the planned text and deletes the fragments in the same run. With no fragment it calls `_update_changelog_header` exactly as before. A dry run plans, so it refuses what the cut would, lists the fragments under `changelog_fragments`, and writes and deletes nothing. The release commits (`release pr`, `release tag`) stage `changelog.d/` where it exists (`_release_paths`), so the deletions are committed with the section.
- **Readiness.** `_GROUNDING_CHECKS` (`commands/pr.py`) gains `_leaves_release_files_to_the_cut`: a PR into a `release/*` branch whose changed files add, modify, rename (either path, read from `previous_filename`) or remove `CHANGELOG.md` or `docs/ROADMAP.md` (`CONST_RELEASE_SHARED_FILES`, `CONST_PR_FILE_CHANGED_STATUSES`) gets one blocker naming the files and `changelog.d/<issue>.md`. It reports nothing when the file list could not be read, which `_changed_files_were_read` already reports, so each cause is still one blocker. Release-process PRs are exempt from the whole table, as the release PR is: head `chore/open-vX.Y.Z` or `chore/cut-vX.Y.Z`, optionally followed by `-<slug>` (`CONST_RELEASE_PROCESS_BRANCH_RE`), from the same repository, into `release/vX.Y.Z` of the same version (`_is_release_process_pr`). The `check-readiness` docstring describes both, and the generated docs are refreshed.
- **Migration.** The twelve entries under `## [Unreleased]` move, byte for byte and in their categories, to one fragment per issue their sub-bullets cite: `changelog.d/593.md` (Added 1, Fixed 2), `changelog.d/704.md` (Added 1, Changed 2), `changelog.d/739.md` (Added 1, Changed 1, Removed 1) and `changelog.d/768.md` (Added 1, Changed 1, Fixed 1). Each entry cites one issue only. `## [Unreleased]` is an empty heading. This item's own entry is `changelog.d/933.md`, and it does not tick `docs/ROADMAP.md`.
- **Rule text.** `AGENTS.md` (a new "Changelog Fragments, Never the Shared Files" rule beside topic-branch isolation, and the readiness sentence under issue-only linking), `docs/agent/tasks/README.md` (rule 5), `.github/pull_request_template.md` (the fragment path, and the release-process branch names) and `RELEASE_CYCLE.md` (Stage 1 rule 6 and the `prepare` row) say: add `changelog.d/<issue>.md`; do not edit `CHANGELOG.md` or `docs/ROADMAP.md` in an item PR; release-process PRs use `chore/open-vX.Y.Z` or `chore/cut-vX.Y.Z`. `AGENTS.md` also says to open an issue where it elsewhere says to add an item to `docs/ROADMAP.md`. `docs/ROUTINE_TASKS.md`'s cut step says the fragments are collected, and `CONTEXT.md` defines a changelog fragment. The edits are small, since #840 rewrites `AGENTS.md`.
- Generated docs (`README.md` matrix, `docs/CLI_REFERENCE.md`, `docs/commands/*.md`) stay out of scope, as the issue decides.
