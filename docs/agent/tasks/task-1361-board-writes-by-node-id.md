# Task: Board writes go to the card by node id and read only that card (#1361)

**Issue**: [#1361](https://github.com/dan-petty/devops-cli/issues/1361)
**Status**: Done
**Milestone**: v0.2.29
**Priority**: priority/p1-high
**Scope**: type/bug, scope/github, priority/p1-high

## Description

The roadmap store wrote board fields by name and re-read the whole board around every write. `gh project field-list` and a name-addressed `gh project item-edit` each read the board's first 100 items with every field value (about 101 GraphQL points), and `_require_entry` re-read the whole board, so one `set_field` cost about 320 points and one intake placement about 1,300. The Service spent the machine account's hourly GraphQL budget by itself twice on 2026-10-07/08. Intake also read its card back from the board listing right after `gh project item-add`, which can lag the add by up to two minutes, so three placements failed with "#N is not on the board after intake added it".

- **Card identity.** `RoadmapStore.add_item` returns the `Item` it added: the card id comes from `gh project item-add --format json` (GitHub answers with the existing card for an issue already on the board), and its fields from one `RoadmapBoardCard` read of that id. `Item` and `BoardEntry` carry `card_id`, from the add or from the listing. Intake's placement writes to `subject.item` or the returned `Item`; it never calls `store.item()`, and the read-back error is gone.
- **Writes by node id.** `set_field`, `set_marks`, `set_card_field` and `set_run_record` write through `card_edit_args` (`--id`, `--project-id`, `--field-id`, and an option's id or `--text` or `--clear`). The board's node id and fields come from the GraphQL fields query (it now selects the board's `id`), read once per store. `_read_board_options`, `_edit_board_field`, `_require_existing_board` and `_require_card` are deleted. `item-add --url` stays: it has no id form.
- **One card read before a write.** `_require_entry` reads the card by node id (`RoadmapBoardCard`: `node(id:) { ... on ProjectV2Item { isArchived ...the page's item fields } }` with `rateLimit`, about one point). The record a write sends joins the record the card holds then (ADR 0002). A card that is gone (GitHub's `NOT_FOUND`, which `gh` reports by exiting 1 with the answer on stdout), archived, or another issue's raises "#N is not on the board" before any write. `require_write_floor` refuses the write while that read reports fewer than the 250-point reserve.
- **A change since the read stops the write.** Before `set_field` writes a board field, and before `set_card_field` writes any, the store compares the field on the card it just read with the value it read: the card's copy in its listings, which its own writes keep current, or the caller's `Item` or `Card` when no listing holds the card. When they differ and the card does not already hold the value being written, it raises `RoadmapCardChangedError` ("#N's Field is X on the board but was Y when this run read it…") before any edit, so a job never reverts a person's change it did not see (ADR 0002); the job fails and the next round plans with a fresh store. The card read takes only the job record into the listings, so a change seen while writing one field still stops a later write of another. Both adapters keep this contract through `store.require_unchanged`.
- **No listing after a write.** The run record card is written by the id `gh project item-create --format json` returns, with nothing read after the create. `remove_card` and `set_card_field` read their card by node id.
- **One listing per filter per store.** The store reads the board listing the first time it needs a filter and keeps it for its life (one command or one Service round). `items`, `item`, `backlog`, `candidates`, `cards`, the job records `changes_since` attaches, the run record lookup and the cross-job checks in `run.py` share it. Its own writes keep it current: each edit updates the card with the value sent, a card it adds joins the unfiltered listing and, when its issue is open, the open items' (`is:open`) listing, and any other filtered listing, which it can't judge, is read again when next needed. A close (`close_issue`, `close_as_duplicate`) drops every listing, because the board's own "Item closed" workflow then sets the card's Status to Done, so a cut rendered in the same round shows Done. Nothing else is cached; the next store reads afresh (ADR 0003).
- **The Service's own events cost no board read.** `changes_since(since, except_actor=...)` drops the actor's changes before it attaches job records; `run.py` passes the session's login. An empty actor leaves out nothing.
- **Request plans.** `StoreRequests` lists each write's card read and id-addressed edit, the fields read and each filter's listing under "the run has not read … since it began or last closed an issue", `add_item`'s `item-add --format json` and card read, no `board_read` after the run record's create, and the card read before `set_card_field` and `remove_card`. Intake's placement drops its `item` step. `--dry-run` still sends no request.

## Decisions and deviations

- **`field_list_args`, `item_edit_args` and `FieldListingPayload` stay**, unused by the store: `gh project reconcile` reads and writes through them since #892 merged, and the issue leaves that path to #892 and #999. Their docstrings say what they cost and that the store sends neither.
- **The reserve check for a write** is `require_write_floor`, beside `require_floor`: it reads the card read's `rateLimit` and refuses while fewer than the 250 reserved points are left, with a message about the write. `require_budget` prices a read about to happen, so its message would misdescribe a write.
- **The board's node id** comes from the fields query (which now selects it), so `set_card_field` and `set_run_record` no longer read `gh project list` before writing; a board that does not exist fails the fields read.
- **The run record card is still found by its title in the listing**, the store's one listing for the run, which reprioritize has already read for `run_record()`; the write then reads that card by node id.
- **`item(number)` keeps the shared listing**, as the issue proposes: no write path calls it, and after the store's first read it costs no GraphQL point.
- **A card the store adds** joins the unfiltered listing, which selects every card not archived, and the `is:open` listing when its issue is open, so intake's backlog and candidates hold it without a re-read GitHub's lag could leave it out of; a listing that already holds the card keeps its copy, and any other filtered listing is dropped and read again when next needed, because the store can't evaluate a Projects filter.
- **"Changed since it was read" compares the listing copy, not the `item` argument**, so a reprioritize apply that reverts a field and then writes its decision to it, both from one planned `Item`, compares the second write with the first. The caller's value is the baseline only for a card no listing of the store holds. A write of the value the card already holds is not a revert and goes ahead: the board's own "Item added" workflow sets Status New on a card intake adds, and intake writes the same New. The card read before a write takes only the job record into the listings; taking the whole card, as before, would have hidden a person's change to one field behind a write to another.
- **The Release is not compared:** it is the issue's milestone, written over REST, and the card read does not carry it.
- **A close drops every listing** rather than patching the closed card: the Status the board's workflow sets is GitHub's, and only a read shows it.
- **The worker pause and the per-round spend line** are split out to #1400, as the issue's "One pull request?" question allows: the store changes are the fix, and they end the budget exhaustion at its source.
- **An unchanged poll** still reads the board once, about 12 points on board #2. Skipping that read is #1401.
