# Task: Tests Wait for a Background Thread With One Generous Bound, Not a 1-Second Deadline (#1664)

**Issue**: [#1664](https://github.com/dan-petty/devops-cli/issues/1664)
**Scope**: scope/cli
**Feasibility**: At release/v0.2.37 (0510f6e) `tests/test_server_service.py` and `tests/test_review_embeddings_unserved.py` passed 17 of 20 runs with `-n logical` while other agents' suites kept the host's load average at 20-50 on 16 CPUs. The failures were `_queue.Empty` in `test_a_budget_refusal_in_the_model_lane_holds_the_release_lane_too` and `test_every_worker_refused_for_one_reset_logs_one_wait_line`, and a broken barrier in `test_once_the_model_answers_lookups_stop_taking_turns` (4 embedding requests, not 5) although its timeout had already been raised to 10 s. With every wait on the 30 s bound the first loop still failed once, `test_every_worker_refused_for_one_reset_logs_one_wait_line` after waiting the whole bound, so two causes are not deadlines. Printing each post that reached the barrier showed the tracer's `devops-otel_0` and `devops-otel_1` exporter threads posting `/v1/traces` through the same patched `httpx2.Client.post`, once ahead of every worker. A scratch test that started the release lane's worker after the model lane's refusal reproduced the `_queue.Empty`: the refusal's pause held the release lane's first round for the whole bound. The issue's grep matched 38 calls at the tip, in 10 of the 11 named files (none in `tests/test_review_embeddings_unserved.py`, whose 10 s waits the grep does not match) and `tests/test_cli_startup_imports.py`, and the same 38 in the same files at 3b70671; two of them are no waits (`github.comments.get(1)`, and `limiter.acquire(1.0)`, a token count). For the amendment of 2026-10-18: `import numpy` took a process from 1 thread to 16 on this host, and `/proc` sampled while a 16-worker run collected the suite showed 17 threads in each worker, 272 in all. Recording `socket.getaddrinfo` in the embeddings tests showed a served lookup looking up the Qdrant host six times, three attempts for each collection, each refused by the suite's guard. Review of this change found four tests whose hold had the observer's bound, so each passed with its bug back in; a mutant reproduced each.

## Description

A test that waits for another thread to do something gave it 1 or 2 seconds. Under load a ready thread can wait longer than that for a CPU, so correct code failed the gate and cost a rerun. Three of the failures seen had other causes, which the bound could only slow down.

- **The bound.** `tests/support/waits.py` holds `THREAD_HANDOFF_BOUND_SECONDS` (30 s) and `wait_until(condition, bound=...)`, which reads a condition until it holds or the bound passes. It checks the deadline after each sleep and before the next read, so a sleep that overruns the deadline counts no later event. A plain import with no fixtures. In the files this changes, every wait that expects its event uses the bound: `Event.wait`, `Queue.get`, `Thread.join`, `Barrier(timeout=...)`, a Service worker's `wait_active`, `acquire_ollama_slot`'s timeout, the Service's drain timeout and the polls. Such a wait returns when its event fires, so a passing test is no slower; only a failing one waits the bound out.
- **Holds outlive their observers, or record their release.** Anything a test relies on to stay alive or blocked must outlive the bound of every wait that observes it, or record whether the test ended it; the module docstring says so. With the hold and its observer on one bound, the hold ran out inside the observer's window and the test passed with its bug back in. The holds:
  - the #958 group members in `tests/test_harness.py` sleep `MEMBER_LIFETIME_SECONDS` (10 times the bound), so only `stop_command` ends them inside the 30 s check; `_kill_if_running` ends one a failing test left;
  - the model lane's round in `_Lanes` (`tests/test_server_service.py`) records `model_released`, asserted by both lane tests;
  - Repo 1's held round in `test_multi_concurrency_coalescing_and_multi_repo` records `repo1_released`, and Repo 2's round records whether Repo 1's was still running (`repo1_running_beside_repo2`), which the cross-blocking check asserts;
  - `_QuietResponse` in `tests/test_k8s_service.py` records `ended_by_shutdown`;
  - the held jobs in `test_webhook_delivery_and_batch_coalescing` (`unblocked`) and `test_shutdown_drains_pending_delivery_enqueued_during_active_job` (`released`), the refine hold in `tests/test_roadmap_run.py` (`refine_released`), the slot holders in `tests/test_ai_request_priority.py` (each returns whether the test let it go), the docs search held in `test_an_interrupted_query_does_not_wait_for_the_other_searches` and the docs reply held in `test_a_query_waits_for_a_collection_search_that_ends_after_its_own` (`tests/test_rag_query_telemetry.py`), and the replies `_hold_replies_until_lookups_start` holds (`tests/test_review_embeddings_unserved.py`) all record their release and assert it;
  - the two refusals' `Barrier(2)` in `test_every_worker_refused_for_one_reset_logs_one_wait_line` is asserted unbroken, and the embedding barrier was already.
- **The 38 grep matches.** 32 waits that expect their event now use the bound: 19 in `tests/test_server_service.py` (with `_Rounds.wait` and `_Rounds.held`), 5 in `tests/test_rag_query_telemetry.py`, 4 in `tests/test_ai_request_priority.py`, and one each in `tests/test_ai_client_security.py`, `tests/test_roadmap_run.py`, `tests/test_k8s_service.py` and `tests/test_cli_startup_imports.py`. `limiter.acquire(1.0)` reads `limiter.acquire(tokens=1.0)` and `github.comments.get(1)` reads `github.comments.get(1, [])` against `[]`, so the grep no longer takes them for waits. The 4 waits left check that nothing happens (below). The 27 waits of 3-30 s in files this change does not touch, `tests/test_ui_reactive.py` (18), `tests/test_trace_propagation.py` (3), `tests/test_http_connection_pool.py` (2), `tests/test_github_session.py` (2), `tests/test_valkey_concurrency.py` (1) and `tests/test_ai_client_network.py` (1), are outside #1664's scope: the issue's "Where" names the 38 waits of 2 s or less.
- **Waits the grep cannot see.** `_wait_until_waiting` in `tests/test_ai_request_priority.py` polled for 1 s and `_poll_until` in `tests/test_harness.py` for 2 s; both are now `wait_until`, and the preemption test asserts its two queue handoffs. `test_prometheus_metrics_export` slept 0.1 s before reading `/metrics`; it now waits for every worker to go idle. `test_shutdown_drains_pending_delivery_enqueued_during_active_job` drains with `drain_timeout=int(THREAD_HANDOFF_BOUND_SECONDS)`, not 5 s. `_await_background_finish` in `tests/test_harness.py` polled with its own 20 s budget; it now waits with `wait_until` and returns one last report. In the touched files the 3-20 s waits use the bound too, so each file has one.
- **The barrier.** `test_once_the_model_answers_lookups_stop_taking_turns` holds only embedding requests at its `Barrier(WORKERS, timeout=THREAD_HANDOFF_BOUND_SECONDS)`. A trace export passes straight through instead of taking a worker's place and leaving that worker's request at the barrier until it broke.
- **Two refusals that could come first.** A budget refusal holds every round that has not started yet. `test_every_worker_refused_for_one_reset_logs_one_wait_line` needs both repositories' first rounds refused, and `test_a_budget_refusal_in_the_model_lane_holds_the_release_lane_too` needs the release lane's first round to run before the model lane's refusal, but neither made sure: when one worker was slow to take its batch, the other's refusal held it. The two first refusals now meet at a `Barrier(2)` before refusing, and the model lane's refusal waits (`wait_until`) for the release lane's first round to start, which the test asserts.
- **Waits that check nothing happens.** Four short windows stay: `tests/test_k8s_port_forward_daemon.py` (0.2 s, the second launch does not spawn while the first holds the state-file lock; 0.1 s, a list or stop does not finish while the lock is held) and `tests/test_roadmap_github_store.py` (0.3 s twice, the model lane's write or milestone check does not land while the release lane holds the job-record lock). Each opens only after a bounded wait for the competing thread to reach the call it would race on; each test records that wait's result, with the wait before it, and asserts them, and a comment at each window says so. A slow competitor can only let such a window pass when it should not, never fail a correct run. `_Rounds.held` needs no window: it waits, with the bound, for every worker to go idle, then reads that no round finished.
- **No rerun plugin.** The bound, the barrier, the recorded holds and the two refusal handoffs remove the causes.
- **Idle OpenBLAS threads (the amendment).** The first lines of `tests/conftest.py` call `os.environ.setdefault("OPENBLAS_NUM_THREADS", "1")`, OpenBLAS's documented setting, before any of its own imports. xdist workers and the processes tests start inherit it, so none parks an idle thread per CPU against the container's pids.max. `tests/test_ci_repeat.py` imports `numpy.random` inside `global_rngs_restored`, the fixture that uses it, so collecting that module loads no numpy. `devops ci test --repeat` (`-n 0 -p randomly`) loads pytest-randomly, which imports numpy before the conftest runs, so that one process keeps OpenBLAS's per-CPU threads; the conftest comment says so.
- **No lookups from the embeddings tests.** The `embedding_posts` fixture's Qdrant now answers `get_collection_info` and `scroll_points` (in the wrapper's scroll shape) as well as `search_points`: collections holding one point embedded with the configured model. The collection check a served lookup makes went to the real client, which looked up the Qdrant host (refused by the suite's guard) and slept through about 3 s of retries. The only name the file still resolves is `localhost`, from the embeddings cache's Valkey probe, which the guard refuses on loopback.
