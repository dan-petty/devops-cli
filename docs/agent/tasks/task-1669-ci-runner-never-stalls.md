# Task: A Test That Hangs Fails at a Per-Test Timeout, and a Narrowed `devops ci test` Sizes Its Workers and Stops Its Whole Process Group (#1669)

**Issue**: [#1669](https://github.com/dan-petty/devops-cli/issues/1669)
**Scope**: scope/ci
**Feasibility**: Checked at release/v0.2.37 bf9481e. pytest-timeout 2.4.0 is the current release on PyPI: 2.5.0, of 2026-08-16, is yanked as "accidental breaking change (probably)". 2.4.0 requires `pytest>=7.0.0` and loads under the locked pytest 9.1.1, whose header then shows `timeout: 600.0s` and `timeout method: signal`. xdist workers run tests in their main thread, so SIGALRM reaches them, which the pytester run under `-n 2` shows. `test()` built its pytest command with no `-n` unless one was given, so `addopts`' `-n logical` started 16 workers for any selection, and ran it through the sync `run_subprocess`, whose `subprocess.run(timeout=...)` kills only `uv`. `run_subprocess_async` starts its child in a new session and stopped the whole group on a timeout with the guarded `_terminate_process_group_async`, but not on a cancellation, and a cancellation that landed while the child was still starting reached only asyncio's clean-up, which kills the child alone. In CPython 3.14.7, `asyncio.Runner` turns a first Ctrl-C into a cancellation of its task and a second into KeyboardInterrupt, after which `Runner.close` cancels every task.

## Description

### PR 1: the per-test timeout, the narrowed run's workers and its process group

- **pytest-timeout.** `pytest-timeout==2.4.0` joins the `dev` group and `uv.lock`. `[tool.pytest.ini_options]` sets `timeout = 600` and `timeout_method = "signal"`: a stuck test fails in its own process with pytest-timeout's report, which names it, `subprocess.run` inside it gets the exception and kills its child, and the run and the xdist worker carry on. No per-call `timeout=` is added to the subprocess calls under `tests/`; the suite-wide bound covers them and every other hang.
- **The bound.** 600 s is a hang bound, not a speed target. Over 185 cached gate runs from 2026-09-25 to 2026-10-20, the slowest test took 139 s, at a load average of 30-50 on 2026-10-18; the slowest of the latest runs took 21-34 s, and this change's own gate run's slowest took 19.3 s. The longest non-call phase was a 37 s setup. The bound is 4.3 times the slowest test ever recorded, above `THREAD_HANDOFF_BOUND_SECONDS` (30 s), which a failing wait sits out, above the 300 s sleep of the #958 tests' members, which those tests stop, and under half the run's 1800 s timeout: the slowest full run recorded, 931 s, plus one 600 s hang stays under it, so a hung test is reported by name before the whole run would be stopped. A test that needs longer says so with `@pytest.mark.timeout(<seconds>)`.
- **The narrowed run's workers.** Given paths and no `-n`, `devops ci test` runs serially for up to `DEFAULT_CI_TEST_SERIAL_MAX_FILES` (12) test modules and on `DEFAULT_CI_TEST_NARROWED_WORKERS` (4) workers above that (`_narrowed_workers` in `src/devops_cli/commands/ci.py`). The full suite and the fallback to it pass no `-n`, so `-n logical` applies, and `devops ci` is unchanged; a given `-n` is kept. The same tests run, and no threshold changes.
- **Calibration.** Direct `uv run pytest -n <N> <selection>` runs, three each, interleaved, at a load average of 7-30 on 16 CPUs, median wall and CPU seconds at `-n 0` / 4 / 16: 1 test module (6 tests) 6 / 11 / 15 s and 9 / 30 / 133 CPU-s; 3 modules (28 tests) 13 / 14 / 20 s; 5 modules (264 tests) 15 / 25 / 19 s and 18 / 63 / 191 CPU-s; 8 modules (121 tests) 36 / 51 / 40 s and 37 / 101 / 303 CPU-s; 12 modules (552 tests) 79 / 82 / 54 s and 84 / 193 / 358 CPU-s; 19 modules (1092 tests) 75 / 27 / 39 s and 75 / 89 / 357 CPU-s. Up to 8 modules the serial run was the fastest or within the noise at about a third (29-37%) of the CPU of 4 workers; at 12 it matched 4 workers' wall time at less than half their CPU; at 19, 4 workers were 2.8 times faster than serial at about the same CPU, as the amendment found (94 s at `-n 0`, 50 s at 16, 44 s at 4). Over the 553 source modules a narrowed run maps to test modules by name and import, the median selects 3, the p90 12, and 90% select at most 12.
- **The process group.** Every pytest run `devops ci test` starts, single or `--repeat`, goes through `_run(..., own_session=True)`, which runs it with `run_subprocess_async` in a session of its own under `asyncio.run`. A run past its timeout stops the whole group, `uv`, pytest and its workers, and fails, naming the command and the timeout.
- **The stop sequence** (`src/devops_cli/core/process.py`). The group is in no process group a terminal or supervisor signals along with devops, so `run_subprocess_async` stops it when cancelled, as Ctrl-C cancels `asyncio.run`'s task, and SIGTERM and SIGHUP cancel a `devops ci test` run the same way while it lasts. A cancellation first forwards the SIGINT a terminal would have sent, so a pytest runs its KeyboardInterrupt teardown and its `finally` blocks, then SIGTERM, then SIGKILL, each after `DEFAULT_SHELL_STOP_GRACE_SECONDS`; a timeout, which `devops ci`'s checks share, still starts at SIGTERM, and their exit codes and output are as before. Once begun, the stop is not given up: a further cancellation cuts the grace short and is raised again only once the group is killed, and the SIGKILL is sent from a `finally`, so a second Ctrl-C's KeyboardInterrupt cannot skip it. The start is shielded (`_spawn_under_stop`), so a cancellation while the child is still starting stops its group once the start completes. It survives one cancellation only: a second Ctrl-C while the child is still starting makes `asyncio.Runner.close` cancel the start itself, and asyncio's own clean-up then kills the direct child alone; no further mechanism covers that window, a few event-loop turns wide. A cancellation after the leader exited still stops the members left, and the fallback kill of a leader asyncio has already reaped is skipped, so such a run stays a cancellation rather than a ProcessLookupError. The group wait sleeps between probes once the leader is gone instead of spinning. The guards against PID 1, 0, negative ids and the caller's own group are the existing ones.
- **Signal handlers.** `_cancelled_by_stop_signals` takes over SIGTERM and SIGHUP only from the main thread, so a run from the MCP server's thread pool sets none, leaves alone any signal this process ignores, so `nohup` still keeps a hangup from cancelling a run, and hands back the previous handlers after, `SIG_DFL` for one set outside Python, which Python cannot put back.
- **The tail after a serial run's summary.** No serial run hung after its summary in the 21 measured serial runs and the probes beside them. A faulthandler probe of a serial run shows where the tail goes: pytest's unraisable-exception `gc_collect_harder` at unconfigure (0.6 s), the capture teardown (0.4 s) and interpreter finalization with no Python frame (over 1 s); the measured tail was 1.6-3.5 s, median by selection, against 1.1-1.9 s for xdist runs, and 7.8 s at a load average of 44. The amendment's candidate, the atexit `shutdown_tracer` taking `_client_lock` (`src/devops_cli/telemetry/tracer.py`), cannot deadlock there: the lock is held only for lazy set-up and cache reads (`_ensure_meter`, `_get_sdk_instrument`, `_get_grpc_exporter`, `_get_executor`, `_get_http_client`) and by `shutdown()` after `flush()`, which waits for queued exports at most `DEFAULT_OTEL_DRAIN_TIMEOUT_SECONDS` (1 s); no export holds it during network I/O, every export's HTTP timeouts are 1 s, and nothing under it takes it again; in the probe, the atexit handlers finished inside the first half-second sample. The only bound after the summary line is the run's timeout, counted from the start of the run: 1800 s for `devops ci test`. A hang there is stopped at that timeout with the whole group.
- **Tests and doubles.** The tests drive `devops ci test` through the CLI, `runner.invoke(ci_app, ["test", ...])` in-process or the real `devops` command in a process of its own with a fake `uv` first on PATH, and double the process edge at the stdlib, `asyncio.create_subprocess_exec`, with `record_spawns` (`tests/support/session_spawns.py`); its process has pid 0, which the group stop refuses to signal. The ci, selection, repeat and process tests ask for `refuse_nested_test_runs`, which fails any real `uv` or pytest child; #1666 makes such a refusal suite-wide. The hung children are `sh` with a sleeping grandchild (`tests/support/hung_children.py`), watched through pidfds opened as soon as their pids are read and SIGKILLed through them on the way out if still running. The watch fails the test when the child leads no session of its own, and when the grandchild is outside the child's actual session, which also guards against a later process taking its pid; a check that fails never reads as an exit. The tests that rely on signal dispositions ask for `default_signal_dispositions`, which puts SIGINT on Python's handler and SIGTERM and SIGHUP on their defaults for the test, so a run under `nohup` or as a background job, which inherits SIGHUP or SIGINT ignored, behaves as one from a terminal. The real-`devops` driver puts the tree under test's `src` first on its PYTHONPATH, so it runs that tree. The driver runs with telemetry off and its output in a file. One exception to the public path: `devops ci test` has no timeout option, so its 1800 s bound cannot be shortened through it, and the tests of a run stopped at its bound drive the runner it uses, the public `run_subprocess_async`, with a short timeout.
- **Docs.** The targeted-test command is `uv run devops ci test <test-file>` in AGENTS.md's verification step and commands table, CONTRIBUTING.md, `docs/SDLC.md`, `docs/SELF_IMPROVEMENT.md`, `docs/ROUTINE_TASKS.md` and the knowledge base's quality-gate task; the generated AGENTS.md for devops-cli lists it and labels a bare `uv run pytest` as the full suite. `docs/TESTING.md` describes the per-test bound, the narrowed run's workers, its session and stop sequence, and the doubles. The `-n` help and the knowledge base's package table say the same.
- The fail-to-pass replay that pytest could not start, reported as could-not-run (the second amendment of 2026-10-19), is the pull request that closes #1669.
