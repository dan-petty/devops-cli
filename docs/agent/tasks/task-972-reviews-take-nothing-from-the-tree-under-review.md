# Task: Reviews Take No Config, Data, Contracts, Scanner Config or Probe Suppressions From the Tree Under Review (#972)

**Issue**: [#972](https://github.com/dan-petty/devops-cli/issues/972)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p1-high
**Scope**: scope/review

## Description
A review must treat the repository it reviews as untrusted (#946). The adversarial review of #946 reproduced five more channels through which that repository changed its own review or received its secrets. This change closes all five. One repository is exempt from the config and data channels: devops-cli's own, whose checkout holds the source of the devops-cli that runs. Its code already runs in the process, so a review of this repository from its own checkout or any worktree of it reads its project config and keeps all data under the main worktree's `.data`, exactly as before.

- **The rule, and which commands it covers** (`core/untrusted_trees.py`, new). `reading_untrusted_trees()` marks the process as running a command that reads a tree it does not own, and `reads_untrusted_trees()` says whether one runs. The `devops review` group callback (`review_main`) enters it with `ctx.with_resource`, so it holds for every review command, under `devops review` and `devops ai review` alike, and for the MCP tools that run them in-process (`review_path`, `review_branch`, `review_pr`, `review_findings`, `verify_finding`, `review_stats`, `review_export_feedback`). It covers every command of the group, not only those whose target lies in the working directory's repository: `devops review findings`, `verify`, `stats`, `export-feedback`, `hallucinations`, `corpus`, `samples` and `benchmark` read what a review wrote, and must resolve the data directory where the review wrote it, and `devops review pr` starts in the user's checkout, which `gh pr checkout` may have filled with the pull request's tracked `.data`. Other commands that read a tree, `devops scan`, `devops ai analyze` and the rest, keep the project layer, a feature for the user's own repositories. The state is the process's, behind a lock and a count, not a context variable: the review's work runs on worker threads, some of which start without their creator's context (`pool.py`'s fallback executor), and a lost flag would read the reviewed tree's config without a sign. In the MCP server a command that runs while a review does reads the user-level config and data too, unless its working directory is devops-cli's own repository. `reads_untrusted_trees()` is true only while such a command runs and the working directory is outside devops-cli's own repository (`is_own_source_repository`, below), so everything keyed on it, the config walk, the config cache key and `resolve_data_path`, behaves there as before #972. The root command (`main._delegate`) enters the rule as well for `devops review` and `devops ai review` (`_runs_a_review`, `CONST_REVIEW_COMMAND_WORDS`), before it opens the command's span: opening that span builds the process's tracer from the config, and its endpoint receives every span of the review, each LLM call's `llm.prompt_preview` among them. The MCP server's in-process dispatcher runs commands through that root command too.
- **Config** (`config/settings.py`). `_find_project_config_path` returns the file `DEVOPS_CLI_CONFIG` names, as before, and otherwise, while the rule holds, no file: the walk from the working directory would find the reviewed repository's `.devops/config.yaml`. In devops-cli's own repository the rule does not hold and the walk runs. `DEVOPS_CLI_CONFIG` is the explicit opt-in, as this repository's devcontainer uses for its own `config.yaml`. The cached merge is keyed on `reads_untrusted_trees()` too, so a merge made before a review is not reused inside it, nor one made inside after it.
- **Data** (`core/repo.py`). While the rule holds, `resolve_data_path` resolves a relative path under `CONST_USER_DATA_ROOT` (`~/.local/share/devops-cli`), in place of the main worktree, so the default data directory of a review started in another repository is `~/.local/share/devops-cli/.data`. An absolute path is one the user named and stands: an absolute `DEVOPS_CLI_DATA_DIR`, `data.dir` or `DEVOPS_CLI_DATA_*` path is the opt-in for keeping review data in a repository. A relative one is re-rooted like the default. What a review keeps, other commands read and write too, so `resolve_review_data_path` resolves a relative path to it under `review_data_root()` for every command: the main worktree when the working directory is in devops-cli's own repository, as `resolve_data_path` gives there, and the user-level root otherwise. The data has one place either way: the reviews directory (`_get_reviews_base_dir`, and the dashboard's `_reviews_root`), so the history and the leave-one-out baseline of #607; the hallucination catalog; the mitigations ledger, which `devops pr check-readiness` reads; the feedback dataset, which `devops review export-feedback` writes and `devops ai prompt-eval` reads, its `--dataset` too (`review_data_root()`); the run store, which `devops ai runs` reads; samples; library contracts, which `devops ai ingest` writes; and the spend ledger and pricing registry beside it, which `devops ai cost` reads. `resolve_ledger_path` lost its `start_path`, which no caller passed. Caches stay with `resolve_data_path`: the analysis cache, the LLM response cache and the probe's mypy cache resolve under the user-level root inside a review started in another repository and under the main worktree otherwise, which costs only misses. Outside devops-cli's own repository, review data a repository's `.data` already holds stays there and is no longer read: moving it into `~/.local/share/devops-cli/.data`, or an absolute `DEVOPS_CLI_DATA_DIR` naming that `.data`, keeps it.
- **devops-cli's own repository** (`core/repo.py`, `core/untrusted_trees.py`). `is_own_source_repository(start_path=None)` says whether the repository at `start_path`, by default the working directory, is the one whose checkout holds the running devops-cli's package (`_own_source_dir()`, `Path(devops_cli.__file__).resolve().parent`). It compares git directories: `_source_repository(package_dir)` is the shared git directory (`_own_common_dir`) of the nearest checkout holding the package, and `_repository_at(start)` that of the nearest checkout holding the start, so every worktree of the repository, linked outside the checkout or nested in it, is the same repository, whichever of them holds the running source. Two cases decided against comparing `main_worktree_root`, which climbs to the top-most root: a clone nested in the checkout, such as this checkout's `repos/google-antigravity/antigravity-sdk-python` or `.data/samples/express`, resolves to the checkout's main worktree, yet the config walk from inside it stops at the clone's own `.git` and would read the `.devops/config.yaml` it commits; and an installed devops-cli in a project's `.venv`, or under a `$HOME` that is a dotfiles repository, resolves to the repository around it. So a clone with a `.git` of its own is another repository, and a package that lies in the interpreter's install directories (`sysconfig` purelib and platlib, `site.getsitepackages()`, `site.getusersitepackages()`, `_is_installed_copy`) trusts no repository, nor does one outside any checkout. The source's lookup is cached for the process (`_own_source_dir` and `_source_repository`), the start's per absolute path (an `lru_cache` of 64), so the config cache key, read on every `load_settings`, walks nothing twice; neither runs git. `reads_untrusted_trees()` folds the check in, and `review_data_root()` uses it, so one predicate decides both. `resolve_grounded_contracts` refuses contracts inside the tree under review unless that tree is devops-cli's own repository (`_reviewed_tree_holds`), so a review of this repository grounds the contracts in its `.data/libraries`. The test suite runs as an installed devops-cli does (`conftest.isolate_own_source_repository` points `_own_source_dir` into the venv's site-packages), since it imports devops-cli from the checkout it runs in, and the tests of the exemption point it at a repository under `tmp_path`.
- **Contracts** (`ai/rag/library_store.py`, `ai/review/contract_grounding.py`, `ai/review/pipeline.py`, `ai/review/review_environment.py`). `library_contracts_dir()` is `libraries/` under the data directory (`CONST_LIBRARIES_DIR_NAME`), resolved by `resolve_review_data_path`; `LibraryVectorStore`, contract grounding, `devops ai ingest library|index-libraries|query-library`, the drift auditor and the MCP `resource://libraries/indexed` resource all default to it, where each used `.data/libraries` relative to the working directory. `resolve_grounded_contracts(..., reviewed_tree=...)` refuses, with a warning, contracts that lie inside the tree under review, even in a data directory the user named there, unless that tree is devops-cli's own repository. The pipeline passes `reviewed_tree(self.target_dir)`, the checkout holding the target or, outside one, its directory; a single-file path review's folder (#1038) walks up to its checkout, so the refusal covers the whole repository.
- **Scanners** (`security/base.py` and the scanner modules). `BaseSecurityScanner.scan(..., isolated=True)` runs the scanner in a fresh `tempfile.TemporaryDirectory` and appends each of its `isolation_files` (`ScannerConfigFile(flag, name, text)`), written there: kube-linter `--config` (`checks: {}`), Trivy `--config` (`{}`) and `--ignorefile` (empty), Gitleaks `--config` (`[extend] useDefault = true`) and `--gitleaks-ignore-path` (empty), Bandit `--ini` (`[bandit]`). Each keeps the scanner's defaults (`CONST_REVIEW_SCAN_*`). Pluto reads no config or ignore file, and Semgrep takes its rules from `--config` alone and does not apply `.semgrepignore` to a file named on its command line, which is how the review names every file, so both only run from the temporary directory. The `run_*_scan` functions take `isolated` (keyword, default off); the review's scanner helpers pass it, and `devops scan` and the other scanner commands do not, so they still read the project's own scanner config. As the issue allowed, a project's own scanner config does not count for a review, so nothing is read at the base revision.
- **The probe** (`ai/review/verification.py`). `_strict_pass_settles` gates `_check_none_dereference_hallucination`. `_module_suppresses_type_errors` reads the module before mypy runs, as mypy decodes it (`_text_mypy_reads`): after any UTF-8 byte order mark, and not at all when its first two lines declare an encoding other than UTF-8 (`CONST_SOURCE_CODING_DECLARATION`), since mypy decodes by that declaration and a module declaring UTF-7 spells `# mypy:` as `+ACM- mypy:`. It refuses a module holding a `type: ignore` comment, read with `tokenize` from the comments, where mypy takes it (`CONST_TYPE_IGNORE_COMMENT`), or a line starting `# mypy:`, read from the raw lines as mypy 2.3.1's `get_mypy_comments` reads it, a line inside a string too (`CONST_MYPY_CONFIG_LINE`); each match is wider than mypy's, which only withholds a claim. A module that does not tokenize, or exceeds the 50 MB file cap, gets no claim either. After the existing strict pass, `_any_typed_lines` runs mypy once more, isolated as the probe is and on its warm cache: on a copy of the module with `# mypy: disallow-any-expr` appended after its last line (`--shadow-file`, `--output json`), so the option holds for that module alone, its lines keep their numbers and mypy reports them under the module's own path. The module passed the strict pass, so each error names a line holding an expression of type Any. The probe claims nothing when the cited lines hold one, when the finding cites no line and any line does, or when mypy cannot answer. `_probe_command` builds both argvs, so the first stays exactly #946's.
- **Messages and docs**. `devops review findings` names the directory it found no session in (`MESSAGES.review.no_review_sessions_found`), since it is not always `.data/reviews/`. `docs/CONFIGURATION.md` (its generator now names the real project config files, not `.devops-cli.yaml`) and `docs/ENV_VARS.md` state the rule and the exemption; `docs/SELF_IMPROVEMENT.md` describes the probe's new refusals; `docs/CLI_REFERENCE.md`, `docs/commands/ai.md` and `docs/MCP_TOOLS.md` are regenerated (`devops docs generate --sync-readme`) for the contracts defaults and the `--dataset` help, which say where review data is kept. The other documents keep naming `.data/reviews/`, `.data/common_hallucinations.json` and `.data/feedback_dataset.jsonl`: the configured relative paths, and where review data is in this repository. The review knowledge base's `devops review branch --export-md` example named an option that does not exist, and now reads the session's `review.md`.
- **What the merged items had already done**. #950 closed the issue's exact catalog reproduction: a planted signature entry no longer matches, since signature matching reads the shipped entries alone. Run against the merged tip, it leaves the SSRF finding UNVERIFIED. A learned entry recording a person's verdict on the exact claim of a real finding still came from the reviewed tree and still invalidated it, which `test_a_review_takes_no_verdict_from_a_catalog_the_repository_commits` shows. #946 had isolated the probe's mypy from the tree and read conventions at the base revision; it did not touch config, data, contracts, scanner config or suppressions. #846, #847, #915, #948, #949, #951, #987 and #1009 change none of these channels.
- **#1014**. The review clients' response cache is `ai.cache.dir`, by default the relative `.data/cache/llm`, resolved by `resolve_data_path`. Under a review started outside devops-cli's own repository it now resolves under `~/.local/share/devops-cli/.data/cache/llm`, out of the tree under review, so #972's rule covers it (`test_a_reviews_data_lives_under_the_user_level_data_root`). It is a cache, not review data, so outside a review it still resolves under the main worktree (`resolve_data_path`, not `resolve_review_data_path`). #1014's location criterion is met only in part: inside a review the cache never lies in the tree under review, but `ai.cache.dir` still does not follow `data.dir`, so `DEVOPS_CLI_DATA_DIR` does not move the cache to `<DATA_DIR>/cache/llm`. That half, the key check and the key-field write stay with #1014.
- Known limits, not covered by the issue: inline suppressions in reviewed files that the scanners honour (`# nosec`, `# nosemgrep`, `gitleaks:allow`, kube-linter's `ignore-check.kube-linter.io/*` annotations), and type lies a strict pass accepts without a suppression comment (`cast`, `typing.no_type_check`, an `if TYPE_CHECKING:` declaration, a lying `.pyi` stub beside an imported module). The kube-linter parser reads the check name from `Diagnostic.Check`, where kube-linter 0.8.3 writes it beside `Diagnostic`, so every kube-linter finding is titled `kube-linter-check`; that is unrelated to this change. The MCP server builds its tracer once, when it starts, from the config of the directory it starts in, so the spans of a review it runs go to that endpoint; started inside an untrusted repository, the whole server reads that repository's config. The telemetry export-failure marker, touched at exit on a terminal when every export failed, resolves the data directory after the rule has ended. `devops workspace clean` prunes the repository's data directory, not `~/.local/share/devops-cli/.data`, which now holds the data of reviews started in other repositories. A review of a `repos/` clone started in the clone keeps its data under `~/.local/share/devops-cli/.data`, while one started in this checkout with the clone's path keeps it under this checkout's `.data`. A working directory inside devops-cli's own checkout but in no git checkout of its own, such as an unpacked archive, counts as that repository, as it did before #972: the config walk from there reads a `config.yaml` it holds. The analysis cache under the user-level root is shared by every repository a review reads, and `load_cached_analysis` takes the newest analysis there: the pipeline reuses a file's analysis only when its content hash matches, but `runner._load_file_analysis_metas` does not check, which an absolute shared data directory already did before this change.
