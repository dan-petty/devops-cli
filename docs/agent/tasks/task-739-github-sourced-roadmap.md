# Task: GitHub-Sourced Roadmap, Migration and Generated Roadmap View (#739)

**Issue**: [#739](https://github.com/dan-petty/devops-cli/issues/739)

**Milestone**: v0.2.25
**Priority**: priority/p1-high
**Scope**: scope/github

## Description
`docs/ROADMAP.md` was the roadmap's hand-edited source, pushed to GitHub along three paths that no code kept honest, and work kept joining the current release. ADR 0001 reverses the direction: issues are the items, milestones the releases, the board holds Status and Priority, and `docs/ROADMAP.md` is generated. This adds the `devops roadmap` command group with `migrate` and `render`, and removes every path that pushed the file to GitHub.

- **Config.** `.github/roadmap.toml` sets `board = 2` and `planning_horizon = 3`, which keeps v0.2.26 and the v0.2.27 and v0.2.28 releases that hold the work due before v0.3.0. `roadmap/config.py` parses it with `tomllib` into `RoadmapConfig`, a frozen pydantic model with `extra="forbid"`: `board` is required, and `release_cap`, `discovery_threshold`, `planning_horizon` and `stall_days` default to 12, 24, 2 and 14 (`DEFAULT_ROADMAP_*`). An invalid file raises `ConfigurationError` naming the key. Both commands read it, the board template and `docs/ROADMAP.md` through the store's `repository_file`, which reads the contents API at `--ref` (the default branch when omitted). A failed read stops the command with exit 1.
- **Store additions** (`roadmap/store.py`, both adapters, contract suite): `board()`, `create_board(title, fields)`, `board_fields()` (option ids, colors and descriptions from GraphQL), `delete_field(name)`, `cards()`, `set_card_field(card, field, value)`, `remove_card(card)`, `issues()`, `create_issue(title, body, labels)`, `close_issue(number, reason, comment)`, `delete_release(version)`, `workflows()` and `repository_file(path, ref)`. The GitHub adapter edits any card, drafts included, by its node ids, and a card write records the value in the card's `Job record`, as an Item write does.
- **No option replacement.** The issue asked for a store operation that replaces a single-select field's options while sending every kept option's `id`. GitHub's public GraphQL schema rules that out: `ProjectV2SingleSelectFieldOptionInput`, the type both `updateProjectV2Field` and `createProjectV2Field` take options as, defines only `color`, `description` and `name`, and GitHub rejects an input field the type doesn't define. `updateProjectV2Field` is the only mutation that edits options, and the REST Projects API only creates fields. So every option list sent gives each option a new id, clearing it from every card and from every built-in workflow that sets it. The store has no option-editing operation. A person renames, adds and removes options in the board's field settings, which keep ids, and migrate lists those edits. The GitHub adapter sends an option list (`option_update_request`, name, color and description only) just once: to align the Status of a board it has just created, which holds no cards. The in-memory adapter's `edit_options_by_hand` models the field settings page: an option kept by its id keeps its cards' value under its new name, and a removed one clears it.
- **Board template** (`.github/project-template.json`): Status is New, Ready, In Progress, In Review, Done and Blocked. New carries `"replaces": ["Backlog", "Todo"]` (`ProjectFieldOption.replaces`). Migrate's plan has a person rename the first one the board has to New in the field settings. Migrate then moves the cards holding the other to New, and the person removes it. Category and the Milestone text field are gone, the Roadmap Timeline drops Category, and the Value vs Effort view groups by Value.
- **Code that follows the template** (`github/projects.py`): the default Status and the `status/backlog` mapping are New, `plan_item_changes` no longer plans the Milestone field (the board mirrors it), and `project sync` creates missing fields only. `_sync_single_select_field_options` and `_format_remote_options` are deleted. `initial_status` and `declared_priority` are public because migrate fills unset fields by the same label rules. `CONST_PROJECT_WORKFLOW_EXPECTATIONS` matches board 2 as its owner set it on 2026-10-01: New on add and reopen, Done on close and merge, In Review on a linked pull request, and no auto-close, auto-archive or auto-add entry.
- **`devops roadmap migrate`** (`roadmap/migrate.py`) reads everything once, then plans every write as a `PlannedWrite` (one store call and the changes it makes). The steps, in order:
  - **Board.** A board number that names no board plans one board created from the template. The command prints its number and asks the person to check the Status each built-in workflow sets, since the new board's Status options were replaced. Otherwise, for every template single-select field, migrate plans `OptionEdit`s that a person makes in the board's field settings. A template option the board lacks is a rename of the first option it `replaces` that the board has (Backlog to New), or else an addition (Blocked). Any other option it replaces (Todo) is merged: migrate sets every card holding it to the template option, then a person removes it. Options the template doesn't know are kept. Single-select fields the template lacks (Category) are deleted. A board that lacks a template field is refused before any write, naming `devops gh project sync`, which creates it.
  - **Fields.** An open Item's unset Status gets its `status/*` label's status, else New; an unset Priority gets its `priority/pN` label's. Closed issues, pull requests and epics are left alone.
  - **Epics.** Every open `type/epic` issue is closed as not planned with a comment that links ADR 0001, and every epic card is taken off the board.
  - **Releases.** The current release (the lowest open one) and the next `planning_horizon` open releases stay. Open Items of later releases move to the backlog, and those milestones are deleted. Closed milestones are left alone.
  - **Matrix.** For each open matrix row whose Feature / Focus matches exactly one issue title, an unset Value or Effort is set; a set value that differs is listed under "Left alone".
  - **Not planned.** Each "❌ Rejected" row and each "not building" entry becomes an issue closed as not planned, carrying the row's text, unless an issue of that title already exists.
  - **ROADMAP import** (`roadmap/document.py`). Every heading counts, range and `####` headings included; an entry belongs to its release only when its heading names exactly one version, so entries after the v0.5.x themes are backlog entries. An entry is linked when its heading names its issue (`Issue #N`, `Issues #N, #M`) or exactly one issue title equals it once a conventional-commit prefix is dropped and case and whitespace are folded. No keyword or fuzzy matching. A file carrying render's marker is not imported. Migrate edits no issue body.
  - **Report**, printed as Markdown: (1) P0 feature candidates, the open P0 entries in releases beyond the newest kept release, with "matches #N" for a linked entry and "overlaps #N" for a heading's `Overlaps #N` tag; (2) every other open entry without an issue, with its `docs/ROADMAP.md:line`, section and priority; (3) open entries whose issues are all closed; (4) every planned write with its old and new value, the option edits a person makes by hand (each marked before or after `--confirm`), the matrix values left alone, and any enabled auto-add workflow.
  - Without `--confirm`, or with `--dry-run`, it prints the plan and writes nothing. With `--confirm` it first checks that no rename or addition is still due, because the planned writes set those options (`require_option_edits_made`). If one is due, it exits 1 before any write and names the edits. Otherwise it makes the writes in order. A run with nothing to write that still has a removal to make says so instead of "Nothing to migrate". Every step plans only what is still to do, so a second run plans nothing and a run that stopped part-way continues. Item and card writes go through `set_field` and `set_card_field`, so each is in the job record (ADR 0002).
- **`devops roadmap render`** (`roadmap/render.py`) renders the whole file before writing: the marker line, the current release, the `planning_horizon` planned releases, then the backlog. Items are ordered by the board's Priority options, unset last, then by number. Each line holds the checkbox (checked when closed), number, title, Status, Priority, Value and Effort. Nothing in it depends on time or the local checkout. `--dry-run` prints it; a failed read writes nothing and exits 1.
- **MCP**: `roadmap_render(repo, ref, dry_run=True)` and `roadmap_migrate(repo, ref)`, which always passes `--dry-run` and has no `confirm` parameter. `roadmap` joins `CONST_MCP_LAZY_DOMAINS`, the dispatcher's prefix map and the `hydrate_tool_domain` docstring.
- **Removed, without shims**: `gh issues sync-roadmap`, `gh issues reconcile-roadmap`, `github/roadmap_sync.py`, `gh milestones sync` with `--create-release-epics`, `extract_roadmap_milestones`, `sync_repository_milestones`, `MilestoneSpec`, `MilestoneSyncResult`, `diff_milestones`, `find_milestones_to_update` and their exports, `devops release epic`, `github/release_epics.py`, `CONST_ROADMAP_PRIORITY_LABELS`, `CONST_ROADMAP_SCOPE_KEYWORDS`, the MCP tools `gh_sync_roadmap`, `gh_issue_reconcile_roadmap`, `gh_milestone_sync` and `release_epic_sync`, their help strings, `tests/test_github_roadmap_sync.py`, `tests/test_release_epics.py`, and the roadmap tests in `tests/test_gh_issues_milestones.py`, `tests/test_github_milestones.py` and `tests/test_gh_cmd.py`. The mentions in `AGENTS.md`, `docs/ROUTINE_TASKS.md`, `docs/SDLC.md` and `ai/knowledge_base/devops_cli/tasks/github_project_management.md` now describe the GitHub-sourced roadmap, and their descriptions of Category and the Backlog status follow the template. The generated reference docs and the README matrix are regenerated.
- **`docs/VISION.md`** holds the 16 principles, the six v0.3.x section themes and the v0.4.x/v0.5.x themes, moved as they are without release numbers.
- **`docs/ROADMAP.md`** before migration: a banner under the title says GitHub is the source (ADR 0001), `devops roadmap render` regenerates the file at the next cut, and people open an issue instead of editing it. Of the entries D9's #836-#862 were filed from, two had no number yet:
  - Instruction Envelope Audit → `Issue #841`, which supersedes it.
  - Retire the Tuple-Assert Mandate → `Issue #851`.

  #839, #843 and #850 each filed only part of an entry (the `ci_run` defect half, steps 1, 3 and 4 of the single-source CI gate, and changed-line coverage without the vanished-test report). Their bodies leave the rest "for the #739 triage", so those entries keep no number and stay in the report's second section. The six `devops gh pm` entries carry `Overlaps #N`, naming the roadmap job each overlaps without a verdict: fleet and daemon → #741 (the service and `devops roadmap run`), research and deps → #740 (reprioritization, which reads blocked-by links), plan → #744 (refinement), reconcile → #743 (closure).
- Split off to their own items: #879 (task files without status lines), #880 (the board's Priority as the only priority source) and #881 (remove `docs/RELEASE_NOTES.md` and `devops docs compact`).
