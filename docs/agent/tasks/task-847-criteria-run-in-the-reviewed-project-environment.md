# Task: Criteria Commands Run in the Reviewed Project's Environment with a Measured Python Timeout (#847)

**Issue**: [#847](https://github.com/dan-petty/devops-cli/issues/847)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p2-medium
**Scope**: scope/review

## Description
Executable verification criteria ran in the host sandbox with `PATH=/usr/local/bin:/usr/bin:/bin` and only `/usr` bound. `python` was the system's Python 3.14.8, whose third-party modules came from the devops-cli install in `/usr/local/lib/python3.14/dist-packages`, not from the reviewed tree's dependencies. `pytest`, `ruff`, `rg` and `file`, all allowlisted, were not on that PATH: in the saved review sessions all 11 pytest and all 6 ruff criterion runs failed with `bwrap: execvp`. Python criteria shared the 5 s limit of `grep` and `git`, and 1,353 of 4,027 python criterion runs in the saved sessions (34%) hit it, most of them still importing the code they were to check. Nothing told a timed-out criterion from one that ran and failed.

- **The repository's environment** (`sandbox/host.py`). `HostSandbox._resolve_repo_environment` looks for `<repo root>/.venv/bin`, using `CONST_HOST_SANDBOX_VIRTUALENV_BIN`. When it is a directory whose resolved path stays inside the bound repository, and its `python` can start in the sandbox, it leads the PATH (`<root>/.venv/bin:/usr/local/bin:/usr/bin:/bin`); otherwise the policy's PATH stands, so a repository without a usable virtualenv behaves as before. The caller's `env` still wins over it, and it wins over the policy's `default_env`. `_effective_repo_root` now holds the root lookup `_resolve_repo_mounts` did inline, so both use one rule. Verification runs criteria in the review's target directory (`target_dir`), so path and branch reviews of a local checkout use its `.venv` once `uv sync` has made one; a PR review writes only the changed files into a fresh directory (`_materialize_pr_head`), with no `.venv`, so its criteria keep the system PATH, as before.
- **The interpreter's installation** (`sandbox/host.py`). The issue assumed `.venv/bin/python` links into `/usr`. It no longer does in the devcontainer: `.python-version` pins 3.14.7 and the system ships 3.14.8, so uv installs a managed CPython under `~/.local/share/uv/python` and the virtualenv links there, outside every mount, as the main checkout's `.venv` has done since 2026-10-02. `_virtualenv_interpreter_binds` resolves the link; when the interpreter lies outside `/usr` and the repository, it binds the installation (the interpreter's `bin/..`) with `--ro-bind`, whatever the policy's `read_only`. Only that directory, and the empty directories above it, appear under `/home` in the sandbox. The reviewed repository chooses where that link points, so `_is_python_installation` binds a prefix only when it holds CPython's standard-library landmark (`CONST_PYTHON_STDLIB_LANDMARK_GLOB`, `lib/python3.*/os.py`, which `getpath` looks for), contains neither the home directory nor the repository, and has no `CONST_SANDBOX_SENSITIVE_SUBPATHS` part (`.ssh`, `.aws`, `.kube`, `.git`). A link aimed at the home directory, a credential directory, a directory above the repository or any directory that is not a Python installation binds nothing, and neither does a link to nothing. Such a virtualenv's `python` could not start, so it stays off the PATH and criteria use the system's tools, as before.
- **The allowlist** (`config/constants.py`, `ai/tasks/review.md`, `ai/tasks/review_output_instruction.md`). `CONST_ALLOWED_CRITERIA_BINARIES` drops `pytest`, `rg` and `file`; every binary left resolves inside the sandbox's mounts, `python`, `python3` and `ruff` from the repository's `.venv/bin`. A pytest criterion is now refused by `validate_criteria_command`, so the schema keeps it as a sentence (`executable: false`) and the executor never runs it. That holds for every form pytest took in the saved sessions (12 distinct bare `pytest`, 35 `python -m pytest` and 63 `pytest.main` commands), and for the forms below that none of them took: `_check_python_command` refuses `-m pytest` and `-m _pytest` (and their submodules), and `_check_python_script` refuses a script that `_starts_pytest`, that is, one that imports `main` or `console_main` from `pytest` or `_pytest`, pytest's implementation package, or reaches either through an attribute chain that starts at a name `_pytest_names` finds bound to one of them (`import pytest as p`, `import _pytest.config`, `from _pytest import config`) or at `__import__` or `import_module` of a pytest module's literal name (`_imports_pytest_by_name`; `CONST_PYTEST_MODULES`, `CONST_PYTEST_RUNNER_FUNCTIONS`, `CONST_IMPORT_BY_NAME_CALLS`). A runner the script names only at run time (`getattr(pytest, 'main')`, `runpy.run_module('pytest', run_name='__main__')`, `__import__('py' + 'test')`) is not seen; see the pending bullet. Under the repository's interpreter and the 30 s python limit those forms would run the project's real tests, and `pytest.main` with its return value discarded exits 0 even for a test file that does not exist (replayed here: exit 0 in 0.99 s, `ERROR: file or directory not found`). Importing pytest stays allowed, for `pytest.raises` or a test module that imports it. `find` is still allowlisted, for searching, but `_check_find_actions` refuses the actions that run a command or write a file (`CONST_FORBIDDEN_FIND_ACTIONS`: `-exec`, `-execdir`, `-ok`, `-okdir`, `-delete`, `-fprint`, `-fprint0`, `-fprintf`, `-fls`): with the repository's `.venv/bin` first on PATH, `find tests/… -exec pytest … {} +` ran the project's tests (the review's replay: `1 passed … in 3.67s`), and `find . -maxdepth 0 -exec echo ran {} +` runs `echo`, which is not allowlisted, through the sandbox (replayed here: exit 0, `ran .`). None of the 19 distinct `find` criteria in the saved sessions uses one. `validate_criteria_command` now looks the argument check up by binary (`_ARGUMENT_CHECKS`: `find`, `git`, `python`, `python3`). Saved sessions holding `executable: true` pytest criteria still load, as sentences. Both prompts now describe an executable criterion as a `python -c` command only. `CONST_PYTHON_CRITERIA_BINARIES` names `python` and `python3` once, for the three checks in `review_environment.py` that spelled the set out.
- **The python criterion's shape** (`ai/review/criteria_evidence.py`, `ai/review/review_environment.py`). Python reads its own options up to the first `-c` or `-m`, inside a cluster too (`-Bc <script>` runs the script, and so does `-cpass`), and passes what follows to that script or module. The validator and the evidence rule each read the command their own way: `_check_python_command` took the first `-c` or `-m` token, missing one inside a cluster, and the evidence rule's `_python_script` took the script after the first `-c` token wherever it stood. So `python -m this -c '<assert>'` and `python -Bc pass -c '<assert>'` passed the validator, exited 0 without running the assertion, and the evidence rule counted the assertion: a failing assertion over the cited code settled VERIFIED 1.0, or INVALIDATED 0.0 (the review's replay through real bubblewrap, repeated here before the fix, and `test_an_assertion_python_never_runs_settles_no_verdict`); `python -Bc "<script importing subprocess>" -c pass` checked only `pass` and ran the script (the review's replay, repeated here, printed `id -u`'s `1000`). Both predate this item (b6847e9 accepts and counts the same commands, per the review). `python_invocation` in `criteria_evidence.py` is now the one reading of a python command: it returns the option and its script or module only when `-c` or `-m` is the first argument, and None for every other shape. `_check_python_command` refuses a command it returns None for ("A python criterion is `python -c <script>` or `python -m <module>`, with -c or -m as its first argument"), and `_python_script` returns a script only for `-c`, so `python -m X -c '<assert>'` may run X but its trailing assertion never counts. All 3,710 distinct python criteria in the saved sessions have `-c` or `-m` first, so none of them changes; the prompts describe `python -c` only. The `-m` check now refuses a submodule of a forbidden module (`http.server`), as `_is_safe_ast_node` does for an import. `_criterion_argv` inserts `-W ignore::SyntaxWarning` unconditionally: a validated command can no longer hold a `-W` of Python's own, only one of the script's.
- **Timeouts** (`config/defaults.py`, `ai/review/review_environment.py`). `execute_criterion_command` takes `timeout=None`. `_criterion_argv` gives a `python` or `python3` criterion, by the binary's name as the allowlist reads it, its `-W ignore::SyntaxWarning` as before (now always, see above) and `DEFAULT_CRITERIA_PYTHON_TIMEOUT_SECONDS` (30.0), and every other command `DEFAULT_CRITERIA_EXECUTION_TIMEOUT_SECONDS` (5.0, unchanged), `grep` and `git` included. An explicit `timeout` still wins. The measurement is below.
- **Timed-out criteria** (`sandbox/host.py`, `ai/review_schema.py`, `ai/review/pipeline.py`). The sandbox's internal 4-tuples became `_SandboxOutcome`, a `NamedTuple` with `timed_out`, set by the selector loop's deadline and, for a mocked process, by `subprocess.TimeoutExpired`. `HostSandboxResult.timed_out` and `CriterionExecutionResult.timed_out` carry it to `findings.json` and `candidates.json`; older sessions load with `false`. `_build_criteria_outcomes_section` adds "## Executable Criteria" to `review.md` after the verdict distributions, with one row of Passed, Failed, Timed Out and Not Run over the candidate findings' executable criteria, and nothing when there are none. Failed counts only a criterion that ran to a non-zero exit. Exit code -1 is what `_evaluate_criteria_verdict` treats as not run: with `timed_out` it is Timed Out, and without it (no bubblewrap, a spawn error, output past the cap) it is Not Run.
- **#846, and the merge order.** #846 merged into `release/v0.2.25` first, as b6847e9 (#1035), and this branch is rebased onto it, so #847 never lands without it. This change does not touch the verdict functions #846 rewrote, `_evaluate_criteria_verdict` and `_reconcile_finding_from_criteria`: a timed-out criterion has exit code -1, which they treat as not run. Without #846 the verdict function counted any exit 0 as proof, and the 30 s limit and the repository's interpreter let criteria finish that timed out at 5 s, most of which check nothing: in the saved sessions, 635 of 650 distinct verification and 539 of 563 invalidation python criteria that timed out at 5 s hold no `assert`, `raise` or `sys.exit(` (the review's count). On top of #846's evidence rule, a print-only criterion like it now finishes and passes yet settles nothing, and one that asserts over the cited code still settles the verdict; two new tests hold both (see Acceptance Criteria).
