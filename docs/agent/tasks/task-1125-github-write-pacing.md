# Task: GitHub write pacing decided from the request gh sends (#1125)

**Issue**: [#1125](https://github.com/dan-petty/devops-cli/issues/1125)
**Status**: Done
**Milestone**: v0.2.26
**Priority**: priority/p1-high
**Scope**: type/bug, scope/github, priority/p1-high

## Description

GitHub asks for at least a second between mutative requests, and its secondary limits count REST and GraphQL writes together. `run_gh` gives a write that interval (`mutation_min_interval`) only when the classifier calls it a write, and the old classifier read argv tokens: a GraphQL mutation, a `gh api` call gh sends as an implicit POST and `gh project link` went out unpaced, while `gh issue list --label sync` was paced as a write. Part A (this pass) decides read or write from the request gh will send.

- **Request description**: `devops_cli/github/request_classifier.py` classifies a `GitHubRequest` (method, endpoint, GraphQL document, operation name) with `is_write_request`. A REST request writes when its method is POST, PUT, PATCH or DELETE; a `graphql` request writes unless the operation it runs is a query. #983's session can build the same description and ask the same question.
- **gh's argv**: `describe_gh_api_request` builds the description from `gh api`'s argv, parsed by `argparse` (`allow_abbrev=False`, `exit_on_error=False`, `parse_known_args`) with every flag `gh api --help` lists, so `-XPOST`, `-X=POST`, `--method=post`, `-iXPUT` and attached fields read as gh reads them. The only rule written by hand is gh's documented method default: GET, or POST when a field or `--input` is given. The document comes from the `query` field (`-f`, or `-F` with `@path` or `@-`, which gh reads; `-f` sends `@path` as is) or from the `--input` body (stdin or a file), and `operationName` selects among several operations. `run_gh` passes its `input` and `cwd`.
- **GraphQL documents**: graphql-core (`graphql.parse`, `graphql.utilities.get_operation_ast`), exact-pinned at 3.3.0 and imported only when a `graphql` request is classified.
- **Uncertain cases are writes**: an argv that doesn't parse, a document that doesn't parse, an `--input` body that isn't JSON, an unreadable `@file`, and several operations with no `operationName`.
- **High-level commands**: classified by the verb in the verb position, the second word once an `argparse` parser (same settings) has skipped the `-R`/`--repo` and `--owner` flags gh takes before the verb. `CONST_GH_READ_VERBS` (`view`, `list`, `status`, `checks`, `diff`, `show`, `item-list`, `field-list`, shared with the response cache) and the `search` group read; every other verb writes. `CONST_GH_MUTATION_VERBS` is removed. `gh auth` stays outside the ledger.
- **Across resources**: `_acquire_locked` schedules a write at least `mutation_min_interval` after the last write it scheduled, whatever its resource, so concurrent callers in one process share the spacing; `_last_mutation_epoch` is now read. Only the write moves to that slot: each resource's own schedule keeps its quota's pace, so reads are paced by their quota alone and never wait behind another resource's write or quota reset. Spacing across processes is not in this item.
- **`--paginate`**: `run_gh` classifies before its cache and page-by-page paths; a write with `--paginate` goes to gh once, as given, paced as a write.
- **Caching**: `_is_cacheable_api_call` uses the same parser, caching only a GET with no field or body. Reads cache as before; a call with a non-GET method in any form (`-X=POST`, `-XHEAD`), an attached field (`-ftitle=x`, `--field=k=v`) or an `--input` body, which the old token check let through, is no longer cached. `_is_api_mutation` and `_is_mutation_command` are removed.

## Part B: board reads within the GraphQL budget, and points charged

Built on #741 and #742. Stage 1 is the store and the limiter; stage 2 makes dry runs request-free and adds `--plan`.

- **Paged GraphQL board reads** (`roadmap/board_read.py`). `RoadmapBoardItems` reads `ProjectV2.items(first: 100, after:, query: $filter, archivedStates: [NOT_ARCHIVED])` with each item's id, content (`__typename`, number, title, url, repository) and its single-select, text and date field values, plus `rateLimit { cost limit remaining used resetAt }`. The store turns each node into the shape `gh project item-list` gave, so `_BoardItemPayload` is unchanged. `RoadmapBoardBudget` reads `rateLimit` and the same filter's `totalCount` (`items(first: 1, ...)`), and `RoadmapGraphQLBudget` reads `rateLimit` alone. The three documents are fixed templates, validated with graphql-core against GitHub's public schema; the test validates them against `tests/fixtures/roadmap/github-schema-board.graphql`, the schema cut to the types they use.
- **Argument builders.** `board_items_args`, `board_budget_args` and `graphql_budget_args` are pure, and so is every other `gh` argv and stdin the store sends: `roadmap/github_store.py` builds each with a module-level builder (`repository_query_args`, `board_fields_args`, `field_list_args`, `item_edit_args`, `card_edit_args`, `milestone_args`, `issue_milestone_args`, `comment_args`, `close_issue_args`, `create_issue_args`, `label_args`, `release_tag_args`, `branch_ref_args`, `create_branch_args`, `closures_args`, `issue_status_args`, `create_field_request`, `close_as_duplicate_request` and the rest). A number may be a `<placeholder>`. The store runs what they return, and the request plans list the same argv.
- **Budget.** Before a board read, the budget query; the read refuses with `GitHubRateLimitError`, having read no page, when `remaining` minus the read's cost (pages × the page cost, `DEFAULT_GH_PROJECT_ITEM_PAGE_POINTS` = 1 until a page reports more) is below `DEFAULT_GH_GRAPHQL_BUDGET_FLOOR` (250, 5% of the hourly 5,000). Before each later page, the read stops while `remaining` is below the floor.
- **Counts.** A read is whole when every page reported the same `totalCount` and the read holds that many distinct items. Otherwise it is read once more, and a second miss fails closed: "Read N of M" when the total held, or "changed while they were read" naming every total seen.
- **Filters.** Whole-board reads pass the job's filter (`CONST_ROADMAP_*_BOARD_FILTER`, through `open_roadmap(board_filter=)`); the backlog and candidate reads pass `is:open` (`CONST_ROADMAP_OPEN_ITEMS_FILTER`). Every job's filter is `""`, every item not archived: reprioritize judges a Release's closed members, render lists them, intake looks up any issue it is given, and migrate's one-time reads may include closed items. Closed items leave the reads once the board's auto-archive workflow is on.
- **Points in `run_gh`.** A GraphQL response's `rateLimit.cost` is charged to the limiter (`charge_points`, `points_charged`) and its `remaining` sets the points left; a command that reports no cost is charged `acquire`'s estimate. Neither the store nor project sync (`github/projects.py::_fetch_project_items_data`, which pages `RoadmapBoardItems` with the floor check) pages with `gh project item-list`, which reports no cost; no `src` module runs it.
- **Spend line.** `devops roadmap migrate`, `render`, `reprioritize` and `intake` end, however they end, with "GraphQL: N points spent, M left until HH:MM UTC.", from the first budget a response reported to a closing `RoadmapGraphQLBudget` read; a run the hourly reset crossed counts what it spent since the reset. The in-memory store prints nothing.
- **Caching fold.** `_is_cacheable_cli_read` takes the group and verb from `request_classifier.gh_command_words`, the verb-position parser, so `pr create --title list` is not cached.
- **Dry runs make no request** (stage 2, #412). `devops roadmap reprioritize`, `migrate`, `render` and `intake` `--dry-run` open no store, run no `gh`, start no process and open no socket. Each returns its job's real result type marked `dry_run`: `ReprioritizationPlan` and `MigrationPlan` with `requests` (the reads, ending with the closing `RoadmapGraphQLBudget` read) and `write_requests` (what `--confirm` adds before that read), `RenderedRoadmap` (new; render's result, its `text` empty) with `requests`, and `IntakePlan` as before. `roadmap/request_plan.py`'s `StoreRequests` gives the ordered `PlannedRequest`s of each store operation from the store's builders; `reprioritize_requests`, `migrate_requests` and `render_requests` put a job's operations in the order the job makes them, with each `condition` and `repeat` (a page repeat runs once or more, a per-item or per-release repeat any number of times). `run_gh` classifies each command for its method line ("GraphQL read", "REST write"). The dry run prints each request's method and target above its exact command and stdin, then the writes. A global `--dry-run` wins over `--confirm`.
- **`--plan`** (stage 2). `migrate`, `reprioritize` and `render` take `--plan`, following intake: it reads GitHub, writes nothing (render prints the file instead of writing it) and ends with the spend line. `migrate` and `reprioritize` without a mode flag still preview; render without one writes the file. One of `--dry-run`, `--plan` and `--confirm` at a time.
- **Intake's exact commands** (stage 2). Intake's dry run lists every `gh` command of each store operation, from the same builders, one line per command under the operation's target: a board write shows the field listing, the board read and the job record before the field. Only the embedding and model calls have no argv. Its reads end with the closing budget read.
- **MCP mirrors** (stage 2). `roadmap_render`, `roadmap_migrate` and `roadmap_reprioritize` take a `mode`, as `roadmap_intake` does: `plan` by default, `dry-run` makes no request, and `write` (render) or `confirm` (reprioritize) writes; `roadmap_migrate` has no writing mode.

## Follow-ups

- The store's other GraphQL reads (fields, workflows, pull requests, statuses, closes) ask for no `rateLimit`, so `run_gh` charges them its estimate; they read one request each.
- `devops_cli.exceptions.ai` imports `pydantic_ai.exceptions`, about 1.0 s of every CLI start (`python -X importtime -c "import devops_cli.main"`).
- Migrate's and intake's real runs are checked against their plans by store operation and by command set, not argv sequence; the sequence test covers reprioritize and render.
- High-level `gh issue list`, `gh pr list` and `gh label list` calls outside the roadmap (`commands/gh.py`, `github/issues.py`, `github/client.py`) page GraphQL inside gh with no cost reported; they are not board reads and stay as they are here.
- Narrower job filters (`is:open` plus a Release's closed members) need reprioritize and render to read closed members separately; the auto-archive workflow takes old closed items out of every read once it is on.

- Write spacing across processes: the per-target schedule and the last write are not persisted (`_persist_to_disk_locked`); a shared write clock belongs with the per-identity session of #983.
- `run_gh`'s page-by-page `--paginate` path rewrites a `gh api graphql --paginate` read to `graphql?page=1`; every paginated call in `src` is a REST GET, so gh's own GraphQL pagination is not used yet.
- argparse takes neither a `gh api` switch given a value (`--paginate=true`, `-i=true`) nor a value starting with a dash (`--jq -.a`), both of which gh accepts; such a call counts as a write, so it is paced as one and not cached. No call in `src` uses these forms.
- A write slot comes after the last write scheduled, not from a gap between writes: with concurrent callers in one process, a write waiting out one resource's reset holds later writes on other resources until it goes.
- `commands/pr.py::_run_gh_pr_command` has no caller.
