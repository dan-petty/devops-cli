# Task: The Generated Docs Mask Only Credentials and Show Off Switches, and Docs Name Only Things That Exist (#956)

**Issue**: [#956](https://github.com/dan-petty/devops-cli/issues/956)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p2-medium
**Scope**: scope/cli

## Description
A triage of review session 20261001-224227 against `release/v0.2.25` (c279c18) confirmed seven documentation defects. Each is fixed as the issue's **Fix** line says, with the differences given below, and each has a regression test that fails on the base of this change (e3ff98c) and passes here.

- **Masked defaults.** `DocGenerator.introspect_param` masked a default whenever any of eight keywords was a substring of the parameter's name or envvar, whatever the default's type. `_masks_default` (`docs/generator.py`) now masks only when the default can be a credential and the name or envvar says it is one. A bool, int, float or path default is never masked. `_names_a_credential` splits a name on `_` and `-` and matches whole words against `CONST_DOC_CREDENTIAL_NAME_WORDS` (APIKEY, AUTH, CREDENTIAL, PASSPHRASE, PASSWORD, SECRET, TOKEN) and the pair API, KEY (`CONST_DOC_CREDENTIAL_NAME_WORD_PAIRS`), both in `config/constants.py` with the old keyword set gone. So MAX_TOKENS, VALKEY_PORT and KEY_SIZE name no credential. A name whose last word is NAME (`CONST_DOC_CREDENTIAL_NAMING_WORD`) holds what a credential is called, so `--secret-name` shows `homelab-tls`, while `--secret-id`, an AppRole credential, stays masked. The issue's **Fix** also offers an explicit marker; Click's own one is used: an option with `hide_input=True` is always masked, whatever its type. The regenerated reference shows `1500` and `200` (`--max-tokens`), `0.2`, `6379`, `2048` (twice), `~/.config/devops-cli/tls/tls.key` (`k8s create-tls-secret --key`), `homelab-tls` (twice) and `valkey-runs-auth`, and no `<masked>` cell remains in `docs/commands/` or `docs/CLI_REFERENCE.md`. `docs/SELF_IMPROVEMENT.md`'s #951 A/B protocol keeps its bare-`<masked>` known-positive check unchanged: it builds its corpus from arm A, the commit before #951 (`38517a8~1`), whose command pages still hold those cells (at the protocol's seed 413, the four in `ai.md`). Differences from the **Fix** line:
  - The suffix exemptions `_size`, `_port` and `_increase` are not needed, because those defaults are numbers.
  - Exempting `secret` when the help text names a Kubernetes Secret was not done, since matching help text is brittle. `devops ai runs connect --secret` is renamed `--secret-name` (no alias, pre-1.0) instead. Its value names the Secret, as `--secret-name` does on `k8s enable-tls` and `tls enable-k8s`, and `security/sanitizer.py`'s `_SENSITIVE_ARG_FLAGS` already treats a bare `--secret` value as a credential.
  - A default that is neither text nor a number, boolean or path, such as a list or a callable, stays masked under a credential name. The **Fix** line would show it, and masking errs on the safe side.
  - The optional "show a plain resource identifier" rule was not added: `abc`, which the issue's test requires masked for `--api-token`, has the same shape as a resource name.
- **Off switches.** `ParamDoc.off_flags` holds Click's `secondary_opts`, which no longer join `flags`, and `_option_flags_cell` renders the off switches after a slash: `` `--rootless` / `--root` ``, `` `--all-nodes`, `-a` / `--single-node` ``. Every `--x/--no-x` pair in the reference reads the same way.
- **Telemetry variables.** `config/options.py` adds `TELEMETRY_ENABLED` and `TELEMETRY_ENDPOINT`. `config/env.py` maps them to `DEVOPS_CLI_TELEMETRY_ENABLED` and `DEVOPS_CLI_TELEMETRY_ENDPOINT`, with `EnvVarSpec` rows, and names `ENV_OTEL_EXPORTER_OTLP_ENDPOINT` with a row of its own. `get_tracer()` takes `enabled` and `endpoint` from `load_settings()`, whose `_apply_env_overrides` applies the registered names. `OTEL_EXPORTER_OTLP_ENDPOINT` is read only when that leaves the endpoint unset, and the built-in `http://localhost:4318` comes last. For the fallback to be real, `TelemetryConfig.endpoint` is `str | None = None`, and its field description names the fallback and the default, so `CONFIGURATION.md` still tells a reader both. `save_settings` dumps with `exclude_none`, so a save no longer writes the built-in endpoint into the file. A file saved before this change still names it, which now outranks `OTEL_EXPORTER_OTLP_ENDPOINT`; the changelog says to delete that line or set `DEVOPS_CLI_TELEMETRY_ENDPOINT`. The reads of `DEVOPS_TELEMETRY_ENABLED`, `DEVOPS_OTEL_ENDPOINT` and `DEVOPS_CLI_OTEL_ENDPOINT` are deleted without a shim, along with `_resolve_telemetry_settings`'s `otel` fallback, which named a section `Settings` does not have. The `devops telemetry profile` error, `tests/conftest.py`, `tests/test_telemetry_collector_export.py`, `tests/test_rag_query_telemetry.py`, `tests/test_review_untrusted_tree.py`, the `TELEMETRY.md` exporter line and the configuration knowledge-base article use the new names. `env_nested_delimiter` is dropped from `Settings` rather than documented as inert: `load_settings()` never honoured it, but a bare `Settings()`, which builds `CONFIGURATION.md` and the API's `/config` answer, did. #858 (tracer start-up imports) had not landed. The tracer imports nothing new at module load: the env name is imported inside the first `get_tracer()` build, as `load_settings` already was. `get_tracer()` called `load_settings()` before whenever the old variables were unset, so start-up work is unchanged in the usual case. The issue does not say what happens when the settings cannot load, as when a configuration layer does not parse or another registered variable cannot apply. A review of this change found the tracer then exporting to `OTEL_EXPORTER_OTLP_ENDPOINT` despite `DEVOPS_CLI_TELEMETRY_ENABLED=false`, where the base had held its own opt-out variable. `_resolve_telemetry_settings` now takes the section from `telemetry_from_environment` (`config/settings.py`). That applies the two registered telemetry variables, through the same `_apply_env_overrides` (now given the options to apply), to a default with export off. The layer that cannot be read may be the one turning export off, so export stays off unless `DEVOPS_CLI_TELEMETRY_ENABLED` turns it on. That also holds a file's `telemetry.enabled: false`, which the base lost in this case. The `TELEMETRY.md` exporter line says so.
- **Cadence letters.** `docs/ROUTINE_TASKS.md`'s `### Cadence B: Final Pre-Commit / Pre-PR Validation Stage` is `### Cadence A (final stage): Pre-Commit / Pre-PR Validation`, so B, C, D and E keep naming what task files cite them for. No link targets the old heading's anchor. #921 had not landed. This change touches only that heading line.
- **Knowledge-base examples.** The FastMCP manual's example imported `pods` from `devops_cli.commands.k8s` and returned a canned string. It now shows the real `k8s_pods`, and item 3 of its key concepts says tools validate with `_validate_mcp_arg` and run the `devops` CLI through `_run_mcp_cmd`. The new test found a second broken import: the Pydantic AI manual's example imported `Finding` from `devops_cli.models.review`, which does not exist and which the example never used, so that line is gone. The test reads fences with tree-sitter's Markdown grammar (`tree-sitter-markdown`, a direct dependency `ai/ast/engine.py` already loads), not a regex. It reads only articles that mention `devops_cli`, and reports each import as `<article>:<line>: <name>`. The issue asks to add the example to #920's correction list. That list is on GitHub, which this change does not write to, and the example is fixed here, so #920 need not carry it.
- **`k8s_pods`.** The MCP tool ran `devops k8s status`, ignoring its validated `namespace`. It runs `devops k8s pods -n <namespace>`, or `devops k8s pods -A` when the namespace is empty. These are two literal argv lists rather than one with a starred variable, so `devops docs check` resolves both `-n` and `-A` against the real command.
- **NVD and failed lookups.** `NVDClient`, `_parse_nvd_record`, their export from `devops_cli.security` and their test are deleted. `OSVClient.query_package` returns a `PackageLookupResult` with a new `reason` field: OSV's status code or the request's error, capped at `CONST_MAX_ERROR_DETAIL_LENGTH`. `query_batch`'s failures carry it too. `scan_osv` answers `OSV lookup failed: <reason>` instead of `No known vulnerabilities found`. Beyond the **Fix** line, the other caller, `DependencyRemediator.scan_and_plan` (`devops scan fix --package`), read a failed lookup as a package with nothing to fix, the same defect. It now raises `SecurityError` with the reason (`_found_vulnerabilities`). `scan_osv`'s reply moved into `_osv_records_reply`, so neither function's complexity rises: `scan_and_plan` stays at 6 by `devops scan complexity`. NVD is gone from:
  - the `security_intel_package` and `scan_osv` docstrings and `scan_osv`'s reply;
  - three places in the review pipeline, not two: the `review.md` dependency heading and both console table titles;
  - `PackageIntelResult.advisories`' description and `VulnerabilityRecord.source`'s comment;
  - the security cheatsheet row and the code review manual's line.

  `AGENTS.md` (CVE citations may come from NVD) and the Trivy manual (NVD CVE ids) mention NVD as a source of CVE ids, not as a lookup devops-cli makes, so they stay.
