## Description

The process's GitHub session (#767) had a token, a login and PyGithub; two calls built their own `httpx2.Client`, and every other request went through `gh`. This item makes the session the transport: REST requests, `Link` pagination and conditional requests on gidgethub, one ledger for gh and the session, and one place that classifies failures. It is delivered as seven pull requests, in the order of the plan on the issue. [ADR 0006](../../adr/0006-github-session-requests-go-through-gidgethub.md) records the choice of gidgethub and the transport's lifecycle.

**The REST transport (PR 1).**

- **Dependency.** `gidgethub==6.0.0` is pinned in `pyproject.toml`; `uv.lock` gains it and `uritemplate` 4.2.0.
- **Session.** `GitHubSession.rest(method, path, *, accept=None, body=None)` returns the decoded answer: JSON as Python values, any other body as text. The REST transport opens on the first request. `close()`, `reset_github_session()` and a `get_github_session()` that replaces the session on a token change close it.
- **Transport.** `src/devops_cli/github/session_transport.py` holds `SessionGitHubAPI`, a subclass of `gidgethub.httpx.GitHubAPI`, and `RestTransport`, which owns one anyio blocking portal and the client on its loop. The client comes only from `new_async_http_client(level=EgressLevel.PUBLIC)`, which this pull request leaves unchanged. The client follows redirects, sends `CONST_GITHUB_API_VERSION` and carries one request hook, `refuse_other_origins`. The hook compares `request.url.origin` with the origin of `CONST_URL_GITHUB_API_BASE` and raises `GitHubUnreadError` naming the refused origin before anything is sent. gidgethub sends `CONST_GITHUB_USER_AGENT` as the User-Agent. A path's `{` and `}` are percent-encoded before gidgethub expands it as a URI template (RFC 6570).
- **Lifecycle.** A `RestTransport` registers `weakref.finalize` over its resources, so it is closed by `close()`, when it is garbage-collected, or at interpreter exit while the portal's daemon thread still runs. Closing closes the client on the loop, then stops the portal with `cancel_remaining=True`, so a request waiting out a retry or a pacing pause is cancelled, not waited for. A request a close stops raises `GitHubUnreadError`. Before this, a process that sent a request and never closed its session hung at exit.
- **Pacing and ledger.** `_request` paces each attempt through `GitHubRateLimiter.acquire` in a worker thread, with the resource from `gh_request_resource(["api", path])` and `is_mutation` from `is_write_request`; a close abandons the pacing wait. `GET /rate_limit` is not paced (`gh_request_is_paced`, beside `gh_request_resource`). Each answer's quota, read with `RateLimit.from_http`, is charged to the resource `x-ratelimit-resource` names, or else to the paced one. The ledger is the session's own identity's: `identity_rate_limiter(token)` keeps one limiter per identity (at most `CONST_GITHUB_IDENTITY_LIMITERS_KEPT` in memory), and `get_github_rate_limiter()` is the process identity's, so `run_gh` and the session share it.
- **Retries.** `handle_rate_limit_error` retries a rate limit (`RateLimitExceeded`, a 429, a 403 with `retry-after`) up to `DEFAULT_GH_MAX_RETRIES` times. It waits what the ledger's new `retry_delay` gives, the rule `calculate_backoff_delay` now delegates to: the Retry-After, else until the quota resets, else jittered backoff from the secondary-limit floor. A 5xx is retried only for a read, from `DEFAULT_GH_SERVER_ERROR_RETRY_FLOOR_SECONDS`, because GitHub may have applied a write it failed to answer. A refused connect and a refused origin are not retried. The wait is recorded with `record_throttle`, as `run_gh` records its own. The wait and the throttle record run in a worker thread, since the ledger's lock may be held through another thread's quota refresh. A wait past `max_rate_limit_wait` raises `GitHubRateLimitError` naming the request's path and status. `_parse_retry_after_safe` is now the public `parse_retry_after`, which the classifier reads Retry-After with.
- **Test seam.** The session is faked through the repository's existing httpx2 client seam, `stub_web`'s pattern. The `github_api` fixture patches `httpx2.AsyncClient` with a class from `GitHubApiFake.client_class()`. That class keeps everything the factory passes except the transport, which becomes an `httpx2.MockTransport` over the fake. The fake's handler is wrapped in `vetted_handler`, now shared with `StubWeb` in `tests/web_fakes.py`, at the level `egress_level_of` reads from the transport the factory built. The factory, its timeouts and the session's options stay real, and every request is still vetted at the public level. `install_async_client_fake` in `tests/conftest.py` installs either fake and raises when a test asks for both, so neither silently wins. This deviates from the plan, which gave the session constructor a `transport=` argument: such an argument needs a way around egress vetting in the factory, product code used only by tests.
- **Errors.** `GitHubScopeError`, `GitHubNotFoundError` and `GitHubUnreadError` are new subclasses of `GitHubOperationError`, with `CONST_GITHUB_SCOPE_ERROR_CODE`, `CONST_GITHUB_NOT_FOUND_ERROR_CODE` and `CONST_GITHUB_UNREAD_ERROR_CODE`. `GitHubFileNotFoundError` is now a `GitHubNotFoundError`, and `GitHubUnauthenticatedError` takes an `operation`. `src/devops_cli/github/error_classifier.py` maps gidgethub's exceptions by type, status and headers: a 401, a rate limit, a 403 whose `x-accepted-oauth-scopes` the token's `x-oauth-scopes` hold none of, a 404, and a 5xx or a 3xx left unfollowed. An httpx2 error is `GitHubUnreadError`, and so is an answer that cannot be read: a body that does not decode, a charset Python does not know, a status outside `http.HTTPStatus` or quota headers that are not numbers. Any other answer is a plain `GitHubOperationError`. A `DevOpsCLIError` raised on the way, such as the origin refusal or a rate-limit refusal, passes through unchanged. Every classified error carries the request path, at most 256 characters, and an answered one its status as an int. `GitHubRateLimitError` now keeps a numeric detail as a number, as #983's amendment for PR 3 asks. The header names are constants in `config/constants.py`.
- **Callers.** `GitHubClient.get_pr_diff` is one `rest("GET", ..., accept=CONST_GITHUB_DIFF_MEDIA_TYPE)` call that raises `GitHubUnreadError` when the answer is not text. The redirect code that copied the token onto a github.com hop is gone, and so is `GitHubClient`'s unused `_token`. `_add_signing_key` takes the session, makes one `rest("POST", "/user/ssh_signing_keys", ...)` call and treats a 422 as already registered by its status.

**Pagination (PR 2).**

- **Session.** `GitHubSession.paginate(path, *, iterable_key=None)` is a lazy, synchronous iterator over a REST listing's items. Each page is one call through the portal (`RestTransport.page`, `SessionGitHubAPI.page`), made only when the consumer has read the items before it, so a consumer that stops early sends no further request. A page goes through the same pacing, ledger, retries, origin hook and classification as `rest()`, which now shares its exchange with `page()`.
- **Links.** The next page is the `rel="next"` URL gidgethub reads from each answer's `Link` header, whether it names a page number or a cursor (`after=`). A `Link` to another origin is refused by the origin hook before it is sent.
- **Fail closed (#1034).** `listed_items` takes a page's items: the page when it is a JSON array, or the array an object holds under `iterable_key` (`check_runs`, `workflow_runs`, `items`). Anything else raises `GitHubUnreadError` from `unlisted_page`, naming the endpoint, the page number and the type of what came back, never its text. That covers an HTML page, an error object, a missing body and a wrapped page without its key. A truncated page raises `GitHubUnreadError` from the classifier, which now names the page of a listing in its message and details (`FailedRequest.page`). An empty array, or a page without `rel="next"`, ends the listing. gidgethub's `getiter` is not used, since it iterates whatever a page decodes to: a string's characters, or an object's keys when its key is missing.
- **Callers.** `_fetch_issues_rest` reads `/repos/{repo}/issues` through `paginate()`, its query built with `urllib.parse.urlencode` at `DEFAULT_GH_REST_PER_PAGE`, and stops reading once `limit` issues are kept. `_resolve_milestone_number` reads `/repos/{repo}/milestones` the same way and stops at the matching title. `_parse_milestones_response` is gone. Both raise the session's typed errors where they raised a plain `GitHubOperationError` on a failed `gh api --paginate`. An answer that is no list now raises rather than reading as no issues or no milestones.

**gh failures classified once (PR 3).**

- **Table.** `src/devops_cli/config/constants.py` holds the gh-output table, matched lower-cased against what gh wrote to stderr: the one place gh's failures are classified by gh's text. `_is_branch_unprotected_error` (`github/branch_protection.py`), `create_repository_issue` (`github/issues.py`), `_report_create_failure` (`commands/pr.py`) and `extract_retry_after` (`github/rate_limiter.py`) still match gh's text of their own. `CONST_GITHUB_RATE_LIMIT_PATTERNS` and `CONST_GITHUB_SECONDARY_RATE_LIMIT_PATTERNS` lose the rows gh never writes for a failure: `abuse-rate-limit`, `retry-after` and `retry after`. `CONST_GH_UNKNOWN_OWNER_TYPE` stands alone, read by `is_gh_owner_lookup_failure` and the classifier's owner-lookup row, never by `run_gh`'s retry. `CONST_GITHUB_SCOPE_PATTERNS` is the board scope check's list without `insufficient_scopes`, GraphQL's error type, which gh rewrites as `missing required scopes`, plus gh api's scope suggestion (`this api operation needs the`). `CONST_GITHUB_UNAUTHENTICATED_PATTERNS` holds `not logged in`, `authentication required`, `http 401` and `bad credentials`. `CONST_GH_AUTH_REQUIRED_EXIT_CODE` is gh's exit status 4. `CONST_GH_HTTP_STATUS_RE` is the one regex that reads the status gh names, and replaces `CONST_GH_API_HTTP_STATUS_RE`. `CONST_GH_PROJECT_SCOPE` names the scope board sync needs.
- **Classifier.** `classify_gh_failure(output, *, exit_code, operation)` in `src/devops_cli/github/error_classifier.py` returns `GitHubUnauthenticatedError` for exit status 4. Otherwise it returns, by the table, `GitHubRateLimitError` for a rate limit or for an owner lookup gh dropped the cause of, `GitHubScopeError` or `GitHubUnauthenticatedError`; or None when neither names one, so the caller reports the failure as its own. `output` is gh's stderr. gh writes every failure there, and its stdout holds GitHub's answer, which for a failed GraphQL read may carry partial data such as item titles, so stdout is never classified. Each error carries gh's exit status and the HTTP status gh named, both as ints, the operation, and gh's stderr on one line, at most 256 characters. `is_gh_rate_limited`, `is_gh_owner_lookup_failure`, `gh_http_status` and `gh_failure_details` read the same table. `parse_retry_after` moves into this module from `rate_limiter.py`, which now imports the classifier.
- **Callers.** `GitHubRateLimiter.is_rate_limit_error` is `is_gh_rate_limited`. `run_gh`'s retry decides on gh's stderr, and its wait still reads stdout for the Retry-After header `gh api -i` prints there. `check_github_rate_limit_error` is gone. `verify_project_auth_scopes` raises the classified error, and for a missing scope asks for the `project` scope board sync needs, which includes read:project. It asks for the scopes on `GitHubScopeError`, and otherwise raises gh's text with GitHub's reasons from the classified error. The store's file and REST reads and `devops pr`'s task-directory read find a 404 with `gh_http_status`. `devops gh views sync` prints a failure as gh wrote it, so `[read:project]` is not read as markup. `apply_intake` stops a round on a refused token as on a rate limit.

Any other failure, a run past `DEFAULT_GH_QUOTA_REFRESH_TIMEOUT_SECONDS` (10 s) or an empty answer raises `GitHubUnreadError`, where every one of them raised `GitHubRateLimitError` before, and the timeout escaped as a raw `TimeoutExpired`. **The roadmap store's REST listings on the session (PR 5).**

- **Store.** `GitHubRoadmapStore` takes the session beside its runner (`session=`, a `ListingSession`: anything with `paginate`), and reads through the process's session when given none. Its ten REST listings (milestones, issues, the repository's issue events, an issue's events, comments and blocked-by dependencies, pull requests by update and into a base, a pull request's files, and GitHub Releases) are `session.paginate()` reads of `listing_path(endpoint, per_page)`, each entry validated as it comes. `_read_listing`, `listing_page_args` and the store's own page cap are gone; the session follows `Link: rel="next"`, raises on a failed page, a page that holds no list and a listing past `DEFAULT_GH_MAX_PAGINATED_PAGES`, and the list adapters became entry adapters. The store's gh commands keep the runner.
- **Early stop.** A listing read newest first stops at its first entry older than the cutoff, and the session requests no later page. The issue events and the pull requests are ordered by the time they are cut on, so that loses nothing. The GitHub Releases are ordered by their tags' times but judged by when each was published, so that read (`to_page_end`) goes on to the end of the page it stops in, which GitHub has already sent since it fills every page but the last: a Release for an older tag published after the cutoff, listed below one created before it, is still a ship, as #1360 read it, with no request more.
- **Plan.** `roadmap/request_plan.py` plans a listing as the session's read: `planned_session_read` gives `REST read` with the argv `GET https://api.github.com/<path>`, repeated per page while GitHub links a next one (`MESSAGES.roadmap.plan_repeat_page`). The `<n>` page placeholder and `intake_repeat_page`, which nothing planned any more, are gone.
- **Owner lookup.** A command with no `@me` fallback, the store's `--owner <login>` commands (`_failure`) and `github/projects.py`'s board reads (`_read_failure`), asks GraphQL for its own budget when gh project writes `unknown owner type`, through one helper, `owner_lookup_failure` in `src/devops_cli/github/owner_lookup.py`. GraphQL's own `rateLimit` is the source the project trusts since #1125, where `gh api rate_limit` reported 4,899 points while GraphQL said 17; the read costs about one GraphQL point, where the amendment had expected none. A budget at or above `DEFAULT_GH_GRAPHQL_BUDGET_FLOOR` makes a plain `GitHubOperationError` naming the points left and the causes still possible, a secondary limit among them. A budget below the floor, or a budget read refused for a rate limit or unread, keeps PR 3's rate limit, so an intake round still stops; a budget read GitHub refuses the token for is the unauthenticated error naming the failed command.
- **Signing key.** `_add_signing_key` confirms a 422 against `session.paginate("/user/ssh_signing_keys")`, as PR 3's gh path confirms its own: a listed key, or a listing that can't be read, is registered, and otherwise the 422 raises. `_key_body` and `_listed_key_bodies` are shared by both paths. `register_key_on_github` turns any refusal on the session path into `SSHRegistrationError`, as the gh path raises, so `devops ssh register` reports it and `rotate` removes the key it generated.
- **Spend.** `devops roadmap intake --plan`'s spend line counts the requests the identity's ledger paces from the start of the run, by resource (`GitHubRateLimiter.requests_paced`): every gh command through `run_gh` and every request the session sends waits its turn in `acquire`, each attempt once, so the listings now read through the session are counted again, and so is each retry. `SpendMeter` no longer wraps the runner.
- **Rate-limit reads.** `run_gh` parses a `gh api rate_limit` answer only when gh succeeded; a failed one, with GitHub's error body on stdout, comes back as the failed process, as `_refresh_from_github` reads it, instead of raising about the body.
- **Connect timeout.** `session_client` passes the factory `request_timeout(connect=DEFAULT_GH_SESSION_CONNECT_TIMEOUT_SECONDS)`, 10 s, and keeps its read timeout; the factory is unchanged. Its own 1 s connect timeout suits the local services it was written for, but api.github.com is reached over the public internet, where a lost SYN is resent after 1, 2 and 4 s: on 2026-10-19 two `devops pr monitor` check-runs reads and one `devops roadmap intake --plan` failed with `ConnectTimeout` and succeeded seconds later, where gh's dialer, which read them before PR 4, allows 30 s. A connect that still fails is not retried.
- **Docstrings.** The store's module docstring and the listing's own describe the session's paging; the justification by `run_gh`'s `api --paginate`, gone since PR 4, is removed.

**Conditional requests (PR 6).**

- **Dependency.** `cachetools==7.1.8` is declared in `pyproject.toml`; `uv.lock` held it only through `py-key-value-aio` and now lists it as the project's own.
- **Store.** `SessionGitHubAPI` passes gidgethub's `cache=` a `cachetools.LRUCache` of `DEFAULT_GH_SESSION_ETAG_CACHE_SIZE` (64) answers that it builds itself, so each session's transport holds its own in memory, one identity's ETags are never sent as another's, and closing the session drops them. gidgethub stores a GET's answer with its ETag and sends the next GET of that URL with `If-None-Match`; a 304 gives back the stored answer and next link. A write's answer is never stored.
- **Ledger.** Every attempt, a 304 too, goes through `_request`, so it is paced and charged, and the ledger takes the `x-ratelimit-remaining` the 304 reports, which GitHub leaves unspent. A retry sends the same `If-None-Match`, and the origin hook vets every attempt and hop as before.
- **Pages.** A stored page still goes through `listed_items`, so a stored error object fails closed again. GitHub's ETag covers a page's body only and its 304 carries no `Link`, so a full last page that gains a next page keeps its ETag, and its 304 would end the listing short. `SessionGitHubAPI._forget_last_page` therefore drops the stored answer of a page that linked no next page before that page is read. A page that links a next one still answers 304: a poll's issue events, pull requests and Releases, read newest first, stop on their first page, which links the next.
- **Copies.** Each GET's answer is a `copy.deepcopy` of what gidgethub stored, so a caller that changes an answer never changes what a later 304 gives back.
- **Fake.** `GitHubApiFake` answers a request whose `If-None-Match` names the ETag of the response it would get with a 304: that response's headers, without its body or `Link`.

## Risks and Notes

- gidgethub sends `Authorization: token <token>`, where the old diff and signing-key code sent `Bearer`; GitHub accepts both for a personal access token or an OAuth token.
- A redirect to github.com is now refused. The old diff code followed one and copied the token onto it; nothing else in `src` sends the token to another GitHub host.
- A 5xx is retried for reads only. The plan says a 5xx is retried; a write is excluded because GitHub may have applied it, and `run_gh`, whose rules the retries follow, never retried a 5xx at all.
- The portal's thread is a daemon thread, but that alone does not let a process exit: the portal context's own exit needs the thread to run. A transport left open is therefore closed by its finalizer at interpreter exit, while the thread still runs.
- `get_pr_diff` now raises `GitHubUnreadError` for an empty body, since gidgethub decodes an empty body as None. An empty diff would need a pull request with no change against its base.
- The egress factory is unchanged: `git diff origin/release/v0.2.37 -- src/devops_cli/http/` prints nothing. #1314 later moves the session's client construction behind one HTTP seam.
- `_fetch_issues_rest` and `_resolve_milestone_number` now fail closed. An answer that is not JSON, or an object where a list belongs, raises `GitHubUnreadError`; before, the issue read returned no issues and the milestone read reported the title as not found.
- PR 4: the reconcile listings lost `run_gh`'s 60 s response cache, which was kept on disk and so served a later CLI run. Each `devops gh project reconcile` or `sync` run now reads every listing page, one core request per 100 items, so `--plan` followed by a write run reads each listing twice. Reconcile runs from the CLI and the MCP server, never on a Service tick. PR 6's ETag cache lives in memory, one per session, so it serves repeat reads within one process (the MCP server), not separate CLI runs.
- PR 4: `devops gh api --paginate` is one gh process that follows every `Link` page at 100 items a page. It is paced as one request though gh sends one per page, the whole walk runs under `DEFAULT_GH_API_PAGINATE_TIMEOUT_SECONDS` where each page had 30 s before, and a rate-limited walk is retried from page 1 where the old page path did not retry.
- PR 3: `unknown owner type` is no rate-limit row, so `run_gh` never backs off on it and `_run_project_cli` resends the command as `--owner @me` at once. gh project writes it for any failed owner lookup that is not a not-found (a 401, a 403, a 5xx, a network error or a rate limit) and drops the cause. Where no `@me` fallback recovers it, it is classified as a rate limit, as the board lookup read it before, so intake still stops a round on it; from PR 5 those commands, the store's `--owner <login>` commands and the board reads in `src/devops_cli/github/projects.py`, ask GraphQL for its budget first and keep the rate limit only when it is spent, refused for a rate limit or unread.
- PR 3: the board lookup through `gh project list` raises a missing scope, a refused token or a rate limit, where it returned no board for the first two. `verify_project_auth_scopes` asks for the `project` scope board sync needs (`gh auth refresh -s project`, which includes read:project), with gh's own words in the message and details.
- PR 3: a failed quota refresh raises the class the gh classifier names, so a refused token or a rate limit at the refresh stops an intake round after one refresh, as a refused write does; `apply_intake` stops on `GitHubUnauthenticatedError` as on `GitHubRateLimitError`. Any other failed refresh is `GitHubUnreadError`, which skips the candidate, as an outage may pass before the next. The plan said any failed refresh other than a 401 is `GitHubUnreadError`; a rate-limited refresh raising `GitHubRateLimitError` instead is an owner-approved change of 2026-10-18.
- PR 3: `_gh_add_key` no longer reads gh's text for an existing key. On a 422 it lists the keys again: a listed key, or a listing that can't be read, is registered, and a listing read without the key raises gh's text with GitHub's reason, such as `key is invalid` or `key is already in use` on another account. PR 5 confirms the session path's 422 against the session's signing-key listing the same way.
- PR 5: `devops roadmap intake --plan`'s spend line now counts each attempt, so a retried request counts twice, where it counted gh commands once; it counts every request the process's identity paces during the run, which in one CLI process is the run's own.
- PR 5: the issue events and pull requests a poll reads stop at their first older entry, where they read on to the end of that page; both are ordered by the time they are cut on, so nothing is lost. A GitHub Release, ordered by its tag's time, is still judged to the end of its page; one for an older tag published after the cutoff and listed on a later page is not reported by that poll, as before #983, and the stall check and the `release published` hint cover it.
- PR 6: a page that links no next one, the last page of every listing and the only page of a short one, is read in full every time, so a one-page listing, such as a pull request's reviews or an issue's comments, gains nothing from the store. A poll's listings link a next page and answer 304.
- PR 6: a 304 still waits its turn on the ledger and counts in `requests_paced`, so `devops roadmap intake --plan`'s spend line counts it, though GitHub does not charge it.
- PR 6: each GET's answer is deep-copied on the portal's loop, where it was decoded; a 100-item page of pull requests, about 2 MB, is copied once per read. A session holds at most 64 answers, each at most a page of `DEFAULT_GH_REST_PER_PAGE` items, until it closes.
