## Description
A release's scope is fixed when it starts (CONTEXT.md), and no code enforced that. `devops roadmap reprioritize` (`src/devops_cli/roadmap/reprioritize.py`, in #739's `roadmap` group) holds the current release to its admission rule, size and stall window, and starts each release when the one before it ships. It writes GitHub state only with `--confirm`, never a commit (ADR 0001), and comments a one-line reason on every item it moves, readies, admits or nudges. It never sets Priority, Value or Effort, never closes or merges a pull request, and its only branch write creates a missing `release/vX.Y.Z`.

- **One table.** `TRANSITIONS` maps a release state (`ReleaseState`: planned, started, cut, shipped) and an `Event` to a `Transition` (an `Action` and a `Reason`). A cut release inherits the started release's rows (`INHERITS`) except the cut lock, which is one row: `(CUT, FIX_JOINED) -> TO_NEXT`. The reasons' texts are `MESSAGES.roadmap.reasons`.
- **The interface #742 builds on**, documented in the module docstring: `current_release(releases)` (the open Release with the lowest version, compared as versions), `release_state(store, release, default_branch)`, `admission_event(item)` and `decide(state, event)`. Intake asks the same table what an item joining the current release meets. `is_critical_fix`, `is_p0_feature`, `placed_by_person` and `admitted_to` are public too.
- **Release state.** An open pull request into the default branch with the `release` label and the release's milestone cuts it, draft or not (`is_release_pull_request` in `store.py`, which #743 shares, since its head is `chore/release-vX.Y.Z`). A merged one keeps it cut until GitHub Release vX.Y.Z is published, which ships it: the code is in `main` already, so a fix filed then goes to the next release even if `release.yml` fails to publish.
- **The run record** is the job record of one draft card on the board, the run record card (`CONST_ROADMAP_RUN_RECORD_TITLE`, "Roadmap run record"), read and written through `RoadmapStore.run_record` and `set_run_record` in both adapters, beside the last-set record #768 keeps on each card, as the issue's Store bullet asks. Its `Started` mark names the release the job last started, or recorded at its first run, and its `Size` mark that release's size then. No `Admitted` mark decides whether a run is the first or which release last started, so a release whose admitted items were all descoped or moved out, a release that started or was first recorded empty, and a run that stopped part-way never make the job start a release again. The GitHub adapter creates the card on its first write (`project item-create`) and finds it by its title. With no run record while items carry the job's marks, the job has run before and the card is gone (deleted, archived, converted or renamed), so `plan_reprioritization` refuses with a `ConfigurationError` that names the "Roadmap run record" card and the marked items, where it used to take the run for a first run and admit everything added since the start; a run record naming a milestone the repository no longer has is refused the same way. A card whose record has no `Started` mark that is a milestone number, such as a title typed in by hand or an older version's value, gets its own refusal (fourth fix round, `reprioritize_record_unreadable`): it says the card is on the board and its record can't be read, shows the mark, and gives the current release's milestone number to set, where it used to say the card was missing.
- **Releases by milestone number.** Every mark that names a Release (`Started`, `Admitted`, `Left`) holds its milestone number, which GitHub keeps when a person renames the milestone, so a renamed current release is the same release: it is not started again, its admitted items stay admitted, and the plan, the report and every comment use its title as it is now. The plan holds titles and `apply_reprioritization` writes numbers, taking those of Releases the run creates from `create_release`. `is_own_change` counts an item leaving a Release while it carries any `Admitted` mark as a person's change, since a change names the Release by title; an item leaving another Release with a mark left over only makes a run due that finds nothing to do. The in-memory adapter now shows a renamed milestone's new title on its issues and pull requests, as GitHub does. The job record's own `Release` values stay titles (#768's last-set record): after a rename the job reads an item a job placed in a renamed release as a person's, so a start pulls fewer items, never more.
- **The admitted set** lives in the job record of each card. An admitted item carries the release's milestone number as its `Admitted` mark (`JobMark`). An item in the current release without the mark joined after the start, so a missed poll or a late run still finds it. A first run and a start admit the release's closed items too, so one reopened there never joined it; the size still counts open items only. Both also clear the mark of an item no longer in the release, which a first run or a start that stopped after its marks left behind. Every run clears the mark of an admitted item that left the release, open or closed, and records its `Left` mark (fourth fix round: closed items were left out), so a closed item a person takes out, puts back and reopens is judged as a join. With no run record, a run is the first: it records the admitted set of the release under way and moves nothing.
- **Starts.** Once the release the run record names is closed (`release.yml` closes the milestone after it publishes the release), the current release is newer than it, and it starts, but only once the release before it has shipped (`_unshipped_before`): a milestone closed by hand starts nothing, and the plan says which release has not shipped. A shipped release whose milestone is still open is closed last, and so is each open release right after it that has shipped too (`_shipped_after`, eleventh fix round, seed 15007): a person who cut and shipped the next release while no run had started it, as while a run that would have stopped and waited, leaves it shipped and never started, so the run starts the first release after the shipped ones, or a first run records it, and closes every shipped milestone last, the current one first. It used to start the shipped release: it pulled backlog items into it, admitted them there and closed only the release before it, and the next run closed the shipped one with those items inside. When the run record already names a release newer than every shipped one, a start, or a first run at a ship, stopped at those closes, its last writes: the next run holds the release the run record names to the rules as the current release, in its own state, and closes the shipped milestones last (`_plan_close` with `_under_way`, seventh fix round), so an item a person added to the started release in between is judged by that run, not left until a later run is due; when that release is closed, the closes are all that run does. When the release the run record names has shipped too since, as when a person cut and shipped it while that run waited to close the one before it, the run starts the release after it and closes the shipped milestones still open (eleventh fix round; it used to close only the release before it, and the start waited for a later run). That holds when `release.yml` has closed the milestone of the release the run record names, too (`_shipped_since`, twelfth fix round, the reviewers' findings 0 and 7): a closed milestone is not among the open shipped releases, so the run used to close only the release before it, and a P2 feature a person placed in the unstarted release meanwhile was admitted by the late start, with no comment; the same when a person reopened the shipped milestone before it. A release a person cut before any run started it, as when no run finishes between one ship and the next cut, is topped up with nothing at its start (`_is_cut` in `_fill_or_trim`, twelfth fix round): nothing joins a cut release. Its start used to pull Ready items in past the cut lock, and once it shipped they sat Ready in its closed milestone, where no later start looks. A start creates the planned milestones up to `planning_horizon` (patch bumps of the highest), creates `release/vX.Y.Z` at the default branch's head unless it exists, sends New items to the backlog (a critical fix stays), sends a Blocked critical fix to the next planned release and any other Blocked item to the backlog, then fills the release to the cap from Ready items in the backlog and the later planned release that no person placed (critical fixes, P0 features, then Priority, Value and number), or trims it to the cap into the later release (lowest Priority, lowest Value, highest number; a critical fix or a P0 feature only when nothing else is left), and records its admitted set and size. The top-up comment gives the size the release reached.
- **First run.** A first run never starts a release, as the issue says: it records the release under way and moves nothing. That is the current release, or, when the current release has shipped with its milestone still open, the first release after it that has not shipped, which started at the last ship; every shipped milestone is closed last. So a first run right after a ship records the same release whether `release.yml` closed the milestone or not, and its Blocked items are judged by the next run's descoping rules.
- **The commit point.** Every write of a start or a first run comes before its run record's `Size`, but the close of a shipped milestone, which comes last. A run that stops part-way leaves the run record without the new size, so the next run starts or records the same release again, finishing what the first began. A start writes the run record last, not first, on purpose: written first, it would make the next run hold the half-started release to its admission rule and send away the items the start had not yet marked, which is the reviewers' second blocker. A first run names its release in the run record first and gives the size last: a run record without a size is a first run that stopped part-way, which the next run does again, so the refusal above never mistakes one for a missing card. A run that stops at the close itself has made every other write, so the run after it is a run of its own, which holds the release to the rules: after a first run at a ship, it descopes an item that was Blocked already.
- **Older than the started release.** A current release older than the one the run record names, such as a hotfix milestone opened after v0.2.25 started, never started and has no admitted set: the job holds it to no rule and moves nothing (`ReprioritizationPlan.behind`, with a headline saying so), and no move ever targets the started release from it. When it ships, its milestone is closed as before.
- **Each change is finished once, if it still holds.** A change to an item writes its `Pending` mark first (the decision with its Releases by milestone number, its comment, the number of comments with that text the item already has, and the item's Release, Status and last status change as it found them), then its fields (the Release before the Status), then its reason comment, then one job-record write that sets its `Admitted` or `Nudged` mark and clears `Pending`. A run that finds a `Pending` mark judges the change again first. Once its comment is posted, only its marks are left. Values alone can't tell the job's write from a person's (fourth fix round), and on GitHub a field write is two calls, the job record first, then the milestone or the board field, either of which can fail (fifth fix round). So the mark records each field as begun (`_Pending.begun`) in the job-record write that records its value (`set_field(..., marks=...)`), before the field call, and as written (`_Pending.written`) in a job-record write made once the field call has returned. When the change begins, it also records what the job record held for the fields it writes (`_Pending.recorded`) and how many times the issue had joined or left a Release (`_Pending.moves`, from `release_changes`), beside `status_at`. A written field that holds the change's value is the job's until it changes since (twelfth fix round, the reviewers' finding 10): the written mark keeps the issue's Release event count as the job's write leaves it, a leave and a join counted rather than read after the write, which the events may lag (`_Pending.written_moves`), or the Status's clock read once the write has returned (`_Pending.written_status_at`). So a field a person set away and back, or set to the change's value once a dropped change's revert had put it back and stopped before clearing the mark, is the person's; the run used to take it for the job's, and moved the item out of the planned release a person had placed it in, or took the Status clock from before the change and readied and descoped an item a person had just worked on. The count starts when the Release write begins: a Release the change has not begun takes the issue's count as the rerun reads it, since a person may have moved the item out and back since the change began; counted from then, the job's own write read as changed since, and the next run dropped the job's move, uncommented (found while fixing this: the finding's fix as written fails `test_a_release_write_after_a_person_moved_the_item_out_and_back_is_the_jobs`, which passes on the eleventh round's code). A field begun and not written is read again (`_changed_since`): while the issue's Release events still number `moves`, or its Status's `updatedAt` still equals `status_at`, the field call never landed, and the field is neither the job's nor a person's: the change is finished, or judged again, as the job's, and when it is dropped its job record goes back to what it held, so no `Left` mark names a Release the item never reached. When the field changed and holds the change's value, the call may have landed and reported a failure, or the written mark may have failed, or a person may have set that very value; no read tells these apart, so the field is unproven. It is never put back, written or recorded as the job's, and the change, which has happened at least in part, is finished as it stands, with its comment and without being judged again, leaving any field a person set since as it is. Its job record is dropped (sixth fix round; the fifth put back what it held when the change began), so its place counts as a person's, as for an item no job placed: an item a job sent to the backlog in that window is not pulled back in by a later start, which reads its issue's events, and when the job moves an item it had placed itself (one a top-up pulled in, or an earlier descope sent on), the record of that earlier place no longer makes the next run read the job's own move as a person taking the item out of it, with a `Left` mark. A move out of the release clears the item's `Admitted` mark in its last write, except one never announced whose Release a person set back to that release since (eighth fix round, seed 1021): the item stays admitted, as one whose exit no run saw, where it used to lose its mark and go to the backlog by the admission rule. The rerun that posts such a change's comment first records that the move was undone in its `Pending` mark (`_Pending.stays`, one write on that path only), so a run that finds the comment posted keeps the mark too while the item is still in the release (twelfth fix round, the reviewers' finding 9: a rerun that stopped after the comment left the next run clearing the mark, and the admission rule sent the item to the backlog, so the outcome turned on one failed write). Any other field the change writes that has changed since is a person's, even one set to the very value the change was going to write, or set back to what it held before. When a person has set one and no field is unproven, the person's change stands: the run puts back only the written fields that hold the job's values, puts back the record of the begun ones that have not changed since, drops the record of the begun ones a person has set since, and drops the change, and a person's Status keeps its own clock. The record of a begun Release a person has set since is put back instead when the issue's events since the change began show no join of the change's target, by its title now or when the change began (`_never_joined`, `Decision.unlanded`, `_Pending.target_title`; tenth fix round): the change's milestone call never landed, so every move since is a person's, and the record still names the job's last placement, so an item a person moved out and back while the rerun waited is still where a job placed it, as the module's Edges say. A move to the backlog, which no join shows, and one whose target a person has moved the item into since, keep the ninth round's rule. One helper, `_taken_back`, gives the begun fields their record on both paths, a dropped change's and a finished one's, and gives an unlanded Release its record from before the change on both. Dropping the record of a begun field a person set is the ninth fix round's (seed 6031): the eighth put back what the record held when the change began, which could name the place a job last put the item in, so a person who moved the item back there read as that job, and the same run's start pulled the item in again, with a second comment; a run that stopped one write later, after the written mark, left it where the person put it. The ninth round dropped that record even when the milestone call never landed, the opposite error: a top-up that stopped at its milestone call left an item a person moved out of the backlog and back out of the start, as the person's placement, while one that stopped a write earlier, at its job record, pulled it in (tenth fix round). No write leaves a field the job changed without a record of it. Otherwise a change about the release this run judges (the current release in a rules run, the starting one in a start) is decided afresh with the item as it was before the change began, its Status clock as the change found it when the change began its Status write, since the job's own Status write is no activity; a change that never began its Status write leaves the item's Status clock as it is, since every change to it since is a person's, even one that left the Status as the change found it (tenth fix round, seed 10129: a person who set a stalled item In Progress again, or moved it into review and back, while the rerun of its descope waited, had it descoped all the same); the run finishes it only when it decides the same again, else puts the item back and applies the new decision. A Status the change never began counts as a person's once its clock has changed since the change began, even back to what the change found (`_changed_since` in `_resumed`, eleventh fix round): the job writes the Status only once it has recorded it as begun, so every change to its clock since is a person's. The tenth round's fix covered only the path that judges the change again; on the paths that finish it as it stands, an unproven Release (its milestone call landed and reported a failure, or its written mark failed) or a change about another release, the rerun still wrote Ready over a person who had set the item In Progress again, or moved it into review and back. Now the first finishes the move and leaves the person's Status as it is, and the second gives way to the person's edit. A Release the change never began keeps the documented out-and-back edge: a person who moved the item out and back leaves it where a job placed it. A change about another release, such as one that shipped since, is finished, and the item is then judged like any other, so a start clears a Blocked item an interrupted descope moved into it. Once the release such a change moves the item to has shipped too, cut and shipped while the run waited, the item stays in it when the start closes it, as any open item a release shipped with: the job moves no item out of a shipped release (an edge the module now documents, eleventh fix round). A start's pull-in whose milestone call never landed (no comment posted, no Release written or unproven), about a release that has shipped since, is dropped instead (`_pulled_into_shipped`, twelfth fix round, the reviewers' finding 8): the item was never in that release when it shipped, and the start that runs now judges it as one of its own candidates. It used to be moved into the shipped release, a closed milestone when `release.yml` had closed it, and admitted there. The plan lists a dropped change with what it was to do. Admissions come after every other change; an item's changes keep their order, an earlier run's first.
- **The rules after a start**, in one run: admission (only a critical fix joins; a P0 feature goes to the next planned release, anything else to the backlog; while cut, a fix goes to the next planned release too), then descoping of unstarted items (Blocked, an open blocked-by link outside the release, `needs-split`, the last item not done) and the stall window (an In Progress item idle for 14 days goes back to Ready and is descoped, a critical fix goes back to Ready and stays, an idle In Review item gets one nudge per window, kept as its `Nudged` mark), then the cap (each admitted fix that takes the release over 12 descopes the lowest-ranked unstarted item that is not a fix; if there is none, the fix joins anyway). An admitted critical fix is descoped only when it is Blocked. A fix that joins already stalled, or idle in review, gets the stall rule's decision, and that change admits it (`Decision.admits`, kept in its `Pending` mark and set by its last write, eighth fix round): the admission used to be a mark the run wrote after every change, so a run that stopped part-way through the change left the fix unadmitted, and the rerun admitted it again with a second comment or, once a person had made it P1 after the stall comment said it stays, sent it to the backlog. The change's last write admits it once its comment is posted, or while it is still a critical fix, and such a change comes after every other, as an admission does, so the item a cap makes room with still leaves first. Activity is the latest of the Status value's last change and the last update and last commit of the open pull requests that close the item, found with #704's `extract_linked_issues`.
- **A person's placement** is a Release, or the backlog, that differs from the last one a job set, or the one a job set when a person has moved the item since (its `Left` mark). An item no job placed is a person's in a Release, and in the backlog once a person took it out of one (CONTEXT.md: a person's placement stands); one never in a Release is unplaced. A start reads the issue events (`release_changes`) of each Ready backlog item no job placed, and records the Release a person took it out of as its `Left` mark, the way `Left` works for items a job placed, so the item stays in the backlog and later starts need not read its events again. This narrows the issue's line "unplaced in the backlog" to items no one has moved since they were filed; the owner may want to confirm it.
- **`Left` mark (beyond the issue).** Putting an item back where a job last placed or admitted it sets the value the job last set, so by value alone it reads as the job's own change. The job records, in the item's job record, where a person took the item out of since a job last placed it (`JobMark.LEFT`): the current release it was admitted to (and its `Admitted` mark is cleared), an open release a job last placed it in, or the backlog where a job last placed it (`CONST_ROADMAP_LEFT_BACKLOG`); a release by its milestone number. A job that places the item clears the mark, also when its milestone call landed unconfirmed: `_final_marks` counts the move as `_moved` does, by the fields a person set since, so a move a person may have made too clears the mark like a confirmed one (seventh fix round). While it is set, `is_own_change` treats a return to the job's placement as a person's change, and `placed_by_person` counts the item's place as a person's, so a feature the admission rule sent to the backlog, which a person placed in a planned release and moved back, is not pulled in at the next start. Likewise an item leaving the release whose admitted set it is in is never the job's own change unless the job cleared its `Admitted` mark, so the run that clears the mark is due even when the item goes back to where a job last placed it. The plan reports these marks under "Admitted set"; they change no field and carry no comment.
- **`is_due(changes, now, last_stall_check)`** is pure, for #741 and #752. It is true for a release start, cut, un-cut or ship; for an item joining or leaving a release, closing or reopening, or changing Status, Priority, labels or blocked-by links; and once `now` is a day past `last_stall_check` (or there is none). Comments, edits, Value and Effort changes and the job's own changes are not triggers. With no state to read, a change to an item in any release counts, and a run that finds nothing writes nothing.
- **Store additions**, in `RoadmapStore` and both adapters: `set_field` takes `marks` to set in the job-record write that records the value, and the GitHub adapter now makes that write before it sets the field (#768 set the field first); `set_marks` (several marks in one write; since the fifth fix round it also takes `recorded` and `forgotten`, which set or drop the value the job record holds for a field in the same write without setting the field, so a job takes back the record of a field write it began and can't show it made), `run_record` and `set_run_record`, `release_changes` (an issue's own milestone events), `comments_on`, `dependencies` (REST `issues/{n}/dependencies/blocked_by`), `status_changed_at` (the Status value's `updatedAt` in GraphQL, since board 2's timelines hold no status-change events), `open_pull_requests` and `release_pull_requests` (GraphQL, with the last commit's date), `release_published` (REST release by tag; a draft or a 404 is unpublished), `default_branch` (GraphQL), `branch` (REST `git/ref/heads/{name}`, a 404 is None), `create_branch` (REST `git/refs`) and `comment`. `close_issue` comments through `comment`. `ChangeKind` gains the kinds a poll finds by comparison (field changes, blocked-by links, comments, edits, and the four release kinds, `RELEASE_CHANGE_KINDS`). A change carries the field it set, that field's value when read and the Item's job record when read, in both adapters, so it compares with the record; the GitHub adapter reads the board once per `changes_since`. The four GraphQL queries were checked read-only against dan-petty/devops-cli on 2026-10-02 and match the recorded payloads under `tests/fixtures/roadmap/`. The GitHub adapter reads each REST listing a full page at a time (fourth fix round), and a page that is not a JSON list raises, naming the read and the page, before the plan makes any write: `run_gh`'s own paging (`api --paginate`) ended a listing at a page that was empty or not JSON, so a proxy's error page read as an empty or short listing, and a first run could record its release as holding no items.
- **Readiness.** `_GROUNDING_CHECKS` (`commands/pr.py`) gains `_closes_an_item_of_its_release`: a PR into `release/vX.Y.Z` is blocked when the one issue it closes is not in release vX.Y.Z, naming the issue and its release, or saying it is in the backlog. The issue's Release is read with one `gh api repos/{owner}/{repo}/issues/{n}` only for a PR into a release branch that closes exactly one issue; a failed read is one blocker of its own. #933's exemptions (the release PR, `chore/(open|cut)-vX.Y.Z`) and one blocker per cause hold.
- **`Part N of #M`.** The issue's readiness criterion still names an item with `Part 1 of #N`. #704 dropped those lines: a PR closes exactly one issue, so this check judges that one closed issue. A body that only says `Part 1 of #N` closes nothing and gets #704's one blocker, and the release check reads no issue for it (`test_a_part_of_an_item_line_names_no_item_so_only_the_one_issue_rule_blocks_it`).
- **CLI, MCP, labels, docs.** `devops roadmap reprioritize [--repo] [--ref] [--dry-run] [--confirm]` prints the plan (current release, release and branch writes, each change with its reason, the admitted-set records) and writes only with `--confirm`. The MCP tool `roadmap_reprioritize(repo, ref, dry_run=True)` passes `--confirm` only for `dry_run=False`. `.github/labels.yml` declares `needs-split`. The help strings, messages, the GitHub project-management knowledge-base page and the generated docs (`README.md` matrix, `docs/CLI_REFERENCE.md`, `docs/MCP_TOOLS.md`, `docs/commands/roadmap.md`, `pr.md`, `gh.md`) follow.
- **The size binds from the start.** Each fix a run admits that takes the release over its cap descopes one unstarted item that is not a critical fix. Beyond that, while the release holds more than the larger of its cap and its size at start (the run record's `Size`), its lowest-ranked unstarted items that are not critical fixes are descoped (`Event.OVER_SIZE`), so an item a person moves back to Ready after a fix filled a release of started items makes room.
- **Migrated boards only.** `plan_reprioritization` refuses, with a `ConfigurationError` that names `devops roadmap migrate` and what is left, a board whose Status field has no New or Blocked option, still has an option migrate merges into New (`CONST_ROADMAP_PREMIGRATE_STATUSES`: Backlog and Todo, the template's `replaces`), or still holds an open `type/epic` Item. On board 2 as it is today (Todo, Backlog, Ready, In Progress, In Review, Done), the rules can't tell an unready or Blocked item; once a person has made migrate's option edits (Backlog renamed to New, Blocked added) and before `migrate --confirm`, Todo is still there and epic #300 is still an Item of v0.2.25, which a first run would count in the release's size at start.
- **Job records the store can't read.** The GitHub adapter reads the keys of a job record it knows and leaves out the others, such as one a newer version writes (#744's planned `needs_split`), and every write keeps those other keys. A record that is not a JSON object, or gives a known key a value that is not text, fails the read and names the card, so the planner stops before any write; #768 read such a record as empty, which made an admitted item look newly added.
- **Edges, documented in the module.** A condition already present at the first run, such as an item already Blocked, is judged by the next run's descoping rules: the first run's promise covers admission. An admitted item a person takes out and puts back before any run sees it out, or while a run that saw it stopped before recording it, is still admitted: the job reads state, not the change feed, as any poll-based design does (ADR 0003). The same holds for a placement (eighth fix round, seed 746): an item a person takes out of where a job last placed it, such as the backlog the cut lock sent it to, and puts back before any run records it out has no `Left` mark, so it is still the job's placement, and a start may pull it in. The same holds when the person's moves come while the rerun of a change that began to move the item waits, unless nothing shows that change's milestone call never landed (tenth fix round): its record from before is put back when the issue's events show no join of its target, and dropped otherwise, as above. The start reads the issue events only of backlog items no job placed; the machine counts such an item as placed by whoever placed it before (`unseen_moves`), as it already did for the admitted set (`unseen_exits`).
