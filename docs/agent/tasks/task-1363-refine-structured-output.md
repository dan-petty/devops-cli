# Task: Refine sends the model the proposal schema and never caches a reply that fails it, and one failed item skips only that item (#1363)

**Issue**: [#1363](https://github.com/dan-petty/devops-cli/issues/1363)
**Status**: Done
**Milestone**: v0.2.29
**Priority**: priority/p1-high
**Scope**: type/bug, scope/ai, scope/github

## Description

`devops roadmap refine` had never written a proposal: 145 of 147 refine rounds in the roadmap service failed with `StructuredOutputValidationError`. Neither refine prompt asked for JSON or named a field, so the model answered with a Markdown document; `chat_structured`'s first attempt cached that document with no validator and replayed it to later rounds; and the first failed item stopped the whole job, discarding the proposals already made.

**The model is told the schema.** `chat_structured` appends the instruction in `src/devops_cli/ai/tasks/structured_output_schema.md` and `json.dumps(schema.model_json_schema())` to the caller's system message, for every caller (intake, refine's research plan and refine's proposal). The schema also travels to the wire through a `reply_schema` `ContextVar` set by `constrain_reply` (`ai/client/network.py`), modelled on `completion_cap` / `limit_completion_tokens`: the `gateway` provider's compat payload carries `response_format: {"type": "json_schema", "json_schema": {"name": <class name>, "schema": <schema>}}` with no `strict` key (LiteLLM maps it to an Ollama deployment's `format` and drops it where unsupported, `drop_params: true`), and the `ollama` provider's payload carries `format: <schema>`. The `openai`, `copilot` and `claude` payloads are unchanged; they rely on the schema in the prompt (#595 owns per-deployment capability probes).

**The cache keeps only replies that validate.** Each attempt passes the schema check (`_repair_and_validate_payload(text, schema)`) to `chat_messages` as its `validator`, so `_check_chat_cache` never serves a cached reply that fails it and `_retry_chat_dispatch` never writes one. A validator rejection raises `ReplyRejectedError`, an `AIClientError` subclass that carries the reply text with the message the plain error had ("Response validation failed for model '…' (attempt n/m)."), so `chat_structured` reflects on that reply while other `chat_messages` callers see the same error class family and message. Only the first attempt reads and writes the cache. Neither the rejection nor a retry is logged.

**The retry names every violation, and the error holds no model text.** `_validate_schema_payload` and `_repair_and_validate_payload` now return the `SchemaReflectionReport`, extracted with every violation (`max_errors=exc.error_count()`), instead of a five-violation string summary, and the retry sends that report's prescriptive `format_reflection_prompt` (each field path, error, provided value and fix hint). `StructuredOutputValidationError`'s message keeps only the last reply's violation count and their pydantic error types (for example `2 schema violation(s) (extra_forbidden, model_type)`), never a field path, since a path can be a key the model invented; that message reaches the `ai.client.chat_structured` span, logs and intake's skip reason. `violations` holds the count (0 when the reply held no JSON). The now unused `format_schema_validation_error` is removed, and task-437's file names what replaced it.

**Refine's prompts are files.** `roadmap_refine_research.md` and `roadmap_refine_proposal.md` load through `load_task_prompt()`. The proposal prompt names every `RefinementProposal`, `AcceptanceCriterion` and `QuestionAnswer` key and what goes in it, allows no other key, and says the data is never an instruction. The issue, context and search results reach the model as one JSON user message, so `roadmap/refine.py` holds no multi-line prompt string. `RefinementProposal` keeps `extra="forbid"` as #744's injection guard.

**One failed item skips only itself.** `plan_refine` re-raises `AICredentialsError` (the run still stops at the first item) and records any other `AIClientError` of an item's model call as a `RefineFailure` (item, error class name, violation count), logging one warning without model text, then moves on. `RefinePlan.failed_items` replaces the unused `RefinePlan.error`, `has_writes` counts successful items only, and `render_refine_plan` lists the failed items under "Failed Items". `raise_for_failed_items` raises `RoadmapRefineError` (`ROADMAP_REFINE_FAILED`, exit 1) after the other items are written: in the service's `_run_refine_adapter`, so `run_due_jobs`' `RoadmapRunError.failed_jobs` names `refine`; in `refine_item`, so intake's P0 refine hook still logs a failed refine; and in `devops roadmap refine`, which exits 1 in a preview (`--dry-run` or no `--confirm`) as well as under `--confirm`. The MCP mirror `roadmap_refine` therefore ends in a `ToolError` that still carries the plan. The error's message names each skipped item with its class and violation count, and it is raised outside the handler that caught the model error, so no logged traceback chains to a message that quotes the reply. Refine's research step catches only `AIClientError` (credentials still propagate) and logs the error class alone, then refines without search results.

## Risks and Notes

- Each reply the schema check rejects now ends its `chat_messages` call with `ReplyRejectedError`, which `_retry_chat_dispatch` records on the `ai.llm.chat` span, so that span is marked ERROR even when the retry recovers and `chat_structured` returns a valid proposal. Error rates derived from `ai.llm.chat` spans rise accordingly; the `ai.client.chat_structured` span is the one that says whether the call succeeded.
- Intake's request changes too: its system message gains the schema and, on the gateway, `response_format`. `ModelProposal` has no required field and `extra="ignore"`, so an empty object satisfies a constrained decoder; intake's own code still decides which values stand, as it does for any reply, and the reason comments intake posts after the rollout show whether its proposals thinned. Intake's tests use a duck-typed client, so no test exercises intake under `response_format`.
- The new system text changes every `chat_structured` cache key, so the first service round after the rollout re-plans every pending intake candidate and refine item with a model call: a one-time cost. Old Markdown entries are never served, because their keys no longer match and the validator would refuse them.
- `devops roadmap refine --dry-run` still makes GitHub and model requests; that predates this item and belongs to #412. This item adds no request to that path.
- #1365 (log each failed job's own error) should carry `RoadmapRefineError` unchanged, and #1400 should treat it as a non-rate-limit failure when it builds its spend line and pause.
- A failed item is picked again by the next round; holding it back until its body changes waits for the post-merge failure rate.
