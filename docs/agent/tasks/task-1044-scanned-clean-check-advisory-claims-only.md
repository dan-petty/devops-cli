# Task: The Scanned-Clean Check Invalidates Only Claims About a Dependency's Own Advisories (#1044)

**Issue**: [#1044](https://github.com/dan-petty/devops-cli/issues/1044)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p1-high
**Scope**: scope/review

## Description
`_check_scanned_clean_dependency` (`ai/review/verification.py`) invalidated a finding as `deterministic:scanned_clean_dependency` when its title and description held "vulnerab", "cve", "advisory", "outdated" or "unpatched" and named, as a word, a dependency the session scanned CLEAN with no advisory record. Before #948 it received no dependencies on the orchestrator's path and returned at its first line. #948 rightly passed it every dependency the session scanned (58 in session `20261003-012555`), which advisory stripping and the placeholder check need, and the predicate then fired on any security finding that named kubernetes, httpx2, keyring, pytest, docker or bandit, with the false reason "This run's own advisory scan reports <name> CLEAN". Semgrep's `yaml.kubernetes.security.*` findings were discarded by a word in the rule's own text.

- **The predicate** (`ai/review/verification.py`). A module-level `_ADVISORY_CLAIM` pattern, beside the function, matches the words of a claim about a package's published advisories: `CVE` or `CVEs` as a word (so an id such as `CVE-2024-24762` too), a GHSA id (`GHSA-xxxx-xxxx-xxxx`), "advisory" or "advisories", "unpatched", "known vulnerability" or "known vulnerabilities", and "vulnerable version(s)", case-insensitive and on word boundaries. The check runs only when the title and description match it; the rest is unchanged: a named dependency must be CLEAN with no vulnerability record, and the name is still matched as a word anywhere in the text, as the issue decided (no proximity rule). Bare "vulnerab" and "outdated" no longer trigger it.
- **The docstring** says what a CLEAN scan refutes: that the dependency, at the version the project pins, carries a published advisory, and nothing about how the code uses the package, a manifest that names it, or whether the version is current.
- **The early checks stop at the first that fires** (`_check_early_hallucinations`, from review). `apply_verdict` writes on the finding itself, and the function built every early check's result in a list before it looked at any, so the last check to fire wrote the verdict and reason the finding kept. The scanned-clean check runs last, so a finding the placeholder check had invalidated, such as `k8s/cloudflared/deployment.yaml:25-30` (session `20260930-232803`, "Kubernetes best practices ... CVE-2024-xxxx"), was relabelled "advisory scan reports kubernetes CLEAN". This is the false reason this item is about, so it is fixed here, although the issue names only `_check_scanned_clean_dependency`. The checks are now a tuple of `functools.partial` calls run in order, and the first result wins, as in `_check_code_file_hallucinations`. #845's hunks in `verification.py` (imports, `_read_and_mask_related_file`, and the verdict functions after `_without_self_refutation`) do not touch this function or the lines next to it.
- **Left as they were.** #948's wiring of the session's dependencies, advisory stripping and the placeholder check. No function in `verification.py` changes apart from `_check_scanned_clean_dependency`, its `_ADVISORY_CLAIM` pattern, and `_check_early_hallucinations`.
- **`docs/SELF_IMPROVEMENT.md`.** Its sentence on the check said it invalidates "a vulnerability claim naming a package this run scanned clean". It now says "a claim that a package this run scanned clean carries a known advisory".
