## Description
The path review of the whole repository in session `20261001-224227` raised 563 findings. Triage against `release/v0.2.25` (c279c18) upheld two LOW defects in the same area: text from a registry, a build and a scraped metrics endpoint reached the console as Rich markup. A closing tag such as `[/v2/repo]` or `[/]` in that text ended the command in a `MarkupError` traceback, `[internal]` vanished, and `[link=...]` became a terminal link. Both are fixed here as the issue's **Fix** lines say, each with a regression test that fails on the base revision and passes here. The house pattern from #987 is followed: a whole message of remote text goes through `safe=True`, and a table cell holding it is wrapped in `escape_text`.

- **Docker** (`commands/docker.py`). `build` prints each `stream` line, and `push` each registry status, with `print_info(..., prefix=False, safe=True)`, and `push` prints the registry's error with `print_error(..., prefix=False, safe=True)` before its exit 1. The control-character strip before each is unchanged.
- **Metrics table** (`commands/sandbox.py`, `_render_prom_table`). The metric name, the upper-cased type and the label string are each wrapped in `escape_text`. The parser admits no bracket in a metric name, and after the `# TYPE` change below none in a type, so those two escapes keep the table safe without relying on the parser, and the test builds such a metric directly. The label string is still cut to 40 characters, before it is escaped, so the cut cannot land between a backslash and the bracket it escapes. The `escape_text` route was taken over a `safe` parameter on `print_table` because it is the #987 pattern and keeps the change to this function.
- **`# TYPE` lines** (`sandbox/metrics.py`, `_record_type`). A line is kept only when its name matches the metric-name grammar (`_METRIC_NAME_REGEX`, built from the same `_METRIC_NAME_PATTERN` as `_METRIC_LINE_REGEX`, whose pattern is unchanged) and its type, lower-cased, is one of `CONST_PROMETHEUS_EXPOSITION_METRIC_TYPES` (`config/constants.py`): `counter`, `gauge`, `histogram`, `summary`, `untyped`, the closed set the text exposition format 0.0.4 defines. Any other line is ignored, and the samples' type falls back to `_infer_metric_type`. That includes the OpenMetrics-only types (`info`, `stateset`, `gaugehistogram`, `unknown`), which the format this parser reads does not define. The type a sample gets also shows in `devops sandbox metrics --json`.
- **Scrape error** (`commands/sandbox.py`, `_render_metrics_snapshot`), the issue's optional third step. The `SCRAPE WARNING` line and the `encountered telemetry collection error` line print with `safe=True`. The scrape error holds the HTTP client's exception text, which can quote the endpoint's own bytes: h11 reports a malformed header line as `illegal header line: bytearray(b'...')`. The other lines of the same function, the threshold alerts and the healthy and threshold-exceeded lines, print with `safe=True` too, since none holds intended markup. The healthy and threshold-exceeded lines hold the target, which can hold brackets. A threshold alert is the CLI's own text, built from numbers and metric names the parser limits to `[a-zA-Z0-9_:]`, so for it `safe=True` changes nothing a user can see, and the changelog does not claim it does; the test still guards it, as part of the function printing no snapshot text as markup.
- Beyond what the issue asks: the target in the `Cgroup v2 Resource Telemetry` and `Prometheus Application Metrics` table titles is wrapped in `escape_text`. It is the instance name or the URL the user gave, and a URL can hold brackets.
- The issue proposed `tests/unit/commands/test_sandbox_metrics_render.py`. The suite is flat, so the sandbox tests are in `tests/test_sandbox_metrics.py`, beside the parser and CLI tests they share imports with. Their recording console is 400 columns wide, not 200, so no line wraps.
- Not changed, and outside the issue: other tables in `commands/sandbox.py` and `commands/docker.py` still pass text they did not write to `print_table` unescaped: the probe table's `message` and `target`, the trace waterfall's span names (inside `[bold]` markup) and its `[{target}]` title, the instances table's names and images, and the BuildKit cache table's `description` (`docker cache`). They were not part of this issue's triage.

## Acceptance Criteria
- [x] 1. Registry and build text prints as written (`tests/test_docker.py`, `docker_engine` fixture, no Docker daemon). `test_docker_push_registry_error_prints_as_written_and_exits_1` pushes `registry/app:1` with the registry answering `{"error": "denied: [/v2/repo] access"}`. It exits 1 with a `SystemExit` and the error appears literally in the output. Against the base sources it failed with `assert (1, False) == (1, True)`: the exit code was 1 because `rich.errors.MarkupError: closing tag '[/v2/repo]' at position 18 doesn't match any open tag` escaped. `test_docker_push_status_and_build_output_print_as_written` builds with the stream lines `Step [/x] done` and `[internal] load build definition from Dockerfile`, each ending in a BEL, and pushes with the status `[link=https://example.com]Pushed[/link] [internal]`. Both exit 0, every line appears literally, and no BEL reaches the output. Against the base sources the build failed with `assert (1, 0) == (0, 0)`, and the same push printed only the word `Pushed`, the link and `[internal]` gone.
- [x] 2. Scraped labels and types print as written. `test_prom_table_prints_scraped_labels_and_types_as_written` (`tests/test_sandbox_metrics.py`) renders `_render_prom_table` into a recording console with the issue's exposition `# TYPE up [/]` / `up{job="[/]",x="[bold red]FAKE[/]"} 1`, a metric built directly with the name `hits[/h]` and the type `[/x]gauge`, and a 43-character label string with `[/b]` at the cut. Against the base sources it raised `MarkupError: closing tag '[/h]' at position 4 doesn't match any open tag`; before the bracketed name was added it raised `MarkupError: closing tag '[/]' at position 0 has nothing to close` on the issue's exposition.
- [x] 3.
