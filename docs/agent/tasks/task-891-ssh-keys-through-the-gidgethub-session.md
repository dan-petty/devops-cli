**Issue**: [#891](https://github.com/dan-petty/devops-cli/issues/891)
**Scope**: scope/github
**Feasibility**: Read gidgethub 6.0.0 as locked and `src/devops_cli/github/session.py` at the release tip: `GitHubSession.rest` sends one request as the process identity and `GitHubSession.paginate` reads every `Link` page of a listing, and the signing key already went through both (#983 PR 1, 2 and 5). `git grep` over `src` and `tests` finds no caller of `get_user_ssh_keys`, `add_user_ssh_key`, `delete_user_ssh_key`, `create_pr_review_comment`, `get_issues`, `GitHubClient.create_issue`, `GitHubClient.edit_issue`, `get_pages_info`, `get_pages_builds` (the module function of that name in `github/pages.py` is called by `commands/gh.py` directly), `GhCliClient.edit_issue` or `SSHKeyInfo` outside the deleted code and the tests of it. `create_issue` and `edit_issue` also appear as operation strings in `github/issues.py`, `lang/en/messages.py` and `roadmap/request_plan.py`, and as `RoadmapStore.create_issue`; none of those call the client. The new tests run `register_key_on_github` over `GitHubApiFake`, which answers through `httpx2.MockTransport` and fails any test that starts gh; the registration tests fail on the base, where the gh path runs `gh auth status` first. The status a missing scope arrives with was read from the gh output the deleted gh path's test recorded for `POST /user/keys` (`gh: Not Found (HTTP 404)` followed by gh's `This API operation needs the "admin:public_key" scope` suggestion) and from `github/error_classifier.py`: only a 403 whose `x-oauth-scopes` hold none of the `x-accepted-oauth-scopes` is a `GitHubScopeError`, so a 404 is a `GitHubNotFoundError` without the refresh hint unless `github/ssh.py` reads it as a missing scope. The two endpoints' scopes are the ones the deleted gh path's refresh command named: `admin:public_key` for `/user/keys` and `write:ssh_signing_key` for `/user/ssh_signing_keys`. No live GitHub call was made.

## Description
SSH key registration had three paths to GitHub for one identity: the `gh` CLI (`_register_with_gh` and its helpers), PyGithub (`GitHubClient.get_user_ssh_keys` and `add_user_ssh_key`) and the session, which carried only the signing key. Since #767 the first two act as the same identity as the session, so they added a transport, a text parser for gh's failures and a second 422 rule, not a capability.

This step leaves one path. `register_key_on_github` posts the key to `/user/keys` and then to `/user/ssh_signing_keys` with `GitHubSession.rest`, as the session's identity. GitHub answers 422 for a key it already holds, but also for one it rejects as invalid and one in use on another account, so a 422 counts as registered only when `GitHubSession.paginate` lists the key at that endpoint, or cannot read the listing; otherwise the 422 is the failure. The rule is written once, for both endpoints, and the listing reads every page, where the gh path read the first. A refusal on either endpoint is an `SSHRegistrationError` whose cause is the session's error class: a 403 with scope headers is a `GitHubScopeError` carrying `gh auth refresh -s <scope>`. GitHub hides an endpoint a token's scopes cannot reach behind a 404, and these two endpoints have no resource to be missing, so a 404 on either POST is read as a missing scope: the cause is a `GitHubScopeError`, itself caused by the `GitHubNotFoundError`, and its message names the endpoint's scope (`CONST_GITHUB_SSH_KEY_ENDPOINT_SCOPES`) and gives `gh auth refresh -h github.com -s admin:public_key,write:ssh_signing_key`, the scopes registration needs. `devops ssh register` and `devops ssh rotate` both print the registration error's message, so the hint reaches either; `register` no longer prints a fixed `gh auth refresh` tip after every registration error, which named the command for a 5xx or an invalid key as well. A 404 on the listing a 422 sends the session to read, or on any other path, is unchanged. The authentication key is now posted first and listed only after a 422, as the signing key already was, so a key GitHub accepts costs two POSTs and no listing.

Deleted with it, because nothing else called them: `GitHubClient.get_user_ssh_keys`, `add_user_ssh_key`, `delete_user_ssh_key`, `create_pr_review_comment`, `get_issues`, `create_issue`, `edit_issue`, `get_pages_info` and `get_pages_builds`, `GhCliClient.edit_issue`, the `SSHKeyInfo` model with its `models` export, and `edit_repository_issue`, `close_repository_issue` and `_build_issue_patch_payload` in `github/issues.py`, whose only callers were the deleted `edit_issue` methods (`devops gh issues edit` builds its own payload and keeps `_resolve_milestone_number` and `_resolve_updated_labels`).

## Feasibility of the Pull Request Part
`git grep` lists every caller of `get_pull`, `get_file_at`, `get_merge_base`, `get_org_repos` and the label methods of `GitHubClient`.

The recorded answers come from pull request 158 of `octocat/Hello-World`. A read-only token read them on 2026-10-22. They hold the pull request, both pages of its files and the comparison of its base and head. They also hold a file and a missing file at a commit, and `GET /users/octocat/repos`.

The pull request has two changed files. GitHub reports its head repository as null, because the fork is deleted. `GET /orgs/octocat/repos` answers 404, because octocat is a user. The pydantic `AliasPath` reads a null `repo` as no repository. A shell run confirmed this.

`uv run deptry src` reports PyGithub as an unused dependency when no module imports it. `uv lock --offline` removed only the block of PyGithub.

No live call read the contents answer for a directory or for a file over 1 MB. That answer follows the REST documentation of GitHub. No live call read `/user/repos`, because it lists the private repositories of the account.

gidgethub keeps its conditional-request cache by URL only. `get_pull` and `get_pr_diff` read one URL with two media types. The fake sends no ETag, so no test can show a clash. A step of a person in the acceptance criteria covers it.

## Pull Requests, Files, Merge Bases, Repositories and Comments
`GitHubClient` takes the session and makes only session requests. It builds no PyGithub object. Each call returns what GitHub said, or raises why it did not.

`get_pull` returns a `PullRequest`. It holds the title and a `CommitRef` for the head and for the base. A `CommitRef` holds the sha, the branch and the full name of the repository. GitHub reports the head repository as null when the fork is deleted. The `CommitRef` then has no repository, and the callers read the base repository instead.

`get_pull_files` reads `pulls/{n}/files?per_page=100` page by page with `session.paginate`. It returns `PullRequestFile` models. `get_file_at` reads the contents endpoint and decodes the base64. It returns None for a 404, a directory, a link, a submodule, a file over 1 MB and bytes that are not UTF-8. Every other failure raises the error of the session. A 500 that outlasts the retries raises `GitHubUnreadError`, and so does a body that is no file.

`get_merge_base` reads the compare endpoint. It returns None for a 404 only. `get_org_repos` lists `/orgs/{org}/repos`. When GitHub answers 404 and the name is the login of the session, it lists `/user/repos?affiliation=owner` instead. `create_issue_comment` posts one comment with `POST /repos/{repo}/issues/{n}/comments`.

The review runner, `devops review pr`, `devops ai analyze pr` and `devops repos clone-org` use these calls. A GitHub failure ends the command with the failure as its error. PyGithub raised its own exception before. `devops review pr --post` also stops when it cannot read the files of the pull request. It posted a comment that named no file before.

A failed read of a base file is no absent file. `devops review pr` ends with the failure as its error when GitHub cannot answer for a file at the merge base. This holds for a file of a symbol delta and for `.devops/review.toml`. Without the configuration, the review would use the default path classes. `BaseRevision.read` returns None only for a file that is not there.

Two steps of the static stage still read a failed base file as absent: the fingerprints of base findings and the complexity deltas. The handlers of the two stages catch every error of the session. A change of these handlers must come first. This part leaves the two steps as they are.

`devops gh labels sync` uses `GhCliClient`, and `devops gh labels list` has no PyGithub fallback. No Python file in `src` or `tests` imports PyGithub now. The `deptry` check rejects an unused dependency, so this part removes `PyGithub` from `pyproject.toml` and `uv.lock`.

The open tool for the transport is gidgethub (ADR 0006). The facade adds only pydantic models of the fields that callers read. It uses `base64` and `urllib.parse` from the standard library. No new code replaces an open tool.

## Feasibility of the Last Part
`git grep` over `src`, `tests`, `docs`, `k8s`, `.github`, `pyproject.toml` and `uv.lock` found no import of PyGithub. The only `from github import` lines were the examples in its knowledge-base page. `uv lock --check` and `uv run deptry src` pass without PyGithub in `pyproject.toml` and `uv.lock`.

`docs/ERRORS.md` lists the `DevOpsCLIError` subclasses that the process has loaded. The generator imports `devops_cli.exceptions` and the modules of `CONST_DOMAIN_EXCEPTION_MODULES`. The module `devops_cli.github.ssh` was in neither. A test that asserted the `SSHRegistrationError` row failed on the base until the module joined the list. `uv run devops docs generate --sync-readme` then wrote the row.

The unit test depends on import order inside one worker. Any earlier import of `devops_cli.github.ssh` loads the class, and the row appears without the entry in `CONST_DOMAIN_EXCEPTION_MODULES`. The gate `uv run devops docs check` runs in a new process and guards that entry. Without the entry, it fails with `ERRORS.md differs from generated content`.

## The Registration Error, the Dependency and the Documents
`SSHRegistrationError` is a `GitHubOperationError`. It was a plain `RuntimeError` with no error code, which is outside the domain error taxonomy. It takes the code `GITHUB_OPERATION_FAILED` and the exit status 1 from `GitHubOperationError`. `devops ssh register` and `devops ssh rotate` catch it by name as before.

This part deletes the knowledge-base page of PyGithub and its row in the knowledge-base README. `python_packages.md` names gidgethub and the session in place of PyGithub. `docs/KNOWLEDGE_BASE.md`, `tests/test_kb.py` and `tests/test_kb_manuals_metadata.py` count one manual fewer. This part adds no gidgethub manual, because ADR 0006 holds the decision.

This part also edits the words about PyGithub in `AGENTS.md`, `docs/TESTING.md` and ADR 0006. The comment of `CONST_GH_RATE_LIMIT_RESET_MARGIN_SECONDS` keeps the reason for the margin of 1 s. `docs/agent/tasks/task-1308-test-conventions.md` and `docs/agent/tasks/task-1364-quota-reset-boundary.md` described text that these edits changed, so they follow the new text. The other task files that name PyGithub describe history and stay as they are.
