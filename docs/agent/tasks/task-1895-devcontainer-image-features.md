# Task: The Published DevContainer Image Applies Its Features Again, So remoteUser vscode Exists (#1895)

**Issue**: [#1895](https://github.com/dan-petty/devops-cli/issues/1895)
**Scope**: scope/devcontainer
**Feasibility**: Verified against the failing open of a child repository (VS Code Dev Containers 0.469.0, CLI 0.89.0, rootless Podman 5.7 with `--userns=keep-id`: `unable to find user vscode`), the v0.2.34 and v0.2.38 release run logs (`Features: 7 configured` against 8 Dockerfile steps for each platform), the Dev Containers CLI 0.89.0 source and `devcontainer build --help`, and a local run of the action's own `run:` scripts for `linux/amd64` against a local `registry:3`. That run built the 7 features, pushed by digest, opened a child configuration that names only the image as `vscode` through `devcontainer up`, and found uid and gid 1000 and every checked command. `linux/arm64` was not run locally: the machine has no binfmt support.

## Description

Since v0.2.35 the release built `.devcontainer/Dockerfile` alone with `docker/build-push-action` (#1570 for #438). Only the Dev Container Features of `.devcontainer/devcontainer.json` create the user `vscode` and install zsh, git, gh, Node, docker, kubectl, helm, minikube and Claude Code, and only the Dev Containers CLI applies them. So images v0.2.35 to v0.2.38 and `latest` had no user `vscode`, and a child repository with `"remoteUser": "vscode"` did not open. The pull request check still built with `devcontainers/ci` and the features, so it did not build what the release published.

- **Shared action** (`.github/actions/devcontainer-image/action.yml`, new). It sets up QEMU, Buildx with the host network and Node, and installs the Dev Containers CLI with `devops install-tools --tool devcontainers-cli`. It writes `.devcontainer/devcontainer.build.json`, a copy of `.devcontainer/devcontainer.json` whose `build.options` add the OCI labels, `--sbom=true`, `--provenance=mode=max` and a metadata file, because `devcontainer build --label` adds nothing to a Dockerfile configuration (devcontainers/cli#930). It runs `devcontainer build --frozen-lockfile` for `linux/amd64,linux/arm64` with an output that pushes by digest, and reads the digest from the metadata file. Then it runs `devcontainer up --skip-post-create` on a child configuration that names only that digest, checks that `id -un` prints `vscode`, and on each platform runs the image as `vscode` with uid and gid 1000 and one command from each feature.
- **Release** (`.github/workflows/release.yml`, job `devcontainer`). The action replaces the QEMU, Buildx and `docker/build-push-action` steps. A GHCR registry cache at `devcontainer:buildcache` replaces the GitHub Actions cache, because a `run:` step gets the Actions runtime token only from a helper that exports it to every later step of a job that holds `id-token: write`. The job attests the digest that the action returns, tags it `vX.Y.Z` and `latest`, and checks that each tag resolves to that digest. The timeout is 60 minutes.
- **Pull request check** (`.github/workflows/ci.yml`, job `devcontainer`). It calls the same action against a `registry:3` service on the runner, pinned by digest, and reads the release cache. It holds `contents: read` and `packages: read`, and publishes nothing, so the GHCR push of `pr-<n>` tags, the open-state check and `packages: write` are gone. `workflow_dispatch` runs it as `service-image` does, so a person can run the two-platform build on a topic branch. `IMAGE_CONTENT_PATHS` watches the action.
- **CLI pin** (`src/devops_cli/tools_lock/tools.lock`, `src/devops_cli/tools_lock/devcontainers-cli/`). `[npm.devcontainers-cli]` pins `@devcontainers/cli` 0.89.0, the CLI that VS Code Dev Containers 0.469.0 bundles, with a version 3 lockfile that holds its sha512. `npm ci --ignore-scripts`, `npm audit signatures` and `osv-scanner` passed on it. `devops ci audit` now audits its lockfile, and post-create installs `devcontainer` with the other locked tools.
- **Docs**. `docs/DEVCONTAINER_USAGE.md` names both platforms, says how the release builds the image, and names the images that lack the user. `RELEASE_CYCLE.md` lists the devcontainer publish step and the published-tag check. The #438 task file names the builder and the cache.
