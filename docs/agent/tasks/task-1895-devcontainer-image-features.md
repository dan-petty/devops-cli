# Task: The Published DevContainer Image Applies Its Features Again, So remoteUser vscode Exists (#1895)

**Issue**: [#1895](https://github.com/dan-petty/devops-cli/issues/1895)
**Scope**: scope/devcontainer
**Feasibility**: Verified against these sources. A child repository failed to open in VS Code Dev Containers 0.469.0 (CLI 0.89.0) on rootless Podman 5.7 with `--userns=keep-id`, with `unable to find user vscode`. The v0.2.34 release log shows `Features: 7 configured`. The v0.2.38 release log shows only the 8 Dockerfile steps for each platform. The Dev Containers CLI 0.89.0 source and `devcontainer build --help` give the flags. A local run of the action scripts for `linux/amd64` used a local `registry:3`. It built the 7 features and pushed by digest. Then `devcontainer up` opened a child configuration that names only the image as `vscode`, with uid and gid 1000 and every checked command. `linux/arm64` was not run locally, because the machine has no binfmt support.

## Description

Since v0.2.35 the release built `.devcontainer/Dockerfile` alone with `docker/build-push-action` (#1570 for #438). Only the Dev Container Features of `.devcontainer/devcontainer.json` create the user `vscode`. They also install zsh, git, gh, the Copilot CLI, Node, docker, kubectl, helm, minikube and Claude Code. Only the Dev Containers CLI applies them. So images v0.2.35 to v0.2.38 and `latest` had no user `vscode`, and a child repository with `"remoteUser": "vscode"` did not open. The pull request check still built with `devcontainers/ci` and the features, so it did not build what the release published.

- **Build action** (`.github/actions/devcontainer-image/action.yml`, new). It sets up QEMU, Buildx with the host network and Node, and installs the CLI with `devops install-tools --tool devcontainers-cli`. It writes `.devcontainer/devcontainer.build.json`, a copy of `.devcontainer/devcontainer.json` with more `build.options`: the OCI labels, `--sbom=true`, `--provenance=mode=max` and a metadata file. The CLI ignores `devcontainer build --label` for a Dockerfile configuration (devcontainers/cli#930). The action runs `devcontainer build --frozen-lockfile` for `linux/amd64,linux/arm64` and pushes by digest. It reads the digest from the metadata file, then frees the builder's disk space. It writes no `GITHUB_PATH`.
- **Smoke action** (`.github/actions/devcontainer-smoke/action.yml`, new). It runs `devcontainer up --skip-post-create` on a child configuration that names only the digest, and checks that `id -un` prints `vscode`. Then it runs the image as `vscode` on each platform. It checks uid and gid 1000 and one command from each feature. The docker-in-docker feature makes this container privileged, so the caller's job holds no write scope and no OIDC token.
- **Release** (`.github/workflows/release.yml`). Three jobs replace the one `devcontainer` job. `devcontainer-image` (`packages: write`) validates the labels and runs the build action with a GHCR registry cache at `devcontainer:buildcache`. The GitHub Actions cache needs the runtime token, which a `run:` step gets only from a helper that exports it to every later step. `devcontainer-smoke` (`packages: read`) runs the smoke action. `devcontainer` attests the digest and tags it `vX.Y.Z` and `latest`. Then it checks that each tag resolves to that digest.
- **Pull request check** (`.github/workflows/ci.yml`, job `devcontainer`). It runs the two actions against a `registry:3` service on the runner, pinned by digest, and reads the release cache. It holds `contents: read` and `packages: read` and publishes nothing. So the GHCR push of `pr-<n>` tags, the open-state check and `packages: write` are gone. `workflow_dispatch` runs it as it runs `service-image`, so a person can run the two-platform build on a topic branch. `IMAGE_CONTENT_PATHS` watches both actions.
- **Cleanup** (`.github/workflows/cleanup-devcontainer.yml`). `older-than: 1 day` keeps it from deleting the untagged digest of a release that is between its push and its tags.
- **Pins**. `docker/metadata-action` is `v6.2.0` in the three steps that used an untagged commit with the comment `# v5`. `docker/setup-qemu-action` is `v4.4.0`, which declares Node 24, in both actions and in the `service-image` release job.
- **CLI pin** (`src/devops_cli/tools_lock/tools.lock`, `src/devops_cli/tools_lock/devcontainers-cli/`). `[npm.devcontainers-cli]` pins `@devcontainers/cli` 0.89.0, the CLI in VS Code Dev Containers 0.469.0. Its version 3 lockfile holds the sha512 of the package. `npm ci --ignore-scripts`, `npm audit signatures` and `osv-scanner` passed on it. `devops ci audit` now audits this lockfile, and post-create installs `devcontainer` with the other locked tools.
- **Docs**. `docs/DEVCONTAINER_USAGE.md` names both platforms and says how the release builds the image. It also names the images that lack the user, and says that `v0.2.34` has only `linux/amd64`. `RELEASE_CYCLE.md` lists the three jobs and the check of a published tag. `README.md` and the CLI reference name each Node tool. The #438 task file names the builder and the cache.
