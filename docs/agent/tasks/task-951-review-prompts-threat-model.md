# Task: Review Prompts State a Threat Model and an Evidence Bar, and Send Nothing the Pipeline Does Not Use (#951)

**Issue**: [#951](https://github.com/dan-petty/devops-cli/issues/951)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p1-high
**Scope**: scope/review

## Description
In review session `20261001-224227`, 87% of the 563 reported findings were false. An audit of every prompt the pipeline sends a model tied each recurring failure to the prompt text that invited it: no threat model, an instruction to name CVE IDs, three prompts telling the model to report a control it cannot see, severity bands with no reachability condition, mandates read as defect lists, fixes that change nothing, no rule for tests, documentation opinions, a verifier with about 40 rules for invalidating and none for verifying, contradictions between prompts, prompt files nothing loads, and a reply schema of 8,220 characters, most of it fields the pipeline owns.

This item owns the prompt text, including the prompt half of #846 (the criteria rule). #846 keeps the criteria executor. The deterministic guards the audit lists (criteria evidence classifier, advisory cross-check, path routing, syntax, masking annotations, verifier input, quote check, report policy) are not part of this item.

### Prompts
- `personas/devsecops/role.md` judges security by evidence that can be quoted, cites a CWE only when it names the defect, and never cites a CVE or GHSA identifier from memory.
- `personas/devsecops/prompt.md` opens with the threat model: untrusted (network and fetched web content, model output, pull request and issue text, files of a repository the program reviews or builds, Kubernetes and cloud API data, requests to a server the code runs, MCP and tool-call arguments) and trusted (the person running the program, their config files, environment variables and arguments, values the code builds). A vulnerability is the quoted source, the sink it reaches and the missing check between them; a missing guard on trusted input is reported only when the conventions require it, as LOW. Advisories come from the scanners. The persona returns no finding when it cannot quote the source, sink and defective line. Its checklist names defects instead of mandates ("Enforce bounded database searches", "health probes, PSS/PSA" are gone), and the launch-path rule ends in "return no finding" instead of reporting with a lower confidence. The idiom exemptions it repeated from `review.md` and the verifier are gone. The file went from 5,088 to 3,332 characters.
- `tasks/review.md`:
  - trusted and untrusted input are what the project's conventions say; where they give no threat model, a default one applies (untrusted: network and fetched content, model output, pull request and issue text, a repository the program reviews or builds, cluster and cloud API data, server requests, tool-call arguments; trusted: the operator's config, environment and arguments, and values the code builds). This defines the bands for the architect, qa, auditor and pm personas too, whose own prompts define neither;
  - severity follows reachability (CRITICAL needs an untrusted input reaching code execution, credential disclosure or a write outside its root, every step quoted; LOW includes a missing guard on trusted input that the conventions require, and without that requirement it is no finding);
  - the CWE-209 rule asks for untrusted strings to be bounded, instead of every caller-supplied string;
  - report only what you can see; a requirement is not a defect;
  - a fix is replacement code for the cited lines, and a "verify/review/consider" fix means no finding;
  - `observed_value` is copied exactly from the cited lines;
  - criteria are `python -c` or `pytest` checks that import the cited code and `assert` the outcome, and a command that finds, imports or prints code is a sentence with `"executable": false`;
  - the review tool's markers have the form `<masked-kind>` and are never a hardcoded secret, a syntax error or a broken value; a bare `<masked>` or any other mask is the file's own text;
  - its 18 exemption bullets are gone: 14 devops-cli facts moved to `.devops/review.md`, the GitHub-login rule was dropped, and the cluster-HTTP, example-domain and planning-document rules stay in generic form (the last in `docs_review_prompt.md`).

  It no longer asks for `APPROVE`: the recommendation is derived from the findings. The file went from 8,975 to 5,865 bytes.
- `tasks/code_review_prompt.md`: *Report What You Can See* replaces *Segment Boundary Honesty*, a *Test Files* rule says a finding about a test itself is a test that cannot fail while a real credential or a genuine vulnerability in a test file is still a finding, and a fix is the corrected code for the cited lines. MCP also serves this file on its own as the `code_review_prompt` prompt, with no `review.md` and no reply schema, so `code_review_prompt()` in `ai/mcp/server.py` appends `tasks/mcp_code_review_output.md`, which asks for one JSON object of `findings` (each with `severity`, `location`, `title`, `description` and `fix`) and `summary`. The pipeline's pages do not carry that line: they are answered in the reply schema the persona system prompt carries, with all ten reviewer fields, and the five-field line had reached every code page.
- `tasks/docs_review_prompt.md`: a finding is a statement the code contradicts, a broken relative link, or a command, option, key or variable that does not exist; requests for more explanation go in `summary`; roadmaps, changelogs, task files and decision records get no findings.
- `tasks/config_review_prompt.md`: privileges, transport, schema, resource bounds and provenance are written as defects. It no longer asks for `http://` to be flagged (which `review.md` and the verifier call intended inside a cluster) or for digests on pinned tags.
- `tasks/verify_finding_system.md`:
  - a standard for VERIFIED (the quoted defective line with its number, and for a security claim the untrusted source and sink; a command counts only when it runs the cited code and asserts the outcome);
  - trusted input is refuted unless the conventions require the guard. The CWE-209 rule verifies an untrusted string that reaches an exception detail or a log unbounded, and leaves a trusted one to that rule; the validation-coverage rule verifies an untrusted argument that reaches a file path without the containment check the other arguments get, instead of "checks [that] run only on populated schema properties";
  - tests follow section 7: a claim about the test itself is a defect only when the test cannot fail or does not check what its name says, and a real credential or a genuine vulnerability in a test file is judged as anywhere else;
  - a check in the shown code that makes the failure impossible refutes the finding, replacing the rule that made a finding whose description the verifier restated impossible to refute;
  - unverified when the deciding code is not shown;
  - severity on `review.md`'s bands, copied line for line. The verifier's severity replaces the reviewer's (`verification.py` keeps the verifier's when it gives a valid one), and it had no bands of its own;
  - advisories match the reviewer rule: they come from the scanners, whose findings carry the identifier in a bracketed title at a lockfile, and any other finding that rests on a CVE or GHSA identifier, against a dependency or against code, well formed or a placeholder, is refuted. The old rule let a dependency claim stand on any "real, lookup-able" identifier, which the verifier cannot look up. Scanner findings are named because Trivy's lockfile advisories reach this verifier as unverified findings, and a rule refuting every cited CVE would refute them. The deterministic placeholder verdict (`_check_placeholder_advisory_hallucination`) now gives the same reason.

  The marker rules follow the audit. The `Prompt Sanitizer Markers` line, which refuted a claim that a marker is a hardcoded secret, is gone, and the one rule left names only what `mask_secrets` writes, markers of the form `<masked-kind>`: a claim that such a marker is invalid syntax, an undefined name or a broken value is refuted, and a claim that the value behind it is a real secret is about the source and stands. A bare `<masked>`, `***REDACTED***` or any other mask is the file's own text and is judged like any other, so the `<masked>` default in `docs/commands/tls.md` (written by `docs/generator.py`) and the `***REDACTED***` literals in the code are no longer taken for markers. `masked` is out of the placeholder list. The marker's shape tells the two apart, so this needs no excerpt annotation. Of the 31 exemption bullets that followed its cheap checks, 18 devops-cli facts moved to `.devops/review.md`, the NodePort rule went to the narrower one already there, which now covers every NodePort the `k8s/` manifests and Helm values declare, the GitHub-login rule was dropped, and the generic ones were shortened or merged into the verdict rules. The example reply shows a verified verdict whose severity lists all four bands (`"CRITICAL" | "HIGH" | "MEDIUM" | "LOW"`, as `compose.md` writes it) at 0.7, and a refuted one at `LOW`/0.8, instead of `HIGH`/0.95. The verified example is an untrusted request-body path traversal with every step quoted, which the bands rate HIGH or CRITICAL, so a fixed `MEDIUM` there would have taught the verifier to lower real traversals. The file went from 20,836 to 14,262 bytes.
- Fallback loop (`review_output_instruction.md`, `compose.md`): the same rules, an example finding at `MEDIUM` with assertion criteria instead of `HIGH` with `git grep`, and `compose.md` keeps mitigated findings.
- `personas/challenger/prompt.md` no longer restates the marker rule; `tasks/chat.md` no longer asks for CVE identifiers.
- Deleted: `tasks/diff_review_prompt.md` and `tasks/review_pipeline_eval.md`, which nothing loaded. `review_output_instruction.md`, `paginated_review_protocol.md`, `path_review_prompt.md` and `compose.md` reach only the fallback persona loop and stay.

### Reviewer reply schema
`Finding` and `ReviewResult` mark every pipeline-owned field `SkipJsonSchema`: verdicts and their evidence, criteria results, citations, confidence, the recommendation, and scanner and dependency data. Their JSON schema, which the persona agent appends to its system prompt, now lists only what a reviewer writes: `findings`, `summary`, and per finding `severity`, `location`, `title`, `description`, `fix`, `references`, both criteria lists, `observed_value` and `expected_value`. It went from 8,220 to 1,674 characters. Validation is unchanged, so `_review_result_from_dict`, `parse_review_response`, the agent's own parse and retry, and reloading `findings.json` read every field as before. The two models use comments instead of docstrings, because pydantic would send a docstring as the schema's description. `category` is pipeline-owned now (the prompts never asked for it, and `resolve_finding_category` infers it). With an empty conventions section, the devsecops persona system prompt went from 24,669 to 13,244 characters.

### `.devops/review.md`
It gains a threat model (trusted here: `config.yaml`, `DEVOPS_*` and provider variables, keyring entries, arguments, and the user's workspace and repositories where devops-cli acts on them for the user, as `ci`, `workspace` and `git` do; untrusted here: a tree devops-cli reviews, scans, analyzes or ingests, even when it is the user's own (#946), fetched pages and documents, model replies and tool-call arguments, GitHub PR, issue and comment text, Kubernetes API data, MCP client calls, requests to the local server), and the devops-cli facts the shared prompts carried. Without the qualifier, the user's own repositories were both trusted and, as repositories under review, untrusted, and devops-cli reviews itself. The NodePort rule names `k8s/` as a whole: it had named two manifests, one at a path that does not exist (`k8s/valkey-runs.yaml`), and missed the Ollama, Open WebUI, registry and Argo CD NodePorts. The shared "GitHub logins need no case folding" rule was dropped rather than moved: logins are case-insensitive, so it hid that class of bug. The file is 7,295 characters, under the 8,000 a review reads.

### Docs
`docs/SELF_IMPROVEMENT.md` describes the new grounding, severity and remediation rules and the reversed segment-boundary guardrail. Under *Prompt Benchmarking* it records the A/B measurement for this change as a step a person runs: two checkouts on one model-pinned config, the corpus command, A/A first, interleaved runs scored with explicit `--session` ids, `devops ai runs compare`, the guards and effects to read, the nine per-session failure signatures with the baseline session's values and the counter, and the known-negative run for planning documents. The `masked` signature counts only findings about the tool's `<masked-kind>` markers (36 in the baseline); the 10 about a bare `<masked>`, the file's own text, are listed apart with their status as the known-positive check, since counting them would score the `docs/commands/tls.md` finding B should keep as a failure. Run on the baseline session's `candidates.json`, the counter reproduces every stated value. Every review in it runs the default DevSecOps persona rather than `--all`, because the baseline session's 1,625 persona replies were all DevSecOps and the other four personas' own prompts are unchanged. A corpus copies the generating checkout's `.devops/review.md`, and a review of the corpus reads only that copy, so the protocol copies each arm's own file into `<corpus>/.devops/review.md` before each of its reviews: B's prompts no longer carry the exemptions B moved into that file, and under A's copy B would run without them. The paragraph on the conventions files keeps the sentence #946 extends on `release/v0.2.25` unchanged, so the two merge without a conflict.
