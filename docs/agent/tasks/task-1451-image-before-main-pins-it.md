# Task: The Service image a release pins is published before main pins it (#1451)

**Issue**: [#1451](https://github.com/dan-petty/devops-cli/issues/1451)
**Status**: Done
**Milestone**: v0.2.29
**Priority**: P2-Medium (set by intake on 2026-10-08)
**Scope**: type/bug, scope/k8s, scope/ci, scope/release

## Description

The release cut sets `newTag: vX.Y.Z` for `ghcr.io/dan-petty/devops-cli/service` in `k8s/devops/kustomization.yaml`. Argo CD's `devops` Application tracks `main` and syncs about two minutes after the release merges, but `release.yml` published the image only at the end of its run on `main` (23:43:28 to 23:50:20 for v0.2.28). roadmap-service uses the Recreate strategy, so its pod was stopped and its replacement backed off on the missing image for several minutes, and for as long as the release run stayed red (v0.2.27).

The fix publishes the image from the release branch, so it exists before `main` pins it:

- **Triggers.** `release.yml` also runs on a push to `release/v*`. The release job's `if` already skips those pushes. The `service-image` job runs when `!cancelled()` and either the release job succeeded or the run is a push to `release/v*`.
- **Inputs.** The job's `SERVICE_IMAGE_INPUTS` names what the image is built from: the Dockerfile's `COPY` sources (`pyproject.toml`, `uv.lock`, `src`), `Dockerfile`, `.dockerignore`, and `release.yml` itself. The image's `io.github.dan-petty.devops-cli.image-inputs` label holds the sha256 of `git ls-tree HEAD --` those paths.
- **Plan.** A new **Plan Service Image Publication** step decides `publish`, `promote` or `none`.
  - On `release/vX.Y.Z` it does nothing when the branch doesn't hold X.Y.Z yet (before the cut), when the commit is no longer the branch tip, when `main` already holds X.Y.Z, or when `service:vX.Y.Z` already carries this tree's inputs and `release.yml`'s provenance. It fails when `main` has image changes the branch lacks (`git merge-tree --write-tree origin/main HEAD` keeps other inputs than `HEAD`), since the merged tree would differ from the image, and when the branch tip can't be read. Otherwise it publishes `vX.Y.Z` without `latest`.
  - On `main` it promotes when `service:vX.Y.Z`'s provenance verifies, and warns when the image was built from other inputs than the merged tree's, which then ship in the next release. When the registry answers `not found`, it publishes `vX.Y.Z` and `latest` from `main`. An image without verifiable provenance and any other registry error fail closed.
  - **Provenance.** `gh attestation verify oci://service@<digest> -R dan-petty/devops-cli --cert-identity-regex` accepts only `release.yml` signing on `refs/heads/main` or `refs/heads/release/vX.Y.Z`. The inputs label is only its pusher's claim, and other workflows with `packages: write` (`ci.yml`'s devcontainer job on pull requests) could push the tag.
- **Push by digest, then tag.** **Build and Push Service Image** pushes by digest only (`push-by-digest=true`, no `tags`). **Attest Build Provenance** is unchanged. A new **Tag the Attested Service Image** step runs `docker buildx imagetools create --tag ...` on the attested digest, so a tag only ever names an attested image, and a failed attestation is retried by a re-run.
- **Tag.** Right before `imagetools create`, the tag step checks the branch tip and `main` again on `release/vX.Y.Z`: a commit superseded during the build leaves the tag to the tip's run, and a release pull request merged during the build fails the run instead of moving the tag `main` now pins. Every command whose failure decides something sits in an assignment of its own, so `bash -eo pipefail` stops the step on a failed `git ls-remote` instead of reading it as a superseded commit.
- **Promote.** **Point latest at the Published Service Image** runs `docker buildx imagetools create --tag service:latest service@<digest>`. Every build, scan, push, attest and tag step runs only on `publish`.
- **CI cost.** `ci.yml`'s **Service Image** job skips a pull request whose head is this repository's `release/v*`, because `release.yml`'s push run builds, scans and publishes the same tree. A fork's `release/v*` head still builds. On v0.2.28 that job cost 35.8 runner-minutes across 15 runs on the release pull request.

## Decisions and Deviations

- **Publish from the release branch** rather than from `ci.yml`'s pull request run, an Argo CD PreSync gate, or a pin by digest. It meets the first criterion inside git, in one workflow with one signer, and needs no change to the cluster or to GitHub settings. Publishing from `pull_request` runs would give every pull request into `main` packages, id-token and attestations write. A PreSync gate would hold the whole `devops` sync, still go live minutes after the merge, and leave the tag mutable.
- **Tag mutability.** Before the merge each publish moves `vX.Y.Z`. Nothing in the cluster pins that tag until the merge, and `k8s/README.md` says not to run it before then (`imagePullPolicy: IfNotPresent` keeps a node's first pull). Once `main` holds the version, the branch's plan stops, its tag step checks `main` again right before it tags and fails instead, and `main` never replaces an existing tag. Only a merge in the seconds between that check and `imagetools create` slips past it; the release pull request is merged with its check green.
- **`main`'s image changes must be on the release branch.** The release pull request's squash merge commits the merge of `main` and the branch, so the branch run compares the inputs of `git merge-tree --write-tree origin/main HEAD` with its own and fails when they differ. A commit on `main` that leaves the image's inputs alone (docs, a Renovate bump of another workflow) doesn't fail it. The fix is a `chore/open-vX.Y.Z-main` release-process pull request into the branch, merged with a merge commit; `devops pr check-readiness` exempts that head from grounding, and the release ruleset allows the merge method.
- **`main` warns and never fails over other inputs.** `main`'s tree can differ from the published image when `main` moved after the branch's last push, on a later push (Dependabot and Renovate pull requests target `main`), or on the push that recovers a failed release run, which the release job tags. In every case the tag `main` pins is kept and the difference ships in the next release, so the run warns and still points `latest` at the version's image instead of failing.
- **Provenance over the label.** Before this change `main`'s run rebuilt `service:vX.Y.Z` after the merge; now the tag's image lives for the whole branch, so the plan verifies its `release.yml` attestation before it skips a publish or promotes. On the branch an unverified image is published again; on `main` the run fails. Both `refs/heads/main` and `refs/heads/release/vX.Y.Z` are accepted, because `main`'s run builds the image when a release merged over a failed check.
- **`release.yml` is one of the inputs.** That matches `test_image_path_filter_covers_dockerfile_sources`, which treats the building workflow as an image input. Since `main` only warns about other inputs, it cannot fail a correct merge.
- **The gate is advisory.** Ruleset 21466414 requires no status checks. A merge over a red or missing check falls back to `main` building the image, with the old outage until it is published. Required checks belong to #1425.
- **v0.2.29.** The Service cuts v0.2.29 with v0.2.28's code, but the push runs the workflow file from the pushed commit, so the cut's push publishes `service:v0.2.29` once this change is on `release/v0.2.29`. If the cut comes first, merging this change into `release/v0.2.29` before the release pull request merges publishes it the same way, since the plan sees the branch holding 0.2.29 and no image. The owner placed this item in v0.2.29 and holds the v0.2.29 release pull request for it. A person still collects v0.2.29's `changelog.d/` fragments before the release pull request merges (#1450). If the release run fails anyway, the image already exists, and only `latest` and the GitHub Release wait.
- **Not done here.** Older `chore/cut-v` branch names remain in `AGENTS.md`, `.github/pull_request_template.md` and older task files; only `docs/ROUTINE_TASKS.md` step 2, which this change rewrites, is corrected. Untagged digests (about one per publish) build up in GHCR with no retention job. The release job still re-publishes the GitHub Release and the devcontainer image on every push to `main`.
