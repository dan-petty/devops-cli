# Task: Qdrant Requires Its API Key, and Open WebUI Sends It (#1670)

**Issue**: [#1670](https://github.com/dan-petty/devops-cli/issues/1670)
**Scope**: scope/k8s
**Feasibility**: Read-only checks on 2026-10-23. The live StatefulSet `llm/qdrant` (chart qdrant-1.19.1) had `QDRANT_INIT_FILE_PATH` as its only variable, and ConfigMap `llm/qdrant` had no `service.api_key`. The live StatefulSet `llm/open-webui` set `VECTOR_DB` and `QDRANT_URI` but no `QDRANT_API_KEY`. Secret `llm/qdrant-api-key` already exists with key `api-key`, labelled `app.kubernetes.io/managed-by: devops-cli`, and keyring `qdrant_api_key` holds the same value (compared, not printed). The chart 1.19.1 renders only `.Values.env` on the qdrant container (`templates/statefulset.yaml`), and its `values.yaml` declares `apiKey` and `readOnlyApiKey` only in comments. Qdrant v1.19.1 asks no key on `/`, `/healthz`, `/readyz`, `/livez` and the web UI files (`src/actix/mod.rs`), so the readiness probe on `/readyz` needs none. Open WebUI v0.11.4 reads `QDRANT_API_KEY` and gives it to both of its Qdrant clients (`config.py`, `retrieval/vector/dbs/qdrant.py`, `qdrant_multitenancy.py`). `helm template` of qdrant 1.19.1 with the new values renders `QDRANT__SERVICE__API_KEY` from `qdrant-api-key/api-key` and no Secret `qdrant-apikey`. `helm template` of open-webui 16.6.0 renders `QDRANT_API_KEY` on the open-webui container. No other live workload, CronJob or Job names Qdrant. The devops-cli RAG client lists the collections through the configured tunnel host with the keyring key.

## Description

- [x] **Qdrant** (`k8s/llm/values-qdrant.yaml`): `extraEnv`, which the chart does not read, is now `env`, so the qdrant container gets `QDRANT__SERVICE__API_KEY` from Secret `qdrant-api-key`. `apiKey: false` and `readOnlyApiKey: false` are removed. The chart does not declare them, and unset is the same as `false`: the chart makes no Secret of its own.
- [x] **Open WebUI** (`k8s/llm/values-open-webui.yaml`): `QDRANT_API_KEY` comes from `secretKeyRef {name: qdrant-api-key, key: api-key}`.
- [x] **Secret** (`src/devops_cli/k8s/cluster_secrets.py`): a change of `llm/qdrant-api-key` restarts `statefulset/qdrant` and `statefulset/open-webui`, because Open WebUI reads the key only when its pod starts. No new Secret is necessary: `llm/qdrant-api-key` already exists on the cluster, and deploy-stack pushes it before it installs the release, so no push is necessary before the merge.
- [x] **Vendored chart values** (`tests/fixtures/charts/qdrant/`): the `values.yaml` and `LICENSE` (Apache-2.0) of chart qdrant 1.19.1, unchanged, and `VERSION`.
- [x] **Docs** (`k8s/README.md`): the Qdrant paragraph names who sends the key and the check on undeclared keys. The Cluster Secrets row restarts Open WebUI too.
- [x] **Tests**: in `tests/test_k8s_qdrant_security.py`, `test_qdrant_reads_its_api_key_from_the_pushed_secret`, `test_every_top_level_qdrant_value_is_a_key_of_the_pinned_chart` and `test_open_webui_sends_the_qdrant_api_key_from_the_secret` failed on `origin/main`. `test_the_vendored_qdrant_chart_is_the_pinned_one`, `test_the_qdrant_chart_makes_no_api_key_secret_of_its_own` and `test_open_webui_is_the_only_workload_that_names_qdrant` guard the pin, the chart's own Secret and the client list. In `tests/test_k8s_push_secrets.py`, `test_table_holds_each_secret_entry_with_its_source_and_restarts` and `test_a_key_added_to_an_existing_secret_restarts_its_workloads_once` failed on `origin/main`.
- Pending a person: after Argo CD syncs `qdrant` and `open-webui`, `kubectl -n llm get pod qdrant-0 open-webui-0` shows both pods ready. With `kubectl -n llm port-forward svc/qdrant 6333:6333` running, `curl -s -o /dev/null -w '%{http_code}' http://localhost:6333/collections` prints `401`.
- Pending a person: after the sync, a document search in Open WebUI returns results, `devops ai rag status` lists the collections, and `up` of the `qdrant` ServiceMonitor target in Prometheus stays 1.
