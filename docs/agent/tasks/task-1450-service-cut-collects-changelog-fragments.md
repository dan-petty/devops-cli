**Scope**: type/bug, scope/release
**Feasibility**: Confirmed on origin: the v0.2.32 cut commit (`git show --stat` on `origin/release/v0.2.32`'s tip) changed `docs/ROADMAP.md`, `pyproject.toml` and `uv.lock` and no `CHANGELOG.md`, and #1474 and #1517 collected the fragments by hand. ## Description

The roadmap Service's close job cuts a release with `cut_release(is_prepare=True)` (`roadmap/run.py`, `devops roadmap close`, and `devops release prepare --create-pr`). Its cut commit bumped the version and rendered `docs/ROADMAP.md`, but never collected `changelog.d/` into a `CHANGELOG.md` section. `release.yml`'s `devops release check` then failed on the merge to `main`, as it did for v0.2.27 and v0.2.30, and a person collected the fragments by hand (#1260, #1474, #1491, #1517).

The governing decision is the owner's of 2026-10-09 (the issue's "Update 2026-10-09" section): the cut commit does it all. It bumps the version, collects `changelog.d/` into the version's `CHANGELOG.md` section, deletes the fragments and renders `docs/ROADMAP.md`, in one commit, before it opens the release pull request. A critical fix after the cut edits `CHANGELOG.md`'s version section directly in its own pull request, with no fragment and no `chore/open-vX.Y.Z-collate-<issue>` pull request. This replaces the 2026-10-08 re-scope to merge-time collection, and reverses #1103's 2026-10-03 rule that a cut commit never collects.

- **The cut** (`src/devops_cli/commands/release.py`, `cut_release`). On the prepared path, after it checks out the release tip, the cut plans the collection with `_plan_fragment_collection`, which reads and checks every fragment before any write; a bad fragment raises its `ValidationError` with the clone still clean. With no entries for `## [X.Y.Z]`, because there is no fragment or no `## [` heading to place one under, it raises a `ValidationError` (`ERRORS.release.cut_changelog_missing`) before it writes or pushes. The error names the version, the release branch, the missing section, both causes, and the completed items with no fragment, which `cut_release`'s new `missing_fragments` argument carries from the close plan (`Cut.missing_fragments`): `devops roadmap close` and the Service's close job (`roadmap/run.py`, `_run_close_adapter`) both pass it, since the Service logs this error and no plan. `devops release prepare --create-pr` has no plan, so its error points to `devops roadmap close --plan` instead. Otherwise it bumps the version and writes the collection with `_write_version_changelog`, which deletes the fragments; `_release_paths` already stages `CHANGELOG.md` and `changelog.d/`. With no fragment and a section already on the tip, as a re-cut finds it, `CHANGELOG.md` is kept as it is. `_update_changelog_header` is never called on the cut path, so no section is rebuilt from commit subjects. The dry-run block, `devops release pr` and the local `devops release prepare` are unchanged. The `--changelog/--no-changelog` help says that `--create-pr` always collects.
- **The plan** (`src/devops_cli/roadmap/close.py`). `CUT_FILES` gains `CHANGELOG.md`, and `--plan`, the confirmed run and the dry-run note say the cut collects the fragments into the version's section and deletes them. A completed item with no fragment is named with what to do: before the cut, add `changelog.d/<issue>.md` in a pull request into the release branch; after it, edit the version's section of `CHANGELOG.md` in a pull request.
- **Readiness** (`src/devops_cli/commands/pr.py`). For a pull request into `release/vX.Y.Z` that edits `CHANGELOG.md` in place, `_grounding_blockers` reads the branch's raw `CHANGELOG.md` at its tip (`gh api -H 'Accept: application/vnd.github.raw+json' repos/<repo>/contents/CHANGELOG.md?ref=release%2FvX.Y.Z`). When it holds a non-empty `## [X.Y.Z]` section, the cut has run and the edit is the critical-fix path, so `CHANGELOG.md` is not a release-file blocker. Without the section the existing blocker stands. A failed read is a blocker of its own (`MESSAGES.pr.grounding_changelog_unread`). After the cut, the blocker that remains for `docs/ROADMAP.md` gives no fragment to add instead (`grounding_release_files_fragment` is appended only before the cut), since the pull request's edit of the section is its entry. `docs/ROADMAP.md` is always left to the cut. No other pull request makes the read.
- **Docs.** `changelog.d/README.md`, RELEASE_CYCLE.md (Stage 1 item 6, and step 4 of "A Critical Fix While the Release PR Is Open"), AGENTS.md ("Changelog Fragments, Never the Shared Files"), CONTEXT.md ("Changelog fragment"), `docs/agent/tasks/README.md` rule 5, docs/ROUTINE_TASKS.md (step 1 of the release procedure), `.github/pull_request_template.md`, the constant comment above `CONST_RELEASE_SHARED_FILES`, `HELP.roadmap.close`, and the `pr check-readiness` help, with the generated `docs/commands/pr.md`, `docs/commands/gh.md`, `docs/commands/roadmap.md`, `docs/CLI_REFERENCE.md` and README.md's command table. The task files of #982, #743 and #1294 each carry a one-line note that #1450 supersedes their no-collection statements.

## Decisions and Deviations

- **"Naming the missing entries."** `--plan` names the completed items without a fragment, and so does the cut's error when its caller holds a close plan, as `devops roadmap close` and the Service's close job do. The cut fails only when there is neither a fragment nor a non-empty section, since a section with entries is what `release check` needs.
- **A re-cut keeps the tip's section.** After a release pull request closes unmerged, the tip already holds the section the first cut wrote and no fragment, so the re-cut passes with `CHANGELOG.md` unchanged. There is no fallback that builds a section from commit subjects.
- **The cut always collects.** `--no-changelog` affects only the local `devops release prepare`; the cut path, `release prepare --create-pr` included, ignored it before and still does, and the flag's help now says so.
- **The readiness read is narrow.** It runs only for a pull request into `release/vX.Y.Z` whose files include `CHANGELOG.md` with status `modified`, so other pull requests cost no request. Removing or renaming `CHANGELOG.md` is never a critical fix's edit and stays blocked without a read. It reads the branch by name, the tip now, because the pull request's base commit can predate the cut, and with the raw media type, because `CHANGELOG.md` is about 480 KB and grows each release, and the JSON contents API returns no content above 1 MB.
- **One blocker per failure.** A failed read is its own blocker, and `CHANGELOG.md` is then left out of the release-file blocker, as the grounding checks keep one blocker per cause.
- **The cut's date in the tests.** The cut tests take the date before the cut and accept it or a later today, so a run across midnight UTC passes.
- **The ruleset-refusal test skips doc regeneration.** `test_release_cut_ruleset_refusal_raises_typed_error` ran `DocGenerator.write_all_docs` twice (about 3 s); it now passes `sync_docs=False` and `--no-sync-docs`, as the other cut tests do.
