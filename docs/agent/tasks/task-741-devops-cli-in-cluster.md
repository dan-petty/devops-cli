# Task: devops-cli in the cluster, and every cluster Secret from the keyring (#741)

## Description
devops-cli runs in the homelab cluster as Jobs made from a suspended CronJob in namespace `devops`, so agents drive it with kubectl and never handle keys, and model calls reach the gateway without the tunnel's edge timeout. Every Secret the stacks read comes from the workstation keyring through one table (`src/devops_cli/k8s/cluster_secrets.py`) and one command, `devops k8s push-secrets`, which `devops k8s deploy-stack` runs before applying anything. It replaces the hand-run `--from-literal` steps and deploy-stack's client-side Qdrant Secret apply, which leaked the key into the last-applied annotation.

## Decisions and deviations
- Image tag during a cycle: `devops release check` holds `newTag` equal to the version at the cut; the gate test only requires a release tag no newer than the version. Opening a cycle (which bumps only `pyproject.toml`) therefore needs no tag change, and between cuts the CronJob keeps naming the last published image instead of one that does not exist yet. For the owner to confirm.
- A missing namespace: the criterion stubs `kubectl get namespace devops` as failing; the push reads it with `--ignore-not-found`, so absence is empty output, while a failing kubectl exits 1 rather than reading as absent (safer: an unreachable cluster never skips a Secret).
- Live values are read by the push's own `kubectl get secret -o json` (`_fetch_live`), not `fetch_secret_data`: that helper returns `{}` on any kubectl failure, which would make the push generate over a live value, and it returns neither annotations nor `managedFields`.
- `deploy-stack --dry-run` runs nothing, so it lists the `devops` rows as "(if namespace devops exists)" rather than asking the cluster. Its preview stays a summary (releases, manifests, Secrets and key names), not the ordered command list the dry-run rule asks for; listing deploy-stack's Helm and kubectl commands in order is #412's work for every delegated command.
- Dry run and plan (owner, 2026-10-04): `--dry-run` makes no request, reads included, and wins over `--plan`; the read-only preview that `push-secrets --dry-run` used to be is `--plan`, which says in its output that it read the keyring and the cluster. A placeholder stands for every value a dry run would need a read for, and the Job name, chosen when a run creates the Job, is `<devops-cli-yyyymmdd-hhmmss-xxxx>`.
- The push names Secrets as `secret/NAME` in kubectl's argv (`kubectl get secret/NAME`, `kubectl annotate secret/NAME`), and runs `gh auth token --user LOGIN --hostname github.com` with `--user` first: the output masker hides a word of 10 or more characters after "secret" or "token", which turned the printed `kubectl get secret llm-gateway-secrets` into `kubectl get secret <masked-token>` and `gh auth token --hostname` into `gh auth token <masked-token>`.
- A dry run exports no telemetry: the root callback clears the dry-run state for a command's own `--dry-run` (the command reads its flag itself), so the entry point records the invocation as a dry run and `OTelTelemetryClient._send_payload` sends nothing for it. This holds for every command's own `--dry-run`, not only this item's. The no-request guard still turns telemetry off to keep the tests fast, and `tests/cluster_secret_fakes.py` warms `platform.platform()` at import: the tracer's resource probe runs a local `uname -p` once per process, which a fake cluster patched in first would record (the `--plan` tests failed when run alone).
- One GitHub identity (#767, ADR 0002; rebased onto it 2026-10-04): the push no longer verifies the machine token with `GH_TOKEN=<token> gh api user`. Under #767's pin that child would have acted as the person's session token and silently checked the wrong account, and running it with the machine token would make the process a second GitHub identity. gh 2.102.0's `gh auth status --hostname github.com --json hosts` reports, per stored account, the `login` gh recorded for the token, its `tokenSource` (`keyring`) and the `state` of gh's own check of that token (`success`, `error` or `timeout`), so the push takes gh's record: the login must be listed with a keyring token whose state is `success`, then `gh auth token --user LOGIN --hostname github.com` reads it. That command reads gh's store for the named account even when GH_TOKEN is set (checked against a scratch `GH_CONFIG_DIR` offline). Both are `gh auth` commands, so they run outside the pin with the ambient tokens unchanged, and `run_subprocess(inject_gh_credentials=False)` is gone. gh's check is an authenticated `GET https://api.github.com/` per stored token (offline it is the request a `state: error` names), the one gh makes whenever the person runs `gh auth status`: it confirms GitHub accepts the token but does not read the token's login again, so the login is the one gh recorded when the account logged in. A token stored under the wrong login, which only hand-editing gh's store produces, would pass; the old `gh api user` check would have caught it, and that is the trade for keeping one identity. An ambient GH_TOKEN appears in the status as an account of its own (source `GH_TOKEN`), so the keyring entry of the login is chosen explicitly. The dry run lists two gh requests instead of three, and `--plan`, its help and k8s/README.md say gh's record is read.
- A locked keyring stops deploy-stack before the cluster check and `kubectl apply -k k8s/`, so bootstrap, the devcontainer auto-deploy and the MCP `k8s_deploy_stack` tool apply nothing while it is locked.
