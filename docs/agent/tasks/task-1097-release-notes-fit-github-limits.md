# Task: Release Notes Fit GitHub's Release and Pull Request Body Limits (#1097)

**Issue**: [#1097](https://github.com/dan-petty/devops-cli/issues/1097)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p0-critical
**Scope**: scope/release

## Description
`release.yml` publishes each GitHub Release with `devops release notes --raw -v <version>` as its body, falling back to `devops release changelog --raw`, and `devops release pr` puts the same notes in the release PR body. GitHub refuses a Release body over 125,000 characters and a PR body over 65,536. v0.2.25 collected 51 fragments into a `[0.2.25]` section of 196,525 characters and 210 entries, so the "Create GitHub Release" step would have failed and v0.2.25 would never have been published.

- **Limits** (`config/constants.py`). `CONST_GITHUB_RELEASE_BODY_MAX_CHARS` (125,000) and `CONST_GITHUB_PULL_REQUEST_BODY_MAX_CHARS` (65,536).
- **Reading entries** (`release/changelog_fragments.py`). `parse_changelog_entries(lines)` splits a category's lines, as `parse_changelog_categories` returns them, into `ChangelogEntry(title, details, block)`: a top-level list item's first paragraph is its title and the lines below it are its details. Any other top-level block, such as a heading or paragraph, is an entry with no details. `block` is the token type less `_open` (`list_item`, `paragraph`, `heading`, ...). The split comes from markdown-it-py's CommonMark tokens and their line maps, not from line prefixes. `find_changelog_section(changelog, version)` returns the section's heading line and body, using the same `_find_section` the cut uses, and `_extract_changelog_notes` now reads through it in place of its own copy of the regex. `changelog_heading_anchor(heading)` returns the id mdit-py-plugins' anchors plugin gives the heading. The plugin's default slug follows GitHub's, so `## [0.2.25] - 2026-10-03` becomes `0225---2026-10-03`.
- **Fitting** (`release/notes_compaction.py`). `fit_release_notes(notes, budget, full_notes)` returns notes that fit unchanged. Longer notes keep each `###` category and each entry's title, drop the details, and end with "Each entry's details are left out to fit GitHub's size limit. The full notes are in [`CHANGELOG.md` at v<version>](<url>)." The first sentence is left out when no entry had details. Consecutive list items stay one list, and any other block is set apart by a blank line, so a paragraph after an item does not run into it. If the titles still do not fit, `bisect_right` finds the most whole entries that fit with the line "Entries left out to fit: N." before the pointer. Later headings go with their entries, and the pointer is never cut. Notes the changelog parser refuses, such as the commit-log fallback's `### Changes in v<version>`, are grouped under their own headings, which go with their entries like categories and are not counted as entries.
- **Commands** (`commands/release.py`). `_release_body_notes` fits `devops release notes` (raw, panel and dry run) and `devops release sync-notes` to the Release limit, less the newline `--raw` adds. `devops release changelog --raw` fits its compiled notes the same way. `_build_release_pr_body` gives the notes whatever the PR limit leaves after the title, summary, deliverables and the `### Release Notes` heading. The link is `https://github.com/<owner>/<repo>/blob/v<version>/CHANGELOG.md#<anchor>`, with the repository from `sync-notes`' `--repo`, the git origin or `GITHUB_REPOSITORY`. If none is known, the pointer names `CHANGELOG.md` and the tag and has no URL. If the version has no section, the link has no anchor.
- **Dependencies** (`pyproject.toml`, `uv.lock`). `markdown-it-py==4.2.0` moves from the dev group to the runtime dependencies, and `mdit-py-plugins==0.6.1` is added. Both were already installed at runtime, through Rich and Textual, at these versions. `uv lock --offline` changed only the project's own dependency lists. They are imported only when notes are over a limit or an anchor is needed.
- **Docs**. `docs/ROUTINE_TASKS.md`'s publishing step says what a Release body holds when the notes are over the limit. The `release notes` and `release sync-notes` docstrings say the same, and `docs/commands/release.md` and `docs/CLI_REFERENCE.md` are regenerated from them.

## Measurements
- `[0.2.25]` on `origin/chore/cut-v0.2.25` (ac31d4d): 196,524 characters as extracted (196,525 with its final newline), 210 entries in 5 categories. `GITHUB_REPOSITORY=dan-petty/devops-cli uv run devops release notes --raw -v 0.2.25 --root <copy>` printed 22,780 characters, with 210 titles and 5 headings, ending with `https://github.com/dan-petty/devops-cli/blob/v0.2.25/CHANGELOG.md#0225---2026-10-03`, in 0.73 s for the whole command. `_build_release_pr_body` on the same copy, offline with no milestone deliverables, gave 22,910 characters in 0.33 s. All 40 sections of that `CHANGELOG.md` fit both limits. Only `[0.2.25]` is compacted. The largest earlier section is `[0.2.24]`, at 18,834 characters as extracted.
- The 210 title lines take 22,520 characters. That leaves about 43K of the PR limit for deliverables and about 102K of the Release limit. The compact form keeps only titles even where the budget could hold some details, which is what the issue specifies.
- Limits: GitHub's limits are measured here in Python characters (code points). The PR body's title, summary and deliverables are not shortened. If they alone exceeded 65,536 characters, the body would still be too long, which would take about 8,000 deliverables. The link points at tag `v<version>`, which exists only once the release PR merges, so in the release PR body it does not resolve until then.
