# Task: A Pull Request That Delivers Part of an Item Says Part of #N and Passes Readiness (#1617)

**Issue**: [#1617](https://github.com/dan-petty/devops-cli/issues/1617)
**Status**: Done
**Milestone**: v0.2.37
**Priority**: priority/p0-critical
**Scope**: scope/github
**Feasibility**: Read `_GROUNDING_CHECKS` and `_closes_one_issue` in `src/devops_cli/commands/pr.py` and `extract_linked_issues` in `src/devops_cli/github/issue_closure.py` at release/v0.2.37 (3dd7fa6): a body with no closing keyword was one `grounding_closes_no_issue` blocker, so every pull request of a multi-PR item but its last failed readiness. `devops roadmap close` (`src/devops_cli/roadmap/close.py`) reads only `extract_linked_issues`, so a new phrase leaves it unchanged.

## Description

Readiness let a pull request into a release branch through only if its body closed exactly one issue. On 2026-10-17 refinement planned nine items as several pull requests each (#983, #1107, #1151, #771, #1144, #1103, #1343, #1345, #1154), and every pull request before each item's last would have failed readiness. The owner chose a `Part of #N` line over a child issue per pull request.

- **Parser.** `extract_part_references(body, repo)` in `src/devops_cli/github/issue_closure.py` returns the issues a body delivers part of, once each and in order. It shares `strip_non_prose` and the cross-repository rule with `extract_linked_issues` through one `_references` scan. `strip_non_prose` reads the body with markdown-it-py's CommonMark parser and keeps the text of its paragraphs, headings and list items outside block quotes: code in any form (backtick and tilde fences, an unclosed fence, indented blocks, inline code) and raw HTML, such as the pull request template's comments, are dropped. The regular expressions it replaced skipped only backtick fences, inline code and `>` lines, so a closing keyword in a `~~~` block or an HTML comment closed an issue through `devops roadmap close`, and `Closes #704` over `<!-- Part of #705 -->` read as naming both. The phrase is `CONST_ISSUE_PART_PHRASE` (`"part of"`) in `src/devops_cli/config/constants.py`, matched case-insensitively with any whitespace between its words and an optional colon, as closing keywords are. `Part 1 of #N` is not the phrase.
- **Readiness.** `_Grounding` carries the body's part references beside the issues it closes, and its `issue` property is the one issue it is grounded on: the one it closes, or the one it delivers part of when it closes none. `_names_one_issue` (was `_closes_one_issue`) passes a body that names exactly one, and otherwise gives one blocker: a closing keyword together with a part reference (`grounding_closes_and_parts`), two or more part references (`grounding_several_parts`), several closed issues, or none (`grounding_closes_no_issue`, which now names `Part of #<issue>`). The task-file, release-file and release checks judge that issue. The issue is read (`_read_grounded_item`, was `_read_closed_item`) into a release branch, as before, and for a part pull request into any base; `_GroundedItem` (was `_ClosedItem`) holds its Release and state. An unread issue is its own check (`_item_was_read`), `_delivers_an_item_of_its_release` (was `_closes_an_item_of_its_release`) says "closes" or "delivers part of", and `_delivers_part_of_an_open_item` blocks a part of an item that is not open.
- **Close.** `devops roadmap close` is unchanged: a part reference is no closing keyword, so the item stays open until its last pull request, which closes it, merges.
- **Reprioritize.** `_Run.linked_pull_requests` in `src/devops_cli/roadmap/reprioritize.py` indexes each open or merged pull request by the issues it closes and those it delivers part of (`_delivered_issues`). An item delivered in parts stays In Progress across them, so its Status last changed when it started: a part pull request's updates and commits now count as its activity for the stall window, and a part pull request protects it from the trims, as a closing one does. Without this, a 14-day-old multi-PR item still busy with its parts was readied and moved to the next release part-way through, and every remaining part then failed readiness against the release its merged parts were already in.
- **Changelog fragment.** Only the pull request that closes an item adds `changelog.d/<issue>.md`; a part pull request adds none, so parts open at once never conflict on the name, and an item moved out of the release part-way publishes no entry under it. `AGENTS.md` (Changelog Fragments), `changelog.d/README.md`, the `changelog_fragments` module docstring, `docs/agent/tasks/README.md` rule 3 and the pull request template state it, and the release-file blocker for a part pull request says the pull request that closes the item adds its fragment (`grounding_release_files_part_fragment`).
- **Rules.** `AGENTS.md` (the PR closing-keywords bullet and both author-as-merged rules), `docs/ROUTINE_TASKS.md` (Zero Disconnected PRs), `docs/agent/tasks/README.md` (rule 3 and the In Progress state), `.github/pull_request_template.md` and the `devops pr check-readiness` docstring, with the generated docs, describe the multi-PR delivery. The docstring's part paragraph stands apart from the grounding paragraph that #1344 rewrites, so the two changes merge cleanly. A part pull request's task file may read `**Status**: In Progress`; the pull request that closes the item sets `Done`. `task-740` and `task-1294` name `_delivers_an_item_of_its_release`. The grounding section's opening comment in `src/devops_cli/config/constants.py` is left as it is, since #1344 rewrites the lines right below it; the `CONST_ISSUE_PART_PHRASE` comment above it states the exception.
