# Task: The metrics job walks its own clone's release tags, and intake stops on an unusable labels.yml before any model call (#1358)

**Issue**: [#1358](https://github.com/dan-petty/devops-cli/issues/1358)
**Status**: Done
**Milestone**: v0.2.29
**Priority**: priority/p2-medium
**Scope**: type/bug, scope/telemetry, scope/github

## Description

Two defects in the roadmap Service (`devops serve --service`).

- **The metrics job read the pod's working directory.** The `metrics` row of `DEFAULT_DUE_TABLE` did not set `needs_clone`, and `_run_metrics_adapter` dropped the `clone_path` the executor passes, calling `collect_project_metrics_report` with no `root`. The report then walked the tags of `find_worktree_root()` from the current directory, which in the pod is `WORKDIR /home/devops`, no git repository. Every run logged `Failed to inspect git tags` (71 lines in the 3 hours before 2026-10-08 ~12:35 UTC) and `devops_cli_project_releases_total` read 0 for every repository. Locally, `find_worktree_root` climbs past a clone kept under `.data/` inside a workspace checkout and returns the outer checkout (the known limit tracked in #617), so passing the clone was not enough on its own.
- **Intake read `.github/labels.yml` late and reported a missing file as GitHub's error.** `_Run.types` turned only YAML and label-spec errors into a `ConfigurationError`; a missing file raised the store's `GitHubFileNotFoundError`, and a file with no `type/*` label passed, after which every proposal was rejected. The file was first read inside `_decide`, after the candidates' timeline reads and the embedding call.

The change:

- **Metrics.** The `metrics` row has `needs_clone=True`, so the job runs in the repository's clone under `<data dir>/roadmap/<owner>/<name>/clone`, as `close` and `refine` do; `build_stub_table`'s `metrics` row follows its `needs_clone` argument. `_run_metrics_adapter` passes its clone to `collect_project_metrics_report` as `root`. That function walks `root` as given and calls `find_worktree_root()` only when `root` is None, which keeps `devops gh metrics` unchanged. A clone that can't be prepared fails the job, as it fails `close` and `refine`.
- **No fallback to the working directory.** `_run_metrics_adapter` and `_run_refine_adapter` take their clone through `_job_clone`, which raises `GitOperationError` naming the job and `needs_clone` when the executor gives none, so a table row that runs either without a clone fails the job instead of reading the working directory. Refine's `clone_path or Path.cwd()` was the same one-line fallback in the same file.
- **Intake.** `plan_intake` and `intake_candidate` take the repository (`repo`), which `_Run` holds; the CLI passes its resolved `--repo` and the Service's intake adapter the repository the executor runs. `_Planner.decide_all` reads `self.run.types` first when the run has a candidate, before `_checked` (timeline reads) and `_embed`; a run with no candidate reads nothing more. `_Run.types` raises `ConfigurationError(details={"path": ".github/labels.yml"})` naming the repository, the file and the ref for a missing file (chained to the store's `GitHubFileNotFoundError`), for a file that declares no `type/*` label other than `type/epic`, and for a file that is no label specs. The first two say the file must declare the `type/*` labels intake may assign. Any other failed read propagates as the store raised it (`GitHubOperationError`). The texts live in `lang/en/messages.py`.
- **Dry run.** `_Steps.decisions` lists the `labels` read first, before the timeline reads and the embedding call. Over the open issues it carries the condition "the run has a candidate"; for a `--title` candidate, which always is one, it carries none.

## Decisions and deviations

- **One pull request closes #1358**, carrying both the metrics and the intake criteria. The issue's option of two pull requests, the first without a closing keyword, is dropped: each item PR closes exactly one issue and changes its task file.
- **The run carries its repository.** `plan_intake` and `intake_candidate` take `repo` as a required keyword, as `plan_migration` does, rather than reading it from the store; the `RoadmapStore` protocol is unchanged. Every error `.github/labels.yml` causes names it, in the Service as on the command line.
- **Live check (c) is skipped:** all eight repositories the Service manages have `.github/labels.yml` with nine `type/*` labels (contents API, 2026-10-08), so none can show the error. Defect 2 is latent there; the fix keeps intake failing closed for the next repository onboarded without the file.
- **Failing closed on the reads stays with #974.** A clone that can't be prepared, or a row that gives none, now fails the metrics job, while a failed tag read, a REST read that warns and drops, a failed collection and a failed status read keep their warnings; the status probes' try blocks are unchanged. Making those reads fail closed, and a `repo` label on every project instrument, are the extensions the issue proposes for #974.
- **The clone check reuses `test_checkouts_git_management`** rather than a near-duplicate test: its failure half already sends the milestones webhook that makes `reprioritize` due, so a `metrics` stub there is the whole check.
- **The metrics run test asserts no WARNING record at all**, which also shows the process-edge fake answered every `gh` read the adapter makes; the adapter and the REST readers would otherwise swallow a missed one. The warning test drives a collection failure from the edge: a milestone whose `open_issues` is null fails the count outside the reader's own `try`.
- **The metrics run test reuses `_make_bare_remote`** and tags the commit it pushes. With only the `metrics` row in the table and no change in the round, the run looks up no current release, so `ensure_checkout` clones the default branch and checks out no release branch, before or after #1366's default-branch rule; tags don't depend on the branch.
- **`GitHubFake` is the shared `gh` fake at the process edge (#1307):** it now answers `gh api user`, `gh api rate_limit` (a full quota resetting in a minute), the repository, its Actions runs and its traffic, takes an `(exit code, output)` for a file, and `GitHubFake.process` stands in for `subprocess.run`: it answers a `gh` argv given as a list or a tuple, raises `CalledProcessError` for a failed answer under `check=True`, and passes every other program to the real one. `test_collect_project_metrics_report` used it too: it had been starting the real `gh` (five `gh api rate_limit` calls to GitHub with the test token).
- **The existing label-spec error text moved to `lang/en/messages.py`** with the two new ones, as all three are raised by the same property, and now names the repository as well.
