# Task: Review tools install from a tools lock with exact versions, binary checksums and hashed Python requirements (#1142)

**Issue**: [#1142](https://github.com/dan-petty/devops-cli/issues/1142)
**Status**: Done
**Milestone**: v0.2.30
**Priority**: priority/p1-high
**Scope**: type/feature, scope/security, scope/review

## Description

`devops install-tools` installed each tool at whatever release was latest when it ran. It checked kubectl, kustomize, helm and the Argo CLIs against checksum files fetched beside them, installed trivy, popeye, pluto and k9s with only a warning when their checksum file could not be fetched, and installed kube-linter unverified. Post-create added a Semgrep of its own with `uv tool install semgrep`, which pins one of Semgrep's 66 distributions at most and has no `--require-hashes`. A review recorded none of the versions it ran, and nothing noticed when devops-cli's own checkout changed under a running review.

The fix:

- **The lock** (`src/devops_cli/tools_lock/`, package data). `tools.lock` (TOML) names each tool's exact version, description and source. A binary tool (`[binary.<name>]`: kubectl, kustomize, helm, argo, argocd, kubectl-argo-rollouts, trivy, kube-linter, popeye, pluto, k9s, gitleaks 8.30.1 and osv-scanner 2.6.0) lists, for linux and darwin on amd64 and arm64, the URL of its build, the build's SHA-256 and, for a tar.gz, the member that is the tool. Each SHA-256 is the release asset's GitHub `digest`, checked against the publisher's checksum file where it has one; popeye, helm and kubectl, whose builds have no digest, take it from the publisher's `checksums.sha256`, `.sha256sum` and `.sha256` files. A Python tool (`[python.<name>]`: Semgrep 1.179.0 and Bandit 1.9.4, the project's own dev pin) names a requirements file written by `uv pip compile --universal --generate-hashes --python-version 3.14`, with every distribution hashed. The lock's header gives the bump procedure. `load_tools_lock()` reads it into pydantic models that refuse unknown fields, `tools_lock_digest()` is the 16-hex digest of the lock and its requirements files in the form of the prompt digest, and `tool_install_dir(name, version)` is `~/.local/share/devops-cli/tools/<name>/<version>`.
- **`devops install-tools` installs only from the lock** (`commands/install_tools.py`). `install_binary` stages in a directory beside the version directory, downloads the lock's URL alone, refuses a build whose SHA-256 differs (`ChecksumMismatchError` naming the tool), unpacks it by format (binary, gzip or tar.gz: the lock's member, copied from the verified archive), renames the stage into the version directory and links the command from the target directory with one rename, which replaces any file or link there. Once a tool's commands link to its locked version, its other version directories are removed. `install_python_tool` runs `uv --no-config venv --relocatable --python 3.14 <stage>` and `uv --no-config pip sync --require-hashes -p <stage>/bin/python <requirements>`, so no `uv.toml` or `[tool.uv]` in the current directory changes the install, keeping `UV_MALWARE_CHECK`, `UV_CACHE_DIR` and `UV_LINK_MODE` from the environment; it renames the environment into place and links its entry points, and a failure removes the stage and reports uv's reason. `devops install-tools` exits 1 when any tool did not install. A platform missing from the lock fails before any request, naming the tool and the platform. A tool is at its pin when each of its commands in the target directory resolves to its version directory: `--only-missing` installs the others, the new `--check` lists them and exits 1, and `status` shows Tool, Description, Pinned and Installed (at pin, the other path PATH finds, or not installed) with no request. Latest-release resolution (`_gh_latest`, `_latest_kubectl`), the per-tool installers, checksum-file parsing and fallbacks, the `Tool` registry, `is_tool_installed`, the version regex and the `--version` option are gone, with `validate_version_str` and the six per-tool download URL constants.
- **Post-create** (`commands/devcontainer.py`) no longer runs `uv tool install semgrep`: `install_managed_tools` installs the locked Semgrep with the other tools, so only one Semgrep is on PATH. `semgrep` runs the `pysemgrep` it finds on PATH, so the lock links both entry points; with `semgrep` alone, a container that had the `uv tool` Semgrep 1.178.0 ran the locked `semgrep` and reported 1.178.0 from the old `pysemgrep`.
- **Review inputs** (`ai/review/profile.py`, `core/repo.py`). A profiler stores `tools_lock_digest()` and `own_source_state()` when the review starts. The digest names the pins the review's tools had in the lock, not the versions on PATH; recording whether each tool was at its pin would be a follow-up. `own_source_state()` is `(HEAD, SHA-256 of git diff HEAD)` of the checkout holding devops-cli's source, or None for an installed copy or one outside a checkout, so a further edit to an already modified file counts and an untracked file does not. `profile.json` gains `tools_lock_digest` and `code_changed_during_run`, which `build()` sets when the state differs from the start's, and `_write_review_profile` prints a warning then. This is #1050's own-code check, which its owner comment moved here.
- **Tests** mirror the source tree: `tests/test_tools_lock.py`, `tests/test_install_tools.py` (rewritten), `tests/test_core_repo.py`, and cases in `tests/test_review_profile.py`, `tests/test_devcontainer.py` and `tests/test_validation.py`. The shared fixture `isolate_user_data_root` also isolates the tools lock's data root, and `StubWeb.content` serves raw bytes, so archives are served through httpx2's transport rather than by patching `_download`.

## Acceptance Criteria

- [x] `tools.lock` holds each tool's name, exact version and source URL and, for binaries, a SHA-256 per platform, with gitleaks 8.30.1, osv-scanner 2.6.0, Semgrep 1.179.0, kube-linter 0.8.3, pluto, trivy and Bandit pinned: `test_the_packaged_lock_holds_every_tool_install_tools_installs` and `test_every_binary_build_is_an_https_url_with_a_sha256`.
- [x] Each Python tool has a hashed requirements file that pins it, installed with `uv pip sync --require-hashes` into its own virtual environment under the user data root: `test_every_python_tool_pins_itself_in_its_hashed_requirements`, `test_a_python_tool_installs_its_hashed_requirements_into_a_relocatable_venv` (with `--no-config`) and `test_a_failed_python_install_leaves_no_stage_and_no_link`; a pin bump removes the earlier version (`test_an_install_removes_the_tools_other_versions`); the locked Bandit is the project's dev pin (`test_the_locked_bandit_is_the_projects_own_dev_bandit`).
- [x] `devops install-tools` installs only from the lock, verifies every checksum and refuses a mismatch: `test_a_verified_binary_is_pinned_and_linked_from_its_url_alone` (the lock's URL is the only request), `test_a_build_whose_bytes_differ_from_the_lock_is_refused`, `test_install_tools_exits_1_when_it_refuses_a_build`, `test_each_archive_format_unpacks_to_the_tool`, `test_a_platform_the_lock_has_no_build_for_is_named` and `test_version_is_no_longer_an_option`.
