# Task: Loki Admits Only the Collector from `otel`, and Persona Exemplars Come from the Review's Target (#1100)

**Scope**: scope/security

## Description
The Copilot review of release PR #1089 left two threads, and the release cannot merge with either unresolved.

- **Loki ingress** (`k8s/logging/networkpolicy.yaml`). The 3100 rule's `otel` peer was namespace-only, and Loki runs with `auth_enabled: false`, so Jaeger, or any workload later deployed to `otel`, could push and query logs. The `otel` namespace's own egress rule admits every pod to `logging:3100`, so this ingress rule is the only gate. The peer now combines `namespaceSelector` (`kubernetes.io/metadata.name: otel`) with `podSelector` on the collector release's labels (`app.kubernetes.io/name: opentelemetry-collector`, `app.kubernetes.io/instance: otel-collector`), with `ports` in the same rule. `k8s/cloudflared/networkpolicy.yaml` records that kube-router refused a combined peer with `ports` on egress, so the shape was proven live on ingress before the change (Measurements), and a comment in the policy says so.
- **Exemplar target** (`ai/review/classification.py`, `ai/review/common_hallucinations.py`, `ai/review/runner.py`, `ai/review/pipeline.py`). `_persona_system_prompt(persona, agents_md, target)` and `render_negative_exemplars(target, ...)` take the target as a required argument and no longer fall back to the working directory. `_execute_review_workflow`, `ReviewPipelineOrchestrator`, `_run_persona_loop` and `_run_review` take a required keyword-only `target_dir`, and `run_pre_analysis_refresh` a required one, so a new caller that leaves the target out fails to type-check rather than showing the working directory's judged claims. `_execute_review_workflow` passes its `target_dir` to the persona loop, the fallback path when the analysis client is not an `LLMClient`.
- **Analysis metadata target** (`ai/review/runner.py`). `--summary` and the persona loop (`_load_shared_metadata_for_pages`, `_prepare_review_metadata`, `_execute_findings_validation`) found the repository to load file analysis metadata from with `find_repo_root(Path.cwd())`; they now use the review's `target_dir`.

## Measurements
- **Probe.** Two throwaway namespaces labelled `app.kubernetes.io/part-of=np-probe`: a busybox `httpd` on 8080 in the destination, on the node Loki runs on, and four clients in the source, one labelled `app.kubernetes.io/name=probe-allowed` and one unlabelled on that node, and the same pair on another node. Without a policy all four connected. With a default-deny ingress policy none did. With the candidate added (`podSelector: {}`, an intra-namespace rule, and a rule whose peer combines `namespaceSelector` on the source namespace with `podSelector` on `probe-allowed`, `ports: [8080/TCP]`), both labelled clients connected and both unlabelled clients were refused, on either node. A second listener on 8081 refused the labelled clients, so the port restriction is enforced too. The namespaces were deleted.
- **Live check.** Before the apply, an unlabelled throwaway pod in `otel` reached `loki.logging:3100/ready`. After it, that pod was refused, and an OTLP log record sent to the collector's 4318 arrived in Loki under its `service_name`, as one sent before the apply had. The pod was deleted. The two marker records (`service_name="np-probe-1100"`) stay in Loki until retention removes them.
