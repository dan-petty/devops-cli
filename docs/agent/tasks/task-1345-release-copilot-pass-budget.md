## Description

A release pull request gets `release_copilot_passes` Copilot passes, read from `.github/roadmap.toml` on the default branch, and once they are spent the stop rule in `RELEASE_CYCLE.md` Step 3 decides which remaining comments block the release. It is delivered as two pull requests, in the order of the plan on the issue.

**The budget, `devops pr copilot-pass` and the stop rule (PR 1).**

- **Budget.** `RoadmapConfig.release_copilot_passes` (`ge=1`) defaults to `DEFAULT_ROADMAP_RELEASE_COPILOT_PASSES`, 2, and `.github/roadmap.toml` lists the key, commented, with the other defaults. A value below 1 or a misspelt key fails, naming the key.
- **Identity.** A review is Copilot's only when its author's login is exactly one of `CONST_COPILOT_REVIEWER_LOGINS`: `copilot-pull-request-reviewer[bot]` (REST) or `copilot-pull-request-reviewer` (GraphQL). `is_copilot_login` and `is_copilot_review` (`src/devops_cli/github/pr_monitor.py`) replace `_is_copilot_review_dict`, which matched "copilot" anywhere in a login, for review records only. The issue timeline names the same account `Copilot`, type Bot, a login the Copilot coding agent shares, so a timeline `reviewed` event ends Copilot's pass only when its `id` is the id of one of Copilot's reviews (`_copilot_review_ids`), never by login and never by the account id alone. A review request names Copilot when its `requested_reviewer` is a Bot whose `html_url` path is `/apps/copilot-pull-request-reviewer` (`CONST_COPILOT_REVIEWER_APP_SLUG`). A review Copilot submits between the reviews read and the timeline read reads as running for that one read; the budget still counts it once, and the monitor sees it end on its next poll. The timeline readers return `_CopilotTimeline` (working, event, requested, error), and `_resolve_timeline_query`, which only tolerated stand-ins returning two values, is gone. A person whose login contains "copilot" is now a person: their approval counts toward the review decision, and their review neither sets Copilot's state nor ends a pass Copilot is running.
- **Counting and requesting.** `src/devops_cli/github/copilot_budget.py` counts a pull request's passes (`CopilotPasses`: each Copilot review submitted, whoever asked for it, and one running or requested and not yet started, which `_detect_copilot_status` reads from the timeline as `is_active` and `pass_requested`) against the budget. A pending request counts because Copilot starts up to a minute after it; the monitor never waits on one, since Copilot may never take it up. `request_copilot_pass` reads the pull request, refuses one that is merged or closed and any but the release pull request, reads the budget, the reviews and the timeline, refuses once the passes are spent, and only then runs `gh pr edit <n> --add-reviewer @copilot --repo <owner/repo>` through `run_gh`. Nothing is stored, so each release pull request starts with the whole budget. A refusal raises `CopilotPassRefusedError` (`COPILOT_PASS_REFUSED`, details bounded), having requested nothing. Reviews or a timeline that can't be read raise the read error, since the passes are then unknown.
- **Command.** `devops pr copilot-pass [<number>] [--repo OWNER/REPO] [--dry-run]` prints `Requested Copilot pass N of M on PR #<n>.`, or the refusal and exits 1: `Copilot budget spent: N of M passes on PR #<n>, ...` once the passes are spent. Without a number it acts on the current branch's pull request. `--dry-run`, or an exported dry run, makes no request and lists the requests a real run would make, each under its condition (#412). Each gh command in it is built by the builder the real run uses: `branch_pr_rest_argv`, `branch_pr_view_argv` and `pr_details_argv` (`pr_monitor.py`), `repository_file_args` and `copilot_pass_argv`. The command is excluded from the MCP tools, since a person requests passes.
- **One path.** `rg -n '@copilot' src` finds only `copilot_budget.py` and `CONST_GH_COPILOT_REVIEWER`. `devops release` requests no pass, and `devops pr edit` has no reviewer option.
- **Release pull request.** `_is_release_pr` and the branch helpers it reads (`_same_repository`, `_branch_ref`, `_default_branch`) move from `src/devops_cli/commands/pr.py` to `src/devops_cli/github/pr_branches.py` as `is_release_pr`, `same_repository`, `branch_ref` and `default_branch`, so the budget module, below the commands layer, refuses exactly what grounding exempts.
- **Policy.** `RELEASE_CYCLE.md` Step 3 states the budget, the command and the stop rule: once the budget is spent, a remaining Copilot comment blocks the release only if it is a regression the release introduces, and every other one becomes a follow-up issue whose thread is replied to and resolved. ADR 0004's decision and `docs/SDLC.md` say a re-review of the release pull request goes through `devops pr copilot-pass` within the budget.
- **The monitor's gate is unchanged.** The plan also had a spent budget lift Copilot's changes-recommended state in `devops pr monitor`. It is not added: `_build_changes_status` already reports that state as completed once no thread is unresolved, and while a thread is unresolved the thread blocks on its own. Filing or fixing the remaining threads and resolving them clears Copilot's state with no further pass, so the change would alter only the monitor's message and its early exit, never whether it passes.

**Review threads as follow-up issues (PR 2).**

- **Command.** A person runs `devops pr threads file-issues <pr> [--repo OWNER/REPO] [--keep <thread-id>]... [--confirm] [--dry-run]`, the step of the stop rule that files the remaining threads. It reads the pull request and refuses one that is merged or closed, or is not the release pull request (`ThreadFilingRefusedError`, `THREAD_FILING_REFUSED`), before reading its threads; that refusal is `require_open_release_pr` in `src/devops_cli/github/pr_branches.py`, which `devops pr copilot-pass` now shares, each command passing its own error and words, and both read the pull request through `pr_monitor.fetch_pr_details`, no longer private. `--keep`, repeatable, leaves a thread open for a regression the release fixes; an id that names no unresolved thread stops the run before any write, with or without `--confirm`, since the thread it meant to keep would be filed and resolved. Without `--confirm` it makes the same reads and prints what it would do with each thread, the kept ones included, writing nothing. Each thread is printed as it is done, so a run that fails part-way has named what it filed. `--dry-run`, or an exported dry run, makes no request and lists the requests a real run makes, each gh command built by the builder the real run uses (`pr_details_argv`, `review_threads_args`, `thread_comments_args`, `viewer_args`, the store's own plan of its issue listing, `StoreRequests.issues`, which gives the session's `GET`, `create_issue_args`, `reply_thread_args`, `resolve_thread_args`). The command is excluded from the MCP tools, since a person runs it.
- **Filing.** `src/devops_cli/github/review_thread_issues.py` files each unresolved thread not kept through `RoadmapStore.create_issue`, with no milestone, labelled `source/agent` only when Copilot started the thread (`is_copilot_login` on its first comment's author), since the label says a model wrote the text; then it replies in the thread `Filed as #N, ...` ending with the line `<!-- devops-cli: filed as #N -->` (`CONST_PR_THREAD_FILED_MARKER`), then resolves it, one thread after another. No model is called; `devops roadmap intake` places the issues later.
- **A rerun opens no second issue.** The marker counts only as a whole line of a reply the account running the command wrote, read once through GraphQL's `viewer`, never in the thread's first comment or anyone else's reply, so a suggestion quoting the marker or another person's reply cannot resolve a thread; a thread whose reply from that account holds it is only resolved, naming its issue. A thread with no such reply is first matched against the open issues the store lists, read once a run through the GitHub session, as every store listing is since #983, so a page that is not a listing stops the run before any write instead of reading as its end: one whose body ends a line with the link to the thread's first comment is the issue a run opened before its reply failed, so the thread gets the reply naming it and is resolved. A failed reply or resolve stops the run with an error naming the thread and the issue already opened. A failed issue stops the run before that thread's reply.
- **The issue.** Title `chore(review): follow up <path>:<line> from #<pr>`, the line being the one the thread was opened on (`originalLine`) once a later push moved it out of the diff, and for a thread on a whole file, which has neither, `<path>, comment <first comment id>`, so two such threads on one file get different titles. The body quotes the thread's comments, each under its author, `ghost` for a deleted account, inside a backtick fence longer than any run of backticks in them, so no `@name` notifies and no `#N` links, cut at `DEFAULT_PR_THREAD_ISSUE_TEXT_CHARS` (4000) characters; then the location and the link to the thread's first comment, its GraphQL `url`. An outdated thread is marked so in every line the command prints for it, since a later push may have dealt with it.
- **The GraphQL calls.** `pr_threads.py` builds every call's arguments through `graphql_args`: the thread listing, which now also selects `isOutdated`, `originalLine` and the comments' `pageInfo`, and reads a thread's comments past its first 50 by cursor (`thread_comments_args`); the viewer's login (`viewer_args`, `read_viewer_login`); and the reply and the resolve. The dry-run plan shares those builders. The filing lives apart from `pr_threads.py` because it reads the pull request through `pr_monitor.py`, which imports `pr_threads.py`.
- **The tests' stand-in.** `tests/test_github_pr_threads.py` holds every thread and comment in the shape GitHub's schema gives it and answers each GraphQL query with only the fields the query selects, read with graphql-core's parser, so a query that stopped selecting `url` fails the link and rerun tests; a reply that GitHub's rate limit refuses makes gh exit 1 naming it. Each run opens the GitHub roadmap store, whose gh commands the stand-in answers, the issue it opens in the shape GitHub's REST API returns from a recorded one, and whose issue listing goes through the GitHub session: `RunnerSession` asks the stand-in for it, and the tests of the single read, a bad page and the dry run read it through the real session over the `github_api` fake.
- **Policy.** `RELEASE_CYCLE.md` Step 3's stop rule says a person runs the command, previewing first with the same `--keep` flags, names the refusal of an unknown `--keep` id and of a merged or closed release pull request, and says how a rerun opens no second issue.
