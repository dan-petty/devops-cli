# Task: A shipped release starts the next one without a person (#1360)

**Issue**: [#1360](https://github.com/dan-petty/devops-cli/issues/1360)
**Status**: Done
**Milestone**: v0.2.29
**Priority**: priority/p1-high
**Scope**: type/bug, scope/roadmap

## Description

v0.2.28 shipped on 2026-10-07 and the roadmap Service did not start v0.2.29; a person did, about an hour later. Two causes:

1. The GitHub store's poll read only issue events, so it never saw a ship. The only ship signal was the milestone webhook hint, held in the worker's memory, and the release rollout restarted the Service minutes after the ship and dropped it. The Service also judged reprioritize with its own predicate, not the tested `reprioritize.is_due`, so the daily stall check never ran by itself.
2. Intake ran first and decided every candidate, one model call each, so after a burst of new issues close, reprioritize and the 15-minute metrics row waited behind 40 to 77 minutes of model work.

The fix:

- **The poll reports release changes.** `GitHubRoadmapStore.changes_since` (`src/devops_cli/roadmap/github_store.py:1474`) also reads the pull requests by last update and the GitHub Releases, REST only and newest first, each up to the first full page that reaches back past the cutoff (`_read_listing`, `:2393`). A release pull request (`cuts_its_release`, `src/devops_cli/roadmap/store.py:616`, by the existing `is_release_pull_request` rule, `:599`) opened since the cutoff is a `RELEASE_CUT` naming its opener, and one closed unmerged a `RELEASE_UNCUT`. A non-draft GitHub Release published since the cutoff whose tag names a Release is a `RELEASE_SHIPPED` (`_ships_since`, `:2364`); every entry of a page is judged by `published_at`, because the listing is ordered by the tag's time, which can be seconds earlier. The default branch comes from the listing (`base.repo.default_branch`), so no GraphQL is sent, and a release change carries no job record, so a poll whose changes are all release changes or the Service's own reads no board (`_with_job_records`, `:1943`).
- **A ship is never the Service's own change.** A ship and an un-cut carry no actor in both stores (the in-memory store's `publish_release`, `src/devops_cli/roadmap/memory_store.py:425`), so `except_actor` never drops one; a cut names its opener in both.
- **No change kind without a producer.** `ChangeKind.RELEASE_STARTED` is removed; the `ChangeKind` docstring (`src/devops_cli/roadmap/store.py:101`) and the contract suite's docstring say which kinds the GitHub adapter reports.
- **One due rule.** `reprioritize.is_due` (`src/devops_cli/roadmap/reprioritize.py:2398`) takes the current release: an item change counts only in it; the release kinds and the stall check count as before, and the rule reads nothing from the store. The reprioritize row's rule (`_reprioritize_due`, `src/devops_cli/roadmap/run.py:358`) passes it the changes since the row's own last success, that success as the stall check's start, and the current release. `_reprioritize_change_predicate` is deleted, so a change outside the current release no longer costs an `issues/N` read.
- **Hints in the table.** `CONST_ROADMAP_REPRIORITIZE_BATCH_KEYS` (`src/devops_cli/config/constants.py:2522`) is `milestone` `closed` and `release` `published`, the reprioritize row uses it, and `_batch_matches` (`run.py:677`) has no per-job case.
- **Order.** `DEFAULT_DUE_TABLE` (`run.py:614`) and `build_stub_table` (`run.py:653`, now built from the table, so the metrics row keeps its clone) run close, reprioritize and metrics before intake and refine.
- **Intake is capped and still makes progress.** A round of the Service's intake (`_run_intake_adapter`, `run.py:407`) decides at most `DEFAULT_ROADMAP_INTAKE_LIMIT` = 5 candidates (`src/devops_cli/config/defaults.py:821`): never-decided or since-edited candidates first, oldest first, then the others, longest waiting first (`_queue`, `src/devops_cli/roadmap/intake.py:687`), after the early `labels.yml` read. Its record (`IntakeRecord`, `intake.py:469`) is `intake.json` beside `schedule.json`: each candidate it decided that is still one, by number, with the issue's `updated_at` (new on `IssueRecord`, `store.py:334`) and when it was decided, and whether a fresh candidate is left, which makes intake due at the next poll (`_intake_due`, `run.py:347`). The record is written before any placement, so intake keeps the round's skips and folds when a placement raises, and a candidate whose placement raised is decided again after the fresh ones. A record that can't be read makes intake due, and its run raises naming the file and the remedy, to remove or repair it (`read_intake_record`, `run.py:186`).
- **The early return respects every rule.** `run_due_jobs` (`run.py:860`) judges each row on no changes before it reads any, so a reprioritize due only by the stall check and an intake left with fresh candidates run even when no trigger and no interval is due.
- **`devops roadmap intake --limit N`** decides the N oldest candidates and lists those it left; it keeps no record. Without it intake decides every candidate, and `--dry-run --limit` still makes no request, its per-candidate steps naming the limit.

## Decisions and Deviations

- **Actors on release changes.** A ship and an un-cut carry no actor in both stores, rather than the Release's author (github-actions[bot]): the listings name no closer, a job never publishes a Release, and a ship dropped as the Service's own is this incident. A cut names its opener, so the Service's own cut stays its own.
- **The releases listing is judged by `published_at`, page by page.** `created_at`, its order, is the tag's time: v0.2.28's tag was created 10 s before it was published. A Release for an older tag published much later can still fall past the page the read stops at; the stall check and the hints cover it, because reprioritize reads a ship from state.
- **One pager, smaller pages.** The newest-first stop is an optional `ends` rule on the store's existing `_read_listing`, which every REST listing already uses, not a second pager. The pull request and GitHub Release listings are read `DEFAULT_ROADMAP_POLL_LISTING_PER_PAGE` = 20 at a time: at 100 a page they were about 2 MB and 0.4 MB a poll, and a poll needs the newest few; a deeper window reads more pages.
- **The milestones are read twice when a poll finds a ship**: once to name the shipped Release (`_ships_since`) and once for the current release (`run_due_jobs`). Reusing the first read would need a releases cache the jobs' own milestone writes invalidate, so it is left as is: one REST listing, only on a ship.
- **The record is written before the placements.** Intake keeps the round's skips and folds when a placement raises, and a candidate whose placement raised before any write is decided again after the fresh ones. One that raised after a write (its label) counts as edited at the next round only, since the retry writes nothing new before the same failure. A placement that raises still stops `apply_intake` at that candidate, so the candidates decided after it in that round are decided again later; new candidates are not held back. Per-candidate isolation of placements is #1443.
- **`--limit` without a record** takes the lowest numbers first. Only the intake that `devops roadmap run` and the Service run keeps `intake.json`.
- **Not done here.** The MCP `roadmap_intake` mirror has no `limit` (optional in the assessment). Board edits a person makes (Status, Priority, blocked-by) are still not polled, as the issue scopes them out. Close's cross-job trigger (`_reprioritize_cross_job`) is unchanged.
- **ADR 0003 is unchanged.** Its promise, that a missed webhook only delays a job until the next tick, now holds for a ship.
