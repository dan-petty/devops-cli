## Description
The path review of the whole repository in session `20261001-224227` raised 563 findings. Triage against `release/v0.2.25` (c279c18) upheld five LOW defects in the AI client area, each with a fix and a regression test. This delivers all five in one PR, as the issue proposes. Every regression test was run against `HEAD`'s `src/`, exported with `git archive HEAD src` into a scratch directory and put first on `sys.path` with `-o pythonpath=`, where it failed, and against this tree, where it passes. The tests answer requests with httpx2's `MockTransport` or the existing `httpx2.Client.post` stubs, and make no network or DNS call.

- **Timeouts** (`ai/client/unified.py`, `ai/review/runner.py`, `ai/pydantic_ai_bridge.py`, `config/settings.py`): `LLMClient._request_timeout` reads `request_timeout_seconds or config.timeout or DEFAULT_HTTP_TIMEOUT_SECONDS`, so `ai.timeout` and `ai.tasks.<task>.timeout` reach every chat, metadata, analysis, verification and compose request, streamed or not. `_make_review_clients` builds its three clients through one local `review_client`, which passes `task_config.timeout or DEFAULT_REVIEW_TIMEOUT_SECONDS`, so a configured task timeout wins and 1,200 s applies only when none is set. `_resolve_ollama_model` passes `ai.timeout` to `create_ollama_model(timeout=...)`. Both `timeout` fields are `Field(gt=0, allow_inf_nan=False)` with a description; `AIConfig.timeout`'s names 3,600 s and 1,200 s from the constants, and `docs/CONFIGURATION.md` is regenerated from it.
- **Reply size limit** (`ai/client/network.py`, `claude.py`, `openai.py`, `ollama.py`, `streaming.py`): `request_limited_json(client, method, url, *, limit_bytes=None, **kwargs)` streams the request, refuses a numeric Content-Length over the limit before reading, counts the decoded bytes of `iter_bytes()` and raises `AIClientError` as soon as they pass the limit, then parses a JSON object. It returns the payload and the reply headers, because the OpenAI path reads the gateway's served-by header. A reply that is not 2xx has its body read under the same limit and raises `HTTPStatusError` on a copy holding that body, so the Ollama thinking fallback and the providers' error messages still read it. It takes a method rather than being `post_limited_json`, because the model lists (`GET /models`, `GET /api/tags`) buffered their replies the same way; all five `read_limited_json` callers use it, and `read_limited_json`, `_check_response_size` and `LLMClient._read_limited_json` are deleted. The limit defaults to `DEFAULT_AI_MAX_RESPONSE_BYTES`, read when called. `size_limit_text` names a limit in MB, KB or bytes, and the stream readers and `StreamingTokenProcessor` use it too; a 4 KiB limit read "0MB".
- **Model resolution** (`ai/pydantic_ai_bridge.py`, `ai/providers/__init__.py`, `ai/durable.py`, `ai/gateway.py`, `config/constants.py`): `_resolve_string_model` has no `except Exception`. `_resolve_remote_inferred_model` turns `InvalidURLError` and `SSRFBlockedError` into a `ConfigurationError` keyed and named by the setting holding the URL (`ai.api_base_url`, `ai.gateway_url` or `ai.portkey_url`), and pydantic-ai's `UserError`, the `ValueError` its provider lookup raises, or the `ImportError` it raises for a provider whose optional package is missing (`mistral:` without `mistralai`), into one keyed `ai.model` that names `ai.provider` and `ai.model` and carries pydantic-ai's reason, such as "Did you mean 'openai-chat:gpt-4o'?". It logs the model prefix and the exception type, never the key. The issue offered raising for an unknown model or mapping `ai.provider` to a prefix; this does both, mapping first. Raising alone would have turned every bare name, such as `gpt-4o` under `openai` or `devops-review` under `gateway`, from a silent fallback into an error. `_resolve_remote_provider_endpoint` returns the inference name, the base URL and its setting, from `_model_prefix_and_target`. A `litellm:` or `portkey:` prefix is kept. Under provider `gateway` every other name is a route of `ai.gateway_provider`'s gateway, sent whole as `LLMClient` sends it: a route whose text before its first colon names a provider, such as the Ollama tag `mistral:7b` or `openai:gpt-4o`, was inferred as that vendor's model, raising a bare `ImportError` for `mistral` and, on `HEAD` as here before the review, sending `openai:gpt-4o` and the configured key to `https://api.openai.com/v1/`. Under any other provider a name whose text before its first colon is not a provider (`is_pydantic_ai_provider`: one `create_pydantic_ai_provider` registers, or one pydantic-ai's `infer_provider_class` knows) takes the prefix `CONST_AI_PYDANTIC_MODEL_PREFIXES` maps `ai.provider` to, so `qwen3-coder:30b` stays whole. `openai` maps to `openai-chat` rather than the issue's `openai:` (pydantic-ai's Responses API), because `LLMClient` sends OpenAI requests to `/chat/completions` and OpenAI-compatible servers at `ai.api_base_url` serve that API. `litellm:` and `portkey:` (`CONST_AI_GATEWAY_URL_SETTINGS`) are inferred as `openai-chat:<model>` at their configured URL: the prefix was stripped before inference, so `litellm:<model>` never resolved, and the bare string left for pydantic-ai went to `https://api.openai.com/v1/`. `_resolve_string_model` sends a `litellm:` or `portkey:` name to its gateway under provider `ollama` too, which made it an Ollama model of that name. `create_pydantic_ai_agent` falls back to `PydanticAgent` only on `TypeError` or `UserError` from building `Agent`, and `create_durable_pydantic_agent` drops its `except Exception` around `resolve_pydantic_ai_model`, which handed the native `Agent` the bare name after a `ConfigurationError`. The cascade's bare members are a path, not a model (`_cascade_member`): `build_fallback_cascade_model` reads `litellm` and `portkey` as that gateway's `devops-chat` route (`CONST_AI_GATEWAY_DEFAULT_ROUTE`, the target `_extract_provider_and_target` gave them before it was deleted) and `ollama` as `ollama:<ai.model>`. `GatewayRouter.build_pydantic_cascade_model` prefixes its route and failover route with the router's gateway and leaves out `direct-ollama`, the failover that names Ollama itself, since its last member is Ollama. On `HEAD`, `"cascade"` raised "Unknown model: litellm" and the gateway cascade "Unknown model: devops-coder", and under provider `ollama` both built Ollama models named `litellm`, `portkey`, `ollama` or the routes; after the deletion here they became gateway models of those names. A bare provider name other than the three cascade members is still a model name, not an error as the review suggested, because a gateway route may be named `mistral` or `groq`. The dead `getattr(ai, "api_key", None)` reads are gone (`AIConfig` has no such field). `create_pydantic_ai_provider` checked its base URL with `validate_service_url(allow=True)`, which passes every host but cloud metadata, so on `HEAD` a prefixed name such as `openai:gpt-4o` under an `ai.api_base_url` on an RFC-1918 address built a model sending the prompts and the key there with `ai.allow_private_network` off, a URL `LLMClient` refuses; the mapping above would have carried that to bare names and gateway routes. The factory now takes `allow_private_network` (default False) and calls `validate_configured_service_url`, and the bridge passes `ai.allow_private_network`, so such a URL raises the `ConfigurationError` naming its setting.
- **Round-robin state** (`ai/client/unified.py`, `ai/client/ollama.py`): the class aliases `_active_ollama_requests`, `_ollama_active_lock`, `_ollama_semaphores`, `_ollama_sem_lock`, `_global_ollama_url_index` and `_global_ollama_url_lock`, the instance attributes `_ollama_url_index` and `_ollama_url_lock`, and the `self._ollama_url_index = getattr(...)` assignment in `_get_ollama_urls_loop` are deleted. `test_ollama_multiserver_failover` asserts only the requested URL order, and the providers test reads `network.active_ollama_requests`.
- **Loopback policy** (`core/validation.py`, `ai/rag/qdrant.py`, `ai/rag/embeddings.py`, `ai/providers/ollama.py`, `ai/providers/__init__.py`, `ai/client/network.py`, `ai/rag/investigator.py`): `validate_configured_service_url(url, purpose, *, allow_private)` lets a configured URL name `localhost` (`CONST_LOOPBACK_HOSTNAME`) or a loopback address, decided without DNS, and otherwise is `validate_service_url`, whose default is unchanged for the HTTP broker and tool downloads. `QdrantClient.__init__`, the four `EmbeddingsEngine` sites (Ollama probe and batch, OpenAI and gateway probe and embed) and `create_pydantic_ai_provider` (see Model resolution) call it. The Ollama provider's `_LOOPBACK_HOSTS`, `_is_loopback_or_private_allowed` and `_validate_ollama_url` are deleted, as is the investigator's `validate_url(allow_private=True)`. The LLM client held a third copy, `validate_base_url(allow_loopback_for_local_tooling=True)`, which the issue does not name: that parameter is deleted and `validate_base_url` calls the same function, so a configured Claude, OpenAI or gateway URL on loopback passes as an Ollama one did (the example's gateway, `http://localhost:4000/v1`, was refused), and a cloud metadata host is refused even with `allow_private_network`, where the client skipped every check. The investigator's first failed lookup of a run logs a WARNING with the masked cause (`MESSAGES.rag.lookup_failed`), later ones log at debug, and `clear_investigation_cache` resets it. `review/pipeline.py`'s handler stays at debug: `investigate_rag_context` catches a lookup's failure itself, so the pipeline's handler sees only failures outside a lookup.
- Docs: `docs/CONFIGURATION.md` is regenerated. `config.example.yaml` says configured AI, gateway, Ollama and Qdrant URLs on loopback need no opt-in, while ArgoCD, Grafana and Prometheus still need it for loopback, and documents `ai.timeout`, `docs/KNOWN_ISSUES.md` (which names the pydantic-ai models among its users) and `README.md` describe the configured-URL policy, and `README.md`'s `DEFAULT_REVIEW_TIMEOUT_SECONDS = 3600.0`, which is 1200.0, is corrected.
- Tests that stubbed `httpx2.Client.post` or `.get` for the five JSON calls no longer intercepted them once they stream. They route through `MockTransport` with the existing `route_client`, or with `route_llm_clients` (`tests/llm_stream_fakes.py`), added for clients built inside the code under test. A stub that read `kwargs["json"]` reads `json.loads(request.content)`.
