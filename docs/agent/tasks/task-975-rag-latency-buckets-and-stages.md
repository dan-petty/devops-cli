# Task: RAG Query Latency Reaches 60 s, Is Timed by Stage, and Searches Its Collections at Once (#975)

**Issue**: [#975](https://github.com/dan-petty/devops-cli/issues/975)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p2-medium
**Scope**: scope/telemetry

## Description
The "RAG Query Latency (p50, p95)" panel on the devops-cli dashboard flattened at exactly 5 s. That was the top bucket of `devops_cli_rag_query_duration_ms`, `(10, 25, 50, 100, 250, 500, 1000, 2500, 5000)`: in any hour where more than 5% of queries took longer, `histogram_quantile(0.95, …)` returned 5000. Over 24 h on 2026-10-02, 64 of 2,856 queries (2.2%) took over 5 s. Nothing recorded how a query's time split between its embedding request, its two Qdrant searches, which ran one after the other, and local ranking, and nothing counted Qdrant's reconnect-and-retry after a transient error.

- **Buckets** (`telemetry/instruments.py`). `_MILLISECONDS` is now `_RAG_MILLISECONDS = (10, 25, 50, 100, 250, 500, 1000, 2500, 5000, 10000, 15000, 30000, 60000)`. The sub-second bounds are unchanged, and 15 s, 30 s and 60 s line up with the query path's timeouts. The panel descriptions state the new cap, 60000 ms, which `tests/test_telemetry_instruments.py` derives from the bounds.
- **The query path's longest wait was an hour, not 60 s** (`ai/rag/qdrant.py`, `config/defaults.py`). The issue read the Qdrant client's timeout as "60 s or more". Every caller on the query path builds `QdrantClient` without a timeout: `_get_or_create_retriever` in `ai/rag/investigator.py`, the `rag_search` tool and `devops ai rag query`. The default was `DEFAULT_HTTP_TIMEOUT_SECONDS`, 3600 s, raised to at least 60 s, so a 60 s top bucket would still have sat below the query's own timeout. `QdrantClient` now defaults to `DEFAULT_QDRANT_TIMEOUT_SECONDS` (60.0, new in `config/defaults.py`), which also replaces the literal 60.0 floor. A request that times out is a transient error, retried after a reconnect as before. Indexing shares the client, so its 64-point upserts with `wait=True`, its collection changes and its deletions also wait 60 s per attempt rather than an hour. On the embedding side, the gateway path (`_embed_openai`) reads with `max(timeout, 30.0)`, 30 s by default, and the Ollama path with the task timeout, 15 s by default. `ai.tasks.embedding.timeout` can still be set as high as 120 s, and an embedding that waits past 60 s then lands in the `+Inf` bucket. The defaults are covered.
- **Stage timing** (`ai/rag/retriever.py`). `_timed_stage(stage)`, a context manager, observes `RAG_QUERY_DURATION` with `{"stage": stage, "outcome": ...}` when its block ends, `ok` or `error`. `SemanticRetriever.search` times `embedding` (`_embed_search_query`), `search` (`_search_collections`), `ranking` (projection, hybrid fusion and `_rank_results`) and `total` (the whole query, which the unlabelled observation used to be), in that order. One series name with a `stage` label, as the issue proposed, keeps the dashboard queries and the cap test simple. The clamping of `top_k`, the fetch limit and the score threshold moved to `_search_limits`, so `search` stays at cyclomatic complexity 9 with three more `with` blocks (it was 10). Each observation also carries `outcome`: a stage that raises an `Exception` is recorded as `error` before the exception propagates, and an interrupt records nothing (`test_a_stage_that_fails_is_observed_as_an_error`: a 15 s embedding failure records `embedding` and `total` at 15000 ms with outcome `error`; without the error branch it records nothing).
- **Concurrent search** (`ai/rag/retriever.py`). `_search_collections` starts a daemon `ContextPropagatingThread` (named `devops-rag-search-<index>`) for each target collection after the first, searches the first collection on the caller's thread, then joins the threads. Each search writes its points into the slot of its collection's index, so the points are pooled code first, then docs, whichever reply comes back first. The pool, and so `reciprocal_rank_fusion` (whose dense pass keeps the last duplicate) and the ranking after it, see the same list as the sequential loop did. `_search_collection` still logs a failed collection's error at DEBUG and adds no points. Each thread runs under a copy of the caller's context, so `ai.rag.qdrant_search` spans stay children of `ai.rag.search`. A single-collection query starts no thread. A first version used a `ContextPropagatingThreadPoolExecutor` in a `with` block. A review found that a pool's threads are joined however the caller leaves, by the `with` block and again by the interpreter at exit, so Ctrl-C during `devops ai rag query` waited out the other collection's search, up to three 60 s attempts against a stalled Qdrant, and the process stayed alive until they ended. A KeyboardInterrupt on the caller's thread now leaves at once, whether it arrives during the caller's own search or while it joins the others (`Thread.join` is interruptible), and daemon threads do not hold the interpreter open. `QdrantClient._get_client` now builds the native client under `_client_lock`, so two searches starting at once on a new client build one native client, not two.
- **Retry counter** (`ai/rag/qdrant.py`, `telemetry/instruments.py`). `QDRANT_RETRIES_TOTAL` is the counter `devops_cli_qdrant_retries_total`. `_execute_with_retry(fn, operation, target="")` takes the client method's name and, for the log only, what it acts on. `_record_retry`, which replaces `_log_retry_warning`, logs the same warning, adds 1 with `{"operation": operation, "error_type": …}`, then sleeps `0.5 * attempt`. qdrant_client's `ApiClient.send_inner` raises every exception from its httpx client as `ResponseHandlingException(source)`, so `error_type` is the class of `exc.source` for that wrapper and of `exc` otherwise. A first version labelled with the wrapper's class, which a review showed gave a dropped keep-alive connection (`RemoteProtocolError`, retried within a second) and a request that waited out its 60 s (`ReadTimeout`) the same label. The values are a small set of class names, such as `RemoteProtocolError`, `ReadTimeout`, `ConnectError` and `UnexpectedResponse`. Collection and file names never become labels. `test_ensure_collection_creates_quantized_collections` (`tests/test_rag_hybrid_search.py`) stubs `_execute_with_retry`, so its stub takes the new arguments.
- **Dashboard** (`k8s/monitoring/dashboards/devops-cli.json`). "RAG Query Latency (p50, p95)" reads `devops_cli_rag_query_duration_ms_bucket{stage="total"}`. Two panels join the first row at `y: 17`. "RAG Query Stage Latency (p95)" (id 15) charts `histogram_quantile(0.95, sum by (le, stage) (increase(devops_cli_rag_query_duration_ms_bucket{stage=~"embedding|search|ranking"}[1h])))`. "Qdrant Retries by Operation and Error" (id 16) charts `sum by (operation, error_type) (increase(devops_cli_qdrant_retries_total[1h]))` as bars. The rows below move down by 8. Each description states its `increase()` limits (#792), the two RAG panels state the 60000 ms cap, and the retries panel says what `error_type` holds, with `RemoteProtocolError`, `ConnectError` and `ReadTimeout` as examples. The stage panel names its stages rather than using `stage!="total"`, which would also match the old series that have no `stage` label.
- **History.** The issue expected `histogram_quantile` to read oddly for about one window, while old and new `le` sets mixed. The panels select by `stage`, and the series earlier releases sent have none, so the two bucket sets never mix, and neither do the series from a host still on an older release. The cost is that the RAG panels draw only queries recorded by this release or later. The old series stay in Prometheus until retention drops them. The changelog says so.
- **Docs.** `docs/TELEMETRY.md` is generated from `INSTRUMENTS`. `uv run devops docs generate` rewrote its two rows, and no other file changed. The changelog entry is `changelog.d/975.md`.

"RAG Query Stage Latency (p95)" sits beside the retries panel in the RAG panel's row. `test_the_dashboards_chart_latency_errors_reviews_and_findings_devops_cli_sends` checks that the dashboards group `devops_cli_rag_query_duration_ms_bucket{stage="total"}` by `le` and `…{stage=~"embedding|search|ranking"}` by `stage`, and that the RAG quantiles charted are p50 and p95. `uv run devops grafana dashboards lint k8s/monitoring/dashboards` reports `Linted 12 dashboard(s), 253 panel(s): 0 error(s), 0 warning(s).`
- [x] Retry counter. `test_a_retried_qdrant_request_is_counted_by_the_error_behind_it` runs the real `QdrantClient.search_points` and the real qdrant_client, whose httpx client is given an `httpx.MockTransport` that raises `httpx.RemoteProtocolError`, then `httpx.ReadTimeout`, then answers. The test checks the hits and the two counts, in order: `{"operation": "search_points", "error_type": "RemoteProtocolError"}` and `{"operation": "search_points", "error_type": "ReadTimeout"}`. The same dashboard test checks that the retries are grouped by `operation` and by `error_type`, and the panel's description names the error types.
- [x] Concurrent search, with the sequential result. In `test_the_collections_are_searched_at_once_with_the_sequential_result`, the code search waits up to 0.5 s for the docs search to start and raises if it does not, which only the overlapping searches avoid. The docs search answers first. The test compares each result's id, file path, score and rerank score with a search of one collection holding the code points followed by the docs points, which is what the sequential loop pooled. A point in both collections, `shared`, appears once, and the ids are `["alpha", "beta", "shared"]`. No thread started by the search is left when it returns. `test_a_failed_collection_search_drops_only_that_collection` checks that a docs search that raises leaves the code-only result. `test_each_collection_search_span_stays_under_the_query_span` runs the real `QdrantClient.search_points` on the caller's and the search thread and checks that both `ai.rag.qdrant_search` spans have the `ai.rag.search` span's trace and parent id. `test_a_query_waits_for_a_collection_search_that_ends_after_its_own` makes the docs search end 50 ms after the caller's code search answered, and checks that its points are pooled and its thread is gone. `test_an_interrupted_query_does_not_wait_for_the_other_searches` raises `KeyboardInterrupt` from the caller's code search while the docs search blocks on an event, and checks that `search` re-raises while the docs search is still blocked, on a daemon thread. Mutations of the worktree's `_search_collections`, each restored after, showed these tests catch the defects the concurrent search could bring: a plain `threading.Thread` failed the span test (the docs span started a trace of its own); dropping the joins failed the wait test (`['src/alpha.py', …]` and a leaked `devops-rag-search-1`); `daemon=False` failed the interrupt test (`(True, [False])`); appending the replies in the order they came back failed the ordering test; and searching every collection on the caller's thread failed the overlap test (`[False]`).

The Qdrant tests replace `NativeQdrantClient`, and the gateway test replaces `httpx2.Client.post`, using `example.com` and `127.0.0.1`.
