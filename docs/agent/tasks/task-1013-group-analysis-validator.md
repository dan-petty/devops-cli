# Task: A Group-Analysis Reply That Fails Its Checks Is Neither Cached Nor Served (#1013)

**Issue**: [#1013](https://github.com/dan-petty/devops-cli/issues/1013)
**Scope**: scope/ai, scope/review
**Feasibility**: At the release tip the client already validates a reply before it caches it and before it serves a cached one, honours `max_retries=0` as one dispatch, and raises `ReplyRejectedError` carrying the original `LLMResponse` with its finish reason (`ai/client/unified.py`, covered by `tests/test_ai_client_retries.py`). `_execute_single_group_job` passed neither a validator nor `max_retries`, so a reply that did not parse or failed a G10 check was cached for 7 days and served again, and an empty reply was sent up to five times. The new tests drive a real `LLMClient` over a `MockTransport` and a per-test cache directory: at the base the unparseable-reply, unknown-finding-id, empty-reply and seeded-cache cases fail, and the served-by, tool-call and credential cases fail for want of the fields and the reason.

## Description

- [x] **Group job** (`review/analysis.py`): `_execute_single_group_job` calls `chat` with `max_retries=0` and a validator that accepts a reply only when `_parse_model_group_output` returns a `GroupAnalysisOutput` and `verify_group_analysis` passes it. `_judge_group_reply` parses and verifies a reply once, and the job reads each verdict back by the reply's stripped text, so no reply is parsed twice. A client that never ran the validator, such as the offline fakes, gets the same verdict from the same judge.
- [x] **Rejections**: a reply the validator refuses is not cached and a cached reply it refuses is not served; the group makes one model call and is recorded with the reason it has today: `schema-validation-failed` when the reply does not parse, the G10 reasons when a check fails, and `reply-truncated` when the finish reason is `length`, read from the reply that `ReplyRejectedError` carries and not from a re-wrapped one. An empty reply with no reasoning never reaches the validator, so it stays `model-call-error`, after one call.
- [x] **Uncached replies** (`config/constants.py`): `tool_call` joins `CONST_UNCACHED_FINISH_REASONS`. No review call offers tools, so a reply that asks for one is not an answer.
- [x] **Cache entries** (`ai/response_cache.py`, `ai/client/unified.py`): each new entry records `served_by` and `response_model`, the backend and model the reply carried, beside `model`, which stays the requested alias. A hit returns them as `served_by` and `model` on its `LLMResponse`, and `backend_info` still names the cache. The field is `response_model` because pydantic reserves the `model_` prefix. `served_by` is what `extract_served_by` returns, with no userinfo, so a gateway that names its backend with credentials leaves them out of the file. An entry written before this change reads back with both `None`.
- [x] **Cleanup**: `_parse_model_group_output` takes the reply text, which is the only thing its one caller gave it. `_group_record` builds the group record for both the rejected and the judged case.
- [x] **Tests**: `tests/test_review_group_analysis.py` runs group analysis through a real gateway client with a stubbed transport and the per-test cache, counting the requests the transport receives: an unparseable reply, a reply citing an unknown finding id, a cut unparseable reply, an empty reply, a verified reply that answers the next run from the cache, and a cached reply that fails its checks replaced by one model call. `tests/test_ai_client_finish_reasons.py` adds `tool_call` to the uncached reasons and checks that a refused reply keeps its finish reason. `tests/test_response_cache.py` checks the entry fields, the hit, and the credentials.
- [x] `docs/agent/tasks/task-599-finish-reasons-stream-completeness-and-truncation-markers-fo.md` lists `tool_call` among the uncached reasons.
