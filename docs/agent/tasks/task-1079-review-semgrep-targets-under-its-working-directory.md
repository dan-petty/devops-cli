# Task: A Review's Isolated Semgrep Scan Names Only Targets Under Its Working Directory (#1079)

**Issue**: [#1079](https://github.com/dan-petty/devops-cli/issues/1079)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p1-high
**Scope**: scope/review

## Description
Since #972 every review scanner runs from a fresh temporary working directory. A review named each Semgrep target by its absolute path in the reviewed tree. Semgrep 1.178.0 takes its fast path only for a target that is a regular file under its working directory (`target_manager.py:716-727` in Semgrep). For every other target it starts its own `semgrep-core -rpc` process, which walks the target's whole checkout, nested worktrees and `repos/` included. Semgrep ran out of its 300 s timeout in 11 of 11 reviews and returned nothing. The reviews lost the findings only Semgrep makes: `runAsNonRoot` and `allowPrivilegeEscalation` on the Ollama DaemonSets (#1060), and config.py:514 (#770, #1022). review.md gave the timeout as a command cut at 256 characters.

- **Materialized targets** (`security/base.py`). `materialize_targets(targets, tree, workdir)` places each target file that lies in `tree` under `workdir` at its path in the tree. It hard-links the file with `os.link` and copies it with `shutil.copyfile` when linking fails, as across filesystems. Each target is resolved with `Path.resolve(strict=True)`, and a target whose real path is not a regular file inside the resolved tree (`is_relative_to`) is left out, so no link in the tree leads the scan out of it. A file named twice, directly and through a link, is placed once. A file already in the working directory, such as a config file devops-cli handed the scanner, is never replaced. `MaterializedTargets` keeps each target's relative name and the path it came from. `names` gives the names for the command line, each led by `./` (`os.path.join(os.curdir, name)`), so a file the tree names `-`, `--autofix` or `--config=x.yml` is a file to the scanner, never an option or its stdin, as an absolute path never was. `origin(name)` maps a reported name back, with or without the `./`.
- **The scanner base** (`BaseSecurityScanner._execute`). An isolated scan writes the scanner's isolation files first, then asks `isolated_targets(target, workdir, **kwargs)` for the targets it names from the working directory, then builds and runs the command (`_run_built_command`). By default `isolated_targets` returns the targets as given. Every scanner command runs with an empty stdin (`input=""` to `run_subprocess`), never the caller's, such as the request stream of `devops mcp`. Only Semgrep pays a per-target cost from the temporary working directory (Measurements), so as the issue proposed only `SemgrepScanner` overrides it, and the hook with `materialize_targets` is what a second scanner would opt in through.
- **Semgrep** (`security/semgrep.py`). `run_semgrep_scan(..., reviewed_tree=...)` replaces `isolated=True`. With a reviewed tree the scan is isolated as before, and `SemgrepScanner.isolated_targets` materializes the scannable files (`_scannable_files`: regular files with no excluded extension) from that tree. `build_command` names each `./<its relative path>`. Semgrep reports a result under the name its command gave the target, and `parse_output` maps each result's path back with `origin`, so a finding carries the reviewed tree's path and its line numbers. The rules still come from `--config` alone, and no other file of the tree is in the working directory. Without a reviewed tree, as `devops scan sast` runs it, nothing changes.
- **Batches** (`security/semgrep.py`, `config/defaults.py`). A review's files are scanned in batches of at most `DEFAULT_SEMGREP_REVIEW_BATCH_FILES` (100) with `itertools.batched`, each in its own temporary directory under its own timeout. `merge_outcomes` combines the batches: every finding, the worst status and each distinct reason, from the first batch's start to the last one's end. A failed batch among several says which it was and how many files it held (`MESSAGES.scan.semgrep_batch_failed`), such as `batch 1 of 4, 100 files: timed out after 300 s`. The issue's rule decided the batching; see Measurements.
- **Shared merge** (`security/base.py`, `security/gitleaks.py`, `config/constants.py`). Gitleaks' private `_merge_outcomes` and its status order moved to `security/base.py` as `merge_outcomes`, with the order as `CONST_SCAN_STATUS_PRECEDENCE`, and Gitleaks imports it. The merged outcome keeps its runs' start and end, and `run_gitleaks_scan` keeps them when it filters test-file findings.
- **Timeouts** (`BaseSecurityScanner._failed_run`). A scan whose command raises `subprocess.TimeoutExpired` gives the reason `timed out after <timeout> s` (`{timeout:g}`), or `timed out after <timeout> s; used built-in patterns` for a scanner with built-in patterns, in place of the exception's text, which quoted the command. Other errors keep their wording.
- **The review** (`ai/review/pipeline.py`, `ai/review/profile.py`). `_scan_semgrep` takes the reviewed tree, `reviewed_tree(self.target_dir)`, the same tree #972 keeps the review's trust decisions out of. `_observe_outcome` keeps each analyzer's outcome for the report as before, its first or a failed one, and adds the scan's run time to the review's profile. The profile records `static_analyzer_reasons`, the reason review.md gives for each failed analyzer, and `static_analyzer_seconds`, how many seconds each analyzer's scans ran. `docs/SELF_IMPROVEMENT.md` names both.

Semgrep 1.178.0 ran with a local file of five rules (`--config <rules> --metrics off --disable-version-check --json --quiet`). Offline, with no version cache, Semgrep's version check spent about 98 s failing to resolve its host (3 files: 99.9 s against 1.7 s), so the runs disable it or seed its cache. "Outside" is the shape #972 runs: absolute paths from an empty working directory. "Under" is the same files hard-linked under the working directory and named by relative path. The host has 16 cores, and other work kept its one-minute load average between 2.8 and 12.5 for the first measurements and between 9.5 and 24.4 for those after the targets were named `./<path>`.

## Known limits
- A file `_resolve_file_path` takes from outside the reviewed tree, which only happens outside a git checkout where a `pyproject.toml` above the review target counts as the repository root, is not scanned by Semgrep.
- `_resolve_file_path`'s last resort, `<target>/<name>`, can itself be a link out of the tree. Semgrep leaves it out now, but Bandit, Gitleaks, kube-linter, Pluto and Trivy are handed it as before and read the file it points to.
- On a timeout `run_subprocess` kills Semgrep's own process, not its process group, so a `semgrep-core` it started can outlive it [not measured].
- Each batch fetches and parses `p/default` again; the time this adds was not measured offline.
- `_match_static_findings_to_files` attaches a static finding to the first reviewed path its location ends with, so a finding located at `--config=planted.yml` is listed under `planted.yml` in the review's per-file payloads. Its location stays the right file. The match predates #972.
