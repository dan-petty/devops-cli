# Task: Semgrep Runs Pinned and Offline with Metrics Off, from a Cached Registry Ruleset plus devops-cli's Rule Pack (#1144)

**Issue**: [#1144](https://github.com/dan-petty/devops-cli/issues/1144)
**Scope**: scope/review, scope/security
**Feasibility**: At release/v0.2.39 b40d48e3, checked against the pinned Semgrep 1.179.0 (`tools.lock`, installed): `semgrep scan --help` lists `--metrics`, `--disable-version-check`, `--disable-nosem`, `--exclude-rule`, `--quiet` and `--json`, and `--dataflow-traces` and `--sarif-output` exist but are not used. A review's scan, started through its adapter with the new command, rule file and rule pack included, ran with no network (`unshare -rn`) and a scratch home in 0.28 s, exit 0, with the JSON on stdout; the version check that #1079 measured at about 98 s of failing DNS offline is off. The issue's text was checked against the code: the hand-written MCP Semgrep tool with an `auto` default is gone (#1720), and the generated MCP tool `scan_sast` comes from `devops scan sast`, defaults to `p/default` and so gets the new argv with no code change, so the plan's MCP item needs none; `build_semgrep_cmd` served only the directory path of `devops scan sast`, while the review's file path (`security/semgrep.py`), the canary (`review/canary.py`) and the agent tool (`ai/tools/builtin_tools.py`) each built their own argv, so the "one builder" goal rewires four places; and the rule pack was added only for the review's file path with the default config. The registry fetch was checked against the live registry with a read-only GET and then with `devops review rules fetch`, twice, into a scratch user data root: `https://semgrep.dev/c/p/default` answers 200 without login with 1,074 rules, of which 28 set `options.interfile` (the `interfile: true` text appears twice per rule, in `options` and in `metadata`, so a text count says 56) and 18 name the AGPL-3.0 licence in `metadata.license`, and it sends a weak `ETag` that it answers with 304 and no body when a request carries it as `If-None-Match`. The command cached 1,074 rules the first time and reported the cached ruleset current the second, with both files untouched. The registry answers a client that sends `Accept-Encoding: gzip` with the ruleset as JSON (`application/json`, 2.29 MB) and a client that does not with YAML (`text/yaml`, 2.52 MB): the rules are the same, only the serialisation differs. Semgrep 1.179.0's `--validate` accepts both under a `.yaml` name, so the cache keeps the answer byte for byte, and a digest taken when the file is read describes what this client received. Whether to build the cache at all was checked against open tools: Semgrep 1.179.0 runs offline from a local `--config` file (the cached `p/default` scanned with no network and ended with no errors) and puts each rule's licence in its findings, and HTTP validators give the refetch, so the cache keeps no record of its own.

## Description

The issue is delivered in four pull requests: the one command builder, the registry fetch and its cache, the review and `devops scan sast` consuming the cache, and the batches with their budget and `paths.scanned`. The first part makes `build_semgrep_cmd` (`config/commands.py`) the only place a `semgrep scan` argv is built, and every scan devops-cli starts goes through it. The second adds the step that downloads the registry ruleset the later parts read, and downloads it again only when it has changed.

- **One builder.** `build_semgrep_cmd(targets, configs, exclude_paths)` emits `semgrep scan --json --metrics off --disable-version-check`, one `--config` per value, `--disable-nosem`, `--exclude` per value, `--quiet` and the targets. Semgrep's `--disable-version-check` does what `SEMGREP_ENABLE_VERSION_CHECK=0` does and shows in the argv, so no environment is passed. `--quiet` stays last before the targets. The review (a file list, or the files linked into its isolated working directory), `devops scan sast`, the agent tool and the canary call it; the pack's own `semgrep --test` keeps its command, as the issue says.
- **The rule pack always runs.** `semgrep_scan_command` (`security/semgrep.py`) adds `RULE_PACK_DIR` as a `--config` after the config a scan names, for the review's files, a directory or file of `devops scan sast` and the agent tool. Before, only the review's file path added it, and only beside `p/default`. A pack that ships in the package is always there, so the `is_dir()` guard is gone: a pack that is missing fails the scan instead of silently scanning without it. The canary runs its probe rules alone, since its expected findings and its ruleset digest are those of the probe file.
- **The agent tool takes the same flags and the pack.** It scans the whole target it is given and excludes no directory, as before, and reports every finding whatever `nosemgrep` marker it carries, as a review does. The directories `devops scan sast` leaves out are now `CONST_SEMGREP_EXCLUDED_DIRECTORIES` (`config/constants.py`) instead of a list inside `security/semgrep.py`, and only that command passes them.
- **Findings stay read from Semgrep's JSON.** The issue's criterion that findings come from `--sarif-output` is dropped, by the owner's decision. Semgrep's SARIF copies the rule's metadata, and the JSON carries the same in `extra.metadata` and `extra.severity`; `paths.scanned` is JSON only; and SARIF would need a working directory that `devops scan sast` and the agent tool, which scan in the user's tree, do not have, and a scanner fake that writes files.
- **The recording.** The Semgrep run in `tests/fixtures/scanner_runs/recorded_runs.json` is recorded again with the real Semgrep 1.179.0, through the contract suite's own adapter call, offline and from a scratch home. A recording cannot fetch `p/default`, so the contract suite's Semgrep case names a rule file of one synthetic rule in the scanned tree as its config, and the recorded command says so.
- `devops scan sast --config`'s help says the pack runs with the config; the generated CLI reference is regenerated.
- **The registry fetch.** `devops review rules fetch [--ruleset p/default] [--dry-run]`, beside `devops review rules test`, downloads the ruleset from `CONST_SEMGREP_REGISTRY_URL_TEMPLATE` through the public-only HTTP client (`new_http_client(level=EgressLevel.PUBLIC)`), reading at most `DEFAULT_SEMGREP_REGISTRY_MAX_BYTES` with a `DEFAULT_SEMGREP_REGISTRY_TIMEOUT_SECONDS` read timeout, and refusing a redirect, an error status, a transport failure or a body that is not a Semgrep ruleset with at least one rule, each with an id. Nothing runs it implicitly: a review never fetches.
- **The cache.** `security/semgrep_registry.py` writes `<user data root>/semgrep/<slug>.yaml`, the ruleset byte for byte as the registry answered, and `<slug>.etag` beside it with the ETag the registry sent. A fetch that finds both files sends the ETag as `If-None-Match`, and a 304 means the ruleset is unchanged: nothing is downloaded or rewritten. Both files are written with the repository's atomic writer, the ruleset first, so a run that stops between them leaves a ruleset whose ETag is old or missing, which the registry answers with the full ruleset: an interrupted fetch costs one download. An answer without an ETag removes the one on disk. A refused download writes nothing and leaves the earlier cache as it was.
- **What the cache does not keep.** No metadata file, rule-id list, interfile list, licence map, digest or age check: Semgrep already provides what they would record, and nothing reads them yet. The AGPL rules are cached with the rest, and each finding carries its rule's licence in `extra.metadata.license`. The consumers part of #1144 takes the digest as the sha256 of the file when it reads it and the age from its modification time, and, if interfile rules are to be excluded, takes their ids from the file; the OSS engine ran the 28 of them without error.
- **The ruleset name.** A registry id is a kind Semgrep's own `is_registry_id` takes (`p`, `r` or `s`), a slash and one name that `urllib.parse.quote` leaves unchanged and that is not `.` or `..`. The name therefore cannot add a path, a query or a fragment to the URL, or a directory to the cache path, and no two rulesets share the slug `<kind>-<name>`.
- **The dry run.** `--dry-run` makes no request: it lists the one GET and the two paths it would write.
- **The YAML loader.** The body is read with libyaml's safe loader where PyYAML has it, and with the pure-Python one where it does not, as `security/checkov.py` already did. The choice is now `YAML_SAFE_LOADER` in `core/serialization.py`, which both use.
