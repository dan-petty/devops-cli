# Task: Semgrep Runs Pinned and Offline with Metrics Off, from a Cached Registry Ruleset plus devops-cli's Rule Pack (#1144)

**Issue**: [#1144](https://github.com/dan-petty/devops-cli/issues/1144)
**Scope**: scope/review, scope/security
**Feasibility**: At release/v0.2.39 b40d48e3, checked against the pinned Semgrep 1.179.0 (`tools.lock`, installed): `semgrep scan --help` lists `--metrics`, `--disable-version-check`, `--disable-nosem`, `--exclude-rule`, `--quiet` and `--json`, and `--dataflow-traces` and `--sarif-output` exist but are not used. A review's scan, started through its adapter with the new command, rule file and rule pack included, ran with no network (`unshare -rn`) and a scratch home in 0.28 s, exit 0, with the JSON on stdout; the version check that #1079 measured at about 98 s of failing DNS offline is off. The issue's text was checked against the code: the hand-written MCP Semgrep tool with an `auto` default is gone (#1720), and the generated MCP tool `scan_sast` comes from `devops scan sast`, defaults to `p/default` and so gets the new argv with no code change, so the plan's MCP item needs none; `build_semgrep_cmd` served only the directory path of `devops scan sast`, while the review's file path (`security/semgrep.py`), the canary (`review/canary.py`) and the agent tool (`ai/tools/builtin_tools.py`) each built their own argv, so the "one builder" goal rewires four places; and the rule pack was added only for the review's file path with the default config. The registry fetch was checked against the live registry with a read-only GET and then with `devops review rules fetch`, twice, into a scratch user data root: `https://semgrep.dev/c/p/default` answers 200 without login with 1,074 rules, of which 28 set `options.interfile` (the `interfile: true` text appears twice per rule, in `options` and in `metadata`, so a text count says 56) and 18 name the AGPL-3.0 licence in `metadata.license`, and it sends a weak `ETag` that it answers with 304 and no body when a request carries it as `If-None-Match`. The command cached 1,074 rules the first time and reported the cached ruleset current the second, with neither file rewritten. The registry answers a client that sends `Accept-Encoding: gzip` with the ruleset as JSON (`application/json`, 2.29 MB) and a client that does not with YAML (`text/yaml`, 2.52 MB): the rules are the same, only the serialisation differs. Semgrep 1.179.0's `--validate` accepts both under a `.yaml` name, so the cache keeps the answer byte for byte, and a digest taken when the file is read describes what this client received. Whether to build the cache at all was checked against open tools: Semgrep 1.179.0 runs offline from a local `--config` file (the cached `p/default` scanned with no network and ended with no errors) and puts each rule's licence in its findings, and HTTP validators give the refetch, so the cache keeps no record of its own.

## Description

The issue is delivered in four pull requests. They are the one command builder, the registry fetch and its cache, the consumers of the cache, and the list of unscanned files. The first part makes `build_semgrep_cmd` (`config/commands.py`) the only place a `semgrep scan` argv is built, and every scan devops-cli starts goes through it. The second adds the step that downloads the registry ruleset the later parts read, and downloads it again only when it has changed. The third makes every Semgrep scan read that cache offline. The fourth lists the files that a scan left out, and measures whether batches and a budget are needed.

- **One builder.** `build_semgrep_cmd(targets, configs, exclude_paths)` emits `semgrep scan --json --metrics off --disable-version-check`, one `--config` per value, `--disable-nosem`, `--exclude` per value, `--quiet` and the targets. Semgrep's `--disable-version-check` does what `SEMGREP_ENABLE_VERSION_CHECK=0` does and shows in the argv, so no environment is passed. `--quiet` stays last before the targets. The review (a file list, or the files linked into its isolated working directory), `devops scan sast`, the agent tool and the canary call it; the pack's own `semgrep --test` keeps its command, as the issue says.
- **The rule pack always runs.** `semgrep_scan_command` (`security/semgrep.py`) adds `RULE_PACK_DIR` as a `--config` after the config a scan names, for the review's files, a directory or file of `devops scan sast` and the agent tool. Before, only the review's file path added it, and only beside `p/default`. A pack that ships in the package is always there, so the `is_dir()` guard is gone: a pack that is missing fails the scan instead of silently scanning without it. The canary runs its probe rules alone, since its expected findings and its ruleset digest are those of the probe file.
- **The agent tool takes the same flags and the pack.** It scans the whole target it is given and excludes no directory, as before, and reports every finding whatever `nosemgrep` marker it carries, as a review does. The directories `devops scan sast` leaves out are now `CONST_SEMGREP_EXCLUDED_DIRECTORIES` (`config/constants.py`) instead of a list inside `security/semgrep.py`, and only that command passes them.
- **Findings stay read from Semgrep's JSON.** The issue's criterion that findings come from `--sarif-output` is dropped, by the owner's decision. Semgrep's SARIF copies the rule's metadata, and the JSON carries the same in `extra.metadata` and `extra.severity`; `paths.scanned` is JSON only; and SARIF would need a working directory that `devops scan sast` and the agent tool, which scan in the user's tree, do not have, and a scanner fake that writes files.
- **The recording.** The Semgrep run in `tests/fixtures/scanner_runs/recorded_runs.json` is recorded again with the real Semgrep 1.179.0, through the contract suite's own adapter call, offline and from a scratch home. A recording cannot fetch `p/default`, so the contract suite's Semgrep case names a rule file of one synthetic rule in the scanned tree as its config, and the recorded command says so.
- `devops scan sast --config`'s help says the pack runs with the config; the generated CLI reference is regenerated.
- **The registry fetch.** `devops review rules fetch [--ruleset p/default] [--dry-run]`, beside `devops review rules test`, downloads the ruleset from `CONST_SEMGREP_REGISTRY_URL_TEMPLATE` through the public-only HTTP client (`new_http_client(level=EgressLevel.PUBLIC)`), reading at most `DEFAULT_SEMGREP_REGISTRY_MAX_BYTES` with a `DEFAULT_SEMGREP_REGISTRY_TIMEOUT_SECONDS` read timeout, and refusing a redirect, an error status, a transport failure or a body that is not a Semgrep ruleset with at least one rule, each with an id. Nothing runs it implicitly: a review never fetches.
- **The cache.** `security/semgrep_registry.py` writes `<user data root>/semgrep/<slug>.yaml`, the ruleset byte for byte as the registry answered, and `<slug>.etag` beside it with the ETag the registry sent. A fetch that finds both files sends the ETag as `If-None-Match`, and a 304 means the ruleset is unchanged: nothing is downloaded or rewritten. Both files are written with the repository's atomic writer, the ruleset first, so a run that stops between them leaves a ruleset whose ETag is old or missing, which the registry answers with the full ruleset: an interrupted fetch costs one download. An answer without an ETag removes the one on disk. A refused download writes nothing and leaves the earlier cache as it was.
- **What the cache does not keep.** No metadata file, rule-id list, interfile list, licence map, digest or age check: Semgrep already provides what they would record. The AGPL rules are cached with the rest, and each finding carries its rule's licence in `extra.metadata.license`. The consumers take the digest as the sha256 of the file when they read it, and the age from its modification time. If interfile rules are skipped, their ids come from the file. The OSS engine ran the 28 of them without error.
- **The ruleset name.** A registry id is a kind Semgrep's own `is_registry_id` takes (`p`, `r` or `s`), a slash and one name that `urllib.parse.quote` leaves unchanged and that is not `.` or `..`. The name therefore cannot add a path, a query or a fragment to the URL, or a directory to the cache path, and no two rulesets share the slug `<kind>-<name>`.
- **The dry run.** `--dry-run` makes no request: it lists the one GET and the two paths it would write.
- **The YAML loader.** The body is read with libyaml's safe loader where PyYAML has it, and with the pure-Python one where it does not, as `security/checkov.py` already did. The choice is now `YAML_SAFE_LOADER` in `core/serialization.py`, which both use.
- **The cache reader.** `cached_ruleset(ruleset)` in `security/semgrep_registry.py` reads the cached file once. It returns the path, the `sha256:<hex>` digest and the age in seconds from the modification time of the file. It returns `None` when the file is missing or is no longer a ruleset, which is the check the fetch applies. `is_registry_id(config)` tells a registry id such as `p/default` from a local path, `auto` or a URL, by the grammar of the fetch.
- **The fetch sets the age.** A 304 rewrites nothing. It now sets the modification time of the ruleset to now, because the registry has just confirmed the ruleset. Without it, the warning for an old cache stays after a successful fetch.
- **Edited caches.** The cache keeps no digest from the fetch. A file edited until it is no ruleset counts as missing. Examples are a file that is emptied, cut short, or has its rules deleted or its ids removed. An edit that leaves a ruleset is read as one. Its new digest shows in `profile.json` and in `devops review score`.
- **The review.** `SemgrepScanner.scan` in `security/semgrep.py` reads the cached ruleset of a registry-id `--config`. A caller can pass the ruleset it already read (`ruleset=`). The isolated scan of a review writes the bytes it read into its working directory under a name made of the digest. It names the file `./<digest>.yaml`, so Semgrep returns plain registry rule ids. The scan writes the file before it places the reviewed files, so no file of the tree can take its place as the config. A fetch that replaces the cached file during a review changes no batch: each batch scans with the bytes that the digest in `profile.json` names.
- **A missing cache in a review.** The scan names the rule pack alone. Its outcome is `coverage_gap` with the reason `The registry rules p/default are not cached, or the cached file is not a Semgrep ruleset. Run `devops review rules fetch --ruleset p/default`.` Review.md and `profile.json` show it. A scan that did not run keeps its own status, as in a dry run, an unavailable binary or a timeout.
- **The profile.** `_scan_semgrep` in `ai/review/pipeline.py` reads the cache once. It records the digest in `profile.json` as `semgrep_registry_digest`, as `osv_snapshot_digest` is recorded. It prints a warning on stdout when the cache is older than `DEFAULT_SEMGREP_REGISTRY_TTL_SECONDS` (86,400 s). The warning names the age and the fetch command. `devops review score` lists the digests of the sessions it scores beside the other input digests.
- **`devops scan sast`.** A registry-id `--config` is read from the cache. Semgrep runs from the cache directory with `--config ./<file>` and absolute targets. It returns plain rule ids and reads the ignore files of the target. With no usable cache the command prints the reason and exits 1, and Semgrep does not start. This holds for table, JSON and YAML output. An old cache is used, and the warning goes to stderr, so JSON on stdout stays clean. A dry run needs no cache, and a local `--config` needs none.
- **`devops scan report` and the agent tool.** The unified scan runs `SemgrepScanner` with its default config. It reads the cache and reports a coverage gap without one. The agent tool `scan_semgrep` reads the cache. With no usable cache it returns the reason and runs nothing.
- **Rule ids outside a review.** These three scans run Semgrep from the cache directory and name the cached file `./<file>`. `SemgrepScanner._resolve_cwd` gives the directory to the first two. `scan_semgrep` passes it as `cwd`. Their rule ids are plain, as in a review. A fingerprint, a SARIF `ruleId` and a suppression pattern see the id that the ruleset file holds.
- **The warning for an old cache.** All four consumers warn. `warn_of_old_cache` in `security/semgrep_registry.py` prints it on stderr, so JSON on stdout stays clean. The review prints it on stdout. `SemgrepScanner.scan` warns when it reads the cache itself, as in `devops scan report`. A caller that passes the ruleset it read, as the review and `devops scan sast` do, warns once.
- **The files Semgrep did not scan.** `ScanOutcome.unscanned` (`security/base.py`) maps each file that a scan left out to the reason. `merge_outcomes` keeps the files of every run, so every batch of a review adds its own. `BaseSecurityScanner.unscanned_files` is the hook, and `_handle_json_output` calls it when it has the JSON of the scanner. A run that leaves files out has the status `coverage_gap`. A scanner that does not opt in leaves none out.
- **The list of Semgrep.** `SemgrepScanner.unscanned_files` returns the files that the command named and that `paths.scanned` does not list. It reads the report of a review, and the reason is `Semgrep did not list the file as scanned`. It judges only the staged files of a review (`MaterializedTargets`), because a directory names no file. It judges only a report that holds a list under `paths.scanned`, because other reports say nothing of the files. It does not read `paths.skipped`. Semgrep fills that key only under `--verbose`, which cannot join `--quiet`, and the key held no file of a review in any probe.
- **The reason of the scan and the files it left out.** `ScanOutcome.reason` stays the reason for a gap of the whole scan, such as a missing ruleset. A scan that left files out and has no such reason has an empty reason. `_registry_rules_missing` keeps the files when it adds the reason of a missing ruleset.
- **The coverage matrix.** `_compute_coverage_matrix` (`ai/review/pipeline.py`) takes the files that each tool left out. It gives such a file the status `not scanned(<reason>)`. A fixture or a file that the tool never takes stays `skipped(...)`. A tool whose only gap is files left out is a tool that ran, so its other files are `scanned`. A tool with a gap of its own, such as a missing ruleset, keeps the gap for its other files. The matrix is in `profile.json` and in the Coverage section of review.md.
- **The report.** The Static Analyzers table shows `coverage_gap: Files not scanned: <count>. The Coverage section lists them.` beside any reason of the scan itself. `profile.json` shows the same text in `static_analyzer_reasons`. The executive summary line and the console summary name an analyzer with a coverage gap apart from the analyzers that ran (`Coverage gap: Semgrep`).
- **Batches and the budget are not built.** The plan was batches of one suffix that close at 100 files or 1.5 MB, with one budget of 300 s for the stage. Its premise was a run that took more than half of the timeout. The measurement above shows one run of 300 files at 81 to 93 s, so the plan is not needed. The batches of 100 files from #1079 stay, because a batch that runs out of time loses only its own files. The comment on `DEFAULT_SEMGREP_REVIEW_BATCH_FILES` carries the new figures.
- **The open tool and the cost.** Semgrep gives its own JSON (`paths.scanned`), and the code uses it as it is. The code maps that key into `ScanOutcome` and nothing more: about 25 lines in `security/semgrep.py`, 25 in `security/base.py` and 75 in `ai/review/pipeline.py`. It took about 350,000 tokens and two hours to build, test and measure. The fixes after the review took about 100,000 tokens and 30 minutes more. The upkeep is the one key that the mapping reads. The recorded run and the real-tool probes above guard it.
- **A limit.** Devops-cli drops some files before Semgrep sees them. They are the files of an excluded extension (`_scannable_files`) and the targets that `materialize_targets` leaves out, such as a link that resolves outside the tree. These files never show as not scanned, and the matrix shows them as scanned. This was so before this change.
