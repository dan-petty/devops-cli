# Task: Criteria Settle a Verdict Only on Evidence About the Cited Code, and the Verifier Judges the Claim, Not the Pipeline's State (#846)

**Issue**: [#846](https://github.com/dan-petty/devops-cli/issues/846)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p1-high
**Scope**: scope/review

## Description
A verdict the criteria settle is final: the finding never reaches the verifier. Any passing invalidation criterion settled INVALIDATED, so `git grep -n os.system app.py`, which only finds the line a finding cites, dismissed the finding. In review session `20261001-224227`, 36 findings were VERIFIED by criteria and none of their 37 passing commands checked the cited code (a regex echoed against a literal on a CRITICAL finding citing CVE-2021-44228, `git log --grep`, version prints), and 59 of 61 criteria-INVALIDATED findings rested on the same kind of command. The verifier was also shown the reviewer's confidence and status and the criteria results with their run times, so a prompt for a finding whose criteria ran was never sent twice, and the branch reviews of release/v0.2.25 replayed only 3 and 6 verifier replies from the response cache.

#951 (38517a8) took the prompt half of this issue: it replaced the `git grep` examples in `review_output_instruction.md` and `compose.md` with assertion criteria, and `review.md` and `review_output_instruction.md` say a command that only finds, imports or prints code proves nothing. #949 (e4ea2e0) added `_VERDICT_FIELDS` in `ai/review/adjudication.py`, which mirrors a person's verdict between candidates.json and findings.json; it is not beside `apply_verdict` and the pipeline's copy-back did not use it. This item owns the executor and the verifier's input.

- **Evidence rule** (`ai/review/criteria_evidence.py`, new): `counts_as_evidence(command, location, repo_root)` says whether a passing command shows anything about the code a finding cites. A `python -c` script counts when it checks a value from the cited code: a name it imports from the cited module (as named from the repository root or from `src/`, both on the criteria's `PYTHONPATH`, a submodule included), the cited file read (`read_text`, `read_bytes`, `open`) and parsed (`json.loads`, `yaml.safe_load`, `tomllib.loads`, `ast.literal_eval`), or a value computed from either, followed through assignments, loops, `with`, caught exceptions and function returns. The check is an `assert` over such a value; a `raise`, or an exit with a failing status, under an `if`, `while`, `and`/`or`, `match` or `try` over one; or `sys.exit`, `exit`, `quit`, `os._exit` or `raise SystemExit` of a comparison, `not`, `and`/`or` or conditional over one. It does not count a search of a cited file's text, so a cited Python file counts only through its import; an existence test (`assert f`, `app.f is not None`, `Path(p).exists()`, `os.path.isfile(p)`); a check that does not depend on the cited code (`import app; assert 1 == 1`, `raise SystemExit(0)`, `exit(0)`); `sys.exit(f(...))`, which exits 0 whenever `f` returns None; or a script that inspects code (a call to `hasattr`, `getattr`, `isinstance`, `type`, `callable`, `dir`, `vars`, `getsource`, `signature`, `getmembers`, `getfullargspec`, or the attributes `__code__`, `co_varnames`, `__dict__`, `__annotations__`, `__signature__`, `__wrapped__`). `pytest` or `python -m pytest` counts only when a test file it names, inside the repository, imports the cited module, and no option ends the run before a test runs (`--collect-only`/`--co`, `--version`/`-V`, `--help`/`-h`, also inside a cluster such as `-qh`, `--fixtures`, `--fixtures-per-test`, `--markers`, `--setup-plan`, `--setup-only`, `--cache-show`; each exits 0 under pytest 9.1.1 with a failing test). `is_tautological_criterion(command)` asks the same without a finding, taking any module outside the standard library as the cited one; the prompt-example test uses it. Both read the script's syntax tree; the substring list they replace (`CONST_TAUTOLOGICAL_CRITERIA_SUBSTRINGS`) took `content_type(` for `type(` and matched message words such as "successfully". The name sets are in `config/constants.py`: `CONST_REFLECTION_CRITERIA_CALLS`, `CONST_REFLECTION_CRITERIA_ATTRIBUTES`, `CONST_READING_CRITERIA_CALLS`, `CONST_PARSING_CRITERIA_CALLS`, `CONST_EXISTENCE_CRITERIA_CALLS`, `CONST_EXIT_CRITERIA_CALLS`, `CONST_PYTEST_NON_RUNNING_OPTIONS`, `CONST_PYTEST_SHORT_OPTIONS_WITH_VALUE`, and `CONST_PYTHON_CRITERIA_BINARIES`, defined with the same text and in the same place as #847 defines it, so the two merge into one definition.
- **Criteria verdict** (`ai/review/review_environment.py`): `_reconcile_finding_from_criteria` takes `repo_root` and keeps, of the passing commands, those that count. Passing commands on both sides, whether or not they count, leave the finding UNVERIFIED with the note `criteria-non-discriminating` (`CONST_CRITERIA_NON_DISCRIMINATING`), as the issue decides and as 79e1e93 left such a finding unverified. A counting invalidation command settles INVALIDATED; counting verification commands settle VERIFIED once every verification command ran, at the share of distinct verification commands that count, so one command listed on both sides no longer scores 2.0. Anything else settles nothing: the results are recorded in `criteria_execution_results`, the matched lists hold only counting commands, and no confidence is written. `_evaluate_criteria_verdict` returns a `_CriteriaVerdict` or None. The PATH, allowlist and timeout code #847 changes is untouched.
- **Verifier input** (`ai/review/verification.py`): `_build_validation_prompt` sends each finding's fields named in the allowlist `CONST_VERIFIER_FINDING_FIELDS` (`config/constants.py`), the issue's list: `finding_id`, `severity`, `location`, `title`, `description`, `fix`, `references`, `category`, both criteria lists as written, `observed_value` and `expected_value`. A field added to `Finding` stays out of the verifier prompt until it is listed there. `category` is no longer in the reviewer's reply schema (#951), but a reply that gives one under its aliases still parses into it, and it is part of the claim. The reviewer's `confidence_score`, `status`, `reportable` and `thinking`, the criteria results and matched lists, and every other pipeline field are gone, so the prompt for a finding is the same whatever its criteria's run times.
- **Citations and refutations**: `_extract_citation_line(item)` reads only `citation_line`, `cited_line`, `line` and `refutation_line`, never the echoed `location` or a number in the reason, so a refutation without one is downgraded by the existing missing-citation rule. An INVALIDATED verdict that cites no line and whose reason matches `tautolog|criteri\w+ (only|merely)|only confirms` becomes UNVERIFIED with its own note, "Refutation is about the criteria, not the code, and cites no line; downgraded to UNVERIFIED"; with a citation it stands.
- **Verifier coverage**: `_awaits_verdict` names the findings the verifier is shown. A shown finding the reply gave no verdict on gets `verifier-no-verdict`, and when the reply holds no list of verdicts every shown finding gets `verifier-reply-unparsed` (`CONST_VERIFIER_NO_VERDICT`, `CONST_VERIFIER_REPLY_UNPARSED`). An empty list is a reply with no verdicts. A reply whose `finish_reason` is `length` binds no verdict, whatever JSON repair (`core/serialization.py`, since 22bba04) salvages from it: `_validate_segment_findings` reads the reason from the client's `LLMResponse` before parsing and gives every shown finding `verifier-reply-cut` (`CONST_VERIFIER_REPLY_CUT`). Its complete verdicts are dropped with the cut one, since which of them repair closed cannot be told from the parsed list. `_mark_degraded_findings` marks the same findings through `_without_verdict`. A file whose verification raised (in `_safe_verify_file_payload`, or in a verification worker of `execute_finding_verification`) is skipped, but its findings are still reported, so `_note_verification_unavailable` (`ai/review/pipeline.py`) gives each unverified one without a note `verification-unavailable: <exception type>`; a verdict or note the copy-back had already written stays. A finding the verifier judged and left unverified, with no note from the checks on its verdict (missing or wrong citation, a refutation of the criteria, a mitigation without its mechanism), gets one from `_no_verdict_note` (`_apply_single_finding_verification`): `verifier-self-refutation` when `_without_self_refutation` withdrew its invalidation, `criteria-non-discriminating` when the criteria noted that, and otherwise `verifier-inconclusive`, for a verdict that neither confirmed, refuted nor found a mitigation, or both confirmed and refuted (`CONST_VERIFIER_SELF_REFUTATION`, `CONST_VERIFIER_INCONCLUSIVE`). `_without_self_refutation` now also says whether it withdrew an invalidation, and leaves a verdict that never refuted (`_refutes`, shared with `_verdict_status`) as it is, so a verdict whose reason only states the claim is inconclusive, not a withdrawn refutation. A finding the verifier was shown therefore never stays unverified without a note. `compute_verdict_distributions` gains `verification_note`, the unverified findings counted by note kind (`CONST_VERIFICATION_NOTE_KINDS`, `other`, `none`), which `profile.json` carries in `verdict_distributions`; `none` is left for findings verification never reached: all of them when verification is turned off, and those of a file whose persona review failed part-way, which keeps the findings it had and is not verified.
- **Verdict fields** (`ai/review/verdicts.py`): `VERDICT_FIELDS` lists every field verification owns, the verdict `apply_verdict` writes, its criteria evidence, and what the verifier rewrites (severity, location, `relocated_from`, observed and expected values). The copy-back in `ReviewPipelineOrchestrator._verify_single_file_payload` copies exactly those; its hand-kept list dropped the verifier's severity. `apply_verdict` clamps `confidence_score` to [0, 1]. `reset_verification_state` also clears `confidence_score`, `citation_line`, `mitigating_mechanism`, `perimeter_files`, `regression_test` and `criteria_execution_results`.
- **Tests**: `tests/test_finding_repetition_compression.py` no longer reads `.data/cache`. `tests/golden/criteria_replay.json` holds the three worst findings of session `20261001-224227` and its one finding still VERIFIED by criteria under the first draft of the rule (`k8s/logs.py:64`), with the results it recorded. Existing tests that relied on a citation from the reason or the echoed location give `citation_line`, and those that verified with `print(1)` or arithmetic assert over the cited code.
- The changelog entry is `changelog.d/846.md`.
- Left as they were: adjudication's `_VERDICT_FIELDS` (#949) still mirrors a person's verdict between the session files; it must not carry the verifier's severity or location onto a consolidated copy, so it stays the narrower list. `docs/SELF_IMPROVEMENT.md`'s session logs still name `_is_tautological_verification_command` and `CONST_TAUTOLOGICAL_CRITERIA_SUBSTRINGS` as what those sessions changed. A script whose outcome rests only on an early successful exit followed by a failing one (`if ok: sys.exit(0)` then `sys.exit(1)`), or that star-imports the cited module, does not count; its finding goes to the verifier.
