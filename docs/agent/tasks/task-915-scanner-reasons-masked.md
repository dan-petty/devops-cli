# Task: Scanner Failure Reasons Are Masked and Capped Before SARIF, the CLI and review.md Print Them (#915)

**Issue**: [#915](https://github.com/dan-petty/devops-cli/issues/915)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p1-high
**Scope**: scope/security

## Description
A scanner's `ScanOutcome.reason` quotes an exception, stderr or, since #1009, the start of output that was not JSON. SARIF writes it into `toolExecutionNotifications[].message.text` (`security/sarif.py`, `_notification_for`), `devops scan report` and the single-scanner commands print it as a warning, and since #1009 review.md's Static Analyzers table writes it after a failed analyzer's state. Nothing masked it. Some producers, dive's among them, cut it to 256 characters before anything could mask it, and that can split a credential so that no pattern matches the part left. `devops scan report` and `ScannerRegistry.scan_all` stored `str(exc)` with no cap at all. The warnings were printed as Rich markup, so a reason with `[/x]` stopped `devops scan report` with a `MarkupError` after it had written the SARIF file.

- **One choke point** (`security/base.py`). `ScanOutcome.__init__` stores `masked_reason(reason)`, a new public function that returns `_cut(mask_secrets(reason), CONST_MAX_ERROR_DETAIL_LENGTH)`: the reason is masked, then cut to 256 characters, and ends in `…` when cut, as #1009's reasons did. Every producer builds a `ScanOutcome`, so this covers `base.py`, `registry.py`, `pipeline.py`, `dive.py` and `gitleaks.py` alike, as long as no producer cuts the text first. `_cut` is the cut that `_one_line` already made, now shared by both.
- **The early cuts are gone** (`security/base.py`). `_non_json_failure_reason` no longer cuts stderr to `[:256]` when stdout is empty, and no longer cuts the whole reason to `CONST_SCANNER_FAILURE_REASON_CHARS` (300). It still folds whitespace, so the reason stays on one line. `_handle_json_output` drops its `stderr.strip()[:256]`, and `_run_scanner_command` drops its `str(exc)[:256]`. Its built-in-patterns reason, `Scanner error: {exc}; used built-in patterns`, was neither masked nor cut and is now both, through `ScanOutcome`. The quote of the start of stdout is still cut to `CONST_SCANNER_STDOUT_EXCERPT_CHARS` (100), and that cut happens inside the reason, so `_non_json_failure_reason` masks stdout before it cuts the quote.
- **One cap** (`config/constants.py`). `CONST_SCANNER_FAILURE_REASON_CHARS` is removed. Every scanner reason is capped at `CONST_MAX_ERROR_DETAIL_LENGTH`.
- **One handler** (`security/registry.py`, `commands/scan.py`). `ScannerRegistry.scan_all(target_path, *, names=None, timeout=..., **kwargs)` runs the named scanners, or every registered one in `list_scanners()` order, and records a scanner that raises as `ScanOutcome("failed", [], str(exc))`. It looks scanners up through `get`, so the tests in `tests/test_security_sarif.py` that patch `ScannerRegistry.get` and `list_scanners` still drive `scan report`. `scan report` checks for unknown names as before, then calls `registry.scan_all(target_abs, names=selected)` in place of its own try/except loop. `scan_report`'s cyclomatic complexity drops from 11 to 8 (`devops_cli.security.complexity`). The unused `image` parameter is gone; `image=` still reaches each scanner through `**kwargs`. `scan report` now passes `timeout=DEFAULT_SECURITY_SCANNER_TIMEOUT_SECONDS`, which is the default `scan()` used anyway.
- **Dive** (`security/dive.py`). `_run_dive_export` cut dive's stderr (or stdout) and its exception text to 256 characters for `DiveAnalysisResult.reason`, with no masking. `DiveScanner` passes that reason to `ScanOutcome`, which could then mask only what survived the cut: a private key whose END marker fell past the cut was not recognized and reached SARIF and the CLI through `scan report`. `devops docker analyze-layers` and the `docker_analyze_layers` tool print the same reason with no masking at all. Both reasons are now built with `masked_reason`, so dive's reason is masked, then cut, for all three. Going through `ScanOutcome` masks it a second time, which leaves it unchanged.
- **Safe printing** (`commands/scan.py`). `_handle_single_scanner_result` (used by `scan trivy`, `secrets`, `sast` and `iac`) and `_warn_missing_scanners` (`scan report`) call `print_warning(..., safe=True)`, which escapes markup.
- **review.md** (`ai/review/pipeline.py`, unchanged). `_static_analyzer_reasons` reads `ScanOutcome.reason`, which is now masked and capped, so the Static Analyzers row for a failed analyzer carries the masked reason.
- **Left as they were.** The `logger.debug` lines in `_run_scanner_command`, `scan_all` and `_run_dive_export` still log the raw exception at DEBUG.
- **Changelog** (`changelog.d/1009.md`). #1009's fragment, unreleased like this one, said its reason keeps as much of stderr as fits in 300 characters. It now says 256, so the assembled v0.2.25 entry never describes the 300-character cap.

## Acceptance Criteria
- [x] `ScanOutcome.__init__` masks the reason before it caps it, and the `[:256]` slices in `security/base.py` are gone. Before this change they were at lines 150 (`_non_json_failure_reason`), 203 (`_handle_json_output`) and 339 (`_run_scanner_command`), with the unmasked, uncapped `Scanner error: {exc}; used built-in patterns` at 337. Evidence: the tests below, plus `test_a_failed_scan_masks_its_output_before_cutting_the_quote` (`tests/test_consolidation_security_scanner_base.py`). That test gives a failing scanner stdout of 87 `x`, a space and a token. The quote is `"x" * 87 + " <masked-git…"` and holds no part of the token. On 79e1e93 the quote ended in `ghp_Q7rT2xW…`, the token's first 11 characters, which are too few for the `ghp_` pattern to match.

Before this change they were at `commands/scan.py` lines 99, 793 and 795. `test_a_reason_holding_markup_prints_literally[report-failed|report-unavailable|trivy-failed]` (`tests/test_scan_outcomes_and_gating.py`) gives a reason with `[/x]` and finds the line printed literally, with exit code 0.
