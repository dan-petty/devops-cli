## Description
A triage of review session 20261001-224227 against `release/v0.2.25` (c279c18) confirmed three defects in the `k8s/` manifests. Each is fixed as the issue's **Fix** line says, with the differences noted below, and each has a regression test that fails on the base revision and passes here. The items merged into `release/v0.2.25` since the issue was written (#846, #847, #915, #948, #949, #950, #951, #987, #1009) touched none of the manifests or functions this change fixes, and none had already met an acceptance criterion: da50329 still has `svc/ollama`, the `0.0.0.0/0` peer and the top-level `securityContext`. Their only overlap with this change's files is `src/devops_cli/config/defaults.py`, where #948, #950 and #847 each added an unrelated constant. #951 only made the NodePort rule in `.devops/review.md` cover all of `k8s/`, so deleting `values-ollama.yaml` leaves that rule's test passing.

- **Monitoring ingress.** Ingress rule 2 of `k8s/monitoring/networkpolicy.yaml` loses its `ipBlock: 0.0.0.0/0` peer and keeps the kube-system/Traefik peer with all ten ports. kube-router matches ingress CIDRs against pod addresses, so the peer admitted every pod in the cluster to Prometheus (no authentication, remote-write receiver) and Grafana (anonymous Viewer). Nothing else outside the namespace needs these ports: the Cloudflare tunnel reaches them through `cloudflared`, whose own policy forwards only to Traefik; the `otel` collector's writes on 9090 and 4040 have rule 3; and the only manifest outside `monitoring` that names a monitoring Service is the collector's remote write. The rule's comment names the real sources, and `kubectl port-forward` needs no rule because it enters the pod's own network namespace. For the `configure-urls --addressing proxy` caveat the issue offered two answers, and this change documents it instead of adding a narrow `ipBlock`. That ipBlock would be the control-plane node's flannel address, a concrete RFC 1918 address that AGENTS.md and `.devops/review.md` forbid in `k8s/` manifests, and it differs per cluster. The policy comment and a new paragraph in `k8s/README.md` (*Port Forwarding & Automated Configuration*) say that kube-router admits host-network traffic only to pods on the same node. The API server proxies from the control-plane node, so Grafana, Prometheus and Pyroscope answer proxy addresses only while they run there; port-forward and `fqdn` work wherever they run. deploy-stack still does not apply this policy, which is #913.
- **Qdrant security context.** `k8s/llm/values-qdrant.yaml` replaces the top-level `securityContext`, which the `qdrant/qdrant` chart never reads, with `containerSecurityContext`: `runAsNonRoot: true`, `runAsUser: 1000`, `runAsGroup: 1000` (matching `podSecurityContext`), `allowPrivilegeEscalation: false`, `privileged: false`, `readOnlyRootFilesystem: true`, `capabilities.drop: [ALL]` and `seccompProfile.type: RuntimeDefault`. `updateVolumeFsOwnership: false` stays. The chart (1.19.1, `charts/qdrant` read with read-only `gh api` into a scratch directory) was rendered with `helm template` against both values files. The old values gave the chart default (`runAsGroup: 2000`, no capabilities, no seccomp profile). The new values give exactly the block above, with no `ensure-dir-ownership` init container, and the chart mounts writable volumes at `/qdrant/storage`, `/qdrant/snapshots` and `/qdrant/init`. `CHANGELOG.md:652` is history and is not edited.
- **Single-Ollama leftovers.** `k8s/llm/ollama-host-service.yaml` and `k8s/llm/values-ollama.yaml` are deleted, with the `values-ollama.yaml` line in `k8s/README.md`'s tree and section 2 of `test_k8s_workload_resource_limits_and_probes` (`tests/test_k8s.py`, later sections renumbered). The README's Ollama access line `minikube service ollama -n llm --url` described the deleted Service and now reads `kubectl -n llm port-forward svc/ollama-16gib 11434:11434`. The other leftovers:
  - Portkey's Ollama egress rule selects `llm.devops.io/provider: ollama` on 11434. Portkey stays, since it is still a configured gateway provider (`CONST_AI_GATEWAY_PROVIDERS`).
  - `devops k8s port-forward --stack llm` (`_collect_port_forward_services`) forwards the default Ollama tier, `DEFAULT_OLLAMA_CLUSTER_SERVICE` (`ollama-16gib`, new in `config/defaults.py`), so the Ollama forward works again. `DEFAULT_OLLAMA_CLUSTER_URL` is built from it. Nodeport `configure-urls` (`_configure_llm_stack_urls`) looks up the same Service instead of the missing `ollama`, but that changes nothing it configures: `ollama-16gib` is ClusterIP, and every detection path (`KubernetesService.resolve_service_endpoint`, `minikube service`, `_extract_service_ingress_or_nodeport`) returns an address only for a LoadBalancer or NodePort Service. It sets `ai.ollama_urls` to `http://localhost:11434` only while something answers there, as it did before, and now the forward can answer there. A tier and not the gateway, because the endpoint lands in `ai.ollama_urls`, which takes Ollama's native API, and the gateway serves only the OpenAI one. `ollama-16gib` is also the tier the router's default routes and the `ollama-ingress` route address. `test_configure_urls_persists_all_llm_endpoints` (`tests/test_k8s_bootstrap.py`) builds each URL from the Service name it is asked for, so it now expects that tier's name.
  - The direct-Ollama failover in `ai/gateway.py` returns `DEFAULT_OLLAMA_CLUSTER_URL` instead of `http://ollama.llm.svc.cluster.local:11434`.
  - `generate_homelab_tls_bundle` drops the `ollama.llm.svc.cluster.local` SAN; `*.llm.svc.cluster.local` still covers the tiers.
  - Left to their owners: the gateway policy's `app.kubernetes.io/name: ollama` and `ollama-volta-1` selectors and its RFC 1918 ipBlock rule (#795, whose key questions take them), and the vLLM rules in the Portkey and monitoring policies (#820). The README's GPU placement section, which still describes an `ollama` StatefulSet, is #795's.
  - `test_zero_homelab_ip_or_hostname_leakage` now scans every `k8s/llm/**/*.yaml`, as the issue's optional step suggests; it found only `192.168.49.1` in the deleted bridge.
