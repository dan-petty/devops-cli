# Task: Closure closes the items delivered into a release whose milestone has already closed (#1362)

**Issue**: [#1362](https://github.com/dan-petty/devops-cli/issues/1362)
**Status**: Done
**Milestone**: v0.2.29
**Priority**: priority/p1-high
**Scope**: type/bug, scope/release

## Description

On 2026-10-07 the v0.2.28 milestone closed while #1295, #1296, #1297 and #1341 were still open, although the pull requests that deliver them had merged into `release/v0.2.28`. Closure (`devops roadmap close`, #743) read only the current release, the lowest-numbered open Release. Once a milestone closed, no later run read its branch again, so one missed run before the ship left delivered items open for good, and nothing reported them. Six writers close milestones (release.yml, `devops gh milestones close` and `edit`, `devops release tag --push`, reprioritize, the MCP tools), and so can a person in the web UI. This change fixes what closure reads, not those writers.

- **Shipped releases first.** `plan_close` (`src/devops_cli/roadmap/close.py:400`) finds each closed Release that holds an open issue from the `store.issues()` it already reads, not from `Release.open_issues`, which also counts pull requests. In version order, `_shipped_closure` (`:351`) reads the pull requests merged into the release's branch and runs the same `_closings` (`:270`), with the same comment template and the same rule that a pull request whose check runs can't be read closes nothing. Each result is a `ShippedClosure` (`:112`) holding the release, its closings, its unread pull requests, the items left open and the items a person reopened.
- **The branch the cut makes.** Both the shipped reads and the current release's read take the branch from `release_cut_branch`, `release/vX.Y.Z`, the branch the cut pushes, not from the milestone's title. A milestone a person titled `0.2.25` is still read from `release/v0.2.25`.
- **An item a person reopened stays open.** A job never reverts a person's change (ADR 0002). An open item whose `state_reason` is `reopened` (`_reopened`, `:343`; `CONST_GH_ISSUE_STATE_REASON_REOPENED`) is left out of the shipped `_closings` and named under its release as reopened by a person. No roadmap job reopens an issue, so that reason marks a person's reopen. GitHub keeps it in the issue listing the run already reads, so this costs no request, and a shipped release whose only open items a person reopened has no pull request read at all.
- **Only that release's own items.** A shipped release's `_closings` gets only the issues in that release. An issue a person reopened and moved to another release is never closed through an old branch, and a current-release item is never closed by a shipped pull request, which would hold the current cut on `OPEN_ITEMS` for that run.
- **One issue is closed once.** The current release's `_closings` gets the issues minus the numbers the shipped reads already planned.
- **One item, one line.** A shipped release's open item that a pull request into the current release's branch closes is a closing. After the current release's read, `_without` (`:390`) drops the current closings from each shipped release's open and reopened items, so the text never names one item both as still open and as closed.
- **The current release's cut reads only the current release.** `_plan_current` (`:433`) is the former body of `plan_close`. `_held` (`:498`) now takes the current release's own unread pull requests, open items and completed items, not `plan.unread`. So an open item in a shipped release, or a shipped pull request with unreadable check runs, holds no cut.
- **The plan's shape.** `ClosePlan.closings` and `ClosePlan.unread` list the shipped entries first and then the current release's. A new `ClosePlan.shipped` carries each shipped section for the text. `apply_close`, `has_writes`, the Service adapter's `closed_items` and the CLI's exit 1 on any unread (`src/devops_cli/commands/roadmap.py:477`) are unchanged.
- **With no current release.** Shipped closings are still planned, and the run then holds `NO_RELEASE`. The issues listing is read only when a release is current or a closed Release's milestone counts an open issue or pull request (`_counts_open`, `:329`, an upper bound used only to skip the read). A run with no closed Release holding an open issue makes the requests it made before. The one difference is order: the issues listing now comes before the current release's merged pull requests.
- **Text output.** `render_close` (`:530`) prints a section for each shipped release before the current release's lines: a heading, its closings with their comments, its unread pull requests, "Still open in vX.Y.Z, holding no cut:" with the open items left, and "Reopened by a person in vX.Y.Z, so closure leaves it open, holding no cut:" with the items a person reopened. When a shipped section comes first, the current release's lines get a heading of their own.
- **Dry run.** `close_requests` (`src/devops_cli/roadmap/request_plan.py:582`) lists the issues read under its own condition, then the shipped release's merged pull requests, files, check runs and task files under "a closed Release holds an open issue no person reopened", repeated for each such Release, oldest first, and then the current release's reads. It still makes no request.
- **Texts.** These now say that closure also covers a closed release that still holds an open issue: the module docstring, `HELP.roadmap.close` (`src/devops_cli/lang/en/help.py:1011`, only the "what closure reads" clause), the `roadmap_close` MCP docstring (`src/devops_cli/ai/mcp/server.py:757`), and `docs/ROUTINE_TASKS.md:245` and `:262`. `README.md`, `docs/CLI_REFERENCE.md`, `docs/commands/roadmap.md` and `docs/MCP_TOOLS.md` were regenerated with `devops docs generate --sync-readme`.

## Decisions and deviations

- **A shipped release closes only its own items.** The issue planned the shipped `_closings` over every issue. The skeptic review found that this would re-close, on every run, an issue a person reopened and moved to another release, with a comment claiming delivery. If that issue was in the current release, it would also hold the current cut on `OPEN_ITEMS` for that run. Limiting each shipped read to its own release fixes both. An issue with no milestone that a shipped pull request names stays open, as it did before this change.
- **"Still open", not "undelivered".** The section lists every open item of the shipped release that the run does not close. That includes an item whose pull request's check runs could not be read: the unread line above it says which those are. A plain "delivered by no merged pull request" label would be wrong for them.
- **The issues listing is gated when no release is current.** Gating it on `Release.open_issues > 0` keeps "no extra listing" true for a run with no open Release. This is the assessment's amendment 1. The dry run gives that read its own condition, so the plan and the run agree.
- **The requests test lives in `tests/test_roadmap_dry_runs.py`.** The issue asked for it in `tests/test_roadmap_close.py`. It sits beside the other "a real run's argv is its plan" tests so that it can reuse their `_Gh` process-edge fake, `open_roadmap` and `follows`. `follows` now also reads a URL-quoted placeholder (`%3C…%3E`) as a placeholder; without that, no close plan could be followed, since its listings quote the branch.
- **The cost of a shipped read.** Each closed Release that holds an open issue costs one REST listing of its merged pull requests, plus one files listing for each of them. For each such pull request whose body names an open item of that release, the checks reader also runs `gh pr checks`. That is a GraphQL read in `gh`, although `run_gh` and the dry run class it as core REST (#1415). With no such Release, nothing is added.
- **The Service adapter still ignores `plan.unread`.** The CLI exits 1 when a pull request's check runs can't be read. The Service's close adapter (`src/devops_cli/roadmap/run.py:349`) does not look at `plan.unread`, so in the Service such a pull request is retried on the next run without a failure or a log line. Nor does it report a shipped release's open or reopened items. That predates this change, which does not alter it; #1414 covers both.
- **The in-memory store reopens as GitHub does.** GitHub sets an issue's `state_reason` to `reopened` when it is reopened and keeps it while the issue is open. `InMemoryRoadmapStore.reopen_issue` (`src/devops_cli/roadmap/memory_store.py:310`) set it to none, so the reopened test could not go through a person's reopen. It now sets `reopened`, and `test_a_person_reopens_a_closed_issue_in_its_release` in `tests/test_roadmap_store_contract.py` asserts that. No other test depended on the old value.
- **A reopened item stays open even when a later pull request delivers it.** GitHub keeps `state_reason` at `reopened` while the issue is open, and the issue listing does not say when it was reopened. So a pull request merged into the shipped branch after the reopen does not close the item either. The run names it under its release, and a person closes it. Telling such a pull request apart needs the issue's timeline, one more read per reopened item, which #1417 weighs for both reads.
- **Reopened items are skipped only in the shipped reads.** The current release's `_closings` still closes any open issue a pull request merged into its branch names, as it did before this change, including one a person reopened after an earlier run closed it. That predates this change and is #1417.
- **Premises checked live on 2026-10-08.** No closed milestone counts an open issue, so the normal case adds nothing. Release branches are deleted when the release pull request merges: `release/v0.2.28` returns 404. Yet `pulls?state=closed&base=release%2Fv0.2.28` still lists 31 closed pull requests, 30 of them merged, and merge commit f67f554 of #1304 still resolves, so a shipped branch's pull requests and their task files at the merge commit can still be read.
- **Line references moved** on the release branch from the ones the issue cites: `store.py:217-229` and `:731`, `github_store.py:1256`, `:1275`, `:1328-1330` and `:1507-1509`, `release.py:2004` and `:2081-2090`, `server.py:757`, `:1800` and `:1811`, `help.py:1011`, `request_plan.py:582`.
- **No writer changes.** release.yml, the milestone commands, `devops release tag`, reprioritize and the MCP tools still close milestones whatever their items. With this fix the order no longer matters.
