## Description
A triage of review session 20261001-224227 against `release/v0.2.25` (c279c18) confirmed five defects in the agent and harness modules, each upheld by a second agent that tried to refute it. Each is fixed as the issue's **Fix** line says, with the differences noted below. Each has a regression test that fails on the base of this branch (e3ff98c) and passes here. The issue's comment adds three unused classes, which are deleted too.

- **Toolset instructions.** `_extract_single_toolset_instructions` (`ai/agents/agent.py`) asks a devops-cli `AbstractToolset` for its instructions with no context, which answers with a list. Any other toolset, devops-cli's `FunctionToolset` among them, is asked with the run's context, or a fresh `RunContext` when there is none, so a dynamic (callable) instruction renders too. Its coroutine is driven by `_await_outside_event_loop` (`ai/agents/runner.py`). That helper runs it with `asyncio.run` when no event loop is running in the thread. Otherwise it closes the coroutine and writes a debug record naming what it skipped. Inside a running loop devops-cli's `FunctionToolset` is asked without a context instead, which gives its static text. Its synchronous `get_instructions()` (`ai/toolsets/__init__.py`) writes a debug record for each dynamic instruction it leaves out. `run_async` calls `run` in an executor thread, so no loop runs there. A toolset that raises is logged as a warning. The str, `.content`, list and tuple result shapes are handled as before, now in `_instruction_texts`. pydantic-ai's own toolsets were dropped with or without a context, which the issue did not list. Prompt assembly stays synchronous. `run_stream_async` builds its prompt on the loop thread, so a pydantic-ai toolset's instructions and a devops-cli `FunctionToolset`'s dynamic ones are skipped there, with the debug records. A review of this change found that its first version asked devops-cli's `FunctionToolset` without a context even when the run had one, so a callable instruction was left out of every run without a log record, while a pydantic-ai `FunctionToolset` rendered it. The synchronous path also lost its unreachable branches: pydantic-ai keeps a toolset's instructions as a list of strings and wrapped functions, never a bare string or an item with `.content`.
- **Deferred-tool context.** `_find_deferred_tool_handler(capabilities, req, ctx=None)` is called with the loop's context from `PydanticAgent._dispatch_tool_calls`. `HandleDeferredToolCalls.handle_deferred` chooses the call by the handler's signature alone. A handler that can be called with the requests alone, by `inspect.signature(handler).bind(None)` in `_accepts_positional_arguments` (`ai/agents/capabilities.py`), gets them alone. Any other gets `(ctx, requests)` as pydantic-ai calls it, with `RunContext()` when there is no context, as `ProcessHistory` and `ProcessEventStream` do. The review found that the first version counted every parameter, so `approve(requests, **kw)`, `approve(requests, *, note='')` or `approve(requests, ctx=None)` was called with the context first and the run ended with an error, where the base, which never had a context in the loop, called it with the requests. The generic hook path had a second crash, outside the issue's text. Every capability inherits pydantic-ai's async `handle_deferred_tool_calls(ctx, *, requests)`, and `getattr(cap, "handle_deferred_tool_calls", None) or ...` always found it, then called it with the requests alone. So a run with `[Thinking()]`, or with any capability ahead of `HandleDeferredToolCalls`, died with `TypeError: ... missing 1 required keyword-only argument: 'requests'` once a tool needed approval. `_call_deferred_hook` calls that hook only when the capability overrides pydantic-ai's no-op, as `hook(ctx, requests=req)`. Otherwise a `handle_deferred` method, whose context comes second as in `HandleDeferredToolCalls.handle_deferred`, gets `(req, ctx)` when it can take two positional arguments, by the same helper, and `(req)` when it cannot. `_find_deferred_tool_handler` runs a coroutine answer with `asyncio.run` when no event loop is running in the thread. Inside a running loop it cannot. It then closes the coroutine, logs a warning naming the capability's class, and stops the lookup. The requests go back to the caller as `DeferredToolRequests`, as when no capability resolves them, so no later capability decides in place of a hook that could not run. A review of this change found that its first version logged at debug level and went on to the next capability instead. Then a deny hook ahead of an approving `HandleDeferredToolCalls` was skipped, and the approval-required tool ran. On the base the same run ended with the `TypeError` above, so nothing ran. Only `run` called from synchronous code inside a loop gets here, since `run_async` calls `run` in an executor thread. A result that is not `DeferredToolResults` resolves nothing. Before, any non-`None` value was cast to one.
- **Sampling-model stub.** The issue's preferred fix: `MCPSamplingModel` is deleted from `ai/agents/models.py`, with its re-exports in `ai/agents/__init__.py` and `ai/agents/pydantic_agent.py` and step 7 of `test_mcp_toolset_and_capability`. `PydanticAgent.set_mcp_sampling_model`, which sets `MCPToolset.sampling_model`, is a different thing and stays, as does the knowledge-base example that calls it.
- **SQLite memory.** The issue's preferred fix: `SqliteMemoryStore.database` has no default. A `field_validator` refuses the names in `CONST_SQLITE_PER_CONNECTION_DATABASES` (`config/constants.py`): `:memory:`, and the empty name, which gives each connection a temporary file that is deleted when it closes. Without `uri=True`, `sqlite3.connect` opens no other name as a private database, so the set is complete. The refusal raises `HarnessValidationError`, which pydantic reports as a `ValidationError`. The field takes a `str` or a `Path`. The docstring says why the name must be a shared file and points at `InMemoryStore`.
- **Shell process groups.** `Shell._terminate_process_group` (`ai/harness/shell.py`) signals `proc.pid` itself, since `start_new_session=True` makes it the group id for as long as any member lives. It refuses a non-int pid, 0, 1 and this process's own group. SIGTERM finding no member ends the call. Otherwise it reaps the leader with `proc.poll()` and probes the group with signal 0 every `DEFAULT_SHELL_STOP_POLL_SECONDS` (0.05 s), until no member is left or `stop_grace_seconds` passes. Then it sends SIGKILL and waits up to the same grace for the leader. The grace is a new `Shell` parameter, `DEFAULT_SHELL_STOP_GRACE_SECONDS` (3.0 s, the old `wait` timeout). A group it may not signal, and a leader still there after SIGKILL, are logged as warnings. The bare `except Exception: pass` is gone. #775's shared process-group helper has not landed, so the fix is in place. A member that has exited but that PID 1 has not reaped yet still counts as in the group, so `stop_command` can take up to the grace period in that case. The SIGKILL it then sends changes nothing.
- **Unused classes from the issue's comment.** `ai/harness/os_access.py` is deleted, taking `MountDir`, `OSAccess` and the harness `ToolSearch`. Their entries leave the imports and `__all__` of `devops_cli.ai.harness`, the lazy name sets and `__all__` of `devops_cli.ai`, and the lazy name set of `devops_cli.ai.agents`, where the `ToolSearch` entry was never reached and `MountDir` and `OSAccess` also leave `__all__`. `devops_cli.ai.agents.ToolSearch` stays pydantic-ai's eager re-export. `test_tool_search_discovery_and_strategies` and the `os_access.py` entry in the module list of `test_no_bare_generic_exceptions_in_refactored_modules` go with them. No alias replaces any of them. `changelog.d/947.md`, #947's unreleased fragment, ended with "`MountDir`, `OSAccess` and `ToolSearch` stay exported (#947)." That sentence is removed so the v0.2.25 section does not contradict this item's Removed entry.
- No doc, knowledge-base page, `AGENTS.md` section or README described any removed class, so none needed a correction. `AGENTS.md`'s process-group guidance did recommend the pattern behind the shell defect, `os.killpg(os.getpgid(proc.pid), ...)`. It now says to signal `proc.pid` itself, never to look the group up with `getpgid`, and to reap, probe with signal 0 and escalate to SIGKILL after a grace period, pointing at `Shell._terminate_process_group`. `AGENTS.md` is maintained by hand; `devops ai agents` generates a different, shorter template that has no process-group guidance. `uv run devops docs check` reports every documentation file up to date. No command changed, so the CLI docs needed no regeneration.
