# Task: One webhook router verifies each provider its own way, parses a typed payload and delivers each event only to the consumers subscribed to it (#1386)

**Issue**: [#1386](https://github.com/dan-petty/devops-cli/issues/1386)
**Scope**: type/feature, scope/security, scope/telemetry, scope/github
**Feasibility**: Checked at release/v0.2.39 (f4177632), offline, against the old router driven through FastAPI's `TestClient` before any change. An `issue_comment` delivery was answered 202 `accepted` and handed to `enqueue_trigger`, which enqueues on every lane. A payload with no `repository`, or with `repository: {}`, was answered 401 "unmanaged repository or signature mismatch". A signature header carrying non-ASCII bytes raised `TypeError: comparing strings with non-ASCII characters is not supported` out of `hmac.compare_digest`. The deliveries counter carried the label `outcome` alone, and `GLOBAL_METRICS` fixes a counter's label names at its first use (`telemetry/metrics.py`), so the new labels are passed on every path through one place. Any non-empty batch makes `run_due_jobs` read changes, and no due rule can fire on `issue_comment`, `push` or `create`, since the batch keys (`CONST_ROADMAP_*_BATCH_KEYS`) name only `issues`, `pull_request`, `milestone` and `release`. Decision D1 (2026-10-17) allows Service code to be built, tested offline and merged at `replicas: 0`, which this item does: nothing here scales, restarts or pushes a secret for `roadmap-service`.

## Description

One router receives every webhook the Service takes. Providers and consumers are declarations; the route takes the same steps for each provider.

- **Providers.** `WebhookProviderName` (`config/constants.py`) keys `WEBHOOK_PROVIDERS` in `src/devops_cli/server/routes/webhooks.py`, which holds `github`. `create_webhook_router` registers `POST /webhooks/<provider>` for each, so a provider nothing declares gets 404 from routing. A frozen `WebhookProvider` names the verifier, the headers the event name and delivery id come from, the payload model, the ping event and the exposure (`WebhookExposure.TUNNEL` or `CLUSTER`).
- **Steps.** Refuse while draining (503), require `application/json` (415), require the event and delivery headers (400), cap the body (413, by the length it declares, whatever its digits, or by the bytes it streams), verify (401), validate the typed payload (400), answer a ping with `pong`, acknowledge an event with no subscriber (200 `no_subscriber`), drop a repeated delivery id through `DeliveryLRUCache` (200 `duplicate`), and deliver (202 `accepted`).
- **Verification.** `HmacSha256(header, prefix)` checks the digest with `hmac.new` and `hmac.compare_digest` against each managed repository's secret and names the repositories whose secret matches. It replaces `verify_webhook_signature` and compares bytes, so a signature header with non-ASCII text is refused with 401. The body is validated only after the signature matches, so a sender without a secret learns nothing of the schema.
- **Typed payload.** `GitHubWebhookPayload` (`src/devops_cli/models/webhooks.py`, pydantic v2, `extra="ignore"`) declares `action`, `repository.full_name` and `sender.login`. A body that does not validate gets 400 with the failing fields' paths and reasons, cut to `CONST_MAX_ERROR_DETAIL_LENGTH` (256) characters by `invalid_payload_detail` and naming no value from the body. No `.get` on a webhook payload remains under `src/devops_cli/server/`.
- **Consumers.** A frozen `WebhookConsumer` names a provider, the events it takes, a refusal that narrows them by the typed payload (the status that says why it ignores a payload, or None to take it; any text, an empty one included, refuses) and its delivery target, which receives the repository, event and action. `roadmap_consumer` takes the events its jobs' batch keys name (`CONST_ROADMAP_WEBHOOK_EVENTS`, derived from them: `issues`, `pull_request`, `milestone`, `release`). Its target is `ServiceManager.enqueue_trigger`, plus the `devops_cli_service_triggers_total` count, and the machine-account filter is its refusal (`ignored_machine_account`). `create_service_app(consumers=...)` replaces it, so a test declares a recording consumer without patching a name. `RepoWorker`, its coalescing and drain, `RoundPause`, the `{repo, lane}` series, `_tick_loop` and `_poll` are unchanged.
- **Logged and counted.** Each request writes one INFO record with `provider`, `event`, `action`, `delivery`, `repo` and `outcome` (`provider` joins `CONTEXT_LOG_KEYS`), and never the body, the signature or an Authorization value. The event and delivery id the sender chose are cut to 256 characters in the record. `devops_cli_service_webhook_deliveries_total` carries `provider`, `event` and `outcome` on every path, with the outcome `no_subscriber`. The event label is the event when a consumer subscribes to it or it is the provider's ping, and `other` otherwise.
- **Exposure and docs.** `tests/test_k8s_roadmap_service.py` derives the Ingress pin from the providers marked `tunnel`. [ADR 0009](../../adr/0009-one-webhook-router-delivers-each-event-to-the-consumers-subscribed-to-it.md) records the decision, and `k8s/README.md` step 8 says that events without a subscriber start no round.

## Decisions and deviations

- One `GitHubWebhookPayload` serves every event, not a model for each of `issues`, `pull_request`, `milestone` and `release`. The fields the Service reads are the same for all four, so per-event models would be identical, and listing each event's actions would be a subset of an open set. What the event decides is the subscription and the counter's `event` label, and the consumers' event sets bound both.
- The deliveries counter's `event` label is bounded by the consumers' subscriptions plus the provider's ping, not by a list of models. An event no consumer takes (`issue_comment`, `push`, `create`) counts as `other`, and its name is in the record.
- The delivery cache sees only deliveries a consumer takes, so the many events a hook sends for nothing never use its capacity. A repeat of a delivery nothing subscribes to is answered `no_subscriber` again.
- The machine-account filter ran before the delivery cache and now runs after it, in the consumer. Its delivery id is cached, so a redelivery of an own-write is answered `duplicate`.
- Every request writes the record and counts, not only those that reach verification, so a refused request shows in Loki with the same keys (`repo` and `action` appear once the payload is read).
- A Content-Length is judged by its digits before it is converted, since Python converts no more than 4300 digits to an integer and a header any sender writes can have more. A number with more significant digits than the cap has is above it, and leading zeros don't count.
- `invalid_payload_detail` is public, and its bound is tested directly. No body of `GitHubWebhookPayload` reaches 256 characters (the longest failure text is 155), so the bound is tested with a pydantic model that has long field names. It is there for the payload models that other providers bring.
- A consumer takes a payload only when its refusal is None. The answer for a payload that every consumer refuses is the first refusal, whatever its text.
- `HmacSha256` compares the digest as bytes. `hmac.compare_digest` on `str` raises `TypeError` for non-ASCII text, which any sender could send in the signature header.
- `create_service_app(consumers=...)` replaces the roadmap consumer, and `roadmap_consumer(service_manager)` is the default.
- `WebhookExposure.CLUSTER`, the `AuthorizationToken` verifier, form-encoded bodies, a consumer's own worker, push routing and Workflow-submit delivery have no user in this item. They arrive with their first user: #1395, #1389's cluster lane and #1535 step 3.
