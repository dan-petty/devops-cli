## Description
The two stack dashboards charted series nothing serves. `llm-stack.json` kept vLLM panels after #734 removed vLLM, and a Qdrant row whose scrape #734 deleted. `otel-collector.json` had lost its scrape the same way and hid it with `or vector(0)`, so a broken export read as a quiet system. Its title promised Jaeger panels it never had. The only guard checked metric names by prefix, never labels, so the GPU panels grouped by `Hostname` while dcgm-exporter 4.x labels its series `hostname`.

Three dashboards now query only series the cluster collects, checked against captures of the deployed exporters:
- **`llm-stack.json`**, "LLM Gateway & GPUs" (uid `devops-llm-stack`): the vLLM panels, the Qdrant row and their tags are gone. Time to first token p95 per deployment takes the vLLM latency panel's place. A new "Routing and Failover" row charts requests per virtual model, responses by status code, output tokens per second per model (in tok/s), and cooldowns per deployment and fallbacks per model pair, each counted per 5 minutes, all from LiteLLM's Prometheus callback. The GPU panels group by `hostname`.
- **`otel-collector.json`**, "OpenTelemetry Collector" (uid `devops-otel-traces`, no `jaeger` tag): spans and metric points accepted and refused per receiver, sent and failed per exporter, exporter queue fill, and process memory against the `memory_limiter`'s 300 MiB soft and 400 MiB hard limits.
- **`prometheus-server.json`**, "Prometheus Server" (uid `devops-prometheus-server`): targets up against total by job, scrape duration for the server's own jobs and Alloy's ServiceMonitor targets, head series and chunks, samples appended, TSDB size against the 20 GiB volume, resident memory against the 2048 MiB limit, remote-write requests by status code, query duration, compactions, compaction p95 over 6h and WAL fsync time.

A timeseries panel scales its y-axis to the data, not to its thresholds, so each panel drawn against a limit (exporter queue fill, collector memory, TSDB size, server memory) sets `axisSoftMax` to that limit and its limit line stays on the axis.

The collector's pods carry `prometheus.io/scrape` and `prometheus.io/port` annotations, so the server's `kubernetes-pods` job scrapes its own telemetry on 8888 directly rather than through Alloy, which it exports to. `prometheus-values.yaml` enables the `prometheus` and `kubernetes-pods` jobs explicitly, since deploy-stack does not pin the chart version that defaults them on.

`selectors`, `grouping_labels` and `falls_back_to_constant` in `src/devops_cli/prometheus/promql.py` read a PromQL expression's series selectors, its grouping labels, and whether an `or` falls back to a constant. They share one tokenizer that reads each string literal and `#` comment as a single token. A name followed by `(`, or by `by`/`without`, is a function or aggregation; the keywords are a closed set in `constants.py`. A quoted name standing alone among a selector's matchers names the metric, as Prometheus 3 allows (`{"utf8.name", job="x"}`), and a quoted label name counts as a label. An `or`, in any case, falls back to a constant when its right operand, after any `on`/`ignoring` list and opening parentheses, opens with `vector(` or a number: `or vector(0)`, `OR vector(0)`, `or on () vector(0)`, `or 0 * up`. `tests/test_stack_dashboards.py` uses them to check each dashboard against the captures in `tests/fixtures/metrics/`. There, a classic histogram serves only `_bucket` (with `le`), `_sum` and `_count`, and a summary serves its own name (with `quantile`), `_sum` and `_count`.
