# Task: The Service runs close and reprioritize in their own lane, so a slow model-bound intake or refine round never holds up a release (#1532)

**Issue**: [#1532](https://github.com/dan-petty/devops-cli/issues/1532)
**Status**: Done
**Milestone**: v0.2.33
**Priority**: unset on the issue; the owner placed it in v0.2.33 as a blocker for its release pull request (2026-10-09)
**Scope**: type/bug, scope/roadmap
**Feasibility**: Checked at release/v0.2.33 (1d1ccc5) and against the running Service (v0.2.32), read-only. `ServiceManager` built one `RepoWorker` per repository, and a round ran every due row of `DEFAULT_DUE_TABLE` in order, so a trigger that arrived during a refine round waited for all of it. Close and reprioritize call no model; intake and refine call the background model, which answers one call at a time. `_execute_due_rows` wrote back the whole `schedule.json` its round had read at its start, which two concurrent rounds would turn into a lost update, and `ensure_checkout` fetches, checks out with `--force` and resets hard in the same `clone` that close's cut commits and pushes from. Rate limiting is not the cause: over 6 h of Service logs the rate limiter's per-request pauses ran from 0.06 to 5.3 s (at most 5.30 s for core, 4.17 s for GraphQL, 3.79 s for search). Between 19 and 21 UTC it logged about 1,350 pauses an hour, about 1,500 s of sleep spread across every worker, while 76 to 97 rounds finished an hour and spent 1,178 to 1,413 GraphQL points. In the 22 UTC hour only 3 rounds finished, with 283 pauses (149 s): requests fell off because the rounds were waiting on the model. The last devops-cli round to finish before the stall ended at 22:04:13 with 4,726 points left.

## Description

The Service runs two lanes per repository, each with its own worker, queue and clone.

- **Lanes.** `src/devops_cli/roadmap/run.py` splits the due table into `RELEASE_LANE_ROWS` (close, reprioritize, metrics) and `MODEL_LANE_ROWS` (intake, refine). `DEFAULT_DUE_TABLE` is the two in that order, so `devops roadmap run`, its `--dry-run`, the MCP mirror and `build_stub_table` keep their order and behaviour. `SERVICE_JOBS` maps each lane (`CONST_SERVICE_LANE_RELEASE`, `CONST_SERVICE_LANE_MODEL`) to `service_job` bound to its rows and its clone, and `devops serve --service` passes it to `create_service_app(jobs=SERVICE_JOBS, ...)`. `service_job(batch, *, table, clone_dirname)` replaces the `(repo_or_batch, batch)` form.
- **The engine.** `src/devops_cli/server/service.py` still knows no roadmap jobs. `ServiceManager` takes `jobs`, one job per lane name, and runs a `RepoWorker` for each repository and lane (thread `service-worker-<repo>-<lane>`), all sharing the one `RoundPause`, so a budget refusal in either lane holds both (#1400). A poll or a webhook is enqueued on every lane of its repository, and `devops_cli_service_triggers_total` still counts it once per repository. `is_healthy` and `drain_and_stop` iterate every worker as before. `create_service_app` without `jobs` runs the logging job in the `default` lane, and `app.state.jobs` replaces `app.state.job`.
- **Visible per lane.** `devops_cli_service_queue_depth`, `devops_cli_service_job_start_timestamp_seconds` and `devops_cli_service_job_seconds_total` are labelled with `repo` and `lane`, and `devops_cli_service_jobs_total` with `repo`, `lane` and `result`. The round's span keeps its name, `service.job <repo>`, and gains the attribute `service.lane`. The round-failure and worker-crash log lines carry `lane`, which `CONTEXT_LOG_KEYS` now prints in the JSON line.
- **One schedule, two writers.** `_record_success` records each success: under a module lock it reads `schedule.json`, sets that one job and writes the file atomically. A round used to write back the whole snapshot it read at its start, which would have dropped a success the other lane recorded meanwhile and made that job run again. Each round still judges its rows by its round-start snapshot; each lane judges only its own rows, and only that lane writes them.
- **One card, two writers.** Reprioritize and refine write the job records of the same cards, each lane through the store its round opens. Every job-record write in `src/devops_cli/roadmap/github_store.py` (`set_field`, `set_marks`, `set_run_record`, `set_card_field`) already joined the record the card held at a read by its node id just before the write; `_JOB_RECORD_LOCK`, one lock for the process, now holds each write from that read to its write. So one lane never writes back a record the other changed since its read. Such a write would drop reprioritize's `Pending` mark or recorded values, which it resumes from and tells its own writes from a person's by, or refine's body and section hashes, which decide whether refine takes an item again. A Release write's check of the issue's milestone (`_require_release_unchanged`) runs under the lock too, so when intake and reprioritize set one item's Release at once, the later one sees the earlier one's milestone and raises rather than replace it (ADR 0002).
- **Reprioritize to refine across lanes.** The refine row gains a due rule, `_refine_due`: refine is due once `schedule.json` holds a reprioritize success later than refine's own, read from the repository's data directory as `_intake_due` reads `intake.json`. In the Service that is the model lane's next poll after the release lane's reprioritize. `_refine_cross_job` stays: it covers intake's critical-fix or P0 placement within a model-lane round, and reprioritize within `devops roadmap run`'s one round. #1515's interval and first-run due are unchanged.
- **A clone per lane.** `ensure_checkout(..., dirname)`, `_prepare_clone`, `_execute_due_rows` and `run_due_jobs(..., clone_dirname)` carry the clone directory name, `clone` by default. The release lane keeps `<data dir>/roadmap/<owner>/<name>/clone`, where close cuts the release (#1450) and metrics walks the tags; the model lane uses `model-clone` beside it (`CONST_ROADMAP_RUN_MODEL_CLONE_DIRNAME`), so its fetch, forced checkout and hard reset never touch a cut in progress or contend for its git locks.

## Decisions and deviations

- `TriggerBatch` carries no lane: each worker knows its lane, and each lane's job is bound to its rows and clone.
- The span name stays `service.job <repo>`, with `service.lane` as an attribute, so the traces #1197 set up keep their name. `devops_cli_service_triggers_total` gets no lane label, since a trigger counts once for its repository.
- The lanes share one pacer: the rate limiter paces each resource on one schedule for the whole process (`_next_allowed_time`), so a release-lane request takes its turn with model-lane requests, and the second lane's reads wait their turn rather than raise the request rate past the pacer's. They do add requests, which the core and GraphQL checks above watch.
- The `--service` help text names the per-repository release and model lanes, and the command reference is regenerated from it.
- `_JOB_RECORD_LOCK` is one lock for the process, not one per repository or card: it is held for one card read and one or two writes, which the pacer already spaces across every worker, and it also covers the run record card and `set_card_field`, which act on any card of the board.

## Known limits

- A success is recorded at its round's start time. A refine round that starts while a release-lane round running reprioritize is still in progress, at the same poll or from a later poll or webhook during a long reprioritize (a release start ran about 20 minutes on 2026-10-06), can read the board before reprioritize's writes land. Its success is then recorded later than reprioritize's, so `_refine_due` does not fire for those writes, and refine reads them at its next hourly run (#1515's interval), at most an hour later. Each success keeps its round's time; the timestamps are unchanged.
- `_JOB_RECORD_LOCK` holds within the Service's process. A `devops roadmap run` someone starts elsewhere can still interleave with it on a card, as before #1532.
- Refine's due rule puts refine's last success into `_oldest_cutoff`, the start of the model lane's change read. That is normally under an hour old, like intake's, but while refine keeps failing the read reaches further back at each poll, as reprioritize's and intake's already do.
- `drain_and_stop` waits on the workers one after another under one deadline, so a long model round can shorten a release round's drain. That was already true with one worker per repository; unchanged.
- Each lane reads the changes at each poll: the issue-event, pull-request and Release listings twice per repository, and the board's job records twice when foreign label changes need them. The core and GraphQL checks above watch this.
