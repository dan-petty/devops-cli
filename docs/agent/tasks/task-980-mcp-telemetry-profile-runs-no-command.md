# Task: The MCP Profile Tool Runs Nothing, and `devops telemetry profile` Runs Only devops-cli (#980)

**Issue**: [#980](https://github.com/dan-petty/devops-cli/issues/980)
**Status**: Done
**Milestone**: v0.2.25
**Priority**: priority/p1-high
**Scope**: scope/mcp

## Description
The MCP tool `telemetry_profile(command=..., trace_id=...)` passed `command` to `devops telemetry profile <command>`, after `_validate_mcp_arg`, which refuses only a leading hyphen. `_run_profiled_command` split it with `shlex.split` and ran it through `run_subprocess(..., isolate_env=False)`, so an MCP caller, which the threat model treats as untrusted, could run any program with every credential in the user's environment.

- **MCP tool** (`ai/mcp/server.py`). `telemetry_profile(trace_id: str)` has no `command` parameter, and `trace_id` is required. It builds `uv run devops telemetry profile --trace-id <trace_id>` and nothing else. Its description, which is what clients and `docs/MCP_TOOLS.md` show, reads "Show the span waterfall Jaeger recorded for a trace ID; the tool runs no command." A call that still sends `command` is refused by the published-schema check (#862) as `HALLUCINATED_PARAM` before the handler runs.
- **CLI** (`commands/telemetry.py`). `_devops_entry_argv` splits the command line with `shlex` and refuses it, with `MESSAGES.telemetry.profile_devops_only` and exit 1, unless its first word is exactly `devops` (`CONST_DEVOPS_CLI_COMMAND`). A line `shlex` cannot split, an empty line, a path such as `/usr/local/bin/devops` and a wrapper such as `env devops` are refused too. The rest runs as `[sys.executable, "-P", "-m", "devops_cli.entry", ...]` (`CONST_DEVOPS_CLI_ENTRY_MODULE`): the entry point the `devops` script calls, `devops_cli.entry:main`, under the running interpreter, so another `devops` found first on PATH is not what starts. `-P` (safe path, Python 3.11 and later) keeps the working directory off the child's `sys.path`, as it is for the `devops` script. Plain `python -m` puts it first, so profiling from a checkout holding a `token.py`, or a `devops_cli/entry.py`, ran that code in place of devops-cli's own, with the full environment; a review of this work found it, and `-P` closes it. The check runs first, before the dry run, so `--dry-run` previews only what a real run would start.
- **Environment.** The child still runs with `isolate_env=False`. `_run_profiled_command`'s docstring says why: the child is devops-cli itself, which needs its own telemetry settings and the credentials it would read when run directly, and `argv` always comes from `_devops_entry_argv`, so no other program receives that environment, and the devops-cli that does is the installed one, not code in the working directory.
- **`docker_sandbox` and the end of options** (`ai/mcp/server.py`, `core/cli.py`). Found by the audit below. `docker_sandbox` appended its `command` list straight after its own options, so `devops docker sandbox` parsed a leading `--root` in it as its own option and ran the container as root, which the tool does not offer. It now appends `--` first, as `sandbox_deploy` and `sandbox_exec` already did. Those two were not protected either: the lazy proxy in front of each command group (`OTelTyper.add_typer`) parsed its extra arguments interspersed, which consumed the `--`, so the command behind it parsed what followed as options, and `sandbox_exec(command=["--workdir", "/", "id"])` set the workdir. The proxy now sets `allow_interspersed_args: False`, so it passes everything from the first positional argument on, `--` included. The MCP dispatcher runs tools through the same root app, as does a user's `devops sandbox exec <id> -- ls -la`, which had failed on `-la`.

### Other MCP tools
Each of the 151 other tools and every resource in `ai/mcp/server.py` was checked for a free-form string split into an argv or passed to a shell, at the tool and in the command it runs.

- `ai/mcp/server.py` has no `shlex`, `shell=`, `os.system` or `Popen`. Its only `.split(` calls are `tls_generate_cert`'s `sans.split(",")` and `gh_issue_create`'s `labels.split(",")`, each part checked with `_validate_mcp_arg` and passed as the value of its own `--san` or `--label`, and `name.split("_", 1)` for a tool's domain. Every tool builds a literal `uv run devops ...` list with each argument as one element; `tests/test_docs_mcp_argv_collector.py::test_every_mcp_server_argv_resolves` resolves all of them, and its count stays at `>= 166`.
- In `src/devops_cli`, `shlex.split` and shell invocations appear only in `commands/telemetry.py` (fixed here), `commands/devcontainer.py` (two fixed installer pipelines with no caller input; not an MCP tool), `ai/harness/shell.py` and `ai/review/review_environment.py`:
  - `ai/harness/shell.py` (`Shell`, the agent harness's shell capability) is reached by `devops ai harness run`, which no MCP tool runs. `ai_subagent_offload` runs `devops ai harness offload`, which searches in process with `rglob` and the AST engine.
  - `ai/review/review_environment.py` splits a finding's verification criteria. They come from the review model, not from an MCP argument. `validate_criteria_command` holds them to `CONST_ALLOWED_CRITERIA_BINARIES` with shell operators refused, and `execute_criterion_command` runs them in bubblewrap with `--unshare-all` (no network) and `--clearenv`. That allowlist still admits `find . -exec sh -c id {} +`, `rg --pre id x` and `pytest`, each of which runs a program inside that sandbox. Changing that is outside this issue.
- The list parameters that name a program, `docker_sandbox`, `sandbox_deploy` and `sandbox_exec`'s `command`, run it inside the sandbox container through the Docker Engine API (`create_container`, `exec_in_container`), never on the host, and the workspace mount refuses `/`, `/etc`, the home directory and credential directories. Their end-of-options defect is fixed above. The other list parameters (`docker_sign`'s `annotations`, `vault_set`'s `key_values`, `vault_sync`'s `keys`, the whitelists) become one argument each, and the whitelists are held to `^[a-zA-Z0-9_\-.:*]+$`.
- Query strings go to an API, not a process: `prometheus_query` and `grafana_dashboards` over HTTP, `rag_search` and `ai_query_library` to the vector store, and `k8s_logs_query` and `k8s_logs_tail` parse LogQL whose namespace and pod are checked with `is_valid_k8s_name` before they reach `kubectl` as single arguments. `valkey_get` and `valkey_set` send length-prefixed RESP arrays (`valkey/protocol.py`), so a key or value cannot add a command. `security_intel_package`, `security_intel_network` and `scan_uv_audit` call `ai/tools/builtin_tools.py` in process, which passes each argument as one list element.

## Acceptance Criteria
- [x] **MCP tool.** `telemetry_profile` takes only `trace_id`, which is required, and its schema and `docs/MCP_TOOLS.md` say so. `tests/test_fastmcp_contracts.py::test_telemetry_profile_publishes_a_trace_id_and_no_command` (red on 9c879ae: `(('command', 'trace_id'), ['command', 'trace_id'], None)`), `test_telemetry_profile_refuses_a_command_before_anything_runs` (red: `(True, False, False, 1)`, the handler ran) and `test_telemetry_profile_reads_the_named_trace`.
- [x] **CLI.** `devops telemetry profile "bash -c true"` exits 1 with a message and starts no process; `devops telemetry profile "devops version"` starts `python -P -m devops_cli.entry version`. `tests/test_telemetry_profile.py::test_profile_refuses_anything_but_a_devops_command`, over `bash -c true`, `/usr/local/bin/devops version`, `env devops version`, `devops 'version` and a blank line (red on 9c879ae: four started the process, `(1, True, False)`, and the unbalanced quote raised `ValueError`, `(1, False, False)`), and `test_profile_runs_a_devops_command_through_the_entry_point` (red: argv `['devops', 'version']`, then, before `-P`, `[sys.executable, '-m', 'devops_cli.entry', 'version']`). `test_profile_child_imports_nothing_from_the_working_directory` starts the child's interpreter and flags from a `tmp_path` holding a `token.py` that exits 99 and imports `token` (red without `-P`: `(99, b'')`). - [x] **Environment.** The child keeps `isolate_env=False` only for the entry-point argv, asserted by `test_profile_runs_a_devops_command_through_the_entry_point` and `test_profile_shows_the_child_spans_jaeger_recorded`, and that argv imports nothing from the working directory, asserted by `test_profile_child_imports_nothing_from_the_working_directory`; `_run_profiled_command`'s docstring gives the reason.
