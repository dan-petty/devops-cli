## Description

The repository has somewhere to plan into and a gate that keeps a plan valid. OpenSpec's `validate`, `archive`, `instructions`, `update` and generated skills are used as shipped with the default `spec-driven` schema; the code is the glue [ADR 0010](../../adr/0010-openspec-is-the-spec-and-change-proposal-layer.md) names, and nothing is deleted.

- **The scaffold.** `openspec/config.yaml` is the ADR's file, every rule a folded scalar, with `openspec/specs/.gitkeep` and `openspec/changes/archive/.gitkeep`. The eight `SKILL.md` of the propose, explore, apply and update workflows sit in `.claude/skills/openspec-*/` and `.agents/skills/openspec-*/` beside `.agents/skills/.openspec-target`, as `openspec init` wrote them. `.gitignore` re-includes only `.claude/skills/openspec-*/`, so other skills, `settings.local.json` and worktrees stay ignored.
- **`devops openspec check`** (`src/devops_cli/commands/openspec.py`, `src/devops_cli/openspec/gate.py`) runs the pinned tool five ways and reports every problem with the check that found it: `validate --all --strict`; `validate --archived`; a regeneration of the skills in a scratch copy, compared with the tree (a changed file, one the regeneration adds, one it removes), and a finding for each glob of the generated files that matches no file, because `update` cannot write back a tree deleted whole; the instructions of a probe change for the proposal, specs, design, tasks and apply operations, with any output to standard error a finding; and the overlap check. The gate archives nothing and reads no git history, because the pull request that closes a change archives it (#1846). It passes a tree with no change and no spec, and fails first, naming `uv run devops install-tools --tool openspec --only-missing`, when `openspec` is not on PATH.
- **The child environment** (`src/devops_cli/openspec/tool.py`). Every run sets `DO_NOT_TRACK=1`, `OPENSPEC_TELEMETRY=0`, `OPENSPEC_NO_UPDATE_CHECK=1`, `OPEN_SPEC_INTERACTIVE=0` and an `XDG_CONFIG_HOME` that is a scratch directory holding the isolated configuration (`telemetry.enabled false`, `delivery skills`, `profile custom` and the four workflows, set with `openspec config set`), which goes when the run ends. The ADR names `extra_allowed_env`, which keeps only a variable the parent already has, so the values go through `env`.
- **`devops openspec regenerate`** (`src/devops_cli/openspec/skills.py`) runs `openspec update --force` in the checkout under that isolated configuration, and a bare `openspec update` is never run. Under `--dry-run` it starts nothing.
- **`devops openspec archive <change>`** (`src/devops_cli/commands/openspec.py`, `src/devops_cli/openspec/archive.py`) runs `openspec archive <change> --yes` and then `openspec validate --all --strict`. Each run uses the runner of the gate: the four opt-outs and an `XDG_CONFIG_HOME` that is a scratch directory holding the isolated configuration. The command passes no `--skip-specs`, because a change that declares `skip_specs` archives without it. When a run fails, the command prints the whole output of that run and raises `ToolExecutionError` (`TOOL_EXECUTION_ERROR`, exit code 1). The error names the command and its exit code, and the command exits 1. The output is not cut, because `validate` prints one line for each passing spec before the failure, and a cut would hide the failed spec. A failed archive skips the validation, because the tool changes no file when it refuses. A failed validation says that the archive is applied, so the author fixes the spec and does not run the archive again. Under `--dry-run`, as the option or the global flag, the command prints both commands and starts no process. MCP does not expose it, because it writes `openspec/specs/`. ADR 0012 (What Stays Custom) requires the wrapper. The wrapper keeps the telemetry and the per-user configuration of the tool out of an archive. The settings allow the direct tool `openspec archive`, so the wrapper is a convention. `openspec/config.yaml` and ADR 0010 tell an agent to run `uv run devops openspec archive <change>`. No entry of the settings enforces it.
- **Existing tool considered, and the cost of the wrapper.** `openspec archive` and `openspec validate` are the open tools. The wrapper runs them as shipped. No open tool runs an archive under the isolated configuration with the opt-outs and then validates the whole tree. The validation is the point: the archive can exit 0 and leave a spec that `validate` fails, as the Feasibility field records. The wrapper is about 20 lines of command and 15 lines of module code. Cost to build, an estimate from the session counter of the builder: about 280,000 tokens and about 30 minutes of elapsed time. That covers the reading, the tests, the code, the recording, the documents and the checks. The tests, the three scenarios and the text edits are most of it. Cost to maintain: `record_scenarios` records the three archive scenarios with the rest at each bump of the pin, and `tests/test_openspec_contract.py` fails until it does. One recording took 28 seconds. With the run and a read of the diff, an estimate is about 10,000 tokens and 5 minutes for each bump. A change in the command line of `openspec archive` changes the one list in `archive_commands`. Cost to fix until it matches the tool: none, because the wrapper runs the tool and copies none of its behaviour.
- **The overlap check** (`src/devops_cli/openspec/overlap.py`) reads `openspec show <change> --json --deltas-only` for each active change and reports a (capability, requirement) that two of them `MODIFY`, `REMOVE` or `RENAME`. OpenSpec's bulk-archive conflict detection is an agent skill, not a command, so no open tool does it; the module is deleted when OpenSpec ships a deterministic check (the ADR's Revisit Conditions). Cost, an estimate: about 60 lines and two test scenarios, some 10,000 tokens to write and test, near none to maintain while `show --json` keeps its shape, and about an hour of elapsed time. `OpenSpecFake` serves the gate and this check alike, over the runs recorded from the real tool, so neither needs a double of its own.
- **The `openspec` row** of `devops ci` runs `uv run devops openspec check` in every run with no path filter and no exemption. The pre-commit hook `openspec-gate` runs `uv run devops ci --only openspec` when a commit touches `openspec/`, `.claude/skills/` or `.agents/skills/`. The `static` job of `ci.yml` runs `actions/setup-node` pinned to v7.1.0 by its commit with `node-version-file: .node-version`, and installs the pin with `uv run devops install-tools --tool openspec --only-missing` before the gate. `.github/workflows/copilot-setup-steps.yml` is written by hand with the same pinned actions, the pinned install and the opt-outs; `openspec init --copilot-cloud` is not used, because its workflow runs an unpinned `actions/checkout@v4` and `npm install -g`.
- **Documents.** `openspec/changes/**/*.md` is class `record`, `openspec/specs/**/*.md` class `release artifact`, and the eight `SKILL.md` a new class `tool-generated`, which is not name-checked; the review routing gains `openspec/**` and the generated skill globs and keeps the task-file entry until the switch. `devops openspec check` and `regenerate` are excluded from the MCP tools, as `devops docs check` and `install-tools` are. The bump runbook in the header of `tools.lock` gains the regeneration and the gate; `RELEASE_CYCLE.md`, `SDLC.md`, the gate's knowledge-base page and `TESTING.md` name the row and the fake; AGENTS.md's CI row ends "docs, deps, openspec)", and `tests/test_agents_md_claims.py` holds the file within `CONST_AGENTS_MD_MAX_CHARS`; ADR 0010 says that the values go through `env`.
- **Tests.** `tests/test_change_folders.py` holds every active folder to the name `<issue>-<slug>`, a proposal with `## Feasibility` and `## Existing Tool Considered` found with markdown-it, a `tasks.md` with a `## <n>.` group holding a task-list item, and no PR, Status, Milestone or Priority line. `tests/test_openspec_scaffold.py` parses the configuration with `yaml.compose` (only `schema`, `context`, `rules` and `operations`, and only folded or literal scalars), reads `generatedBy` of all eight skills against the pin, compares the two trees, checks what git keeps, the inventory classes, the routing and the hook; `tests/test_workflow_contracts.py` checks the `static` job and `copilot-setup-steps.yml`, and `tests/test_agents_md_claims.py` the CI row. `tests/test_openspec_gate.py`, `test_openspec_command.py`, `test_openspec_tool.py` and `test_openspec_contract.py` run the gate and the commands over `OpenSpecFake`, which replays the real tool's runs recorded over eleven scenarios (eight of the gate and three of the archive), writes the skills `update --force` writes, and answers a failure no recording holds (a tool that prints no JSON or runs past its timeout) when a test scripts it. The archive tests in `tests/test_openspec_command.py` show the order of the two runs: `archive <change> --yes`, then `validate --all --strict`, and never `--skip-specs`. They show the four opt-outs and the scratch configuration. They show that a refused archive skips the validation and exits 1. They show that a validation which fails after the archive (a placeholder Purpose) exits 1 and says that the archive is applied. They show that the failed spec and its reason stay in the output when a dozen passing specs come first. They show that a `--dry-run`, in both forms, starts nothing.

## Acceptance Criteria

- [x] `uv run devops ci` runs an `openspec` row, passes on the empty tree, and fails with a clear message when `openspec` is missing, naming `uv run devops install-tools --tool openspec --only-missing`. The real gate passed the repository's empty tree in 4.3 s and failed with the message on a PATH without the tool; `tests/test_openspec_gate.py` checks the commands of the empty tree in order and the missing tool (exit code 1, `DEPENDENCY_MISSING`, no process started), and `tests/test_openspec_command.py` the exit code and output of both cases.
- [x] `uv run devops openspec regenerate` leaves the tree unchanged under any developer's global profile, and `check` fails when a skill file was hand-edited or the profile is wider. The real tool did, as the Feasibility field records; `tests/test_openspec_command.py` checks that `regenerate` sets the four isolated settings and runs `update --force` and never a bare `update`, `tests/test_openspec_gate.py` that every run opts out under a configuration directory of its own whatever the environment says, and that a hand-edited skill, an added archive skill, a deleted skill and a skill tree deleted whole are each reported.
- [x] `check` fails a requirement modified by two active changes. `tests/test_openspec_gate.py` reports, from the real tool's recorded runs, a requirement modified twice and a requirement renamed and modified, each by the check that finds it; and it checks that a change which modifies a requirement another active change adds passes, that a change declaring `skip_specs` passes, and that no run of the gate is an `archive`. A missing Purpose, a `MODIFIED` of a spec that does not exist and a duplicate `ADDED` show only in the pull request that closes the change: `validate --all --strict` fails the placeholder Purpose of the archived spec, and `openspec archive` refuses the other two and changes no file (#1846).
- [x] `tests/test_change_folders.py` fails a folder not named `<issue>-<slug>`, one with no `tasks.md` group and one carrying a `Status` line, and `tests/test_openspec_scaffold.py` fails a plain scalar rule and an unknown key, each with its line.
