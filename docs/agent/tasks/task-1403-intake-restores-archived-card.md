# Task: Intake restores an issue's archived board card instead of failing every round (#1403)

**Issue**: [#1403](https://github.com/dan-petty/devops-cli/issues/1403)
**Status**: Done
**Milestone**: v0.2.29
**Priority**: priority/p2-medium
**Scope**: type/bug, scope/github

## Description

Intake puts an issue on the board with `gh project item-add`, which names the card the issue already has, because the board keeps one card per issue. When a person had archived that card, the store's one read of it (#1361) found it archived. `add_item` then raised "Board #N does not hold card <id> that #N was just added as.", which is the real message; the issue quotes "#N is not on the board", which the field writes raise. The board listing leaves archived cards out, so the issue stayed a candidate and intake raised again every round. `apply_intake` places candidates one after another with no isolation, so the error also stopped every later placement in the round; #1443 isolates each placement.

- **The store restores the card.** `GitHubRoadmapStore.add_item` reads the card `item-add` names once, by node id, archived or not (`BoardCardPayload.listed(archived=True)`, `is_archived()`). When it is archived, the store checks the GraphQL reserve against that read's `rateLimit` (`require_write_floor`), then sends `gh project item-archive <board> --owner <owner> --id <card> --undo --format json` (`item_unarchive_args`). The reply must name the same card, or the store raises before any field write. The card comes back with the fields and job record the read gave, and the store does not read it again. A card that is gone or belongs to another issue raises as before.
- **The contract.** `RoadmapStore.add_item` returns an `AddedItem`, an `Item` marked `restored` when the add brought back a card a person archived, with the fields and job record it holds. The in-memory store keeps archived cards apart (`_Roadmap.archived`), leaves them out of every read, and restores one on `add_item`. A test archives a card as a person does with `archive_card`.
- **Intake decides again on the card the add returns.** Planning reads the board listing, which leaves an archived card out, so it plans the issue as one off the board: for an issue of the current release that is not a critical fix, that means the backlog. Before this change, the round would then clear the milestone, write Status, Value, Effort and Priority over the card's and post a "to the backlog" comment. `_apply_placement` now passes the card `add_item` returns through `_on_card`. A card that holds a Priority is an item `_subjects` would not have picked, so intake writes nothing more to it: no milestone, field or job record write, no comment and no refine hook. `apply_intake` reports it in `IntakeApplied.finished`, and `--confirm` prints a line for it. A card with no Priority gets the planned writes only for the fields it holds no value for. A restored card keeps its milestone, as `_placement` keeps an item's (`_resumed`), and the reason comment is written for the placement and the values intake actually sets (`_reason_lines`, `_comment`). The one same-value write left is Status New on a card the add did not restore, which the board's "Item added to project" workflow sets and intake writes again so that its job record holds it. A value a person set is never claimed by the job record.
- **The plan.** `StoreRequests.add_item` lists the restore after the card read, under "the card the add names is archived", built by the same argv builder as the store. Intake's placement shows it under its add step, and its Priority write under "it has none". `--dry-run` still makes no request.
- **Docs.** `devops roadmap intake --help` says that an archived card of an open issue is restored, and that closing the issue as not planned keeps it off the roadmap; `README.md`, `docs/commands/roadmap.md` and `docs/CLI_REFERENCE.md` are regenerated from it. CONTEXT.md's "Candidate" names the issue whose card a person archived.

## Decisions and deviations

- **Restore the card rather than leave it archived.** Board #2's auto-archive workflow is off (`CONST_PROJECT_WORKFLOW_EXPECTATIONS`), and nothing in this code archives a card, so a person archived every archived card, and the restore undoes that person's action. It is restored anyway, for three reasons. An open issue becomes an item when intake places it (CONTEXT.md, "Item"). GitHub keeps one card per issue per board, so `item-add` can't make another. And the alternative, leaving the card archived with an error for that one candidate, keeps an open issue off the roadmap indefinitely and needs per-candidate isolation in `apply_intake`, which is #1443. The likely trigger is a closed issue's card archived to clear the board, then the issue reopened, and the reopen asks for the work again. To keep an open issue off the roadmap, close it as not planned. The restore undoes only the archive: every value the card holds stays, and so does its milestone.
- **Decide again on the card the add returns, rather than judge it as new.** ADR 0002 says a job never overwrites a value a person set without comparing it with the value the job last set. Intake does no such comparison: it writes only empty fields (`_fields`), and it takes only open issues off the board or items with no Priority (`_subjects`). `_on_card` applies those same rules to the card the add returns, which planning did not see. A card with a Priority is left as it was. Otherwise only empty fields are written, and a restored card keeps its milestone, as `_placement` keeps an item's. Judging the card as new instead reverted a finished card's milestone, posted a reason comment for values the card did not hold, ran the refine hook on its planned Priority and claimed a person's values in the job record. `AddedItem.restored` is the signal, because a card's values can't tell a restored card from a new one: the board's add workflow sets Status New on a new card.
- **Only a new card's Status New is written again over the same value.** On a card the add did not restore, Status New is what the board's add workflow set, and intake writes it so that its job record holds the value, as before (#1361). On a restored card, intake writes only fields with no value, so a Status a person set is never claimed by the job record.
- **The reason comment follows the writes.** `IntakeDecision.reasons` keeps the comment's lines, so `_on_card` writes the comment for the placement it keeps and the values it sets. For a card the add did not need to change, the comment is the one planned. Only the report printed before the writes (`shown`, the planned writes) can't know about a card planning did not see, and `--confirm` names a card it left as it was.
- **A re-run whose card a lagging listing left out** follows the same rules, because planning did not see that card either. A card an earlier run finished (it holds a Priority) is left as it was. An unfinished one keeps the values the earlier run, or a person, set, and gets only its empty fields. Before this change, both were written again.
- **The `type/*` label comes before the add**, as in the order intake documents, so an issue with no type label whose finished card is restored still gets the label. The milestone, fields, job record and comment are left alone.
- **`run.py`'s `placed_critical_or_p0`** comes from the plan, before any write, so a finished card planned as a critical fix would still set it. The Service's own `run.py` is #1358's change surface, and the case needs a P0 with verified evidence on an archived card, so this change leaves it.
- **The restore reply must name the card, and nothing reads it again.** `item-archive --undo --format json` prints the restored item, which `_ADDED_CARD` validates. A reply naming another card raises `GitHubOperationError` before any field write (fail closed). The read before the restore supplies the fields, so the restore costs one write and no further read.
- **The reserve check before the restore** uses `require_write_floor` on the card read's budget, as every other board write does. At that point `item-add` has been sent; it is idempotent, and the next round sends it again.
- **GitHub doesn't document whether `addProjectV2ItemById` unarchives an item**, and reports disagree. The store branches on the card's own `isArchived`, so it is correct either way. `GitHubFake` models the case that failed: `item-add` returns the archived card.
- **The in-memory `archive_card` keeps a view's copy of the card it read.** The GitHub store's `_added` keeps a listing's copy the same way: a write compares against the card as the store read it, so a change a person made before archiving is still caught.
- **No live trigger was found.** The Service's logs had no "does not hold card" line, the Service runs v0.2.28, and nothing archives cards automatically. This is a latent defect, fixed because the owner placed it in v0.2.29.
- **Out of scope:** a run record draft card a person archived is not restored, because `item-create` makes a new draft. The existing message already tells a person to restore it.
