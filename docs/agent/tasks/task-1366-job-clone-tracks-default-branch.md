# Task: The job clone tracks the release branch while origin has it, and the default branch otherwise (#1366)

**Issue**: [#1366](https://github.com/dan-petty/devops-cli/issues/1366)
**Status**: Done
**Milestone**: v0.2.29
**Priority**: priority/p1-high
**Scope**: type/bug, scope/github, scope/release

## Description

`ensure_checkout` (`src/devops_cli/roadmap/run.py`) prepares the per-repository clone that close and refine use. It ran `git fetch origin` without pruning and then `git checkout -B release/<v> origin/release/<v>` whenever a release was current. A ship deletes `release/<shipped>` on merge. Until the milestone closed, the clone kept the stale remote-tracking ref and checked out the deleted branch's last commit. That is how close re-cut the shipped v0.2.27 nine times on 2026-10-06. From the milestone's close until reprioritize started the next release, the ref was missing: the checkout exited 128 (`'origin/release/vX' is not a commit`), and every clone row in the round failed on the reused error. With no release open, the working tree never moved.

- **Checkout rule.** `ensure_checkout` runs `git fetch --prune origin` and `git remote set-head origin --auto`, and reads the default branch from `git symbolic-ref --short refs/remotes/origin/HEAD`. If a release is current and `git rev-parse --verify --quiet refs/remotes/origin/release/<v>` exits 0, the clone tracks that branch. If it exits 1, or no release is open, the clone tracks the default branch. Either way it runs `git checkout -B <branch> origin/<branch>` and `git reset --hard origin/<branch>`, so HEAD is always a named branch, never detached. A current release without a branch logs one INFO line naming the repository, the default branch, the release and its branch name.
- **Fail closed.** Every other git failure raises `GitOperationError` carrying the command and git's reason, credentials masked. That covers clone, fetch, set-head, symbolic-ref, a `rev-parse` exit other than 0 or 1, checkout, reset and the identity writes. Each step runs through `run_subprocess(..., check=True)`, and one `subprocess.CalledProcessError` handler converts the failure. That handler replaces the four duplicated return-code blocks. The branch choice is `_select_tracked_branch`, a decomposition step that runs the fetch and the probes in the clone.
- **Tests** run real `git` against bare remotes in `tmp_path`, which are built with git's plumbing (`commit-tree`, `update-ref`), so no work clone is pushed. The session's `gh api user --jq .login` is answered at the process edge by a `subprocess.run` wrapper. That wrapper passes git through and fails the test on any other gh command, and the core quota is seeded so the login lookup sends nothing else. No devops-cli name is patched.

## Decisions and deviations

- **The cut-check criterion and its test are #1124's**, as the issue's 2026-10-08 update records. Re-implementing them would be a patch on a patch.
- **Run-level batch.** The issue's `("webhook","pull_request","closed")` batch makes only close due. `CONST_ROADMAP_REPRIORITIZE_BATCH_KEYS` is never read, the reprioritize row has no `batch_keys`, and `_batch_matches` routes only milestone webhooks to it. The test adds `("webhook","milestone","closed")`, which a ship sends. It makes reprioritize due today through that special case, and after #1360 through the keys #1360 wires.
- **Only `rev-parse` exit 1 means absent.** Exit 128 is a real error (for example, not a repository), so it raises through `CompletedProcess.check_returncode()`. A milestone title that is not a valid ref name also exits 1, so it takes the logged fallback, as the issue's key questions intend.
- **One handler instead of four return-code checks.** Converting `subprocess.CalledProcessError` once keeps `ensure_checkout` and `_select_tracked_branch` well under the C901 cap, adds no wrapper, and also turns a failed identity write into `GitOperationError`. A `TimeoutExpired` or a missing `git` binary still propagates as before; `_prepare_clone` fails the clone rows on either.
- **The error names the git command and git's reason** (`shlex.join` of the argv), passed through `mask_secrets` because a configured remote URL can carry a credential. `operation` in the details is the git subcommand.
- **The INFO line uses the logger's own formatting**, like the module's other log lines, so the Service's log level decides whether it is built.
- **`set-head --auto` is one more request to origin per round.** It is git transport, not GitHub API quota. Git 2.48's `remote.<name>.followRemoteHEAD` could fold it into the fetch. The Service image takes git from Debian trixie's packages, though, and the explicit command works on any git version, so it stays.
- **Test remotes are built with git plumbing**, not a pushed work clone. Each call phase then stays under 1 s on a loaded machine. `_advance_bare_remote(bare, branch, onto=...)` commits on top of `onto`, so a release branch can move forward from its own tip.
- **The login fake refuses any gh command except `gh api user --jq .login`.** It seeds the core quota so the lookup sends no `gh api rate_limit` first, as the skeptic measured. Without that, a pass-through wrapper would reach GitHub outside the socket guard, and `_get_session_login`'s silent `devops-cli` fallback would hide it. The (a)+(b) and (e) tests assert the clone's identity is `test-bot`.
- **Out of scope:** `_get_session_login` swallows every exception and falls back to `devops-cli`. Logging the clone error that `_execute_due_rows` drops is #1365.
