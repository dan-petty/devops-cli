# Task: Shuffled repeat runs of a pull request's changed test files (#852)

**Issue**: [#852](https://github.com/dan-petty/devops-cli/issues/852)
**Status**: Done
**Milestone**: `v0.2.32`
**Priority**: `priority/p2-medium`
**Scope**: `type/feature`, `scope/cli`, `scope/ci`, `priority/p2-medium`

## Description

AGENTS.md sets zero tolerance for flaky tests, but nothing reordered or repeated a test, so a test that passes only after another one stayed hidden until xdist's load scheduling put the two in a different order. This item makes order dependence visible where it is cheap to find: in the test files a pull request adds or changes.

- **pytest-randomly 5.0.0** (pytest-dev) joins the dev group. `addopts` blocks it with `-p no:randomly`, so `pytest`, `devops ci` and the gate keep file order. A `-p randomly` on the command line comes after `addopts` and turns it back on.
- **`devops ci test --repeat N --seed S`** runs the selected test files N times, one run after another, each as `uv run pytest -n 0 [-v] [-k K] [-x] -p randomly --randomly-seed=<S+i> <files>`. S defaults to HEAD's commit hash, its first eight hex digits read as an integer (`git rev-parse HEAD`). The first failing run stops the command, which prints `Run i/N failed with seed S+i` and the command that reproduces it. pytest-randomly prints `Using --randomly-seed=<seed>` at the top of every run. `-n` is ignored, since the runs are serial. The default N, `DEFAULT_CI_TEST_REPEAT_RUNS` in `config/defaults.py`, is 0: a single run in file order.
- **The Changed-Test Independence job** in `ci.yml` runs on `pull_request` only, with `contents: read` and no `needs`. It lists the added, modified and renamed test files against the base branch (`git diff --name-only --diff-filter=AMR "origin/${BASE_REF}...HEAD" -- ':(glob)tests/**/test_*.py'`), then runs `uv run devops ci test --repeat 3 -- <files>`. When no test file changed, its toolchain and test steps are skipped. The job is advisory: the rulesets require only Static Analysis and Tests & Coverage (ADR 0004).

The code is two helpers next to `_build_test_cmd` in `commands/ci.py`, `_head_seed` and `_run_shuffled_repeats`. Both reach git and pytest through `run_subprocess`, the seam the existing `ci test` tests double.

## Decisions and Interpretations

- **"Skipped" is a step-level skip.** The job always starts and runs its checkout and detect steps, then skips the toolchain and test steps, as the DevContainer Image and Service Image jobs do. A workflow-level `paths` filter would skip every job in `ci.yml`.
- **The default N is 0, meaning off.** `ci.yml` passes `--repeat 3`; a person passes any N.
- **The whole suite is refused.** `--repeat` needs test files to narrow the run, so a run with no paths, or one a trigger file widens to the whole suite, exits 1 with "--repeat needs test files to narrow the run". Shuffling the whole suite waits for per-test thread-leak isolation, as the issue's constraint says.
- **`--repeat` shuffles what `ci test` selects.** It takes the issue's "selected targets" literally and uses `ci test`'s own selection, coverage-index drift included. Locally, with a built coverage index, the run also takes the tests covering every file changed since the index was built. If a trigger file (`conftest.py`, `pyproject.toml`, `uv.lock` or `.python-version`) has drifted, the selection widens to the whole suite and `--repeat` refuses, even with test files named, until `devops ci coverage --build-index` runs again; the trigger warning printed first says which file. CI has no index, so the job shuffles exactly the changed test files. Shuffling only the named files would need a second selection path, which is a re-scope for the owner, not part of this item.
- **A pull request that changes many test files** runs each three times, one run after another; the job's `timeout-minutes: 30` bounds it, and it is not a required check. No cap was added.
- **`--seed` without `--repeat` does nothing.** Its help says so, rather than a guard refusing it.
- **`--dry-run` reads HEAD.** Without `--seed`, a dry run still runs `git rev-parse HEAD`, a local read, so the planned commands carry the real seeds; each repeat run prints as its own one-step plan.
- **The job's toolchain caches `.pytest_cache` under its own `changed-tests` key.** The default paths, `.mypy_cache` and `.ruff_cache`, do not exist in this job, and actions/cache would warn about them on every run.
- **The pytester test loads only the plugins it needs.** It sets `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` and loads xdist with `-p xdist`: autoloading every installed plugin cost seconds and raised pytest-asyncio's unset-loop-scope deprecation warning. Its inner `addopts` adds `--tb=no`, since formatting the failing run's traceback scanned every module the test process had imported (about 1 s). pytest-randomly 5.0.0 orders tests by `crc32(f"{seed}::{nodeid}")`; for `tests/test_shared.py`, seed 2 keeps the order and seed 3 reverses it, so a change of pin or path means re-checking the seeds.
- **The pytester test puts the global RNGs back.** pytest-randomly reseeds the global `random` and numpy RNGs in the process it runs in, and pytester restores `sys.modules`, not RNG state, so the `global_rngs_restored` fixture saves both states before the test and restores them after it. Without it, every later test on that worker would start from a fixed seed. Running the inner runs in a subprocess instead would not fit the 1 s budget.
