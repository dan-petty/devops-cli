# Task: The Argo Workflows Controller Runs in Its Own Namespace, and a `--version` Workflow Measures Start-Up and API-Server Load (#1535)

**Issue**: [#1535](https://github.com/dan-petty/devops-cli/issues/1535)
**Scope**: scope/k8s
**Feasibility**: Confirmed against the chart and the CLI, offline. `helm template` of argo-helm `argo-workflows` 2.0.13 (app v4.1.5) with the committed `k8s/argo-workflows/values.yaml` renders eight CRDs, the controller Deployment, its Service, a ServiceMonitor, a ConfigMap, two ServiceAccounts, two Roles and two RoleBindings, and no ClusterRole, no CRD-install Job and no reference to Secret `devops-cli`. The executor's Role grants `create` and `patch` on `workflowtaskresults` and nothing else. At one replica the chart renders `strategy: Recreate` and `LEADER_ELECTION_DISABLE=true` itself. A Pod Security `restricted` check over the rendered controller Deployment, and over a pod built from the WorkflowTemplate plus the executor's `securityContext`, admits both. The chart's defaults do not: they leave `controller.podSecurityContext` and `executor.securityContext` empty, so the controller pod is refused for its missing seccomp profile, and, with the argo-server off, they add six ClusterRoles and three ClusterRoleBindings, which `createAggregateRoles: false`, `singleNamespace: true`, `crds.full: false` and `controller.clusterWorkflowTemplates.enabled: false` together remove. Only `singleNamespace` restricts what the controller watches, since `controller.workflowNamespaces` does not, and the chart enables the argo-server unless `server.enabled` is false. Without a `command`, the controller looks the image's entrypoint up in the registry over HTTPS, which the perimeter refuses, so the template names `command: [devops]`. The chart index (generated 2026-10-16) and the `argo-workflows` v4.1.5 release were the newest. The v4.1.5 CLI checksums in `tools.lock` are the release assets' digests, equal to the publisher's `argo-workflows-cli-checksums.txt`. `kubectl kustomize k8s/argo-workflows` renders the perimeter and the template, and `argo lint --offline` accepts the template, with no cluster reached.

## Description
The roadmap Service hand-rolls its queueing, scheduling and locking, and the owner chose Argo Workflows to replace it ([ADR 0008](../../adr/0008-argo-workflows-run-the-roadmap-jobs-after-a-measured-go.md)). Step 1 installs the controller and measures what a Workflow costs before any job moves onto it. It touches nothing in namespace `devops`: `roadmap-service` stays at 0 replicas, and no GitHub request, GitHub identity or Secret is involved.

The controller runs in a new namespace, `argo-workflows`, under Pod Security `restricted`. It is one replica that the Recreate strategy replaces, it watches only its own namespace, and it has no argo-server, database or workflow archive. Its CRDs are the chart's minimal ones, kept on uninstall, with the sync options Argo CD's own CRDs carry. The executor ServiceAccount `argo-workflows-executor` may only create and patch `workflowtaskresults`. The perimeter admits only the metrics scrape from `monitoring` and lets pods reach only DNS and the API server on port 6443. WorkflowTemplate `devops-cli-version` runs `devops --version` in the Service image with the cluster job template's security context, mounts no Secret, turns telemetry off and removes finished Workflows. Alloy scrapes the controller through the chart's ServiceMonitor, and the Scrape Ownership table names it.

Two Argo CD Applications install it (`argo-workflows`, the pinned chart, and `argo-workflows-manifests`, the perimeter and the template with `SkipDryRunOnMissingResource=true`), and deploy-stack's `infra` stack registers the same pieces: the release after `argocd`, the perimeter among the manifests applied before the charts, and the template in the post-Helm step that applies it after the Helm releases and deletes it before they uninstall. The argo CLI pin moves from v4.1.4 to the chart's app version, v4.1.5, because the measurement submits its Workflows with that CLI.
