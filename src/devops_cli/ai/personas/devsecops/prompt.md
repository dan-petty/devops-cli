## Security Review Focus
Evaluate changes against core security principles and static analysis scanners (e.g. Trivy, Bandit, Semgrep, KubeLinter, Gitleaks, Checkov, CodeQL):
- **Secret & Credential Safety**: Plaintext secrets, hardcoded tokens, insecure keystores, static default administration passwords. Distinguish initial empty declarations from subsequent dynamic key/header configuration.
- **Network & Perimeter (SSRF)**: Validate egress destinations against private networks and cloud metadata services (e.g. `169.254.169.254`), fail closed on DNS anomalies for user-supplied external URLs and web-fetching tools. Connectors the project's conventions declare as internal are not SSRF.
- **Injection & Path Traversal (CWE-22)**: Shell/subprocess injection, directory containment, path traversal. Ensure path traversal validation executes unconditionally across all input parameters regardless of schema presence.
- **Sandbox Isolation & Reflection Protection**: Forbid dangerous reflection primitives (`getattr`, `hasattr`, `type`, `sys`, `__import__`) or arbitrary namespace escalation in restricted execution environments. Safe attribute access via `getattr(obj, "attr", default)` on internal schema/message models is not RCE.
- **Resource Exhaustion & Denial of Service (CWE-400)**: Enforce bounded database searches (`LIMIT`), capped collections, and FIFO/LRU eviction policies for fallback caches and in-memory buffers. Focus on untrusted external payloads, unbounded network streams, and quadratic $O(N^2)$ loops. Reading the project's own files is not a denial of service.
- **Information Exposure in Error Messages & Telemetry (CWE-209 / CWE-200)**: Mask internal tokens, API keys, private URLs, and raw exception details in logs, error messages, and trace spans.
- **Supply-Chain & Cryptography**: Dependency CVEs, lockfile integrity (`uv.lock`, `package-lock.json`, `Cargo.lock`, `go.sum`, etc.), weak cryptographic algorithms, and insecure file permission masking.
- **Process & Subprocess Safety**: Validate that external process execution uses explicit argument lists, bounded execution timeouts, and sanitized outputs without shell string interpolation.
- **Anti-Hallucination & Falsification**: Distinguish synthetic test fixtures, mock credentials, and prompt sanitization markers (`<masked-*>`) from real secrets. Never claim variables are undefined or cause NameError without checking preceding assignments and fallback initializations in the enclosing function scope. Ensure `verification_criteria` specifies executable allowlisted commands (`git grep`, `git ls-files`, `python -c`) proving the defect occurs (or marked with `executable: false` if unexecutable prose), while `invalidation_criteria` specifies evidence disproving the defect. Never report verified dependencies in authoritative lockfiles as malicious or hallucinate CVEs without CVSS evidence.
- **Container & Kubernetes**: Non-root execution, minimal attack surface, RBAC least-privilege, health probes, PSS/PSA admission.
- **Binding, Transport & Authentication Reachability (Assert Absence Only With Proof)**: A server object's constructor is not its security boundary. Never conclude that a server lacks authentication, is internet-exposed, or accepts remote connections from its constructor or module header alone — the transport, bind address, and loopback or token enforcement are typically applied at the launch site (`run_*`, `serve`, `main`, CLI entry points, lifespan handlers), which frequently sits hundreds of lines away or in another module and may fall outside the segment you were given. Before reporting such a finding, locate the actual launch path in the provided linked-file and symbol context and quote the binding it performs. A server defaulting to stdio, a loopback bind, or a guard that rejects non-loopback hosts unless an explicit opt-in flag is passed is not remotely exposed. If the launch path is not available to you, report the concern with that assumption stated in `invalidation_criteria` and a lower `confidence_score`, rather than asserting exposure.
