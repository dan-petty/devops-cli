Perform an in-depth code review on '{target}'.

### Code Review Rules:
- **Target Context**: Ground evaluations against the target project's declared conventions (`AGENTS.md`, `CLAUDE.md`, `README.md`) and universal software engineering principles (OWASP Top 10, CIS Benchmarks, SOLID) without imposing external host assumptions.
- **Falsification & Lockfile Verification**: Actively attempt disproof against target runtime idioms and authoritative lockfiles before reporting.
- **Report What You Can See**: You are shown part of the program. A control (authentication, validation, error handling, bounds, cleanup) may live in an entry point, caller or wrapper you were not given. Report a missing control only when the code in front of you shows the path that needs it and where it belongs. Before reporting that code is missing or wrong, read the rest of the page: the guard, the `shutdown`, the `except` or the assertion may be a few lines away. If you cannot show it, return no finding.
- **Test Files**: A finding about a test itself is a test that cannot fail or does not check what its name says; quote the line. Literals, mocks, fixtures and fake credentials in tests are inputs, not secrets or attack surface, but a real credential or a genuine vulnerability in a test file is still a finding.
- **One Finding Per Root Cause**: Report each defect exactly once, at its root cause, and never file separate findings for multiple symptoms of a single underlying bug. If an unassigned attribute makes a shutdown path ineffective, that is one finding — not one for the unassigned attribute, one for the ineffective shutdown, one for the un-joined thread, and one for the leaked resource. Enumerate the downstream consequences inside that single finding's description instead. Distinct defects that merely share an enclosing function remain separate findings.
- **Narrowest True Location**: Anchor `location` (`path/to/file.ext:start-end`) to the specific lines that must change, not the enclosing block, class, or whole file. Whole-file ranges (`file.py:1-250`) are only acceptable when the defect genuinely is the file's overall structure.
- **Line Numbers**: Each line of the file starts with its line number and a tab, counted from the top of the whole file on every page. Cite those numbers in `location`, and never copy them into quoted code or a fix. In a diff, a removed line has no number.
- **Fix Is Code**: Every finding carries a `fix` containing the corrected code for the cited lines; a fix that says to verify, ensure, consider or review means there is no finding. Use raw strings (`r'...'`) for regular expressions and path patterns containing backslashes.
- **Never Declare A Symbol Unused Or Dangling From Its Declaration Site**: Help strings, constants, message catalogues, enum members, and configuration defaults are declared in one module and consumed in another. Before reporting that a declaration is unused, orphaned, or references something that "does not exist", find the consuming call site in the provided context. When the consumer is not available to you, omit the finding.
- **Suggestions Are Not Findings**: Improvements that fix no defect belong in `summary`, never in `findings`.
