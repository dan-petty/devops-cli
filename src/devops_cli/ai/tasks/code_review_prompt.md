Perform an in-depth code review on '{target}' using the '{persona}' persona.

### Core Review Mandates:
- **Target Context**: Ground evaluations against the target project's declared conventions (`AGENTS.md`, `CLAUDE.md`, `README.md`) and universal software engineering principles (OWASP Top 10, CIS Benchmarks, SOLID) without imposing external host assumptions.
- **Falsification & Lockfile Verification**: Actively attempt disproof against target runtime idioms and authoritative lockfiles before reporting. Distinguish production code from test fixtures, mocks, or sample configurations.
- **Remediation & Hygiene**: Output structured JSON citing exact canonical locations (`path/to/file.ext:start-end`), minimal drop-in fixes, and isolated verification criteria.
- **One Finding Per Root Cause**: Report each defect exactly once, at its root cause, and never file separate findings for multiple symptoms of a single underlying bug. If an unassigned attribute makes a shutdown path ineffective, that is one finding — not one for the unassigned attribute, one for the ineffective shutdown, one for the un-joined thread, and one for the leaked resource. Enumerate the downstream consequences inside that single finding's description instead. Distinct defects that merely share an enclosing function remain separate findings.
- **Narrowest True Location**: Anchor `location` to the specific lines that must change, not the enclosing block, class, or whole file. Whole-file ranges (`file.py:1-250`) are only acceptable when the defect genuinely is the file's overall structure.
- **Segment Boundary Honesty**: You are shown a bounded segment of each file, not the entire program. Never assert that a control is *absent* — authentication, validation, error handling, bounds checking, cleanup — when the code that would establish it (entry points, callers, wrappers, factory or `run_*`/`main` functions) lies outside the segment you were given. Before reporting any "missing X" finding, confirm X is genuinely absent using the linked-file and symbol context provided. If you cannot confirm it from the material in front of you, either omit the finding or state the unchecked assumption explicitly in `invalidation_criteria` and lower `confidence_score` accordingly. An unverifiable suspicion reported as a CRITICAL finding is a defect in the review, not in the code.
- **Mandatory Concrete Fix**: Every finding must carry a non-empty `fix` containing the actual corrected code or a precise, mechanical change description. A finding without a fix is not actionable and must not be emitted.
- **Never Declare A Symbol Unused Or Dangling From Its Declaration Site**: Help strings, constants, message catalogues, enum members, and configuration defaults are declared in one module and consumed in another. Before reporting that a declaration is unused, orphaned, or references something that "does not exist" — a help string for a missing command, an unused import, a dead constant — you must find the consuming call site in the provided context. Absence of the consumer from your segment is not evidence of its absence from the codebase. When the consumer is not available to you, omit the finding.
- **Forward-Looking Suggestions**: Proactively identify forward-looking architectural enhancements, useful features, and meaningful integrations that can advance the codebase, formulating them as actionable suggestions for the roadmap (`docs/ROADMAP.md`).
